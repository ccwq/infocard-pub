Failover 复盘

CLIProxyAPI 多 Provider 聚合时，为什么配置了 round-robin 仍然不自动切换？422 为什么导致请求直接结束？

HTTP 状态码 = 错误分类信号 422 = Terminal Error 429 = Quota / Suspend Streaming 特殊陷阱 request-retry ≠ HA
核心结论

CPA Failover 不是"任意失败就切换下一渠道"，而是先判断失败类型：credential/provider 故障才接力，request 本身错误（400/422 等）默认不接力。这意味着多 Provider 不等于任意错误下的高可用。

02
HTTP 状态码 = 错误分类信号
HTTP 状态码CPA 分类是否可能接力说明
429Quota / Suspend✅ 正常接力标记 quota exceeded → suspend → 选择下一个 Credential
403Retry / Cooldown✅ 接力进入 retry 路径，换 Provider
408Retry / Cooldown✅ 接力超时，进入 retry
500Retry / Cooldown✅ 接力服务端错误，进入 retry
502Retry / Cooldown✅ 接力网关错误，进入 retry
503Retry / Cooldown✅ 接力服务不可用，进入 retry
504Retry / Cooldown✅ 接力网关超时，进入 retry
400Terminal（v6.8.55 及之前）❌ 不接力v6.9.33+ 已修复为 502，issue #1082
422Terminal❌ 默认不接力默认视为 Request 本身非法，不进入 retry
404Terminal❌ 通常不接力视为请求错误，换渠道不一定解决
409Terminal❌ 通常不接力冲突，通常是请求本身问题

关键：HTTP Code 同时承担"这是不是 Provider 故障"的信号
Credential / Provider 故障
→ 标记 Cooldown → 选择下一个 Credential
429/403/5xx 通常落入此类
Request 本身可能有问题
→ 不要盲目重放 → STOP
400/422/409/404 通常落入此类
为什么会这样设计

盲目 Failover 对合法请求也可能全失败

假设请求本身非法
A(422) → B(422) → C(422) → D(422) → E(422)
五个 Provider 全失败，延迟成倍，浪费资源
副作用风险
重复 Tool Calling（Streaming 场景）、错误 cooldown 正常 Credential
高并发场景下可能制造 retry storm
04
422 根因 · Provider 兼容性问题
典型案例 · gpt-5.6-terra → xAI / grok-4.6
# CPA 将 gpt-5.6-terra 映射为：
provider = xai
model = grok-4.6

# xAI Responses 兼容层转换后，上游返回：
HTTP 422
Failed to deserialize the JSON body into the target type:
data did not match any variant of untagged enum ModelInput

# CPA 决策：
422 → Terminal → STOP
# 同 Request ID 后续没有出现其他 Provider
❌ 错误归因
"Grok 返回 422，所以 Grok 不支持 Failover"
"Provider A 不行，所以整个多渠道没生效"
✅ 正确归因
422 被 CPA 分类为 Request Error → 不进入 retry
xAI 返回 422 ≠ 所有 Provider 都返回 422
OpenAI-compatible 可能接住同一请求 → 应该 failover
05
Streaming 特殊陷阱
v6.8.55 旧版本 Bug

Streaming bootstrap 错误返回 nil 导致不切换

问题
executeStreamWithModelPool 在最后一个模型遇 bootstrap 错误时，将错误包装进 StreamChunk channel 并返回 (result, nil)
nil error → caller 认为是成功 → 不旋转到下一个 Credential
触发条件
空 Stream、context canceled、连接在发送任何数据前关闭
issue #2189：Empty SSE / context canceled / Undefined error 均不触发 failover
v6.9.33+ 已修复

Streaming 透明 Failover 的合理限制

第一个有效字节发给客户端前
→ 可以安全重试
bootstrap 阶段，客户端未收到任何数据
已向客户端输出后
→ 原则上不能透明 Failover
可能出现两个不同模型输出拼接，或重复 Tool Calling 副作用
06
无 HTTP Code 的错误 · 分类盲区
错误类型HTTP CodeCPA 行为备注
DNS failure—❌ 分类盲区无 Status → 无法进入 Retry 路径
TLS failure—❌ 分类盲区同上
Connection reset—❌ 分类盲区同上
Context canceled—❌ 分类盲区v6.9.33+ streaming 路径已修复
Empty SSE200⚠️ 特殊处理HTTP 200 但 SSE 内含 server_is_overloaded
❌ 错误认知
request-retry: 10 = 任何失败最多重试 10 次
多 Provider + round-robin + request-retry = 高可用
✅ 正确认知
request-retry 只对 Retry 类型错误生效
真正 HA = 候选池还有 Provider 能完成请求，就找到它
CPA 当前不提供这个语义保证
07
现有补救机制 · request-scoped-errors
YAML 配置示例
# 针对特定 422 + Body 精确匹配才 continue（更安全）
request-scoped-errors:
  - status: 422
    match:
      - "ModelInput"
    action: continue

# 语义：422 + 响应包含 ModelInput → Provider 不兼容 → 尝试下一个
# 其他 422（如 invalid request）仍然 STOP

# 对比：全局 422 继续（风险较高）
request-scoped-errors:
  - status: 422
    action: continue
