Agent Trace：让 Agent 执行可观察、可复盘、可审计

不只记录“做了什么”，还要让一次执行能够被理解、回看、重放，并对关键事实与副作用留下清晰边界。

OBSERVE / REPLAY / AUDIT
01 / CORE

先把问题说清楚

生产 Agent Runtime 是否应采用 ATIF 或其他 Agent Trace 格式，仍处于标准化讨论之中。现阶段可能存在各自实现、缺乏统一标准的情况。

核心概念：Agent Trace 是围绕一次 Agent 执行形成的可理解记录。它的价值不在于“日志更多”，而在于让执行过程具备连续上下文与可检查的证据链。
01 · OBSERVE

执行可观察

能看见工具调用、关键决策与执行阶段，而不是只看到最终输出。

02 · REVIEW

过程可复盘

能沿着时间顺序回看成功、失败与转向，理解结果是怎样形成的。

03 · AUDIT

结果可审计

能区分外部事实、系统动作与副作用，为后续检查保留边界。

02 / TRACE MAP

一条 Trace 至少要连起三层

输入与上下文任务目标、执行环境与可用上下文。重点是让回看者知道 Agent 当时“基于什么开始”。
→
过程与转折工具调用、决策、失败步骤与后续动作。重点是让过程不被最终答案遮蔽。
→
事实与影响外部事实、副作用、最终结果与可重放信息。重点是区分“观察到的”与“执行产生的”。
03 / DESIGN

实践问题 / 设计要求

以下不是对原文已证明事实的复述，而是围绕可观察、可复盘、可审计目标提出的工程设计问题与要求。

01

工具调用是否可定位？

每次调用应能放回执行顺序中：调用了什么、处于哪一步、产生了什么返回或异常。

02

决策是否能被解释？

不要只保留动作结果；应保留足以理解关键转向的决策上下文，避免过程成为黑箱。

03

失败步骤是否被保留？

失败不是噪音。应记录失败发生的位置、后续如何处理，以及失败是否改变了最终路径。

04

事实与副作用是否分层？

外部事实、Agent 推断、工具返回和实际副作用不应混成一段无法核对的文本。

05

执行能否重放？

应明确哪些信息支持重放，哪些外部条件会变化，以及重放结果与原执行如何对照。

06

审计边界是否明确？

应能回答谁、何时、基于什么上下文、调用了什么、造成了什么影响，并保留必要证据。

04 / REVIEW LOOP

用五个问题做一次 Trace 走查

看见了吗？工具调用与执行阶段是否可见？
解释得通吗？关键决策与路径转折是否有上下文？
失败丢了吗？失败步骤与恢复动作是否仍在记录中？
影响分清吗？事实、推断与副作用是否有边界？
能重放吗？回看、对照与审计需要的材料是否齐全？
结论：Trace 不是装饰性日志，而是执行理解与责任边界的工程接口。
