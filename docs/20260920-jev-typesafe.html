01 · RLCD：Jev 的核心创新

维度RLHFRLCD（Jev）
优化目标 人类偏好（subjective preference） 概率校准度（Calibration）：模型说 70% 有把握时，实际正确率也约 70%
训练信号 人类评分 / 偏好对比 输出答案之间的对比反馈（comparative feedback）
模型输出 自然语言（自由生成） 固定 Schema（调用者预定义结构，无法返回非法值）
延迟量级 3–329 秒（逐 token 生成） 70–500ms（并行输出所有答案）
适用任务 对话 / 生成 / 创意 判断型任务（判断 → 执行）

RLCD 技术细节

• 并行生成：不是逐 token 预测，而是在单次查询中并行输出所有候选答案

• 固定 Schema：调用者预定义输出结构，模型无法返回非法值，输出可直接驱动程序执行

• confidence 计算：选项数为 n 时，confidence = 最高概率与均匀分布的距离（1/n）

• 自动化路由：低置信度 → 自动 Escalation；高置信度 → 自动执行

Calibrated 的含义：概率校准（Calibration）≠ 准确率。模型可以在低校准下高准确，也可以在高校准下低准确。RLCD 训练模型对自身置信度诚实，使置信度值可以直接用于决策路由。

02 · System One：Kahneman 认知框架

⚡ System One（直觉系统）

快速、自动、低认知负荷的直觉判断——看见数字 2+2 即知等于 4，无需推理。Jev 定位：AI 领域的 System One，毫秒级完成判断。

慢速、审慎、逻辑推理——用于复杂计算、规划与创造性问题解决。传统 LLM（GPT-4、Claude）属于 System Two 类。

08 · 三种问题类型：Choice / Noul / Score

🔘 Choice（单选）

从预定义选项列表中选出一个最合适的。返回：首选答案 + 各选项概率分布 + 置信度分数。

{
  "type": "choice",
  "instructions": "Which action?",
  "criteria": {
    "click": "Click this element",
    "skip": "Skip to next",
    "cancel": "Cancel operation"
  }
}

⚖️ Noul（布尔）

返回是/否概率（0~1）。等价于二元选择题，但更简洁，适合前置校验。

{
  "type": "noul",
  "instructions": "Is this a login button?"
}

📊 Score（评分）

对某个属性在连续标尺上评分（0~N 范围）。返回期望值 + 各刻度概率分布 + 置信度。适合质量评估、优先级排序等需要量化的场景。

{
  "type": "score",
  "instructions": "How urgent?",
  "criteria": [
    "0: Not urgent, can wait days",
    "1: This week",
    "2: Today",
    "3: Immediately"
  ]
}
Confidence ≠ 概率最大值：Choice 中 confidence 衡量的是"最高概率选项比均匀分布高出多少"。例如三选项时，概率 0.8 对应 confidence = 0.8 - 1/3 = 0.47。Confidence 反映的是模型对自身判断的确信程度，而非绝对概率。

10 · 开源替代：SemIf / OpenJev / Decider

Jev 的方法并非全新——它在分类（Classification）、校准（Calibration）和选择性预测（Selective Prediction）研究基础上做了工程整合。以下开源项目用现有模型复现了部分能力：

项目方法特点GitHub
SemIf 选择性预测 + 置信度路由 低置信度样本交给更强模型，高置信度走轻量路径 开源可复现
Bespoke Nimble 任务自适应分类器 针对特定领域微调，比通用模型更快更准 开源可复现
OpenJev 复现 Jev API 协议 兼容 Jev SDK 的开源实现，可用自有 LLM 提供商 社区驱动
Decider 约束解码 + 校准后训练 在开源 LLM 上实现结构化输出 + 概率校准 研究代码
注意：开源替代在特定窄任务上效果接近 Jev，但 Jev 的优势在于"通用 + 预训练好的判断能力"，无需自己准备训练数据或微调。开源方案更适合有专项数据积累的团队。

12 · 置信度路由：让决策自动化

Jev 的置信度分数（confidence）可直接驱动自动化路由，这是它区别于普通 LLM 的关键能力：

置信度门控（Confidence Gate）

result = await client.jev({
  state: { ticket: "I need help with billing" },
  questions: {
    intent: {
      type: 'choice',
      instructions: 'Classify customer intent',
      criteria: {
        billing: 'Billing or payment related',
        technical: 'Technical support',
        sales: 'Pre-purchase inquiry',
        other: 'Everything else'
      }
    }
  }
})

confidence = result.answers.intent.confidence

if confidence > 0.85:
    # 高置信度：自动处理
    auto_route(intent)
elif confidence > 0.5:
    # 中置信度：人机协作
    escalate_to_agent(result)
else:
    # 低置信度：人工处理
    queue_human_review()

分层路由（Tiered Routing）

# 第一层：Jev 毫秒级判断（$0.00001/次）
if jev.quick_judge(state).confidence > 0.9:
    execute()  # 自动执行
else:
    # 第二层：LLM 深度分析（$0.01/次）
    llm_response = await llm.analyze(state)
    if llm.confidence > 0.7:
        execute(llm_response)
    else:
        escalate()  # 最终兜底人工

这种分层架构可以在保持高自动化率的同时，把成本控制在 LLM 全程使用的 5%~10%。

14 · 局限性诚实评估

✗ 不能做什么

• 不生成自由文本、代码、文章
• 不做开放式对话
• 不处理需要多步推理的复杂任务
• 无法自我判断"这个问题适不适合用 Jev"

⚠ 需要注意的

• Early Access：需要排队，稳定性不如大厂 API
• 暂无独立第三方校准可靠性报告
• confidence 阈值需要在自己的数据集上调优
• 跨语言（非英文）场景效果待验证

关于「幻觉」：Jev 不会产生文本幻觉（因为不生成文本），但会产生"判断幻觉"——对不了解的领域给出高置信度的错误答案。使用前请在自己真实数据上做一次校验。

16 · Computer Use 集成：Jev 作为操作判断层

Jev 最热门的用法是作为 Computer Use（AI 操作电脑）的判断节点。当 AI Agent 需要在网页上点击按钮时，传统方案让 LLM 判断"应该点哪个"，Jev 则提供毫秒级、结构化的操作决策：

Browser Use + Jev 流水线

# 1. 获取页面 DOM 结构
dom = get_page_dom()
# → {"elements": [{"id": 1, "tag": "button", "text": "Submit"}, ...]}

# 2. Jev 判断应该操作哪个元素
result = await jev({
  state: {
    goal: "Complete the checkout payment",
    dom_elements: dom["elements"]
  },
  questions: {
    action: {
      type: 'choice',
      instructions: 'Which element should the agent interact with next?',
      criteria: {
        submit_btn: 'Primary submit button with id=submit or type=submit',
        back_btn: 'Back navigation button',
        cancel_link: 'Cancel or abandon checkout link',
        other: 'None of the above'
      }
    }
  }
})

# 3. 置信度高 → 自动执行，低 → 人工确认
if result.answers.action.confidence > 0.85:
    execute_action(result.answers.action.choice)
else:
    require_human_confirmation()

✓ 优势

• 延迟从 LLM 的 3~30s 降到 100ms 以内
• 成本降低 40~400 倍
• 输出结构化，不会返回"我觉得应该点这个"
• 可批量处理多步决策

⚠ 限制

• 需要提前定义"选项列表"（criteria）
• 对复杂上下文理解不如 LLM
• 需要 DOM 解析作为 state 输入
• 不适合开放式探索任务

17 · 批量处理：MapReduce 架构

Jev 的并行输出 + 固定 Schema 使其天然适合大规模批量判断任务。以下是 daf-jev 工具包的并发评估器实测数据：

并发评估器（Concurrent Corpus Evaluator）

import asyncio
from daf_jev import ConcurrentEvaluator

evaluator = ConcurrentEvaluator(api_key=api_key, concurrency=50)  # 并发 50 个请求

# 批量判断 10,000 封邮件的优先级

18 · API 参数详解

参数类型必填说明
model string ✓ jev-latest（稳定版）或 jev-preview（预览版）
state object ✓ 任意 JSON 对象，Jev 据此做出判断（可以是页面 DOM、表单数据、日志行等）
questions object ✓ 问题映射，键为问题 ID，值为问题定义（type + instructions + criteria）
version_id string 返回本次请求使用的具体模型版本 ID（如 jev-1.13.0），建议在生产环境记录并固定
Question Type字段说明
noul instructions 是/否问题，返回 0~1 概率
choice instructions + criteria 单选，criteria 为 dict（键为选项标识，值为描述）或 list（自动编号 0~N-1）
score instructions + criteria 评分，criteria 为 list[N+1]，返回期望值（0~N 之间）

21 · 常见问题与避坑

问题答案
版本别名（alias）和版本 ID 该用哪个？ 生产环境建议记录并固定 jev-1.13.0 这类版本 ID，而非 jev-latest，避免模型更新导致行为变化。
单次调用最多能问多少个问题？ Jev 支持最多 255 个选项（choice cardinality），问题数量无明确上限，但建议不超过 20 个以保持响应速度。
Noul 和二元 Choice 哪个更好？ Noul 更简洁（无需定义 criteria），返回 0~1 概率；Choice 有概率分布和置信度。在意置信度分数时用 Choice，只做简单布尔判断时用 Noul。
网络延迟对 70ms 延迟影响大吗？ TypeSafe 服务位于美国西部。从欧洲访问额外增加 ~100ms 延迟。敏感场景建议实测后再做 SLA 承诺。
如何判断 Jev 适合我的场景？ 问自己：这个任务可以提前定义"可能的答案集合"吗？答案可以用概率表示吗？如果都是 yes，Jev 很可能适用。
Output tokens 免费意味着什么？ Jev 的输出是固定大小的结构化数据（JSON schema），而非自由文本，因此无法按 token 计费。这让高频调用场景成本可控。

import os, asyncio
from jev import JevClient
from state_schema import TicketState, QUESTIONS

client = JevClient(api_key=os.getenv("TYPESAFE_API_KEY"))

async def route_ticket(ticket: TicketState) -> dict:
    """返回路由决策 + 置信度"""
    result = await client.jev(
        model="jev-latest",
        state=ticket.model_dump(),
        questions=QUESTIONS
    )

    answers = result["answers"]

    # 置信度路由：低置信度 → 人工复核
    dept_confidence = answers["department"]["confidence"]
    priority_score = answers["priority"]["score"]

    return {
        "department": answers["department"]["choice"],
        "priority": priority_score,
        "is_escalation": answers["is_escalation"]["probability"] > 0.5,
        "confidence": dept_confidence,
        "auto_route": dept_confidence > 0.8 and priority_score < 2,
        "notes": f"Confidence={dept_confidence:.2f}"
    }

# 使用示例
ticket = TicketState(

    sender_email="ops@techcorp.io",
    sender_tier=4,
    has_attachment=True,
    previous_tickets=3,
    time_since_last=2
)
decision = asyncio.run(route_ticket(ticket))
print(decision)

23 · 置信度校准：如何调优阈值

Jev 的 confidence 分数在出厂时已校准，但不同业务场景的"可接受错误率"不同。以下是系统性调优方法：

Step 1：收集标注数据

# 用历史工单构建测试集（每个工单有人工标注的正确答案）
test_corpus = [
    {"state": {...}, "ground_truth": {"department": "technical", "priority": 2}},
    ...
]

Step 2：批量评估

from daf_jev import CalibrationAnalyzer

analyzer = CalibrationAnalyzer()
results = analyzer.evaluate_corpus(
    corpus=test_corpus,
    questions=QUESTIONS,
    confidence_thresholds=[0.5, 0.6, 0.7, 0.8, 0.9]
)

# 输出每个阈值下的：精确率、召回率、自动通过率
for threshold, metrics in results.items():
    print(f"Threshold {threshold}: precision={metrics['precision']:.2%}, "
          f"recall={metrics['recall']:.2%}, auto_pass={metrics['auto_pass']:.2%}")

Step 3：选择最优阈值

# 典型输出示例（基于 1000 张工单测试集）
# Threshold 0.50: precision=71%, recall=95%, auto_pass=78%
# Threshold 0.70: precision=83%, recall=82%, auto_pass=59%
# Threshold 0.80: precision=91%, recall=71%, auto_pass=44%
# Threshold 0.90: precision=96%, recall=55%, auto_pass=28%

# 决策：
# • 追求高自动化率（不在乎偶发错误）→ 0.70
# • 平衡精度和覆盖率 → 0.80
# • 不能容忍错误（金融/安全场景）→ 0.90
阈值策略适用场景预期自动通过率
0.5（低门槛） 高吞吐量、低错误成本（垃圾邮件分类） ~80%
0.7（平衡） 一般业务工单，推荐默认值 ~60%
0.8（稳健） 中等容错能力（大多数 B2B 场景） ~45%
0.9（严格） 金融、医疗、法律等零容忍场景 ~25%

metrics = JevMetrics(prefix="jev_production")

@app.middleware
async def track_jev_metrics(request, call_next):
    start = time.time()
    result = await call_next(request)
    latency_ms = (time.time() - start) * 1000

    metrics.observe("latency_ms", latency_ms)
    metrics.observe("confidence", result["answers"]["..."]["confidence"])

监控指标告警阈值建议含义
jev_latency_p99 > 500ms 99% 请求延迟超过 500ms = 服务异常或限流
jev_confidence_avg < 0.6（持续 10 分钟） 模型整体不确信，可能 state 格式变化
jev_error_rate > 1% API 错误率异常
jev_cost_per_day > 预期值 2x 可能有人滥用或 state 过大
jev_auto_route_rate < 30% 或 > 90% 太低 = 置信度阈值太高；太高 = 可能过度自动化

置信度漂移检测

# 监控 confidence 分布是否随时间变化（分布漂移 = 模型能力退化）
import numpy as np
from scipy.stats import ks_2samp

def detect_confidence_drift(reference_confidences, current_confidences, alpha=0.05):
    """Kolmogorov-Smirnov 检测置信度分布是否漂移"""
    stat, p_value = ks_2samp(reference_confidences, current_confidences)
    if p_value < alpha:
        alert(f"⚠️ Confidence drift detected! KS stat={stat:.3f}, p={p_value:.4f}")
        return True
    return False

# 每周运行一次
detect_confidence_drift(
    reference_confidences=week_1_confidences,
    current_confidences=week_2_confidences
)

26 · 从 LLM 判断迁移到 Jev 检查清单

如果你的系统当前用 LLM 做判断决策，以下检查清单帮你评估迁移可行性：

检查项评估方法通过标准
答案空间可枚举 能否列出所有可能的答案？ 选项 ≤ 50 个，且答案互斥
State 可结构化 判断依据能转为 JSON 吗？ 每条记录的 state < 4096 tokens
误差容忍度 错误分类的后果是什么？ 低风险或有人工复核兜底
调用量 每天多少次判断？ Jev 在 > 1000 次/天时成本优势明显
延迟要求 能接受 < 1s 响应吗？ Jev 70ms，远低于 LLM 的 3~30s
离线测试覆盖 有历史标注数据吗？ 至少 100 条，覆盖各答案类别
渐进式上线 能否先灰度后全量？ 置信度 > 0.9 才自动路由，其余人工
不要迁移的场景：涉及多步推理、开放式生成、法律/医疗高风险决策、答案空间无法枚举的判断。这些场景 LLM 仍是最佳选择。
