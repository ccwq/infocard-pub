F

不是 Vibe Coding

不是换一个更聪明的编辑器，而是重新设计“人如何让 Agent 建设软件”的工程系统。

把开发者从打字员变成 Agent 系统架构师

当 Agent 能自主写代码、跑测试、修失败并连续工作更长时间，速度的关键不再是你打字多快，而是你是否给它清楚的方向、足够的上下文、快速的反馈和不可越过的边界。

人定方向

定义 done、约束、验收标准和不可接受的结果。

Agent 执行

实现、运行验证、读取失败并在边界内自我修正。

系统守质量

代码库、测试、权限和配置让闭环不依赖人盯屏。

官方提醒：这是工程投资，不是开关。前期可能更慢；只有上下文、反馈和任务分解逐步成熟后，收益才会复利。
01

先改角色：你负责写意图，不是代替 Agent 打字

Frontier Engineering 的第一条不是“少写代码”，而是改变责任分工。人类需要写清楚系统要做什么、什么不能做、什么算完成，以及如何验证。Agent 可以产出大部分实现，但它不会自动知道你的业务边界、架构偏好和风险容忍度。

模糊请求可执行意图验收证据
给 API 加认证列出角色、端点权限、令牌过期、未授权响应和刷新策略权限矩阵、过期测试、未授权集成测试
优化这个页面明确首屏任务、目标设备、内容优先级和可接受的性能指标浏览器截图、键盘路径、性能记录
修好这个 bug给出复现输入、预期行为、影响范围和回归条件回归测试、失败前后日志、最小 diff
第一份产物不是代码：先写完成定义、约束和验收命令，再让 Agent 选择实现方案。
02

让 Agent 连续工作：把验证写进长任务

典型低效循环是：提示一次、等待、手动测试、把错误贴回聊天。长任务的区别不是提示词更长，而是任务合同已经包含自我验证步骤和失败处理。Agent 应该能执行实现、写测试、运行测试、读错误、修正并再次验证。

实现“导出报告”功能，并持续工作到闭环：
1. 先阅读相关模块和现有测试，列出假设；
2. 写出需求、边界和验收标准；
3. 实现最小垂直切片；
4. 添加单元测试和至少一条集成测试；
5. 运行 lint、类型检查、测试和构建；
6. 若失败，读取真实输出并修复，不要绕过检查；
7. 最后给出变更文件、验证命令和未解决风险。

并行 Agent 或后台 Agent 只有在任务边界清楚时才有意义。每个任务都需要独立工作范围、依赖关系、交付格式和停止条件；否则并发只会放大冲突与重复劳动。

03

把代码库变成 Agent 的上下文基础设施

人类新成员通常只需入职一次；Agent 每次会话都要重新理解项目。因此 README、架构文档、模块边界、强类型、快速构建和信息丰富的错误，不是“文档卫生”，而是每次 Agent 运行都会产生回报的基础设施。

01Steering files：项目规范、禁区、命名和完成标准。
02Skills：按需加载的操作流程和领域知识。
03Scripts：重复的环境准备、检查和修复自动化。
04CLI / MCP：让 Agent 能取上下文、执行受控动作。
05Decision log：保存设计选择和背后的 why。

面对遗留大库，不要让 Agent 一次理解所有模块。先准备一个模块，定义允许触碰的范围和局部验收，再逐步扩大。上下文不是越多越好，而是要能支撑当前决策并避免无关噪声。

最小仓库准备清单

  • README：如何启动、如何验证、常见失败如何解释。
  • 架构入口：模块关系、边界、数据流和不能绕过的契约。
  • 测试入口：一条命令跑核心测试，失败输出可定位。
  • 变更规则：哪些目录可改，哪些文件必须人工确认。
  • 决策记录：为什么选这个 API、依赖或数据模型。
04

反馈回路：在你看代码前，让 Agent 先证明自己

如果 Agent 不能在本地运行测试并根据结果修正，人类就成了验证瓶颈。凡是你验证工作时会用的工具，Agent 也应能在受控环境中使用：linter、类型检查、单元测试、浏览器、依赖服务 mock 和完整技术栈。

示例测试只回答一件事

“输入 1 得到 2”能证明一个样例，但不能证明边界。适合检查具体 API 约定和回归案例。

属性测试回答不变量

无论输入如何变化，排序结果保持有序、权限不会越界、序列化再解析仍保留关键性质。

浏览器视觉验证也属于反馈回路：UI Agent 不应只看构建成功，还要读取 DOM、截图、检查移动端和确认关键交互。反馈越快，Agent 越能在错误成本变高之前收敛。

验收顺序：先机械检查，再行为测试，再浏览器/视觉检查，最后由人判断架构、产品意图和风险。
05

执行变便宜后，把注意力移到方向与规格

当一个下午就能生成实现，昂贵的部分变成系统设计、API 契约、依赖关系和架构取舍。Frontier Engineering 建议把 Agent 当成头脑风暴伙伴：让它调研方案、找反例、探索替代路径；当两个方案都合理时，让它各做一个可丢弃原型，用证据代替争论。

规格先行：报告导出 v1
目标：用户可以把筛选后的报告导出为 CSV。
不做：PDF、定时任务、跨租户共享。
约束：导出只能读取当前用户有权限的数据。
失败：无数据、超时、部分字段为空时必须给出可恢复提示。
验收：权限集成测试、空结果测试、10000 行性能测试、浏览器下载验证。
决策：先实现同步导出；超过阈值时返回异步任务，不在 v1 隐式引入队列。

规格不是为了让 Agent 无法发挥，而是把高代价的持久性决策显式化，避免模型用一段看似合理的实现替你决定系统未来。

06

实现可丢弃，但系统契约不能丢

生成成本下降后，原型可以更快做、更快扔。真正危险的是把“代码可重写”误解成“行为不需要守护”。每次重写仍要满足系统边界上的契约：

  • 端到端集成测试：验证真实行为、服务边界和关键用户路径。
  • 属性测试：验证不变量，捕捉显式样例覆盖不到的边界。
  • 负载测试：验证规模、延迟、资源消耗和退化方式。

因此安全的推倒重来需要两层分离：内部实现可以删除，外部行为和风险契约必须保留。把测试、数据迁移和回滚策略当作重写的门槛，而不是事后补丁。

07

以人类标准要求 AI：责任一直延伸到生产

凡是署你之名上线的代码，无论是谁写的，你都要负责。可以从逐行审查开始，逐渐把重复检查交给 AI reviewer 和 CI，但人的注意力应集中在最难自动化的判断：架构是否正确、变更如何影响上下游、安全边界是否完整。

阶段Agent 可做人必须确认
本地lint、测试、类型、代码审查建议实现是否符合意图，是否引入隐性取舍
PR/CI重复扫描、风险分类、测试质量检查是否合并、是否需要改规格或架构
部署监控、回归探测、自动创建修复任务生产权限、回滚、不可逆数据操作

PR 合并不是责任终点。生产验证、监控、回归发现和修复闭环都应属于交付定义的一部分。

08

信任边界：信任护栏，不是信任 Agent

让 Agent 长时间运行，不应依赖它“本性可靠”。应从最小权限开始，只给它需要的文件、工具、网络和凭证；随着证据积累逐步放宽。生产账号和部署凭证默认不提供，无法撤销的操作保留人工确认。

自动化护栏

  • SAST 与依赖漏洞扫描
  • 凭证/密钥扫描
  • 文件系统和网络 allowlist
  • 类型、契约和属性检查

人工红线

  • 生产部署与数据删除
  • 凭证写入和权限升级
  • 不可逆迁移与外部发送
  • 无法回滚的架构变更
安全判断：每自动化一道可重复护栏，就少一个必须留在监督循环中的理由；但不可逆操作不能因为“Agent 已经通过测试”就自动放行。
09

同一套方法可以扩展到代码之外

文档、运维调查、状态更新、冲刺总结和值班报告都可以采用同一模式：提供上下文、定义期望结果、让 Agent 起草、通过反馈回路审查和打磨。关键是共享 steering files、工具约定和交付格式，而不是让每个 Agent 都拥有一套互相冲突的标准。

任务输入上下文验收结果
运维调查日志、时间窗、服务拓扑、假设根因证据、影响范围、复现或排除记录
文档更新代码、接口、读者和版本示例可运行、术语一致、链接有效
值班报告告警、时间线、操作记录事实、决策、未决风险和后续动作
10

持续调优：每次错误都要变成系统资产

Frontier Engineering 的收束原则是把 Agent 配置视为活的工程产物。每当 Agent 走错方向、漏掉验证或把你拉回手工流程，都要追问：怎样让同类错误下次更难发生？答案可能是一条 steering 规则、一个 skill、一段脚本、一个 MCP 工具、一个测试，或者一条被证明过严的权限规则。

发现记录 Agent 做错了什么，以及你如何发现。
定位判断是上下文缺失、反馈太慢、权限不当还是规格含糊。
固化把修复放进规则、测试、脚本或工具，而不是只提醒自己。
验证用代表任务确认新护栏真的阻止旧错误。
复评模型和代码库变化后，删除已经过时的 workaround。

最终目标不是让 Agent 永远不犯错，而是让错误更快被发现、更便宜地修复，并且每次修复都提高下一轮自主工作的可靠边界。

一周试行清单

  1. 选一个低风险、可自动验证的真实任务。
  2. 写完成定义、约束、验收命令和不可逆操作清单。
  3. 让 Agent 在隔离环境运行并自我修正一轮。
  4. 记录人类仍被迫介入的三个节点。
  5. 把其中一个节点固化为测试、脚本、skill 或 steering 规则。
  6. 下周用同类任务验证是否真正减少介入。
