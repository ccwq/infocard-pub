Frontier Engineering：把开发者从打字员变成 Agent 系统架构师

Kiro 团队 Clare Liguori 提出的十条工作原则：人定方向，Agent 执行 · 来源 kiro.dev/topics/frontier-engineering
执行顺序：先写意图规格，再给上下文，让 Agent 自主跑，人守验收红线
1写意图
2给上下文
3定反馈
4授权执行
5守红线

当 AI Agent 可以自主写代码、跑测试、修 bug、连续数小时不需人介入时，开发者的价值不再是敲代码的速度，而是把工程意图翻译成 Agent 可执行的规格。Frontier Engineering 十条原则描述的正是这个转变：它不是 vibe coding，而是一套需要持续投入的工程纪律。

先说边界：官方文章明确指出，前期建立规格、测试和工具链时速度会变慢；"手写代码低于 1%" 是个体案例描述，不是行业基准；长时自主运行仍需要人在关键节点监督。

01 把方向写成规格，而不是对话

人类负责定义方向、完成标准和不可逆决策；Agent 负责执行、测试和修正。关键机制是把"想做什么"写成可交给 Agent 的意图规格：目标、约束、非目标、验收标准。

你要给的形式质量判据
方向与完成标准意图规格 / task brief换一个工程师读也能判断做没做对
技术约束架构决策、非目标清单Agent 知道什么不该做
不可逆决策人工审批点发布、删除、付费等操作必须人签字
修正方向更新规格而非口头改后续会话可复用，不靠记忆

判断自己的规格是否合格：把规格交给没参与对话的同事或另一个 Agent，看能否独立判断"做对了没有"。不能，就继续补完成标准。

02 让代码库自己说明上下文

Agent 每次会话都是新人。上下文不靠聊天记录，而靠代码库里的持久文件承载：架构文档、目录说明、决策记录和约定。Kiro 用 steering files 表达"这个仓库怎么工作"，团队 skills 固化"这类任务怎么做"，scripts 与 CLI/MCP 把"怎么验证"变成可执行命令。

repo/
  .kiro/steering/          # 架构与约定：新会话先读
  .kiro/skills/             # 任务级 SOP：部署、迁移、发布
  scripts/                  # 可执行验证：build / test / lint
  docs/decisions/           # 关键决策与理由，供 Agent 引用

验收标准：新开一个空白会话，只说"按仓库约定完成 X"，Agent 能找到规格、约定和验证命令；如果它要靠你复述背景，说明上下文没有沉淀在代码库里。

03 建反馈回路，让 Agent 自己发现错误

Agent 能长时自主工作的前提是能自己判断对错。测试、类型检查、lint、本地运行、浏览器截图、mock 服务，都是给 Agent 的"传感器"。反馈越快、越确定，Agent 自主跑的时间越长、质量越稳。

单元 / 集成测试类型与 lint端到端验证CI 绿灯失败即停

给每类任务指定验证命令与通过标准，写入规格或 steering；Agent 每完成一步先跑验证再继续。没有可靠反馈回路的任务，不要授权长时自主执行。

04 规格驱动与可丢弃实现

方向性错误最贵。Frontier Engineering 的做法是：用规格驱动开发（SDD）先冻结行为，再让 Agent 并行产出 2–3 个候选实现做对比，好的留下，其余丢弃。丢弃的是代码，保留的是对问题的理解。

阶段产物丢弃成本
意图冻结规格 + 验收标准极低，只改文档
方案对比多个候选实现可控，Agent 生成
实现收敛选定实现 + 测试高，因此前面先收敛

原则：允许 Agent 大胆试错的前提是错误发生在便宜的阶段；进入生产路径的实现必须有测试与评审保护。

05 责任、权限与持续调优

生产责任始终在人：发布审批、事故处置、安全红线不可下放。信任边界靠机制建立——最小权限凭证、沙箱执行、分支保护、渐进授权：Agent 先在受控分支跑，验证记录积累后再扩大权限。

同一套方法可扩展到代码之外：文档、运维任务、值班报告都可以用"规格 + 上下文 + 反馈回路"的方式交给 Agent。最后一条原则是把每次失败固化：错误复盘后更新规则、测试、脚本或 skill，让 Agent 下次不再犯。这套体系的复利来自持续调优，而不是某次爆发。

一周试行清单：选一个中等任务写意图规格；把该领域约定沉淀进 steering；为它配一条可执行验证命令；让 Agent 在分支上自主完成一轮；人工只审规格与结果；把踩的坑写回规则。
