01
为什么这事大

设计系统从“口头传达”变成“机器可执行”

这份规范把设计意图分成两层：YAML 负责精确 token，Markdown 负责解释为什么。也就是说，AI 不再靠你反复描述“高级感 / 好看 / 稳重”，而是靠文件本身去消费规则。

前置格式

文件顶部是 YAML front matter，适合放 colors、typography、spacing、rounded、components 等 token。

正文是 Markdown prose，适合解释 brand tone、视觉理由、组件约束，以及“为什么是这个值”。

适合谁

  • 需要多人/多代理保持一致视觉语言的团队
  • 要把 design token 作为工程资产管理的人
  • 想把 UI 约束写成可 lint、可 diff 的项目
02
规范长什么样

一个 DESIGN.md = 机器能读的 token + 人能读的理由

Google 的示例直接给出 colors / typography / rounded / spacing / components 的 schema，并把 section order 固化成可解析的约束。它本质上是在告诉模型：什么是 norm，什么是 rationale，什么是能被导出的实施细节。

Colors

primary / secondary / tertiary / neutral，明确语义角色。

Typography

h1 / body / label 等级，fontFamily、fontSize、weight、lineHeight、letterSpacing 一起定。

Layout

网格、间距、安全区和节奏都可以写入 token 体系。

Components

按钮、chip、列表、input、tooltip 等组件能有可追踪的 token 映射。

03
工具链

lint / diff / export / spec，规范不是写完就算

Google 不是只发了个文档，而是给了完整 CLI：`lint` 检查结构、token、WCAG 对比度；`diff` 看 token 级变化；`export` 输出 Tailwind / DTCG JSON；`spec` 把规范本身吐给 Agent 用。规范直接进入工程循环。

npx @google/design.md lint DESIGN.md npx @google/design.md diff DESIGN.md DESIGN-v2.md npx @google/design.md export --format tailwind DESIGN.md npx @google/design.md export --format dtcg DESIGN.md

你说 → 我做

  • 你说“把 UI 做得好看点” → 我补 token，不补空话。
  • 你说“保持一致” → 我让 lint / diff 去守住它。
  • 你说“迁移到新项目” → 我导出 token，而不是重新讲一遍审美。
04
设计判断

AI 编程的“指示个人化”要结束了

这正是这份规范最强的信号：未来不该靠每次对话临时“指挥审美”，而应该靠设计契约持续执行。它把 UI 变成可版本化、可审计、可导出的工程输入。

“不是让 AI 记住你的偏好，而是把偏好写成文件。”
05
边界

它不是 Figma 替代品，而是设计契约

DESIGN.md 解决的是“如何让 agent 按同一套视觉语言做事”。它不替代设计稿、不替代交互评审，也不替代品牌策略；它只是把这些东西压缩成一个能被工具消费的、持续执行的规范文件。

优点

适合多代理协作、token 治理、风格迁移、设计一致性审计。

风险

如果 prose 写得空，token 再多也只是“漂亮但没方向”的词表。

落地方式

把 DESIGN.md 放进项目根目录，然后用 lint / export / diff 进入 CI 或本地检查。
