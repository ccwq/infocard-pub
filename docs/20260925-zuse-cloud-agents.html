01推文核查：11 条机制主张逐条对账

推文主张核查结果
封装 Claude Code、Codex、Grok、Gemini、Cursor、OpenCode 等到统一 GUI属实且保守：docs 的 Provider 表实列 7 个——还有 Kiro（kiro-cli，ACP 接入）；settings schema 里 defaultProviderId 枚举甚至有 9 个值（含 opencode2、pi）。推文漏列 2 个
SQLite 事件源持久化，会话/消息/轮次落盘，重开完整恢复逐字属实：SQLite 存 projects/sessions/messages/tool calls；cloud README 八条系统不变量第一条就是"workspace 运行时 SQLite 是聊天/会话/消息/轮次/队列/回执的唯一可写权威"
每聊天会话绑定独立 Git worktree，并行改同一仓库互不干扰属实：worktree 属于 chat，同 chat 的所有 session（跨 provider）共用同一 checkout+branch；@ 搜索、文件树、终端、Changes/commit/PR 全部 scoped 到该 checkout
云端工作区：桌面关掉继续跑，手机（Expo 推送）审批属实：cloud README 原话"关闭应用、合上笔记本、换网络，都不会终止已被接受的 agent turn"；Phase 1 的 Expo push（PR-H #272）发五类事件（approval-needed/completed/error 等）
Provider 双平面：管理平面共享池、会话平面独占进程逐字属实：管理平面按配置键租用/单飞缓存/空闲回收；"startup 超时必须拒绝挂起请求，不得留下中毒池条目"为文档原话
单一数据流：命令→SessionDomain→SQLite→游标→运行时→ClientBus→UI逐字属实：realtime-runtime.md 给出同一条 7 步链路
WebSocket 可抛弃；断连重连先画缓存再追补（512 事件/1 MiB 上限）逐字属实："A client WebSocket is disposable"为原文；追补上限 512 events / 1 MiB 精确命中
DO 只做"不透明字节路由器"，命令走 WorkspaceMailbox 加密邮箱逐字属实：WorkspaceGateway DO "opaque byte router with no replay buffer"；WorkspaceMailbox 独立持有加密投递/租约/回执，且"不能应用命令、不能成为转录权威"
bun run check:architecture 架构 lint 防渲染层直写实证存在：package.json scripts 命中，ratchet 渲染层 raw-RPC、SessionDomain 绕过等
六瓶颈：机器/规划/编排/测试/评审/合并，各配机制逐字属实：spec 第 1 节原文六条；microVM 活进程快照、双模型规划+批评、5–9 并行 worker、90 秒视频证据全命中

02推文没讲的三个关键设计

A会话平面为什么默认独占进程——文档直接回答了多 CLI 混跑最脏的并发问题：除非 provider 协议明确保证多路复用安全，否则一个会话独占一个进程（独占通知、审批、工具、凭证）；管理客户端永远不许携带会话级 MCP 配置，会话客户端不许拿去做后台探测。Login/OAuth/配置写入不算"读"，必须走隔离 client。
BDurability 预算是精确数字，不是口号——ACP provider 50 ms 或 4 KiB 内 flush；首屏快照 900 KiB 投影预算，更早消息走游标分页；活跃 checkpoint 每 100–250 ms 或 16 个事件落一次；归档 = 停写 + 最终加密 R2 转录 + 沙箱暂停 30 天（不是删除）。还有一条工程底线：一旦运行时 SQLite 成为权威，"provider 沙箱丢失"就是终末存储损失——Zuse 保留缓存转录，绝不 fork 一个空壳替代、也绝不把不确定的命令当恢复重放。
CFork 安全：先隔离、再换锁——ADR 0033 承认 fork 是"比特级复制品"，克隆会继承父机全部密钥。方案：宿主层断网启动 → 隔离舱里销毁继承密钥、进程冷启、机器本地生成新 Ed25519 密钥对 → 单次注册 token 换新身份 → 才放网。任何一步失败就整机销毁重 fork（fork 约 1 秒，销毁重试便宜过修复）。预览 URL 永不迁移："links die honestly"。

03上手第一步：安装与接 Provider（官方安装文档照录）

Zuse 用你电脑上已有的 agent CLI，不捆绑任何付费订阅。首次启动会检测装了哪些、登录没登录。三个平台三条路：

  1. macOS：从 zuse.sh/download 下载，拖进 Applications。签名+公证的 universal 包（Apple Silicon + Intel），应用内自动更新。
  2. Debian/Ubuntu：终端一键脚本，安装器先校验 GitHub 发布的 SHA-256 摘要再调 apt，会装上 Secret Service 和 Avahi 两个运行时依赖：
    curl -fsSL https://raw.githubusercontent.com/swarajbachu/zuse/main/scripts/install-linux.sh | sh
  3. 其他 Linux x64：从 GitHub Releases 下 AppImage，chmod +x 后直接跑。AppImage 用户需自备 Secret Service 实现（GNOME Keyring 或 KWallet）；要附近设备发现就装 avahi-publish-service。

装好后接 Provider。Settings → Providers 里每个 CLI 是三种状态之一：Ready（装好+已登录+版本兼容）/ Needs attention（能用但要更新或重新登录）/ Unavailable（没装、登出或版本过低）。修复顺序官方也给了：查状态 → 确认 CLI 在你自己的终端能跑 → 走一遍该 provider 的登录流程 → 按提示更新 → 回项目新建会话。App 托管的 API key 存 macOS Keychain / Linux Secret Service，不进设置 JSON 明文。

Provider运行时接入方式

Grok / Gemini / Kiro各自本地 CLIACP 协议集成

注：版本 manager 装的 CLI 检测不到时，在 provider 设置里填绝对路径即可（README 原话）。模型、斜杠命令、工具语义、账号限额都是 provider-specific，Zuse 只保证统一的会话历史/流式/工具展示/模型选择/生命周期。

04上手第二步：搞懂 Plan 模式与四档权限（新手最容易踩）

Zuse 有两个容易混淆的开关：Plan mode 管智能体"能不能动手"，runtime permission mode 管"哪些动作免问"。Plan mode 是只读的——就算权限档开到 Full access，改动类工具照样被禁；批准或退出 plan 才回到正常执行。什么时候用？官方判据一句话：实现形态/范围/取舍还没定就用 Plan mode，已经"decision-complete"就直接跑。

权限档自动放行仍要问
Supervised只读工具Bash、编辑、web 请求、MCP 等全部
Auto-accept edits只读 + 文件编辑Bash、web 请求、MCP 等
Auto-accept edits + Bash读、编辑、Bashweb 请求、MCP 等
Full access普通工具Plan 退出与敏感路径

敏感路径（环境变量文件、SSH 材料、凭证、密钥）全档保护，Full access 也不放行。审批请求出现在 composer 位（带操作与上下文）；拒绝后控制权交还 agent，它可以解释、调整或换路。会话级覆盖只影响当前会话；默认档可全局或按仓库配。/plan 进 Plan、/run 回执行、/mode <name> 切权限档。

05上手第三步：并行 worktree——Zuse 的招牌工作流

这是推文"多个会话并行改同一仓库互不干扰"的官方操作版，六步：

  1. 打开一个 Git 仓库项目，先把主 checkout 里重要改动 commit 或 stash。
  2. 新建聊天，在 workspace picker 选全新 worktree 和起始 branch/revision（开了自动 worktree 就已默认选好；只有不需要隔离才选 Current checkout）。
  3. 发出第一个任务。Zuse 在 ~/.zuse/<project>-<id>/<worktree>/ 建 checkout + 分支、链接配置的本地文件、跑仓库 setup。有 origin 的仓库会先 fetch 远端默认分支，新任务不会从过期的本地分支静默开始。
  4. 等 Environment setup complete 再依赖依赖和生成物（创建立即返回，setup 后台继续，输出挂在 worktree 上）。
  5. 第二个任务再开一个聊天重复上述。验证隔离：每个 chat 的 workspace 指示器应显示 worktree 名而非 Main checkout；各自终端跑 git branch --show-current + git status --short，分支与目录应不同；一边小改动只出现在那边的 Changes 视图。
  6. 想从现有对话分叉试探另一条路：fork 菜单选 Fork into a new worktree。

存储模型（为什么worktree不等于再clone一遍）

Zuse 用 git worktree 不是 git clone：Git 历史和对象库与主仓库共享，每个任务只新增工作文件。node_modules 在主 checkout 存在且 lockfile 逐字节一致时直接链接进 worktree——认 5 种 lockfile（bun.lock / bun.lockb / package-lock.json / pnpm-lock.yaml / yarn.lock），不一致或已有非空目录就不动它。但".next/dist/target/缓存/venv"这类生成物仍占每个活跃 worktree 的空间，不免费。

可重复的项目准备写进 .zuse/settings.toml，别每次写进 prompt：

file_include_globs = [".env", ".env.local"]

[scripts]
setup = "bun install"
run = "bun run dev"
archive = "rm -rf .next .cache"
auto_run_after_setup = false

setup 在链接完成后跑、以 worktree 为当前目录，官方要求写成可安全重跑；setup 失败不毁 checkout，修好命令点 Rerun setup 即可。file_include_globs 解决"被 ignore 的文件不在 worktree 里"——.env 这类机器本地文件从主 checkout 符号链接进每个新 checkout，已存在的目标永不被覆盖；模式要窄，因为从任何 worktree 编辑链接文件改的是同一份源文件。仓库级 settings 还支持 defaultProviderId、defaultModel、defaultRuntimeMode（就是 04 节那四档）、autoCreateWorktree、worktreeBaseDir 和 environment_variables。

归档与恢复（别丢工作）

归档 = 立即隐藏对话 + 后台五步清理：关终端进程 → 跑 archive 脚本清生成物 → 若还有未提交改动，先打内部 checkpoint commit → .context 附件移出保留 → 删目录并 prune worktree 记录。还有别的 chat 引用同一 worktree 时会等全部归档才删。两个纪律：归档前先 push 想留的东西（checkpoint 是本地恢复机制，不是 reviewed commit 的替代）；unarchive 会在原路径原分支重建 checkout，checkpoint 被拆掉、文件回到普通未提交状态。

故障速查（官方五条）：setup 失败→读 setup 卡片输出修命令后 Rerun；chat 显示 Main checkout→说明首条消息没走 worktree，重开；选错 base→从目标分支另建 worktree，Zuse 不会静默同步上游更新；分支/PR 已有 worktree→用 Create from… 复用；worktree 目录被 Zuse 外删除→Git 找回分支或重建，从未提交且 checkout 已删的文件救不回来。

04.5第一个任务的官方模板（first-chat 照录）

官方给新手的第一个任务判据：小到能复核，大到碰真项目——修一个聚焦的 bug、补一个测试、讲清并改进一条工作流。流程五步：

  1. Open project… 选仓库——只是读取 Git 状态，不复制不移动仓库；纯文件夹也能用（会话/文件/终端），Zuse 会在你需要版本控制时提议 git init。
  2. New chat，发送前选三样：provider+model、环境（主 checkout 或新 worktree——实现类任务用新 worktree，保住主 checkout；只读讲解用主 checkout 即可）、权限档。
  3. 给可验证的结果。官方模板原文：问题 + 期望结果 + 怎么验证——"Find the cause, fix it without changing the surrounding layout, and run the focused tests. Tell me which behavior you verified and call out any checks you could not run." 用 @ 挂相关文件，视觉/文档依赖可加图片或 PDF。
  4. 跟进而不管控：时间线把推理/工具调用/编辑/提问/错误分层；可以内联回答提问、批准或拒绝动作、当前回合运行中排队后续消息、叫停跑偏的回合、不离开聊天直接打开变更文件或终端。
  5. 复核结果：开 Changes 读 diff，只勾属于本次提交的文件，在 Terminal 跑相关检查，需要就同一聊天里发修正；分支就绪后走 commit/push/开 PR/盯 checks/merge 的完整工作流，动作随真实 Git/PR 状态变化。

重启后什么还在？项目、聊天、会话时间线、工具结果、worktree 关联全部保留——provider 进程可能要恢复或重启，但本地持久历史是"发生过什么"的记录。

05.5派活给子智能体：两种姿势，别混淆

Zuse 有两种分工方式，隔离边界完全不同（官方明确警告：会话内子代理替代不了并发编辑时的独立 worktree）：

  1. 会话内 subagent：provider 在当前对话里委派一个有界的调查/实现步骤。Zuse 把这段活动折叠成 agent 行（有 provider 数据时显示委派 prompt、进度、摘要、模型、时长、回合数），游离工作出现在 Subagents 面板的 Active/Done。适合聚焦调研、测试分析、第二意见——用父会话的环境。Claude/Codex/Grok/Gemini 支持；全局预设可以给新会话的子代理更窄的指令或工具权限。README 还点名这是省钱手段：Opus 4.7 可以派 Haiku/Sonnet 干子任务，有 per-agent token 记账。
  2. 独立委派任务（delegated task）：另一个侧边栏聊天，有自己的 worktree 和分支——独立实现、分支级实验、可能长成独立 PR 的活。额外的 session tab 则留在本聊天内共用 checkout——复核、换 provider/model 继续、对同一 diff 的第二视角。

委派 prompt 官方公式：结果 + 边界 + 要什么证据回来。原文示例："Inspect the session recovery path. Do not edit files. Return the likely failure points, the tests that cover them, and any unanswered question."；编辑类加独占权："Own the settings form and its tests only. Do not edit the shared navigation components."。两条铁律：不许给两个 agent 重叠的写权限（除非明确一个是集成负责人）；委派不能绕过 Plan mode、运行时权限和敏感路径保护。完成的委派是证据不是验收——自己开 transcript 查文件和命令，让协调 agent 调和冲突、跑横切检查，在 Changes 里复核合并 diff 后再提交。

05.7Provider 排障速查（Status → 修复 → 重启会话）

  1. 读状态：Ready=装好+已认证+过兼容检查；警告=有更新或账号检查没完成；错误=确认的阻塞（缺认证/CLI 不兼容）；Disabled=保留安装但隐藏。
  2. CLI 检测不到：Zuse 通过桌面服务环境和已知安装位置找命令——shell 里能跑但 Zuse 找不到时，改完 shell path 或安装后完全重启应用（README 另提示：version manager 装的可在 provider 设置填绝对路径）。
  3. 登录：按 provider 显示的登录动作走——内联流程、启动官方登录命令、或填 API key 三选一；浏览器授权完成再回应用。Cursor 只支持 API key（存 macOS Keychain）。provider 登录 ≠ Zuse 账号登录（后者管托管远程访问）。
  4. 更新：低于最低版本会阻止新会话（协议不兼容），普通新版本提示不会。更新 provider 后要新建或重启它的会话——存量会话不会原地换进程。
  5. 模型：picker 显示 provider 上报的描述符，有的暴露推理力度等控件；可在设置里选默认、隐藏不想要的模型。OpenCode 还会透出它自己配的 providers/models。
  6. Pi：装 @earendil-works/pi-coding-agent，终端跑 pi 后 /login；可选填绝对二进制路径；用原生权限和它已有的项目信任配置。

06上手第四步：云端工作区与 Boat/E2B 选型

云端是 public beta，账上跑在隔离 sandbox 里，桌面/手机只是"可抛弃的查看器+控制器"。当前 beta 的沙箱 provider 是 E2B，但产品模型是 provider-neutral——E2B 只是 adapter，不是第二种聊天类型。

新聊天 composer 的 Run on 菜单选 Cloud · Boat 或 Cloud · E2B，选择只作用于这个新聊天；换 provider 不搬已有 workspace 的文件。选型表（官方）：

Boat（默认）E2B
机器规格Small / Standard / Large 三档所用 E2B template 的配置
暂停恢复保磁盘状态；Zuse 重启 runtime 和 agents，冷恢复要等服务重启普通暂停保磁盘和内存，进程活着
适合常规开发、构建、要挑 CPU/内存工作流在乎暂停间保持进程存活

两个 provider 的账号认证一次打通（Cloud Authentication），不用为 E2B 再登每个 agent；镜像在 Settings → Cloud → Cloud image 按 provider 分别构建/更新，互不覆盖。走 API 也行：POST /v1/api/workspaces 带 providerId（box/​e2b）、Zuse API key + Idempotency-Key 头；provider 不可用会报错而不是静默换机。暂停时照常发消息：内容和附件在 composer 队列等 workspace 唤醒，mailbox 还允许取消时可以撤。

钱怎么算（internal 文档）：Cloud Workspace 订阅 $40/月，含 $35 可归因沙箱算力；超出部分按 provider 成本 +5% 计，默认透支上限 $25（税前）。Boat 的用量直接采其上报（已按机器规格折算、停机时间不计），标价是 list price，不含 provider 计划折扣/赠金。官方提醒：provider 零售价 ≠ 你的 Zuse 账单。

05.9验收边界：Changes 面板与 PR 工作流

官方对 Changes 的定位一句话：它是"agent 说做完了"和你"确认分支就绪"之间的验收边界。变更/新增/删除/重命名文件显示为当前 checkout 的 diff；逐个打开看真实 patch，生成物和依赖文件要跟源码一样认真查。文件勾选决定内置 commit 动作暂存什么——不相关的改动可以不进这次提交，但不会被藏出审查视野。两个安全提示：Discard 是破坏性的（Git 清理后没有应用层撤销）；顶部主按钮跟随仓库状态变化：脏树 → Commit & push；本地领先 → Push commits；已发布无 PR → Create PR；有 PR 后 → PR 健康动作。

PR 面板展示描述/提交/变更文件/审查反馈/CI 状态（来自仓库 host 工具），可做的动作：在 GitHub 打开、让当前 agent 消解合并冲突、带捕获的 CI 上下文修失败检查、draft 转正、checks 未完时开 auto-merge、按配置的合并方式 merge、merge 后归档聊天。仓库访问和 host 认证仍是前提——动作失败时去内置终端查 git remote 和 gh 登录态。注意区分：有些动作是发给活跃 agent 的任务，而 push 已提交分支这类机械操作由 Zuse 直接执行。

06.5自动化入口：Public API 要点（给 Slack bot/CI/脚本）

Public API（/v1/api/**）只覆盖核心闭环：建 workspace（可带 prompt）、发跟进消息、读回复、查状态；SSH/预览/转录/账单仍走第一方界面。密钥在 Settings → Cloud Workspace → API keys 生成，secret 只显示一次：32 字节随机数 base62 编码（zk_ 前缀），api 只存 SHA-256 哈希，撤销立即生效；key 继承账号全部 cloud 权限，官方原话"当密码对待"。

  1. 建 workspace：POST /v1/api/workspaces 带 Idempotency-Key；prompt/projectId/providerId/agent/model/baseRef/branch 全部可选（唯一就绪项目自动默认、agent/model 继承上个 workspace、baseRef 默认远端默认分支）。API 建的 workspace 默认 runtimeMode: "full-access" 供无人值守跑——要更严需显式设另外三档；重放创建请求不改变已有 workspace 的访问模式。
  2. 发附件+消息：附件先传 /attachments（原始字节，单文件上限 20 MiB、每条消息最多 8 个，封存在 workspace 域对象存储、只有该 workspace 的已认证 runtime 能取），再 /messages 引用 assetId。消息至少送达一次经网关进沙箱，运行时按幂等命令路径注入——重投永不重复回合；发给暂停中的 workspace 会排队并触发唤醒（resumeTriggered: true），未送达消息 24 小时过期。
  3. 轮询回复：GET /messages?afterSeq=N。对话账本是单调递增的 user/assistant 行序列；assistant 行带 turnId/outcome 和最多 16 KB 的最终回复摘录（工具输出和附件不在内，在完整转录面）。deliveredAt - createdAt 度量"API 受理 → 运行时确认"，与轮询频率和模型完成时间无关。
  4. 幂等语义：key 非空且 ≤200 字符；header 与 body 同给必须一致；同 key 不同规范化请求返回 409 而不是静默丢弃新工作。消息回执至少保留 30 天（且在最新 1000 行内更久），过期后不许重用 key。
  5. Webhooks：每回合完成 POST workspace.turn.completed（带确定性 messageId、分支、outcome、回复摘录）。目标必须公网 HTTPS（禁凭证/私有/环回地址/重定向），每账号最多 20 个端点；whsec_ 签名密钥只显示一次，HMAC-SHA256 签名验证要拒绝 5 分钟前的请求、常数时间比较；按 zuse-event-id 去重（至少一次投递），失败重试 30s 起指数退避封顶 1 小时、最多 20 次。

06.8云端生命周期的精确规则（暂停≠归档≠删除）

状态机六态：ready（在线或暂停）/ pausing / paused（provider 算力停、存储保留）/ archived / deleting / deleted。三条边界最容易混：

  1. 暂停=静默新工作、尝试最后一次有界转录 checkpoint、记录 provider 用量、暂停同一 E2B 沙箱。checkpoint 上传失败不会毁掉权威 SQLite、也不阻塞暂停——云上副本只是冗余。打开暂停/归档的转录走缓存/R2；发消息会唤醒同一沙箱。
  2. 归档 = 30 天回收站（官方小标题"Archive is 30-day trash"）：不是恢复镜像、不复制整机。API 记 archiveRequestedAt 和 30 天后的删除截止；归档窗口内暂停的 E2B 沙箱保留完整文件系统，转录从本地缓存或 R2 可读。Unarchive 取消删除截止、回到 Active 且不启算力，第一个交互动作才恢复同一暂停沙箱。目录刷新无法把"归档中"拉回 Active——可重试失败留在 Archives 重试，确定性拒绝才带着错误回来。
  3. 删除：到期或手动 Delete，对账过程幂等地杀沙箱、删全部 workspace R2 对象、吊销运行时密钥与票据、移除 checkpoint 与启动元数据，标记 deleted；再留一个无内容墓碑 30 天，让离线设备同步状态。

对账失败铁律：create/resume/archive/unarchive/delete 全部幂等；失败的归档或 checkpoint 永不删除最后一个权威沙箱。

06.9Slack 接入：不用 API key 的团队入口

第一方 Slack app 让团队在频道里 @mention 或 DM 驱动仓库任务，全程不贴 API key/agent ID/model ID。要点：@mention 同一 thread 即复用同一 workspace，开新 thread 才是新 workspace；连接时导入更早的 thread 消息和图片作为上下文。可配置告警自动化：选项目、频道 ID、来源告警 bot ID、dry-run/live 模式——匹配的告警自动发起云端调查并把结果发回原 thread；它只读被授权的频道与文件，忽略人类消息/编辑/threaded 更新/已解决与部署更新/Slack Connect 事件。Thread 上下文上限：最新 500 条消息、60,000 文本字符。要撤新请求，从 App Home 私密设置撤销即可。

07路线图的可信与存疑

spec 的自我定位诚实："activation-and-extension sequence, not a rewrite"——Phase 1 的隧道（PR-E #266）与推送（PR-H #272）已落地并标注验证日期 2026-07-18。三个最险假设也自己列了：A1 活进程快照/fork 生产可用性（Phase 2 内嵌 spike 先验证，fallback 降级为分钟级冷启）；A2 用户真的会在"计划之计划"高度批准；A3 无人值守跑的成本/质量过不过目标门禁（先拿自家 repo 3–5 张票试跑）。

新手三问：① 会话关了丢不丢？——SQLite 事件源落盘，重启后项目/聊天/时间线/工具结果/worktree 关联全在（04.5 节"什么还在"）。② 我的 API key 安全吗？——App 托管的 key 进 Keychain/Secret Service 不进设置 JSON；云 API secret 只显示一次、服务端只存哈希；敏感路径（.env/SSH/凭证/密钥）四档权限全保护。③ 和直接在终端开 Claude Code 有什么区别？——区别不在模型在系统：会话持久化、worktree 隔离并行、四档权限+权限检查器、云端断网续跑、 Changes/PR 验收边界、子代理 token 记账，这些是终端里没有的工程边界。

08判断：谁现在就该试，谁该等等

现在就值得装：同时用 2+ 个 agent CLI、受够了"每个终端一套会话"的人——本地双平面架构 + worktree 隔离是今天就能兑现的价值，不依赖云端路线图。想让 agent 过夜干活、早上手机审批的人——可以关注但别押注，那要等 Phase 2/5/7 落地。

该等等的：想"开箱即用全自动 Devin 体验"的人——它需要你自己装好并登录每个 CLI、自己的订阅、自己付沙箱算力；把 Zuse 当"另一个聊天窗口"用的人——价值全在会话模型和工程边界里，不理解 worktree/权限档就用不出差异。

按身份对号入座（全部基于上文已核实能力）：

  1. 多 CLI 重度用户：装桌面端，今天就把 2-3 个 CLI 收进一个界面；先用 Supervised 档跑小任务，熟了再升 Auto-accept edits。
  2. 想把 agent 当同事派活的：读 05.5 两种姿势——并行写代码用 delegated task（自带 worktree），第二意见用 session tab；委派 prompt 记住"结果+边界+证据"公式。
  3. 团队协作：Slack app 是零配置入口，@mention 即任务，告警自动化适合 on-call；API 适合 CI 里"build 失败自动发起调查"这类闭环，记住 API 默认 full-access，CI 里务必显式收权。
  4. 开源贡献者：Bun 1.3.10+ / Node ≥ 22.13，bun install + bun dev 即起；架构约束有 check:architecture 兜底，ADR 全部编号可溯。
