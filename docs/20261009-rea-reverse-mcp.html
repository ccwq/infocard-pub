初学者引入 · 什么是 REA？

💡 一句话解释

REA（Reverse Engineering Agent）是一个 MCP 协议工具——你可以把它理解为一个给 AI Agent 用的逆向工程瑞士军刀。它让 AI 能够像专业逆向工程师一样，实际去看二进制里有什么字节、去找函数在哪里、去追踪调用链——而不是凭感觉瞎猜。

如果你用过 ChatGPT、Claude Code 或 Cursor，你可能已经注意到：AI 在解释程序行为时经常会说"可能"、"大概是"、"我猜"。这在简单代码上没问题，但遇到闭源软件、混淆代码、二进制固件、智能合约字节码时，AI 的"猜测"几乎总是错的——因为它根本没有真的去看那些字节。

REA 解决的就是这个问题。它通过 MCP 协议连接到你的 AI Agent，然后调用真实的逆向工程工具（Hopper、Ghidra、IDA），把真实证据——汇编指令、函数符号、字符串、调用引用——返回给 AI。AI 看到的不再是"猜测"，而是"这条指令在地址 0x1000 处做的是字符串比较，比较对象是 'password' "。

什么是 MCP？ MCP（Model Context Protocol，模型上下文协议）是 Anthropic 提出的开放标准，让 AI 模型能够调用外部工具。你可以把它想象成 AI 的"USB 接口"——只要设备支持这个接口，什么牌子的工具都能插上去用。REA 就是一个 MCP 工具，它向 AI Agent 暴露了 133 个逆向工程相关的工具调用。
什么是逆向工程？ 逆向工程（Reverse Engineering）指的是在没有源代码的情况下，通过分析二进制文件、程序行为或运行时数据来理解程序内部工作原理的过程。普通人可能遇到它的场景：分析一个闭源软件的安全性、解包一个 APK 看看它偷偷收集了什么数据、检查固件里有没有后门——这些都是逆向工程的范畴。REA 让 AI Agent 能够参与这个过程，并且每一步都给出真实证据。

REA 由 morluto 开发（GitHub 16,758 ★，MIT 协议），主语言支持 12 种，建仓于 2026-04-14。目前主要贡献者：morluto(782 commits)、N0zoM1z0(249)、kaoru0822-kitauji(179)。版本演进从 2026-07-12 首发 0.2.1，到 2026-10-09 的 v6.1.0，三个月内发布 6 个大版本，工具数量从个位数增长到 133 个。

证据驱动哲学 · 为什么"猜测"不够用
✗ 普通 AI 方式

AI 直接猜

根据表面特征（变量名、代码风格、字符串片段）生成推测，结论无证据支撑。遇到混淆代码、闭源组件、运行时行为直接失效。

✓ REA 方式

证据驱动逆向

附具体汇编指令、调用链、字符串、截图作为支撑。每条结论可复核、可溯源、可复现。AI 看到的不是猜测，而是事实。

🔍 Evidence 是什么？

REA 输出的每一份结果都叫做 Evidence（证据）。一份 Evidence 包含：目标文件身份（SHA-256）、源位置（文件 + 偏移量）、观察结果（看到了什么）、推断结果（这意味着什么）、未解问题（还有哪些不确定的地方）。这种结构让 AI 不再把推断当事实，也让人类可以验证 AI 的每一步逻辑。

观察 / 推断 / 未知 · 三分法

REA 的 MCP prompts 要求 AI 在报告中严格区分三类内容：

  • ● 观察（Observation）：RE 工具实际报告的内容，附带文件位置和偏移量
  • ● 推断（Inference）：基于观察得出的结论，标注置信度和依据
  • ● 未知（Unknown）：当前证据无法回答的问题，列出以便后续调查

MCP 工作流详解

REA 的 MCP 实现包含三类核心能力：

  1. 工具调用（Tools）：133 个 MCP 工具，覆盖二进制分析、JS/Electron 反编译、浏览器取证、EVM 字节码、固件解析等。AI 通过这些工具主动"去看"字节，而不是"猜"字节。
  2. 引导提示（Prompts）：6 个结构化工作流 prompt，告诉 AI 在不同场景下应该如何组织调查步骤、如何分离观察/推断/未知。
  3. 自动补全（Completion）：针对 prompt 参数的上下文补全——比如当 AI 在调查某个二进制时，补全建议使用哪些函数地址和过程名称。

REA 不需要 AI 了解具体的逆向工程引擎 API。所有复杂性被封装在 REA 内部——AI 只需要说"分析这个二进制文件"，REA 自动选择可用的引擎（Hopper/Ghidra/IDA），执行分析，把结构化证据返回给 AI。

六大引导工作流 Prompts

这些 prompt 不增删工具，只给 AI 提供调查路线图。它们要求 AI 把「观察 / 推断 / 未知」分开，Evidence 内联返回。

Prompt 名称 用途
investigate_feature 从功能发现追踪到相关函数证据。例：分析"离线搜索"功能在 Notes 应用中如何实现。
compare_application_versions 对比两个发布的产物，可选静态分析和运行时跟进。适合版本差异分析。
verify_reconstruction 对照 Evidence 评估重建规格的完整性和准确性。
trace_crash 将崩溃症状与静态路径关联，可选进程捕获证据。
audit_residual_unknowns 审计当前残余的未知项和证据覆盖的解决情况。
prepare_bounded_process_capture 设计有界受控进程实验，在执行前规划边界和预期输出。

通过 MCP 协议调用：prompts/list 列出所有 prompt，prompts/get 获取具体 prompt 并传入参数。

十大分析对象 · EVM 字节码已升级为正式能力

✅ EVM 字节码：已解除待确认状态

经过官方实测验证（2026-10-09），EVM 字节码分析已正式支持。通过 inspect_evm_interface / rea inspect-evm-interface 工具，可以从本地字节码文件推断接口候选。底层使用打包的 EVMole 0.9.3。EOF-style EF00 容器返回 unsupported_target。需要主机提供 util-linux prlimit（通常为 /usr/bin/prlimit），可用 REA_EVM_PRLIMIT_COMMAND 环境变量指定替代路径。载体 SHA-256 标识原始文件（不是以太坊的 Keccak code hash）。 

rea inspect-evm-interface ./runtime.hex hex --json
rea inspect-evm-interface ./runtime.bin raw --json

⚠️ 重要限制：返回的选择器、参数类型和状态可变性均为推断值，不是经过验证的源 ABI。函数名/签名不会通过链上注册表查询。优化后的代码可能产生不同的可变性候选。空候选列表不证明合约无可调用接口。

诊断工具 · rea doctor

rea doctor 是纯读取性诊断工具，读取主机前置条件和 agent 配置，不修改任何内容。无参数时审计所有检测到的注册、已安装 skill 和可选分析引擎。可指定作用域：

命令 检查内容
rea doctor --json 全量审计：所有注册、技能、分析引擎、整体健康状态
rea doctor --client codex --json 检查 Claude Code 注册状态（aligned / stale / missing / invalid）
rea doctor --provider ghidra --json 检查 Ghidra 引擎可用性（ambiguous 时列出 candidate_ids）
rea doctor --skill --json 检查已安装的 workflow 指令

注意：doctor 检查文件和前置条件，不检查活动连接。一个 aligned 注册 + 缺失工具 = 需要重启 agent，不是因为 doctor 报告有问题。

CLI 命令族 · 完整参考
自动分析 · 无需指定引擎

rea analyze PATH 对目录和 .asar 文件自动选择 JS 工作流，无需 --provider 参数。 

# 通用分析（自动选择 JS 工作流）
$ rea analyze /path/to/appdir --json
$ rea analyze /path/to/app.asar --json

# 指定引擎的原生分析六命令
$ rea analyze    /path/to/binary --provider ghidra --json  # 全局概览
$ rea search     /path/to/binary "pattern" --provider ghidra --json  # 搜索
$ rea function   /path/to/binary main --provider ghidra --json  # 函数档案
$ rea decompile  /path/to/binary 0x1000 --provider ghidra --json  # 伪代码
$ rea xrefs      /path/to/binary 0x1000 --provider ghidra --json  # 交叉引用
$ rea trace      /path/to/binary "symbol" --provider ghidra --json  # 追踪
$ rea instructions /path/to/binary 0x1000 --provider ghidra  # 仅汇编
Provider 选择逻辑

自动选择规则：唯一可用 provider 时直接使用；多 provider 时按目标支持度选择（可查看 details.candidate_ids 选择）。显式指定 --provider hopper|ghidra|ida 或设置环境变量 REA_ANALYSIS_PROVIDER=ghidra 覆盖自动选择。Ghidra 的首次查询有可配置的启动 deadline（v6.1.0 新增），超时后可关闭/重开来恢复。 

# 查看可用 provider 及其支持的操作
$ rea providers --json
$ rea capabilities --json
快照与 Evidence 管理

快照（Snapshot）保存成功分析结果供后续查询复用。目标字节、操作、参数、provider 和设置完全一致时重用精确结果。变异和光标相关调用不进入缓存。 

# 保存快照
$ rea analyze /path/to/binary --provider ghidra --snapshot /path/to/snapshot.json

# 复用快照（完全一致的查询直接从缓存读取）
$ rea analyze /path/to/binary --provider ghidra --snapshot /path/to/snapshot.json

# Evidence 导入/导出/对比
$ rea evidence-import /path/to/evidence.json
$ rea evidence-export /path/to/evidence.json canonical.json
$ rea compare /path/to/left.json /path/to/right.json

# 导入历史源码（与当前产物对比）
$ rea import-reference-source /path/to/oldsource
CLI 退出状态
状态码 含义
0 操作完成（可能含 partial evidence、warnings 或未解问题）
1 操作无法完成（invalid input / permissions / cancellation / timeout / 其他失败）
128 + N 信号 N 终止了进程（如 137 = SIGKILL）

在管道中使用 JSON 输出时，建议启用 pipefail：set -o pipefail; rea inspect-artifact ./app.asar --json | jq . > inspection.json

Native 分析 · 原生二进制深度能力
Hopper 特有行为
  • address_to_file_offset：先验 SHA-256 校验源文件，再做 image-relative → 原始文件坐标映射。源文件变化或损坏时报 artifact_changed，并保留 partial_observation（含原生偏移和 provider 路径，但原始文件坐标不可用）
  • v6.1.0 BREAKING 变更：Hopper 正则搜索从默认语义改为 ECMAScript Unicode 语法（可取消 worker，5秒超时）。旧版正则可能不再工作
  • 快照重放：重放历史快照是当时状态的证据快照，不是当前状态的描述。目标字节变化后需重新分析
Mach-O / macOS 专项
  • inspect_macho：保留 otool 报告的 file_offset（含 lipo slice offset），用于 universal binary 场景
  • trace_dylib_resolution：解析 Mach-O load commands，跟踪 @rpath / @loader_path / @executable_path 的每种展开结果。系统共享缓存库（shared-cache）路径保持 undetermined
  • inspect_asset_catalog：通过 macOS assetutil --info 读取编译后的 Assets.car 元数据（不支持图片提取）
  • inspect_keyed_archive：读取 XML 或二进制 Foundation keyed archive，不实例化类。UID 0 无法区分条件 nil 与普通 nil
  • inspect_native_dispatch_metadata：解析 64-bit little-endian Objective-C class/metaclass records、superclass 指针、方法条目、ivar、C++ vtable（chained fixups 和 legacy bind 均支持）

FAQ · 常见问题（10 条）
任何 agent 都能用？
任何支持本地 MCP 协议的 agent 均可，包括 Claude Code、Codex、Cursor、Gemini CLI、Windsurf、Devin 等 14 个客户端。
原生分析需要什么？
需要 Hopper / Ghidra / IDA 之一。setup 时 REA 可自动安装 Hopper（macOS 首跑可能弹 license 对话框），Ghidra/IDA 用已有安装即可。Hopper 有免费 demo 限制，付费 license 可选。
JS / .NET 分析需要引擎？
不需要。静态 JS 和 .NET 程序集分析只读文件、不运行应用，无需任何逆向引擎。
数据安全吗？
⚠️ 应用从不离开你的机器。全在本地分析，agent 模型 provider 自有数据政策适用。

v6.0.0 的 BREAKING 变更。MCP 协议本身支持相对路径，但 REA 为保证分析结果的确定性和快照可复用性，要求所有文件系统输入必须是绝对路径。CLI 也有同样要求。

MCP 注册固定到执行 setup 时的确切版本。升级 npm 包（rea update）不会自动更新已有 agent 的 MCP 注册。正确升级：运行新版本 setup → 审查变更计划 → 批准 → 重启 agent。旧注册会变成 stale 状态，用 rea doctor 可检测。
doctor 和 setup 有什么区别？
doctor 是纯读取性诊断（不修改任何内容），检查文件、前置条件和配置状态。setup 是引导式安装程序，会修改 agent 配置、安装 Hopper（需用户批准）和 skill 文件。--dry-run 模式下 setup 只返回计划不执行。
LLM 会看到 REA 的哪些工具？
连接到 REA MCP server 后，agent 会看到 133 个工具（v5.0.0）、6 个引导 prompt 和对应的补全支持。工具按功能分类：二进制分析、JS/Electron、网络存档、APK、固件、EVM、浏览器取证等。agent 无需知道具体工具实现细节。

MCP 技术细节 · 内部工作原理

🔌 MCP 协议基础

MCP（Model Context Protocol）是一个基于 JSON-RPC 的通信协议。客户端（Claude Code 等）通过 stdio（标准输入输出）与 REA 服务器通信。通信流程：客户端发送 initialize 请求 → REA 返回服务器能力（工具列表、prompt 列表）→ 客户端调用 tools/call 执行分析 → REA 返回结构化结果（含 Evidence）。

REA 的 MCP 实现采用 stdio 传输（不是 HTTP），这意味着它通过进程的标准输入/输出来交换 JSON-RPC 消息。这种设计有两个重要优势：（1）完全本地化——不需要网络连接，数据不会离开你的机器；（2）简单可靠——不需要处理 HTTP 错误、连接重试、CORS 等问题。

工具调用的生命周期
  1. Agent 构造请求：AI 根据用户意图选择合适的工具（如 analyze_javascript_application），填入参数（如 input_path 为分析目标路径）
  2. MCP 客户端转发：Claude Code 的 MCP 客户端将请求序列化为 JSON-RPC，通过 stdio 写入 REA 进程
  3. REA 服务端处理：解析请求 → 验证参数（检查绝对路径等）→ 调用内部分析逻辑 → 生成 Evidence
  4. 结果返回：Evidence 序列化为 JSON-RPC 响应，通过 stdio 发回给 MCP 客户端
  5. Agent 解读结果：AI 解析 Evidence，提取关键信息，回答用户问题或继续追问
133 个工具如何组织？ REA 的 133 个 MCP 工具按目标类型分组：原生二进制工具（约 30+ 个）、JavaScript/Electron 工具（约 20+ 个）、浏览器取证工具（约 15+ 个）、EVM 字节码工具（约 5 个）、固件工具（约 5 个）、快照/Evidence 管理工具（约 10 个）、Apple 专项工具（约 10 个）、通用工具（约 40 个）。工具命名遵循 verb_object 模式（如 analyze_javascript_application、inspect_macho、trace_dylib_resolution）。
Session 和 Evidence 的关系

REA MCP 的一个重要概念是 Session（会话）。当 Agent 打开一个二进制目标（open_binary）时，REA 创建一个会话，加载目标到选定的逆向引擎（Ghidra/Hopper/IDA），返回分析结果。这个会话在连接关闭前保持活跃，后续的 decompile、xrefs、function 等调用都复用同一个会话状态。

每个工具调用的结果都包含 Evidence 记录。Evidence 有自己的 ID（仅在当前会话内有效），可以传给其他工具作为输入（如 inspect_analysis_view 接受 Evidence ID 作为参数）。这种设计让 AI 能够引用之前观察到的证据，而不需要重复分析。

重要：MCP 连接的 Evidence ledger 属于该连接。不同 CLI 调用是独立进程，不共享会话 Evidence。export_evidence_bundle 可以将当前会话的 Evidence 导出为文件，供后续独立 CLI 调用使用。

Provider 调度机制

"Provider"是 REA 对逆向引擎的抽象层。目前支持三种 Provider：

Provider 引擎 支持平台 费用
hopper Hopper Disassembler macOS 12+, Ubuntu 24.04+, Fedora 41+, Arch Linux 免费 demo 有厂商限制
ghidra Ghidra（SNSA） Linux, macOS, Windows（实验性 P0） 免费开源
ida IDA Pro / IDA Starter 各平台（需自行安装并配置路径） 商业软件（昂贵）

REA 的 Provider 层封装了不同引擎的 API 差异，让 AI 用统一的工具名称操作不同引擎。自动选择逻辑：只有一个可用 Provider → 直接用；多个可用 → 按目标支持度选（ambiguous 时返回 candidate_ids 让 AI 选择）。Ghidra 的每次查询有可配置的首次启动 deadline（v6.1.0 新增），超时后可关闭/重开来恢复。

高级使用场景 · 超越基础分析
场景一：安全审计

使用 REA 对闭源软件进行安全审计时，推荐工作流：先用 analyze 获取整体结构 → 用 search 搜索敏感字符串（如 "password"、"api_key"、"eval"）→ 用 function 分析可疑函数 → 用 trace 追踪数据流。Browser Observation 可以检查 Web 应用是否有可疑的网络请求（如向未知域名发送数据）。

EVM 字节码分析可以用于审计智能合约：检查 inspect_evm_interface 返回的接口候选是否包含可疑的外部调用（CALL、DELEGATECALL）、访问控制是否正确（require/revert 的参数来源）、是否有整数溢出风险（通过伪代码分析）。

场景二：软件兼容性研究

当你需要理解一个旧版本软件的行为以便在新平台重建时，REA 的 compare_application_versions prompt 和 compare CLI 命令非常有用。导入历史源码树（import-reference-source），让 REA 对比源码与闭源产物的差异，自动推断哪些功能可能已被移除或修改。

对于 macOS 应用，inspect_native_dispatch_metadata 可以分析 Objective-C runtime 元数据，理解类的继承关系和协议遵循情况。trace_dylib_resolution 帮助追踪动态库依赖，解决"这个函数是从哪个 dylib 来的"问题。

场景三：固件安全研究

REA 与 Binwalk / Unblob 集成进行固件分析：先用 REA 调用固件提取工具（Binwalk 提取文件系统分区、Unblob 解析压缩包）→ 将提取结果传给原生分析引擎（Hopper/Ghidra）→ 追踪关键函数（如加密实现、网络初始化、 UART/JTAG 调试接口）。

固件分析的特殊挑战：通常是混合架构（ARM + MIPS + x86）、包含裸机代码和文件系统、需要处理 U-Boot、Linux kernel、busybox 等多个组件。REA 的证据结构让复杂固件的逐步拆解成为可能。

场景四：Electron 应用深度分析

Electron 应用分析是 REA 的强项——不需要任何逆向引擎，100% 静态 JS 分析就能获取大量信息。关键分析点：

  • › IPC 通道映射：追踪 renderer 进程与 main 进程之间的通信通道（如 notion:clipboard:write），理解数据如何跨进程传递
  • › 原生模块关系：分析 node_modules 中的原生绑定（.node 文件），理解哪些 Node.js API 被桥接到原生代码
  • › Source Map 利用：如果有 sourcemap，可以还原出生产前的原始 TypeScript 源码结构
  • › 路由和页面结构：从打包后的 JS 中提取前端路由配置，理解应用有哪些页面和功能入口
场景五：CTF 逆向题目

在 CTF（Capture The Flag）比赛中，REA 可以加速逆向题目的解决过程。对于 ELF/PE/Mach-O 二进制：先用 analyze 获取整体概况 → 用 search 找 flag 格式字符串（如 flag{、Correct!、Wrong）→ 用 decompile 分析关键函数 → 用 trace 追踪 flag 检查逻辑。

DX-Ball 和 TH04 的案例表明，REA 在"重建"类逆向题目中特别有价值——不仅能分析出算法，还能通过差分测试验证重建代码的字节级正确性。

MCP Prompts 深入使用 · 调查路线图

REA 的 6 个引导 prompt 是精心设计的工作流模板，AI 使用它们时可以跳过无关步骤、直接进入核心调查。每个 prompt 都会指示 AI 将报告分成「观察 / 推断 / 未知」三部分，并给出可选的起点（当前 REA 工具名称）。

investigate_feature · 功能调查

这是最常用的 prompt。当你有一个具体的功能想知道它怎么实现时（如"Notes 应用的离线搜索怎么做的"），用这个 prompt。它会引导 AI：从发现（功能入口点）→ 追踪（调用链）→ 取证（具体函数实现）→ 结论（功能如何实现 + 证据）。

对于 JS/Electron 应用，它直接指向 analyze_javascript_application，不需要先 open_binary。对于已有 Evidence 的情况，它建议先 inspect_analysis_view 再追踪功能种子。

compare_application_versions · 版本对比

用于比较两个版本的产物。prompt 建议先打开每个目标再调用 inspect_artifact——检查对活跃目标生效，返回图和发现一起内联返回。可以配合静态分析和可选的运行时跟进（process capture）。

典型用法：对比 v1.2 和 v1.3 的 Electron 应用，找出新增功能、修改行为或移除代码。通过 Evidence 对比，AI 可以量化版本间的差异。

trace_crash · 崩溃追踪

将崩溃症状（segmentation fault、assertion failure、输出异常）与静态代码路径关联。prompt 引导 AI：从崩溃症状（已知）→ 静态分析（找相关代码）→ 进程捕获（可选，运行程序复现崩溃）→ 根因定位。

结合 REA 的进程行为观察工具（Linux/macOS PTY），可以在有界环境中运行目标，记录终端输出、退出码和文件系统变化，找到导致崩溃的确切输入条件。

audit_residual_unknowns · 残余未知审计

在完成一个调查后，Evidence 中通常会留下一些"未知"项（不确定的函数用途、未解析的引用、无法确认的数据流）。这个 prompt 引导 AI 系统性地回顾所有残余未知，评估哪些已有证据可以解决它们，哪些需要额外调查。

Completion 功能支持对"残余未知"补全：AI 在填写 prompt 参数时可以获取当前未解决的 unknown heads 列表作为候选。

MCP 补全系统的实际价值：当 AI 在填写 prompt 参数时，补全系统提供的不是随意猜测，而是当前会话的真实状态——已有的函数地址列表、已分析的文档列表、已保留的 Evidence ID 列表。这让 AI 的补全选择总是基于真实数据，而不是训练知识。
资源限制与边界 · 知道工具的极限
⚠️ EVM 字节码资源限制（v6.1.0 实测数据）
  • 输入文件 ≤ 4 MiB
  • 完整回复 ≤ 16 MiB
  • 组合诊断输出 ≤ 1 MiB
  • Worker JS 堆 ≤ 256 MiB
  • 虚拟地址空间 ≤ 3 GiB（与常驻内存不同）
  • CPU 时间 ≤ 30 秒
  • 命令截止时间 ≤ 30 秒
Native Xcode 命令限制

REA 执行 macOS Xcode 命令（如 assetutil、otool）时有严格限制：60 秒 deadline + 64 MiB stdout/stderr 总预算。超时、取消、流失败和输出耗尽都会在错误结果中保留捕获的输出——从不将截断输出解析为完整观察。

Browser CDP 限制
  • › REA 不启动、不拥有、不控制浏览器。CDP 端点必须是 loopback（127.0.0.1），不接受公共地址或 HTTPS 端点
  • › 默认观察窗口 500ms，可在 MCP 参数中指定更长时间
  • › Source-map 获取有 30 秒 deadline 和 64 MiB 聚合流响应预算
  • › 源映射解码将原始解析身份绑定到 64 MiB，聚合内联证据绑定到 32 MiB
Keyed Archive 限制
  • › 输入 ≤ 64 MiB / 对象引用 ≤ 200,000 条 / 嵌套层级 ≤ 128 层
  • › UID 0 无法区分条件 nil 与普通 nil
不支持的场景
  • ✗ REA 不做通用浏览器自动化（无导航、无输入、无下载控制）——Browser Observation 是取证工具，不是 Selenium 替代品
  • ✗ REA 不做运行时断点调试——这是 IDA/Ghidra/Hopper 的职责
  • ✗ EVM 分析不查链上数据（无 RPC、无 explorer 查、无交易广播）——这是链上分析工具的职责
  • ✗ Browser CDP 不暴露 WebMCP.invokeTool——只发现声明，不执行调用
