路线 / 控制落在哪里

JSON 把自由度移进目录，但并未消除取舍

文章把两条路的不足放在一起：AI 直写代码，生成结果难以控制；只回 Markdown，又难以承载所需交互。第三条路让模型输出 JSON，由开发者定义的组件承接 UI。这个论证适合解释为什么需要中间层，但不能据此断言代码或 Markdown 在所有任务里都失败。

机制短注：开发者先规定 catalog，再把允许的组件映射到 registry；模型产出 spec，Renderer 按映射呈现。README 的“Guardrailed / Predictable / Stream”主张与文章“AI 不写代码、由自己的组件渲染”的描述一致。这是约束生成空间的设计，不是正确性证明。

还要补上文章三角之外的一条现行路线：MCP Apps 使用 iframe 与标准 web 技术。Google 官方博客把它与 A2UI 视为互补，并给出组合模式。因此，选项不止“代码、Markdown、JSON”三个互斥格子；隔离承载 web 界面也是需要评估的方案。

延伸阅读：旧卡《json-render》已展开 Catalog / Registry / Spec、渲染器与集成机制，本卡不再逐项复述。

争议 / 提问 → 回应 → 未知

两类反对意见，分别问到了哪一层？

“为什么不直接用 JSON Schema / OpenAPI？”

按文章转述的 HN 讨论，回应是：那些描述数据，json-render 描述 UI。这个回答指出了抽象对象的差别，却没有证明已有 schema 工具不能参与 UI 描述。现行 README 的入口本身也接受 schema；真正需要对照的是，谁定义可用组件、谁负责把描述变成界面。

不确定性：HN 原帖未直接核对；以上问答仅按文章转述保留，不能当作社区共识。

“有了 A2UI，为什么还需要 json-render？”

文章的协议与工具比较，也引出了这个反方问题；此处是问题归纳，不是已核对的 HN 原帖引语。可核对的回应是：二者均使用结构化描述与本地组件，但定位不同，比较时应先确定互操作边界。

比较标准A2UIjson-render
第一方定位跨客户端的 JSON 流式协议；“send data not code”，客户端用本地组件目录渲染。“The Generative UI framework”；应用定义 catalog 与 registry，渲染自己的组件。
已有证据当前 v0.9 stable；生产用于 Gemini Enterprise、Opal、Flutter GenUI。README 有 defineCatalog、defineRegistry 与 Renderer 的应用内接线示例。
选型问题是否需要不同客户端共同理解界面描述？是否需要把生成界面接进现有应用的组件体系？

“A2UI 是协议做通、json-render 是工具做深”是文章的概括判断，上表的定位为这个判断提供依据，但不意味着二者完全不重叠。仅凭这些材料，无法判断互换成本，也不能推出谁的生成质量更高。

用途 / 文章判断，不是实测排名

四种用途，需要四种验收问题

文章建议的场景包括以下四类。它把 text-to-dashboard 称为“验证最充分”，这是文章判断；材料没有提供共同测试集或比较结果。

  • 仪表盘：作者建议用自然语言组合看板。本卡建议核对指标含义、筛选条件与图表是否对应，而不只看组件是否出现。
  • 营销后台：作者建议让既有业务组件按需组合。本卡建议检查操作范围与确认流程，不把合法按钮视为授权证明。
  • 助手界面升级：作者建议把纯文本回答变为交互界面。本卡建议先确认交互确实减少操作，再承担目录维护工作。
  • 动态报表：作者建议按问题生成展示结构。本卡建议核对统计口径与数据出处，避免把排版完整误认成报告正确。
边界 / 本地验证

先测“合法但错误”，再决定接入

推断：catalog 主要约束组件与属性的结构，无法单凭这些约束保证语义。依据是 README 把生成空间限定在开发者目录内，而目录合法性不等于任务正确性；模型仍可能用合法组件拼出指标错配或操作含义不符的 UI。这里没有把这种风险写成已复现缺陷。

实验边界：README 明确把 Jev composition 标为 Experimental，自 v0.21.0 起提供 experimental_composeSpec / experimental_createEvaluator，playground 可选。不要把它与稳定承诺混在一起。

15 分钟验证任务 · 建议流程，未在本卡执行

  1. 克隆仓库，安装依赖。在仓库中选择 examples/chat 或 playground，按其现行 README 确认环境要求与启动目录。
  2. 启动开发环境，向示例提出一个需要多个组件的界面请求，观察 JSON spec 到界面的流式渲染。
  3. 对照请求与输出，记录：界面是否随 spec 增量出现、组件类型是否属于目录、字段与数据含义是否匹配；再提出超出目录能力的要求，观察它如何处理。
