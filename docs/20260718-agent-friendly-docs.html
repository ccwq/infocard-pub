让编码代理读懂文档

页面、Markdown 与 llms.txt 可以组成不同的阅读入口，但入口不是能力保证。真正需要设计的是：信息如何被发现、压缩、核验与调用。

核心判断：补充约定 ≠ 既定标准 ≠ 效果承诺
网页页面完整语境
Markdown结构化正文

内容入口处理节点不可省略的核验
01 / WHY

背景与动机：问题不只是“模型能不能读”

复杂网站把导航、广告、脚本和正文混在同一页面里；直接转成面向模型的纯文本，可能困难，也可能不精确。与此同时，上下文窗口未必能容纳整个站点。[1]

NODE A · 页面层

网页是完整语境

它保留导航、页面层级、链接与交互线索，适合人类浏览，也可能承载模型需要的背景。但“信息存在”不等于“信息容易抽取”。

NODE B · 文本层

Markdown 是压缩后的正文

它可以减少视觉噪声，让标题、段落与代码更直接；仍需检查是否丢失上下文、版本信息、示例限制或页面之间的关系。

NODE C · 选择层

入口文件服务于定位

llms.txt 提案设想在网站根路径提供一份 Markdown 文件，给出背景、使用指引，以及通往详细 Markdown 页面​​的链接。[1]

02 / MAP

实践检查清单：一份提案，放在一条可核验路径上

不要把文件名当作终点。更可靠的工作流是从入口发现内容，再回到原始页面与正文核对。

① 先找入口确认站点是否公开提供约定文件；没有该文件，不代表文档不可用。
② 再看地图读取背景、使用指引与详细页面链接，建立“主题—页面—关系”的索引。
③ 回到证据对关键结论回看原始页面、版本与示例，不把摘要直接当成完整事实。
④ 最后调用依据任务选择页面、Markdown 或两者组合；调用方式与信息架构同样会影响结果。

边界提醒 / 不要过度归因

当前研究没有可复现的统一评测数据，因此不能断言某一种格式普遍更适合全部模型或任务。页面可访问性、信息架构、内容正确性和调用方式，都可能共同影响结果。

证据边界：三种入口，三类工作

04 / PRACTICE

把“友好”写成可检查的设计动作

面向编码代理的文档，不应只追逐某个特殊文件名，而要让每一步都可发现、可定位、可验证。

DO · 建立可追踪链路
  • 为重要主题提供清楚的页面标题、稳定链接与短摘要。
  • 让 Markdown 版本保留标题层级、代码块、限制条件和相关链接。
  • 用入口文件汇总背景与指引，并明确链接指向的详细内容。
  • 给版本、变更与示例加上可核对的上下文。
CHECK · 保留不确定性
  • 把提案写成提案，不写成已经普遍采用的标准。
  • 不承诺一定提升检索、引用、生成或任务完成效果。
  • 对关键答案回到原始页面核验，而不是只依赖压缩入口。
  • 记录缺失内容、转换损失和任务自身的调用限制。
05 / 语境

工具定位也要和证据分开

Mintlify 官网将自身定位为“为编码代理构建的知识平台”。这是产品公开定位，不等同于独立评测结论。[2]

因此，阅读工具、文档平台与入口约定可以帮助团队组织知识，但“更适合代理”仍应拆成具体任务来讨论：发现页面、理解概念、执行代码、处理版本差异，分别需要什么证据？没有统一评测时，最稳妥的答案是保留路径、保留来源、保留人工核验。
