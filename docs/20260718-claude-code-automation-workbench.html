CLAUDE CODE · 可控工作流

Claude Code 自动化工作台：
能力层、权限层与可控边界

把代理放进工程流程，不是把交付责任交出去。功能可组合，权限须收敛；每一项输出仍要经过代码审查、测试与发布审批。

先定边界，再接自动化。 高影响命令、网络访问、依赖安装和外部发布，均应在执行前获得显式确认；密钥不得进入提示词、日志或页面。
01

五个能力入口，五种不同职责

官方文档为权限、Hooks、MCP、子代理与 Skills 分别提供入口。它们适合被组织为能力分层，而不应被描述为可以自行完成无人值守交付的承诺。

权限

作为配置层控制允许与需要确认的操作。以最小权限为起点，并按任务、目录和风险逐步放开。

Hooks

用于工具生命周期中的可配置自动化扩展点。仅依照官方事件与配置模型接入，并让结果可观察、可复核。

MCP

外部连接应被当作新的信任边界：明确服务来源、可访问数据和调用范围，不把连接能力等同于默认授权。

子代理与 Skills

可分别用于任务分工与可复用指令封装。每个角色保持窄职责、清晰输入输出，并接受主流程的审查门槛。

02

一条可审查的工程路径

界定任务给出目标、范围、允许目录和验收条件。
受限执行按权限策略操作；风险动作先确认。
人工复核审代码差异、配置变化和安全影响。
测试与审批运行测试；发布前由责任人批准。

代理生成的补丁、说明或命令是候选产物，不是已验收结果。审查关注正确性、依赖变化、权限扩大、数据暴露与回滚路径；测试验证行为；发布审批决定是否进入外部环境。

03

把“确认”设计成硬门槛

可默认推进的低风险工作

  • 在限定工作区内阅读、归纳与提出方案
  • 生成待审查的代码草案和测试建议
  • 在既定策略内执行可重复的本地检查

必须显式确认的高影响动作

  • 执行可能改变系统状态的命令
  • 访问网络、安装或更新依赖
  • 写入外部服务、提交发布或触发部署
04

运行卫生：让自动化可停止、可追踪

隔离工作区：把试验、生成与受控变更留在清晰边界内。
最小化上下文：只提供完成任务必要的信息，尤其不提供密钥、令牌或私人数据。
可审计输出：记录决策依据、变更摘要和测试结果，但避免把敏感值写进提示词或日志。
可逆设计：对依赖、配置和发布动作预先准备回滚与人工接管点。
