CORPUS-DERIVED AGENT SKILL

把“AI 味”拆成可以测量、可以返工的写作流程

lieflat-gongwen 不是套话生成器。它把公文文体先分族、再分文种，读取对应 DNA 与范文，建立参数行，得到确认后写正文，最后跑自检器——把“像不像”与“对不对”分开。

01

它解决的不是“不会写”，而是“写得太像模板”

先做读者判断：需要的是开放文体的风格复现，还是固定格式文件的结构填充？

适合

开放文体

调研报告、领导讲话、工作意见、经验材料、工作方案、经验总结，以及党建/基层经验材料。

不覆盖

固定格式公文

通知、请示、批复、函等法定固定模板文体，README 明确把它们排除在量化蒸馏之外。

边界

参数不是事实核稿

句长、顿号密度和标题结构只能判断风格相似度，不能替代政策表述、事实、涉密和对外口径终审。

核心取舍：它让 Agent 更像“按文种路由的写作教练”，不是一台自动盖章的公文打印机。
02

安装与首次使用：先把 Skill 放进 Agent，再给它完整任务约束

官方 README 给出的是仓库目录安装路径；执行能力取决于宿主 Agent 是否能读文件和运行脚本。

# 仓库安装到 Claude Skills 目录（README 示例） git clone <this-repo> ~/.claude/skills/lieflat-gongwen # 或把整个目录复制到你的 Agent Skills 根目录 # 不要只复制一份参数表，入口 SKILL.md 与 supporting files 要一起保留

第一次提问应包含

  • 文种或写作目的
  • 读者、篇幅、事实材料
  • 哪些数字必须使用占位符
  • 是否先输出骨架等待确认

不要这样期待

它不会替你补真实地方数字，也不会因为参数都落在区间内就证明内容正确；README 要求无法核实的数字使用占位符。

没有终端怎么办

可以让 Agent 解释流程和生成清单；如果宿主没有本机文件/脚本能力，就不能声称已运行自检器。

03

六步工作流：第 3 步不能跳

差异不在“多写几句套话”，而在先读同文种 DNA 和范文。

01判文体族 → 判文种 → 定参数行
02读对应文种的骨架公式
03读同文种 DNA + 范文
04先出骨架，停下等确认
05按参数写正文
06跑自检，按报告修正
阶段输入输出验收问题
判别写作目的、读者、文种线索文体族、文种、参数 profile有没有把工作方案误写成调研报告？
取 DNA对应文种的 DNA 文档与范文标题长度、句式、分层与收束特征是否真的读过同文种材料，而非只读摘要？
骨架确认章节、事实、待补字段可审阅的 outline本地数字未确认处是否保留占位符？
写作自检正文 + 参数参数报告与返工点报告是提示还是硬冲突？是否经过人工核稿？
04

七种文体不是七个按钮：先看它们的“文种指纹”

README 将参数作为参考区间，而不是把均值当成合格线。

类别结构/篇幅线索可观察特征错误路由
调研报告约 2,500–3,700 字；2–5 个一级标题判断＋转折标题；段内“一是二是”；案例/原话套用工作方案的短业务标题
领导讲话公文族；按场合组织围绕讲话对象与任务展开写成无场景的观点清单
工作意见公文族；部署与要求方向、原则和任务关系用分析报告叙事代替行动要求
经验材料/经验总结公文族；案例与做法做法、机制、结果和可借鉴处只报结果，不写怎么做
工作方案公文族；大量三级标题目标、任务、分工、进度、保障用散文式长标题替代部署骨架
党建/基层经验材料约千字；零一级标题段首提领句、群众原话、链条叙事加多个一级标题变成压缩公文
05

数字怎么用：把“量化”当作自检提示，不当作自动评分

README 明确记录统计方法的弱点：正则可能只匹配字面，不等于理解语义。

可以测什么

平均句长、长句占比、顿号密度、一级/三级标题数量、“一是二是”频率、程式化结语出现率等。

不能证明什么

参数落入区间，不能证明事实真实、政策表述得体、材料可以公开，也不能证明某篇文本质量高。

发现异常怎么办

高覆盖率关键词先怀疑词表污染，逐条复核命中项；不要把一个自检数字直接当成结论。

# 修改 skill 或范文后运行（官方 README） PYTHONUTF8=1 python scripts/check_params.py # 语料数值化脚本（仅对授权、合规的本地材料使用） PYTHONUTF8=1 python scripts/strip_meta.py
06

版权、合规与核稿：这里比“像不像”更重要

语料不随 Skill 分发，README 的统计也不能替代你的材料来源审查。

语料边界

README 称原始语料因版权被移除，随包提供的是 DNA 文档与合成范文。合成范文只能借结构和节奏，不能借内容。

许可证边界

GitHub API 的 license 字段为 Other；仓库 LICENSE 文件标题为 PolyForm Noncommercial License 1.0.0。README 尾部的 MIT 表述冲突，应以 LICENSE 为准并审查商业、公司内部和客户交付用途。

最终责任

政治表述、事实依据、涉密信息、署名和对外口径必须由有权限的人工核稿人终审。Skill 的参数不能替代审批流程。

不要把“非商业”读成“无条件可用”。 PolyForm 条款的适用范围、组织身份、分发和改作边界应由使用方结合具体用途复核。
07

读者自检：第一次使用是否真的闭环？

把验收从“文风像”推进到“来源清楚、文种正确、事实可核”。

输入检查

  • 文种、读者和用途明确
  • 事实材料和本地数字有来源
  • 缺失信息使用占位符

过程检查

  • 先读 DNA 与范文
  • 骨架先确认再写正文
  • 参数报告逐项看命中样本

输出检查

  • 事实和政策表述经过人工核稿
  • 许可证与语料来源已审查
  • 对外版本没有内部敏感信息
一句话：把文种路由、语料 DNA、参数自检和人工核稿串成链路，才能减少“整齐但不像真的”——但任何参数都不是内容正确性的替代品。
