AUTO ENV ON CD · 自动进入，自动生效

cd 之后，环境变量自己就位

面向 Windows、macOS、Linux 的项目级环境变量方案：直接给出首选、复制即用的配置、工具边界、安全规则和团队落地 SOP。

推荐首选 / BEST FIT
mise

原生覆盖主流平台与 Shell；同一份 mise.toml 同时管理环境变量、PATH、运行时版本和任务。

1 个 Shell Hook首次安装后配置一次
1 份项目配置进入目录自动解析
自动加载 / 卸载离开目录恢复原环境
显式信任边界先审查，再允许项目配置
一句话结论

跨三大桌面平台选 mise；全员 Unix/WSL 可选 direnv

如果团队含 Windows 原生 PowerShell，使用 mise + mise.toml。若只需要环境变量且环境统一为 Linux、macOS 或 WSL，direnv + .envrc 更轻。

不要混淆：dotenvx、cross-env、`docker compose --env-file` 只在执行某条命令时注入变量；它们不会因为你执行了普通的 cd 就改变当前 Shell。
核心要点

先记住 4 件事

  1. 01
    自动加载依赖 Shell Hook外部进程无法直接修改父 Shell，必须由 Shell 执行工具生成的环境差异。
  2. 02
    离开目录必须自动卸载否则项目 A 的变量会污染项目 B；mise 和 direnv 都会维护差异。
  3. 03
    配置文件等同于代码它可能影响 PATH、执行脚本或改变工具来源，首次必须审查。
  4. 04
    密钥不应提交 Git提交声明和样例；真实值放本机 `.env`、密码库或 CI Secret。
机制图 · WHY A HOOK

为什么不能写一个普通命令，永久修改当前终端？

01你执行 cdShell 改变自己的工作目录
02Prompt Hook 触发每次提示符前检测当前路径
03mise / direnv 计算差异读取项目配置，比较加载前后环境
04Shell 执行导出语句真正修改当前 Shell 的进程环境
05离开时反向恢复撤销项目变量与 PATH 变化

事实：环境变量属于进程状态；子进程只能把“应如何修改”的指令返回给父 Shell，不能直接回写父进程。因此所有可靠方案都需要激活脚本、Hook 或使用一个新的子 Shell。

敏感性分析

什么时候推荐会翻转？

全部是 Linux/macOS/WSL

如果把 Windows 原生兼容权重降到 0，并把“单一职责、极简”提高，direnv 会与 mise 进入同一梯队，甚至成为首选。

密钥加密与生产注入优先

dotenvx 会成为密钥层首选，但仍建议由 mise 负责目录自动激活，或仅使用 dotenvx run -- command 做最小暴露。

环境必须完全可复现

当需求从“变量自动加载”升级为“编译器、系统库、服务均可复现”，devenv/Nix 才值得承担复杂度。

GET STARTED · MISE

首选方案：三步完成跨平台自动加载

01

安装并激活

每台机器只做一次。激活不是可选步骤；没有它就不会随 cd 改变当前 Shell。

02

项目写 mise.toml

提交非敏感声明；真实密钥放 `.env`，并加入 `.gitignore`。

03

审查、信任、验证

先看配置，再运行 `mise trust`；进入与离开目录各验证一次。

PowerShell · 安装 + 写入 Profile + 立即激活
winget install jdx.mise
New-Item -ItemType Directory -Force (Split-Path $PROFILE) | Out-Null
Add-Content $PROFILE '(&mise activate pwsh) | Out-String | Invoke-Expression'
. $PROFILE
mise --version

也可使用官方推荐的 `scoop install mise`。若 Profile 已有激活行，不要重复追加。

Zsh · 官方 Shell 专用安装器
curl https://mise.run/zsh | sh
exec zsh
mise --version

也可 `brew install mise`，再按需将 `eval "$(mise activate zsh)"` 写入 `~/.zshrc`。

Bash · 官方 Shell 专用安装器
curl https://mise.run/bash | sh
exec bash
mise --version

生产或受控环境建议固定版本并校验安装脚本/二进制；不要盲目管道执行未知网络脚本。

同一个仓库，三大平台复用

如果打开新终端时已经处于项目目录，却没加载变量，先确认 Profile 的激活行已生效，再用 mise doctor 检查 Hook，而不是反复修改项目配置。

DIR​ENV · 条件性首选

纯 Unix / WSL 团队的极简做法

.envrc
dotenv_if_exists .env
export APP_ENV=development
PATH_add bin
首次授权
direnv allow .

direnv 会在每次提示符前查找当前目录或父目录的 `.envrc`，授权后在 Bash 子 Shell 中执行并捕获导出的变量；退出目录时自动卸载。

Windows 边界

GitHub Release 已提供 Windows 构建并包含 PowerShell 支持，但官方首页仍把 Unix-like OS 列为前置，而且 `.envrc` 的执行模型依赖 Bash。对 Windows 原生团队，先做 POC 再标准化。

DOTENVX · 安全补充层

当密钥需要加密或只给单条命令

运行时注入
dotenvx run --redact -- node app.js

dotenvx 跨平台支持明文与加密 `.env`，并可在运行时脱敏日志。它的安全模型更适合 CI、生产和 AI CLI，但不会自动修改当前 Shell。

组合建议

普通开发变量交给 mise；高敏感密钥尽量不常驻当前 Shell，使用 dotenvx 或密码库按命令注入。

最小权限

变量一旦进入当前 Shell，后续所有子进程通常都能继承。自动加载越方便，越不应装入生产密钥。

TEAM SOP · 落地边界

团队实施：配置可共享，密钥不可共享

A

仓库提交

mise.toml、`.env.example`、`.gitignore`、README 安装说明；必要时锁定工具版本。

B

个人本机

安装 mise、激活 Shell、从样例复制 `.env`、从密码库填真实值、审查并 trust。

C

CI / Agent

避免依赖交互式 Prompt Hook；使用 `mise exec -- command` 或 `mise run task`，密钥来自 CI Secret。

安全铁律

不要全局设置“进入任何目录都无条件读取 `.env`”，也不要对整个磁盘关闭 trust。克隆陌生仓库后，先查看 `mise.toml`、`.envrc`、hooks 和 tasks；信任是一次代码审查动作，不是报错消除按钮。

排障速查

变量没有自动出现，按这个顺序查

  1. 01
    确认二进制可见mise --version；找不到命令先处理 PATH。
  2. 02
    确认激活脚本已执行重新打开终端，或 source / dot-source 当前 Shell Profile。
  3. 03
    确认配置被发现在项目目录运行 mise config ls、mise env --dotenv。
  4. 04
    确认信任状态mise trust --show；只信任你已经审查的目标文件。
  5. 05
    区分交互 Shell 与 IDE/CI非交互进程可能不读 Profile；改用 mise exec 或 IDE 的显式环境入口。
已知风险与未知项

不会影响首选，但实施前要知道

已确认：mise 配置可包含会执行代码的 directives、hooks 与 tasks，因此官方提供 trust 模型；敏感变量的 redaction 主要用于 mise 任务输出，并不能阻止所有子进程读取环境。

平台差异：Windows 环境变量名通常不区分大小写；macOS/Linux 区分。统一使用大写蛇形命名，避免同时出现 `Path` / `PATH` 或 `Api_Key` / `API_KEY`。

未实测：你的具体 PowerShell 版本、终端（Windows Terminal/VS Code）、企业执行策略与代理可能影响激活。若是全团队推广，建议先在 1 台 Windows + 1 台 macOS/Linux 做 15 分钟 POC。
