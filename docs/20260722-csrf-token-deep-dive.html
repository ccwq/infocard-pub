csrftoken
认证链路

CSRF Token 证明"这个请求是否来自可信的前端页面"。它不加密，不验证权限，只验证来源。

什么是 CSRF：浏览器 Cookie 的双刃剑

攻击者借用已登录的浏览器，自动携带 Cookie 发起有副作用的请求

🎯攻击者恶意网页
→
🌐浏览器自动带 Cookie
→
🏦目标服务端只验 Cookie → 被骗
GET /transfer?to=attacker&amount=10000 HTTP/1.1 ← 恶意网页诱导浏览器发起请求 Cookie: session=abc123 ← 浏览器自动携带已登录 Cookie
HTTP/1.1 200 OK ← 服务端只验证 Cookie，误以为是你本人操作

攻击者不一定需要读取响应——只要能"借用"你的浏览器和登录态触发请求，就能造成风险。转账、修改邮箱、删除数据、创建订单等操作都是常见目标。

csrftoken 如何阻止 CSRF

Double Submit 模式：同一令牌从 Cookie 和请求头两处提交，服务端比对

① 服务端下发 Token

登录成功后，服务端同时下发登录 Cookie 和 CSRF Cookie。前者证明身份，后者携带随机令牌。

Set-Cookie: session=abc123 ← 身份 Set-Cookie: csrftoken=7e1a…9b42 ← 来源校验

② 前端读取并显式提交

前端 JavaScript 读取 CSRF Cookie 的值，复制到自定义请求头或表单字段。这是"显式提交"，区别于浏览器自动携带。

POST /api/profile Cookie: session=abc123; csrftoken=7e1a…9b42 X-CSRFToken: 7e1a…9b42 ← 显式提交

③ 服务端比对

服务端收到请求后，同时检查 Cookie 里的 csrftoken 和请求头里的 X-CSRFToken 是否一致。缺失或不一致 → 403 Forbidden。

Cookie[csrftoken] == X-CSRFToken → 一致 → 处理请求 → 不一致 → 403

④ 为什么攻击者伪造不了

恶意网页可以让浏览器自动带 Cookie，但通常无法读取目标站点的 CSRF Cookie（受同源策略限制），因此构造不出正确的 X-CSRFToken 请求头。

⚠ 前提：应用没有 XSS。XSS 可以直接读取 CSRF Cookie。

为什么 csrftoken Cookie 不能设 HttpOnly

登录 Cookie → HttpOnly ✓

登录会话 Cookie 设置 HttpOnly：浏览器 JavaScript 无法读取。即使页面存在 XSS，攻击脚本也拿不到会话 Cookie，避免被盗用登录态。

CSRF Cookie → 不能 HttpOnly

前端必须能读取 CSRF Cookie 才能把它复制到请求头。如果设置 HttpOnly，JavaScript 无法获取值，就无法构造正确的 X-CSRFToken。

// 需要这样读取： const csrf = getCookie('csrftoken') headers:{'X-CSRFToken': csrf}

这意味着：CSRF 防护和 XSS 防护必须配合使用。单独一个 csrftoken 无法防御 XSS；单独的 HttpOnly 无法防御 CSRF。

认证重构检查清单：CSRF 链路五步

每一步缺失都是 CSRF 漏洞

①
服务端下发 csrftoken Cookie 登录成功后同时 Set-Cookie，而非只在某次请求时才给
②
浏览器保存 Cookie 设置合理 SameSite（Lax 或 Strict），避免 SameSite=None 在跨站场景滥用
③
前端请求封装统一读取并附加 所有 POST / PUT / PATCH / DELETE 请求都要走统一封装，自动加 X-CSRFToken
④
服务端比较 Cookie 值与请求头值 不一致 → 403；不能降级为只检查请求头或只检查 Cookie
⑤
一致 → 继续处理 此时才执行修改操作；高风险操作（转账、删数据）可叠加额外确认步骤

还需要检查：Secure（HTTPS only）、Domain/Path 范围、Origin/Referer 头校验、CORS 配置，以及 XSS 防护（CSP、输出转义）。

三个常混淆的概念：CORS · CSRF · XSS

CORS 问：

一个源的 JavaScript 能不能读取另一个源的响应？

服务器显式允许（Access-Control-Allow-Origin）后，浏览器才放行跨域读取。是一种"读取权限"机制。

≠ CSRF 防护。CORS 只管读，不管写。

CSRF 问：

恶意页面能不能借用我的登录态执行修改操作？

利用浏览器自动携带 Cookie 的特性。防护核心：让请求不是"纯浏览器自动触发"，而需要前端显式参与。

≠ CORS 替代品。两者解决不同维度的问题。

XSS 问：

攻击者的 JavaScript 能不能在我网站上执行？

恶意脚本注入后可以读取任意 Cookie（除非 HttpOnly）、操作 DOM、发起任意请求。是最危险的攻击向量之一。

可绕过 CSRF 防护：XSS 能直接读取 csrftoken Cookie。

CORS：限制跨域读取 → 蓝 CSRF：防止跨站伪造请求 → 黄 XSS：防止恶意脚本注入 → 红 · 三者有关联，但不能相互替代

两句话总结

L2 · 简单比喻版

csrftoken 是银行给前端的一张"一次性暗号"。浏览器可以自动带登录 Cookie 进门，但只有带上正确暗号的请求才会被当作"你本人"处理。

L5 · 技术机制版

CSRF Token 利用浏览器同源策略保护一个不可预测的随机值，要求前端将其以自定义请求头或表单字段显式提交；服务端比对 Cookie 中的值与请求头中的值，区分"浏览器自动携带登录态的跨站请求"和"可信前端主动发起的请求"。

自测

为什么攻击者即使能自动携带 session Cookie，通常仍无法伪造正确的 X-CSRFToken？

参考答案：攻击者的网页通常无法读取目标站点（bank.com）的 CSRF Cookie（受同源策略限制），因此不知道正确的随机令牌值，也就构造不出匹配的自定义请求头。服务端要求 Cookie 中的值与请求头中的值完全一致，两者都正确才能通过。
