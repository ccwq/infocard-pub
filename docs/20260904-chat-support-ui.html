THE SHORT ANSWER

后端完全自己写：选 Chatscope

它是 React 聊天 UI 组件库，不绑定后端。你控制 API、实时连接、AI/RAG、数据库、用户体系和知识库，得到最干净的边界。

  • 适合定制右下角悬浮按钮与弹窗
  • MIT，迁移成本低
  • 坐席后台、工单、持久化需自建
THE FASTEST PLATFORM

快速拥有完整客服：选 Chatwoot

它自带网站聊天 Widget、坐席、会话、标签、自动化、Webhook/API、Help Center 和多渠道 inbox。

  • 先上线，再逐步替换部分服务
  • 支持 VM、Docker、Kubernetes 等部署路径
  • Widget、API 和许可证边界要单独核验
评分权重沿用你的输入：自定义后端 30%、弹窗 UI 20%、前端可扩展性 20%、部署 15%、成熟度 10%、License/迁移风险 5%。分数是相对筛选，不是安装、压测或生产验收结论。

02

四个项目：你究竟在买什么

“前端能改”不等于“后端不绑定”；下面把每个项目的真实边界拆开。

01 / HEADLESS UI LAYER

Chatscope Chat UI Kit React

官方定位是开源 React 聊天 UI toolkit。README 给出 npm 安装、MainContainer、ChatContainer、MessageList、Message 和 MessageInput 示例，并提供 Storybook；另有 use-chat hook 管理聊天状态。

  • 自由实现悬浮按钮、弹窗、消息列表、输入框和快捷问题卡片。
  • 可接 REST、WebSocket、SSE 或流式 AI 回复。
  • UI 与服务端解耦，适合 Next.js/React 产品。
  • 不含坐席后台、联系人、工单、会话分配和消息持久化。
结论：后端自己写是硬约束时首选；想今天就有客服后台时，它不是完整答案。
02 / FULL SUPPORT DESK

Chatwoot

官方定位是开源、自托管的客户支持平台。资料列出网站 Live Chat、邮件、社交/即时通讯渠道、统一 inbox、Help Center、自动化、Webhook/API 和报告。

  • 已有 Widget、坐席、标签、自动分配和业务时间。
  • 官方 self-hosted 文档覆盖 Linux VM、Docker、Kubernetes 与云部署。
  • 完全自定义后端通常意味着 fork 前端或适配其数据模型与 API。
  • Widget 与平台 API 耦合深于 UI Kit。
结论：先拥有完整客服，再渐进替换服务；不是最干净的自建后端起点。
03 / OMNICHANNEL WORKSPACE

Rocket.Chat Omnichannel

Rocket.Chat 是更大的实时通讯平台，官方资料覆盖团队沟通、客户沟通、自托管、隔离网络部署和 Apps-Engine 扩展；Omnichannel 是其中的客服方向。

  • 适合客服中心与团队协作、多渠道、权限、路由一起建设。
  • 可选 Docker、Podman、Kubernetes 或 air-gapped 路径。
  • 部署、升级、资源占用与二次开发成本更高。
  • 只拿一个轻量弹窗而不使用整个平台，投入产出不划算。
结论：企业级多渠道确实是需求时再评估。
04 / PRODUCT MESSAGING

Chaskiq

Chaskiq 面向客户沟通、产品内消息、支持和营销。官方 README 列出 Web Messenger、会话路由、GraphQL/OAuth API、Webhook、Help Center、GDPR consent、审计和角色权限。

  • 更接近现代 SaaS 的产品内消息场景。
  • 开发资料列出 Ruby、PostgreSQL、Redis 等依赖。
  • 社区和生态小于 Chatwoot、Rocket.Chat，长期维护需 POC。
  • 开源能力与商业许可有分界，商业使用需看当前条款。
结论：想二开完整客户沟通系统且觉得 Chatwoot 太重时列入 POC。
03

两条可执行架构路线

第一条把客服能力拆成自己的产品；第二条先使用平台，再替换局部。

ROUTE A / MAXIMUM CONTROL

React UI + 自己的后端

Next.js / React
+ Tailwind CSS
+ Chatscope Chat UI Kit React
+ REST / WebSocket / SSE API
+ AI / RAG service
+ DB / auth / knowledge base

适合复刻独特弹窗、控制数据模型、接入自有 AI/RAG 和用户体系。代价是自己处理消息持久化、在线状态、重连、流式增量、客服坐席、审计与权限。

ROUTE B / FASTEST TIME TO VALUE

Chatwoot + Webhook/API

Chatwoot self-hosted
+ brand / widget customization
+ Webhook / API integration
+ your AI or workflow service
+ gradual replacement

适合先上线标准客服能力，再把 AI、知识库或部分服务替换成自己的实现。提前确认 API 边界、数据导出、升级策略和许可证适用范围。

04

安装与最小 POC

先验证 UI、实时连接和数据边界，不要第一次就做全量迁移。

CHAT UI KIT / FIRST RENDER

Chatscope

npm install @chatscope/chat-ui-kit-react npm install @chatscope/chat-ui-kit-styles

官方示例使用固定高度容器承载聊天界面：

<div style={{position:"relative", height:"500px"}}> <MainContainer> <ChatContainer>...</ChatContainer> </MainContainer> </div>

第一轮只验证消息列表、输入区、滚动和弹窗布局；第二轮再接你的 REST/WebSocket/SSE。

PLATFORM / ISOLATED POC

三个完整平台的共同验证步骤

  1. 按官方当前文档启动隔离开发实例。
  2. 只接入一个测试网站 Widget 和一个 inbox。
  3. 验证访客消息、坐席回复、Webhook/API 和重启恢复。
  4. 记录 CPU、内存、数据库、Redis、日志、备份和升级成本。
  5. 用脱敏真实会话测试导出，再决定是否迁入生产数据。
“支持 Docker”只说明存在部署路径，不等于你的生产环境已验证。本卡未在你的 Windows/Node/现有项目中安装或实测。
05

按场景选：决策树比总分更可靠

从硬约束开始筛选，避免为了一个漂亮 Widget 引入整个平台。

A

后端完全自己写

选 Chatscope。先完成悬浮按钮、ChatWindow、一条流式回复，再补会话、鉴权、持久化和人工接管。

B

最快上线客服

选 Chatwoot。先用 Widget、坐席和 inbox，再用 Webhook/API 接自己的 AI 服务。

C

企业级多渠道

评估 Rocket.Chat Omnichannel。只有团队协作、权限、多渠道和隔离网络确实需要时才接受系统重量。

D

产品内消息和营销

把 Chaskiq 放入 POC，重点验证社区、文档、数据模型和商业许可。

E

复刻现成弹窗

优先 Chatscope：组件层不会把 UI 绑在客服平台对象模型上，CSS、布局和交互可以自己重做。

F

客服 + AI + 知识库

先问清谁拥有会话状态和数据；自建路线由你负责，平台路线要核对 API、Webhook、导出和升级兼容。

06

许可证、迁移与数据边界

“开源”只回答源码可获得，不自动回答商业分发、企业目录和第三方依赖。

上线前必须单独核验

  • Chatscope：官方仓库为 MIT；保留版权与许可声明，第三方依赖另行审查。
  • Chatwoot：仓库 LICENSE 对核心内容、enterprise 目录和第三方组件有分层说明，不能简单概括为单一许可证。
  • Rocket.Chat：LICENSE 对 enterprise 目录与其余 MIT 部分有区分；企业功能和 Apps-Engine 要看对应条款。
  • Chaskiq：README 同时说明开源能力与商业许可路径；闭源商业产品必须核对当前商业许可。
  • 数据：分别确认客服消息、访客标识、附件、日志、分析数据和 AI 上下文的存储、备份、删除、导出、权限与供应商访问范围。
  • 迁移：重点测量会话模型、用户身份、消息 ID、附件、Webhook 重试、实时连接和历史导入。
07

验收清单：POC 通过才进入生产评审

把“看起来能用”拆成 UI、后端、运维和合规四组事实。

□ UI / UX
悬浮按钮、弹窗尺寸、窄屏、键盘、焦点、长消息、空态和错误态。
□ Backend
REST/WebSocket/SSE、流式增量、重连、幂等、鉴权、坐席接管和持久化。
□ Operations
实际资源、日志、监控、备份、升级、回滚和恢复时间。
□ Data
访客身份、会话、附件、AI 上下文、导出、删除、权限、审计与保留周期。
□ License
锁定当前 commit/release，分别审查核心、enterprise、第三方和商业许可。
□ Migration
用脱敏真实会话做导入/导出测试，记录字段映射、丢失字段和回退方案。
