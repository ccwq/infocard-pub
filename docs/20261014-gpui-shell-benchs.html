gpui-shell-benchs：五款 AI 从零生成的原生应用，和它们的真实账单

只给一张设计图或一句 brief，加上 gpui-shell 生成的 AGENTS.md 与 gpui-kit.d.ts，让 AI 编码 agent 直接产出能跑的原生应用。这个仓库把五款应用的全过程记了下来，用来量化两件事：agent 有多快多便宜能做完，以及这层运行时到底能承载多复杂的应用。

01

先做这一步

装运行时，再用三条命令验证任意一个应用

没有预编译包，运行时从源码安装：

# 安装 gpui-shell 运行时 cargo install --git https://github.com/longbridge/gpui-kit gpui-shell --locked

依赖 Rust/Cargo 与该平台 GPUI 的构建依赖。装好后，面对 apps/ 下任意应用的三条命令是：

# 生成 gpui-kit.d.ts（不提交进仓库） gpui-shell types -d apps/<name> # 加载、渲染、物化一次 gpui-shell check -d apps/<name> # 运行，保存即热重载 gpui-shell dev apps/<name>
推文说"不需要用 Rust 开发、直接 JS、不编译"，这是作者观点，不是安装事实。 README 的安装步骤仍是 cargo install --git https://github.com/longbridge/gpui-kit gpui-shell --locked，且需要 Rust/Cargo 与该平台 GPUI 构建依赖。不写 Rust、不编译的只是应用层——它通过 gpui-shell types 生成的 gpui-kit.d.ts 调用内置模块。运行时本身与首次安装依赖 Rust 工具链。
02

核心机制

输入是设计图或 brief，中间产物是两份类型文档，产物是能跑的原生应用

设计图 / 一句 brief唯一的人类输入
→
gpui-shell types生成 AGENTS.md + gpui-kit.d.ts
→
AI 编码 agent只按这两份文档写 JS/TS
→
apps/<name> 原生应用真实数据、可落盘、可导出

agent 能看到的只有生成的 AGENTS.md 与 gpui-kit.d.ts，以及 gpui-kit、gpui-base、gpui-component、gpui-fps 这几组内置模块和相对模块。没有 npm 包，没有 DOM 或 Web API。

量化目标一：AI 友好度

只给设计图或 brief，看 agent 多快、多便宜能做出可用的原生应用。计量口径就是 wall 时长、active 时长、prompts 条数、token 消耗——也就是本卡第 04 节那张表。

量化目标二：运行时能力上限

gpui-shell 运行时能否承载真正有用的应用，而不只是静态界面。判定标准是数据来自真实来源或真实计算、存盘撑得过重启、导出文件别的软件打得开。

仓库对每个应用的四条约束

  • 真实功能：数据来自真实来源（本地文件、网络 API、系统设施）或真实计算，不是写死在界面里的数字；存盘要落盘并撑过重启；导出要产出别的软件能打开的文件；要有加载、空、失败、重试状态；破坏性操作要确认且尽量可撤销；纯逻辑（解析、计算、文件格式）拆成独立模块并用 node --test 覆盖。
  • 只用 gpui-shell：只用 AGENTS.md 列出的内置模块与相对模块，不用 npm 包，不用 DOM 或 Web API；gpui-shell.json 只申请最窄授权（fs、network、clipboard、process），并在应用 README 里解释每一项。
  • 布局与文档：应用放在 apps/<kebab-name>/，id 为 com.huacnlee.<name> 且保持稳定；每个应用有 README，写明它是什么、Reference 段注明原始设计或软件并给链接、如何运行、功能与快捷键、权限、与原作的差异和已知限制。
  • 记录成本：尽量一次会话从零做到完成，记下开始时间并保留 transcript；完成后跑 scripts/session-stats.py，把 wall、active、prompts、tokens、model 加进表里，异常情况写进注释。
03

可执行步骤

安装 → 生成类型与检查 → 跑起来

  1. 装运行时：cargo install --git https://github.com/longbridge/gpui-kit gpui-shell --locked。这一步会编译 Rust 运行时，需要 Rust/Cargo 与该平台 GPUI 的构建依赖。
  2. 生成类型：gpui-shell types -d apps/<name>，产出 gpui-kit.d.ts。它是生成物，不提交进仓库。
  3. 检查一次：gpui-shell check -d apps/<name>，加载、渲染、物化一遍，能在不开窗口的情况下发现问题。
  4. 跑起来：gpui-shell dev apps/<name>，保存即热重载，适合边改边看。
  5. 换应用：把 <name> 换成 apps/ 下的任意目录名即可。
# apps/ 下的五个目录 apps/folio-deck # Folio Desk，Gmail 桌面客户端 apps/tendra # Tendra，投标流水线看板 apps/ocean-view # OceanView，船队实时追踪 apps/signed # Signed，PDF 签名器 apps/skills-manager # Skills，agent skills 管理器 # 逐个跑 gpui-shell check -d apps/signed gpui-shell dev apps/signed

安装 / 检查 / 运行的分工

types 只生成类型声明，check 做一次加载 + 渲染 + 物化，dev 才是长期运行的开发模式。想验证"这个应用在 gpui-shell 里到底起不起得来"，用 check 就够。

Total 不是"新烧掉的 token"，它是未缓存输入 + 缓存写入 + 缓存读取 + 输出。把四个应用拆开看，缓存读取占了压倒性的比例，未缓存输入与输出单独列在下面：

这些数字怎么来的

  • Claude Code transcript：~/.claude/projects/<escaped path>/<session>.jsonl；子 agent 在 <session>/subagents/agent-*.jsonl。
  • Codex transcript：~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl。
  • 统计脚本：python3 scripts/session-stats.py <jsonl> [更多 jsonl] [--from ISO] [--to ISO]。
  • Claude Code 按 message id 去重后累加每次调用的 usage；Codex 取最后一个 token_count 事件的累计用量；prompts 只数人写的消息（含只发截图的消息），不数工具结果和注入的系统内容。

已知限制与边界

运行时踩过的 12 条坑（逐条含绕法与出现的应用）、成本口径、推文与 README 的差别

运行时实测踩到的坑

下面每一条都带了实际用的绕法，以及它出现在哪款应用里。照 AGENTS.md 直写会失败的地方已经标出来了。

  1. 01app 之外的文件授权被忽略：manifest 的 fs 授权只有 ${pluginDir} 与 ${dataDir} 生效，所以 ~/.claude/skills 之类用户目录无法直接读写。
    绕法：用白名单命令（base64、ls、cat、mv、cp、find）。出现：signed、skills-manager。
  2. 02运行时没有 home 目录、环境变量或数据目录路径，import.meta.url 是 undefined。
    绕法：安装器写绝对路径、用 find 定位数据目录。出现：signed、skills-manager。
  3. 03没有 TextEncoder / TextDecoder：在 Node 测试里正常的代码在 app 里崩。
    绕法：手写 UTF-8 编解码。出现：signed。
  4. 04window.open_dialog 与 window.push_toast 抛错，报 "needs a ShellRoot as the window's first view"。
    绕法：对话框和提示由视图自己画。出现：signed、skills-manager。
  5. 05gpui-component 用 new Type(...) 构造，而 AGENTS.md 说用 Type.new(...)（这条只对 gpui-base 成立）；照文档写会立即失败。
    出现：signed、skills-manager。
  6. 06gpui-component 的 Input 不能用 gpui-base 的 InputState，而它自己的状态又没有 change 或 submit 事件。
    绕法：改用 gpui-base 的 input。出现：signed。
  7. 07没有捏合缩放手势事件，只暴露滚轮事件。
    绕法：用滚轮和按钮缩放。出现：ocean-view。
  8. 08run -d 把数据存在 <dir>-<hash> 下，而不是 manifest 的 id，所以开发副本和安装副本不共享数据，路径也很难展示。
    出现：signed。
  9. 09fs/promises 缺 stat、rename、readlink；fetch 缺 arrayBuffer()。
    绕法：通过 GitHub API 走 base64、元数据从命令取。出现：skills-manager。
  10. 10fetch 不发 User-Agent，GitHub API 因此返回 403。
    绕法：自己设 header。出现：skills-manager。
  11. 11flex_shrink() 不传参数会在渲染时失败，报 "expected a number, got nil"。
    出现：skills-manager。
  12. 12line_height(n) 是倍数，与其他长度参数（像素）不一致。
    出现：signed。

成本数据的口径

Wall 与 Active 不是一回事

Wall 是会话首末事件之间的时长；Active 只累加短于 15 分钟的间隔，所以过夜和离开的时间不计入。folio-deck 的 651 min wall 里有整整一次过夜暂停。Total 是未缓存输入 + 缓存写入 + 缓存读取 + 输出。

  • 哪些是估算：folio-deck 两个阶段，阶段 1 已测量（591 min wall 含一次过夜暂停、61 min active、14 prompts、6,901,473 tokens）；阶段 2 没有本地 transcript，≈60 分钟与 ≈6.8M token 是作者提供、并按阶段 1 速率（≈113k/active min）估算的。表中 folio-deck 一行的 ≈ 就是这个意思。
  • 哪些不计入：事后在父会话里做的修复不计入，例如 signed 的 TextEncoder 崩溃。父会话中传递的需求计入 prompts，signed 为 19 条、ocean-view 为 4 条。
  • 表里有收尾时间：tendra 的会话含最后一次提交之后约 50 分钟的收尾与上下文压缩。
  • ocean-view 是并行之一：它是一个 Claude Code 会话的三个子 agent 并行建造之一，分两轮——先建，再修地图拖拽、缩放、点击与布局。它的 71 min / 42 min 不代表这个应用独占了一个会话的时长。
  • 没核对的：gpui-shell 与 Rust 版本 GPUI 的性能对比没有逐项核对，README 也没给这份对比数据；推文视频里的具体 case 对应仓库中哪个 app，没有逐帧核对。

推文说法与 README 的差别

"你可能都不需要用 Rust 来开发 GPUI 应用了，直接 JS 就行了，不编译才是最快的"——这是作者本人在 推文原文 里的说法，状态是作者观点。README 显示运行时本身仍用 cargo install --git ... gpui-shell --locked 安装，需要 Rust/Cargo 与该平台 GPUI 构建依赖；应用层是 JS/TS，通过 gpui-shell types 生成的 gpui-kit.d.ts 调用内置模块。也就是：应用不写 Rust、不编译应用代码，但运行时与首次安装仍依赖 Rust 工具链。推文里"仍能获得匹配 Rust 版本 GPUI 的性能"这一句，仓库里没有对应的核对数据。

推文另一条"仅仅给一张参考图，用来测试 AI 基于它 + GPUI Shell 实现完成一个应用"与 README 一致：方法论同样写"只给设计或 brief"，并要求每个应用在 README 的 Reference 段注明原始设计来源。

不得商用

代码用 MIT；但每个应用的视觉设计、交互与产品功能归其参考的原设计或软件作者所有。这些应用只为评估 gpui-shell 而存在，不得商用；商用前要拿到原作者的许可，或先把设计换成自己的。所有示例数据均为虚构。
