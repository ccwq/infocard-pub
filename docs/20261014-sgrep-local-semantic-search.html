sgrep ≠ ripgrep

01

读者第一动作：先把命令跑起来

可直接复制

前置条件：Rust 1.90 或更新版本，以及 ripgrep。

step 1 — 装 ripgrep
brew install ripgrep
step 2 — 从 git 安装 sgrep
cargo install --git https://github.com/context-dot-dev/sgrep --locked
Alternative

不用 cargo 的话

从 releases/latest 下载 macOS Apple Silicon 二进制。

Upgrade

旧的 Python 安装要先卸载

旧版本如果是 Python 装的，先卸载：uv tool uninstall sgrep 或 pip uninstall sgrep。

为什么是两步：sgrep 本身靠 ripgrep 列出候选文件，所以 ripgrep 不是可选项，是前置依赖。
02

核心机制：切块、混合检索、静态向量

靠什么做到
Chunking

切块

  • ripgrep 列出文件，Rust 用 Chonkie + Tree-sitter 切成 passage。
  • 代码解析器支持 Python、C/C++、Go、Java、Rust、JavaScript/JSX、TypeScript/TSX；其余文件用文本切分。
  • 每个 passage 目标 2048 字符，按整行切。
Hybrid retrieval

混合检索

  • 取词法 top 200 与语义 top 200 合并：75% 语义 + 25% BM25，各自先缩放到 0–1。
  • 完全精确、大小写敏感的标识符匹配排最前（camelCase、下划线、美元符、数字）。
Static vectors

静态向量模型

  • embedding 用 Minish Lab 的 Potion Code 16M v2 与 Potion Base 8M：静态向量模型，每个 token 一个向量。
  • 查询时没有 transformer 前向，纯 CPU 搜索，向量归一化到 256 维。
  • 模型固定 revision，MIT 许可。
为什么还要 BM25 和精确匹配：静态向量平均会丢 token 顺序，可能丢上下文；因此额外加了 BM25 与精确标识符优先。
03

可执行步骤：安装 → 首次搜索 → 管道 → 模型 → 索引与缓存

照抄即可

① 首次搜索（会触发模型下载）

语义查询 · 代码目录
sgrep "when does a failed scrape consume credits" ./src

选项：-n 10 取十条，--json 出 JSON。

首次成本：首次搜索下载模型（32–34 MB）与所需解析器，之后可离线运行。源码与查询留在本机；本地索引会存 passage 的副本。

② 管道模式（给 ripgrep 的结果重排序）

rg --json -C 3 | sgrep --stdin
rg --json -C 3 'creditCost|shouldBill' ./src | sgrep "when does a failed scrape consume credits" --stdin
两条命令要在同一目录执行。

③ model code / text 怎么选

--model code

代码语义

代码库查询
sgrep "retry with exponential backoff" ./src --model code
--model text

文档 / 自然语言

文档目录查询
sgrep "how do refunds work" ./docs --model text

④ 索引与缓存控制

  • 索引缓存上限 256 MiB / 128 条，LRU 清理，30 天未用的清掉。
  • 超大条目不保存；缓存失败会退回无索引搜索。
  • 源码副本会一直留到清理或手动删除。
04

预期现象：执行后你会看到什么

验收口径
Output

返回文件 + 行范围

输出是命中的源码 passage 与其位置，不是生成的答案。--json 则给出结构化结果。

First run

首次会先下模型

第一次搜索下载 32–34 MB 模型与解析器，之后离线可用；查询与源码留在本机。

Pipeline

管道模式换序不换料

ripgrep 的 JSON 上下文进入 sgrep 后被重排序，两条命令必须在同一目录执行。

一句话验收：提问是英文句子，回的是文件路径和行号——没有解释、没有总结、没有改写。

已知限制与边界

先看清楚再用
Not this

它不做的事

  • 只返回源码 passage，不生成答案。
  • 不解析 PDF 与图片。
  • 静态向量平均会丢 token 顺序，可能丢上下文（所以才补 BM25 与精确标识符优先）。
Storage

缓存与副本

  • 索引缓存上限 256 MiB / 128 条，LRU 清理，30 天未用的清掉。
  • 超大条目不保存，缓存失败退回无索引搜索。
  • 本地索引会存 passage 的副本；源码副本会一直留到清理或手动删除。
Repo hygiene

语言统计与安装方式

  • GitHub 语言统计里 Python 字节数大于 Rust（README 说明本体是 Rust CLI，Python 用于测试与基准脚本）。
  • 旧的 Python 安装方式需要先卸载：uv tool uninstall sgrep 或 pip uninstall sgrep。
Maturity

项目很新

  • 2026-10-07 建仓，快照时 54 star，最新标签 v0.3.0（2026-10-09）。
  • README 给出的对照分工，不是全部替代关系：

ripgrep：适合已知名称、精确文本和正则。意图查询要 agent 先想出合适的模式，宽了结果太多，窄了会漏。

CK：本地语义与混合检索，多个 embedding 模型，带 MCP server。要计入索引构建、更新与查询时间。仓库承认在 CoSQA 上 CK 的语义模式赢过 sgrep。

mgrep：托管语义检索 + 重排 + agent 集成，文件同步到 Mixedbread，需要认证，本次基准未测。

RepoQA + CoSQA

600 道 RepoQA + 500 道 CoSQA，对比 CK、Jevgrep、ripgrep，sgrep 主分支 0fbe8e5。RepoQA 看结果里是否包含目标函数完整体（8000 源 token 内）；CoSQA 看标注片段是否出现在前十条。

Latency

2160 次计时调用

120 条固定查询、每条 6 次重复、2160 次计时 CLI 调用；模型与索引预热，中位与 p95 都含进程启动，全部在共享的 M5 Max 上串行执行。

这些数字不能证明什么

  • 这是本项目自己的基准，不是第三方评测。
  • ripgrep 用的是固定 literal-OR 查询，不是人或 agent 选的正则，所以不测量 agent 选查询的能力。
  • RepoQA 的度量是为检索改编的，不是官方代码生成分数。
  • 两个数据集都在开发期间被用过。
  • 图表中省略了存在构建失败或搜索超时的配置——廉价的失败不算成本优势。
  • 本机是四核 8 GiB Linux CPU 沙箱；结果只描述这个面板，不外推到其他机器与负载。
