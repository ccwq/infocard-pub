02从“风格”到“规范” · WHAT TO WRITE DOWN

DESIGN.md 最低结构

颜色主色、背景、语义色、对比度
字体字族、字号、字重、行高
组件按钮、卡片、导航、表单、状态
布局容器、网格、间距、断点
行为交互、反馈、动效、错误态
语气文案风格和 AI prompt guide

不要只记录色板

如果文件只有几个 HEX 值，Agent 仍然不知道什么时候使用它们。完整设计语言还应回答：什么是主层级？哪些元素必须对齐？卡片如何分组？移动端如何降级？哪些组件禁止重新发明？

错误：\n“请做得像 Stripe 一点。”\n\n可执行：\n“使用 8px 间距基线；正文 15/1.6；\n主操作使用深蓝实心按钮；\n移动端卡片单列，保留 16px 安全边距。”

品牌目录的参考价值

awesome-design-md 将品牌系统整理为 AI 可读取的 DESIGN.md，通常包含配色、字体、组件、布局、响应式、设计语气和 prompt guide。

它的价值不是让项目复制某个品牌，而是提供一套观察框架：把“品味”拆成可传递的工程信息。

03让 Agent 持续执行 · SKILL LAYER

Designer Skills：过程层

适合把设计决策拆成阶段和检查点，避免 Agent 直接从需求跳到代码。

  • 先追问目标和约束
  • 形成 DESIGN_BRIEF 与信息架构
  • 检查现有 tokens、组件和依赖
  • 从 375px 移动布局开始
  • 完成实现后按 brief 做 review

Taste Skill：品味层

作为“前端反模板”规则层，帮助 AI 避免默认 SaaS 外观。它适合快速接入，不等于完整的项目设计系统。

  • 约束常见模板化选择
  • 提醒层级、排版和视觉节奏
  • 适合快速建立审美底线
  • 不能替代项目专属 tokens

Impeccable：审查层

提供设计语言、命令和 deterministic detectors，用来发现 AI 生成界面的反模式。

  • 检查是否过度使用 SaaS 模板
  • 检测可重复的视觉问题
  • 适合作为生成后的质量门禁
  • 不是组件库，也不负责逆向提取
04决策树 · CHOOSE BY YOUR STARTING POINT

如果你已有产品

先提取，再固化。从 `/design sync`、代码扫描或人工审计开始，找出现有组件和 token；然后写入 DESIGN.md，并用 Designer Skills 约束后续改动。

已有 UI → 提取 Design System → DESIGN.md → review

如果你从零开始

先定义，再实现。用 brief、信息架构和 tokens 先把意图写清，再让 Agent 生成页面；Taste 可以作为反模板底线，Impeccable 负责检查。

brief → IA → tokens → frontend → detectors

如果你要迁移风格

不要只换 accent。需要保留结构语法、层级、组件锚点、响应式行为和文案语气；否则得到的只是配色变体，不是设计语言迁移。

观察 Design DNA → 重建结构 → 验证组件 → 多尺寸复核
05验收清单 · BEFORE YOU SHIP

内容层

  • 是否写清目标读者和使用场景？
  • 是否区分提取、固化、执行和审查？
  • 是否给出最小可执行示例，而非只列工具名？
  • 是否明确工具边界和证据来源？

工程层

  • DESIGN.md 是否包含颜色、字体、组件、布局和行为？
  • tokens 是否与现有代码一致？
  • 移动端、明暗模式和响应式是否有规则？
  • Agent 是否会先读取现有系统，而不是重新造组件？

审查层

  • 是否有 deterministic detectors 或 review 流程？
  • 是否检查模板化、层级混乱和低对比度？
  • 是否在多个尺寸下复核？
  • 是否保留人工批准和回滚入口？

最终判断：先把设计意图写成系统

FROM VISUAL TASTE TO EXECUTABLE DESIGN LANGUAGE

最可靠的路径不是寻找一个“万能 UI Skill”，而是把存量界面中的设计决策提取出来，写成 DESIGN.md 或 tokens，再用 Designer Skills 组织流程，用 Taste 和 Impeccable 守住生成质量。这样，Agent 获得的不是模仿对象，而是一套可解释、可复用、可验收的设计语言。

06A 路径实操 · EXISTING PRODUCT EXTRACTION

0. 先冻结调查对象

已有产品的第一步不是安装 skill，而是定义“什么算事实”。选择一条代表性用户路径：入口页、列表页、详情页、表单页至少各一张；同时保留对应源码、组件目录、token 文件、字体加载和运行截图。不要只调查营销首页，因为它往往不能代表产品内页的密度、状态和错误处理。

页面样本 + 源码 + 运行环境 + 截图 → 可追溯证据包调查输出必须能回指到页面、文件或 computed style；“感觉像”只能作为待验证假设。

1. 记录存量，不急着重构

先建立 inventory：颜色变量、字体族、字号层级、间距单位、圆角、阴影、z-index、断点、组件入口、状态类和第三方 UI 框架。把重复值分成“已命名 token”“局部硬编码”“疑似遗留”。同一个蓝色在按钮、链接和图表里可能承担不同语义，不能因为 HEX 相同就合并。

页面：/settings/profile 组件：Button / Input / Toast / Modal 事实：--color-primary 出现 38 次 假设：--color-primary 同时承担品牌色与操作色 待验：错误态、暗色模式、hover 是否复用该变量

2. 输出差异，而不是漂亮报告

提取的价值在于暴露不一致：同一组件的 padding 是否有三种写法？移动端是否存在另一套断点？设计稿与线上字体是否不同？旧页面是否绕过共享组件？把结果分为“保留事实”“需要决策”“禁止推断”三栏，后续 DESIGN.md 只吸收已经确认的规则。

07逐项调查与取舍 · KEEP / DOWNGRADE / DELETE

Claude Design · 保留为提取入口

调查事实：官方 Claude Design 文档把 design system 作为可持续复用的对象，支持从现有项目建立设计系统，并在后续生成中使用。与本卡目标最贴近的能力是“从存量界面开始”，而不是只给一个审美 prompt。

真正适合：你已经有网页、组件或品牌材料，需要先得到可讨论的视觉基线；团队想在生成新页面前，先把现有语言提取出来。

不能夸大：它是托管产品能力，不等于本地仓库里的可审计脚本；命令、可用范围和账号能力可能随产品版本变化。不能把一次同步结果当作代码库的规范真相，也不能跳过人工核对。

推荐：用 Claude Design 生成初稿 → 回到源码和浏览器核对 → 将确认项迁入项目 DESIGN.md保留理由：提取入口的匹配度最高；限制：可重复性、版本锁定和本地 CI 能力需由项目自行补齐。

Google DESIGN.md · 保留为规范核心

调查事实：官方仓库定义了 YAML front matter + Markdown rationale 的双层格式。CLI 提供 lint、diff、export；lint 会检查 broken reference、对比度、孤立 token、缺失 typography、section order 等结构问题；export 支持 Tailwind 与 DTCG 等输出方向。

真正适合：把提取结果变成项目级、可版本控制、可被不同 coding agent 读取的契约。机器值负责精确，正文负责解释“为什么”和“何时使用”。

风险边界：当前规范标注为 alpha，schema 和 CLI 仍可能变化；lint 通过不代表页面视觉正确，也不代表响应式和交互完整。必须把版本、来源和项目扩展字段写清楚。

Impeccable · 保留为验收与修复

调查事实：官方 README 描述为 1 个 skill、23 个命令和 61 条 deterministic detector rules；命令覆盖 init、document、extract、audit、critique、polish、harden、adapt 等。CLI 可扫描目录、HTML 或 URL，并输出人读诊断或 JSON；检测器覆盖模板化字体、渐变、卡片嵌套、行长、触控目标、标题层级等可重复问题。

真正适合：在已有产品提取后，检查新改动是否引入常见 AI 反模式；`document` / `extract` 可作为辅助生成 DESIGN.md 和提取组件的入口；`audit`、`harden`、`adapt` 适合接在垂直切片之后。

08把提取结果写成契约 · DESIGN.md FOR AN INCUMBENT SYSTEM

第一层：规范值

规范值是 Agent 不应自行发挥的部分。至少记录颜色角色而非颜色列表、完整字体层级、间距基线、圆角尺度、阴影/边框、容器宽度、断点和组件状态。每个 token 要能回到源码或截图证据；未经确认的值标注 provisional，而不是伪装成最终标准。

colors: canvas: "#..." surface: "#..." ink: "#..." action: "#..." danger: "#..." typography: body: {fontFamily: "...", fontSize: 1rem, lineHeight: 1.6} spacing: {xs: 4px, sm: 8px, md: 16px} rounded: {sm: 4px, md: 8px}

第二层：应用规则

同样重要的是“如何使用”。写清 action 色只用于什么、surface 如何分层、标题最多几级、表格什么时候允许密集、空态和错误态如何表达、移动端导航如何收缩、暗色模式是否是独立语义映射。把规则写成可判断的句子，避免“高级、简洁、现代”这类无法验收的形容词。

  • 主操作每个 viewport 只保留一个视觉主锚点
  • 列表页沿用现有行高与密度，不因新页面擅自变成卡片墙
  • 错误色必须同时有文字或图标，不只依赖颜色
  • 窄屏优先保留内容顺序，再决定隐藏次要装饰

第三层：边界和例外

存量系统一定有例外。不要把例外偷偷抹平；记录“例外在哪个页面、为什么存在、谁批准、何时复查”。组件 token 可以按 `button-primary`、`button-primary-hover` 等状态拆分，避免让 Agent 用一个值覆盖全部交互状态。

允许旧版结算页保留独立支付状态色
禁止新页面重新引入第二套按钮圆角
待决营销页与产品内页是否共用 display font
证据链接源码、截图、issue 或设计评审记录

09一条垂直切片的执行协议 · ONE CHANGE, FULL LOOP

输入包

给 Agent 的输入不能只有一句“优化设置页”。输入包包括：目标用户与任务、代表性截图、相关路由、现有组件入口、DESIGN.md、禁止触碰的范围、验收尺寸、回滚方式和本次变更的唯一目标。已有产品最怕范围漂移，所以先限制垂直切片。

目标：只改 profile 表单的错误态，不改导航、字体和整体布局输入越窄，越容易判断是设计语言改进，还是无授权重做。

执行协议

  1. 先读 DESIGN.md 和现有组件，不创建同名新组件。
  2. 搜索 token、样式覆盖和状态实现，列出将要修改的文件。
  3. 先实现最小垂直切片，保留原有路由和数据流。
  4. 在 375/390px 与桌面宽度各渲染一次。
  5. 运行 detector/audit，再做人工截图审查。
  6. 把新发现的规则或例外回写 DESIGN.md。

输出包

交付不只是代码 diff。至少包含：变更文件、遵循的 token、未遵循的例外、桌面/移动截图、检测器结果、已知风险和回滚点。若审查发现“看起来更漂亮”但偏离存量语言，应以系统一致性优先，而不是把主观美化当成功。

10最终验收矩阵 · EVIDENCE BEFORE ADOPTION

提取验收

  • 是否调查了真实页面，而不是只读设计稿或品牌站？
  • 每个关键 token 是否能回指源码、computed style 或截图？
  • 是否覆盖正常态、空态、错误态、加载态和窄屏？
  • 是否区分事实、推断、冲突和待决策项？
  • 是否识别局部硬编码与共享 token 的关系？

固化验收

  • DESIGN.md 是否同时包含机器值与应用理由？
  • 组件是否写了状态、尺寸、padding、颜色角色和响应式行为？
  • 是否记录版本、来源、例外和有意省略的章节？
  • lint/diff 是否通过；警告是否有明确处理？
  • 是否避免把 Taste 或样本库的通用审美写成项目事实？

执行验收

  • Agent 是否先探索现有代码再提出修改？
  • 是否只改一个垂直切片，且保留组件所有权？
  • 是否在真实移动端尺寸验证，而非只看桌面？
  • 是否运行 detector 并人工审查其误报与漏报？
  • 是否有截图、diff、风险和回滚证据？

11调查记录模板 · FROM OBSERVATION TO DECISION

记录一：页面证据卡

每个代表页面单独建立证据卡，不把多个页面的印象混成一个结论。记录 URL、路由、viewport、浏览器、登录状态、页面状态、截图时间和源码 commit。视觉参数要区分声明值与最终生效值：CSS 变量可能被组件局部覆盖，字体可能因加载失败回退，布局可能被运行时脚本改写。

Evidence ID: profile-error-mobile-01 Route: /settings/profile Viewport: 390 × 844 State: validation error / keyboard closed Observed: button height 44px; page padding 16px Source: components/ProfileForm.tsx + styles/form.css Confidence: confirmed by computed style + screenshot Open question: error summary是否与字段错误重复

记录二：规则候选卡

观察到重复事实后，才创建规则候选卡。规则必须写成“条件 → 行为 → 例外”，并保留反例。比如“所有卡片使用 8px 圆角”可能被一个核心工作台反例推翻；更准确的写法是“信息型卡片使用 8px，编辑器画布保持无圆角；营销页例外需注明范围”。

条件产品内信息卡，非全屏编辑画布
行为使用 surface + 8px radius + 1px border
例外拖拽工作区沿用无边框平面
证据三个路由、四个实例、一个反例

记录三：冲突卡

当两个页面不一致时，不要立即“选一个最好看的”。先判断冲突类型：版本迁移、业务语义不同、局部遗留、响应式变体，还是确实的缺陷。冲突卡要有 owner 和决策期限；在决策完成前，Agent 只能沿用目标页面现状，不能自行统一全站。

  • 冲突：按钮有 40px 与 44px 两种高度
  • 可能原因：桌面密度与触屏目标不同
  • 需要调查：断点、输入设备、可访问性要求
  • 暂定规则：窄屏 44px，桌面沿用现有 40px
12TOKEN 映射与组件边界 · DO NOT FLATTEN THE SYSTEM

从原始值到语义 token

提取时可以先保留原始值，再逐步映射到语义层。不要一开始就把所有相近颜色合成一个 `blue-500`。原始值说明系统现在是什么，语义 token 说明系统打算如何使用；两者混在一起会让迁移不可逆。

raw: 候选语义：action-primary / link / chart-series-2 验证：检查三类使用是否共享 hover、对比度和禁用态 结论：若行为不同，保留三个语义 token，即使底层色值暂时相同

组件边界要跟着所有权走

DESIGN.md 里的组件不是视觉清单，而是 Agent 修改边界。写清组件在哪里定义、谁负责组合、哪些 props 是稳定 API、哪些样式只能通过 token 修改。若页面有局部 wrapper，不要因为视觉相似就把它宣称为共享组件。

共享组件Button 的状态、尺寸、禁用和 loading
页面组合ProfileForm 的字段排列和错误摘要
业务语义支付失败提示的文案和恢复动作
禁止推断相同颜色不代表相同组件所有权

状态比静态截图更重要

一个组件只有静态截图时，Agent 很容易在 hover、focus、pressed、disabled、loading、empty、error 和 long-content 状态上自行发挥。已有产品提取应优先补齐状态矩阵；如果某状态尚未实现，就明确写“未定义”，而不是让通用 skill 替你决定。

13视觉回归协议 · RENDER, COMPARE, EXPLAIN

基线必须可重现

视觉回归不是“打开页面看一眼”。固定页面状态、数据、字体加载、动画暂停策略、浏览器版本和 viewport；截图命名包含路由、状态和尺寸。动态内容要脱敏或冻结，否则 diff 只会反映时间变化。

baseline/profile-default/390x844.png candidate/profile-default/390x844.png baseline/profile-error/1280x900.png candidate/profile-error/1280x900.png review.md: 说明差异、预期、未解决问题

差异要分级

把截图差异分成四类：预期变化、结构回归、内容变化、环境噪声。结构回归包括横向溢出、首屏主次关系改变、组件状态缺失和断点坍缩；环境噪声包括字体渲染差异、抗锯齿和时间戳。不要用一个相似度分数代替解释。

  • Critical：核心流程不可用或内容被遮挡
  • Major：布局、状态或响应式规则明显偏离
  • Minor：局部间距、色差或非阻断细节
  • Accepted：有记录、有 owner、有回滚条件

机器门禁与人工门禁分工

lint、diff、detector 可以稳定发现一部分问题，但它们不理解所有业务语义。机器门禁适合挡 broken token、低对比度、缺失引用、横向溢出和重复反模式；人工门禁负责判断层级、节奏、文案意图、品牌一致性和是否真的解决用户任务。

机器发现 → 人工解释 → 修复或记录例外 → 再次渲染任何“视觉通过”都必须绑定具体 viewport 和截图，而不是只绑定命令退出码。
14失败恢复 · WHEN EXTRACTION GOES WRONG

失败一：提取结果过于通用

症状是 DESIGN.md 充满“现代、简洁、用户友好”，却没有页面事实。恢复方法是退回证据卡：为每条规则补充至少一个路由、一个组件实例和一个 computed style；没有证据的句子标为 hypothesis。若无法确认，就从规范值中删除，不让 Agent 把猜测当约束。

失败二：Agent 重做了整个页面

症状是颜色和卡片看起来更“高级”，但路由、组件所有权、数据流或信息架构被改变。恢复方法是把任务缩到一个垂直切片，在 brief 中列出 must preserve 和 forbidden changes；要求 Agent 先输出拟改文件，未经批准不得扩展范围。

失败三：工具之间互相覆盖

症状是 Taste 选择了新风格，Designer Skills 重新生成了 tokens，Impeccable 又按通用反模式规则要求改掉存量字体。恢复方法是明确优先级：项目事实与人工批准 > DESIGN.md 规范 > 过程 skill > 可选审美护栏 > 通用 detector 建议。工具只提建议，不能互相篡改事实层。

失败四：通过了 lint 但页面坏了

这是正常边界，不是工具失效。lint 主要验证结构和 token，无法覆盖所有真实渲染问题。恢复方法是加入本地渲染、桌面/移动截图、长文本、错误态、暗色模式和键盘焦点检查；将视觉证据作为发布门禁，而不是最后的可选步骤。

A 路径的停止条件

以下任一条件未满足，就不要宣布“设计语言已固化”：代表页面和状态覆盖不足；关键 token 无证据；冲突没有 owner；DESIGN.md 只有色板没有应用规则；Agent 没有在原组件边界内工作；没有移动端和桌面端截图；detector 警告没有解释；例外没有记录；或团队成员无法从文件中复现同一决策。

停止不是失败：冻结未决项、标明证据缺口、保留现有系统、等待下一轮调查比生成一套漂亮但不可追溯的新规范更可靠。

已有产品的设计语言通常分散在不同业务表面。提取至少覆盖以下五类页面；如果某类不存在，要明确记为 omitted，而不是假设它会遵循其他页面。

16工具组合的输入输出 · MAKE EVERY HANDOFF EXPLICIT

提取入口的输入与输出

Claude Design 或 Impeccable 的 document/extract 可以帮助建立初始材料，但输入必须包含代表页面、仓库上下文和目标范围。输出要被当作候选清单：哪些颜色可能是 token，哪些字体被加载，哪些组件看起来重复，哪些地方需要人工确认。

输入源码、运行页面、截图、页面状态、目标范围
输出候选 tokens、组件线索、视觉摘要、疑问
人工动作核对 computed style、调用关系和反例
落盘evidence cards、inventory、open questions

规范层的输入与输出

DESIGN.md 的输入不是“模型认为好看的设计”，而是已经确认的事实和决策。输出既要能被 Agent 读取，也要能被人审阅和 diff。每次修改只改变一个有理由的维度，避免一次重写颜色、字体、布局和组件状态，导致无法知道哪一项造成回归。

确认事实 → token schema + rationale → lint/diff → 版本化提交规范文件是共享契约，不是一次性 prompt 的替代品。

执行层的输入与输出

Designer Skills 负责把规范转成 brief、任务和 review 节点；Taste 只在明确授权时提供审美方向；Agent 最终输出代码和截图。每个阶段都要留下可读文件，后续的人或 Agent 才能知道当前停在哪一步、哪些问题尚未决定。

17团队协作与回滚 · KEEP THE CONTRACT ALIVE

谁可以改变设计语言

如果任何 Agent 都能直接改 DESIGN.md，规范会很快退化成最近一次生成结果的描述。团队需要区分三类变更：实现修复、局部例外、系统级规则变更。实现修复只改代码；局部例外要记录范围和理由；系统级变更要有证据、影响页面列表、视觉回归和批准人。

  • 实现修复：不改变 token 语义，修正组件对现有规则的错误使用
  • 局部例外：只对一个业务表面生效，必须标注退出条件
  • 系统变更：更新 DESIGN.md、版本、迁移计划和回归基线

回滚不只是 Git revert

设计系统变更可能已经生成了多个页面。回滚时要同时恢复代码、token、截图基线和文档说明；若只回退 CSS，DESIGN.md 仍会诱导下一次 Agent 继续使用错误规则。每次系统级变更都应有迁移范围和回滚顺序。

停用新 token → 恢复组件实现 → 恢复页面基线 → 标记 DESIGN.md 版本 → 复查例外先恢复可用性，再处理规范清理；不要在故障中继续扩大重构范围。

更新后的最小评审会

评审不需要重新讨论所有审美，只回答四个问题：这条规则来自哪些页面？有没有反例？会影响哪些组件和状态？移动端与桌面端是否都验证？如果答不出来，规则回到候选状态，不进入规范值。

18最终执行卡 · A PATH IN ONE PAGE

已有产品从调查到发布

第 0 步冻结目标：一个用户路径、五类页面覆盖、一个变更范围
第 1 步采样：保存源码、状态、computed style、桌面和移动截图
第 2 步提取：用 Claude Design 或 document/extract 生成候选 inventory
第 3 步核对：逐条确认 token、组件所有权、响应式和状态矩阵
第 4 步固化：写 DESIGN.md，分离规范值、应用规则和例外
第 5 步编排：用 Designer Skills 生成 brief、任务和 review 节点
第 6 步小步实现：只做一个垂直切片，禁止无授权重做
第 7 步机器检查：lint、diff、detector、a11y 和响应式检查
第 8 步人工验收：真实 375/390px、桌面、长文本、错误态、暗色模式
第 9 步归档：代码 diff、截图、风险、例外、批准和回滚点

这条路径把“设计语言”从形容词变成可追踪的工程对象：有输入，有证据，有明确的工具边界，有停止条件，也有下一次迭代可以复用的文件。

19最小调查命令 · START WITHOUT A NEW TOOLCHAIN

先搜，再看，再渲染

已有产品不需要先引入一套新设计平台。先用仓库现有工具定位事实：搜索 CSS 变量、主题配置、字体声明、组件目录和断点；再用浏览器确认最终计算值；最后只对代表页面截图。命令只是定位器，不能替代页面证据。

find src -type f \( -name '*.css' -o -name '*.tsx' \) grep -R "--color\|font-family\|border-radius\|breakpoint" src # 再回到浏览器检查 computed style # 最后固定 viewport、状态和截图命名

何时停止继续加工具

当团队已经能回答“页面为什么这样排、组件从哪里来、窄屏如何变化、错误态怎么表达”时，继续增加 skill 通常不会提高可靠性。此时应把精力放到证据覆盖、规范版本、视觉回归和例外治理，而不是再寻找一个新的万能提示词。

工具数量减少 → 事实质量提高 → 复现成本下降对已有产品，最好的自动化往往是更窄的输入、更清楚的边界和更稳定的回归。
