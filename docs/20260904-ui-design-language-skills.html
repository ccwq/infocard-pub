02从“风格”到“规范” · WHAT TO WRITE DOWN

DESIGN.md 最低结构

颜色主色、背景、语义色、对比度
字体字族、字号、字重、行高
组件按钮、卡片、导航、表单、状态
布局容器、网格、间距、断点
行为交互、反馈、动效、错误态
语气文案风格和 AI prompt guide

不要只记录色板

如果文件只有几个 HEX 值，Agent 仍然不知道什么时候使用它们。完整设计语言还应回答：什么是主层级？哪些元素必须对齐？卡片如何分组？移动端如何降级？哪些组件禁止重新发明？

错误：\n“请做得像 Stripe 一点。”\n\n可执行：\n“使用 8px 间距基线；正文 15/1.6；\n主操作使用深蓝实心按钮；\n移动端卡片单列，保留 16px 安全边距。”

品牌目录的参考价值

awesome-design-md 将品牌系统整理为 AI 可读取的 DESIGN.md，通常包含配色、字体、组件、布局、响应式、设计语气和 prompt guide。

它的价值不是让项目复制某个品牌，而是提供一套观察框架：把“品味”拆成可传递的工程信息。

03让 Agent 持续执行 · SKILL LAYER

Designer Skills：过程层

适合把设计决策拆成阶段和检查点，避免 Agent 直接从需求跳到代码。

  • 先追问目标和约束
  • 形成 DESIGN_BRIEF 与信息架构
  • 检查现有 tokens、组件和依赖
  • 从 375px 移动布局开始
  • 完成实现后按 brief 做 review

Taste Skill：品味层

作为“前端反模板”规则层，帮助 AI 避免默认 SaaS 外观。它适合快速接入，不等于完整的项目设计系统。

  • 约束常见模板化选择
  • 提醒层级、排版和视觉节奏
  • 适合快速建立审美底线
  • 不能替代项目专属 tokens

Impeccable：审查层

提供设计语言、命令和 deterministic detectors，用来发现 AI 生成界面的反模式。

  • 检查是否过度使用 SaaS 模板
  • 检测可重复的视觉问题
  • 适合作为生成后的质量门禁
  • 不是组件库，也不负责逆向提取
04决策树 · CHOOSE BY YOUR STARTING POINT

如果你已有产品

先提取，再固化。从 `/design sync`、代码扫描或人工审计开始，找出现有组件和 token；然后写入 DESIGN.md，并用 Designer Skills 约束后续改动。

已有 UI → 提取 Design System → DESIGN.md → review

如果你从零开始

先定义，再实现。用 brief、信息架构和 tokens 先把意图写清，再让 Agent 生成页面；Taste 可以作为反模板底线，Impeccable 负责检查。

brief → IA → tokens → frontend → detectors

如果你要迁移风格

不要只换 accent。需要保留结构语法、层级、组件锚点、响应式行为和文案语气；否则得到的只是配色变体，不是设计语言迁移。

观察 Design DNA → 重建结构 → 验证组件 → 多尺寸复核
05验收清单 · BEFORE YOU SHIP

内容层

  • 是否写清目标读者和使用场景？
  • 是否区分提取、固化、执行和审查？
  • 是否给出最小可执行示例，而非只列工具名？
  • 是否明确工具边界和证据来源？

工程层

  • DESIGN.md 是否包含颜色、字体、组件、布局和行为？
  • tokens 是否与现有代码一致？
  • 移动端、明暗模式和响应式是否有规则？
  • Agent 是否会先读取现有系统，而不是重新造组件？

审查层

  • 是否有 deterministic detectors 或 review 流程？
  • 是否检查模板化、层级混乱和低对比度？
  • 是否在多个尺寸下复核？
  • 是否保留人工批准和回滚入口？

最终判断：先把设计意图写成系统

FROM VISUAL TASTE TO EXECUTABLE DESIGN LANGUAGE

最可靠的路径不是寻找一个“万能 UI Skill”，而是把存量界面中的设计决策提取出来，写成 DESIGN.md 或 tokens，再用 Designer Skills 组织流程，用 Taste 和 Impeccable 守住生成质量。这样，Agent 获得的不是模仿对象，而是一套可解释、可复用、可验收的设计语言。
