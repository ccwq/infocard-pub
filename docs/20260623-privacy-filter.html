privacy-filter：LLM 前的隐私网关

一个纯 Go写的 LLM 隐私网关：在请求进入模型之前，毫秒级脱敏 PII 与密钥，生产中已在用。它不做 NER，不引入额外模型或 GPU，只做不可逆脱敏，让 LLM 网关在性能与合规之间多一条可落地的中间路线。

毫秒级脱敏 纯 Go / 静态二进制 RE2 线性时间 生产中已用
TWO-LAYER DETECTION
结构化 PII 走正则；秘密/凭据走 gitleaks + 熵兜底。
Layer 1

结构化 PII

邮箱、电话、身份证、银行卡、IP 等，靠规则直接抓取。

Layer 2

秘密 / 凭据

gitleaks 规则集 + 上下文正则 + Shannon 熵兜底，覆盖 key / token / password / private key。

不做 NER，避免延时；只做不可逆脱敏，避免把敏感信息留回去。
Go 原生 regexp 是 RE2，线性时间、无回溯爆炸风险；因此这类网关特别适合放在 LLM 入口前，做低延迟、可预测的隐私过滤。
1输入用户提示词、对话历史、工具输出、系统回显。
2检测结构化 PII 正则 + gitleaks 规则 + 熵兜底。
3替换生成类型化占位符，单次重建文本，不可逆。
4转发将净化后的内容送进 LLM 网关或后端服务。

脱敏架构

regexp → spans → merge → rebuild

WHY IT WORKS

为什么它适合做网关前置层

性能

不跑 NER，不引入模型

没有额外推理、没有 GPU 依赖、没有长尾模型冷启动；对接 LLM 网关时更容易守住延迟预算。

安全

不可逆脱敏

输出只保留占位符，不提供回填；适合把 PII / 凭据在进入模型前彻底切掉。

工程

单函数 / 单二进制

核心包可直接 import 到网关，也能起 HTTP 或 gRPC 服务，方便嵌入现有 API relay。

DETECTION

两层检测的分工

层覆盖方法

实现特征

每个命中先生成 span，再合并去重，最后单次重建文本。这样可以同时处理重叠命中和多规则匹配，避免把原文顺序打乱。

DEPLOYMENT

怎么接进现有系统

Core package

import 进网关

import "privacyfilter/filter"，启动时创建一次过滤器，随后每个请求直接调用，零额外 HTTP hop。

HTTP / gRPC

薄封装服务

需要独立服务时可直接起 cmd/http 或 cmd/grpc；它们只是 core package 的轻薄壳。

生产使用

已在 PackyCode 生产在用

README 明确写了已在生产环境运行，说明这不是 demo，而是已经被实际流量验证过的网关组件。

INSTALL · BUILD · API

安装 / 构建 / 接口

安装

go build -o bin/server-http ./cmd/http、go build -o bin/server-grpc ./cmd/grpc；核心包可直接依赖，不强制走服务。

WHY NOT NER

为什么它不做 NER

延迟优先

NER 需要额外模型与计算，长文本下 CPU 时间会明显上升；这个网关的目标是毫秒级脱敏，而不是语义识别。

边界清晰

它只处理“必须切掉”的敏感项，不试图理解人名/地名/组织名这类语义实体，避免误伤和复杂性膨胀。

更适合网关

对接 LLM gateway 时，最重要的是稳定、快速、无模型依赖；这份设计把这些要求放在第一位。

TRADE-OFFS

它的利弊很明确

优势

纯 Go、静态二进制、线性时间 regexp、两层检测、生产可用、易嵌入现有网关。

代价

不做 NER，意味着它不解决所有隐私问题；它更像是一个“先把最危险的东西切掉”的前置安全层。
