SECTION ONE

SeaweedFS 是什么

已核实：开源分布式存储系统，Go 语言开发，支持对象存储（S3 兼容）、POSIX 文件系统与 Iceberg 表格式，面向海量文件横向扩展。

类型定位
分布式文件系统

SeaweedFS 最初基于 Facebook Haystack 论文实现，专注于海量小文件存储场景，声称可存储 billions 级别文件量，核心设计理念是元数据与数据分离。

已核实
核心组件
Master · Volume · Filer

Master：管理文件 ID（fid）与 Volume 的映射关系，不存文件本身。
Volume：实际存储数据的节点，多副本支持。
Filer：提供类 POSIX 文件系统接口，支持目录层级与 S3 协议兼容。

已核实
协议支持
S3 · Filer · Iceberg

S3 兼容 API 可直接对接现有对象存储客户端；Filer 提供 HTTP 文件服务；Iceberg 支持使其可作为大数据表格式的底层存储引擎。

已核实
技术特点
横向扩展 · 多副本 · O(1) 访问

Master 仅维护 fid→Volume 映射，理论上 O(1) 查找；Volume 按需扩容，支持机架/数据中心级别的副本策略；去中心化设计避免单点瓶颈。

已核实
许可证
Apache-2.0

Apache License 2.0 开源许可证，允许商业使用，无需担心许可证合规风险。

已核实

Agent 时代的文件操作风险

当 Agent 获得 shell 执行权限时，rm -rf 类误操作的后果远超传统软件错误，延迟删除是降低损失的关键机制。

风险场景
Agent rm -rf 灾难链

1. Agent 获取了服务器写权限
2. Agent 解析指令时将 "清理 /tmp" 误解为 "清理根目录"
3. 执行 rm -rf /* 或误删挂载卷
4. 传统存储：数据永久消失
5. 具备延迟删除的存储：在 GC 触发前保留数据副本

SECTION THREE

延迟删除的技术原理

SeaweedFS 的删除流程涉及 Filer 元数据标记、Volume GC 与物理回收三个阶段，以下为基于源码和社区讨论的推断性描述，非官方确认文档。

原理（推断性）
标记删除 → 延迟回收 → GC 清理

第一步：标记删除 — Filer 收到删除请求后，在元数据层标记文件为"已删除"，而非立即释放数据块。

第二步：延迟窗口 — 删除标记生效后，数据在 Volume 中暂存，物理文件尚未覆写，此时可通过恢复 fid 访问。

第三步：GC 触发 — Master 调度 Volume Garbage Collection，被标记文件的数据块被真正释放。GC 触发时机由配置参数（如 garbageThreshold）控制。

待核验 · 推断性描述
S3 兼容模式（推断性）
Delete Marker 机制

SeaweedFS S3 网关（s3api）可能实现了类似 AWS S3 的 Delete Marker 行为：删除对象时写入一个删除标记而非物理删除，列出对象时该版本被跳过，恢复时删除标记被清除即可访问原对象。需在官方 S3 兼容文档中确认此行为。

待核验 · 推断性描述

风险边界
已知局限与注意事项

1. 延迟删除依赖 Filer 或 S3 网关层实现，纯 Volume 层删除可能是即时的。

2. GC 触发后数据不可恢复，与 AWS S3 版本的即时性不同。

3. 分布式多副本场景下，各副本 GC 时机可能不同步，理论上存在短暂的恢复窗口不一致。

4. 配置不当（如过小的 GC threshold）可能导致存储空间快速耗尽。

5. 本卡信息不构成技术选型建议，实际部署前请阅读官方文档。

收口 · 本卡结论

SeaweedFS 作为分布式存储系统，其 S3 兼容、Filer 和 Iceberg 能力已核实；"延迟删除可恢复"的核心卖点来源于 X 帖宣传，尚未在官方文档中核验，实际行为请以官方文档为准。在 Agent 场景下，无论使用何种存储系统，限制 Agent 的直接 shell 权限、通过 API 层暴露安全操作接口，均是比依赖延迟删除更可靠的安全策略。

  • 已核实：SeaweedFS 是 Apache-2.0 分布式存储系统，支持 S3/Filer/Iceberg，架构为 Master+Volume+Filer。
  • 待核验：延迟删除 / GC 延迟回收的具体行为、参数配置、恢复窗口时长。
  • 建议：在生产环境部署前，测试实际删除行为，并结合备份策略，不将延迟删除作为唯一的数据保护手段。
