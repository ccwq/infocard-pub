03
开源实现

两条可落地路线

路线 A · Codex 原生优先

AGENTS.md + Skills + 人工触发

适合个人项目与中小任务：先写项目约束，再把“规划 → 实现 → 测试 → 复盘”固化为 Skill；需要并行时由主代理显式拆分。优点是依赖少、容易理解；缺点是编排、恢复和可观察性需要自己维护。

04
推荐模板

一个可复制的“研究—实现—验收”管线

动态工作流的关键不是“代理越多越好”，而是把每个阶段的输入、输出和失败处理写清楚。

const findings = await parallel([ () => agent("检索官方文档，输出带 URL 的事实表"), () => agent("检查 GitHub 源码，确认实现细节"), () => agent("整理社区实践，标注未经核实的说法") ]) const checked = await pipeline(findings, [ (item) => agent(`核验这条证据：${item}`), (item) => agent(`将已核验事实转成可执行方案：${item}`) ]) return await agent(`汇总为报告，并列出风险与验收命令：${checked}`)
建议的失败策略： 单个 agent 失败 → 重试一次；事实冲突 → 保留来源差异；预算不足 → 先交付已核验部分；最终输出必须经过验证代理或脚本，不允许把“生成成功”当成“任务完成”。
05
边界与验收

把工作流当成软件，而不是一段神奇提示词

必须可观察

  • 记录每个阶段的输入/输出
  • 显示运行状态、耗时和错误
  • 保留可恢复的 run journal
  • 区分缓存结果与重新执行

必须可验收

  • 源码级事实有一手来源
  • 生成代码跑测试与 lint
  • 写入动作有权限边界
  • 最终结果能被人复核
结论： Codex 动态工作流的最小闭环 = 规则文件 → 可复用技能 → 明确角色 → 并行/管线编排 → 验证与恢复。先用路线 A 固化纪律，再在任务确实需要时引入路线 B。
