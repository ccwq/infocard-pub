FastClaw：Go 写的 AI Agent Runtime

这不是一个单纯的聊天壳，而是一套把 LLM provider、agent、skills、memory、sandbox、API、dashboard 连成闭环的运行时。它的核心价值在于：让“怎么跑 Agent”成为标准化基础设施，而不是每个项目都从零拼装。

语言Go 1.25+
许可MIT
入口curl install.sh | bash
默认端口18953
定位Agent Factory / Runtime

一句话判断

core take

FastClaw 在解决什么

它把 AI Agent 的常见底座能力统一起来：全局配置、agent 目录、skills、会话历史、模型适配、工具执行、沙箱隔离和 API 暴露。适合想做“自己的 Agent 平台”的团队，而不是只想写一个单独 prompt 的人。

关键判断：FastClaw 的卖点不是“更会推理”，而是“把 Agent 运行和管理做成一套可部署、可持久化、可扩展的系统”。

你可以怎么理解它

更像 Agent Factory：创建 Agent、给它分配人格（SOUL.md）、记忆（MEMORY.md）、技能（skills）、模型、沙箱和工作区，然后由 gateway / dashboard / API 统一调度。它提供的是运行环境和编排能力，不是一个单独模型，也不是一个单一聊天页面。

能力矩阵：四个最值钱的部件

capabilities
01 / providers

多模型接入，不锁死单一厂商

支持 OpenAI、Anthropic、Ollama、OpenRouter、Groq、DeepSeek、Mistral，以及任何 OpenAI-compatible API；还能给每个 agent 单独覆盖模型与参数。

02 / tools & sandbox

工具执行 + 隔离环境

内置 exec、read_file、write_file、list_dir、web_fetch、web_search、memory_search；沙箱可选 E2B 云沙箱或 Docker 沙箱，并支持技能与工作区的自动 hydrate / 回写。

03 / skills

共享技能与 agent 私有技能

技能既可以来自 ClawHub / GitHub，也可以只挂在某个 agent 下；它让重复工作流、领域知识和最佳实践变成可安装资产。

04 / memory

会话与长期记忆分层保存

MEMORY.md、sessions、agent config 都会持久化；这意味着 agent 不只是“当场回答”，而是能跨会话续接。

你实际会碰到的界面与入口

surface

Dashboard 里有什么

FastClaw 的前台不是一个单一聊天页，而是分成 Agents / Skills / Models / Settings 四个核心区。进入某个 agent 后，还能继续看 Chat、Files、Skills、Models、Sessions，能直接编辑 SOUL.md、IDENTITY.md、MEMORY.md 等文件。

适合什么工作流

更适合“要做成平台”的场景：给不同 agent 分模型、挂不同技能、隔离工作区、统一鉴权、统一 API，再由你的上层产品消费输出。它不是给单次对话做一个漂亮壳，而是给 Agent 系统做基础设施。

API 面

README 里明确列出了 OpenAI-compatible /v1/chat/completions、Web chat SSE、session 管理、agent CRUD、config 管理、skill 安装和 API key 管理，说明它已经把“可集成性”当成一等公民。

运维面

有本地启动、Docker、Kubernetes 三种部署姿势；配置里又把 gateway、storage、sandbox、providers、agents defaults 分层拆开，方便真正落到服务环境里。

存储与配置：哪些数据归 FastClaw

storage map
数据 归属 存储 说明
SOUL.md / IDENTITY.md Agent FastClaw 人格与身份定义，决定 agent 的“说话方式”和角色边界。
MEMORY.md Agent FastClaw 长期事实与偏好，通常由 heartbeat 自动更新。
Skills Agent / Global FastClaw 共享或私有的工作流资产；适合复用。
Sessions Agent FastClaw 对话历史，支持续接与审计。
User accounts / billing 你的应用 Your app README 明确提示：这部分不由 FastClaw 托管。
Output files 你的应用 你的应用 / S3 适合把结果交给外部业务系统做持久存储。
边界要点：FastClaw 管的是 agent runtime 与基础设施，不负责替你的业务系统管理账户、计费和最终产物归档。把它看成“Agent 平台层”，不要把它误读成“整个产品后端”。

快速上手：最短路径

quick start
step 1

安装并启动

README 给出的路径很直接：先拉 install.sh，再跑 fastclaw，首次启动会打开 setup wizard。

# 安装并运行
curl -fsSL https://raw.githubusercontent.com/fastclaw-ai/fastclaw/main/install.sh | bash
fastclaw    # 打开 setup wizard
step 2

进入 Dashboard

访问 http://localhost:18953，用安装过程生成的 admin token 登录，然后先配置 LLM provider，再创建默认 agent。

# 常见首次动作
1. 配置 provider（OpenAI / Anthropic / Ollama / OpenRouter...）
2. 创建 default agent
3. 编辑 SOUL.md / MEMORY.md
4. 安装 skills
5. 进入 Chat / Files / Sessions 调试
step 3

按任务给 agent 分层

如果你要把它拿来做产品，建议把“对话、文件、技能、模型、会话”分开验证：先确认 provider 能通，再确认 tool / sandbox 能跑，再确认 sessions 和 memory 能持久化，最后再把它接到你的上层业务里。

适合谁，不适合谁

decision boundary

适合

1
要做 Agent 平台 / 内部助手需要统一模型接入、权限、工具、沙箱、记忆和会话管理。
2
要做多 Agent / 角色化系统每个 agent 都需要自己的 personality、skills 和模型覆盖。
3
要把运行结果接入业务系统你希望输出文件和 API 都可被外部系统消费。

不适合

1
只想做一个轻量聊天页FastClaw 的能力明显偏“平台底座”，不是最轻的聊天包装器。
2
不需要持久化和沙箱如果你只是一次性 prompt 调用，它会显得偏重。
3
把它当成业务计费后端README 已明确：账户、计费、输出归你的应用处理。

发布时要盯住的三件事

ops checklist
01

provider 是否先通

没有模型接入，后面的 dashboard、skills、sessions 都只是壳；先跑通 provider 是第一步。

02

sandbox 是否真的隔离

如果你要在生产里跑 agent，沙箱与工作区 hydrate / sync 的行为必须明确，不然工具执行会污染宿主环境。

03

持久化边界是否清楚

sessions、memory、skills、agent config 归 FastClaw，业务账户和输出归你自己的系统，这条线要先画清。

最终结论

FastClaw 更像一套 AI Agent 运行底座，把 agent 的“创建、运行、记忆、技能、工具、沙箱、API”打包成一套可部署系统。它的价值在于降低搭建 Agent 平台的工程摩擦，而不是再发明一个模型。

你可以怎么用它

  • 做内部 AI 助手平台
  • 做多角色 agent 系统
  • 把技能和模型配置标准化
  • 把 sessions / memory / tool sandbox 统一管理
