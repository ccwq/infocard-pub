面向自改进的
Harness 工程

Harness 是 AI 部署的重要组成部分，编码 agent 产品如 Claude Code 和 Codex 的成功就是例证。Harness 不是 prompt 模板，而是运行时和软件系统设计。

LLM Harness RSI Meta-Harness Self-Harness DGM
2026 年 AI Agent 竞争的核心不在模型，而在围绕模型的 harness

递归自改进（RSI）的近期路径不太可能是模型直接重写自身权重。更务实的方向：模型改进训练流程和部署系统（harness），反过来使更好的后继模型产生。

01
OVERVIEW · 一句话概述

Harness 工程是什么

Harness 是围绕基础模型的系统，编排执行并决定模型如何思考与规划、调用工具与行动、感知与管理上下文、存储制品、评估结果。相比早期 agent 框架（"agent = LLM + memory + tools + planning + action"），额外包括工作流设计、评估、权限控制和持久状态管理。

关键数据

性能差距 6 倍

同一模型，仅因外部 Harness 不同，性能差距可达 6 倍。这是 2026 年 Agent 竞争核心转向 harness 的量化依据。

核心类比

Harness ≈ 操作系统

Harness 应封装复杂逻辑，同时保持接口简单，参考现有软件工程实践以受益于预训练知识。与 OS 有强烈类比关系。

案例

Claude Code / Codex

编码 agent 产品的成功是 Harness 作为 AI 部署重要组成部分的例证。核心接口在 Claude Code、Codex、OpenCode、Cursor 之间已趋于稳定。

02
THREE PATTERNS · 三大设计模式

Harness 工程的设计模式

三大核心设计模式：工作流自动化、文件系统作为持久记忆、子 agent 与后端任务并行。

Pattern 1

工作流自动化

Karpathy autoresearch repo 是简洁案例。常见的目标导向循环：

  • 规划（Plan）
  • 执行（Execute）
  • 观察/测试（Observe/Test）
  • 改进（Improve）
  • 再次执行 → 直到目标达成

设计应刻意简单和通用以促进泛化。

Pattern 2

文件系统作为持久记忆

Harness 不应在上下文中携带整个工作流和所有日志，应将持久状态保留在文件中：

  • 实验日志 / 代码 diff
  • 论文摘要 / 错误踪迹
  • Rollout 轨迹数据

以文件形式管理持久记忆，自然受益于核心模型能力提升。

Pattern 3

子 Agent 体系

Harness 生成多个子 agent 并行执行并监控后端任务。父 agent 需要进程管理器：

  • 启动任务 → 检查日志
  • 取消失败运行
  • 将结果合并回主线程

并行应变得显式和可检查：子 agent 输出存文件/日志/状态记录。

03
CONTEXT ENGINEERING · 上下文工程

上下文管理三阶段演进

简单地把所有工具响应追加到上下文会迅速失控。上下文工程从 ACE → MCE → Meta-Harness 逐层深入。

ACE

Agentic Context Engineering

将上下文视为不断演化的 playbook，三个组件：

  • Generator：生成任务轨迹
  • Reflector：从成功/失败中提取洞见
  • Curator：用增量条目更新结构化上下文（而非重写完整 prompt blob）
MCE

Meta Context Engineering

将"机制"（如何管理上下文）与"制品内容"（上下文中有什么）分离。

  • 元优化层面：运行 skill 进化
  • 基础层面：运行上下文优化
  • 用自由形式的 skill 存储任务最重要知识
  • 迭代同时进化 skill 和上下文
Meta-Harness

优化 harness 的 harness

被优化的对象：决定和优化"什么信息应该被存储、检索和呈现给模型"的代码。提案者本身是编码 agent。

Meta-Harness（Stanford）：文本分类 40.9% → 48.6%，上下文开销 50.8K → 11.4K tokens

05
WORKFLOW DESIGN · 工作流设计

自动工作流发现

工作流设计可以由领域专家手工完成，也可以被公式化为搜索问题，由算法找到更好的解决方案。

ADAS

Agent Design as Search

将 agent 设计本身公式化为优化问题。元 agent 提出新的 agent 工作流设计，所有新 agent 用代码编写。

AFlow

图驱动工作流优化

将 agent 工作流表示为图：节点 = LLM 调用动作，边 = 用代码实现的逻辑操作。基于 MCTS（蒙特卡洛树搜索）优化。

AI Scientist

自动科学研究系统

提出想法 → 写代码 → 跑实验 → 分析结果 → 写论文 → 同行评审。每条声明必须追溯到证据源，可验证性作为中心设计约束。

06
SELF-IMPROVEMENT · 自改进 Harness

自改进 harness 的三种方案

代码是定义程序和系统的通用语言。如果 LLM 能优化执行 agent 的代码，它能访问比手写 prompt 大得多的设计空间。

STOP

Self-Taught Optimizer

种子改进器拿到初始解决方案 + 效用函数 + 黑盒模型 → 返回改进后的解决方案。目标不是改进解决方案，而是改进改进器本身。

发现的策略：遗传算法 / 分解改善 / 多臂 bandit / 模拟退火 / 波束/树搜索

⚠ 警示：仅递归结构不够。GPT-4 有效，GPT-3.5/Mixtral 反而退化——基础模型必须足够有能力来改进机制。
Self-Harness

自优化 Harness

使用 propose-evaluate-accept 循环：

  • 弱点挖掘：将失败聚类为可验证的失败模式
  • Harness 提案：基于失败模式提出有限编辑
  • 提案验证：用回归测试验证并合并合格编辑

在 MiniMax M2.5 / Qwen3.5-35B / GLM-5 上学到模型特定的 harness 指令。

DGM

Darwin Gödel Machine

基于 LLM 的编码 agent 修改自己的 harness 代码库。从池中选父代 → 检查评估日志 → 提出对自身 harness 的改进来生成新版本 agent。

Claude 3.5 Sonnet + 简单初始 harness：
SWE-Bench: 20% → 50%
Polyglot: 14.2% → 30.7%
07
EVOLUTIONARY SEARCH · 进化搜索

进化搜索：Harness 的 Pareto 前沿

进化搜索在搜索空间巨大或形状古怪、难以用梯度优化但易于评估解决方案时适用。Harness 搜索非常匹配。

AlphaEvolve

候选池进化

候选程序和 prompts 存储在池中，冻结 LLM 生成 diff 改进。在池中反复评估子程序并保留成功者，随着时间发现更好的解决方案。

Darwin Gödel Machine

自我修改的进化

明确的自我修改能力：从池中选父代 → 检查基准评估日志 → 提出对自身 harness 代码库的改进来生成新版本 agent。

08
SIA + TRAJECTORY · 联合优化

优化对象演进 + 与模型权重联合优化

Harness 系统中被优化对象的演进：指令 prompt → 结构化上下文 → 工作流 → harness 代码 → 优化器代码。

优化对象演进路径
阶段被优化对象特点
1.0指令 prompt说什么
2.0结构化上下文看什么
3.0工作流怎么做
4.0harness 代码用什么架子
5.0优化器代码怎么自动找到更好的架子
SIA

Synergistic Improvement Agent

将 harness 改进和模型参数更新结合在同一优化循环中。

  • Meta-Agent：提出初始 harness
  • Task-Specific Agent：执行任务
  • Feedback-Agent：基于最近轨迹选择更新 harness 还是更新模型权重
09
7 BOTTLENECKS · 未来挑战

构建自改进 AI 的七个瓶颈

Trehan & Chopra 观察到 LLM 在最小脚手架下从研究想法到论文时反复出现六个失败模式。以下是七个关键瓶颈。

1

弱而模糊的评估器

许多研究声明没有快速精准的验证器。自改进循环在评估指标可测量和客观时效果最好。

2

上下文和记忆生命周期

上下文工程将成为智能的核心部分，而非停留在软件系统层。

3

负面结果

研究者被激励发表成功结果，文献偏向成功。LLM 可能不擅长决定何时放弃假设。

4

多样性崩溃

进化和 RL 循环倾向于开发现有的高奖励模式，抑制探索。

5

Reward Hacking

自改进循环优化任何给它信号的东西，包括利用评估器的漏洞。

6

长期成功

许多优化目标仍然太短期，缺乏对长期价值的衡量。

7

人的角色

人应该上移到堆栈上层，而不是从循环中移除。

10
PRACTICAL OUTLOOK · 实用展望

Harness 与核心智能：近期预测

很难预测 RSI 的未来在多大程度上依赖于 harness 工程，但近期路径已有明确方向。

近期路径 A

元方法论方向

Harness 工程将朝元方法论方向演进——改进获得更好答案的机制，而不仅仅是改进答案本身。

近期路径 B

自动研究闭环

成熟的 harness 使自动研究成为可能，模型自改进循环运行起来。更智能的模型防止 harness 过度工程化。

内化 vs 接口：许多 harness 改进可能被"内化"到核心模型行为中，但与外部上下文和工具的接口应保留。
