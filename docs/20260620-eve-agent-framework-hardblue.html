01核心判断
eve 的核心价值不是“封装一个模型”，而是把持久化 agent 的结构、状态与操作入口，变成一套可读、可扩展、可运维的文件系统约定。
02文件系统即接口
01

agent.ts

放模型与运行时配置，决定 agent 的基础能力边界。

02

instructions.md

常驻系统提示词，定义角色、目标和工作方式。

03

tools / skills

工具是 typed functions，技能是按需加载的程序化步骤。

04

channels / schedules

把消息通道和定时任务也纳入同一目录树。

03从 README 提炼的三条能力

可检查

项目结构天然可读，agent 的意图不只在代码里，也在目录名和 markdown 里。

可扩展

工具、技能、频道、调度器按文件组织，适合逐步扩展而不是一次写死。

可运维

持续任务、消息流、恢复和命令入口更像一个系统，而不是单次推理 demo。

05适合谁 / 不适合谁
类型判断原因
适合要长期运行的 agent 项目需要工具、技能、消息通道、调度任务和持久状态一起协作。
适合喜欢目录即文档的团队把协议、配置与操作入口都写在文件系统里，便于审查和协作。
不适合只想要一个薄薄 SDK 封装如果目标只是快速调一个模型，eve 的系统化结构会显得偏重。
不适合不打算维护持久状态它的价值主要来自 durable workflow，而不是一次性脚本。
06一句话总结
如果把传统 agent 框架理解成“API 集合”，那 eve 更像是把 agent 运行系统 直接放进了项目目录：结构、权限、命令、调度 同时成为一等公民。
