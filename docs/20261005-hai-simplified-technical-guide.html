01 / 技术文档手册

它解决的是表达歧义，不是替你判断事实

hai-simplified-technical 属于 hai-stack。它为 Claude Code / Codex 提供技术写作规则：统一术语、拆开动作、写明主体、固定要求强度。

适合的输入

  • README、设计文档和 API 文档。
  • runbook、故障排查、迁移指南。
  • 提交说明、PR 描述、代码注释、错误信息和界面帮助。

不适合的输入

  • 营销文案、品牌故事和文学写作。
  • 博客、社交帖子、演讲和宣传段落。
  • 混合文档只改技术部分：改了什么、怎么升级、哪里不兼容。

规则约束措辞，不证明系统正确。文档与代码是否一致，属于另一个审计任务。

安装：保留 references 和 scripts，不只复制 SKILL.md

下面是仓库 README 的安装方式。它链接整套技能，不是仅安装本卡主角。执行前检查同名技能冲突；本页展示命令，不替读者安装。

git clone https://github.com/hylarucoder/hai-stack.git
cd hai-stack
make link

make status
make validate
make unlink
  • make link 将技能链接到 ~/.agents/skills/ 和 ~/.claude/skills/。
  • 安装器不覆盖真实目录或指向其他仓库的链接；同名独立安装会提示冲突。
  • make unlink 只移除指向本仓库的技能链接。
  • 若选择单独复制，至少保留该技能的执行源、references 和 scripts；不能把中文阅读版改名冒充执行源。

Python 检查器使用标准库，源码注明 Python 3.8+。宿主能否加载这些链接，仍应以实际安装状态为准。

首次调用：限定文件、保留语义、说明不做什么

先选择一份技术文档，避免把整仓库或营销内容交给同一次改写。以下为本页教学提示词，不是作者评论区原句。

使用 hai-simplified-technical 改写 docs/runbook.md。
采用简化技术中文。保留章节、链接、代码、数字和事实条件。
不要新增性能数据，不要删除风险和例外。
先检查项目术语表，再改写，再运行机械检查。
交付改写后的文件、规则计数和保留软规则的理由。

只审查时

明确说“只列问题，不修改文件”。要求定位行号、规则编号、原文和可直接粘贴的建议。

已指定文件时

输出模板允许在有版本控制且用户指定目标文件时原地改写；否则交付清楚命名的邻近文件。

05 / 技术文档手册

词与动词：用术语表消灭同义漂移

1.1–1.4：硬规则

  • 一概念一词，一词一义。不要为文风换同义词。
  • 按项目术语表命名新概念，再使用它。
  • 适当、有关的、较为、若干、显著、大幅等词要换成名称、条件或已有数字。
  • 没有真实数字时不要编数据；把证据缺口交给作者。

3.1 与 3.4：硬规则

  • “进行校验”改成“校验”；“加以处理”要写清具体动作。
  • 中文要求词固定为：应、不应、宜、不宜、可、不必。
  • 如果项目使用 RFC 2119 等约定，以项目约定为先。
  • 3.2 主动句、3.3 简单时态为软规则，不把所有命中都判错。

2.1 的“最多两个的”和 2.2 的“最多三个连续名词”是软规则。正确的技术名词不会因为包含禁用词就被擅自更换。

06 / 技术文档手册

句子与指代：一个动作一个主体

应守的硬规则

  • 4.1：一句只讲一个主题。
  • 4.2：主语变了就写出来。
  • 4.3：它、这、该、其只指向一个对象。
  • 6.1：每段先给结论。
  • 6.4：每个测量数字带条件与日期。
  • 6.5：已做与计划分开。

有理由可以不守的软规则

  • 4.4：因为、所以、如果、但要写清关系。
  • 4.5：三项以上用纵向列表。
  • 6.2：一段一主题，最多六句。
  • 6.3：说明句中文最多 50 字，英文最多 25 词。

规则不是把文字写成电报。为缩短句子而删掉条件、风险和例外，违反了保留语义的边界。

07 / 技术文档手册

步骤与警告：把条件放到操作之前

5.1–5.3 是硬规则：编号列表、一步一条指令、动词开头，条件在动作前。5.4 是软规则：中文步骤句最多 40 字，英文最多 20 词。

警告：不可逆或生产影响

数据丢失、不可逆、静默错误、生产影响、对外发布，使用“警告”。先写指令，再写后果；放在对应步骤前。

注意：等待和返工

变慢、返工、长等待，使用“注意”。每条只说一个风险是软规则。

警告：删除数据前，应确认备份可恢复。
如果备份不可恢复，删除后无法找回数据。

1. 如果检查失败，停止本次操作。
2. 修复失败项。
3. 重新运行检查。

以上为本页教学例，不代表仓库内某个真实数据库操作规程。

09 / 技术文档手册

检查脚本：退出码是扫描结果，不是语义判决

python3 skills/hai-simplified-technical/scripts/check.py docs/runbook.md --lang zh
python3 skills/hai-simplified-technical/scripts/check.py README.md --lang en
python3 skills/hai-simplified-technical/scripts/check.py README.md docs/runbook.md

能识别的模式

  • 含糊词、包装动词、要求词。
  • 标点、中英文间隔、范围符号。
  • 混用引号、句长、过多“的”。
  • 部分英文被动式、进行时、空主语和套话。

不能替你判断的事情

  • 事实是否真实，数字是否有实测证据。
  • 代词是否真的歧义，步骤是否安全。
  • 术语是否应该保留，软规则是否有充分理由。
  • 模型是否自动触发、读者阅读速度是否提升。

脚本跳过 fenced code、行内代码、URL 和表格分隔行；引号中的词通常按示例处理。默认逐行判语言：有中文且 CJK 数不少于拉丁词数时按中文，无中文且至少三个英文词时按英文。

发现任意 hard 命中返回 1；只有 soft 或无命中返回 0。soft 可以有理由保留，hard 命中也可能来自引用上下文，应核对原文。

11 / 技术文档手册

交付：文档之外，给作者单独列证据缺口

写作或改写

  • 先交付文档。
  • 按规则编号计数修改，不堆逐句 diff。
  • 写出脚本剩余 hard / soft 数。
  • 解释每个保留 soft 的理由。
  • 无数据的声明按原强度保留，缺证据事项放在“给作者”说明。

只做审查

  • 先列硬规则。
  • 逐项写位置、规则、准确引用原句和可粘贴改写。
  • 结尾说明 hard / soft 数。
  • 说明是否遵守术语表，或未发现术语表。

只有读者缺了信息就做不了事时，才在正文放“[待补：……]”。不能把每个未测量的声明都改成占位符，也不能把猜测数字写入占位符。

证据边界：哪些已经核实，哪些只是作者判断

本页核对了 SKILL.md、中英文规则、输出模板、检查脚本和仓库 README；教学样例的脚本命中是本次真实运行。仓库 GitHub 快照为 289 Stars、16 Forks（本次采集值，非技能单项数据）。API 未识别许可证，不能据此标注 MIT。

  • 推文称受 Karpathy 推荐的 ASD-STE100 启发：本页只将它记为作者背景说法，不确认背书关系。
  • “篇幅增长但更快读懂”来自作者体验，没有本页独立阅读速度测试。
  • 中文规则是项目对简化技术写作的适配，不是把中文称为 ASD 官方认证标准。
  • 评论区案例未获取，不用本页自拟样例冒充。

初次验收应比较事实、条件、例外、链接与代码是否保留；不能只凭 hard=0 宣称文档已正确。

初学者完成清单：一次只改一个文件

  • 选择技术文档，排除营销段落。
  • 读取项目术语表与写作约定。
  • 明确本轮是只审查还是允许改写。
  • 保留条件、风险、例外、数字和代码。
  • 按文档语言读取 rules-zh.md 或 rules-en.md。
  • 运行检查器，逐项裁决命中，不盲改全部 soft。
  • 对照 diff 核查语义，再交付规则计数与未决问题。

若文字看起来更短，却丢了重试条件、权限限制或回退办法，改写没有完成。
