01

一句话读懂

awesome-autoresearch 的价值，不在“列了很多项目”，而在把 autoresearch 从一个 Karpathy 风格实验循环，拆成跨行业可复用的模式：固定目标 → 修改候选 → 运行验证 → 只保留改进 → 继续迭代。
它回答两个实用问题：哪里已经用过 autoresearch？哪些模式可以跨行业迁移？

03

首批该看的代表条目

karpathy/autoresearch

原始模式：agent 修改 GPT training script，固定时间实验，只把 loss 改善的提交留在 git history。

AutoResearchClaw

科研管线：从研究想法到论文，多阶段 autonomous pipeline，包含实验自愈和 pivot/refine loops。

Sibyl Research System

Claude Code 上的 autonomous AI scientist：内部研究迭代 + 跨项目外层自进化。

AutoKernel

GPU 优化：围绕 kernel bottleneck 迭代代码、benchmark，并只保留速度提升且不破坏正确性的改动。

Claudini / autovoiceevals / AutoPrompter

评测红队方向：自动产生攻击、测试 prompt、评估语音代理，核心是可重复 eval 与硬性评分门槛。

atlas-gic / autoresearch-trading / BTCautoresearch

金融方向：策略结构由 agent 迭代，参数或评分由回测/优化器裁决，避免“看起来聪明但不可验证”。

04

仓库真正的“分类纪律”

单条目单分类

每个 entry 只放进一个最接近直接应用域的类别。好处是避免“一个项目重复出现在 AI / Research / Tool 三个区”的 awesome-list 噪音。

不是综合数据库

README 明确说它不是 comprehensive database，而是 high-signal, fast-scanning field guide。

Related Practices 单独承接弱证据

X threads、Reddit、访谈等如果能说明真实 autoresearch 用法，但没有独立案例页，就进入实践讨论区，而不是混进强案例。

开放类别保持 0

Competitive Intelligence、Content Research、Customer Discovery、Lead Generation、Trend Monitoring 仍是待播种区，说明维护者没有为了凑数硬塞条目。

05

怎么把它用于自己的项目

找迁移模式

先按行业看：科研、软件优化、评测、金融、工作流。不要先看工具名，先看“评分函数是什么”。

抽象验证器

每个案例都问：它的 keep/discard gate 是 loss、speed、coverage、Sharpe、RMSE、人工 rubric 还是任务成功率？

复制实验边界

真正可复用的是“单一可变文件 / 固定预算 / 可重复命令 / git ratchet / crash recovery”，不是某个模型名。

避免泛化误读

不是所有 research agent 都是 autoresearch。缺少修改—验证—保留/丢弃闭环，就只是研究或监控 agent。

优先看 Infra

Infra / Skills / Forks 有 122 条，是把概念落成可运行系统的关键：并行、分支、日志、调度、评估。

再看实践讨论

135 条讨论可用来判断市场正在把 autoresearch 迁移到广告、预测市场、Amazon seller、NEPSE 量化等新场景。

06

收录门槛：什么不算 AutoResearch

必须公开可引用source public and citable；私有、不可访问或太模糊的来源不进入列表。
必须直接相关不能只是 generic research / monitoring / multi-agent system，必须明确 autoresearch 或体现可验证迭代闭环。
必须有方法与价值summary 需要一句话说明 scenario、method、value；不是把长文塞进 README。
排除纯观点纯理论、泛泛 AI 评论、没有 concrete practice 的内容不收。
