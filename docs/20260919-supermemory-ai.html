5 分钟上手：TypeScript / Python 示例

开发指南

Supermemory SDK 提供 add() / profile() / search() 三个核心接口。无需配置向量数据库，无需设计切分策略，安装后直接调用。

TypeScript 示例

import Supermemory from "supermemory"; const client = new Supermemory(); // 1. 存入一段对话 await client.add({ content: "User loves TypeScript and prefers functional patterns", containerTag: "user_123", }); // 2. 生成用户画像（含静态事实 + 近期动态） const { profile } = await client.profile({ containerTag: "user_123", q: "What programming style does the user prefer?", }); // profile.static → ["Loves TypeScript", "Prefers functional patterns"] // profile.dynamic → ["Working on API integration"] // 3. 混合检索（RAG + 记忆） const results = await client.search({ q: "how do I deploy?", containerTag: "user_123", searchMode: "hybrid", // 知识库文档 + 个人偏好一起返回 });

⚠️ 需要谨慎评估的场景

需要 100% 精确事实的场景 事实提取依赖 LLM，存在 hallucination 风险。医疗、法律、金融等高风险场景需额外人工审核机制。

纯文档检索（无对话上下文） 如果只是需要一个文档搜索引擎，传统 RAG（如 LlamaIndex）更成熟；Supermemory 的优势在于"记忆"而非"检索"。

🔬 技术原理深度解析

原理揭秘

理解 Supermemory 背后的设计逻辑，帮你在调试、性能优化和定制开发时做出正确决策。

1. 为什么传统 RAG 解决不了 AI 失忆？

RAG（Retrieval-Augmented Generation）的本质是"用更好的检索改善生成"。它把文档切成固定大小的块（chunk），用向量相似度找到最相关的块，然后塞进 prompt 让 LLM 生成答案。这个方法在纯问答场景有效，但在"记忆"场景有三个根本缺陷：

缺陷一：chunk 边界破坏语义 按 512 tokens 强制切分，会把一句完整的句子拆成两段。例如"我上周从北京搬到了上海"可能被切成"我上周从北京搬"和 "到了上海"——检索时只能匹配到前半段，丢失关键迁移信息。
缺陷二：无法处理知识演化 RAG 的索引是静态快照。新事实进来时，要么追加（索引越来越大、检索质量下降），要么重建（全量重新计算，成本高）。它无法理解"新信息覆盖旧信息"这一基本逻辑。
缺陷三：检索质量不稳定 向量相似度匹配依赖 Embedding 模型的质量，且不同领域的语义空间差异很大。在中文技术文档上的效果往往不如英文。

2. Supermemory 的三层架构

Supermemory 采用了"事实提取 → 知识图谱 → 时序推理"的三层设计，从根本上规避了 RAG 的缺陷：

① 事实提取层（Fact Extraction） Supermemory 不存储原始文本块，而是用 LLM 从对话/文档中提取结构化事实三元组：主体（Subject）+ 关系（Predicate）+ 对象（Object）。例如从"张三在 2024 年 3 月加入字节跳动担任后端工程师"中提取 fact_id=42, subject="张三", predicate="职位", object="字节跳动后端工程师", timestamp="2024-03-01"。每个事实还附带 LLM 评估的置信度分数（0~1）。
② 知识图谱层（Knowledge Graph） 所有事实以图结构存储，实体是节点，关系是边。图的增量更新成本远低于全量重建。当新事实与旧事实主体相同但对象矛盾时（如新fact说"张三搬到深圳"，旧fact说"张三住在广州"），图谱更新算法自动将旧事实标记为 superseded_by=new_fact_id，而非直接删除——这保留了知识演化的历史轨迹。
③ 时序推理层（Temporal Reasoning） 查询记忆时，系统根据当前时间戳和 fact 的有效时间窗口（valid_from / valid_until）动态构建召回上下文。同一实体的多个历史版本中，只有当前有效的事实会被召回。这解释了 LongMemEval 中 720 tokens 的极低开销——它不需要把整个知识库塞进 prompt，只需要当前相关的几条事实。

3. 嵌入模型的选择策略

Supermemory 支持可插拔的嵌入模型。本地默认使用 Xenova/bge-base-en-v1.5（轻量、CPU 友好），云端版本使用经微调的专用嵌入模型。选择建议：

英文为主、数据量 < 10 万条 → bge-base-en-v1.5（本地默认）
中文为主 → bge-base-zh（需手动配置）
追求精度、数据量 > 10 万条 → openai/text-embedding-3-large（云端）
完全离线 → Ollama + nomic-embed-text（无网络依赖）

4. MCP 协议的工作机制

MCP（Model Context Protocol）是 Anthropic 主导的 AI 工具互操作标准。Supermemory 作为 MCP Server，扮演"记忆服务提供者"的角色。当你在 Cursor 中配置了 Supermemory MCP 后，完整的交互流程如下：

1. 你在 Cursor 对话中提到："记住我的项目用 TypeScript，数据库是 Postgres"
2. Cursor 的 AI 将这段文本通过 MCP protocol 发送给 Supermemory
3. Supermemory 的 add() 方法被调用，LLM 提取事实三元组
4. 事实存入本地知识图谱（SQLite/PostgreSQL）
5. 下次新会话开始，Cursor AI 调用 profile() 注入用户画像
6. AI 在回复中引用："了解了，你用 TS + Postgres，我用 Prisma ORM 风格"

❓ 常见问题 FAQ

FAQ
Q: Supermemory 和向量数据库（如 Qdrant/Pinecone）有什么区别？ 向量数据库是"更好的检索工具"，Supermemory 是"记忆系统"。向量数据库存的是文档块，Supermemory 存的是从文档中提取的事实。两者可以互补使用——用向量数据库做快速语义检索，用 Supermemory 做事实追踪和知识演化。
Q: 支持中文吗？效果如何？ 支持。事实提取和语义搜索均支持中文。实测 bge-base-zh 在中文技术文档上的召回率约为英文的 85%。中文场景的实体链接和关系抽取效果略弱于英文，主要因为高质量中文知识图谱训练数据相对稀缺。
Q: 数据存储在哪里？隐私安全吗？ 本地部署时数据完全存储在你指定的数据库（默认 SQLite，本地开发；或 PostgreSQL，生产环境）。云端版本数据在 Supermemory 服务器，但支持加密存储和私有部署。关键：不要往 Supermemory 里存密码、密钥、身份证号等敏感明文数据。
Q: 可以同时给多个 AI 工具共享同一个记忆库吗？ 可以。通过 MCP 协议，多个 MCP 客户端（Cursor、Claude Code、VS Code Copilot 等）可以同时连接到同一个 Supermemory 实例，共享同一份记忆。这是 Supermemory 相对单工具插件的核心优势之一。
Q: 事实提取的延迟是多少？会影响 AI 响应速度吗？ 事实提取是异步的，不阻塞 AI 响应。add() 调用立即返回（< 100ms），实际提取在后台进行（通常 2~5 秒）。用户画像生成（profile()）延迟约 50ms（在 LongMemEval 基准测试中），这个延迟发生在 AI 开始生成之前，会注入到系统 prompt 中。
Q: 如何处理事实冲突（如用户前后说法矛盾）？ Supermemory 不会自动删除旧事实，而是将新事实标记为有效、旧事实标记为 superseded。这保留了知识演化的完整轨迹。如果需要只保留最新状态，可以在查询时设置 temporal_policy="latest_only"（默认行为）。
Q: 可以导入已有的 Notion 笔记或浏览器书签吗？ 可以。云端版本内置 Notion、Google Drive、GitHub 连接器，可以配置定期自动同步。本地版本可以通过 CLI 工具批量导入：supermemory import --source notion --workspace-id XXX。
Q: Supermemory 本身是开源的吗？许可证是什么？ 核心 SDK 和 MCP 服务是开源的（GitHub: supermemoryai/supermemory）。部分连接器（Notion、Gmail 等）和云端基础设施是专有服务，需要订阅。开源许可证为 Apache 2.0。
Q: 与 Personal Knowledge Management（PKM）工具如 Obsidian 相比有什么优势？ Obsidian 是人类可读的个人笔记系统，Supermemory 是 AI 可消费的结构化记忆。两者定位不同，可以互补使用——用 Obsidian 做日常笔记，用 Supermemory 提取笔记中的关键事实供 AI 使用。
Q: Supermemory 支持哪些数据库后端？ 本地开发默认使用 SQLite（零配置）。生产环境推荐 PostgreSQL（支持向量索引和全文搜索）。也支持 MySQL（需手动配置向量扩展）。所有数据库都支持加密存储（AES-256）。
Q: 可以自定义事实提取的 prompt 吗？ 可以。通过 client.configure({ extractionPrompt: "..." }) 自定义事实提取的系统提示词。这对于特定领域（如医疗、法律）的专业术语处理非常重要。
Q: 记忆容量有上限吗？ 本地版本无硬性上限，受磁盘空间限制。建议每百万条事实预留约 2GB 存储空间。云端版本根据订阅计划有不同的存储配额。

🔧 常见问题排查指南

排错指南

从安装到生产环境，整理了开发者最常遇到的问题和解决方案。遇到报错先查这里。

❌ 安装与启动问题

npm install 报 peer dependency 冲突 Supermemory 依赖较新的 Node.js API（如 Uint8Array、structuredClone）。确保 Node.js ≥ 18.x。使用 nvm use 20 切换版本，或用 npm install --legacy-peer-deps 强制安装。
supermemory: command not found（npm 全局安装后） npm 全局 bin 目录不在 PATH 中。检查 npm config get prefix，确保 $PREFIX/bin 在 ~/.bashrc 或 ~/.zshrc 的 PATH 中。也可以用 npx supermemory 代替全局安装。
Ollama 拉取模型失败（connection refused） 确保 Ollama 服务已启动（ollama serve），且默认端口 11434 未被占用。可以用 curl http://localhost:11434/api/tags 验证服务状态。代理环境需要设置 OLLAMA_HOST 环境变量指向代理地址。
pip 安装后 ImportError: No module named 'supermemory' 确保使用正确的 Python 版本。Supermemory 需要 Python ≥ 3.10。用 python3 --version 确认版本，并用 pip3 show supermemory 检查安装路径是否在当前 Python 环境中。

❌ MCP 连接问题

Cursor 中 MCP 工具不生效（连接成功但 AI 不调用） 检查 Cursor 的 MCP 配置是否正确（JSON 语法、路径、参数）。确认 supermemory mcp server 命令可以正常启动（不会立即退出）。在 Cursor Settings → MCP 中查看连接日志排查。
MCP server 启动后立即崩溃 通常是数据库连接失败导致。用 supermemory debug --verbose 启动，查看详细错误日志。常见原因：SQLite 文件权限不足、PostgreSQL 连接字符串错误。

❌ 事实提取质量问题

提取的事实不准确，hallucination 严重 这是模型能力问题。解决方案：① 切换到更强的 LLM（如 Claude 3.5 Sonnet 或 GPT-4o）；② 自定义 extractionPrompt，要求更保守地提取；③ 降低置信度阈值，过滤低质量事实。
中文事实提取效果差 默认模型针对英文优化。使用中文优化的模型：client.configure({ extractionModel: "claude-3-5-sonnet-20241022" })（Claude 对中文支持较好）。同时确保 Embedding 模型切换为 bge-base-zh。
重复事实堆积，同一实体出现多个相似条目 这是 fact deduplication 模块的问题。在 client.add() 时设置 dedup: true（默认开启）。如果仍有问题，检查嵌入模型的语义区分度，可能需要切换到更精细的 embedding。

❌ 性能问题

profile() 调用延迟超过 500ms 通常是因为向量检索规模过大。优化方案：① 启用缓存（client.configure({ cacheProfile: true })）；② 使用 HNSW 索引（client.configure({ indexType: "hnsw" })）；③ 限制检索结果数量（profile({ maxFacts: 50 })）。
大批量导入（>10,000 条）时内存溢出 Supermemory 支持分批处理。使用 client.addBatch(items, { batchSize: 100, concurrency: 4 }) 控制并发和批量大小，避免内存峰值。
