PRODUCT DISCOVERY · MULTI-AGENT · HERMES

一个人如何用
多 Agent 压缩
产品发现周期

用 Hermes Agent 的 subagent 并行能力，把传统产品发现流程（用户访谈→需求分析→原型设计→验证）的串行时间压缩为可重叠的并行流水线。

核心思路：把"人肉串行"换成"Agent 并行 + 结果汇总"。用 delegate_task 把研究、分析、生成、审查任务同时交给独立 Agent，结果由父 Agent 合成。每个阶段可审查、可中断、可修正。

subagents 并行 delegate_task terminal / web_search ⚠ 证据边界标注
HERMES AGENT 角色映射
四类 Agent × 产品发现阶段
🔍 研究 Agent
并行抓取竞品、用户评论、社交媒体信号；用 web_search 批量收集一手资料。
工具：web_search、browser_navigate
📊 分析 Agent
对研究结果做结构化分析：痛点聚类、需求分类、优先级打分，输出 Markdown 报告。
工具：read_file、patch、terminal
⚡ 原型 Agent
根据分析结论快速生成 PRD、原型描述或代码骨架，不等待人工确认。
工具：terminal、write_file、skill_view
✅ 审查 Agent
对原型做质量门禁检查：逻辑一致性、技术可行性、竞品差异化。
工具：read_file、browser_*

02 / Hermes Agent 能力核查

仅列出 github.com/NousResearch/hermes-agent README 明确标注的能力

能力 描述 在本流程中的作用 状态
subagents / parallel 父 Agent 可同时启动多个独立 subagent 进程并行执行任务 研究、分析、审查三路同时启动，时间成本从串行叠加变为最大路径 ✓ 已核实
delegate_task 将任务分发给独立 Agent，每个拥有独立 session 和工具集 各阶段 Agent 互不干扰，工具集按需配置（研究用 web_search，审查用 browser_*） ✓ 已核实
terminal 在宿主机执行 Shell 命令，支持 Python/Node/Go 等工具链 运行 Python 脚本做数据清洗、执行 MCP 工具、部署验证脚本 ✓ 已核实
memory 跨 session 持久化存储（User Profile + Agent Memory） 产品背景、品牌约束、技术栈偏好写入 memory，后续 Agent 自动注入 ✓ 已核实
skills 可复用技能单元，SKILL.md 格式，支持触发条件与步骤 将"竞品研究 → 分析 → 原型 → 审查"封装为 4 个 Skill，一键加载完整工作流 ✓ 已核实
cron 定时触发 Agent 任务，支持推送结果到指定平台 每日自动跑竞品监控竞品评论更新，新信号出现时主动推送 ✓ 已核实
web_search 内置网页搜索工具 研究 Agent 批量抓取市场数据、用户评论、竞品信息 ✓ 已核实
browser_* 浏览器操作工具集（navigate、snapshot、click、type 等） 审查 Agent 截图验证竞品 UI、分析页面结构、提取动态加载内容 ✓ 已核实
gateway / 多平台 接入飞书、微信、Telegram 等多平台消息渠道 发现结果自动推送到飞书群或个人微信，减少人工盯屏成本 ✓ 已核实
session_search 在历史 session 中检索上下文 父 Agent 回顾上一轮发现结论，避免重复研究同一问题 ✓ 已核实

03 / 证据边界与风险

显式区分"已核实事实"、"来源未核验"与"已知局限"

✓ 已核实（Hermes 官方 README）

terminal / subagents / parallel / delegate_task / memory / skills / cron / web_search / browser_* / gateway / session_search 均为 Hermes Agent 明确标注并文档化的能力，可直接在产品发现流程中调用。

⚠ 来源未核验（X 帖文 / 第三方案例）

X 帖文 @tyaplyap_ai（x.com/tyaplyap_ai/status/2079348474340888847）提及的收入数字、人物背景、具体案例均为未核验信息，不代表 Hermes Agent 实际能力上限或行业平均水平，不作为结论依据。

⚠ 已知局限与风险边界

幻觉风险：各 Agent 的 LLM 生成内容（PRD、需求假设、技术选型）均可能产生幻觉，审查 Agent 只能降低概率，不能完全消除。

并行成本：多 Agent 并行消耗 token 数量约为串行的 2~4 倍，需要评估 API 成本是否匹配发现阶段的价值。

工具可用性：web_search 质量依赖搜索引擎返回内容，竞品新功能或未公开信息无法被自动发现。

⚠ 流程适用边界

本流程适合探索期产品发现（方向未明确、需要快速扫市场），不适合以下场景：
· 交付确定性要求高的产品迭代（需要人工深度审查）
· 涉及敏感数据的用户研究（Agent 无法访问受保护数据源）
· 需要面对面访谈才能捕捉的隐性需求（仅靠二手数据分析）

04 / 使用风险速查

三个最常见的使用误区与对应的防御策略

🤖
把 Agent 结论当事实
PRD、需求假设、竞品分析均由 LLM 生成，存在幻觉。建议至少保留一个人工审查节点，尤其是关键决策点（Go / No-Go）。
💸
忽视并行 token 成本
4 个 Agent 并行 → 约 4x 单 Agent 成本。发现阶段预算有限时，优先对研究 + 分析两个高价值阶段并行，原型与审查仍可串行。
🔒
敏感信息注入风险
将竞品分析、用户评论输入给 Agent 前，确认数据合规边界。涉及用户隐私、NDA 协议内容不应通过 Agent 处理。
