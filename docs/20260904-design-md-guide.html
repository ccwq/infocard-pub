DESIGN.md：给 coding agent 的可执行设计系统

它不是灵感板，而是一份放在项目根目录的持久契约：用 YAML front matter 保存精确 token，用 Markdown 解释为什么这样设计，让 Claude Code、Cursor、Stitch 等代理在不同会话里保持视觉身份。

01 / MAP

这是什么

两层结构

YAML front matter 是机器可读的规范值；Markdown body 是人类和代理都能理解的设计理由。token 是 normative values，prose 说明应用语境。

解决重复口述

把“用什么颜色、字体、圆角多大”从一次性 prompt 变成项目内长期存在的 DESIGN.md。

当前状态

官方仓库标记为 alpha。规范、schema 和 CLI 仍会演进，版本敏感细节必须查当前 README。

02 / SCHEMA

八段骨架

固定阅读顺序

Overview → Colors → Typography → Layout → Elevation & Depth → Shapes → Components → Do's and Don'ts。

可省略，但别乱序

规范允许省略不相关 section；出现的 section 必须按顺序。重复 section 会被视为错误。

组件变体

hover、active、pressed 不塞成未知字段，而是用相关命名的独立 component 条目表达。

03 / DECIDE

什么时候值得写

适合

有存量页面、多个 coding agent、反复生成 UI、需要 Tailwind/DTCG 互操作的项目。

不适合

只有一次性的草图、没有可确认素材、或把设计选择完全交给模型而不准备验收的项目。

L4 目标

给定任意素材，能选择正确提取路径，写出能 lint 的 DESIGN.md，并区分可靠值与待核对值。

04 / FORMAT CONTRACT

Token schema：四种类型，先把值写对

下面是可复制的最小骨架。字段名和类型遵循官方 spec；自定义 token 名称可以有语义，但不要发明与规范字段冲突的顶层键。

---
version: alpha
name: Heritage
description: A warm editorial design system
colors:
  primary: "#1A1C1E"
  secondary: "#6C7278"
  tertiary: "#B8422E"
  neutral: "#F7F5F2"
typography:
  h1:
    fontFamily: Public Sans
    fontSize: 48px
    fontWeight: 600
    lineHeight: 1.1
    letterSpacing: -0.02em
rounded:
  sm: 4px
  md: 8px
spacing:
  sm: 8px
  md: 16px
components:
  button-primary:
    backgroundColor: "{colors.tertiary}"
    textColor: "{colors.neutral}"
    rounded: "{rounded.sm}"
    padding: 12px
---
类型写法注意
Color任意 CSS 颜色；推荐六位 hex要给描述性名称、精确值和功能角色。
Dimension数字 + px / em / rem例如 48px、-0.02em；spacing 也可使用数字。
Token Reference{colors.primary}引用路径必须真实存在，组件可引用复合 typography。
TypographyfontFamily / fontSize / fontWeight / lineHeight 等对象从代码拿 fontFamily 比从像素猜更可靠。
05 / IMAGE PATH

路径 A：从图像生成 DESIGN.md

图像适合回答什么

截图能帮助识别整体气质、视觉层级、颜色角色、圆角语言、阴影性格和组件关系。它适合命名和解释，不适合把一个像素颜色当成精确 token。

取色原则先用取色器、浏览器 DevTools 或设计稿工具得到真实值，再让模型负责“Boston Clay”这类语义命名。

四步做法

  1. 收集截图或设计稿，记录页面和组件上下文。
  2. 提取主色、辅助色、字体层级、圆角和间距节奏。
  3. 把不确定的字体、透明度和几何值标为“待确认”。
  4. 将结果写进 front matter，并在正文说明为什么这样用。
06 / CODE PATH

路径 B：从代码逆向，通常更精确

扫描顺序

  1. tailwind.config.js/ts 的 colors、fontFamily、borderRadius、spacing。
  2. globals.css 和 CSS custom properties。
  3. tokens.json、Figma 导出或组件库 theme 对象。
  4. 真实组件 className 与状态样式。

把 class 映射成组件 token

bg-[#B8422E]
text-white rounded-md px-3

→

components:
  button-primary:
    backgroundColor: "#B8422E"
    textColor: "#FFFFFF"
    rounded: "{rounded.md}"
    padding: 12px
证据分层Measured 是从代码或工具直接读到的值；Derived 是由 token 关系计算出的值；Inferred 是根据截图或语义推断的值。不要把 inferred fontFamily 写成已确认事实。
07 / VERIFY LOOP

生成之后的标准动作

npx @google/design.md lint DESIGN.md
npx @google/design.md diff DESIGN.md DESIGN-v2.md
npx @google/design.md export --format css-tailwind DESIGN.md > theme.css
npx @google/design.md export --format json-tailwind DESIGN.md > tw.json
npx @google/design.md export --format dtcg DESIGN.md > tokens.json

lint

检查结构、断裂 token 引用，并输出可供代理处理的结构化 findings；官方示例还展示 WCAG 对比度提示。示例 JSON 是示例，不是本机运行结果。

diff / export

diff 用来发现 token 和 prose 回归；export 将规范转成 Tailwind v3/v4 或 DTCG，适合做 round-trip 检查。

Windows 注意.md 后缀可能触发系统文件关联。PowerShell 的调用细节随 CLI 版本变化，使用前查当前官方 README；不要把未经当前版本验证的别名当成绝对保证。
08 / L4 CHECK

三问自检：你真的掌握了吗？

1 / 主提取源
截图 + CSS 同时存在时，选代码作为颜色、字体、圆角和间距的主源；图像补充氛围与语义。
2 / 优先拿什么
先拿颜色 token、fontFamily、borderRadius/spacing 和组件状态，而不是猜阴影扩散或字体名称。
3 / 最终命令
运行 npx @google/design.md lint DESIGN.md，再按 findings 修复结构和引用。
4 / 是否可消费
把 DESIGN.md 放在项目根目录，让代理读取后做一项真实但可回退的 UI 改动，再人工核验结果。
DECISION / STATUS

把设计判断写成契约，但别把 alpha 当成定稿

DESIGN.md 的价值不在于让模型“看起来更像”，而在于让设计系统拥有持久、可解释、可验证的来源。图像提供气质，代码提供精确值，YAML 提供结构，Markdown 提供理由，lint 提供机器可读的反馈。
