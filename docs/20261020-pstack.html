AI 写代码太快，但不敢信？ pstack 把 Lauren Tan 的工程规矩装进编程 Agent：先验证，再留痕，最后才谈速度。

它是什么：React 核心团队开发者 Lauren Tan（网名 poteto）把自己日常用的工程原则和 playbook 打成一个插件，住在 cursor/plugins 仓库的 pstack/ 目录。它不替你写代码，它管的是代码怎么被证明。
为什么值得看：它把"怕跑偏、怕写多、怕假完成、怕自吹、怕查不到"这五种不信任，各自换成一条可检查的机制，而不是又一段提示词。

作者原话 "i want you to write less, but with higher quality" 仓库 github.com/cursor/plugins（pstack 子目录） 目录清点 2026-10-20 github.com/cursor/plugins/tree/main/pstack
pstack 的赌注很直白：Agent 的可信度不来自更强的提示词，来自把验证成本、撤销成本和留痕成本做进流程里。
本页事实来自仓库 README、GitHub 目录清点与一条中文解读视频的转述。视频里的性能数字属于项目方自述，本卡未安装、未运行、未复现任何数字。

01 · WHAT IT IS

它不是又一个提示词包，是一套带验收条件的工程规矩

fearless parallelism是作者对设计目标的概括：当单个 Agent 能产出可验证代码时，可以并行启动多个 Agent，并让它们按同一套工程原则工作。这是 README 的项目方描述，不是本卡测出的成功率。

整套东西的骨架是三件套：playbook（流程）规定做事的顺序，principle（原则）规定什么时候必须停下改方向，subagent（子代理）负责把该拆的活拆出去。三件套之外没有魔法：它不接管你的仓库，也不替你决定要不要合并。

三条最能代表它态度的原文

  • "if you want to go fast, go deep first."——想快，先钻深。
  • "throughput without quality is not a goal i aspire to."——不把"吞吐"当目标。
  • 没有默认规划技能。README 原话是她不信规划，"the best spec is code"；需要规划时由 /poteto-mode 现场覆盖。

这一条决定了它的整体形状：先用 /prototype、/architect、/arena、/hillclimb 拿到证据，再把证据写成计划，而不是先写一份计划去解释。

02 · FIVE DISTRUSTS

它假设你会怕五件事，并给每件事配了一条机制

解读视频把使用者的恐惧归成五类，pstack 的条目几乎能一一对上。这张表是本卡认为最值得抄的部分——它给的不是形容词，是"出问题时有东西能看"。

你在怕什么对应机制具体怎么起作用
方向跑偏
做着做着不是你要的		/prototype · /architect · /arena · /hillclimb先出可丢的一次性原型，再要至少两份不同设计；/arena 让多个模型平行做同一件事，再由另一个模型当裁判按标准打分。
写多余东西laziness-protocol · subtract-before-you-add · minimize-reader-load · no-comments默认动作是删，不是加。第一条就是找到能删的部分；最小的改动是只动一处。30 秒内要能答出"这个数从哪来、什么会让它变"，否则不许加抽象层。
假装完成prove-it-works · test-behavior-not-implementation必须对着真实产物验证，不许拿模型自述当结论；"能编译"和"测试过了"都算不上证明，要跑一次真实交互，或举出没有证据时结论能错在哪。
自我吹捧/interrogate · attack-the-premise · 审阅模型 ≠ 编写模型审同一个改动的模型不能是写它的模型；只换人设不换模型，仍会漏掉同一批盲点。同一道关卡连续两次修复失败时，被质询的是前提本身。
事后查不到跳过留痕 · /show-me-your-work · encode-lessons-in-structure · /reflect跳过的步骤不会静默消失，留在 todo 里标 skip: 原因；决定日志按 TSV 记下做了什么、为什么、证据是什么；重复错误要变成 lint、runtime check 或脚本，而不是再多一句提醒。
视频里那句被反复引用的话：提醒本身是症状。如果一条规则需要每次都提醒，说明它应该被写成检查，而不是写在文档里。这条是 pstack 与其他规则包差别最大的地方。

04 · WHO DOES WHAT

默认按模型强度分工，不按"谁更聪明"分工

开箱状态下 /poteto-mode 就把活分成两路：规定得清清楚楚的代码任务给便宜快的那档，最难的改动、写文字和下判断留给强模型。默认面板是 opus 5.5 / grok，可以用 /setup-pstack 换成你自己的组合。

这一点很实用，因为它把成本绑到任务类型上，而不是一路用顶配。视频里那句吐槽也成立：这些平台都很烧 token，改一行明显的拼写错误不需要动用全套。

# Cursor
/add-plugin pstack

# Claude Code
/plugin marketplace add cursor/plugins
/plugin install pstack@cursor-plugins
# 命令带命名空间：/pstack:poteto-mode

Claude Code 那份是从仓库里生成的副本，只带当前版本用到的部分；Cursor 专有能力（bugbot、automations、benny 包）在别处用不到，命中时会跳过并留一行说明。

05 · GREEN IS NOT MERGE

"检查全绿"和"可以合并"在 pstack 里是两个决定

playbook 明确禁止两件事：把批准当成安全，把"能编译"当成"真的能跑"。审阅结果只写成 ready to merge，真正按下合并键仍然是人的事。绿色表示自动检查通过、没有未处理的 blocking finding。

证据必须带标签

凡是给出数字，得说明它属于哪一类：measured（量出来的）、inferred（推出来的）、guess（猜的）。explain-the-number 要求任何被引用的估算都带着假设、来源和不确定性；/show-me-your-work 把每条决定按"做了什么 / 为什么 / 证据 / 结果"记进 TSV。

项目方自述，本卡未复现：视频提到 pstack 团队用专门构造的陌生代码库做对照测试，两组都跑通 16 / 16 次运行，使用 pstack 的一组生成文本量按 token 计少约 62%。该数字来自视频转述，README 未给出实验数值，本卡没有安装或复现，不能当作普遍效果，也不能写成省 token 的保证。视频中另一句"某开发者当天省下约两小时"属于个人叙述。

注释这条也值得一抄：no-comments 会派 comment-sicko 在 review 前把注释剥掉，并把"别删这段、这里有约束"这类注释转成类型、runtime check、测试或 lint 规则——约束留在代码里，而不是留在文字里。

06 · REVERSIBILITY

可逆就别停下来问人，不可逆必须停

never-block-on-the-human 的写法很干脆：重新决定、重做一步、再跑一次测试、读一个文件、写代码、贴到团队群、更新任务清单、本地提交——这些都可逆，继续做。只有代价真正很高才要人来定：force-push 共享代码、部署上线、删数据、给真实客户发消息。

separate-before-serializing-shared-state 管另一件容易翻车的事：并行的写入方必须各有独立工作副本，写完之后再把改动汇到一起。

/orchestrate 更进一步，派一个专职协调者，它自己不写一行代码，管几十上百个 worker 推进几天量级的活。视频里给它的画面感是：你不用一直盯到全部合并完成，每天回来查两次就行。

这三条其实是同一条纪律的不同写法：把代价高的动作和代价低的动作分开，然后只在高代价那一侧要人。这一条不需要装 pstack 也能直接抄进你自己的 Agent 配置。

07 · WHAT IT COSTS

先说清楚哪些人不该装

  • 多模型并行会把开销放大。整套规则是按"高推理预算"设计的：审阅要换模型、/arena 要跑 N 份、反思要三个 Agent 做复盘。小的、明确的改动用不上全套。
  • 原则需要主动指定才能生效。不通过命令调用的那批 principle，是需要在对话里指定名称来转向；模型是否真按原则改了决定，仍需人工抽查证据。
  • 官方主入口是 Cursor。Claude Code 走生成的 harness 副本，部分 Cursor 专有能力不可用，命中时只留一行跳过说明。
  • 不随包提供 /deslop、control-cli、control-ui（它们在 cursor-team-kit），也没有 /create-skill（用 Cursor 内建）。
  • 数字会变。本卡的计数只是 2026-10-20 那一次目录快照；默认模型分工、playbook 名称和数量都可能随版本调整。
  • 它不解决"要做什么"。没有规划技能是它的立场，不是遗漏。如果你的问题本身还没定义清楚，这套规矩只会让执行更严格，不会替你把问题想明白。

本卡核对：README 原文、GitHub API 目录清点。本卡未核对：项目方性能数字、作者现任职务（视频称其在 xAI，本卡未核官方来源）、以及视频里被自动字幕转写坏的命令拼写——命令一律以 README 为准。

08 · MINIMUM USEFUL DOSE

别第一天就上全套：四件可以马上做的事

作者自己在视频里给的就是这个用法：先按平时的方式正常使用，看它到底在哪里让你难受；同一个问题第二次出现，再给它加一个技能或一条检查。下面四条按投入排序。

  • 只试一条纪律：在你的 Agent 配置里写死"可逆动作继续做，不可逆动作先问人"，并列明你这边哪些算不可逆。这是 pstack 里迁移成本最低、收益最直接的一条。
  • 抄"跳过要留痕"：让 Agent 把没做的步骤留在清单里写明原因，而不是静默跳过。审计成本几乎为零，出问题时能救回来。
  • 用"别加提醒，加检查"：同类错误第二次出现时，把它写成 lint 规则、类型约束或一个小脚本。README 的原话是：重复的失败要变成代码、测试或约定，而不是变成更多文档。
  • 想真装就一次到位地试小任务：装好 pstack 后，只拿一个真实的小 bug 跑 /poteto-mode，重点看你拿到的证据和跳过留痕长什么样，再决定要不要扩大使用。
一句判断标准：如果你现在的问题是"AI 写得慢"，pstack 不会帮你；如果你已经卡在"AI 写得快，但每次都要我重看一遍"，它这套分工值得照着改自己的流程。
