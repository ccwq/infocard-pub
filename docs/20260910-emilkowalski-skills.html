README 明确以 Claude Code、Codex 为主要运行对象。Skill 本身是 Markdown + 项目规则，能读取 SKILL.md 并执行 shell 的 Agent 理论上也可跟随，但不应把“理论可用”当成官方测试矩阵。

03

动画决策顺序：先问“该不该动”

ANIMATE

频率门

100 次以上/天的键盘快捷操作、命令面板切换：不做动画；每天几十次的 hover/list navigation：只做极轻的反馈；偶发的 modal、drawer、toast 才进入标准动画预算。

目的门

动画必须能归入反馈、空间一致性、状态提示、避免突变、解释或少量 delight。只有“看起来酷”不算理由。

工具门

简单淡入淡出用 CSS；需要 spring、layout、exit 或 gesture 才引入 motion。不要为了一个 hover 效果安装整个动画库。

核心判断：动画不是默认装饰，而是信息架构的一部分。被频繁触发的动作应该优先追求即时，而不是让用户等待一段“漂亮”的过渡。

05

从审查到落地：一次真实 UI 改动怎么走

WORKFLOW

第一步 · 让 Agent 先读现状

  1. 找现有 duration/easing tokens。
  2. 列出动画发生位置和触发频率。
  3. 区分现有动效问题与尚未动画机会。

第二步 · 选择入口

  • 要从零写一个交互：animate。
  • 要审查已有动效：review-animations。
  • 要全库只读扫描并生成计划：improve-animations。
  • 要找不该漏掉的少量机会：find-animation-opportunities。

第三步 · 验收交付

  • 进入/退出低于 300ms，除非有明确理由。
  • 有 reduced-motion；hover 有 fine pointer gate。
  • 快速触发可中断，不从零重播 keyframes。
  • 审查模式用 Before / After / Why 表格交付。
06

其它 Skill：不要只装 animate

SCENARIOS

pick-ui-library

面对 toast、OTP、command menu、drag and drop、virtualization、charts 等任务，优先从作者信任的列表选库；它要求先检查项目已有依赖，避免无谓换库。

07

边界：规则不是自动审美，也不是万能保证

BOUNDARIES
许可证：GitHub API 显示 MIT。数据快照：36,622 Stars / 2,062 Forks 是 2026-09-10 API 快照，README 的“12 skills”是仓库作者当前目录描述，不应把数量当稳定 API。运行边界：本卡没有在本地安装或执行这些 Skill；命令、规则和兼容性均按官方仓库 README/SKILL.md 核验。审查边界：Skill 能把判断框架交给 Agent，但不能替代浏览器、设备、性能和真实用户测试。
最小行动：先安装 → 只选一个实际问题（例如下拉菜单动画）→ 让 Agent 按“频率→目的→工具→曲线/时长→中断→无障碍”顺序给出决策 → 再查看 Before/After/Why 表格，不要一开始把 12 个 Skill 全部塞进上下文。
