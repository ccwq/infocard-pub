01

为什么“先变成文字”不是唯一入口

传统 RAG 通常先把 PDF / 图片 OCR 成文字，再切 Chunk、Embedding、进向量库。可是表格的位置、图表趋势、字体、颜色和空间关系本来就是信息；把它们压成文字，可能已经丢掉了检索线索。

OLD / 01Parse Everything先 OCR 全部文档，统一变成文字。
OLD / 02Search Text对文本切块、向量化并检索。
NEW / 01See Everything保留页面的视觉结构做检索。
NEW / 02Parse What Matters只解析被召回的相关页面。
NEW / 03Reason交给 LLM 做答案与推理。
核心判断这不是“EVIE 替代 PaddleOCR-VL”，而是把检索和解析拆成两个职责：先找对页面，再把页面变成模型可消费的结构。

03

三段式 Document RAG：把成本花在相关页面上

01 / RETRIEVE

视觉空间召回

离线为页面建立 EVIE 多向量索引；用户查询与页面视觉 token 做 late-interaction 匹配，先返回候选页。

02 / PARSE

按需结构化

将 Top-K 页面交给 PaddleOCR-VL 完整解析链，恢复版面、阅读顺序、表格、公式和图表。

03 / REASON

上下文推理

将解析后的 Markdown / JSON 与来源页交给 LLM，生成答案、引用或后续行动。

query → EVIE(page_images) → top_k_pages top_k_pages → PaddleOCR-VL(layout + recognition) → structured_docs structured_docs → LLM → answer + citations
04

EVIE：小向量不等于单一向量

EVIE 模型卡报告 4.54B 参数、原生 128D token vectors，并用 ColBERT 风格的 MaxSim 做 late interaction。它是多向量页面表示：保留多个视觉 token 的细粒度匹配，而不是把整页粗暴压成一个向量。

模型卡报告

ViDoRe V3 与 V1+V2 排名靠前；具体分数来自模型卡自报，接入生产前应独立复现。

索引成本

128D token 让每个 token 更窄；实际成本还取决于每页 token 数、精度、索引结构和语料规模。

工程条件

模型约 4.54B、BF16；部署需评估显存、吞吐、批量大小和多页图像预处理。

05

PaddleOCR-VL：解析不是“只跑一个 VLM”

PaddleOCR-VL 系列的核心 VLM 负责元素识别，但官方文档强调完整文档解析还需要布局分析和阅读顺序：先定位区域、裁剪元素，再识别并按顺序合并为结构化 Markdown / JSON。

解析对象可处理方向落地时要检查
文字多语言文字与版面内容扫描质量、字体、语言覆盖
表格单元格内容、行列关系和结构合并单元格、跨页表格、低清图片
公式识别并转为结构化公式表达手写/复杂公式和渲染一致性
图表图表元素与趋势相关内容是否开启 chart recognition、坐标语义
版本边界PaddleOCR-VL-1.6 的 96.3% OmniDocBench v1.6 是官方 benchmark claim；本文不把它当作所有业务文档上的保证。
06

什么时候值得采用这条链

✓ 更适合

  • 财报、论文、扫描件、表格和图表占比高的文档库
  • OCR 全量解析成本高，但大多数页面不会被查询到
  • 检索问题依赖版面、图形或空间关系
  • 已有 RAG reader，只需要更好的 visual retriever

✗ 不要直接套用

  • 纯文本语料或页面结构不影响检索的场景
  • 期待 EVIE 直接回答问题
  • 没有 GPU / 推理预算 / 索引维护能力的环境
  • 把 benchmark 排名当成自己的业务准确率
07

落地前的四个核验点

① 召回是否真的更好

用自己的文档、查询和 hard cases 比较 Recall@K / nDCG，而不是只看模型卡排行榜。

② 解析是否保留证据

保留页码、坐标、表格来源和原图，避免结构化结果脱离原始视觉证据。

③ 资源是否可承受

测算离线索引、Top-K 解析、显存、延迟、批处理和多页文档的总成本。

④ 隐私与版本

金融、医疗、内部文档需明确部署位置、日志、缓存、模型权重和第三方服务边界。
