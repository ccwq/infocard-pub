MattPocock 三技能：pr 讲清变化，implement-spec 推进实现，retro 改进环境。

这是一组可组合的编码 Agent 技能，不是一个替你包办决策的开发平台。适合已有代码仓库、真实验收条件，并愿意保留测试与审查的开发者。

PR：证据与风险实现：依赖与合流复盘：环境改进
第一步：先选一个目标仓库，再确认安装与项目约定。

第一次使用，先读下面的安装前提；已有代码变更，直接看 PR 模板。不要在需求未对齐时直接启动并行实现。

02
INSTALL & SETUP

安装前提：先有可用的编码 Agent

插件与 skills.sh 文件安装，每个 Agent 选一种，避免技能重复出现。

下面以 Claude Code 插件为默认路线。需要已安装且可用的 Claude Code；文件安装路线需要能运行 npx 的 Node.js 环境。完整实现还需要 Git、可读写的目标仓库、工单系统权限、测试工具，以及支持子 Agent 的执行环境。项目许可与权限应先确认；技能仓库采用 MIT License，不等于目标代码也采用 MIT。

Shell / 终端 · 官方 Claude Code 插件路线
claude plugin install mattpocock-skills@claude-plugins-official
其他 Agent，或需要可编辑文件？使用 skills.sh 路线

下列 <agent> 是占位符，替换为安装器支持的目标 Agent，例如 cursor；也可以省略 -a <agent> 交互选择。安装器询问技能时，包含 setup-matt-pocock-skills。

Shell / 终端 · 与插件路线二选一
npx skills@latest add mattpocock/skills -a <agent>
# 更新已安装技能；如需新增技能，再运行 add
npx skills@latest update

插件默认自动更新；skills.sh 会复制可编辑文件，需要你主动更新。不要给同一 Agent 同时装两份。

Agent 会话输入 · 在目标仓库中首次设置
/setup-matt-pocock-skills
  1. 选 issue tracker：GitHub、GitLab、本地文件，或明确描述其他系统。
  2. 约定分诊标签：告诉 Agent 你如何标注工单，供 triage 等流程使用。
  3. 选文档目录：确认生成文档应保存在哪里，不照抄别人的路径。

每个仓库运行一次 setup。首次验收不是“命令输完了”，而是 Agent 能找到已安装技能，并能正确复述当前仓库的 tracker、标签和文档目录。安装或 setup 若报错，先解决，不继续启动实现。

03
PR · SHOW THE CHANGE

PR 正文：最小图示、真实证据、合并风险

pr 是 model-invoked 技能：Agent 可在编写 PR 正文时主动采用它，不要求你必须输入某个固定 slash 命令。

它约束的是正文形状，不是授权 Agent 自动创建、合并或发布 PR。省去长开场，用项目 GLOSSARY.md 的领域语言表达变化，把图示紧贴对应说明。

Summary：选最小的视图

  • 逻辑变化 → 伪代码或控制流 diff。
  • 调用关系 → 调用树；UI 变化 → 组件树。
  • 目录职责 → 浅层文件树；交互顺序 → Mermaid。

不是六种图都要放；一个能说明关键变化的视图通常更好。

Evidence：前后来自同一问题

Before 给修改前截图、失败运行或输出；After 给相同场景的修改后证据。视觉变化且环境可用时，优先截图；否则给真实测试或运行结果。

未执行的测试只能标“未执行”，不能改写成“通过”。证据还应能定位命令、场景与对应提交。

+    return cached result

## Merge Danger
**Door:** two-way
[教学假设：不改持久化格式，可回退旧保存逻辑；合并前需核实]

**Blast Radius:** saving
[需验证重复保存、内容变化与缓存失效；不声称已经通过]

Door：回滚成本，不是情绪

two-way：能够低成本回退，例如可撤销的内部逻辑改动。one-way：破坏性迁移、数据删除或难以撤回的决定；恢复代码未必能恢复数据。

Blast Radius：影响范围

模板先要求一个词概括范围，再按需写后果。要考虑消费者兼容性、布局变化、移动端与共享服务，不是只数改了几个文件。

最小验收：审查者能在正文里找到“变了什么”“前后怎么证明”“出问题能否回退”“还会波及哪里”。PR 格式完整，不代表代码已经正确。

04
IMPLEMENT-SPEC · ORCHESTRATE THE GRAPH

按依赖图实现，不按列表盲目开工

implement-spec 是 user-invoked 技能。输入应是已对齐的 spec、关联工单及 issue tracker 约定。

Agent 会话输入 · 已完成准备与授权后
/implement-spec
# 同时提供：spec 的链接或路径、关联 tickets、tracker 约定
# 所有示例路径或链接均应替换为你的真实项目资源

目标：整个 spec 落到一个 integration branch（集成分支），每个工单按 tracker 的方式闭环。缺少 tracker，先运行 /setup-matt-pocock-skills，不是临时猜一个工单系统。

教学工单图（并非此技能仓库内置工单）：

             ┌─ B：调用方接入 ─┐
A：约定接口 ─┤                ├─ D：端到端验收
             └─ C：失效策略 ──┘

ready frontier：
开始只有 A → A 合流后 B / C 可并行 → B 与 C 都合流后 D 才就绪
  1. 读图与探索：理解阻塞关系；必要时用 exploration 子 Agent 调研，把可共享研究笔记存到仓库外的可访问目录。通信主要传 spec、工单、笔记与提交的指针，避免重复整份上下文。
  2. 建立集成分支：全部实现最终合流到这一分支。若 tracker 通过 PR 关闭工作，或用户要求 PR，在首次合流产生有效提交后再开 draft PR，关联 spec 和工单；空分支不能先开。
  3. 只派发就绪工单：implementer 尽可能后台并行。每个 implementer 使用自己的 worktree 与分支，开工确认基于集成分支；不一致时按原流程重新对齐。
  4. 每票用 TDD：implementer 调用 tdd，以测试反馈推进；报告完成前，将集成分支最新提交合入自己的分支。
  5. 独立合流：已完成工单交给 merger 子 Agent 合入集成分支；重新计算 ready frontier，再启动新解锁的票。
  6. 全量审查与修复：所有票完成后，在集成分支调用 code-review；审查发现交给单个 implementer 修复，避免多人同时追同一批问题。
  7. 收尾：已有 draft PR 则转为 ready for review；否则按 tracker 的闭环方式解决工单并报告集成分支。最后清理 implementer worktrees。
什么叫“真正完成”？看集成结果，不只看子 Agent 的 done

将 spec 的每个验收点映射到工单、代码与运行证据；确认阻塞图没有遗漏或被误判为就绪，合流后测试仍可复现，审查问题已处理，tracker 状态与实际交付一致。TDD 与 review 提供反馈，但不自动保证并发代码或产品行为正确。

执行环境是硬前提。原始技能明确要求 worktrees、分支与 merge。本信息卡仓库禁止 worktree；教程不在此仓真跑这套流程，也不改变发布约束。若你的目标项目禁止 worktree，或 Agent 不支持相应并行能力，不能原样执行，须先另议执行方案。

05
RETRO · IMPROVE THE ENVIRONMENT

复盘不是总结心情，而是减少下次犯错

retro 是 user-invoked：读取指定会话的一手记录；未指定则默认当前会话，按严重程度提出环境改进候选。

Agent 会话输入 · 建议明确复盘对象
/retro
请复盘当前编码会话，先提出改进建议，不修改配置或清理文件。

原流程先使用 writing-for-agents 作为文风指南，再检查导航、自动检查、编码标准、全局 AGENTS.md、工具经济性、无效指令与信息访问。重点是错误为什么能穿过环境，而不是写一篇“收获很多”。

机械问题 → 确定性检查

固定语法模式、禁用 API、import 形状、文件位置等，应优先交给现有语言 linter、pre-commit 或 CI。先读仓库真实 lint / check / test 脚本与 CI；已有但没接上、静默失效的检查本身就是发现。

没有任何 guardrail 也应指出，不当作正常默认值。不要另造一套检查器来重复已经能用的检查。

判断问题 → 审查标准

跨文件一致性、是否符合周边风格、难以被机械检查替代的判断，才进入 CODING_STANDARDS.md，主要由 reviewer 执行。

实现 Agent 承担探索、编码与调试的上下文压力；审查 Agent 接收 diff，更适合执行编码标准。

会话中的观察更合适的候选改进先验证什么
反复找不到文件或隐藏依赖在精简的 AGENTS.md / CLAUDE.md 中加入导航指针现有 docs 是否已有答案；不要复制整篇文档
可被 lint / 类型 / 测试捕获的错误漏过接通或修复仓库现有检查；确实缺失再补 guardrail真实脚本与 CI 是否运行、是否可靠失败
指令文件越来越长、无效要求堆积移动规则到标准或检查，删除行为无变化的指令候选指令是否实际改变行为，是否只是重复口号
昂贵工具调用或关键日志缺失精简工具路径；建议保存开发日志或只读信息入口成本与错误之间的因果证据、权限和敏感数据边界

有效提案的形状：会话证据 → 原因 → 最小环境改动 → 如何验收。retro 的原始交付是建议候选；未经同意，不把建议升级成改配置、扩大服务权限或删除文件。

07
FAILURE MODES & PERMISSIONS

常见误用：别把流程当成正确性保证

以下是从原始技能要求归纳的使用边界，不是视频“常见错误”章节的转述。

把所有技能当固定 slash 命令

pr 可由 Agent 按任务调用；implement-spec 与 retro 标记禁止模型自主触发，应由用户明确启动。不同宿主的命令展示可能不同，先确认安装后可发现。

跳过 setup，猜 tracker 与路径

spec、tickets 的关联和关闭方式依赖项目约定。没有 tracker 先设置，不拿示例路径当真实资源。

把独立工单误判为全部可并行

只能并行 ready frontier；依赖未满足不能开工。worktree、分支合流、冲突处理和最后 review 都不能省略。

用“测试通过”替代实际证据

保留相同场景的 Before / After。截图、输出、失败与通过运行来自真实执行；没有证据就明确缺口，不能编造数字。

把复盘建议变成自动改环境

CI 配置、全局指令、信息权限和清理动作都要确认范围。先用现有检查，别用更长的文档替代能自动拦截的错误。

误把标题 1.3 当当前 release

当前官方文档可能继续演进。视频的版本口径与线上文档分别引用，不把旧技能命名或过时 CONTEXT.md 约定混入当前流程。

不适合原样启动实现的情况：需求未收敛、工单依赖缺失、目标仓库禁止 worktree、宿主缺少所需子 Agent 能力，或没有写入 / 合并授权。安装技能不是授予权限，提出建议不是批准删除，PR 正文也不是合并许可。

本轮仅制作中文指南，未安装插件，未运行三个工程技能，也未创建分支、工单或 PR。
