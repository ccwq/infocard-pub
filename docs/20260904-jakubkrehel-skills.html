A PRACTICAL SKILL LIBRARY

把界面做好，变成 Agent 可执行的检查项

jakubkrehel/skills 是一套面向设计工程的 Agent Skills 集合：把 UI、字体、颜色、可访问性、布局和文案经验，组织成可以安装、调用、复盘的工作流。

THE FIRST DECISION

先安装“总审查”，再按问题深入

如果你只想马上开始：安装仓库，然后让 better-interface 对真实项目做一次基线审查。它会按 accessibility → layout → writing → typography → colors → ui 的顺序编排领域 Skill，并统一严重度、合并重复发现、最多输出 15 条，最后给出 Block / Approve。

读者今天可以做的第一步：npx skills add jakubkrehel/skills，再对一个真实页面运行一次审查。
01 / KNOWLEDGE

六个领域 Skill better-*

解决“应该用什么值、由谁负责”的具体知识问题。

02 / WORKFLOW

五个流程 Skill

把全局审查、变更评审、极端状态、变体和逆向分析串起来。

03 / EVIDENCE

证据优先

将结论区分为 Measured、Derived、Inferred，不把审美意见伪装成测量结果。

04 / BOUNDARY

不越权

break 只观察不评判，variant 列出取舍但不替用户选优。

05 / REUSE

一次安装，多个项目复用

把个人设计判断沉淀为项目级 Agent 可调用能力，而不是每次重新解释一遍视觉标准。

01 · DOMAIN MAP

六个领域：从视觉细节到可用性底线

这六个 better-* Skill 是知识层。它们不负责替你编排全部检查，而是各自覆盖一个具体质量维度。

  1. UI
    better-ui：检查同心圆角、光学对齐、上下文图标、点击区域和动效，让界面细节更有秩序。
  2. TYPE
    better-typography：处理字阶、间距、尺寸、可变字体、OpenType、换行与截断，避免“字能看但层级不稳”。
  3. COLOR
    better-colors：生成和整理色板，使用语义 token，在格式转换和对比度测量之间保持一致。
  4. A11Y
    better-accessibility：覆盖语义、键盘、焦点、表单和读屏；它是上线前的底线，不应被视觉偏好覆盖。
  5. LAYOUT
    better-layout：检查分组、对齐、阅读顺序、响应式和其他让页面“易于理解”的布局关系。
  6. WORDS
    better-writing：统一产品文案、术语和语气，让界面在视觉修复后仍然清楚、可信、可行动。
02 · WORKFLOW MAP

五个流程：不同问题，不同入口

不要把所有任务都交给同一个“审美 Agent”。先按任务性质选择入口，再让它输出可审阅结果。

  1. ALL
    better-interface：全局编排器；按固定顺序调用六个领域 Skill，收敛为最多 15 条并给 Block / Approve。
  2. DIFF
    interface-review：变更评审；解析 diff 范围，扩展“爆炸半径”，逐行找回归，并分类 Introduced / Regression / Pre-existing。
  3. BREAK
    break：把一个组件放入临时页面，渲染超长文本、空态、窄屏等极端场景；只观察，不评判。
  4. VAR
    variant：沿单一设计轴构建 3 个刻意不同的变体，挂到真实页面的 ?variant= 切换器后，列出取舍表，不选优。
  5. XRAY
    explain-interface：按绘制顺序拆解别人的网页效果，找图层栈，并给每个结论标注证据等级。
03 · DAILY ROUTE

日常使用：四种场景，四条最短路径

01

新页面基线

先运行 better-interface。它适合发现跨维度问题，但结果仍需人类确认。

02

改动后回归

使用 interface-review，先看 diff，再区分本次引入的问题与历史遗留问题。

03

组件压力测试

使用 break，把真实组件放进临时页，专门观察 320px、长文本、空态和异常数据。

04

设计探索

使用 variant，只改变一个轴，例如密度或圆角，比较取舍而不是寻找唯一审美答案。

05

参考网页逆向

使用 explain-interface，把“看起来很高级”拆成可验证的图层、时序和材料。

06

最终收口

回到 better-interface 或人工清单，复核严重度、范围和是否真的可发布。

04 · ORCHESTRATION

编排顺序：为什么先可访问性，再谈视觉

顺序检查层要回答的问题输出
1Accessibility键盘、焦点、语义和读屏用户能否完成任务？底线问题 / Block
2Layout分组、阅读顺序、响应式和逻辑属性是否成立？结构问题
3Writing用户是否知道发生了什么、下一步是什么？理解问题
4Typography字阶、换行、截断和数字信息是否稳定？阅读问题
5Colors语义 token、格式和对比度是否可测量？系统问题
6UI圆角、图标、动效和点击区域是否精确？表面问题 / Approve
关键原则：审查不是“列出越多越好”。合并重复发现、限制输出数量，并让每条结论回到真实 diff、DOM、截图或测量。
05 · INSTALL

安装与 Claude Code 插件

仓库本身是 Markdown Skill 集合，不是需要编译的运行时服务。可以使用 skills CLI 安装，也可以通过 Claude Code marketplace 使用。

npx skills add jakubkrehel/skills # Claude Code /plugin marketplace add jakubkrehel/skills /plugin install interfaces@interfaces

安装完成后，先读仓库 README 和目标 Skill 的 SKILL.md，确认它的输入、只读边界和输出形式，再在真实项目执行。

06 · VERIFY

如何验证，而不是盲信

  1. READ
    先确认项目范围：本次是新页面、改动评审、压力测试、变体探索还是逆向分析。
  2. RUN
    提供真实但可回退的页面或组件，避免只在抽象描述上审查。
  3. CHECK
    对长文本、空态、窄屏、键盘、焦点、颜色对比度和真实 diff 做针对性复核。
  4. CLASS
    标注 Measured / Derived / Inferred；把模型建议与事实测量分开。
  5. DECIDE
    人类负责最后的 Block / Approve，不把一次 Agent 输出当成生产质量证明。
DECISION / BOUNDARIES

适合沉淀设计判断，不适合替代验收

这套 Skills 最适合已经有真实项目、希望把设计工程经验变成可复用 Agent 工作流的团队。它能缩短检查清单的组织成本，但不会自动拥有你的产品上下文，也不会因为“better”前缀就保证结论正确。

  • 适合：UI 质量基线、变更回归、组件极端状态、设计探索、参考网页拆解。
  • 不适合：没有真实页面或 diff 的空泛审美评判；不可逆发布前的唯一审批；无法提供脱敏输入的敏感项目。
  • 风险：实际兼容性、Agent 输出质量和项目适配需要在你的环境中验证；本卡未在本机运行这些 Skill。
  • 来源边界：项目事实以第一方 GitHub 仓库为准；社交帖仅作为发现线索。
