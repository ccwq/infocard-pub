先记住：这不是“把界面做得像苹果”的皮肤教程，而是一套将 Human Interface Guidelines 转换为可检查决策的学习和工作方法。品牌可以改变颜色、插画和文案，但不要为了独特而破坏用户已经熟悉的导航和交互。

01 · 先做判断：HIG 解决什么问题

设计一个 App 时，最难的往往不是画出一个漂亮页面，而是决定用户下一步该做什么、系统是否能解释当前状态、错误能不能恢复，以及不同能力和不同设备的人能否完成同一任务。Apple 的 Human Interface Guidelines（HIG）提供跨 Apple 平台的设计指导与最佳实践，帮助设计者在信息架构、交互、文字、颜色、动效和可访问性上做出有理由的选择。

来源帖子把 HIG 进一步整理成一套可供 Agent 学习的实践框架。它的价值不在于把 Prompt 贴给模型后自动生成“正确设计”，而在于把隐性的设计判断显式化：每个模式要说明何时使用、何时不使用、对应什么系统组件、有哪些空状态和错误态，以及最终可以用哪条规则验收。

设计问题应该问什么对应原则
页面为什么存在这个界面帮助用户完成哪一个主任务Purpose / Simplicity
操作是否可控用户能否取消、撤销、返回并知道发生了什么Agency / Feedback
学习成本是否过高是否复用了用户已经熟悉的系统模式Familiarity
是否覆盖不同人群文字、颜色、声音、手势是否有替代路径Flexibility / Responsibility
是否只是装饰动效和视觉细节是否帮助任务而非打断任务Craft / Delight

02 · 八条原则：从口号变成决策句

  1. Purpose：先明确当前界面服务的任务，删除不能帮助任务的内容。如果首页同时争抢五个主操作，说明 Purpose 还没有被确定。
  2. Agency：让用户按自己的方式完成任务。破坏性操作需要确认，能撤销就提供撤销，网络慢时不能让用户猜测是否已经提交。
  3. Responsibility：少要权限，解释用途，默认保护隐私。权限弹窗不是增长入口，而是用户对风险的授权判断。
  4. Familiarity：优先使用系统已经建立的导航、返回、搜索、分享和编辑模式。用户不应该为每个 App 重新学习一套基础语言。
  5. Flexibility：适配不同尺寸、横竖屏、动态字体、VoiceOver、深色模式和辅助输入方式。响应式不是只把两栏变一栏。
  6. Simplicity：一层一个任务，文案短，层级清楚。减少装饰性选项比增加说明文字更有效。
  7. Craft：间距、对齐、触控热区、动效时长和反馈位置都应该有理由。细节不是最后的抛光，而是任务能否完成的一部分。
  8. Delight：愉悦是顺畅完成任务后的结果，不是不断弹跳、闪烁和打断。动效应帮助用户理解状态变化。
实践句式：“当用户要完成 X 时，使用 Y 系统模式，因为它符合 Z 原则；验收标准是用户能在不阅读教程的情况下完成 A，并能观察到 B 状态。”

03 · iPhone 平台惯例：先复用系统心智模型

来源框架建议把平台惯例放在品牌个性之前。对 iPhone App，常见的默认选择包括：主导航使用底部 Tab（通常 3–5 个）或顶层 NavigationStack；设置、账户和列表型内容使用 Inset Grouped List；次级页面使用 Push；临时任务使用 Sheet 或 Full Screen Cover；搜索采用系统 Search 形态；主操作在 Toolbar 与 FAB 中选一套，而不是让两套主按钮互相竞争。

需求优先模式不要先做什么
切换一级区域底部 Tab，控制在 3–5 个高频区域发明带复杂手势的环形导航
查看详情NavigationStack + Push每次都弹全屏对话框
完成临时任务Sheet 或 Full Screen Cover把临时任务混入主导航
设置/账户/列表Inset Grouped List照搬 Web Dashboard 多栏侧边栏
搜索内容系统 Search 入口除非有强理由，否则不要自绘搜索栏
一个主动作Toolbar 或 FAB 二选一同时放两个同权重浮动按钮

这些是默认起点，不是无条件规则。游戏、专业工具或有特殊硬件输入的 App 可能需要不同结构，但偏离系统模式时应该能说明用户收益和替代方案。否则“更独特”往往只是增加学习成本。

04 · 参考产品：提取模式，不复制皮肤

来源框架列出 WhatsApp、Reddit、Slack 和 GitHub 作为模式参考。观察它们时，不要只截取颜色和圆角，而要拆解它们如何组织任务、层级和返回路径。WhatsApp 把账户和设置放进分组列表，让聊天成为内容主场；Reddit 以稳定底部导航承载个人页和内容浏览；Slack 处理工作区切换与列表层级，并将次要功能收进 More；GitHub 用标准列表、分区头和详情层级承载仓库、讨论和收藏。

提取信息架构

一级入口有几个？用户从首页到核心任务需要几步？返回后是否回到原上下文？

提取状态设计

加载、空状态、错误和成功反馈分别在哪里出现？是否能恢复？

提取系统组件

哪些部分可用 SwiftUI 原生组件表达？哪些只是内容和品牌层？

提取决策规则

把观察写成 If X then Y，而不是“这个看起来很舒服”。

边界：参考 WhatsApp 等产品是为了复用用户已有的心智模型，不代表它们的每个交互都适合你的产品，也不代表你的实现已经获得 Apple 合规认证。

05 · 模式知识卡：每个组件都要能回答八个问题

无论你研究的是 Inset Grouped Settings、Tab 导航、搜索还是错误反馈，都用同一张知识卡记录。统一格式能让人和 Agent 共同消费，也能让设计评审从审美偏好转为可执行约束。

  1. 模式名称：使用用户和平台都能理解的名称。
  2. 适用场景：什么任务、信息量和用户状态下使用它。
  3. 不适用场景：什么时候会增加层级、遮挡内容或打断任务。
  4. 信息架构：父级、子级、返回路径、主次任务和状态位置。
  5. 关键组件：对应的 SwiftUI 或通用系统组件，避免抽象成自定义万能容器。
  6. 状态集合：默认、加载、空、错误、完成、离线和权限不足。
  7. 无障碍：VoiceOver 标签、动态字体、对比度、辅助输入和非手势替代。
  8. 一句规则：写成 If X then Y，便于代码评审与测试。
模式：Inset Grouped Settings
适用：设置、账户、分组型选项
不适用：连续阅读、沉浸式画布、需要强横向比较的表格
IA：设置首页 → 分组 → 详情/编辑 → 返回原位置
组件：List / Section / NavigationStack / Toggle
状态：默认、加载、空、错误、已保存
无障碍：Dynamic Type、VoiceOver label、足够热区、不要只用颜色
决策规则：If 用户要修改少量相关设置 then 用分组列表而不是自定义 Dashboard

06 · 触控、文字与层级：把“好用”写成尺寸规则

来源帖子建议触控热区至少 44pt、正文使用系统字体层级、尊重 Safe Area 和系统材质层级。Apple Accessibility 页面则给出更细的参考：iOS/iPadOS 系统定义的文字默认大小为 17pt，最小参考为 11pt；默认控件尺寸为 44×44pt，最低参考为 28×28pt。控件之间的间距同样重要，不能只把可点击区域做大，却让相邻动作容易误触。

检查项最低实践常见失败
触控目标默认按 44×44pt 设计，必要时扩大不可见热区图标看起来小，点击区域也小
文字缩放支持 Dynamic Type，放大后不截断核心操作固定高度导致标题和按钮被裁切
Safe Area关键内容不被刘海、底部指示条或浮层遮挡把按钮贴在屏幕边缘
颜色使用系统色或提供足够对比，并用形状/图标辅助只用红绿区分成功和失败
文案按钮用动词，标题用名词，避免内部黑话“继续”“处理”“执行”没有上下文

不要把 44pt 当成唯一的设计答案。文字链接、列表行、手势区域和复杂控件的具体实现要结合平台规范与实际测试；但任何低于常用触控尺度的设计都应该有明确理由和替代路径。

07 · 无障碍验收：不要等开发完成才检查

Apple 官方将可访问界面概括为直观、可感知和可适配。设计时不要依赖单一感官或单一交互方式。VoiceOver 用户需要准确的元素标签和操作结果；低视力用户需要更大文字和足够对比；色觉差异用户不能只依靠红绿；听觉信息应有字幕、文字稿、视觉提示或触觉反馈；行动受限用户需要键盘、辅助设备或屏幕上的替代操作。

  • VoiceOver：按钮标签要说清动作和对象，状态变化要能被辅助技术感知。
  • Dynamic Type：将文字当作会变化的布局输入，测试放大后的换行、按钮高度和滚动。
  • 对比度：普通小字号文字参考 WCAG AA 4.5:1；粗体或较大文字可参考 3:1，实际以当前平台和标准为准。
  • 不要只用颜色：为状态补充图标、形状、文字或位置差异。
  • 手势替代：滑动删除旁边提供编辑/删除按钮，复杂多指手势不要成为唯一入口。
  • 键盘与语音：检查 Full Keyboard Access、Voice Control、Switch Control 和 Pointer Control。
  • 动效：响应 Reduce Motion，减少自动、重复、快速闪烁、缩放和外围运动。
  • 限时界面：避免没有明确理由的自动消失，让用户有时间阅读和恢复。
验收问句：如果用户看不见颜色、听不见声音、不能完成复杂手势或需要把文字放大 200%，核心任务是否仍然可以完成？

08 · 状态设计：默认、加载、空、错误和成功都要有路径

很多界面只设计了“有数据且网络正常”的理想状态。真正的产品体验发生在等待、失败、权限不足和用户第一次打开页面时。每个模式知识卡至少要画出状态集合，并说明用户下一步能做什么。

状态用户需要知道设计动作
加载系统正在做什么，是否可以离开显示进度或稳定占位，避免无意义闪烁
空状态为什么为空，如何开始说明原因，给一个明确动词入口
错误发生了什么，数据是否安全短文案 + 重试/返回/修复动作，不责怪用户
权限不足为什么需要权限，不授权会怎样先解释用途，再让用户选择
成功操作是否完成，结果在哪里提供可感知反馈，必要时支持撤销
离线哪些内容是旧的，哪些操作会延后明确同步状态，不伪装成实时数据

状态反馈是 Agency 的一部分。用户不应该通过猜测按钮颜色或等待页面自己变化来判断结果；设计要让状态可感知、可解释、可恢复。

09 · 设计决策工作流：从观察到实现

  1. 定义任务：写一句“用户在这个页面要完成什么”，再列出非核心内容。
  2. 选系统模式：从 Tab、NavigationStack、List、Sheet、Search、Toolbar 等已知模式中选择。
  3. 写知识卡：记录适用、不适用、IA、组件、状态、无障碍和 If X then Y 规则。
  4. 做低保真原型：先用黑白和系统组件验证层级，暂时不投入品牌视觉。
  5. 加入品牌：将品牌放到颜色、插画、图标、空状态和文案，而不是改写基础导航。
  6. 做代表性任务：测试首次打开、正常流程、错误恢复、返回、取消和重复操作。
  7. 做辅助验收：放大文字、开启 VoiceOver、Increase Contrast、Dark Mode 和 Reduce Motion。
  8. 记录偏离：如果没有采用系统模式，写清原因、收益、风险和替代方案。
任务：用户在 30 秒内找到并修改通知设置
模式：Settings → Inset Grouped List → Push detail
主操作：保存，完成后返回原位置
错误态：保存失败，保留输入并提供重试
无障碍：支持 Dynamic Type / VoiceOver / 44pt 触控目标
验收：首次用户不看教程能找到入口；失败后不会丢失修改

10 · 反模式：哪些“看起来特别”其实在伤害体验

  • 为了品牌个性改掉 Tab、返回、系统分享或权限弹窗，迫使用户重新学习基础动作。
  • 把 Android Material、Web Dashboard 或游戏 HUD 直接搬到 iPhone，没有重新考虑触控、层级和导航。
  • 用自绘搜索栏、自定义返回手势或多指手势替代系统模式，却没有提供可访问替代。
  • 把所有功能塞进首页，认为信息越多越显得产品强大。
  • 只做成功态，不做空、错、加载、离线和权限态。
  • 用颜色、阴影和动效掩盖信息架构问题。
  • 让模型背诵 HIG 条款，却没有要求它输出适用场景、反模式和验收标准。
  • 把参考产品的视觉皮肤当成设计系统，忽略自己的用户、任务和平台约束。
判断规则：如果一个设计只能通过“用户看教程”才能完成核心任务，先检查是否偏离了 Familiarity 和 Simplicity，而不是继续增加提示气泡。

11 · 给 Agent 的学习输入：如何使用这套 Prompt

来源帖子建议把 Apple HIG 链接、截图和要参考的 App 一起提供给 Agent，再让它以资深 iOS/跨平台产品设计师的角色工作。更可靠的使用方式是把 Prompt 当作任务合同，而不是权威答案：每次要求 Agent 先引用对应原则，再给出平台模式、组件、状态、无障碍和反模式，最后输出可执行的决策句。

请分析这个 App 的设置页：
1. 先说主任务和非主任务；
2. 指出使用了哪些系统模式；
3. 对每个模式给出适用/不适用场景；
4. 列出默认、加载、空、错误、成功状态；
5. 检查 Dynamic Type、VoiceOver、对比度和触控目标；
6. 引用 Purpose / Familiarity / Simplicity / Agency 中相关原则；
7. 输出三条 If X then Y 决策规则；
8. 明确哪些判断来自官方 HIG，哪些只是你的设计建议。

如果 Agent 的结论涉及最新平台组件、尺寸或无障碍细节，应回到 Apple 官方 HIG 对应章节核对。来源帖本身是经验整理，不应被伪装成 Apple 的官方 System Prompt。

12 · 最终验收清单：一张屏幕是否真的准备好了

  1. 能否用一句话说清页面主任务，并删掉非必要争抢项？
  2. 一级导航、返回、搜索和临时任务是否优先采用用户熟悉的系统模式？
  3. 按钮是否使用明确动词，标题是否表达内容对象？
  4. 触控目标、间距、Safe Area 和不同屏幕尺寸是否经过测试？
  5. Dynamic Type 放大后是否仍可读、可滚动、可操作？
  6. VoiceOver 是否能读出元素名称、角色、状态和操作结果？
  7. 是否没有只用颜色表达成功、错误、选中或警告？
  8. 加载、空、错误、离线、权限不足和成功状态是否都有下一步？
  9. Reduce Motion 开启后，动效是否减少且任务仍然清楚？
  10. 不可逆操作是否确认、可撤销，或至少提供明确恢复路径？
  11. 品牌是否落在视觉和内容层，而不是破坏基础交互语言？
  12. 每一个偏离系统模式的决定是否记录了理由、收益和风险？
