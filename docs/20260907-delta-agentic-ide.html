01Zed 创始人的新赌注：为什么"编辑器 → 线程"是范式转移

如果你用 VS Code + Copilot，或者 Cursor、Claude Code，你会发现一个共同的不便：每次开始新对话，AI 就忘掉了之前的一切。你花了半小时解释项目结构、代码规范和架构决策，下一次打开窗口，这些记忆就消失了。

这就是 Delta 试图解决的核心问题。它的创始人 Nathan Sobo 同时也是 Zed 编辑器的原作者——那个以"速度极快"著称的代码编辑器。2024 年，Sobo 从 Zed 团队抽身，创立了新公司 Delta，推出了同名产品 Delta IDE。

"Software is moving from the editor into the thread. We built DeltaDB to make the conversation and worktree one shared, replicated space for developers and agents." — Nathan Sobo, Founder and CEO, Delta（delta.dev 官网原文）

这句话值得细读：Sobo 认为软件开发的未来不在"编辑器"里，而在"线程"（Thread）里。你不再是在编辑器里敲代码、偶尔召唤 AI 补全一下；而是在一个"线程"里发起任务，AI 帮你把代码改好，对话和代码变更永远绑在一起。

Delta 的核心技术叫做 DeltaDB——它把"对话"（你发给 AI 的指令和它的回复）和"工作树"（你的代码文件）放进同一个"共享、可复制的空间"。这意味着：每当你回看一段代码的变更历史，你看到的不只是 diff，还有产生这段 diff 的原始对话。

初学者提示：什么是范式转移？ 简单说就是"做事方式的根本改变"。从"在编辑器里写代码"到"在线程里管理任务"，就像从"手写书信"到"即时通讯"——表面看都是通信，底层逻辑完全不同。

传统 AI 编程工具的做法

Copilot 做补全、Cursor 做 Composer——每次对话是独立的，上下文窗口用完即丢弃，项目知识靠手动文档化（CLAUDE.md、RULES 文件等）。

Delta 的做法

对话本身成为项目资产的组成部分。DeltaDB 自动记录每个任务的所有对话历史和代码变更，跨会话保持 Agent 状态，不需要手动维护项目文档。

02核心架构：DeltaDB 如何让对话与代码"合二为一"

理解 Delta 最好的方式是理解它的核心抽象：Thread（线程）。你在 Delta 里做的每一件事——不管是问"How does this module work?"还是让 AI 重构一个函数——都发生在一个 Thread 里。

传统 IDE 的工作流是这样的：你写代码 → 遇到问题 → 打开 Copilot 问一句 → 得到答案 → 继续写 → 答案从此消失。而 Delta 的工作流是：你创建一个 Thread → 在 Thread 里描述任务 → AI 执行 → 结果记录在 Thread 里 → 随时可以回到这个 Thread 继续对话。

DeltaDB 负责背后的一切同步工作。它是一个专为这种"对话 + 代码"双写场景设计的数据库（推测基于 CRDT 或类似的无冲突复制数据结构，以支持多人实时协作）。官网宣称它是"shared, replicated space"——同一个空间里的所有参与者（开发者、多个 AI Agent）看到的是同一份状态。

Thread 的锚定特性

官网明确指出："The thread stays connected to every change"——每个代码变更都可以追溯到产生它的对话与提示词。评论锚定在对话或任意代码行，feedback stays anchored as the work evolves。

多人实时协作

"Invite teammates into the same thread to review, comment, and work alongside the agent in real time"——把队友邀请到同一个 Thread，实时审查、评论、与 AI 并肩工作。

三端同步

官网说"Open Delta from the desktop or web, or move to a cloud runner. The conversation and code stay synchronized"——桌面客户端、Web 版本、云端 Runner，数据随时同步。

过程可见性

官网 demo 展示了 agent 的思考过程可见："Thought 2 times, ran 1 search, read 2 files"——你看到 AI 在想什么、用了什么工具、读了哪些文件。

Jump to Prompt 导航：官网 demo 里有一个实用特性——你可以从任意一段代码"跳转回"产生这段代码的原始 prompt。这个功能把代码追溯从 Git blame（只能看到提交信息）提升到了"看到完整的 AI 思考链和指令上下文"。

04五大核心机制：Delta 与传统 AI 编程工具的根本区别

如果你只看"AI 能写代码"这个维度，Delta 做的事和其他工具差不多。但 Delta 的差异在于五个系统级机制，它们共同构成了一种新的编程体验。

机制 1：Thread 锚定（Traceability）

每个代码变更都连接到产生它的对话。"The thread stays connected to every change"——这是 DeltaDB 的核心承诺。当你不理解某段代码为什么长成这样，可以直接回到那个 Thread 看原始指令和 AI 的思考过程。

机制 2：多人实时协作（Multiplayer）

官网描述："Invite teammates into the same thread to review, comment, and work alongside the agent in real time"——队友加入同一个 Thread，实时评论和与 AI 并肩工作。代码审查和 AI 协作不再是分开的两个流程。

机制 3：过程可见性（Transparency）

官网 demo 展示了思考轨迹："Thought 2 times, ran 1 search, read 2 files"——你可以看到 AI 的思考次数、工具调用和文件读取。配合 Jump to Prompt 导航，从任意代码行跳转回产生它的 prompt。

机制 4：Checkpoint 人工审核

Agent 提出方案后暂停等待人工审核；用户可以批准、修改或重定向，Agent 根据反馈继续执行。这与 GitHub Copilot 的"直接写入"和 Claude Code 的"自行判断"都不同。

机制 5：三端同步（Cross-Device）

"Open Delta from the desktop or web, or move to a cloud runner. The conversation and code stay synchronized"——桌面客户端、Web 版本、云端 Runner 之间无缝同步。可以在本地桌面启动任务，在云端 Runner 继续运行。

对比提示：这五个机制里，大多数传统工具只实现了"机制 3"（过程可见，通过 tool use logs）。机制 1（Thread 锚定）和机制 2（多人协作）是 Delta 真正独特的地方，也是它区别于"AI 增强版编辑器"的核心。

06初学者上手路线：从零到熟练的三日计划

Delta 对有经验的开发者来说学习曲线不陡，但对完全的新手来说，它的"线程 + 对话"模型需要一点思维转换。以下是一个三日上手计划，帮助你从传统 IDE 的习惯平稳过渡到 Delta 的工作流。

Day 1下载安装 · 创建第一个 Thread · 问一个简单问题
Day 2发起第一个真实任务 · 体验 Checkpoint 审核流程
Day 3多人协作：邀请队友 · 使用 Cloud Runner
Week 2自定义 Skill · 分析项目历史 Thread
第一天：安装与环境

从 delta.ai 或 npm（npm install -g delta-ide）安装 Delta 桌面客户端。首次启动时，Delta 会引导你连接一个云端账户（或使用本地模式）。关键认知：Delta 不是"装了插件的 VS Code"，而是一个独立的 IDE。它的界面里有 Thread 面板、Agent 输出面板和代码编辑器三栏布局。

第二天：真实任务体验

选一个小但真实的任务——比如"帮我把这个函数的错误处理改得更清晰"，或者"给这个模块加单元测试"。发出指令后，观察 Delta Agent 的思考过程（"Thought N times, ran N searches"），在 Checkpoint 审核它的计划，决定批准还是修改。关键认知：不要把 Delta 当搜索引擎用——它的价值在于多轮迭代和代码变更的持久记录。

第三天：协作与扩展

邀请一个队友加入你的 Thread，尝试一起审核 AI 的方案。也可以体验 Cloud Runner——当你的本地机器性能不足时，把任务迁移到云端 Runner 继续运行。关键认知：Delta 的协作不只是"分享屏幕"，而是真正的多人 Thread——每个人都可以与同一个 Agent 实时交互，评论锚定在代码行。

进阶：自定义 Skill

Delta 有 Marketplace，里面有社区贡献的预制 Skills（类似 VS Code 插件但面向 AI Agent）。你也可以编写自定义 Skill——Skill 本质上是一段指令，告诉 Delta Agent 在什么场景下用什么方式处理什么任务。注意：Skill 可以执行任意代码，来源必须可信。

常见误区：把 Delta 当"更聪明的 Copilot"用，只问单次问题然后关闭。这种用法浪费了 Delta 的核心价值——多轮迭代、上下文保持和对话-代码追踪。建议至少在一个真实项目里完成一个完整的多轮任务，才能体会到 Delta 的差异。

07典型使用场景：什么时候用 Delta 最合适
大型重构任务

需要跨多文件、跨多层依赖的修改，Delta 有完整项目上下文，不需要每次手动说明背景。多轮重构的每一步都记录在 Thread 里，随时可以回退或审查。

新成员 onboarding

把项目交给 Delta，新成员通过与 Agent 问答理解架构和逻辑。Delta 的回答带真实项目上下文，而不是泛泛的"一般做法"。可以回溯任何一段代码的来历。

自动化测试生成

Delta Agent 理解代码后生成测试用例，在 Checkpoint 人工确认覆盖范围。测试失败时，Delta 可以根据错误信息直接在 Thread 里讨论并修复。

文档自动维护

代码变更后 Delta Agent 自动更新 README、API 文档和 Changelog，保持文档与实现同步。文档的每个变更同样锚定在原始 Thread 里，可追溯。

代码审查辅助

Delta Agent 预审 PR，标注潜在问题、重构建议和安全风险。审查者聚焦业务逻辑判断，技术细节交给 Agent 预检。多人协作让审查过程更透明。

AI Agent 工具

作为其他 AI Agent 的工具，提供持久态项目理解和代码执行能力。DeltaDB 的跨 Agent 状态共享意味着一个 Agent 学会的东西可以惠及整个团队。

什么时候 Delta 优势不明显？简单的单次补全、快速语法查询、即时 bug 修复——这些场景用 Copilot/Cursor 的补全功能更高效。Delta 的价值在中等以上复杂度的、需要多轮迭代的、需要上下文保持的任务上最为显著。

08深入 DeltaDB：为什么"对话 + 工作树"需要新的数据库

DeltaDB 是理解 Delta 整个系统的钥匙。传统 IDE 没有"对话记录"这个概念，Git 只记录代码变更，Slack/Discord 的对话和代码是完全割裂的。DeltaDB 的创新在于：它把这两者统一存储在同一个数据空间里。

从技术角度推测（官网未公开实现细节 ❓），DeltaDB 需要解决几个非平凡的问题：

问题一：一致性。对话（自然语言文本）和代码（结构化文本）的数据模型完全不同。DeltaDB 需要一个能够同时存储和索引这两种数据的统一索引结构。从官网"shared, replicated space"和"multiplayer"描述推测，底层可能采用了 CRDT（Conflict-free Replicated Data Types，无冲突复制数据类型）——这是现代协作工具（如 Figma、Notion）常用的技术，用于支持多人实时编辑而不产生冲突。

问题二：可追溯性。DeltaDB 必须能够回答"这段代码是由哪个 prompt 产生的"这个问题。这需要为每个代码变更维护一个"来源图谱"（provenance graph），记录代码块和对话片段之间的引用关系。这个图谱是 Jump to Prompt 功能的基础。

问题三：性能。大型项目的 Thread 历史可能非常长（数百个 turn 的对话、数千个文件变更）。DeltaDB 需要高效的存储和查询策略，避免随着项目增长而性能退化。官网 demo 中展示的"uncommitted 状态"（Uncommitted +6−4）说明 DeltaDB 也在维护工作区状态——类似于 Git 的 staging area，但与对话上下文绑定。

问题四：隔离与共享。Delta 既支持单人使用（本地数据优先），也支持多人协作（数据在参与者之间复制）。这要求 DeltaDB 在"隔离"和"共享"之间找到灵活的边界——本地优先意味着默认数据不离开你的设备，但当你邀请队友时，数据按需同步。

Delta 的愿景不只是做一个"AI IDE"，而是重新定义软件开发中"人"和"工具"的关系——从"人指挥工具"到"人在线程中与工具协作"。 — 基于 delta.dev 官网信息整理（具体措辞以官网为准 ❓）
09Skill 系统：让 Delta Agent 学会"你的方式"

Delta 的 Skill 系统是它的扩展性机制。类比一下：传统 IDE 有插件系统（VS Code 插件、Zed 插件），Skill 则是"AI Agent 的插件"——但 Skill 影响的不是 IDE 的 UI，而是 AI Agent 的行为模式。

举例来说：一个"测试工程师 Skill"可能包含这样的指令："当你收到重构任务时，自动生成相应的测试用例，覆盖率目标不低于 80%。"当你在项目里安装了这个 Skill，Delta Agent 在处理任何重构任务时都会自动带上这条规则。

Skill 的来源有两种：

① Marketplace 技能：Delta 官方和社区贡献的预制 Skills，涵盖测试、安全审查、文档生成等常见场景。

② 自定义技能：你可以在项目里编写自己的 Skill 脚本（推测是 YAML 或 Markdown 格式的指令集），告诉 Delta Agent 在你的项目里什么情况用什么方式处理。

Skill 系统的价值和风险并存：价值在于它让 Delta Agent 能够学习组织特定的工作流程和编码规范，而不需要每次手动重复说明。风险在于 Skill 可以执行任意代码（不像 UI 插件只影响界面），所以必须确保 Skill 来源可信。

Skill 的持久性

一旦安装了 Skill，Delta Agent 在这个项目里的所有后续任务都会应用这条 Skill。它不像系统提示那样每次重置，而是项目级的能力积累。

Skill 的作用域

Skill 可以是全局的（所有项目生效）或项目级的（只在一个项目里生效）。项目级 Skill 使得每个项目可以有自己独特的处理规范。

10风险与边界：Delta 的局限性，以及你需要知道的事

① 许可证：Freemium 模式，具体条款待确认
Delta 采用专有 / Freemium 模式。具体授权条款、功能限制和定价方案需要查阅官方最新文档（delta.dev）。闭源许可证意味着无法自行审计代码行为。

② 数据边界：本地优先≠数据永不离开
虽然 Delta 默认本地优先，但多人协作时数据会在参与者之间同步。确认企业部署方案的数据流路径和合规要求，特别是涉及敏感代码的场景。

③ Skill 安全：自定义 Skill 可执行任意代码⚠️
Skill 脚本不是只读的配置——它可以执行任意系统操作。安装来源不明的 Skill 相当于给 AI Agent 开了系统权限。只安装来自可信来源的 Skill。

④ 模型选择：官网未公开具体模型信息
Delta 使用针对代码理解微调的模型，但官网未公开模型名称、供应商和具体能力边界。不同模型的代码质量、推理能力和上下文窗口有差异，重要任务建议人工验证输出。

⑤ 演示数据未独立复现
官网演示案例（SumTree 41.2µs → 3.4µs，12× 加速）的数据来自官网宣传页，尚未经过独立验证。❓ 实际项目中的性能提升可能因场景不同而有显著差异。

⑥ 学习曲线：从"编辑器"到"线程"的思维转换
Delta 的工作流与传统 IDE 有根本差异，需要改变"写代码 → 召唤 AI → 得到答案"的习惯。团队采用前建议预留一定的适应时间。

11术语表：Delta 核心概念速查
DeltaDB
Delta 的核心数据库技术——一个将"对话"（自然语言指令和 AI 回复）与"工作树"（代码文件）统一存储在同一个共享、可复制空间的数据库。它是 Delta 实现"每段代码都可追溯到原始 prompt"的技术基础。
Thread（线程）
Delta 中的基本工作单元。每个 Thread 包含一个完整的任务上下文：发起指令、AI 思考过程、工具调用记录、代码变更。你可以在任何时候回到一个 Thread 继续对话，它记得所有的历史。
Checkpoint（审核点）
Delta Agent 在执行计划前暂停，等待人工审核的机制。用户可以批准、修改或重定向 Agent 的方案。这个机制让 AI 的行为始终在人类监督之下。
Jump to Prompt
Delta 的导航功能——从任意一段代码可以直接跳转回产生这段代码的原始 prompt。这比 Git blame（只能看到提交信息和作者）更进一步，能看到完整的 AI 思考链。
Skill（技能）
Delta 的可扩展机制——预制或自定义的指令集，告诉 Delta Agent 在什么场景下用什么方式处理任务。Skill 安装后是项目级的，可以跨 Thread 持久保持。
Cloud Runner（云端运行器）
Delta 的云端执行环境。当本地设备性能不足或需要更强的算力时，可以把任务迁移到 Cloud Runner 继续运行，对话和代码状态全程同步。
Generation Counter（代数计数器）
Delta 演示案例中使用的缓存失效机制（SumTree 优化）。每个树节点维护一个 generation counter，结构性编辑时递增计数器（而非急切地重算所有节点的摘要），从而实现增量缓存。
Multiplayer Thread（多人线程）
Delta 的多人协作单元。多个开发者可以加入同一个 Thread，实时评论、与 AI 并肩工作。评论锚定在对话或任意代码行，feedback 随代码演化而保持关联。
SumTree
Zed 文本缓冲使用的树状数据结构，用于加速位置查找（如从行号到字符偏移的映射）。Zed 使用 SumTree 而非传统的 Rope 数据结构，以支持更高效的并行编辑。
CRDT（Conflict-free Replicated Data Types）
无冲突复制数据类型——一种允许多个副本在不同步的情况下独立修改，合并时自动解决冲突的数据结构。Figma、Notion、Linear 等协作工具的底层技术。
Worktree（工作树）
代码库的文件系统状态。DeltaDB 把 Worktree 和对话放在同一个空间，意味着你的代码变更和产生这些变更的对话有天然的双向链接。
