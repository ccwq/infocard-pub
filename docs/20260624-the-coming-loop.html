The Coming Loop：我们正在进入一个由 harness 驱动的循环时代

Armin Ronacher 不是在写“AI 会不会写代码”的老问题，而是在拆一个更具体的变化：Agent loop 之外，正在出现一个更上层的 harness loop。任务进入队列、机器接手、停止、判断是否完成、再注入下一轮——工作开始持续存在于模型说“done”之后。

核心引语

“I don’t prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops.” — Boris Cherny

这句引语把文章的中心钉得很牢：人不再只是直接和模型对话，而是越来越多地设计让模型自己循环工作的外层系统。

这篇文章在讲什么
不是反对循环，而是在问：当循环成为默认工作方式时，如何不把判断权一并交出去？
文章承认 loops 在迁移、性能探索、研究、扫描、机械转换等场景里非常强，但对长期、重要、需要人真正理解的代码，它会放大复杂度、削弱可理解性，并制造新的依赖。

01

文章主张：循环会来，而且已经来了

作者看到的不是“一个更聪明的 prompt 技巧”，而是工作方式的迁移：任务被放进队列，机器被派去尝试，harness 决定是否继续，甚至用另一个机器判断是否“完成”。

Agent loop

模型在工具调用中迭代：读文件、改文件、跑测试、再继续。它依然保留了一个“模型在做事，人类在审阅”的熟悉边界。

Harness loop

外层 harness 负责分配、继续、评判和传递任务，模型甚至可以被再包装成另一个 judge/orchestrator。人逐渐退到“发号施令”之外。

02

作者为什么不完全拥抱它

他坦白说：对自己真正关心的代码，目前并不喜欢这种工作方式。理由不是“技术上做不到”，而是“味道不对”：太防御、太复杂、太局部、太容易用更多 machinery 去掩盖不清晰的设计。

理解性

他仍然希望能解释清楚代码，而不是先让机器解释给自己听。

不变量

真正的修复应该让坏状态不可写，而不是为每个坏输入都加防御。

放大效应

若每次循环都再加一层本地防御，系统会表面更稳，实际上更难懂。

03

循环什么时候真正有用

文章并不悲观地否定 loops。相反，它认为在某些场景里，循环能把人从繁琐实验中解放出来，而且效果非常好。

1
迁移 / 转换

把已有代码从一种语言转到另一种语言，适合机械验证。

2
性能探索

机器可以并行试实验、跑 benchmark、淘汰失败路径。

3
安全扫描 / 研究

很多研究任务本质上就是探索复杂空间并汇报结果。

4
机械翻译

只要结果可被清晰验证，循环就非常适合。

04

真正令人不安的地方：我们会依赖这些机器

作者最担心的不是某一次循环做错，而是长期之后：代码本身、审查本身、判断本身，都慢慢建立在“机器会一直在”的前提上。若失去这些模型、失去预算、失去访问，我们是否还理解自己维护的系统？

依赖 1
代码由 loops 写，
也由 loops 审查，
最终也由 loops 维持生命。
依赖 2
不只是钱包依赖，
而是认知依赖。
人会逐渐离开上下文本身。
依赖 3
对话也开始变成
经由 LLM 的转述，
人和人的沟通多了一层机器。
05

他对 Pi 的态度：谨慎，但不会装作看不见

文章里最值得放进信息卡的另一条线索，是作者把 Pi 视为 harness，而不是纯 UI。未来重要的不是“模型更会聊”，而是“队列、子代理、持久会话、任务编排”这些外层系统。

任务队列

把 coding task 先排队，再分发给合适的机器。

子代理 / 持久会话

任务可跨回合持续，模型不会因为一次“done”就退出语境。

人类角色变化

人的角色从“直接写”转向“设计约束、保留判断、监督边界”。

06

作者最终想保住的是什么

不是要阻止循环，而是要在循环时代继续保留工程的可理解性、责任边界和可监督性。问题不是“会不会 loop”，而是“如何 loop 而不放弃判断”。

人类判断 可理解性 责任边界 可监督性 工程规则
TAKEAWAY
这篇文章的价值，不在于给出一个“支持/反对 loops”的简单结论，而在于把 harness loop 这层变化说清楚：它会成为默认架构，但越是这样，越要设计能让人类继续看懂、继续追责、继续监督的工具链。
