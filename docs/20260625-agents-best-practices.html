agents-best-practices：
把 Agent Harness 从“会跑”拉到“可上线”

DenisSergeevitch 的 provider-neutral Agent Skill，不教你再堆一个 Planner，而是把 attention 放回真正决定上线质量的地方：授权、验证、记录、预算、终止条件与可审计运行时。

一句话判断

这不是“Agent 最佳实践清单”，而是一套更激进的判断：模型负责提案，harness 负责验证、授权、执行、记录与回传观察。它把 AI Agent 的核心问题，从“提示词写得对不对”转回到“运行时边界设得对不对”。

它是什么

一个兼容 Codex、Claude Code 与 agentic harness 设计的 provider-neutral Skill。仓库提供安装方式、使用场景、哲学、参考资料与 workflow orchestration 指南。

它不是什么

不是新的多代理框架，不是 CLI 包装器，也不是单纯 prompt 模板。它更像一个“runtime discipline kit”，约束 Agent 何时该停、该问、该批、该记。

最重要的五个工程判断

01 / Proposal
模型先提案，不直接执行。
仓库首页的中心句已经把职责切开：模型提出动作，真正的执行权在 harness 手里。
02 / Validate
每个工具调用都必须先过 schema / permission / budget。
这意味着 tool call 不是 function call，而是一次需要验证、授权和预算检查的资源请求。
03 / Record
可观测性不是附加项，是运行时主干。
没有 event trace、终止原因和执行回放，Agent 就只是黑盒自动化。
04 / Pause
外部副作用必须可暂停、可审批、可拒绝。
尤其适合 CRM、工单、邮件、采购、法务、医疗等高副作用流程。
05 / MVP
先做最小可上线 harness，不先做“大而全 Agent 系统”。
README 里反复强调 MVP blueprint、audit、refactor、explain 四类入口，本质是在压缩系统复杂度。

它解决的不是“能力”，而是“失控”

为什么值得现在看

和 taxonomy 重构正好同一条线

你刚让我把首页从扁平 tags 升级成结构化 taxonomy，这个仓库做的是同一件事在 Agent runtime 上的版本：把“混在一起的能力描述”拆成明确的职责层。

和当前 Agent 框架争论点直接相接

它不是继续强化 Planner，而是强化 harness。和 Fable 5 那种“安全 / 授权 / 无状态优先”的工程哲学高度同频。

最值得抄的不是它的 prompt，而是它的边界感。 如果你的 Agent 系统里，还没有把“审批、预算、终止、追踪、回放”放进主路径，那你做的仍然更像 demo，不像 production runtime。

适用场景

AI 产品开发

给产品侧明确：什么该交给模型，什么必须交给 harness。

Agent 架构设计

为现有 ReAct / workflow / multi-agent 系统补 runtime discipline。

工程落地 / 审计

用于 review 现有 Agent 是否具备上线前的授权与可观测能力。

高副作用流程

邮件、CRM、support、finance、procurement、legal、healthcare 等需要审批链路的系统。
