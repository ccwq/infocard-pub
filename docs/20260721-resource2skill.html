问题动机

现有技能库的局限

现有技能库多为手工编写，以文本为中心，或从 Agent 执行轨迹中派生，教程视频等大量多模态人类资源未被充分利用。

  • 手工编写成本高、扩展慢
  • 文本中心缺少视觉/时序信号
  • Agent 轨迹数据质量不稳定
  • 多模态教程视频利用率极低
核心方案

分层多模态 Skill Wiki

每个技能词条融合多种模态信息：视频捕捉时序操作与视觉效果，代码捕获可执行工具模式，文章或制品提供概念和风格锚定。

  • 结构化文本（说明 + 步骤）
  • 可执行代码片段
  • 视觉示例与截图
  • 元数据与来源溯源

多模态输入通道
Skill Wiki 结构
├── Skill Wiki（根） ├── Domain A ├── Skill 1.1 │ struct text │ code │ visual examples │ metadata └── Skill 1.2 ├── Domain B ├── Skill 2.1 └── Skill 2.2 └── ...

分层结构：按领域（Domain）组织叶节点为技能（Skill），每个技能词条包含 5 个标准字段。

多模态信号互补：

· 视频（Video）→ 时序操作、视觉反馈
· 代码（Code）→ 可执行工具调用模式
· 文章（Article）→ 概念与风格锚定
· 制品（Artifact）→ 参考输出、约束条件

在线获取：当推理时 Wiki 覆盖不足，同一蒸馏操作器可在线获取新技能，无需重新手工编写。

适用边界
适用场景

软件 Agent 需要复用操作知识的场景：工具调用、代码生成、自动化工作流构建、跨仓库任务规划。

不适用场景

需要实时感知环境（摄像头/麦克风输入）、需要完全零样本泛化、或资源本身质量低下的场景。

⚠ 风险与局限

· 资源质量依赖：输入多模态资源本身质量直接影响蒸馏技能质量

· 模态缺失时性能退化：若某资源类型缺失，相关信号无法补全

· 在线获取延迟：覆盖不足时实时获取新技能可能引入延迟

· 论文自报指标：所有实验数据来自论文 v4，未独立复现验证

Ablation 消融结论
01

多模态技能格式本身有价值（单模态显著弱于多模态）

02

分层组织比扁平列表更有利于检索与复用

03

来源多样性（多类型资源混合输入）优于单一来源

04

选择策略（检索与排序）影响最终 Agent 表现

05

在线获取机制扩展了静态 Wiki 的覆盖边界
