什么是 slash skill？为什么不能上来就写代码？

在 Hermes Agent 里，/grilling、/wayfinder 这些都是「slash skill」——它们不是直接执行代码，而是先帮你思考、澄清问题，再决定要不要动手。

为什么要「先问再写」？因为很多任务在你没想清楚之前就动手，返工成本很高。Matt Pocock 的 Skills 仓库（281K ★）反的是 GSD/BMAD/Spec-Kit 式重型流程，主张「Skills For Real Engineers」——用最小的认知开销，找到正确的行动路径。

progressive-doc：渐进式文档，边问边澄清再行动
📊 Section 02 · 三种工作方式对比
⚡

One Shot：直接写

把任务丢给 Agent，直接出结果。不问问题，不画图，不讨论。
适合：diff 很小、方向明确、你已经知道怎么做、造错成本≈0 的场景。比如加一个日志行、改一个配置项。

🔥

Grilling：层层追问

Agent 先用 design tree + frontier 提问机制，把你的需求拆透、理清再写代码。找事实派 sub-agent 负责验证信息，决策归用户。
适合：需求模糊、方向不明、影响面大的场景。

🗺️

Wayfinder：画地图

在 issue tracker 上建 map 索引，不是存储而是索引。生成 decision tickets，核心纪律是「Plan, don't do」——先规划，不执行。
适合：任务已经中途失控、涉及多模块/多决策点、需要全局视野的场景。

⚙️ Section 03 · Grilling 机制拆解
🌲

Design Tree + Frontier 轮次提问

Grilling 用「design tree」来结构化问题空间：每轮问一个核心问题，同时提供推荐选项，用户回答后继续深挖（frontier 边界）。每轮只问一件事，问完不写代码，直到用户确认方向正确。

🔍

Sub-agent 分工：找事实 + 做决策

Grilling 里有一个「找事实派 sub-agent」负责信息验证和背景收集，决策始终归用户。Agent 不替用户做决定，只确保用户在做决定时有足够的信息。

⏱️

轮次上限 & 共识纪律

Grilling 遵守轮次上限：到了上限还没达成共识，就停下来记录分歧，不无限追问。共识达成之前不写代码——这是它的核心纪律。

🔗 Section 04 · Grill-with-Docs 组合层
🧩

Wrapper Skill：组合优于单兵

/grill-with-docs 不是独立实现，而是一个 wrapper skill——它组合了 /grilling（追问机制）和 /domain-modeling（领域建模）两个底层 skill。

Wrapper 的价值在于：追问 + 建模型，两件事同时发生，信息不丢失、上下文不断层。

📐

Domain Modeling 是什么

领域建模 skill 负责在追问过程中建立和维护项目的领域模型——把用户描述的模糊需求，翻译成结构化的实体、关系和约束。

  • 追问过程中信息分散在对话里，容易丢失
  • wrapper 把「问」和「建模」同步进行
  • 问完就有模型，模型指导下一步写代码
🗺️ Section 05 · Wayfinder 机制拆解
📋

Issue Tracker Map：索引而非存储

Wayfinder 在 issue tracker 上建 map 索引——它不把信息存在某个地方，而是维护一个索引，告诉你信息在哪里可以找到。这避免了信息孤岛，让全局视图始终可追踪。

📌

Decision Tickets：「Plan, don't do」

Wayfinder 的核心产出是 decision tickets——每个 ticket 代表一个需要决策的问题点。核心纪律是：先规划，不执行。不是不能执行，而是先把决策点显式化，再按优先级推进。

🚫

为什么不能从 Wayfinder 起步

Matt 的规则 2 明确说：永远别从 wayfinder 起步。如果任务还没开始就画地图，你会陷入「规划瘫痪」——地图越画越大，行动却停在原点。Wayfinder 是失控时的救援工具，不是起点。

⚖️ Section 06 · 三条决策规则逐条讲解
📏

规则 1：diff 小就别 grill

造错成本≈0 时，直接写。Grilling 是有认知开销的——你要回答问题、确认方向。如果任务只是「加一行日志」或「改个配置值」，grill 的成本比写错还高。

反例场景：你想让 Agent 把某个函数的超时从 30s 改成 60s。这件事你很清楚，diff 极小，直接说就行。等你 grill 完，Agent 还没动笔，你已经花了 5 分钟在问答上。

🚫

规则 2：永远别从 wayfinder 起步

Wayfinder 是「中途失控」时的救援工具，不是起点。如果你还没开始就画地图，你会发现地图越画越大，行动却停在原点——「规划瘫痪」。

反例场景：你接到一个「重构用户模块」的任务，还没想清楚要改什么，就先开了 wayfinder 建了一堆 decision tickets。结果 2 小时后你还在画地图，代码一行没动。

⬆️

规则 3：渐进升级

任务进行中如果发现失控——方向不清楚、多处冲突、越改越乱——就说「/wayfinder let's turn this into a map」，把已有对话转成 map，把决策点显式化，然后从 map 重新出发。

反例场景：你已经在 /grilling 里追问了 3 轮，突然发现这个问题涉及 5 个模块的依赖关系。硬着头皮继续追问，但每个答案都引发新问题——这时应该主动升级，而不是继续在 grilling 里打转。

核心心法

「Plan, don't do」是 wayfinder 的纪律；「共识前不写代码」是 grilling 的纪律；「直接执行」是 one shot 的纪律。三种纪律对应三种状态——失控了就升级，清楚了就执行，不要在错误层级硬撑。

🚀 Section 07 · 初学者上手路线（今天就能试）

1
从 one shot 开始，测试最小改动
遇到任何任务，先评估 diff 大小。如果改动只有几行、方向明确，直接说「/[task]」让 Agent 执行。观察返回结果，如果方向错了就撤销重来——这一步的成本几乎为零。
2
遇到模糊需求，启动 /grilling
当你不确定「这个功能到底要做什么」或「改了会不会影响其他模块」时，调用 /grilling 或 /grill-with-docs。回答 Agent 的追问（每次只答一个），直到方向确认。注意：共识前不写代码，这是纪律不是建议。
3
失控时，触发升级：say 「/wayfinder let's turn this into a map」
如果 grilling 过程中发现涉及 3 个以上模块、依赖关系复杂、越问越乱——主动升级。把已有对话和决策点转成 wayfinder map，生成 decision tickets，从「规划」重新出发。
