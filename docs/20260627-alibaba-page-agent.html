一行代码集成
// npm 安装 npm install @alibaba/page-agent // ESM / CDN 引入（最简） import { PageAgent } from '@alibaba/page-agent'; const agent = new PageAgent({ model: 'gpt-4', apiKey: 'your-api-key' }); agent.run('帮我填写这个表单');
零后端。零运维。 只需在前端页面引入 SDK，配置模型 API Key，立即可用。
解决的问题

传统自动化方案的痛点：

• Playwright / Puppeteer / Selenium：跑独立进程，搭后端服务，运维成本高

• screenshot-based AI：把网页截图发给视觉模型，精度低、费用高、速度慢

Page-Agent 的思路：

直接读取页面的 DOM 树，把结构化 DOM 文本发给大模型。大模型输出操作指令，SDK 执行点击、填值等行为。全程在浏览器内，不依赖后端。

本质区别：基于 DOM 而非截图。精确、安全、可控、省钱。
01
两种接入形态
按使用场景选，不是一套方案走天下。
形态 A：Side Panel（侧边栏）

浏览器扩展，用户打开任意网页后从侧边栏呼出 AI 操控面板。适合：最终用户直接使用，不需要开发者集成。

特点：

• Chrome 扩展，零侵入

• 支持任何网页，无需目标网站配合

• 模型 API Key 由用户自行配置

• 适合企业内部工具、个人效率工具

形态 B：SDK 嵌入（npm）

通过 npm 包 `@alibaba/page-agent` 嵌入自有产品。适合：SaaS 开发者把 AI 操控能力作为产品功能交付。

特点：

• 一行 import，即时生效

• 可自定义模型服务商和 Key

• 可深度定制提示词和行为逻辑

• 面向产品用户，不是面向开发者

选型判断：如果用户是"个人要提升效率" → Side Panel 扩展。如果你是"产品要把 AI 能力包装成功能" → SDK 嵌入。
02
核心技术差异：DOM vs 截图
这是 Page-Agent 和市面上大多数 AI 浏览器工具的本质区别。
维度 Page-Agent（DOM 方式） 传统 screenshot-based 方案
精确度 直接读取 DOM 结构，知道每个元素的真实属性和文本，不会误判 靠视觉模型识别截图，准确率依赖模型 vision 能力，容易被相似按钮误导
费用 只传 DOM 文本 Token，费用低 每帧截图占大量 Token，视觉模型调用成本远高于文本
速度 纯文本传输，响应快 截图生成 + 视觉模型推理，延迟高
安全性 SDK 运行在浏览器沙箱内，不访问目标网站后台，只读 DOM 截图方案有时需要把页面截图发到第三方 API，存在隐私风险
动态内容 DOM 实时反映页面当前状态，包括动态渲染内容 截图有时差，动态内容可能出现"看到的是旧状态"

基于 browser-use 的工程优势
站在开源巨人肩膀上，工程质量有保证。
DOM 处理组件

页面 DOM 解析、可交互元素识别、元素去噪（去掉装饰性节点，保留功能性节点）均由 browser-use 成熟模块处理，坑已被前人踩过。

提示词工程

模型指令 → 页面操作映射的提示词模板经过社区大量迭代，覆盖点击、输入、滚动、下拉、提交等常见操作，不需自己从头设计。
