01 / 核查结论（v1 保留）

✓ 可证实："朴素文件方案打平甚至胜过专用记忆系统"有多个独立来源背书——Letta 官方实验：纯文件存储 + search_files 工具，在 LoCoMo 拿 74.0%，显著超过 Mem0 自报的图谱变体 68.5%；memento-memory 三方对比：Markdown 80.8% > 向量库 79.8%（多会话与时间推理两项 md 全面占优）。
⚠ 未溯源：文章标题级数字——"1800+ 真实任务、12 个系统、纯 MD 与 Cognee 并列 97.1 分、响应快 5 倍、60% 翻车因过度切片、3 个系统要求遗忘后数据泄漏"——五轮检索（中英文 + GitHub + arXiv + 官方文档）均未找到原始基准出处。97.1 恰是 LongMemEval 单会话-user 类目的常见分数段（memento 的 md 臂在该类目拿 94.3%，其图谱方案拿 97.1%），"1800"与 Mem0 论文的 tokens/对话数撞车，疑似转述时数字混装。引用前请当"未核实转述"处理。

03 / "复杂工具反而翻车"的三个实锤机制

机制一 · 过度切片

写入时切碎，召回时失忆

文章说"六成翻车源于过度切片"。可验证的对应事实：Mem0 写入按 LLM 抽取事实分片存储；MemoryAgentBench 论文实测 Cognee 在准确检索类目仅 22.8 分（满分 100），并专门设了 FactConsolidation 数据集测"选择性遗忘"。切片粒度确实是结构化系统的真实失败面。

机制二 · 写入即滤除

"关键名词当噪音"有同款案例

Reddit 那位"排查大半天"的用户无法溯源，但机制成立：所有抽取式记忆（Mem0/LangMem）都要先过一道"什么值得记"的 LLM 判断——memento 实测显示 LLM 蒸馏偏向用户侧陈述，助理侧问题丢了约 60%（41.1%）。抽错在写入那一刻就发生了，日志里什么都没有。

机制三 · 遗忘即泄漏：文章称"3 个系统要求遗忘后数据泄漏"。直接证据未找到，但有旁证：MemoryAgentBench 的 SF（selective forgetting）类目里，Cognee 得分 2.3/100、Mem0 2.0、Zep 3.0、MemGPT 3.0——"要求忘掉"和"真的删干净"在主流结构化系统里几乎不成立（满分 100 个个考个位数）。删不干净的普遍性，比"3 个系统"这个精确数字更值得警惕。反差样本：HippoRAG-v2 在同表 SF 拿 5.0 依然不及格，但全类目均分 41.6 是全场最高——遗忘是全行业未解难题，不是某家 bug。

3.1 Letta 给出的机制解释（为什么简单工具反而强）

Letta 在实验后给了一段值得每个初学者记住的分析：今天的 Agent 是在海量代码任务上后训练出来的，文件系统操作（grep/读文件/写文件）恰恰是它们最熟的工具；而专用记忆 API 在训练数据里罕见，Agent 反而不会用。实验里 Agent 还会自发把问题改写成更好的检索词（"Calvin 受挫时怎么保持动力" → 搜"Calvin motivation setbacks"）并多轮迭代搜索直到找到答案——这些行为专用记忆工具的固定接口给不了。结论一句话："记不记得住"取决于 Agent 会不会用工具，多于取决于存储机制本身。补充一条硬背景：Mem0 曾声称在 LoCoMo 上跑分了 MemGPT，Letta（MemGPT 原班人马）公开表示无法找到合理方式把 LoCoMo 数据回灌进 MemGPT/Letta，向 Mem0 索要复现细节未获回应——评测乱象可见一斑。

04 / 纯 MD 为什么能打：四个工程理由 + 成本账

理由机制证据
零写入损耗没有"什么值得记"的预判，原文全量保真，抽错的入口不存在Letta 实验：不做任何抽取直接存文件
检索够用现代模型 + BM25/grep 级检索，长上下文窗口内自读自答Letta 74.0% 仅用 2 个工具；OpenDB FTS5 实测中位召回延迟 1.1ms、p95 2.1ms（R@1–R@10 全 100%）
人类可审计记错了直接打开文件改，git diff 可追溯，错了能修文章核心卖点，与 CLAUDE.md/AGENTS.md 实践完全同构
成本近零无向量化 API、无图谱构建 LLM 调用、无数据库运维OpenDB 报告：FTS 查询零 API 成本；向量方案每查询付 embedding 费 + Agent 额外 read_file 补偿调用

4.1 一笔具体的 token 账（OpenDB FileDB vs 命令行 Agent 实测）

OpenDB 的 FileDB 实验（4 模型 × 6 任务 × 3 跑，25 份企业文档）：文件式记忆 vs 让 Agent 用命令行自己翻文件，token 节省 55%–73%（deepseek 71%、minimax 73%、kimi 55%），任务完成率 23/24 vs 19/24——命令行 Agent 失败方式很典型：陷入抽取循环，写 Python 脚本解析二进制文件直到烧光轮次。这就是"用文件组织记忆"比"让 Agent 现场摸索"省钱的直接证据。

但纯 MD 有边界：memento 数据里它单会话-assistant 类目崩到 41.1%（蒸馏丢助理侧事实）；MemoryAgentBench 显示长史档（115K-1.44M tokens）下结构化方法在事实更新类占优（Zep substring-EM 44%）。语料小、单人用、可全量读 → 纯 MD；跨会话综合、事实频繁更新、多实体关系 → 该上结构。另外 FTS 也有软肋：OpenDB 自曝纯 FTS 的盲区是换说法检索——问题里不含代码库原词时 R@5 从 100% 掉到 79.2%，它后来加了 opt-in 混合检索补这个洞（诚实披露，值得加一分）。

4.2 三种"朴素路线"的细分（别把"纯 MD"当成一种东西）

路线怎么工作实测表现适合谁
全量原文 + Agent 自检索（Letta Filesystem 式）对话原样进文件，Agent 用 grep/搜索多轮自取，零抽取LoCoMo 74.0%（gpt-4o-mini）；无写入损耗，靠模型自己消化长文有强模型 + 会话可回放的 Agent 用户
蒸馏要点 + 单文件（CLAUDE.md/mem0 式，memento 的 md 臂）每会话 LLM 蒸馏成要点追加进一个 md，查询时全文件截断进上下文LME 总分 80.8%；偏好 100%、知识更新 88.5%，但助理侧 41.1%大部分人：文件小、人可直接维护
FTS 检索 + 时间衰减（OpenDB 式）md/文档进 SQLite 全文索引，查询零 API 成本，旧记忆按时间降权召回 R@1–10 全 100%、中位 1.1ms；E2E 93.6%（换说法检索是盲区 79.2%）记忆量涨到"Agent 读不全"的阶段

选择线索：三者是递进关系而非竞争关系——从蒸馏单文件起步，记忆变多加 FTS 索引，只有"原文保真 vs 上下文预算"不可兼得时才需要考虑图谱（memento 用 verbatim fallback 两手抓：图谱之外永远存一份原文）。文章笼统说"纯 MD 最强"，实际是这条递进路线的每一步都打平了同期的复杂方案。

05 / 初学者十步：从零到可用的 MD 记忆库

以下每一步都可以今天做完，不需要任何数据库和 API key。以 Claude Code / Codex / Cursor 等支持工作区文件的 Agent 为例：

  1. 建目录：在你的项目根（或 home）下建 memory/ 目录。就四个文件起步，别贪多：profile.md、preferences.md、projects/、lessons.md。
  2. 写第一行：在 profile.md 写三行——你是谁、常用技术栈、绝对偏好（如"回复用中文""代码注释要英文"）。不用一次写全，缺什么补什么。
  3. 接进 Agent：在 CLAUDE.md（或 AGENTS.md）加一句：回答前先读 memory/ 下与问题相关的文件；对话中出现新的稳定事实（身份/偏好/项目约定/教训）时，写入对应文件并带日期前缀。
  4. 设定写入纪律（见 06 模板）：日期前缀、改原文不追加、单文件 200 行拆分——三条从第一天就执行，比事后清理便宜十倍。
  5. git 化：memory/ 纳入 git（私有仓库或本地裸仓库都行）。价值：任何一次错误写入都可以 git diff 定位、git revert 回滚——这是记忆库独有的"时光机"，专用系统基本给不了。
  6. 跑一周再复盘：用满一周后人工读一遍全部文件。删过期条目（带日期前缀就是为这一刻）、合并重复、把"当时觉得重要其实没用"的直接删掉。记忆库的敌人不是遗漏而是噪音。
  7. 观察两个失败信号：① Agent 明明该记得却没记得（翻文件发现条目在——是检索/上下文预算问题）；② 条目本身错了或丢了（是写入纪律问题）。两种病的药方不同，别混。
  8. 文件大了就加索引：单文件超 200 行拆成主题文件（如 projects/app-x.md、lessons/deployment.md），并在目录下放一个 index.md 列出每个文件管什么——这就是 Claude Code 自动记忆的同款架构（见 07）。
  9. 需要跨会话自动综合时再引入工具：装 OpenDB（pip install open-db[cli] && opendb index ./memory && opendb serve-mcp，3 行命令得到 12 个 MCP 工具 + 1.1ms FTS 召回）——它读的仍然是你的 md，只是给 Agent 配了搜索引擎。
  10. 只有当"多实体关系+时间线+频繁改事实"成为日常痛点时，才评估图谱方案（memento/Mem0/Zep/Cognee），并用 02 节的口径表对号入座（见 08）。
为什么这个顺序是对的：每一步都在给下一步留退路。md 阶段的积累（干净的分类、日期前缀、教训库）在升级到 FTS 或图谱时全部可以复用——OpenDB 的 verbatim fallback 和 memento 的 verbatim 层本质都是"图谱之外再存一份原文"，你手写的 md 就是那份原文。

6.1 写入质量的三条红线（新手最常踩）

红线一：记"结论"不记"过程"。"调试了三小时才发现是端口被占"不是记忆；"这台机器 4204 端口有僵尸进程，起服务前先 ss -tlnp 查占用"才是。过程留在会话记录里，结论才进记忆库。

红线二：能合并就合并。五条"用户喜欢 X"的分次记录是噪音，一条"用户偏好：X、Y、Z（2026-09 更新）"是记忆。memento 的 consolidation 引擎（衰减+去重+孤儿清理）在文件世界里就是你每周十分钟的手工维护。

红线三：可疑的宁可不记。记忆库一旦混入错误事实，它会被反复检索出来强化——比没有记忆更糟。拿不准的信息先放 inbox.md，验证后再转正（memento 的 confidence decay 机制的人工版）。

07 / 不想自己维护？Claude Code 自动记忆就是"官方版纯 MD"

如果你是 Claude Code 用户，其实已经有一个开箱即用的 md 记忆系统，官方文档确认的机制如下——它的设计恰好印证了本文全部论点：

机制官方行为对应的设计智慧
双层结构CLAUDE.md/AGENTS.md（你写的指令）+ auto memory（Claude 自己记的笔记）人机分工：规则归人，事实归 Agent
MEMORY.md 预算每次会话加载前 200 行或 25KB，超出部分不加载；超限时写入仍成功但提示重写索引硬预算逼出简洁——印证 06 节"200 行拆分"纪律
主题文件细节自动移入 user_role.md、feedback_testing.md 等主题文件，启动不加载、按需用文件工具读索引+分片，正是 05 步骤 8 的官方实现
人可审计/memory 随时查看，全部是纯 markdown，可读可改可删；排除在会话记录清理之外"看得见摸得着"的文章卖点，官方背书
边界明示指令是"上下文"不是"强制配置"；要硬拦某操作得用 PreToolUse hook文件记忆的天花板：影响概率，不保证执行

实操建议：Claude Code 用户可以不建 memory/ 目录，直接用 /memory 检查自动记忆都存了什么、把错误条目手动修掉——这本身就是文章说的"AI 记错事实，人类直接打开文件删改"。文件超 200 行会让遵循度下降（官方原话），超 4MiB 直接跳过加载。

09 / 何时升级：一张决策表

memory/ 总量 < 200KB 且 Agent 答得上健康状态什么都不用做，纯 MD 就是终点
Agent 说"没有相关记忆"但你确定写过检索失败（文件多到读不全）先加 index.md + 拆主题文件；还不够 → OpenDB FTS
同一条事实反复改（>每周一次）时效性成为一等公民升级双时序方案（memento）——md 的时间戳只够人看，不够机器推理
回答要同时用到 5+ 个文件的事实需要跨文件综合推理图谱方案（memento/Zep），md + FTS 的"拼片段"模式开始漏
多项目/多人共享记忆写冲突 + 权限需求md + git 依然可行（分支+review），但审计成本上升；考虑自托管 Mem0 server
合规要求"删除=真删除"任何抽取式系统都不合格回到 md + git（revert 可全史删除）或选带 hard-delete 的方案——memento 明示有 Privacy Layer（export/audit/hard delete）

10 / 运维与排障（用起来之后）

症状 · 记忆"越记越笨"

八成是噪音堆积

条目相互矛盾（新旧版本并存）、过期事实没删、过程日志混进结论。处方：每周 10 分钟走一遍 05 步骤 6；矛盾条目当场合并。memento 用 confidence decay 自动做这件事，文件世界靠人肉。

症状 · Agent 不主动读记忆

指令太软或入口太深

CLAUDE.md 里的那句要具体到"什么时候读什么文件"；index.md 保持一行一文件。官方文档明确：指令越具体越简短，遵循度越高；文件超 200 行遵循度下降。

10.1 三条运维纪律

纪律一：记忆库进 git 但别进公共仓库。记忆天然含个人/项目敏感信息，与密钥同级对待——要么私有仓库，要么本地裸仓库；不含任何 API key 的前提下才考虑任何远端。

纪律二：改了记忆文件要重开会话。多数 Agent 在会话开始时加载记忆（MEMORY.md 的 200 行预算也是会话开始时结算），会话中途改文件对当前会话无效——改完记得重开，别误判"改了没用"。

纪律三：升级/迁移前先导出。memento 提供隐私层导出（export/audit/hard delete），Claude Code 的 auto memory 就是磁盘上的 md 直接拷走。任何时候你的记忆都应该是"离开任何工具也能活着"的一堆文本文件——这是判断某记忆方案是否值得托付的终极标准：它能不能一键变成你的 md？

12.1 常见追问（FAQ）

Q1：直接用 Claude Code 的 auto memory 不就完了，为什么还要自己建 memory/？
两者不冲突。auto memory 记的是"Claude 观察到的你的习惯"，粒度偏操作层（怎么改代码、什么别碰）；自己的 memory/ 记的是你主动交代的长期事实（身份/项目背景/业务约定）。要硬绑定团队规范或敏感偏好，写 CLAUDE.md；要跨项目跟人走的习惯，auto memory 已覆盖。

Q2：Codex CLI / Cursor / 没有记忆功能的 Agent 怎么办？
同一套 memory/ 照样能用：Codex 读 AGENTS.md，Cursor 有 .cursorrules（或在对话里粘贴）。文件方案的兼容性正是它的核心优势——同一位"记忆"可以同时供给所有 Agent，谁都能读 md。

Q3：记忆库要不要让 Agent 自动写？
要，但要限定"写哪里+什么格式"。全自动无纪律会复刻 Mem0 的写入滤除问题（03 机制二）；全手写撑不过一周。折中：CLAUDE.md 里写明"只允许写 projects/ 和 lessons.md，其他文件只读"，每周人工审一次 diff。

Q4： 多设备/多机怎么同步？
git 私有仓库 push/pull 即可；或用 Syncthing/iCloud 同步 memory/ 目录。避免数据库方案的原因：同步冲突在 md + git 里是一次 merge，在专有数据库里是一场事故。

Q5：这套东西和 RAG 什么关系？
RAG 是"检索外部文档回答问题"的技术，记忆库是"Agent 的长期状态"。你的 memory/ 长大后接 OpenDB（FTS）其实就是给自己建了一个极小的私人 RAG——只是语料全是你亲自核过的事实，没有网页噪音。02 节向量库的短板（多会话 67.7%）提醒：别拿通用 RAG 工具直接当记忆库用，检索质量再高也补不了"没有时间线结构"的缺口。
