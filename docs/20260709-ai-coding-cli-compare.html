04 核心差异深度解析

🎯 模型哲学：封闭 vs 开放

Claude Code + Codex CLI 代表"模型即产品"路线：工具与模型深度绑定，追求模型能力最大化的端到端体验。Claude Code依赖Claude 4系列，Codex CLI依赖o3/o4-mini，各自发挥最强推理能力。

OpenCode + oh-my-pi 代表"模型即服务"路线：工具是平台，模型是可替换组件。OpenCode支持75+路由，oh-my-pi内置多模型resolver，用户可随时切换供应商，避免锁定。

关键取舍：封闭路线 = 更深度优化；开放路线 = 更多自由但需自行调优。

📋 许可证：专有 vs 开源

Claude Code（专有）：闭源商业产品，Anthropic控制更新节奏，适合企业合规场景。

Codex CLI（MIT）：2025-04完全开源，GitHub完全开放，开发者可fork魔改。

OpenCode（AGPL-3.0）：AGPL传染性强，商业使用需注意开源暴露；核心价值在于模型路由架构。

oh-my-pi（AGPL-3.0）：同上，但项目更小众，社区治理为主。

企业选型建议：先确认AGPL合规成本，再决定OpenCode/oh-my-pi是否可用。

🖥️ TUI体验：谁最懂终端？

Claude Code（Ink TUI）：Anthropic自研Ink框架，彩色输出、进度条、文件diff展示。强调"不要让我看到终端以外的地方"，对工程化场景优化。

Codex CLI（原生终端）：最小化TUI，o3/o4-mini推理过程输出清晰，适合观察模型思考链路。

OpenCode（Neovim风格）：terminal.shop团队打造，继承了Neovim的终端美学，键盘导航原生感强，适合Vim用户。

oh-my-pi（自研UI）：以Pi极简哲学为基础，但omp分支增加了更多内置视图，信息密度高。

🔧 深度功能：工具链完整性

LSP支持：oh-my-pi 内置自动加载，OpenCode 内置，Claude Code和Codex需配置。

Debugger：oh-my-pi 内置完整调试器，Claude Code 需通过MCP配置，其余暂无。

子代理编排：oh-my-pi 多级嵌套，Claude Code 插件系统支持，OpenCode 插件生态，Codex 基础并行。

MCP生态：Claude Code官方SDK最强；OpenCode和oh-my-pi通过插件/内置支持；Codex基础支持。

选型结论

2026年终端AI编程Agent生态已形成清晰分层：Claude Code代表"官方深度集成"路线，Codex CLI代表"开源+强推理"路线，OpenCode代表"全开源自由路由"路线，oh-my-pi代表"终端极客内置全家桶"路线。

没有绝对最优解，只有场景最优匹配：已有Claude Pro优先Claude Code；追求最强推理+截图优先Codex CLI；多模型切换+免费优先OpenCode；终端极客+内置全家桶优先oh-my-pi。

关键趋势：开源工具正在快速追赶商业产品差距，模型绑定壁垒正在被OpenCode/oh-my-pi的路由架构打破。
