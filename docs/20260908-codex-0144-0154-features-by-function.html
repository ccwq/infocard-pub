关键判断

升级重点已经从“模型回答更强”转向“工作如何被组织”：任务、上下文、插件、MCP、远程 runtime 和预算正在形成统一控制面。但可见性与控制能力增强，不等于 Agent 槽位泄漏、孤儿 Agent、级联关闭和 join-subtree 已经彻底解决。

0.154 边界：截至 2026-09-08，仅见 0.154.0 Alpha。Context Management 延伸、voice host/runtime、MCP event stream 生命周期、Agent command center、Realtime history、plugin reconciliation、嵌套 tracing 应标为“开发方向”，不能写成稳定版已交付能力。

第三章：重点新特性使用 Cheatsheet

WINDOWS · GIT BASH · CODEX CLI
先做能力探测：Git Bash 与 PowerShell 都先运行 codex --version、codex --help；TUI 输入 / 查看当前真正可用的命令。若通过 npx 启动，把下文每个 codex 替换成 npx -y @openai/codex@latest。状态分级：稳定可用＝官方命令参考已收录；条件可用＝依赖版本/市场/账号；实验性＝默认关闭；Alpha 观察＝不要用于关键流程。
01 · 稳定可用 · MULTI-AGENT

/agent：查看与切换 Agent

功能：在主线程与并行 Agent 线程之间切换；multi-agent 默认稳定启用。场景：你让多个 Agent 分别调查、测试、审查，现在需要确认谁完成、谁卡住。

前置
进入 Codex TUI；当前任务确实启动过子 Agent。
最简 SOP
①输入 /agent；②查看线程与状态；③切到目标 Agent 阅读结果；④回主线程汇总；⑤不再需要的 Agent 明确停止/关闭。
成功信号
界面显示多个 Agent，可切换并看到各自独立记录。
排错
没有 /agent：升级 CLI；没有子线程：尚未生成 Agent；显示 Done 但仍报上限：按 runtime 槽位问题处理，不能只信 UI。
codex --version
codex
# 进入 TUI 后：/agent
# 临时显式启用：codex --enable multi_agent

一行速查：先 /agent 看状态，再决定复用、等待或关闭；不要盲目继续创建。

02 · 条件可用 · TASK ROUTING

@任务、队列与正在运行的 Turn

功能：把补充指令送入已有工作流。官方稳定行为是：任务运行时输入 slash command 后按 Tab，可排到下一轮；App Server 用 turn/steer 给正在运行的 turn 追加输入。场景：测试 Agent 正在执行，你发现还应覆盖 Windows 路径。

最简 SOP
①确认目标 Agent/线程；②在 TUI 用 /agent 切换；③输入补充要求；④若是 slash command，按 Tab 排队；⑤等待当前 turn 结束后检查下一轮是否执行。
成功信号
补充要求出现在正确线程，不新建重复 Agent。
排错
本机若存在 codex queue 或 @任务选择器，以 --help/界面为准；不存在就使用 /agent 切换后发送，不能照抄未收录命令。
# 官方稳定入口
/agent
# 任务运行时：输入 slash command 后按 Tab
# 能力探测
codex --help

一行速查：先定位线程，再追加消息；“能引用任务”不代表跨 Provider 的历史一定可见。

03 · 稳定可用 · SESSION

/export、/fork、resume 与 archive

功能：导出会话、从当前或历史会话分叉、恢复和归档。场景：当前修复已有结论，但你要并行比较“最小补丁”和“重构”两条路线。

最简 SOP
①先 /rename 给会话命名；②/export 导出 Markdown；③当前会话用 /fork，历史会话用 codex fork；④在分支尝试替代路线；⑤用 /diff 比较；⑥完成后 /archive，不要误用 /delete。
成功信号
fork 获得新 ID，原会话内容不变；归档后仍可 unarchive。
排错
/archive 在任务运行时不可用；resume 为空时检查 cwd、Provider/profile 与 --all。
# TUI：/rename 修复登录超时
# TUI：/export
# TUI：/fork
codex fork --last
codex resume --last
codex unarchive <SESSION>

一行速查：分支用 fork，暂存用 archive，永久删除才用 delete。

04 · 实验性 · CONTEXT MANAGEMENT

长会话上下文管理

功能：使用 notes 与可搜索历史保留长期细节，替代反复压成单一摘要。场景：一个项目连续调试数天，普通 compact 开始丢失早期约束。

前置
ChatGPT Plus、Pro 或 Pro Lite 登录；API Key/自定义 Provider 不满足官方条件。
最简 SOP
①备份 config.toml；②用 /experimental 查找功能，或写入开关；③重启 Codex；④新开测试会话；⑤用 /status 观察；⑥不符合预期立即关闭开关。
成功信号
功能被识别且长会话使用 notes/history；strict config 不报未知字段。
排错
开关存在但无效果：检查登录方式和套餐；报未知字段：CLI 过旧。
# Windows：%USERPROFILE%\.codex\config.toml
[features.context_management]
experimental_mode = true

# 一次性严格检查
codex --strict-config

一行速查：短会话用 /compact；只有长周期任务才尝试 Context Management。

05 · 条件可用 · PLUGINS

插件市场：查找、安装、移除

功能：插件把 Skills、MCP、Hook 等能力打包分发。场景：你希望多个项目都能复用同一套调查或设计工作流。

最简 SOP
①列出已安装与可用插件；②确认 marketplace 来源；③使用 add 安装；④重启/新建会话；⑤触发插件 Skill 验证；⑥不用时 remove。
成功信号
list --json 中 installed=true、enabled=true；新会话能发现对应能力。
排错
不要用 install，正式子命令是 add；安装成功但 App 不工作时，继续检查外部授权。
codex plugin --help
codex plugin list --json
codex plugin list --available --json
codex plugin add <plugin@marketplace> --json
codex plugin remove <plugin@marketplace> --json

一行速查：list available → add → 新会话验证 → remove；先审查插件来源和 Hook。

06 · 稳定配置 · MCP

MCP 接入、认证与输出限额

功能：把外部服务接入 Codex，并为单个工具限制返回 token。场景：日志 MCP 每次返回几万行，挤掉真正需要的代码上下文。

最简 SOP
①用 CLI 添加 Server；②list 检查；③需要 OAuth 时 login；④TUI /mcp 确认连接；⑤在 config.toml 为高输出工具设置上限；⑥重启后做一次大结果测试。
成功信号
/mcp 显示已连接；目标工具被截断，其他工具不受影响。
排错
启动慢调 startup_timeout_sec；执行慢调 tool_timeout_sec；截断过头就提高 limit 或改用分页。
codex mcp add context7 -- npx -y @upstash/context7-mcp
codex mcp list
codex mcp login <server-name>

[mcp_servers.logs.tools.search_logs]
output_token_limit = 10000

一行速查：先 /mcp 确认连接，再限制“具体工具”，不要把所有 MCP 一刀切。

07 · 稳定能力 / 需信任 · HOOKS

Hook：自动检查与中断后处理

功能：在 SessionStart、PreToolUse、PostToolUse、SubagentStart、Stop 等生命周期事件运行命令或 MCP handler。场景：Agent 每次执行 Bash 前，自动运行一条只读策略检查。

最简 SOP
①先在项目 .codex/hooks.json 配置只读 Hook；②启动 TUI；③输入 /hooks 审查来源与内容；④显式信任；⑤触发一次匹配事件；⑥确认日志；⑦修改 Hook 后重新审查。
成功信号
/hooks 显示 trusted，触发时出现 statusMessage，退出码符合预期。
排错
项目不可信时项目 Hook 不加载；同层同时放 hooks.json 和 [hooks] 会警告；不要默认绕过信任。
# TUI
/hooks

# config.toml
[features]
hooks = true

# 仅限已由外部流程审查的自动化
codex --dangerously-bypass-hook-trust

一行速查：先只读、再 /hooks 审查、再信任；Hook 必须幂等且有 timeout。

08 · 条件可用 · AMAZON BEDROCK

Bedrock：企业 AWS 路由

功能：使用内置 amazon-bedrock Provider 的 AWS Profile 和 Region。场景：团队要求通过既有 AWS 身份、区域与账单调用模型。

前置
AWS CLI 身份有效；目标 Region 已获得相应 Bedrock 模型访问。
最简 SOP
①aws sts 验证身份；②在 config.toml 设置 profile/region；③选择 amazon-bedrock Provider 和支持的 model；④启动新会话；⑤/status 核验真实 Provider/模型；⑥失败时先查 AWS 权限和区域。
成功信号
凭据刷新成功，/status 显示预期 Provider 与模型。
排错
不要使用不存在的 --provider；命令行 Provider 切换应使用已定义的 profile/config override。
aws sts get-caller-identity --profile work

[model_providers.amazon-bedrock.aws]
profile = "work"
region = "us-east-1"

# 启动前用 codex --help 核对当前模型配置

一行速查：先验证 AWS，再验证 Region/模型授权，最后看 /status，不能凭回答风格判断 Provider。

09 · 稳定可用 · APPROVALS & SAFETY

审批模式、安全边界与额度

功能：控制命令什么时候请求批准，并用 sandbox 限制可写范围。场景：你希望 Agent 自动读取和测试，但修改敏感目录或执行危险命令时停下来。

最简 SOP
①默认使用 workspace-write；②审批设为 on-request；③TUI /permissions 检查；④先运行只读任务；⑤写入前确认目标；⑥/status 查看会话与额度；⑦仅在外部隔离环境使用 yolo。
成功信号
普通读取不中断，越界写入或高风险操作触发审批。
排错
Windows sandbox 降级时运行 /setup-default-sandbox；额外只读目录用 /sandbox-add-read-dir。
codex --sandbox workspace-write --ask-for-approval on-request
# TUI：/permissions
# TUI：/status
# Windows：/setup-default-sandbox
# Windows：/sandbox-add-read-dir

一行速查：日常 workspace-write + on-request；不要把 --yolo 当作排错默认选项。

综合场景：复杂 Bug 的最简协作 SOP

END-TO-END · 10 STEPS
01 基线

codex --version、--help；进入项目后 /status、/permissions。

02 查任务

/agent 查看已有线程，优先复用，避免无意义 spawn。

03 分工

主线程保留决策；子 Agent 只做日志、代码、测试等有边界任务。

04 工具

/mcp 确认连接；为日志搜索工具设置 output_token_limit。

05 追加

发现新条件时切到正确 Agent 追加，slash command 可按 Tab 排队。

06 汇总

回主线程对齐证据、冲突和未决项，不让子 Agent 直接裁决。

07 分叉

/rename 后 /export；用 /fork 分出“最小修复”和“重构”路线。

08 验证

分别测试，用 /diff 与 /review 检查改动和遗漏。

09 回收

/agent 检查状态；停止不再需要的任务，若仍报上限则重启 runtime。

10 留档

保留有效分支并 /archive；不要用 /delete 代替归档。

Windows 路径速查：PowerShell 中用户配置通常写作 $env:USERPROFILE\.codex\config.toml；Git Bash 中通常写作 ~/.codex/config.toml。项目级配置放在 项目目录/.codex/config.toml，仅可信项目加载。修改配置后建议新开 Codex 进程，并用 codex --strict-config 捕获未知字段。
