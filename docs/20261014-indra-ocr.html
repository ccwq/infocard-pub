它是什么

本地 PDF → 结构化文本

一个 Python 包加一个 CLI。读 PDF，逐页出 markdown、纯文本或 json。json 每个页面一个对象，含每行的 box/text/confidence、版块 label + bbox + text、阅读顺序、source 字段、rotation/skew 和 timings。

来源：官方 README 输出格式段
适合谁

要自建 PDF 解析管线的人

  • 本地跑、不想把文件传出去的团队
  • 文档量大、需要多核并行（--cores N）
  • 要版块标签和阅读顺序做下游 RAG 或索引
  • 接受复杂表格、手写会出错的场景
判断为作者观点，非官方定位

03
最小可用命令

两条命令：批量出 markdown，单文件出 json

先把输出拿全，再调开关。json 里的版块和阅读顺序是这张卡最有价值的部分。

# 批量：*.pdf 每个文件一份 md，落 results/，占满全部核心
indra-ocr *.pdf --out results/

# 单文件：json，含 box / 版块 / 阅读顺序
indra-ocr paper.pdf --format json --out results/

命令形式来自官方 README。通配符由 shell 展开，一个输入文件对应一个 worker 进程。

# 输出有三种
--format markdown   # 默认
--format text
--format json

# 打一个 json 对象（节选字段名）
{
  "pages": [{
    "markdown": "...",
    "blocks": [{ "label": "Table", "bbox": [...], "text": "..." }],
    "lines":   [{ "box": [...], "text": "...", "confidence": 0.98 }],
    "reading_order": [...],
    "source": "hybrid",   // text|ocr|hybrid|error
    "rotation": 0, "skew": 0.3,
    "timings": {...}
  }]
}

版块 label 全集：Text、Section-Header、Page-Header、Page-Footer、List-Group、Table、Caption、Footnote、Table-Of-Contents、Form。

source 字段是最省事的排错依据。 text 表示这页直接用了 PDF 文本层，ocr 表示整页走识别，hybrid 表示只 OCR 缺失部分，error 表示这页失败。做数据质量抽样时先按这个字段分组，比逐页人眼看快得多。（来源：官方 README json 输出说明）
04
CLI 关键开关

真正影响结果的是这几个

其余开关（--no-image-ocr、--model-order、--timings）不影响识别质量，按需用。表格可横向滚动。

开关默认作用与代价
--modeautoauto：有文本层就读层、只 OCR 缺失部分；文本层检查失败时也照样用它。ocr：完全不看文本层，全页识别。text：只抽文本层，不识别。混合语料（扫描件+数字 PDF）保持 auto。
--cores全核每个核一个 worker 进程。indra-ocr *.pdf 传多个文件时本就占满核心；单文件想并行要靠这个。
--dpi200渲染 dpi。超过 100 兆像素的页会被降 dpi 渲染，小字可能丢（见第 09 节）。
--keep-furniture丢默认丢掉页眉页脚。补录正文里的重复行、或页眉本身有信息时才加。
--math关默认公式只出纯文本；开则出行内 LaTeX，更慢。文本分从 41.3 升到 57.5，就是靠它。
--max-pages不限只处理前 N 页，试跑时用它控成本。
--password无加密 PDF 的口令。
--model-dir缓存本地模型目录，等价于 INDRA_OCR_MODEL_DIR。离线部署用。
--timings关耗时打到 stderr，不污染输出文件。

以上默认值与语义来自官方 README CLI 段。读不了的文件会被跳过；只要有一个文件失败，退出码为 1——批处理脚本里别只看 stdout 有没有内容。

05
Python API 与批量

convert_many 少了那行保护会退化成单进程

批量 API 用多进程，坑在 __main__ 保护上：macOS 和 Windows 缺这行会警告并单进程跑完全部文件。

# 批量：每核一个单线程 worker，按输入顺序返回
import indra_ocr

if __name__ == "__main__":          # macOS/Windows 必需
    pages = indra_ocr.convert_many(
        ["a.pdf", "b.pdf", "c.pdf"],
        cores=None,          # None = 每核一个 worker
    )

来源：官方 README Python API 段

# 单文件逐页产出
conv = indra_ocr.load(threads=4, mode="auto")

for page in conv.convert("paper.pdf"):
    page.markdown   # 该页 markdown
    page.blocks     # 版块
    page.lines      # 行

# 不可读文件按异常类型判断，不要静默吞掉
from indra_ocr import INDRA_OCR_INPUT_ERROR
try:
    ...
except INDRA_OCR_INPUT_ERROR as e:
    print("bad input:", e)

速度基准

官方自测的四核到三十二核

口径必须一起读：AMD EPYC x86、无 GPU、OCR 模式、300 页 OmniParseBench；模型加载和每个 worker 的首页预热不计入时间。

PaddleOCR PP-OCRv6 small（RapidOCR）0.651.242.424.28只出行，不出版块与表格

单位：页/秒。数据来自官方博客自建基准，本轮未实测。

倍数怎么来的。 32 核时，Indra 是 PP-OCR 文本模型的 11.5 倍、Tesseract 5 的 16.9 倍、约 280 倍 PP-StructureV3（后者是封顶上界，倍数只会更大不会更小）。四个对比对象里只有两个产出完整文档结构。
更贴近生产的两个数。 单页延迟约 230ms（4 vCPU）；含模型加载的 300 页短任务，32 核跑到 37.7 页/秒。开 --math 后 32 核约 30 页/秒，4 核从 6.8 掉到 4.8、32 核从 44.9 掉到 29.2，低 30–35%。带文本层的数字 PDF 页中位 130ms，需要 OCR 的页 304ms。

09
什么时候不该用

官方自己列的限制，照抄

下面每条都对应官方 README / 博客限制段。中途碰到这些再回来看一眼，比调参数省时间。

表格

复杂表格会行列错位

合并单元格、跨行单元格、多级表头、无框线表格都可能错。规整的网格表没问题。

手写

不支持

OmniParseBench 上手写体约 8%。手写稿直接排除。

公式

默认纯文本

默认不出 LaTeX，要 --math。旧扫描件里的公式仍难（22.2 → 23.1，几乎没动）。

文种

扫描件上非支持文种会认错

见第 10 节的 OCR / 仅文本层分界。例：韩文扫描件会认成错误汉字。

扫描质量

退化件约 20%

老、褪色、低分辨率的扫描件正确率只有两成。

排版

竖排不支持

竖排文本不处理。方向模型还会把约一半竖直的阿拉伯 / 希伯来页面误转。

版面

极宽页与工程图

极宽横幅页读得差。工程图内部标签常被当成小表格处理。

超大页

200dpi 下超过 100 兆像素

会以降 dpi 渲染，小字可能丢。超大图纸/海报要么先切分，要么降 dpi 前先评估。

兜底

官方托管平台

官方平台跑他们的 Chandra 模型处理手写、数学、复杂表格、退化扫描，zero data retention、SOC 2 Type 2；批量服务称每天 10 亿+ 页。商业选项 · 未实测

10
语言支持的真实边界

“支持 50 种语言”和“扫描件只认这些”，是两件事

最容易踩的坑：官方列了两组语言，一组是真能识别，一组只是能从数字 PDF 里抽文本层。

OCR 识别（扫描件 / 图片）

拉丁约 50 种 + 少量其他

Latin 约 50 种、Cyrillic、Greek、Devanagari、Bengali、中文简体与繁体。含汉字的行走中文识别器在这一组里。

RTL（阿拉伯、希伯来）行内保序。

来源：官方 README 语言段
仅文本层（数字 PDF）

这些文种只靠文本层活着

阿拉伯、希伯来、波斯、泰、柬、老、缅、高棉、亚美尼亚、埃塞、印地系、中日韩——只依赖数字 PDF 的文本层，不进 OCR 识别列表。扫描件上会认错。

文本层模式本身支持任意文字系统。官方在 75 个语言家族的 1125 页上测过，通过检查的页面保留至少 98% 文本层字符。

来源：官方 README 语言段与评测说明
对你意味着什么。 中文文档如果同时有数字 PDF 和扫描件，要分开设预期：数字 PDF 走文本层、几乎不会错；扫描件里汉字没问题，但日文、韩文一旦是扫描件就不可靠。这条直接决定 --mode 怎么设（混合格式保持 auto）。

12
上手建议

拿自己 20–50 页先跑一轮

这是作者建议的操作路径，不是官方推荐，也不是实测结论。

1
选 20–50 页自己的 PDF。 要含一份扫描件和一份数字 PDF，混着才能测出 --mode auto 的真实行为。
2
先只出 markdown。 indra-ocr paper.pdf，看整体可读性和版块顺序对不对。
3
再出一次 json。 --format json，重点看两件事：表格的 bbox 和行列有没有错位，reading_order 在多栏页上对不对。
4
开 indra-ocr-viewer 对照原页看。 逐块叠加行、版块、阅读顺序，比在 json 里翻快。
5
公式多就加 --math 重跑对比。 接受 30–35% 的速度损失换 text 分从 41.3 到 57.5。

推文转述里需要打折的三处

转述源为程序员鱼皮 X 帖（x.com/yupi996/status/2110334301367845184）。下面按官方一手材料逐条校正，避免照搬二手结论。

推文说法官方口径怎么理解
“每秒 49 页，是 PaddleOCR 的 11 倍”49.4 页/秒；32 核 OCR 模式成立，但有三重限定：32 核、纯 OCR 模式、对比对象是 PP-OCR 文本模型——后者只出行，不出版块和表格。换成完整流水线 PP-StructureV3，比的是准确率不是这个倍数。
“18MB”模型合计约 18MB是模型体积，不是安装体积。依赖 ONNX Runtime、OpenCV、pypdfium2。
“手写和复杂表格认不好”与官方限制一致这条转述准确，见第 09 节。
“M2 Max 150 页 9 秒、1025 个汉字全对”官方无此基准作者自测，只能当第三方观察；官方未给 M 系列基准，本文不替他推算原因。
