01
它是什么

从 Karpathy 的"LLM 编码陷阱"观察，到一份可执行的行为规范

这个项目的本质是：把 Andrej Karpathy 在社交媒体上公开指出的 LLM 编码通病，翻译成一份 CLAUDE.md 文件，让 Claude Code 在每次编码时都遵守。

来源Karpathy 观察

不是凭空设计，而是针对真实痛点

Karpathy 在推文中明确指出：模型会默默做错误假设并一路跑下去，不管理困惑、不寻求澄清、不暴露矛盾、不展示权衡、该反驳时不反驳。

  • 静默假设 → 不检查就执行
  • 过度复杂化 → 1000 行做 100 行的事
  • 乱改无关代码 → 作为副作用删掉不懂的部分
形态单文件

一份 CLAUDE.md，不是框架不是库

它不依赖任何运行时、不需要安装依赖，核心交付物就是一个 CLAUDE.md 文件。Claude Code 原生支持读取项目根目录的 CLAUDE.md 作为上下文指令。

  • 零运行时依赖
  • 纯文本配置
  • 可合并到已有 CLAUDE.md
目标行为约束

给 Claude 装"刹车"，不是装"引擎"

它不增加 Claude 的能力，而是约束 Claude 的行为：编码前先想、改动只做该做的、用可验证目标驱动循环执行。核心是减少错误，不是增加功能。

  • 减少不必要改动
  • 减少过度工程返工
  • 强制先澄清再实现
Karpathy 原文（第二段）："They really like to overcomplicate code and APIs, bloat abstractions, don't clean up dead code... implement a bloated construction over 1000 lines when 100 would do." 这段话直接对应"简洁优先"和"外科手术式改动"两条原则。
02
核心能力

四条原则，逐条对应 Karpathy 指出的编码陷阱

每条原则都有明确的"针对问题"和"可操作规则"，不是泛泛而谈的价值观，而是可以直接检查的行为约束。

01 / Think Before Coding

编码前先思考

针对：错误假设、隐藏困惑、缺失权衡。

规则：显式声明假设；存在歧义时呈现多种解释而非静默选择；有更简方案时主动提出；困惑时停下来问而不是猜。

检验：不确定时是否先问而非先猜？

02 / Simplicity First

简洁优先

针对：过度复杂化、抽象膨胀。

规则：不做没要求的功能；单次使用的代码不抽象；不做没要求的"灵活性"和"可配置性"；不可能的场景不写错误处理；200 行能压到 50 行就重写。

检验：资深工程师会不会觉得过度？

03 / Surgical Changes

外科手术式改动

针对：无关改动、触碰不该碰的代码。

规则：不"改进"相邻代码、注释或格式；不重构没坏的东西；匹配现有风格；发现无关死代码提一句但不删；只清理自己改动产生的孤儿代码。

检验：每行改动能否追溯到用户请求？

04 / Goal-Driven Execution

目标驱动执行

针对：命令式指令 → 可验证目标。

规则：把"加校验"变成"为非法输入写测试再让它通过"；把"修 bug"变成"写一个复现测试再让它通过"；多步任务先列计划再逐步验证。

检验：有明确成功标准吗？

原则针对的 LLM 陷阱可操作规则
Think Before Coding静默假设、不寻求澄清、不展示权衡显式声明假设 · 多解释呈现 · 主动反驳 · 困惑即停
Simplicity First过度工程、抽象膨胀、1000 行做 100 行的事不做多余功能 · 不抽象单次代码 · 压缩行数
Surgical Changes乱改无关代码、删不懂的注释、副作用改动只碰必须碰的 · 匹配现有风格 · 提到但不删死代码
Goal-Driven Execution弱成功标准导致反复澄清、无法自主循环测试先行 · 可验证目标 · 多步计划带验证点

"Goal-Driven Execution" 是 Karpathy 核心洞察的落地：LLM 擅长循环到满足特定目标，关键是你得给它明确的成功标准，而不是告诉它"怎么做"。

03
怎么上手

两条安装路径：插件全局生效，或 CLAUDE.md 按项目生效

根据你是想"所有项目都受约束"还是"只约束当前项目"，选择插件安装或直接下载 CLAUDE.md 文件。

路径 A插件（推荐）

Claude Code 插件安装

Step 1：/plugin marketplace add forrestchang/andrej-karpathy-skills
Step 2：/plugin install andrej-karpathy-skills@karpathy-skills

安装后，指南作为 Claude Code 插件在所有项目中生效。适合希望统一行为约束的开发者。

  • 一次安装，全局生效
  • 跨项目复用同一套规则
  • 推荐给重度 Claude Code 用户
路径 BCLAUDE.md

按项目下载 CLAUDE.md

新项目：curl -o CLAUDE.md https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md

已有项目（追加）：echo "" >> CLAUDE.md && curl https://raw.githubusercontent.com/forrestchang/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md

把 CLAUDE.md 放在项目根目录，Claude Code 会自动读取。已有 CLAUDE.md 的项目可以追加合并。

  • 按项目独立配置
  • 可与已有规则合并
  • 支持自定义项目特定规则
Cursor跨编辑器

Cursor 用户也能用

仓库内置了 Cursor 项目规则文件 .cursor/rules/karpathy-guidelines.mdc，打开项目时同一套指南自动生效。详见仓库中的 CURSOR.md 文档，涵盖在其他项目中使用该规则的方式，以及它与 Claude Code 的关系。

自定义可合并

如何与项目特定规则合并

这些指南设计为可以与项目特定指令合并。在 CLAUDE.md 中添加项目特定规则段落即可：

## Project-Specific Guidelines
- Use TypeScript strict mode
- All API endpoints must have tests
- Follow the existing error handling patterns in src/utils/errors.ts

通用四原则 + 项目特定规则 = 完整的行为约束体系。

04
适合谁

适合被 LLM "过度工程"和"乱改代码"困扰的开发者

如果你经常发现 Claude Code 或 Cursor 给你塞了一堆你没要求的改动、过度抽象、或者改着改着把你无关的代码也动了——这份 CLAUDE.md 就是为你的场景写的。

01 / Claude Code 用户

想统一行为约束

日常重度使用 Claude Code 编码，经常被它的"自作主张"困扰。

插件安装一次全局生效，所有项目自动遵守四原则。

02 / Cursor 用户

想要同样的约束

仓库自带 Cursor 规则文件，开箱即用。

不需要自己从零写 mdc 规则，直接复用 Karpathy 钦点的约束体系。

03 / 团队协作

想统一团队的 AI 编码规范

把 CLAUDE.md 提交到仓库，所有使用 Claude Code 的成员自动继承同一套规则。

减少"每个人和 AI 协作的方式都不一样"导致的 PR 质量波动。

04 / 效率优先者

受够了返工和过度工程

四原则直接针对"1000 行做 100 行的事"和"乱改无关代码"。

如果 diff 里总出现你没要求的改动，这份规范能显著减少 review 成本。

05
边界与风险

它约束行为，不替代判断——简单任务别套全套流程

这份指南明确偏重"谨慎优先于速度"。对于琐碎任务（简单拼写修正、明显的一行修改），README 自己也说要用判断力，不是每个改动都需要全套流程。

1

可能拖慢简单任务

四原则偏重谨慎，对琐碎改动（typo 修复、一行修改）可能显得过重。README 自己承认这个 tradeoff，建议对简单任务用判断力而非机械执行。

2

不增加能力，只减少错误

它是行为约束，不是能力增强。如果你的问题是"Claude 不会做某件事"，这份 CLAUDE.md 帮不上忙；它解决的是"Claude 做了不该做的事"。

3

需要与项目规则磨合

通用四原则可能与项目特定约定冲突。比如"不做没要求的功能"可能与团队"主动优化"的文化矛盾。需要根据项目实际情况调整合并策略。

场景适合不适合
非平凡的编码任务四原则全套生效，减少错误——
琐碎修改（typo / 一行）用判断力，不必套全套流程机械执行四原则反而拖慢
需要 Claude 做更多——这是约束工具，不是能力增强
团队统一规范提交到仓库统一行为约束团队文化与之冲突时需调整

README 原文："These guidelines bias toward caution over speed. For trivial tasks, use judgment — not every change needs the full rigor." 目标是减少非平凡工作的高成本错误，不是拖慢简单任务。
