01
核心问题

Karpathy 的诊断：LLM 编码时有三种系统性坏习惯

Karpathy 在公开推文中精准描述了当前 LLM 辅助编码的三类通病。这份 CLAUDE.md 的每一条原则，都能追溯到下面这三段原话——它不是凭空设计的价值观，而是针对真实痛点的对症下药。

问题 1静默假设

不检查就跑，不澄清就猜

Karpathy 原话：模型会默默做错误假设并一路跑下去，不管理困惑、不寻求澄清、不暴露矛盾、不展示权衡、该反驳时不反驳。

原文："The models make wrong assumptions on your behalf and just run along with them without checking. They don't manage their confusion, don't seek clarifications, don't surface inconsistencies, don't present tradeoffs, don't push back when they should."
  • 静默假设 → 不检查就执行
  • 不暴露不确定性和矛盾
  • 该反驳时不反驳
问题 2过度工程

1000 行做 100 行的事

Karpathy 原话：模型喜欢过度复杂化代码和 API，膨胀抽象，不清理死代码——100 行能搞定的事，偏要写 1000 行的臃肿实现。

原文："They really like to overcomplicate code and APIs, bloat abstractions, don't clean up dead code... implement a bloated construction over 1000 lines when 100 would do."
  • 过度复杂化代码和 API
  • 膨胀抽象层
  • 不清理死代码
问题 3乱改无关代码

作为副作用删掉不懂的东西

Karpathy 原话：模型有时会改动或删除它们并不充分理解的注释和代码，即使这些代码与当前任务无关——作为副作用被波及。

原文："They still sometimes change/remove comments and code they don't sufficiently understand as side effects, even if orthogonal to the task."
  • 改动与任务无关的代码
  • 删掉不充分理解的注释
  • 副作用波及正交部分
归纳三病 → 四原则

三个问题，四条原则，一份文件

张家园（@freschange）把 Karpathy 这三段诊断，翻译成了四条可直接写入配置文件的行为约束。三病对应四原则：静默假设 → 编码前先思考；过度工程 → 简洁优先；乱改无关代码 → 外科手术式改动；而第四条「目标驱动执行」，则来自 Karpathy 的另一个关键洞察——LLM 擅长循环到满足目标，前提是你给它明确的成功标准。

02
四原则详解

四条原则，逐条对应 Karpathy 指出的编码陷阱

每条原则都有明确的「针对问题」和「可操作规则」，不是泛泛而谈的价值观，而是可以直接检查的行为约束。写入 CLAUDE.md 后，Claude Code 在每次编码时都会读取并遵守。

01 / Think Before Coding

编码前先思考

针对：错误假设、隐藏困惑、缺失权衡。

规则：显式声明假设；存在歧义时呈现多种解释而非静默选择；有更简方案时主动提出；困惑时停下来问而不是猜。模型不应该替你做决定然后一路跑下去。

检验：不确定时是否先问而非先猜？

02 / Simplicity First

简洁优先

针对：过度复杂化、抽象膨胀、1000 行做 100 行的事。

规则：不做没要求的功能；单次使用的代码不抽象；不做没要求的"灵活性"和"可配置性"；不可能的场景不写错误处理；200 行能压到 50 行就重写。

检验：资深工程师会不会觉得过度？

03 / Surgical Changes

外科手术式改动

针对：无关改动、触碰不该碰的代码、删掉不懂的注释。

规则：不"改进"相邻代码、注释或格式；不重构没坏的东西；匹配现有风格；发现无关死代码提一句但不删；只清理自己改动产生的孤儿代码。

检验：每行改动能否追溯到用户请求？

04 / Goal-Driven Execution

目标驱动执行

针对：弱成功标准导致反复澄清、无法自主循环。

规则：把"加校验"变成"为非法输入写测试再让它通过"；把"修 bug"变成"写一个复现测试再让它通过"；多步任务先列计划再逐步验证。

检验：有明确成功标准吗？

原则针对的 LLM 陷阱可操作规则检验标准

Simplicity First过度工程、抽象膨胀、1000 行做 100 行的事不做多余功能 · 不抽象单次代码 · 压缩行数资深工程师觉得过度吗？

06
效果验证

为什么这套方法有效：给目标，不给指令

第四条原则「目标驱动执行」背后的核心洞察，直接来自 Karpathy——LLM 擅长循环到满足特定目标，关键是你得给它明确的成功标准，而不是告诉它"怎么做"。这也是这份 CLAUDE.md 区别于普通 prompt 模板的地方。

核心洞察success criteria

LLM 擅长循环到满足目标

Karpathy 原话："LLMs are exceptionally good at looping until they meet specific goals... Don't tell it what to do, give it success criteria and watch it go."

这段话是「目标驱动执行」原则的设计依据。与其告诉模型"加校验"（指令式），不如告诉它"为非法输入写测试再让它通过"（目标式）——模型会自主循环直到测试通过。

  • 指令式 → 模型猜你要什么，容易跑偏
  • 目标式 → 模型循环到满足标准，可验证
  • 成功标准 = 可执行的验证条件
验证方式可观测

怎么知道 CLAUDE.md 生效了

效果是可观测的。如果四原则在起作用，你会看到：diff 更小更干净、没有你没要求的改动、模型在不确定时主动提问、过度抽象减少、bug 修复附带复现测试。

  • diff 更小——没有无关改动
  • 模型主动提问——不再静默假设
  • bug 修复附带复现测试
  • PR review 成本下降
指令式（弱）

"加个校验"

模型猜你要什么校验、加在哪里、校验什么——容易跑偏，需要反复澄清。

目标式（强）

"写测试再让它通过"

为非法输入写测试 → 运行 → 失败 → 修代码 → 再运行 → 通过。模型自主循环到满足标准。

关键差异

成功标准可验证

指令式没有终止条件；目标式有明确的"完成"定义——测试通过即完成。这就是 Karpathy 说的"watch it go"。

07
适用边界

它约束行为，不替代判断——简单任务别套全套流程

这份指南明确偏重"谨慎优先于速度"。对于琐碎任务（简单拼写修正、明显的一行修改），README 自己也说要用判断力，不是每个改动都需要全套流程。它是约束工具，不是能力增强。

1

可能拖慢简单任务

四原则偏重谨慎，对琐碎改动（typo 修复、一行修改）可能显得过重。README 自己承认这个 tradeoff，建议对简单任务用判断力而非机械执行。

2

不增加能力，只减少错误

它是行为约束，不是能力增强。如果你的问题是"Claude 不会做某件事"，这份 CLAUDE.md 帮不上忙；它解决的是"Claude 做了不该做的事"。

3

需要与项目规则磨合

通用四原则可能与项目特定约定冲突。比如"不做没要求的功能"可能与团队"主动优化"的文化矛盾。需要根据项目实际情况调整合并策略。

场景适合不适合 / 需注意
非平凡的编码任务四原则全套生效，减少错误——
琐碎修改（typo / 一行）用判断力，不必套全套流程机械执行四原则反而拖慢
需要 Claude 做更多——这是约束工具，不是能力增强
团队统一规范提交到仓库统一行为约束团队文化与之冲突时需调整

README 原文："These guidelines bias toward caution over speed. For trivial tasks, use judgment — not every change needs the full rigor." 目标是减少非平凡工作的高成本错误，不是拖慢简单任务。
