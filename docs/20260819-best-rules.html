设计理念

为什么需要这套规则？

现状
AI Coding 工具默认行为过于自由，容易产生幻觉、超纲改动、不验证就提交
Rules 是给 AI 设定边界的最有效手段
效果
小改动优先、不无关重构、不添加不必要的依赖、先验证再提交
规则驱动而不是对话驱动
核心原则

最小改动 · 证据优先 · 验证闭环

最小改动
只改能解决当前问题的最小代码，不做顺手重构、不过度测试
不要在修复 Bug 时顺手改善相邻代码风格
证据优先
不凭感觉猜测根因，先收集证据再动手，3 次失败后停止并询问
3 次修复失败 → 架构层问题，需要人工介入

global.md · Implementation 部分
# Implementation · 实施阶段
Fix the root cause with the smallest clear and debuggable change.

Avoid unrelated refactoring, excessive defensive checks,
redundant fallback logic, and compatibility paths for
unsupported or hypothetical scenarios.

Stay focused on the current task. Pursue improvements only
when they materially advance the requested outcome.

Do not pursue excessive consistency or over-testing. Do not add
unnecessary gates, SHA-256 hashes, checksums, verification
layers, or redundant tests unless they are required for
correctness or by the task.

Follow the existing code style.

03
使用对比 · 有规则 vs 无规则
✅ 有规则
最小改动：只改 bug 相关代码
不添加不必要的测试、哈希、校验层
3 次失败后主动停下来询问
先验证再提交，运行实际检查命令
遵循现有代码风格，不做顺手重构
❌ 无规则
修复 Bug 时顺手重构相邻模块
为"以防万一"添加过度防御性代码
猜测根因，不验证就提交
连续修复 6 次仍不停止
随意添加依赖，不检查现有工具
