1
重 Workflow 为什么正在失效
Token 消耗 · 流程惯性 · 模型能力溢出

传统 AI 开发依赖「超级英雄式」Workflow：Superpowers 围绕 Spec → TDD → Review 建约束流，要求每步都走完。但强模型时代（上下文 200K+、推理能力强），这套做法正在变成噪声。

❌ 旧范式的问题

Token 消耗快 · 上下文已够仍走既定流程 · Prompt 膨胀 · 维护成本高 · Agent 行为僵化

✓ 新范式核心

用「方法论名称」替代手写大段 Workflow——几十个字指定五种认知动作，告诉模型「以什么方式思考」

OpenAI 发布 Astra 时专门写博客教大家清理不必要的 Skill 和系统提示词——「工具越多，模型越乱」。

本质变化：从「告诉模型做什么步骤」到「告诉模型以什么心智模型思考」。方法论名称 = 压缩了多年的工程经验。

2
作者的工具分工表
按任务特性分配模型，而非全押一个
🧠 Codex + GPT-5.6 Sol

主力编码 Agent。复杂业务逻辑、多文件改动、测试编写——执行层主力。

📐 Astra

规划 Agent。需求分析、任务拆解、工作流编排——先用它对齐方向再开工。

⚡ pi + DeepSeek V4 Flash

简单需求快速处理。重复 CRUD、格式调整、小修小补——不上主 Agent。

🔍 Claude 5 Fable

对抗性审查 / Code Review。专门找漏洞、追假设、质疑方案正确性。

💡 GPT-6 Pro（网页端）

方案设计。架构选型、技术方案讨论、方案原型——在浏览器里快速推演。

分工原则

按「任务复杂度 × 所需模型特性」分配，不是全押 GPT，也不是一个模型干所有事。

3
Skill 实用清单
重复三次就沉淀成 Skill · 自建 SOP 体系

自沉淀原则

一个流程重复超过三次就整理成 Skill。「重复三次就沉淀」是防止 Workflow 膨胀的反向约束。

think
think（来源：tw93）

方案对齐与头脑风暴。在动手前让模型把思路说出来，避免方向跑偏。

grill me
grill me / grill with docs

需求澄清连续追问。追问「为什么」直到隐性假设浮出水面 → 沉淀 ADR / CONTEXT.md。

implement
implement（Matt Pocock 全家桶）

实现 + 测试。配合 grill 使用，先把需求搞清楚再implement，避免改返工。

ponytail
ponytail

清理 AI 过度设计。砍掉「看起来很厉害但实际上不需要」的抽象层，降低人工 Review 难度。

handoff
handoff

上下文成文件跨会话交接。把当前状态写进文件，下一个 Agent 启动时直接读，不再靠记忆。

check
check

提 MR 审查。提交前触发质量门禁，跑测试、对照验收标准，确保 MR 足够小可被人工 Review。

4
五法思维快捷键 ⭐ 重点节
第一性原理 · 对抗性审查 · 消融实验 · 奥卡姆剃刀 · 高内聚低耦合

每个方法三要素：是什么 / 真实 Prompt 例 / 模型反应 / 适用场景。「五法」可以单独使用，也可以组合——组合时按顺序执行效果最佳。

① 第一性原理

FIRST PRINCIPLES
不要基于「加 Redis 缓存」继续设计。重新分析接口为什么慢——瓶颈到底在 SQL / 网络 / 序列化 / 锁竞争 / 重复计算？

模型会从「我想到的解法」退回到「真正的问题是什么」，找到根因而非症状。

适用：性能优化 · 技术方案评审 · 接手遗留代码

② 对抗性审查

ADVERSARIAL REVIEW
不要帮方案找理由，想办法证明它是错的。追问：幂等吗？锁服务挂了怎么办？过期业务没完怎么处理？

模型从「辩护者」切换到「攻击者」，主动暴露风险而非等 Review 提出来。

适用：方案设计 · PR Review · 架构选型

③ 消融实验

ABLATION STUDY
三个优化接口 800ms→100ms，设计消融实验判断真正收益。可能只加索引就 800→120ms，其余是幻觉。

拆解组合收益，分离真实贡献与噪声干扰，防止把「优化了但没效果」的改动合入。

适用：性能调优 · 算法改进 · 多方案对比

④ 奥卡姆剃刀

OCCAM'S RAZOR
Kafka + Redis + 锁 + 状态机 + 补偿——删除非必要机制。单库写入 + 一个事务 + 唯一索引就够。

每次引入新机制时追问「去掉它会怎样」，保持方案精简，降低后续维护成本。

适用：架构设计 · 新增抽象层 · 依赖引入

⑤ 高内聚低耦合

COHESION & COUPLING
审查 OrderService 2000 行——职责边界清晰吗？不要为拆而拆。激活模块化 / 信息隐藏 / 依赖方向判断。

追问「这个模块只因一个原因改变吗」「依赖方向是否自顶向下」，防止假分层真耦合。

适用：代码重构 · 服务拆分 · 大文件拆分 · 新增抽象层
新 Prompt Engineering 的本质： 几十个字指定五种认知动作——重新定义问题 → 攻击假设 → 验证贡献 → 删除复杂度 → 整理边界。告诉模型「以什么方式思考」而非写死流程。
5
日常开发全流程
需求对齐 → 沉淀 Spec → 分派 → 交叉对抗 → E2E → 小 MR Review
①
需求对齐（grill + 控制尺度）

PRD / 会议纪要 / 聊天记录 / 用户反馈全部给 Agent + grill 追问。控制尺度：剩下问题不显著改变方向即可开工。

grill with docs <需求文档>
②
沉淀 Spec / CONTEXT.md

grill 结论写成文件，包含：目标、约束、验收标准、已否决方案。下一轮开工直接读，不重复对齐。

③
按复杂度分派（subagent + worktree）

简单直做；复杂拆独立验收 Issue，交 subagent 多 worktree 并行开发，主 Agent 负责集成。

subagent --task=issue-42 --worktree=feature/x
④
交叉对抗审查

引入其他 Agent（Claude Fable）做对抗性审查——不是找优点，是找漏洞。问题反馈主 Agent 修复后重验。

⑤
端到端测试

浏览器自动化（ego-lite + pi + DeepSeek V4 Flash）或 API 链测试，验证真实业务路径。

⑥
小 MR 人工 Review

不逐行读，看测试结果 + 核心业务逻辑。前提：MR 足够小（建议 <400 行）。

6
Agent 友好端到端测试四件事
环境 · 操作 · 查证 · 复用 · 统一 CLI
① 熟悉环境

一键启动 / 测试数据 / 版本账号权限 / 清理重置

Agent 需要可复现的环境描述。提供：启动命令、测试账号、数据 fixture、权限说明、清理脚本。

② 操作业务系统

浏览器 / API / CLI 真实流程

不只是单元测试，要能在真实系统里跑完端到端路径。推荐 ego-lite + pi + DeepSeek V4 Flash。

③ 查库表日志

只读 DB MCP + 日志 Skill + Trace

给 Agent 提供查数据库、日志、Trace 的工具，让它自己验证结果而非靠「感觉对了」。

④ 稳定流程复用

操作写脚本 + 入口排障成 Skill

把常用操作固化脚本，把故障排查路径沉淀成 Skill，下次遇到同类问题直接调用。

统一测试 CLI 框架

环境检查 → 数据准备 → 场景执行 → 结果查询 → 清理。一条命令覆盖完整生命周期。

核心原则：工具帮拿证据，不替定正确答案。预期结果必须来自业务契约，「不能让 Agent 看到系统返回了什么就认为什么是正确的」。产品本身是 Agent 时加 Agent Eval。

7
Review 四实践
先标准后结果 · 沿业务路径 · 奥卡姆再审 · Review Bot

① 先验收标准再对照结果

Review 前先确认「这 MR 要解决什么问题」，再看测试结果是否符合验收口径，而不是直接看代码对不对。

✓ 先问：需求是什么？验收标准是什么？

② 沿业务路径看高风险

权限变化、状态流转、并发、重试、数据一致性、迁移回滚——沿真实业务路径追高风险点。稳定 CRUD 少看甚至不看。

✓ 看业务链路，不看代码语法

③ 新增抽象用奥卡姆再审

每个新增的类/模块/服务，用奥卡姆剃刀追问：去掉它会怎样？现有的能合并吗？防止为抽象而抽象。

✓ 每层抽象必须有不可替代的理由

④ MR 多则建 Review Bot

当 MR 量大时，建 Review Bot 结合 Git 变更 + 预设审查流程，自动过滤低风险 PR，让人专注高风险路径。

✓ 人做判断，Bot 做过滤
8
瓶颈反思与行动建议
Review 速度 · Harness 三要素 · 定期做减法 · 验收标准仍需人给

⚠ 当前瓶颈

Agent 可以并行推进，但人的判断不成倍增加。Review 速度是人肉瓶颈。

Harness 三要素

正确上下文（CONTEXT.md / Spec）+ 可执行环境（一键启动）+ 判断结果依据（验收标准 / 业务契约）。三者缺一，Agent 在黑暗里跑。

✓ 工作流定期做减法

OpenAI Astra 更新后主动删 AGENTS.md 的过严约束。工作流会随工具进化变臃肿，需要定期清理。

✓ 验收标准仍需人给

代码和测试互相对得上也可能一起误解需求。人是最终的需求契约方，AI 只是执行器。

行动建议： 挑一条最常做的自测路径，让 Agent 独立跑通、保留证据、沉淀步骤。从「跑通一条路」开始，不是建一整套体系。

AI 减少踩坑机会，留出时间学习复盘。关键不是用更多工具，而是用对方法——每次问自己：这个流程重复三次了吗？要不要沉淀成 Skill？

9
术语表
Harness · Spec · ADR · CONTEXT.md · subagent · worktree · 消融实验 · 对抗性审查 · Agent Eval
术语 解释
Harness 测试脚手架。指让 Agent 在「正确上下文 + 可执行环境 + 判断依据」里跑通验证的完整体系。
Spec 技术规格说明文档。包含目标、约束、技术选型、验收标准——在开工前与 Agent 对齐。
ADR Architecture Decision Record。记录架构决策的背景、选项、结论与后果，供后续查阅。
CONTEXT.md 跨会话上下文文件。grill 结论沉淀在此，下一个 Agent 启动时直接读，不再重复对齐。
subagent 子 Agent。复杂任务拆成独立 Issue，分配给 subagent 并行处理，主 Agent 负责集成与 Review。
worktree Git worktree。在同一仓库的不同目录并行开发不同分支，适合 subagent 并行时隔离工作区。
消融实验 Ablation Study。逐步移除/单独启用各个优化项，分离真实贡献与噪声干扰，判断真正收益。
对抗性审查 Adversarial Review。不是帮方案找理由，而是想办法证明它是错的——主动暴露风险而非被动等待 Review。
Agent Eval Agent 评测。当产品本身就是 Agent 时，用自动化方法评估 Agent 输出质量，而非传统 UI 验收。
