它是什么、不是什么

是什么 Hermes 的 Holographic memory provider，底层 SQLite + FTS5，支持 trust score、实体解析与组合检索。

不是 聊天摘要工具、临时笔记、无限日志桶，也不是把所有原文塞进去的记录仓库。

适合存

  • 用户长期偏好、项目约定、工具参数、环境事实。
  • 已经确认且会反复引用的稳定结论。
  • 需要跨会话复用的事实、规则、决策、实体关系。

不适合存

  • 一次性聊天、临时任务、原始长日志。
  • 未确认的猜测、模糊线索、会过期的短期上下文。
  • 本该放在 session_search 的短期内容。

接入 Hermes 的方式

  • 在 config.yaml 中设置 memory.provider: holographic。
  • 插件配置写在 plugins.hermes-memory-store 下。
  • 默认数据库：$HERMES_HOME/memory_store.db。
  • 确认状态：hermes memory status（输出 holographic: active）。
  • built-in memory 继续生效，两套并行不冲突。
配置项：
db_path · auto_extract: false · default_trust: 0.5 · min_trust_threshold: 0.3 · hrr_dim: 1024

常用工作流（五步）

1
先写入，再验证：先 add 存事实，再用 search/probe 查回来。
2
先 probe，再扩展：围绕实体看全貌，用 related/reason 继续扩展。
3
先 search，再整理：关键词找到旧记录，决定 update 还是 remove。
4
发现冲突用 contradict：先查矛盾，判断旧事实失效还是新事实需修正。
5
做信任反馈：用 fact_feedback 给 helpful/unhelpful，训练 trust 排序。

9 个 actions + feedback

动作作用典型用法
add新增事实存偏好/约定/工具参数，高价值知识首选。
search关键词检索按词找"chrome / cdp / deploy"等主题。
probe实体召回问"关于这个实体，我都知道什么"。
related结构关联找与某实体相连的周边事实。
reason多实体组合检索找同时与 A、B、C 相关的交集事实。
contradict冲突检测找互相矛盾、时序冲突、版本冲突的事实。
update修订事实事实更正、tags 修订、trust 调整。
remove删除事实清理过时、错误、已失效的记录。
list列出现有事实盘点、审计、清理前检查。
fact_feedback信任反馈helpful → trust +0.1；unhelpful → -0.2 或 remove。

自动镜像机制

内置 memory 工具（memory(action=add/replace, target=user)）写入时，自动触发 on_memory_write() 桥接函数，同步写入 fact_store。

源码位置：agent_runtime_helpers.py:1577-1584
触发条件：内置 memory add/replace 调用
写入字段：target=user → category=user_pref；其他 → category=general

这意味着：你用内置 memory 说"记住我偏好 uv" → 自动镜像进 fact_store，不需要额外操作。

auto_extract 机制

会话结束时（on_session_end）若 auto_extract: true，自动扫描用户消息，用正则提取偏好和决策模式：

  • I prefer / I like / I use / I want / I need... → user_pref
  • my favorite/default X is... → user_pref
  • we decided / we agreed / the project uses... → project
默认关闭：保守策略，避免低质量抽取污染知识库。开启后建议每季度 review 一次自动抽取的内容。

使用技巧

  • 优先写 实体 + 断言 + 条件/时间，后续 probe/reason 更稳。
  • 高价值事实单独存：偏好、约定、配置、决策，不要和任务噪音混在一起。
  • 低置信信息先保守存储，必要时降低 trust，不要直接给 1.0。
  • 实体名保持统一写法；别名太多会让检索变得松散。
  • 事实变更优先 update/remove，不要让冲突版本长期共存。
  • 把 fact_store 当"事实数据库"，不是"聊天备忘录"。

两层记忆怎么分工

Layer A · 内置 Memory

  • MEMORY：环境事实、工具约定、项目规则
  • USER PROFILE：用户偏好、输出风格、长期要求
  • 特点：小、常驻、会话启动时冻结注入 prompt

Layer B · fact_store / Holographic

  • 定位：按需调用的深层事实库，不把所有内容塞进 prompt
  • 能力：全文搜索、实体召回、组合推理、冲突检测、trust 管理
  • 存储：本地 SQLite，跨会话持久化
分工原则：内置 memory = 必须常驻的高价值摘要；fact_store = 可检索、可纠错、可推理的长期事实库。

到底该怎么用

日常写入

  • 最重要、必须常驻的事实 → 写内置 memory

关于 auto_extract：开还是不开

从技术上讲，你可以开启 auto_extract: true，让 provider 在会话结束时自动抽偏好 / 决策 / 项目约定。

优点

  • 省手动写入
  • 适合英文、结构化表达较多的会话

缺点

  • 容易把噪音和半成品表达写进库
  • 中文自然对话不一定适合 regex 抽取
  • 长期会把 fact_store 污染成“半自动垃圾场”
就你当前工作流而言：维持 auto_extract: false 是合理的。你偏好高密度、可控、低噪音，这和保守配置一致。

源码核对出的真实细节

  • on_memory_write() 确实存在，built-in memory 的 add 会镜像进 fact_store。
  • 镜像规则：target=user → category=user_pref；其他 target → general。
  • sync_turn() 在 Holographic 中是空实现：它不是每轮自动把整段对话塞进库，而是更偏向“显式事实存储”。
  • contradict 当前实现更像“全库冲突巡检”，不是严格按某个 entity 过滤。
  • HRR / compositional retrieval 依赖更结构化的事实与实体；不是只开了 provider 就自然变强。
