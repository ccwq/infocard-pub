02
CHAPTER · Loop vs Graph

Loop Engineering vs Graph Engineering

不是谁取代谁，而是适用场景不同。

Loop

一个人转圈

一个 AI 理解任务 → 执行 → 检查 → 修正 → 循环，直到完成。厨师自己包揽一切——切菜、炒菜、调味、装盘。

Graph

一群人接力

多 AI 各管一段，按流程图交接。一个后厨团队——有切配、有炒锅、有打荷、有出菜，每个岗位只干一件事。

临界点

任务复杂度

写一篇文章 → 一个 Loop 够用。做一个产品 → 需要一群 AI 协作。复杂度突破临界点时，Loop 不够用了。

03
CHAPTER · Graph 三要素

Graph Engineering 三要素

节点 + 边 + 状态，构成一张可协作的任务图。

Nodes

节点

一个干活的单元：AI / 工具调用 / 点头的人

Edges

边

决定下一步跑什么：顺序 / 并行 / 按结果走分支

State

状态

节点间共享的信息：每个节点读它、也写它

节点类型

Nodes 可以是什么

  • 一个 AI Agent（Claude Code / GPT-4）
  • 一次工具调用（搜索 / 写文件 / 执行命令）
  • 一个人工审批节点（Human in the loop）
  • 一个条件判断（满足则走 A，否则走 B）
边类型

Edges 可以是什么

  • 顺序边：上一个完成 → 下一个开始
  • 并行边：多个节点同时执行
  • 条件边：根据上一步结果走不同分支
  • 循环边：结果不满足条件 → 回到某个节点重跑
04
CHAPTER · 具体案例

Graph 案例：写一篇深度文章

三个节点，两条边，一个共享状态——最小可用 Graph。

N1

研究节点

搜索资料、整理要点。输出：研究结果写入共享状态。

N2

写作节点

读取研究结果，写正文。输出：草稿写入共享状态。

N3

审阅节点

读取草稿，检查质量。不合格 → 退回 N2；合格 → 完成。

Loop 版本：一个 AI 自己研究、自己写、自己审、自己改，不停循环直到完成。
Graph 版本：研究 / 写作 / 审阅 分属三个节点，各司其职，状态共享，不满意就退回重来。
05
CHAPTER · 何时用 Graph

何时从 Loop 切换到 Graph

不是所有任务都需要 Graph。

翻译文章

Loop 够用

简单、线性、单人可完成

写深度文章

过渡区

研究 + 写作 + 审阅，可分开

做一个产品

必须 Graph

多工种协作、多角色、多阶段

Bug 修复

Loop 够用

理解 → 重现 → 修复 → 验证

舆情调查

过渡区

抓取 + 分析 + 写作 + 核查

端到端产品开发

必须 Graph

产品 / 设计 / 工程 / QA / 运营多节点

06
CHAPTER · 工具与框架

Graph Engineering 工具栈

已有多个框架支持 Graph 范式。

LangGraph

LangChain 生态

基于 LangChain 的 Graph 构建框架，支持状态机、条件分支、循环。

AutoGen

微软 Multi-Agent

多 Agent 协作框架，支持人机混合、群聊模式、代码执行。

CrewAI

角色化 Agent 团队

定义角色（研究员 / 写手 / 审阅），分配任务，按流程执行。

Dify

开源 AI 应用平台

可视化 Graph 构建，支持工作流编排、节点拖拽。

Flowise

低代码 LangChain

拖拽式 Flow 构建，支持 LangChain 所有组件。

自建 Graph

状态机 + 消息队列

完全自控：用状态机定义节点转换，消息队列传递状态，适合深度定制。

07
CHAPTER · Loop 的边界

Loop Engineering 的真实价值

宣告死亡不等于没价值——边界依然清晰。

Loop 优势

Loop Engineering 仍然有效的场景

  • 单一任务、目标清晰（翻译 / 总结 / 润色）
  • 执行路径线性（输入 → 处理 → 输出）
  • 需要快速验证（Prompt 工程 / 小功能）
  • 资源受限（单机、单 Agent）
Graph 优势

Graph Engineering 的真正价值

  • 复杂任务分解（产品 / 舆情 / 报告）
  • 多角色协作（研究员 / 写手 / 审阅 / 主编）
  • 可审计（每节点的输入 / 输出清晰可见）
  • 可复用（Graph 模板，新任务直接套用）
