把原始工具输出存在沙箱，只把结构化摘要注入上下文
Agent 在十几轮工具调用后变慢、变笨、变健忘——根因是 grep 结果、构建日志、API 响应全部挤进上下文窗口。Context Mode 用沙箱机制隔离原始数据，让 LLM 只看到精简后的摘要，token 消耗直降 98%。
01 问题背景：工具输出正在谋杀你的上下文窗口
📈
上下文膨胀
grep 结果、构建日志、API 响应、文件内容——每轮工具调用都在往上下文窗口塞原始数据，十几轮后窗口就被撑爆了。
🐢
Agent 降级
上下文被工具输出淹没后，LLM 开始变慢、变笨、遗忘关键上下文，输出质量断崖式下降。
💸
Token 成本失控
原始工具输出不做过滤直接注入上下文，token 消耗速度极快，预算很快见底。
🔄
Session 无法恢复
Agent 重置或对话中断后，上下文全部丢失，无法从断点继续，重复劳动严重。
02 解法：沙箱化工具输出
核心机制
Sandbox — 原始数据隔离，摘要注入上下文
Context Mode 为每次工具调用建立沙箱：原始工具输出（grep、build、API 响应）存在沙箱中，只有经过结构化提炼的摘要才会被注入 LLM 的上下文窗口。

这意味着 LLM 仍然"看到"工具调用的结果，但看到的是精华版而非原始噪音。
实测效果
-98% Token 消耗
03 三大附带能力
Capability 01
Session 状态恢复
Agent 重置或对话中断后，沙箱中存储的上下文可完整恢复，不丢进度，不丢记忆。
Capability 02
上下文自动过滤
自动剥离工具输出中的噪声（冗长日志、重复内容），只保留决策相关关键信息。
Capability 03
跨 Agent 架构支持
不绑定特定 Agent 实现，适配多种主流 Agent 框架的上下文管理需求。

05 适用场景
🧠
长程 Agent 会话
需要多轮工具调用的复杂任务，上下文窗口被工具输出快速撑满是核心痛点，沙箱化是根本解法。
⚡
大量工具调用的复杂任务
grep / build / API / file read 多类型工具混合调用，每轮都在积累上下文噪音，沙箱化可保持会话始终清爽。
💰
Token 预算紧张
上下文 token 成本高、预算有限时，减少 98% 的工具输出注入可以直接降低使用成本。
🔁
需要 Session 恢复的场景
长时间运行任务、可能被中断的任务，沙箱存储的上下文可随时从断点恢复，无需重来。
