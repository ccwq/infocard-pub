多 Agent vs 单 Agent
实战总结

一句话：单 agent 适合简单任务和需要密集上下文的工作；多 agent 适合需要拆分独立部分的大任务——但你要自己承担编排成本。

Pi 社区 189 Stars 4 大成本 JSON Workflow
核心判断原则

如果单 agent 能持有相关上下文并连贯地完成任务，通常没有理由拆开。多 agent 不是银弹，编排成本是真实的。

Decision Matrix

单 Agent vs 多 Agent

何时选哪种模式 — 实战判断树

✅ 用单 Agent

  • 简单任务、小任务
  • 需要密集上下文
  • 一个 agent 能掌控所有上下文并一致地完成
上下文够用 → 不拆

🔀 用多 Agent

  • 工作独立于主上下文
  • 需要读大量文件
  • 需要广泛探索
  • 大任务可拆成独立部分
边界清晰 → 再考虑拆
⚠️ 多 Agent 的 4 个实际成本
1
上下文转移
一个 agent 不自动知道另一个 agent 知道什么
2
重复工作
边界不清晰 → agent 做重复的事
3
事实验证
不应该不检查就信任 agent 的输出
4
编排
总要有人决定谁做什么、怎么拼在一起
🛠️ pi-workflow — 声明式多 Agent 工作流工具

📌 解决什么问题

把多 agent 工作流标准化为可复用、可验证、可扩展的 JSON spec。用声明式 JSON 描述：何时分拆 → 怎么分配角色 → 在哪里验证 → 怎么拼回来。

声明式

🔑 核心价值

把"多 agent 到底怎么拆"这个问题，从临时决策变成可配置的规范。流程变了？改 JSON 就行，不用重写代码。

可复用
📋 JSON Workflow Stage 模式
模式 用途 运行时形态
single 单一步骤 一个 prompt → 一个子 agent
foreach 动态并发 JSON 数组 → 多个并发子 agent → fan-in 合并
reduce 归并汇总 从多个上游输入聚合为单一输出
support 辅助支持 调用本地辅助脚本（验证/规范化/工件保存）
