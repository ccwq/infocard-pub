05
THE WORKTREE PROBLEM

隔离不是魔法，是目录 + 分支 + 生命周期

Worktrunk 把 Git worktree 的路径、切换、启动、合并和清理收进 wt 命令。

PARALLEL AI AGENT WORKFLOW

让多个 Agent 各自改代码，但别把隔离误当成合并策略

Worktrunk 是面向并行 AI agent 工作流的 Git worktree CLI。它解决的是“多个任务如何同时拥有独立工作目录、如何少记路径、如何在结束时收口”，不是自动判断哪个改动应该合并。分支命名、审查、测试和合并目标仍由人或团队流程负责。

01

按分支定位

使用分支名寻址，路径由模板计算，不必手写三遍 `git worktree add` 的路径。

02

启动即绑定 Agent

wt switch -x claude 可切换后启动命令；参数经 -- 传给 Agent。

03

状态可扫读

wt list 汇总工作区、变更、ahead/behind、CI 和活动标记。

04

生命周期收口

wt merge 可提交、rebase、合并并清理；也可走 PR 流程后再 remove。

05

把重复 setup 放进 hooks

依赖安装、环境文件、测试、开发服务器和缓存复制可按 pre/post 生命周期编排。

阅读原则：先决定“是否需要隔离”，再决定“如何启动”，最后才决定“如何合并和清理”。
01

先判断：你的冲突来自共享目录，还是来自共享决策？

Worktrunk 能隔离文件系统与工作分支，但不会替你解决需求重复、接口冲突或合并优先级。

症状Worktrunk 能解决仍需人工/团队流程
两个 Agent 同时修改同一 checkout每个分支拥有独立 worktree 目录合并后的语义冲突、测试回归
手工记 worktree 路径按分支寻址、路径模板和 shell integration目录规范、磁盘空间和权限策略
多个 dev server 端口冲突hash_port 模板可生成分支稳定端口应用是否真正读取该端口、外部依赖是否可并行
任务结束后目录堆积wt remove 或 merge 后自动清理未合并改动是否可删除、产物是否已归档
本仓库边界：本信息卡项目不使用 Git worktree；这里介绍的是外部工具的适用场景，不代表当前发布链路采用它。
02

安装与第一次切换：先让 shell 能切目录

官方安装方式覆盖 macOS/Linux、Windows、Arch 和 Conda/Pixi；shell integration 是目录切换生效的关键。

# macOS / Linux：Homebrew brew install worktrunk && wt config shell install # Rust 用户：Cargo cargo install worktrunk && wt config shell install # Windows：避免 wt 与 Windows Terminal 别名冲突 winget install max-sixty.worktrunk git-wt config shell install # Arch Linux sudo pacman -S worktrunk && wt config shell install
01

进入已有 Git 仓库

在目标仓库运行命令；不要在非仓库目录期待分支状态可用。

02

创建隔离任务

wt switch --create feature-auth 创建分支与 worktree 并切换目录。

03

回读状态

wt list 查看当前标记、未提交变更、ahead/behind 和路径。

验收标准：命令结束后，当前 shell 位于新 worktree；wt list 能看到新分支；在其中创建的文件不会出现在主 worktree 的工作树里。
03

并行启动：给每个 Agent 一个任务，不要让它们共享 cwd

`-x` 负责切换后执行命令；多个任务要使用不同分支名，并在合并前各自完成验证。

# 启动三个独立任务 wt switch -x claude -c feature-a -- 'Add user authentication' wt switch -x claude -c feature-b -- 'Fix the pagination bug' wt switch -x claude -c feature-c -- 'Write tests for the API' # 如果要接 Codex / 其他 Agent，直接运行对应 CLI wt switch --create feature-docs codex # 状态查看 wt list wt list --full

Claude Code

官方插件可通过 wt config plugins claude install 安装；Worktrunk 可接管 Claude 的 worktree lifecycle hooks。

Codex

插件支持活动追踪和配置 Skill；文档说明 Codex 没有可改变会话 cwd 的 worktree isolation hook，因此仍需直接使用 wt switch / wt remove。

活动标记

wt list 可显示 Agent 工作/等待标记；进程被强杀可能留下 stale marker，需要手工 clear。

04

配置 hooks：把可重复 setup 变成项目级契约

用户配置与项目配置职责不同：个人路径/提交生成在用户侧，团队 hooks 在仓库的 `.config/wt.toml`。

# ~/.config/worktrunk/config.toml worktree-path = ".worktrees/{{ branch | sanitize }}" # .config/wt.toml（可提交、团队共享） [pre-start] deps = "npm ci" [pre-merge] test = "npm test" # 后台启动开发服务器 [post-start] server = "npm run dev -- --port {{ branch | hash_port }}" # 预览 hook，不执行 wt hook pre-start --dry-run
Hook时机失败/并发语义
pre-start新 worktree 创建时阻塞后续启动；适合安装依赖、生成 env
post-start新 worktree 创建后后台执行；适合 dev server、watcher、长构建
pre-commitWorktrunk 提交前格式化、lint、类型检查；失败阻止提交
pre-merge合并前测试、安全扫描、构建验证；失败阻止合并
post-remove删除 worktree 后停服务、清容器、通知；不要假定被删目录仍存在
05

合并与清理：选择 PR 流程，或让 wt 合并到目标分支

“一键合并”仍有明确前提：分支可审查、测试已跑、目标分支正确、未提交改动的处理策略已知。

PR workflow

wt step commit → gh pr create → 在 GitHub/GitLab 合并 → wt remove。适合需要 review、CI 和审计的团队。

Local merge

wt merge main 可按配置提交、rebase、fast-forward/merge，并在成功后清理源 worktree。

保留现场

需要继续检查时使用 --no-remove 或相应配置，避免合并后立即删除仍有价值的调试现场。

# PR 路径 wt step commit gh pr create # review + CI + merge 完成后 wt remove # 本地路径（示例） wt merge main # 只看帮助，不执行工作流 wt merge --help wt remove --help
06

缓存、端口和可观测性：便利功能也有平台边界

Worktrunk 的体验增强依赖文件系统、shell 和 Agent hook；不能把 README 的功能描述当成每台机器的保证。

共享编译缓存

wt step copy-ignored 可在 APFS、btrfs、XFS 等文件系统共享/复制忽略文件；具体行为需按你的文件系统和构建工具实测。

独立端口

{{ branch | hash_port }} 生成稳定端口，但应用启动脚本必须消费该变量；端口分配不是网络隔离。

CI / 活动状态

wt list --full 可展示 CI 状态和摘要；活动标记由插件/生命周期事件维护，异常退出可能残留。

验证动作：第一次启用 hooks 时先运行 wt hook <type> --dry-run，查看实际展开命令；项目命令首次执行需要 approval，变更后的命令会重新要求批准。
07

安全与许可证：隔离目录不等于隔离权限

Worktrunk 会执行 hooks、调用 Agent 和 Git 操作；项目配置应当像代码一样审查。

风险点官方机制使用前动作
项目 hook 执行任意命令首次执行要求 approval；命令变化需重新批准先 dry-run，逐条审查命令与写入路径
Agent 读写范围每个 Agent 进入自己的 worktree仍要审查 Agent 权限、网络、凭据和共享服务
合并自动清理merge 默认可 remove worktree/branch确认未提交改动、日志、构建产物已留存
端口/缓存共享模板和 copy-ignored 提供便利确认不会泄露本地数据或复用错误环境
代码再分发MIT OR Apache-2.0，二选一保留对应许可证和归属/NOTICE 要求
不适合：你明确禁止 worktree、仓库流程要求单一 checkout、磁盘空间不足、或团队还没有分支审查和清理规则时，不要因为“多 Agent”三个字就引入 Worktrunk。

结论：先隔离冲突，再建立合并纪律

WORKFLOW VERDICT / USE WITH EXPLICIT BOUNDARIES
  • 适合同时推进互不依赖的前端、测试、文档或修复任务。
  • wt list 是状态入口，wt hook --dry-run 是配置入口，wt merge/remove 是收口入口。
  • PR review、CI、凭据边界和删除前归档仍不可省略。
  • 本卡只介绍外部 Worktrunk；当前 infocard 项目不使用 Git worktree。
