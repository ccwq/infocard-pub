BACKGROUND

背景挑战：成本优化的真正来源

❌ 传统误区

AI 编程贵 = 模型单价贵

认为只要换用更便宜的模型，或等待模型降价，就能解决 AI 编程成本问题。

✓ 核心真相

成本堆积在流程设计里

Agent 交接时反复读取并加载相同庞大上下文（git diff、终端输出），后续每步都挂在上下文里持续计费。单次推理便宜，但流程重复搬运才是无底洞。

WORKFLOW

系统基础流程：5 阶段卡片流

阶段 角色 核心动作
① Brainstorming Agent 追问目标 / 边界 / 风险 / 验收，形成设计文档
② — git worktrees 隔离环境，初始化脚本，建基线测试
③ — 编写含文件路径 / 接口测试 / 命令 / 预期结果的 Plan，每步 2-5 分钟微动作
④ Controller + Subagent TDD 红-绿-重构，Controller 派发上下文受限的 Subagent
⑤ Task Reviewer Spec compliance + Code quality 双轨审查，分支 / PR 完整测试
1

确定性物料脚本化

Script deterministic artifacts — 禁止模型用上下文窗口现查确定性信息
↑50% 提速 · -10% Token
PROBLEM

上下文携带终端输出

Reviewer 在上下文内自主运行 git log/diff，庞大的终端输出被后续对话反复携带，每次都重新计费。

SOLUTION

脚本预生成 Review Package

脚本自动生成 review package（含 commit list、变更统计、上下文 diff），Reviewer 只读文件路径，禁止大模型用上下文窗口现查确定性信息。

DERIVATIVE

Task Brief 机制

Controller 不反复喂完整 Plan，脚本抽成简短 brief 文件供 Subagent 读取。减少重复传输，Subagent 按需主动拉取。

关键原则：确定性信息 → 脚本预生成；Agent 只读文件路径，不现查
2

审查角色合并 + 边界防爆

Merge reviewer roles + enforce task boundary with cannot-verify warnings
单次 Diff 读两遍 → 一遍搞定
BEFORE

Spec Reviewer + Quality Reviewer 分立

两个独立 Reviewer 分别读 Diff，各跑各的推理轮次，重复计算翻倍。

AFTER

合并为 Task Reviewer

读一次 Diff 同时返回 Spec 合规 + Code Quality 两个裁决，减少一次完整 Diff 读取。

INNOVATION

"Cannot verify from diff" 警告状态

需求跨越多任务时，Reviewer 主动承认"看不见"，标为警告交由 Controller 裁决，维护任务边界，防止越界扩散。

诚实承认盲区，比假装能看见更能守住边界
3

模型按任务形态分层路由

Route models by task shape — 机械执行用便宜模型，判断密集用高阶模型
按需选模型
机械执行型

Plan 已完整，仅转写 / 跑测试 / 修小错

不需要推理判断，只是按指令执行已知步骤，用低成本便宜模型。

判断密集型

多步推理 / 架构边界 / 跨文件契约 / Plan / Review

需要强推理能力、跨模块判断、架构级决策，用高阶闭源模型。

ENGINEERING RULE

每次 Dispatch 必须显式声明 Model

防止 Harness 默认继承最贵模型——即使选错了便宜模型，也能快速回退；但若默认用贵模型，每轮都多付钱。

模型声明 = 成本感知的第一步

模型分层路由矩阵

任务类型 特征 推荐模型层级 示例场景
机械执行型 Plan 已完整，仅转写 / 跑命令 / 修小错 低成本便宜模型 执行 git 命令、转写注释、补全测试用例

三个反向恶化的负面实验

INSIGHTS

三条工程启示

01

看上下文流动，不只看模型报价表

连续工作数小时的成本优化，不能只看模型报价表，要看上下文的流动和证据的交接——重复搬运才是最贵的。

02

删锚点要谨慎，锚点是质量下限

优化要删重复信息 / 废话，但不能粗暴砍掉测试信号、接口定义、任务边界、全局约束等核心锚点——它们是质量下限。

03

便宜模型多绕几轮可能更贵

AI 编程已从单纯的模型选择题，变成了硬核流程与软件工程问题——流程设计失误比选错模型代价更大。

FAQ

常见问题

Q: Superpowers 适合小团队吗？

A: 适合 2 人以上的开发团队，单人开发者可能感受不到多 Agent 交接带来的上下文冗余问题。

Q: 成本优化 60% 是怎么测出来的？

A: Fable 用 AI 审计自己的 25 个实验，在相同任务下对比优化前后的 Token 消耗和运行时间。

Q: 哪些任务类型适合用便宜模型？

A: Plan 已完整、只需机械执行（转写 / 跑命令 / 修小错）的任务。判断密集、跨文件推理类任务不要省。

Q: "Cannot verify from diff" 警告有什么价值？

A: 让 Reviewer 主动承认盲区，比让 Controller 收到错误裁决再返工更高效，维护了任务边界。

Q: 压减 Plan 字数为什么会 -62% 性能？

A: Plan 是后续所有 Agent 的锚点——测试信号、接口定义、任务边界都被砍掉，后续只能靠猜，信息损失远超字数节约。

Q: Superpowers 和 Cursor / Copilot 的区别是什么？

A: Superpowers 是工作流框架而非 IDE 插件；它定义了完整的 Agent 角色分工和交接协议，更适合大型代码库的多 Agent 协作。
