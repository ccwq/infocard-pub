Defending Code Reference Harness：把 Claude Code 变成可验证漏洞发现流水线

Anthropic 的开源参考实现不是一个“一键扫描器”，而是把 threat model、静态扫描、triage、report、patch 串成可迁移的团队工作流；它默认面向 C/C++ memory vulnerabilities，用 ASAN 和 gVisor 把发现、验证、修复分层。

它到底是什么：一个可迁移的安全工作流底盘

这张卡先回答“这东西的本质是什么”，再回答“它交付什么”，最后回答“谁该用、谁别碰”。

定位reference

它不是产品，是 reference implementation

仓库自己写明：这是一份参考实现，不是要开箱即用的产品，也不接受新的贡献。

它来自 Anthropic 与安全团队合作后的经验沉淀，目标是把方法论变成工程模板。

  • 适合学习、二次开发与自建流水线
  • 不要把它当成成熟 SaaS 的替代品
skillsworkflow

它交付的是一组 Claude Code skills

README 的入口非常明确：/quickstart、/threat-model、/vuln-scan、/triage、/patch、/customize。

互动 skills 只读写文件；真正的自治流水线则会进入独立沙箱。

  • 先从 threat model 和静态扫描开始
  • 再把 triage 与 patch 串起来
pipelineASAN

它解决的是流程，不是单点模型

核心价值是把“发现 → 验证 → 去重 → 报告 → 修复”组织成一个可复用的团队系统。

默认面向 C/C++ memory vulnerabilities，使用 ASAN 作为 crash detector。

  • 适合多阶段、多代理、可验证的安全工作
  • 不适合把简单脚本硬塞进团队工厂
boundaryClaude Security

它有清晰的边界和邻居

如果你要的是 managed option，Anthropic 另有 Claude Security 托管产品。

要移植到别的语言或漏洞类，重点改的是 detector、target Dockerfile、prompt 与 grader。

  • 不是万能漏洞扫描器
  • 更像一条可以迁移的安全工作流底盘
02

架构总览：七段式流水线怎么走

官方 pipeline 把问题拆成 build / recon / find / grade / judge / report / patch 七段；judge 在 stream 模式下更关键，patch 阶段则带一条可执行的验证阶梯。

01

Build

Docker + ASAN

先把目标构建成可重复的镜像，确保后续 agent 在同一环境里看同一份代码。

↓
02

Recon

可选的攻击面切分

先拆分子问题，避免所有 agent 都扎堆同一个 bug。

↓
03

Find

并行发现崩溃

多个 agent 在隔离容器里造输入、跑崩溃，直到同一 crash 3/3 可复现。

↓
04

Grade

fresh container 复验

把 PoC 送到新容器里复跑，确认不是噪声、资源耗尽或偶发性问题。

↓
05

Judge

stream 模式去重

把新发现与已知 bug 对比，决定是新问题、替代样本还是重复项。

↓
06

Report

exploitability analysis

生成可利用性分析，说明可达性、影响面和可能的升级路径。

↓
07

Patch

验证阶梯

修复后跑 build / reproduce / regress / re-attack，确认不是“刚好没崩”。

Build + Reconsetup

先把攻击面说清楚

Build 负责把 target 做成带 ASAN 的镜像；Recon 可选，作用是把大问题拆成多个可并行探索的子区域，避免所有 agent 都扎堆同一个 bug。

Find + Gradeverify

再把崩溃变成可复验事实

Find 在隔离容器里做输入生成和崩溃发现；Grade 则在 fresh 容器里复验 PoC，确认不是噪声、资源耗尽或偶发性问题。

Judge + Report + Patchdedupe

最后把发现变成可读、可修、可回归验证的结论

Judge 用来去重与收敛；Report 写可利用性分析；Patch 则爬 build / reproduce / regress / re-attack 的验证阶梯，确认修复不是“刚好没崩”。

03

安全边界：哪里能直接用，哪里必须进沙箱

这个仓库的安全设计不是装饰项，而是工作流的一部分。边界写对了，模型才能在允许范围内发挥。

saferead/write

互动技能是低风险层

README 明确区分了互动 skills 与自治 pipeline。/quickstart、/threat-model、/vuln-scan、/triage 只读写文件。

这类命令适合先把问题边界定义清楚，再决定要不要进入自治执行。

  • 不需要 sandbox 才能跑
  • 适合先做 scoped exploration
gVisoregress

自治流水线必须进 gVisor

真正执行 target code 的那部分必须通过 bin/vp-sandboxed 启动。

每个 agent 都在 gVisor 容器中运行，网络 egress 只允许到 Claude API。

  • 不要用普通 Docker 当隔离替代
  • 不要开 privileged / host network
boundarypolicy

安全边界要写进代码，不要只写进 prompt

README 和 security.md 都强调：约束必须在代码中强制，而不是让模型“自己记得”。

不要把凭据目录、外部写权限或不受信任的 MCP / plugin 接进 agent 世界。

  • 不要挂载 ~/.aws、.env 之类凭据路径
  • 不要让 agent 直接触达生产写接口
Constraints must be enforced in code, not in prompts.这句是整个仓库安全观的核心：不要期待模型自觉遵守边界；要让程序和隔离环境先替你把边界钉死。
04

怎么上手：先互动，后自治，再迁移

README 给的是很现实的路线：先在 canary 上理解流程，再上自治 run，最后才是 port 到自己的语言 / 漏洞类 / build 系统。

interactivefiles only

先用互动 skills 把问题定义住

# 互动技能：先做约束，再做扫描
> /quickstart
> /threat-model bootstrap targets/canary
> /vuln-scan targets/canary
> /triage targets/canary/VULN-FINDINGS.json
> /patch ./TRIAGE.json --repo targets/canary

这组命令适合做 threat model、scoped scan 和 triage；它们是理解问题的入口，不是最终的自治执行层。

autonomous runsandboxed

真正跑 target 时，一定走 sandbox

# 自治流水线：先搭 sandbox，再跑 target
python3 -m venv .venv && .venv/bin/pip install -e .
./scripts/setup_sandbox.sh
export ANTHROPIC_API_KEY=***
bin/vp-sandboxed run drlibs --model <model-id> --runs 3 --parallel --stream --auto-focus
bin/vp-sandboxed patch results/drlibs/<timestamp>/ --model <model-id>

这一步才会真的编译、运行 target 并进入 agent 协作；默认设定是 gVisor + 限制 egress。

customizeporting

要迁移到别的语言 / 漏洞类，改哪些地方

customizing.md 把 C/C++ + ASAN 的特化点拆得很清楚：find / grade prompt、report / patch prompt、crash signature、target Dockerfile。

也就是说，编排框架本身相对通用，变化主要集中在 detector 和目标栈。

  • 改 detector 与 crash 识别
  • 改 target Dockerfile 与 build/test 命令
  • 改 prompt 与 grader 的漏洞语义
day-1day-2+

一条更现实的使用路径

先在 canary / 最小样例上跑通 Day 1 的 threat model → static scan → triage。

再上 Day 2 的自治 run，最后才是 Day 3-5 的 target porting。

  • 不要一开始就追求全自动
  • 先验证 pipeline 的可解释性与可复验性
05

适用场景与资源路径

如果你要的是可重复的安全能力，这套东西很值；如果你只要一个简单 scanner，它就显得重了。

适合repeatable

适合谁

你需要一条可重复的安全工作流，而不是一个单次扫描脚本。

你关心的是发现、验证、去重和修复是否能被流程化、团队化。

  • 安全研究团队
  • 需要代理协作的工程团队
  • 想把漏洞发现做成底层能力的组织
不适合managed

不适合谁

如果你只是想要一个简单、确定性的 scanner，或者只是写一段一次性脚本，这套 harness 就偏重了。

如果你需要托管版能力，README 直接提示可以看 Claude Security。

  • 一次性、单脚本、低复杂度任务
  • 不需要多阶段验证的轻量流程

06

最终结论

这类开源参考实现的价值，不在于“能不能直接上线”，而在于它把一个高风险安全工作流，拆成了可以验证、可以迁移、可以团队协作的工程结构。

如果你要的是“团队化漏洞发现能力”，它值得参考；如果你要的是“托管版能力”，看 Claude Security；如果你要把它移植到自己的栈，先从 threat model 和 sandbox 边界开始。不是黑盒产品，而是可迁移的安全流水线模板。
