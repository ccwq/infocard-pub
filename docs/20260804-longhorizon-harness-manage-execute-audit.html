LONG-HORIZON AGENT · STATE HARNESS

别让长程 Agent 的状态
跟着上下文一起腐烂

LongHorizon-Harness 把执行、状态与验收拆开：每一轮都用新上下文做事，只有独立审计通过的结果，才会进入下一轮的可信状态。

它不是新模型，也不替代 Codex / Claude Code；它是在现有 Agent 外层加上一套“状态可验证、进度可恢复”的长任务控制面。

01 · FAILURE MODE

长程任务最怕的，不是“做错”，而是“把做错写成事实”

传统单会话 Agent 往往让同一段不断增长的上下文同时承担计划、执行、记忆与自我验收。一旦未验证的判断进入记录，后续行动会沿着错误前提继续：目标漂移、重复尝试、过早放弃，都会被累积上下文放大。

LongHorizon-Harness 的处理不是让模型“更聪明地回忆”，而是把任务状态移出执行过程，变成必须由环境证据更新的外部对象。

02 · MEA LOOP

三种角色，一份可信状态

01

Manager

保存原始目标、已证实完成项与下一子任务；它管理进度，但不把主观判断直接固化成事实。

02

Executor

每轮以 fresh context 开始，针对一个明确子任务执行，避免把历史噪声无限带入下一轮。

03

Auditor

以只读方式检查文件、界面、日志和测试；未通过就保留已验证进度，回到待解决部分。

官方仓库架构图：Manager / Executor / Auditor 通过经验证的外部状态衔接，而非依赖单一增长上下文。

04 · ONE CONTINUOUS TASK

浏览器、终端、桌面软件，仍可被视为同一件事

仓库将 GUI 与 CLI 工作流描述为同一连续任务：可以在浏览器开始，转到终端处理代码或数据，再进入桌面软件产出成果，最后回到终端验证。跨工具时，目标、已验证进度和证据仍归入同一状态系统。

🌐 GUI 操作点击、输入、滚动、表格、文档、设计软件等。
⌨️ CLI 执行写改代码、运行脚本、配置环境、诊断与调试。
↻ 可恢复推进失败或换上下文后，从已验证进度继续，而不是重述整段历史。
实现边界：GUI 交互不是该项目默认内置能力；仓库要求接入一个兼容的外部 computer-use MCP server。没有该配置时，Claude Code adapter 不会自动加入 MCP 参数。
05 · FIT / NOT FIT

把它当作长任务控制面，而不是万能 Agent

适合关注
  • 跨多轮、跨工具、需反复验证的复杂任务
  • 不希望执行者同时充当唯一记忆和验收者
  • 希望对每轮计划、结果、审计证据和返工原因可追溯
不要误解
  • 它不训练新模型，也不替代底层 Agent
  • 它不证明所有任务都能获得同等 benchmark 增益
  • 它不自动提供 GUI 权限或外部 computer-use 服务
