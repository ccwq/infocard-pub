01 / 核心判断

read first
关键结论

book-to-skill 的定位不是 RAG。它走的是编译时结构化：先把书提炼成框架、术语、模式与反模式，再按需加载章节，而不是每次对话临时检索片段。

为什么它成立

它把“读过但很快忘”的书，变成能在工作流里反复调用的知识资产。每章只在需要时加载，避免把整本书一次性烧进上下文。

为什么它比“全文搜索”更像技能

输出不是文本块，而是可直接使用的结构：SKILL.md、章节文件、glossary、patterns、cheatsheet。

02 / 技术栈与提取链

pipeline
PDF（技术书）
优先 Docling，保留表格与代码块；技术场景更适合结构化读取。
PDF（文本书）
pdftotext → PyPDF2 → pdfminer.six，速度更快，适合以正文为主的书。
EPUB / DOCX / HTML / RTF
分别走 ebooklib、python-docx、BeautifulSoup、striprtf 等分层兜底，兼顾质量与可用性。
输出
`SKILL.md`、章节文件、`glossary.md`、`patterns.md`、`cheatsheet.md`。
/book-to-skill <path-to-document> [skill-name-slug] # 示例 /book-to-skill ~/books/clean-code.pdf /book-to-skill /tmp/ddd-evans.pdf domain-driven-design

03 / 为什么值得装

value

适合

你想把一本技术书真正“带进工作流”；你希望作者的框架能在写代码、做方案时随手调用；你不想每次都重新翻 PDF。

不适合

你需要跨很多本书一起检索，或者只想做简单全文搜索。那类场景更偏检索，不偏编译。

04 / 证据与边界

facts
GitHub
星标约 2.8k，Fork 364，说明这个方向已经被大量技术用户验证过。
核心差异
它回答的不是“这页讲了什么”，而是“这本书沉淀了哪些可复用框架”。
边界
它不是万能知识库，也不是搜索引擎；强项是单本书的结构化吸收与复用。
