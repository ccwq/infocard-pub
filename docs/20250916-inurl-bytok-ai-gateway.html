Pain Point · 痛点

你以为在用「聚合工具」，实际上在用 Relay（中转）平台：

你把 API Key 交给平台 → 平台代替你调用提供商 → 提供商看到的是平台的 IP + 平台的身份。

大量聚合工具用 Relay 模式却不告诉你，导致你的 Key 被共享 IP 池拖累，遭遇高封号风险。

BYOK（Bring Your Own Key）AI 模型融合平台。密钥在本地加密保管，Agent 直接调用提供商，平台完全不在调用链路中。统一 Token（Bearer byok_live_xxxx...）仅用于本地 Agent ↔ 控制台鉴权，从不出现在对提供商的请求中。

Anti-Ban · 抗封号原理
BYOK 为什么能避免封号
🌐
你的 IP
IP 地址属于你
🔑
你的 Key
密钥由你持有
🆔
你的身份
提供商识别你

Relay 模式：提供商看见平台 IP 段 + 平台账户，所有用户共享身份，一旦有人违规整个 IP 段被封。
BYOK 模式：提供商看见你的真实 IP + 你的真实 Key，每个用户独立身份，互不影响。

Self-Test · 自测清单
3 个问题识别 Relay 平台
1
是否要求你把提供商 Key 粘贴到其 Web 后台，无任何本地组件？
2
文档是否让你把请求发到其公开域名，而非本地地址？
3
是否从不提「本地 Agent / 直连」，只说「我们帮你转发」？
🔴 3 题中 2+ 题回答「是」→ 该平台是 Relay，不要用于生产环境
Selection · 选型三问
评估任何聚合工具时必问
❓ 调用从哪台机器发出？
如果不是「你的机器 / 你的 Key 直连」，生产环境不要用
❓ 平台能否看到我的 Key？
只有「云端只看见密文，主密钥在本地」才可信
❓ 统一 Token 会出现在哪？
如果出现在对 provider 的请求里，仍然是中转
