01
FACT CHECK

数字澄清：42 不成立，规模要带统计口径

把不确定性写进卡片，比用一个看似精确的数字制造确定性更可靠。

一手核查结果

  • Hermes 内置目录：73 个 SKILL.md。
  • Hermes 可选目录：103 个 SKILL.md。
  • 合计可写作约 170+；事实包记录的文件计数为 176，但应注明统计对象与时间。
  • Addy Osmani agent-skills：24 个技能。

为什么不写“42 个”

“42 个 Skills”无法从任一项目的一手来源独立证实。它只在第三方传播线索中出现，不能反推项目实际规模，也不能作为卡片结论。

稳健表达模板：“截至核查日，Hermes 的内置与可选目录合计约 170+ 个技能；精确数字取决于是否计入全部 SKILL.md、子目录与索引缓存。”
02
TWO AXES

两条组织轴线：领域地图 vs 生命周期

没有唯一正确的分类法；关键是让用户在任务发生时找到正确的能力。

HERMES AGENT

按领域与场景铺开

内置与可选技能放入 creative、mlops、finance、research、software-development 等分类目录，适合覆盖广泛任务面。

发现路径：领域 → 子目录 → Skill

按软件交付生命周期串联

围绕 Define → Plan → Build → Verify → Review → Ship 组织技能，把工程纪律嵌入从想法到交付的连续流程。

03
PROGRESSIVE DISCLOSURE

YAML frontmatter + 三层渐进加载

先用短元数据做路由，再按需展开正文，最后读取引用资料。

01 · 索引name + description
启动时预加载
02 · 判定Agent 判断与当前任务相关
03 · 正文读取 SKILL.md 主体
04 · 选择定位 references/、scripts/、templates/
05 · 执行按步骤完成工作流
06 · 验证用检查清单收口
# 最小可发现单元
---
name: requesting-code-review
description: Pre-commit review...
version: 2.0.0
license: MIT
metadata.hermes.tags: [review, security, verification]
---

为什么是三层

  • 第一层减少启动上下文负担，承担路由。
  • 第二层保存可执行的完整工作流。
  • 第三层把长清单、脚本、模板按需拆出，降低噪声并支持复用。

05
DESIGN PHILOSOPHY

设计哲学：核心收窄，能力外置，技能必须能执行

技能不是知识目录的换皮，而是带触发条件、动作步骤和验证出口的工作单元。

核心收窄

Hermes 的贡献准则强调：核心是 narrow waist，能力生活在边缘；新增能力优先以 CLI 命令、技能、受控工具或插件提供，而不是不断扩张核心工具面。

工程托底

Addy Osmani agent-skills 把规格、拆解、测试、评审和交付串成阶段流程，让“能运行”与“可安全上线”之间有可执行的工程门槛。

持续积累

Hermes 的定位包含从经验创建技能、在使用中改进技能，并跨会话沉淀知识；组织系统因此要支持版本、关联、审计与复盘。

06
RISK BOUNDARY

风险边界：数量、来源与可执行性都要可追溯

一张方法论卡不应把统计推断、第三方线索或未验证页面写成事实。

发布前必须保留的边界

  • “42 个 Skills”无法从一手来源核实，不作为项目规模结论。
  • “约 170+”是谨慎表达；若写 176，必须同时说明它是对 SKILL.md 文件的特定统计，且索引缓存不是独立技能。
  • 安装命令、目录结构、YAML frontmatter、三层加载与两条组织轴线，仅引用事实包列出的一手项目资料。
  • 技能内容应区分“可发现元数据”“可执行步骤”“按需参考资料”，避免把参考文档误当作执行流程。
  • 本卡不对未能抓取的外部页面作数字推断，也不把第三方传播线索写入成品。
