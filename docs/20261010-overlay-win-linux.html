普通目录里的跨平台 Overlay 文件系统
Windows + Linux 任意程序透明访问 ⚠ 结论未经验证
可以用普通目录保存底层（lower）和修改层（upper），再将合并视图挂到目录路径。要兼容 Windows 与 Linux，建议共享叠加逻辑，分别接入 WinFsp 与 FUSE。本文是文档调查与设计建议，未在两套系统实测。
⚡
结论：Linux 即用 OverlayFS / fuse-overlayfs；跨平台产品路线是 cgofuse + WinFsp 建立原型 → 共享叠加核心 → 可移植元数据。两套系统若必须复用同一修改层，统一格式列为第一阶段要求。
A 先区分三个要求

Overlay 包含三项核心语义：目录合并（同一路径显示上层版本）、copy-up（修改底层文件时复制到上层再写）、删除遮罩（删除只在上层留标记）。先确认这三个需求各自的实现条件。

要求 能否实现 条件
lower、upper 都是普通目录 ✓ 可以 不需要专门划分磁盘分区
merged 看起来是普通目录路径 ✓ 可以 实际由挂载提供文件系统视图
任意程序透明访问且完全免系统组件 ✗ 未找到完整方案 可考虑复制工作区，代价是失去透明叠加

重要区别：挂到普通目录路径，不等于没有挂载。

操作系统需要将 open、read、write 等请求交给叠加实现。应用内 VFS 只能服务接入该接口的程序。

B 目录如何组织
workspace/ base/ ← lower：原始文件，叠加服务不写入 changes/ ← upper：新增文件和修改后的完整文件 meta/ ← 自建方案的删除标记、事务与格式版本 merged/ ← 应用访问入口，由挂载呈现

Linux 内核 OverlayFS 另外需要 work/；自建方案是否需要临时工作目录由实现决定。不要把 base、changes 或元数据放进 merged，避免递归访问。

操作basechanges / metamerged 结果
读取 a.txt 原文件 无变化 读取原文件
修改 a.txt 原文件不变 copy-up 后写修改版 显示修改版
新建 b.txt 无变化 新文件 显示新文件
删除 a.txt 原文件不变 删除遮罩 不显示 a.txt

常见遗漏："只检查 upper 是否存在，否则读 lower"只能覆盖部分读取逻辑。真实实现还需检查祖先目录、类型冲突、删除遮罩与目录不透明标记。上层文件也应遮住底层同名目录及其后代。

C 方案选择与证据
方案 Linux Win 原生 定位
Kernel OverlayFS ✓ ✗ Linux 即用
fuse-overlayfs ✓ ✗ Linux 用户态
cgofuse + 自建叠加核心 ✓ ✓ 跨平台开发候选
rclone union + mount ✓ ✓ 合并目录视图
HUBFS ✓ ✓ 架构参考
Windows ProjFS ✗ ✓ Win 专用

证实事实：cgofuse 提供 Windows 和 Linux 的 FUSE 接口。Windows 依赖 WinFsp，Linux 使用 libfuse。它不是开箱即用的 overlay 产品。其 Passthrough 示例明确排除 Windows，不能直接照搬。

可行性证据：HUBFS 使用上述跨平台组合。它将本地可写层叠在只读 Git 内容上，允许编辑和构建。这证明架构可行，但不证明其接口可直接挂任意本地目录。

设计判断：若两套系统要共用实现和修改层格式，优先考虑自建核心。若只要求功能类似，可使用 Linux 专用实现和独立 Windows 后端。

D Linux 如何立即验证

以下示例使用 ext4 等满足条件的本地底层文件系统。将 alice 换成实际用户名。

# Linux 内核 OverlayFS · 示例命令，未执行
mkdir -p /home/alice/ovl/{base,upper,work,merged}
sudo mount -t overlay overlay \
  -o lowerdir=/home/alice/ovl/base,upperdir=/home/alice/ovl/upper,workdir=/home/alice/ovl/work \
  /home/alice/ovl/merged
# 之后只通过 merged 读写工作区
sudo umount /home/alice/ovl/merged

upper 与 work 必须位于同一底层文件系统；work 使用空目录。upper 需支持扩展属性与有效 d_type。挂载期间不要绕过 merged 修改 lower 或 upper。

# fuse-overlayfs · 已安装并允许 FUSE 时
fuse-overlayfs \
  -o lowerdir=/home/alice/ovl/base,upperdir=/home/alice/ovl/upper,workdir=/home/alice/ovl/work \
  /home/alice/ovl/merged
fusermount3 -u /home/alice/ovl/merged

这条路线仍是 Linux 方案，不能把同一个程序带到 Windows 原生使用。

能否运行取决于 /dev/fuse、挂载辅助程序与系统策略，不等于零安装。

E Windows 怎样落地

建议布局为 C:\ovl\base、C:\ovl\changes、C:\ovl\meta。入口为 C:\ovl\merged。安装 WinFsp 后，叠加服务负责挂载入口和处理文件请求。

数据流：任意应用 → merged 路径 → 平台适配层（FUSE/WinFsp）→ 共享叠加核心 → base 目录 / changes + meta

WinFsp 约束：它通过 NTFS mountpoint reparse point 挂载目录。不能覆盖已有非空目录，挂载目录由服务创建，卸载时删除。工程上应预留不存在的 merged 子路径，保留已存在的父目录。

不要将正在存放 base 文件的目录直接当作入口。要保留原路径，可在停用后将原内容移到单独的 base，再把原路径留给挂载；需要先处理占用该目录的程序。

F 自建时必须实现什么

以下是建议的可移植语义规格，不是对 cgofuse 已有能力的声明。

操作核心规则最容易遗漏的情况
路径查找 检查遮罩、祖先类型；上层优先 上层文件遮住下层目录
目录枚举 合并子项，去重，排除遮罩 大小写冲突及 opaque 目录
修改底层文件 copy-up 后只写上层 并发首写、权限、时间戳
删除文件 删除上层副本；必要时遮住底层 上层移除后底层重新出现
删除并重建目录 处理目录遮罩与 opaque 状态 重建后旧底层子项复活
rename 同步处理源路径遮罩和目标覆盖 底层目录重命名、崩溃中断
持久化 临时文件、提交顺序、恢复机制 数据与元数据只有一方提交
文件句柄 定义 copy-up 前后句柄一致性 锁、mmap、删除中的打开文件

建议用独立 meta 目录记录 whiteout 与 opaque。记录逻辑路径、元数据版本和事务状态。元数据不可在 merged 中泄漏。

若要 Windows 与 Linux 复用同一状态，不应直接把内核 OverlayFS upper 当通用格式。其删除状态依赖特殊节点或扩展属性。

copy-up 通常以文件为单位。实现时应评估大文件首写的复制成本。文件级叠加不自动提供块级增量存储。

G 兼容性如何验收

"同一代码能编译"不能证明任意应用都正常。建议先选定目标应用，再按其操作验收。

检查项预期结果
修改 lower 文件后卸载base 哈希不变，修改在 upper
删除 lower 文件后重挂文件仍被隐藏
删除 upper 覆盖版本lower 版本不会意外复活
删除并重建目录旧 lower 子项不自动出现
编辑器临时文件替换保存内容完整，rename 行为正确
两个进程首次写同一文件无丢失更新或半份副本
copy-up 或 rename 时强制停止服务重启后恢复到定义好的状态
文件名只差大小写按统一策略拒绝或正确区分
Git、构建器、文件监听器权限、锁、通知符合实际需求

若源目录有 Windows 不接受的名称，应在挂载前检测并给出明确错误。大小写敏感性、可执行位、符号链接、ACL、硬链接、文件通知均需定义范围。不要宣传未经测试的完整 NTFS 或 POSIX 等价。

H 证据账本与最终建议

所有证据来自文档调查。WinFsp、cgofuse、HUBFS 同属相近生态，不能当作三个独立可靠性背书。未核实 HUBFS 内部源码语义，也未测性能。

结论 等级 原始材料与缺口
Linux 普通目录可作 upper/lower 已证实 Kernel 文档，未对用户磁盘实测
Windows 可挂目录路径，不能覆盖非空目录 已证实 WinFsp FAQ；具体部署仍需验证
共享接口可覆盖 Win/Linux 已证实 cgofuse 官方支持表
跨平台可写覆盖架构已有实例 已证实 HUBFS README；非任意本地目录 CLI
自建核心 + 两平台适配可满足本需求 工程判断 可行性有依据，需实现与双平台验收
rclone union 不应直接当严格 CoW 文档推断 依据 action 和 writeback 规则
已有稳定的一键跨平台通用本地 CoW 工具 当前未知 本调查未找到足够官方证据，不代表不存在
→ 建议
1 Linux 即用选 OverlayFS 或 fuse-overlayfs
2 长期跨平台产品：cgofuse + WinFsp 建立原型 → 共享叠加核心 → 可移植元数据
3 若两套系统必须复用同一修改层，统一格式列为第一阶段要求
I 实施前待定项
→ 实现前仍需确定
是否允许安装 WinFsp？ WinFsp 是 Windows 文件系统扩展的工程依赖。若不允许，Windows 路线需要另起方案（应用内 VFS 只能服务接入程序，或接受复制工作区）。
是否跨系统复用同一修改层？ 若同一 changes/meta 目录需要在 Linux 和 Windows 之间迁移或共享，统一格式设计是第一优先。不能直接复用内核 OverlayFS upper 格式。
目标应用是否涉及数据库或大文件？ 大文件首写复制成本、mmap 行为、数据库写粒度都会影响设计。copy-up 以文件为单位，不自动提供块级增量。
base 在挂载周期内是否保持稳定？ 同一状态默认只允许一个服务写入。允许外部修改时，需要额外的缓存失效与一致性协议。
