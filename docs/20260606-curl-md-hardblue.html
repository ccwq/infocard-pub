01
它到底是什么

把 URL 变成 Markdown，不是为了排版，而是为了节省 agent 的上下文

curl.md 的首页和文档都在强调同一个点：它把网站转成“优化过的低 token 输出”，让 agent 更容易读取、摘要、检索和继续处理。

定位中间层

不是浏览器替代品，而是上下文净化层

它的角色不是“再给你一个浏览器”，而是把网页内容压成 Markdown，让后面的 agent、脚本或插件吃更干净的输入。

  • 减少 HTML 噪音
  • 减少手动复制粘贴
  • 减少 token 浪费
结果低 token

它优化的是“可消化性”

官网直接写明 low token output / supercharge your context，说明它关心的不是原样复刻网页，而是让 agent 更快进入有效上下文。

  • 网页 → markdown
  • 正文优先，视觉次之
  • 适合再加工
覆盖面every agent

适配面很广，但入口不止一种

首页和文档把入口拆成浏览器、CLI、plugins、API/SDK 四条线，不同工作流各走各的最短路径。

  • 浏览器直接开用
  • CLI 适合脚本链路
  • 插件适合编辑器 / agent
02
怎么上手

先装 CLI，再决定是浏览器、插件还是 API 路线

文档明确把安装路径分成 CLI、SDK 和插件三层；如果你只是想快速把网页喂给 agent，CLI 是最短路径。

路径 ACLI 优先

最短可用命令

curl -fsSL https://curl.md/install.sh | bash

官方安装页直接给出这个命令，说明它默认把 CLI 作为最通用的入口。对于自动化、脚本和 agent pipe 来说，这是最省步骤的方式。

  • 也支持 npm / bun 安装
  • 适合 shell、脚本、批量抓取
  • 直接对 URL 前缀化使用
路径 B工作流映射

03
最适合谁

最适合频繁读网页、读文档、做 agent 上下文整理的人

它的价值不是一次性“转成 markdown”，而是持续把网页内容变成能被代理、脚本、编辑器直接消费的材料。

01 / 研究

把网页变成可引用资料

适合把文档、产品说明、FAQ、博客和教程压成更干净的文字，再喂给总结、问答或笔记工作流。

减少页面噪声，保留可检索的主体信息。

02 / 编码代理

给 agent 喂上下文

官网自己写了 “works with every agent”，并把 Amp、Claude、Codex、Cursor、OpenCode、Pi 列成兼容对象。

说明它主要服务的是 agent 使用场景，而不是纯人工阅读。

03 / 自动化

让脚本替你扫网页

CLI + URL 前缀的组合，适合放进 shell、CI、采集脚本或自动化管线里做批量处理。

比手动复制网页内容更适合重复工作。

04 / 文档流

减少上下文爆炸

对长文档来说，先抽成 markdown 再处理，往往比直接把 HTML 丢给模型更省 token、更稳。

对上下文预算紧张的工作流特别有用。

04
边界与注意

它解决的是“上下文清洗”，不是“所有网页问题”

这类工具好用，但不要把它误读成万能抓取器：限流、登录、网站结构复杂度和使用额度都会影响体验。

1

高额度需要更完整的使用方式

首页明确提示 sign in 可以获得 higher limits。也就是说，免费体验能用，但高频场景要接受账号与额度管理。

2

并不替代浏览器本身

如果你要处理强交互页面、登录后态或复杂可视布局，仍然需要浏览器；curl.md 更适合把结果压缩成可消费文本。

3

它优化的是文本，不是视觉

信息卡里最重要的判断是：它的强项是 markdown/context，而不是还原网页原始视觉。别把这两个目标混在一起。

能力适合不适合
网页转 markdown文档、博客、FAQ、说明页强交互、登录态强依赖页面
CLI / 脚本自动化、批量采集、agent pipe只想临时看一眼页面的人
插件 / API编辑器内工作流、程序化接入不愿意做任何配置的人

如果你的目标是“把网页内容快速变成 agent 可用上下文”，它很合适；如果目标是“完美还原视觉或交互”，那它不是主工具。
