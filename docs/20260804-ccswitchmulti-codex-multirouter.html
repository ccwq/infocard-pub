CODEX MODEL-LEVEL ROUTING

CCSwitchMulti：把多家模型装进同一个 Codex

它不是把订阅额度“转卖”给第三方模型，而是在本机为 Codex 建一条按 model 分流的路由：官方 OAuth、DeepSeek/Qwen、OpenAI-compatible API 与本地 vLLM/Ollama 各走各的上游。

Codex MultiRouter按 model 分流GUI / 托盘控制面
最重要的边界：官方登录 ≠ 第三方免费额度

auth.json 可保留 Codex 官方登录态；第三方 endpoint/key 写入 config.toml。实际出站、计费、限额和数据政策，取决于当前 route 与对应上游。

01
IDENTITY

不是普通切换器：它的增量在 Codex 路由层

严格对象是 BigStrongSun/ccswitchmulti，不是第一张的 farion1231/cc-switch。

产品形态

Tauri 桌面控制面

Windows、macOS、Linux 本地 App；主交互仍是 Provider 卡片、设置、托盘与 MultiRouter 向导，不是用户在 shell 敲路由子命令。

核心差异

Codex 按模型选上游

请求进入 router 后读取 body.model，按精确模型/前缀/映射表匹配 route。用户无需先在 GUI 把“当前上游”切成某家，才能发出对应模型请求。

版本快照

v3.19.1-2 / MIT

本卡调研读取的 latest release 为 v3.19.1-2（2026-08-03）。动态版本、Star 或模型目录须以运行时/发布页为准。

02
ROUTING MECHANISM

三层机制：登录保留、目录投影、请求分流

把三个容易混淆的事实分开，才不会误读“一个 Codex、多家模型”。

① 身份

auth.json 保留官方登录

先完成 OpenAI Official 登录，可启用“切换第三方时保留官方登录”。它保存 ChatGPT/Codex 登录缓存与 access token；不能复制、分享或把它当通用 API Key。

② 目录

model_catalog_json 让 Codex 看见模型

路由规则生成可见模型目录；修改目录后通常要重启 Codex 才会刷新 /model 菜单。菜单可见不保证 endpoint、Key 或能力一定可用。

③ 出站

config.toml 决定实际 provider

第三方 base URL、模型、provider-scoped token 进入运行配置；本地 router 再按 body.model 选择真实上游。官方账号显示和实际计费方可分离。

MultiRouter 不是“gpt 出错自动降级 DeepSeek/Qwen”的故障转移池。源码明确禁止官方 gpt-* 请求无声回退到其他模型，避免改变用户选择与认证边界。
03
SOURCE TYPES

哪些模型源能接？哪些不随应用附送？

可配置模型源与“工具内置模型/本地推理运行时”是两件事。

官方 Codex / OAuth

作为官方 route；官方身份可保留。但本地接管下不宜把代理访问官方 API 描绘为无风险。

DeepSeek / Qwen

可用 preset 或自定义 route。v3.19.1 起新建 DeepSeek preset 可原生 Responses 直连；旧配置、某些型号或 Chat-only 上游才需转换。

第三方兼容端点

配置 API Key、Base URL、API 格式与 model mapping；“OpenAI-compatible”只是接入前提，不等于所有工具、流式、图像与推理都完整等价。

vLLM / Ollama

向导把它们列为 Codex provider 模型源。它们需要用户自行运行、暴露兼容 endpoint 并保证所选模型/工具能力能满足 route。

04
PROTOCOL ADAPTER

为什么有时必须经过本地 router？

Codex 说 Responses；上游未必说同一种协议。兼容层按 route 格式按需介入。

原生 Responses：可直连

例如 v3.19.1 后新建的 DeepSeek preset 被文档标为原生 Responses 直连；这类 route 不一定经过本地转换，也可能不出现在以 router 请求为维度的用量统计中。

Chat / Messages / Anthropic：按需桥接

本地 router 将 Codex Responses 请求改为上游 Chat Completions 等格式，并把 JSON/SSE、reasoning 与工具调用适配回 Codex Responses。兼容质量仍取决于上游实现与 route capability。

1
创建模型源：在 MultiRouter 向导提供 API Key、Base URL、Responses / Chat 格式、模型菜单映射。
2
获取并处理模型目录：向导可请求 /models；同名第三方模型会追加 provider 名，保留真实 upstreamModel。
3
生成规则、发布并测试：规则存入 settings_config.codexRouting；Codex endpoint 指向本地 router；修改目录/接管后按需重启 Codex。
05
VS CC SWITCH

与第一张 CC Switch 的区别：从“多客户端”转向“一个 Codex 的多模型”

两者不是同一仓库，也都不是用户切换 CLI；下面只比较已被一手材料确认的差异。

维度CC Switch（第一张）CCSwitchMulti（本卡）
核心主轴多客户端 Provider / 配置管理与投影Codex 模型级 MultiRouter：按 body.model 选上游
操作形态GUI / 托盘；无官方用户切换 CLIGUI / 托盘 + MultiRouter 向导；同样无官方用户切换 CLI
路由重点已确认 Claude / Codex / Gemini 本地接管Codex 一入口、多 route、模型前缀/别名映射
官方登录与第三方本卡不将其归因给第一张保留 auth.json 官方登录缓存，同时在 config.toml 使用第三方 route/key；不转移订阅额度
本地/兼容服务不把本卡特性串给第一张DeepSeek、Qwen、vLLM/Ollama、第三方 compatible endpoint 可作为 Codex 模型源
额外 API 面不在此卡声称独立 external OpenAI-compatible sidecar 默认 127.0.0.1:15722；与 Codex takeover 默认 15721 分离
共同点Tauri 桌面控制面、SQLite SSOT、配置投影；不是“敲一条命令就切换”的独立 CLI。
最实用的判断：你要跨 Claude / Codex / Gemini 等工具统一维护配置，先看 CC Switch；你要让一个 Codex 会话在官方、第三方和本地模型之间按模型名分流，CCSwitchMulti 的 MultiRouter 才是差异化能力。
06
LOCAL API & SECURITY

15721、15722 与安全边界

“本地”不是“无需安全判断”；端口、凭据与请求来源都必须分开看。

15721

Codex takeover / MultiRouter

Codex 连接本地 Responses-compatible endpoint；router 按模型规则转发。默认地址可配置，应用需保持运行才能持续接管。

15722

外部 OpenAI-compatible sidecar

给第三方 agent 暴露独立的兼容 API；源码明确它与 Codex current provider/live config/takeover 状态分离，不能互相替代验收。

敏感信息

默认 loopback 更稳妥

项目 SECURITY.md 说明监听可绑定 non-loopback，入站请求被当作不可信输入。不要分享 auth.json、access token 或 API Key；LAN 暴露要自行评估。

07
LIMITS

适合谁、不适合谁

它提高了 Codex 的模型可选性，也引入了本地代理、凭据与兼容矩阵。

适合

已使用 Codex，想把官方 route 作为一条路径，同时按模型名接 DeepSeek/Qwen、聚合 API 或自建 vLLM/Ollama；能够接受在桌面 App 中维护 route、测试 endpoint 并查看第三方账单/日志。

不适合 / 应谨慎

希望完全零代理、零配置写入；要求所有官方工具/图像/compaction/流式能力无损等价；把 OpenAI 订阅当作第三方免费额度；或计划将 localhost router 暴露到不受控网络的人。
