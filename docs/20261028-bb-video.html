01 / PIPELINE ANATOMY

从脚本到 MP4，每一步落在哪个文件

script.json
  → tts.py：音频 + 词级时间轴
  → index.html：renderFrame(t) 生成指定时刻画面
  → render.mjs：无头 Chrome 逐帧渲染
  → ffmpeg：编码输出 mp4

README 将“每帧是时间的纯函数”作为确定性渲染的基础：画面由时间参数决定，因此可并行渲染，也能在整片开始前抽取任意时刻作静帧预检。这里描述的是机制，不是渲染速度实测。

音乐与音效也由代码合成。22 种风格包括 whiteboard / riso / ink / launch / origami / pop / op / cutout / ascii / shadow / bauhaus / pixel / chat / toy3d / newsreel / filmroom / mystery / isometric / trailer / dossier / manga / map。每种有官方样例：GIF 是 7 秒剪辑，完整 MP4 在 samples release；这些是作者样片，不是第三方评测。

02 / TWO CHECKPOINTS

两级自检：先查表达，再查成片

README 把检查安排在渲染前后。前者看设计是否可读、是否忠于 brief；后者看逐帧结果是否出现突变或停滞。

阶段逐项检查读报告时的关注点
渲染前
lint · 六项		① 元素重叠
② 文字来不及读
③ 元素出画
④ 画面事实不在 brief 中
⑤ 信息稀薄
⑥ 运动问题		布局与阅读时间是否合理；画面有没有自行添加 brief 未提供的事实。
渲染后
frame check · 三项		① 跳帧
② 单帧闪光
③ 死空气		死空气指几秒内只有音乐和画面、没有新内容；单帧闪光与跳帧需在成片阶段核对。

检查项是项目声明的流程能力，不等于已经验证“不会漏检”；本卡没有实际运行视频任务。

03 / INSTALL & OUTPUT

两种安装方式，五项运行前提

选择其中一种安装方式。第一条可追加 --skill bb-video -a claude-code -g，指定 skill、agent 与全局安装。

npx skills add BubbleBrainBB/BB-Video

# 或：克隆后复制到 Claude Code 的 skills 目录
git clone https://github.com/BubbleBrainBB/BB-Video.git && cd BB-Video && cp -r skills/bb-video ~/.claude/skills/
  1. Node 18+：项目无 npm 依赖。
  2. Chrome / Chromium：必要时通过 CHROME_PATH 指定浏览器。
  3. ffmpeg 在 PATH：供最后的视频编码使用。
  4. Python 3 + edge-tts：生成配音及词级时间轴。
  5. 可联网：配音、字体和部分 CDN 库需要网络。

可选 Blender 3.6+ 用于 toy3d 吉祥物；没有时用 three.js 构建。请求语言会影响输出语言，中英文完整调优；其他语言可使用相应 edge-tts 声音。

videos/<项目>/
├── index.html       # 浏览器预览，可拖时间轴
└── out/
    ├── MP4 视频
    ├── 封面
    └── board 总览图  # 仅 whiteboard / riso

上图表示产物类别，未虚构具体输出文件名。预览页用于检查画面，最终编码产物到 out/ 查找。

04 / PRIVACY & EXECUTION

旁白会外发，项目代码有本地文件权限

两条红线

旁白文本会发送到微软在线语音服务，这是 edge-tts 的工作机制。机敏内容勿入旁白。

render.mjs 以本地文件权限执行项目代码。只渲染自己或自己 agent 生成的项目。不要把来路不明的项目当普通媒体文件打开渲染。

  • 宣传片研究：promo 会用无头 Chrome 打开目标网站截图，不登录、不下载站点文件。
  • 外部素材：经 Wikimedia Commons API 搜索，只下载你批准的文件；不要求预先准备素材库，不代表没有可选素材下载。
  • 其余网络行为：README 列出配音、字体和 jsDelivr 固定版本库；除上述研究、素材与资源请求外，无其他网络行为、无遥测，无需 API key 或账号。这不意味着全离线。
  • 许可分别看：项目 MIT；内置 KaTeX 为 MIT；CDN 的 three.js、Matter.js 为 MIT，GSAP 用其标准免收费许可；LXGW WenKai、Noto 等字体为 SIL OFL 1.1。

05 / EVIDENCE BOUNDARY

模型偏好与“200%”都只按作者自述读

公众号文章与仓库出自同一作者，交叉验证有限。作者称“最适配 Opus 5.5”，认为其他 agent 效果差一些；作者称 Kimi“太慢”，这是个人体验。作者也承认“没来得及每个模型都测一遍”，不能据此列模型排名。

作者建议将默认 edge-tts 换成字节 seed audio，并称“好声音给视频能力提升200%”。“200%”是作者修辞，不是测量结果；卡片不把换声建议写成已验证的性能收益。

截至 2026-10-28，仓库 2 stars、0 forks；2026-10-05 创建，唯一贡献者 BubbleBrainBB，44 commits。这是发布三周的早期项目快照，不是质量证据。

现有材料无第三方对比评测；README 未给各风格分镜或时长上限，也没有渲染耗时数据。不据此承诺速度、长度容量或风格效果。

06 / A 30-MINUTE TRIAL

留 30 分钟，验证一条 30 秒白板短片

以下是建议的最小验证任务，不是已完成的运行记录，也不是完成时间承诺。

01 · 给 agent 一个小题

“用 BB-Video 的 whiteboard 风格，制作 30 秒《为什么天空是蓝的》。先给 brief 与脚本，再检查画面事实。”不要放入机敏旁白。

02 · 看报告而非只看样片

查看 lint 六项检查的报告；渲染后核对 frame check 三项。把发现的问题与 brief、具体时间点对应起来。

03 · 核对产物与故障点

检查 out/ 的 MP4、封面和白板总览图，再打开 index.html 拖轴。失败先查 ffmpeg 是否在 PATH、CHROME_PATH 是否指向可用浏览器、edge-tts 是否安装且能联网；不预设报错原文。

要比较多条制作路线，读相邻卡 《代码视频工作流》；本卡聚焦单个 skill 的多风格路线，不把它当成三条工作流的替代结论。

BOUNDARIES BEFORE RENDER

进入真实项目之前，先设四道检查点

  • brief 是画面事实的依据：lint 对照它检查，不用作者样片替代自己的验证。
  • 旁白先过敏感信息检查：微软在线 TTS 不是本地处理。
  • 代码来源先确认：本地文件权限意味着需要信任项目。
  • 拿到报告与 out/ 产物后再扩大任务；30 分钟试跑只验证本机与本次内容。
