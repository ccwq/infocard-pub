01

先分类：六项资源解决的不是同一个问题

如果把组件库都叫“UI 资源”，你会在错误的层级比较它们。Fluid Functionalism 关注动效如何表达状态；Watermelon UI 提供基础组件、blocks、dashboard 和 animated components；HeroUI 是更完整的 React 组件体系，HeroUI Pro 还提供商业模板与 AI tooling；ThreeUI 走 3D/WebGL 路线；BoardUI、beUI 等则需要分别核验官方当前状态。

任务优先路线你真正购买/接入的东西第一道风险
表单、弹窗、Tabs、状态反馈Fluid Functionalism / HeroUI OSS组件行为、tokens、无障碍和动效约定依赖版本与现有设计系统冲突
后台、数据看板、页面区块Watermelon UI组件 + blocks + dashboard 结构beta 状态与具体组件维护

02

Fluid Functionalism：动效必须让状态更容易读

官方定位不是“加更多动画”，而是让 motion 具有功能：hover 预览用户即将点击的位置，selection merge 说明项目属于同一组，spring 在用户中途反向操作时自然响应。它构建在 shadcn/ui 和 Radix/Base UI 生态上。

实际安装路径

npx shadcn@latest registry add @fluid
npx shadcn@latest add @fluid/button
# 或直接使用具体组件 registry URL

官方文档提供 fast、moderate、slow 三档 spring，并要求 reduced motion 可用。接入后不要只检查视觉预览：确认现有主题 tokens、primitive flavor、字体变量和 Motion 配置是否一致。

适用判断：如果动画关闭后用户无法理解选中、展开、聚焦或反馈状态，说明信息设计没有站稳；Fluid Functionalism 的价值应体现在状态可读性，而不是动画数量。
03

Watermelon UI：从基础组件到 dashboard blocks

Watermelon UI 官方站点覆盖基础组件、UI blocks、animated components 和页面结构。GitHub 资料说明其组件通过 copy-paste shadcn registry 分发，生成的代码进入消费项目后可编辑。

# 官方仓库 README 中的 registry 形式示例
npx shadcn@latest add https://registry.watermelon.sh/r/card-split-accordian.json

它更像“从页面结构开始”的资源，而不是只给你一个按钮。做后台或 Agent 产品时，可以先挑一个真实任务区块：筛选、数据表、通知、文件上传或设置页，然后替换内容与数据，不要把整套 demo 当成生产架构。

第一次接入验收

  1. 确认组件对应的 registry URL 和当前版本。
  2. 记录新增 npm 依赖、Tailwind tokens 和图标包。
  3. 把 block 放入隔离 route，不要直接覆盖首页。
  4. 替换真实文案、长标题、空态和错误态。
  5. 在 390px、键盘和 reduced-motion 下重新检查。
边界：官网标注 beta；条目数量、维护范围和协议以当前页面与具体仓库为准。
04

HeroUI：区分 OSS 组件库和 Pro AI tooling

HeroUI OSS 官方文档将其定位为 React 组件库，基于 Tailwind CSS v4 与 React Aria Components，强调 focus management、keyboard navigation、screen reader support、类型化 API 和可组合部件。

HeroUI Pro 是另一层产品：包含 premium components、templates 和 AI tooling。官方 Pro 文档列出 MCP Server、React Pro Skill 和 Design Taste Skill；MCP 需要 token 和网络，两个 skill 可以离线加载。不能把 Pro 的能力写成 OSS 免费库的默认能力。

HeroUI OSS

  • 适合基础组件体系与 React Aria accessibility。
  • 适合希望随库更新修复，而非复制代码长期维护的团队。
  • 重点检查 React 版本、Tailwind v4、主题变量和组件组合。

HeroUI Pro

  • 适合模板、设计系统和 AI 辅助开发工具。
  • 需要区分商业条款、token 和在线 MCP。
  • 不要把 Pro 预售/付费能力写成开源能力。
05

3D/WebGL 路线：先核验，再承诺

来源帖将 ThreeUI 作为 3D/WebGL 组件来源，但本轮公开资料没有获得足够稳定的一手仓库和文档来确认其当前安装、协议和维护状态。因此这里不提供未经核实的安装命令。

如果你的目标是 3D Hero，先写出性能和降级合同：

桌面：WebGL Hero，首屏主文案先于 canvas 可见
移动端：静态图或 CSS 版本，不强制加载 3D
低性能设备：关闭粒子、后处理和高分辨率纹理
可访问性：canvas 旁有等价文本与键盘路径
验收：LCP、内存、帧率、prefers-reduced-motion、无 GPU 设备
不要被示例图骗过：3D 组件的真实成本在加载、GPU、移动端和退化方案，不在截图中的第一眼效果。
06

一次最小实验：用同一个页面验证三条路线

不要收藏六个站点后直接重写全站。选一个真实页面，例如“Agent 任务详情页”，拆成三块实验：

01固定内容、路由、字体和颜色 tokens，记录基线。
02用 Fluid 做一个状态明确的交互组件。
03用 Watermelon 或 HeroUI 搭一个数据区块。
04若确有 3D 需求，再隔离测试 ThreeUI 路线。
05四视口、键盘、reduced-motion、错误态和构建。
检查项通过标准不通过时
依赖安装命令可复现，版本和 registry 清楚锁版本或换更透明的来源
视觉组件融入现有 tokens，不是孤岛皮肤写 wrapper 或只保留行为
动效解释状态，关闭后核心任务仍成立降低或删除动效
可访问性键盘焦点、标签、屏幕阅读器和 reduced-motion 可用补实现或拒绝接入
性能主内容先可用，3D/动画不阻塞关键路径延迟加载、静态 fallback 或换路线
07

最终选择清单：把“高级感”变成工程决策

  1. 我做的是基础交互、后台区块、Agent 产品、营销页还是 3D Hero？
  2. 这个资源是开源、商业、beta 还是目前证据不足？
  3. 它是 copy-paste registry、npm 依赖、完整 library 还是 design philosophy？
  4. 安装后代码由谁维护，版本更新是否覆盖本地修改？
  5. 它的 animation 在 reduced-motion 和低性能设备上如何降级？
  6. 组件是否能通过键盘、屏幕阅读器和真实长文案验收？
  7. 如果明天删除它，项目能否回滚而不重写整个页面？
