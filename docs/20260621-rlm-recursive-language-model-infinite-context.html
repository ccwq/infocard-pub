📖 为什么值得看

来自 MIT CSAIL 的 OASYS Lab，背后站着 DSPy 和 ColBERT 的作者 Omar Khattab——VentureBeat 专门报道，开源即冲上 5k ⭐，论文已挂 arXiv（arXiv:2512.24601）。

核心洞察：**上下文窗口的尽头，从来不是模型的极限，而是工具的边界。**

普通模型处理超长文本有个死穴：一本书、一整个代码库、几百页报告，要么塞不进上下文窗口，要么读到后面忘前面。RLM 的思路完全不一样。

一句话

RLM 不靠把窗口撑大，而是让模型把整份上下文当 REPL 里的变量，自己写代码去分块、grep、递归调子模型查——就像程序员在 REPL 里调试，而不是一次把所有代码背进脑子。

🔄 两种范式对比
❌ 传统 LLM Completion
  • 上下文全部塞进 prompt
  • 窗口有硬上限，超出就截断或报错
  • 模型被动接收，无法主动查询局部
  • 长文本越靠后的内容越容易被"忘记"
  • 调用：llm.completion(prompt, model)
✅ RLM：上下文当变量
  • 上下文作为对象存在于 REPL 命名空间
  • 模型可写代码分块、grep、切片
  • 递归调子模型处理局部片段
  • 处理范围超出原生窗口 10–100×
  • 调用：rlm.completion(prompt, model)
⚙️ 底层原理
运行模型
# 模型在 REPL 中执行自己生成的代码 context_doc = "加载的长文本" chunks = chunk(context_doc) # 模型可自由调用子模型处理每个分块 result = sub_rlm(chunks[0]) answer = sub_rlm(chunks[1:5]) final = root_rlm(answer)
  • 把 llm.completion() 替换成 rlm.completion() 即可，API 完全对齐。
  • REPL 环境中，上下文是一等公民——模型可以用 grep / filter / sub_rlm() 自由探索。
  • 子模型调用也是 rlm.completion()，天然支持无限递归嵌套。
  • 内置日志（RLMLogger）记录完整轨迹，可回放任意节点。
  • 支持 RL 训练：直接插入 prime-rl 的训练框架。
📦 安装

pip install rlms
Python ≥ 3.11。无需改动模型，替换掉原来的 llm.completion() 为 rlm.completion() 即可。

curl -LsSf https://astral.sh/uv/install.sh | sh
uv init && uv venv --python 3.12

💻 接入示例
from rlm import RLM

rlm = RLM(
    backend="openai",
    backend_kwargs={"model_name": "gpt-5-nano"},
    verbose=True,
)

print(rlm.completion(
    "Print me the first 100 powers of two, each on a newline."
).response)
只需把 llm.completion() 替换成 rlm.completion()。模型换成任何支持的 provider 即可。

📌 边界说明
  • 本地 REPL 无生产级隔离：默认 local 环境在同一进程执行代码，适合内部基准测试，不适合处理不可信输入。
  • Prime Sandboxes 速度偏慢：官方已知问题，beta 阶段限制。
  • 子模型调用成本叠加：递归调用子 RLM 会累积 token 消耗，需要配合 budget 控制。
  • 训练 harness 仅 local REPL：production RL 训练建议换用云沙箱隔离。
