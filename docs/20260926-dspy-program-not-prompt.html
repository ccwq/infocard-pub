02三层抽象：代码长什么样

Signature 声明"做什么"——两行起步，类型即约束（Literal 枚举直接限定输出取值，嵌套 pydantic 模型也行）：

class Emotion(dspy.Signature):
    """Given a context, judge the emotional tone of it."""
    context: str = dspy.InputField(desc="facts here are assumed to be true")
    sentiment: Literal['sadness','joy','love','anger','fear','surprise'] = dspy.OutputField()

# 更快的手写法：内联签名，一行就能跑
classify = dspy.Predict('sentence -> sentiment: bool')

Module 定义"怎么做"——同一签名可无痛换执行策略：dspy.ChainOfThought(sig) 加推理步、dspy.ProgramOfThought 生成代码解题、dspy.ReAct 走工具循环。官方文档明确：模块、适配器、模型三者互相独立，换任何一个不改其余代码。

Optimizer 调"怎么问"——拿到程序 + 少量标注 + 一个指标，它自己改提示词：

import dspy
lm = dspy.LM('openai/gpt-5.2', temperature=0.7)
dspy.configure(lm=lm)

from dspy import MIPROv2
teleprompter = MIPROv2(
    metric=my_metric,
    auto="medium",   # light / medium / heavy 三档预算
)
optimized = teleprompter.compile(
    dspy.ChainOfThought("question -> answer"),
    trainset=my_trainset,
)
optimized.save("optimized.json")   # 存盘复用，不再手抠措辞

03两个旗舰优化器的真实机制

AMIPROv2 = 生成 + 贝叶斯搜索——为程序里每个 predictor 生成候选 few-shot 示例与新指令，再用贝叶斯优化搜最佳组合；auto 三档控制预算（light/medium/heavy），小任务几条数据就能出效果。
BGEPA = 会反思的提示词进化（Jul'25）——采样完整轨迹（推理、工具调用、输出），用自然语言反思诊断问题、提出并测试提示词更新，再从自己尝试的 Pareto 前沿合并互补经验。论文数字：六任务平均超 RL 方法 GRPO 6%（最高 20%）且 rollout 省 35 倍；超此前最强的 MIPROv2 10%+（AIME-2025 +12% 精度）。一句话：能"从错误里学规则"的提示词优化器，不是随机搜索。

04上手四步（含官方数据预算）

  1. 安装：pip install dspy（v3.4.0；跟进 main 用 pip install git+...）。配模型一行：dspy.configure(lm=dspy.LM('openai/gpt-5.2'))，走 LiteLLM 所以本地 vLLM/Ollama 也认（clients/ 目录 34 个文件：openai/local/databricks/streaming/cache 全套）。
  2. 定义任务：从单个 dspy.ChainOfThought 起步，别急着拆管道。 signature 里用 desc= 写字段约束，输出用 Literal 限枚举。
  3. 攒数据 + 定指标：官方给的预算参考——30 条就有实质收益，建议奔 300 条去。评估器内置：dspy.Evaluate + SemanticF1/answer_exact_match 等现成 metric。
  4. 跑优化器：一个反直觉的官方建议——prompt 优化器用 20% 训练 / 80% 验证的反向划分（提示词优化太容易在小训练集上过拟合）；但 GEPA 例外，它要训练集越大越好、验证集够反映分布就行。优化完 optimized.save() 存 JSON 复用。
选型速记：先 MIPROv2(auto="light") 摸底 → 认真上 GEPA（效果最好、会反思）→ 要动权重走 BootstrapFinetune/GRPO → 两个优化器可以串着跑。24 个官方教程里 papillon（本地小模型+外部大模型的隐私委派）和多跳 RAG 最值得先读。

05模块工具箱：六大内置模块各管什么

所有内置模块都"抽象一种提示技术且适配任意签名"，内部全部构建在 dspy.Predict 之上，参数（提示词片段与演示）可学习——官方类比直接点名 PyTorch 的 nn.Module。标准三步用法：声明签名 → 传参调用 → 取输出字段：

# 三步：声明、调用、取值（官方教程原例）
classify = dspy.Predict('sentence -> sentiment: bool')
response = classify(sentence="it's a charming and often affecting journey.")
print(response.sentiment)   # True

# 换模块不动签名：ChainOfThought 自动在输出前注入 reasoning 字段
classify = dspy.ChainOfThought('question -> answer', temperature=0.7)
response = classify(question="What's something great about the ColBERT retrieval model?")
print(response.reasoning)   # 'We can consider the fact that ColBERT ...'
print(response.answer)
模块机制（官方定义）什么时候用
dspy.Predict基础预测器，不改签名；存储指令与演示示例一切起点；任务明确、输出格式固定
dspy.ChainOfThought提交答案前先逐步推理（注入 reasoning 字段）大多数任务的默认升级——官方原话"simply swapping ... improves quality"
dspy.ProgramOfThought让 LM 输出代码，执行结果作为答案数学/日期/结构化计算，文字推理不可靠时
dspy.ReAct推理+行动循环，可用工具完成签名需要搜索、API、计算器等外部动作
dspy.MultiChainComparison对比多条 CoT 输出后给最终答案单次推理不稳定、代价可承受
dspy.RLM递归语言模型：沙箱 Python REPL 里递归调子 LM 探索大上下文上下文大到塞不进 prompt 时
dspy.majority函数式投票，取最热门答案多路采样后的简单聚合

官方教程还给了五类即抄即用的样例：数学（"question -> answer: float" 掷骰子求 1/36）、RAG（dspy.ColBERTv2 检索维基摘要）、分类（Literal['positive','negative','neutral'] + confidence 浮点）、信息抽取（一句话抽出 title/headings/实体元数据 list[dict]）、agent（ReAct 挂 evaluate_math + search_wikipedia 两个工具算"9362158 除以 Kinnairdy 城堡建造者的出生年份"）。

06自定义程序与工具：组合是纯 Python

多模块组合没有 DSL——就是你熟悉的 Python 控制流，compile 时框架内部追踪 LM 调用。官方多跳搜索教程的 Hop 类一眼能懂：

class Hop(dspy.Module):
    def __init__(self, num_docs=10, num_hops=4):
        self.num_docs, self.num_hops = num_docs, num_hops
        self.generate_query = dspy.ChainOfThought('claim, notes -> query')
        self.append_notes = dspy.ChainOfThought('claim, notes, context -> new_notes: list[str], titles: list[str]')

    def forward(self, claim: str) -> list[str]:
        notes, titles = [], []
        for _ in range(self.num_hops):
            query = self.generate_query(claim=claim, notes=notes).query
            context = search(query, k=self.num_docs)
            pred = self.append_notes(claim=claim, notes=notes, context=context)
            notes.extend(pred.new_notes); titles.extend(pred.titles)
        return dspy.Prediction(notes=notes, titles=list(set(titles)))

hop = Hop()
hop(claim="Stephen Curry is the best 3 pointer shooter ever in the human history")

工具有两种接法。省事用 dspy.ReAct 全托管：传 tools=[get_weather, search_web]、max_iters=5，它自动推理选工具、迭代调用、内建失败恢复，result.trajectory 返回完整推理与调用历史。要精细控制就走手动路径：dspy.Tool 包装普通函数（自动提取 name/docstring/参数 schema），签名里用 dspy.ToolCalls 输出字段，模型只生成调用意图、执行权在你手里（call.execute() 需 ≥3.0.4b2）。函数 docstring 直接成为工具描述——和 Needle 同一哲学。

新手最常见坑：对话应用别每轮新建模块实例——实例内部存着 demonstrations，复用同一实例上下文才连续；换了工具集才需要新实例。要统计花费：dspy.configure(track_usage=True)（≥2.6.16）后从 Prediction 对象 get_lm_usage() 拿每个模型的 token 用量。

07LM 接入与缓存：换模型只改一行

底层走 LiteLLM，所以几十家 provider 全通。三种最常见的接法：

# 云端一行切换（密钥走环境变量或 api_key=）
lm = dspy.LM('openai/gpt-4o-mini', temperature=0.9, max_tokens=3000, cache=False)
lm = dspy.LM('gemini/gemini-2.5-pro-preview-03-25', api_key='GEMINI_API_KEY')

# OpenAI 兼容端点：加 openai/ 前缀即可指向任何自建服务
lm = dspy.LM('openai/your-model', api_base='http://localhost:7501/v1', api_key='')

# 本地 Ollama：ollama_chat/ 前缀
lm = dspy.LM('ollama_chat/llama3.2', api_base='http://localhost:11434', api_key='')

缓存默认开启：同一调用重复执行直接吐缓存结果——调试时省钱，但实验想看随机性要显式 cache=False；要多轮采样又想绕缓存，传唯一 rollout_id + 非零 temperature（DSPy 对两者一起做哈希）。需要同一模型不同参数的场景用 lm.copy(...)，不要手动重建。 这些配置在模块声明处也可覆盖（如 ChainOfThought(…, temperature=0.7)）。

08评测与优化器选型：官方决策树照抄

评测数据怎么攒：官方评测指南给的心理预期是"20 条就有用、200 条走远"；多数场景只需要输入 + 系统最终输出，几乎从不需要中间步骤的标注。metric 本身可以就是一个小 DSPy 程序（长输出场景逐项打分），它自己也能被优化——"metric 的 metric"只需几条样本。内置现成评估：dspy.Evaluate 跑批量、SemanticF1/answer_exact_match 直接可用。

优化器按数据量选（官方 optimizers 指南原话翻译）：

你的数据官方推荐机制
~10 条BootstrapFewShot跑你的程序自生成成功轨迹当 few-shot 演示
50+ 条BootstrapFewShotWithRandomSearch自举演示 + 随机搜索多个候选程序，按 devset 择优
要 0-shotMIPROv2（0-shot 模式）只优化指令不注入示例
200+ 条、跑得起 40+ trialsMIPROv2 全量 / GEPA贝叶斯组合搜索 / 反思式进化（见 03）
要小模型高效率BootstrapFinetune把大模型跑出来的轨迹微调进小模型权重

五大类全景：few-shot 类（BootstrapFewShot/KNNFewShot 按最近邻选演示）、指令类（COPRO 坐标上升、MIPROv2 贝叶斯）、微调类（BootstrapFinetune）、程序变换（Ensemble/重试）、元优化器（BetterTogether 串两个、SIMBA 随机 mini-batch 找高方差难例让 LM 自省失败）。全部共享一个接口：teleprompter.compile(program, trainset=...)。

# 官方"最常见"配置模板（BootstrapFewShotWithRandomSearch）
config = dict(max_bootstrapped_demos=4, max_labeled_demos=4,
              num_candidate_programs=10, num_threads=4)
teleprompter = dspy.BootstrapFewShotWithRandomSearch(metric=my_metric, **config)
optimized = teleprompter.compile(my_program, trainset=my_trainset)

# 存取都是明文 JSON——优化产物可读可审计
optimized.save("optimized.json")
loaded = MyProgramClass(); loaded.load(path="optimized.json")

成本预期管理（官方原话）：典型一次简单优化约 $2、10 分钟；区间从几美分到几十美元，取决于模型、数据量与配置。KNNFewShot 的演示选择、COPRO 的坐标上升、SIMBA 的难例挖掘都是公开论文方法，不是黑盒。

10Signature 精读：类型系统即约束

Signature 是整套体系的地基，官方文档给了三档写法，能力逐级递增：

# 1) 内联一行式：快速原型
classify = dspy.Predict('sentence -> sentiment: bool')

# 2) 类声明式：加字段描述（desc 会进提示词）
class Emotion(dspy.Signature):
    """Given a context, judge the emotional tone of it."""
    context: str = dspy.InputField(desc="facts here are assumed to be true")
    sentiment: Literal['sadness','joy','love','anger','fear','surprise'] = dspy.OutputField()
    confidence: float = dspy.OutputField()

# 3) 输出直接吃 pydantic 模型：嵌套结构一步到位
class QueryResult(pydantic.BaseModel):
    answer: str
    sources: list[str]

class DogPictureSignature(dspy.Signature):
    """Classify a dog picture and cite evidence."""
    image_1: dspy.Image = dspy.InputField(desc="A dog picture")   # 多模态字段
    query: str = dspy.InputField()
    result: QueryResult = dspy.OutputField()

三条硬规则：Literal 枚举是输出合法性的第一道闸（枚举外的值难以出现，后续 optimizer 还能进一步收紧）；desc 不是注释，会被 adapter 编译进提示词；输出字段类型映射到 adapter 的解析策略（chat/json/xml 三大 adapter 之外还有 baml/audio/image/tool/citation 等专项 adapter——git 实测 adapters/ 目录 21 个文件）。信息抽取这种复杂任务用 "text -> title, headings: list[str], entities_and_metadata: list[dict[str, str]]" 一行签名就能拿到结构化结果，官方教程带完整输出示例。

12排障速查：五个高频翻车点

症状原因与处置
改了提示词描述但不生效 / 输出格式怪检查 adapter：默认 ChatAdapter 对部分模型偏脆弱，换 dspy.JSONAdapter 或 TwoStepAdapter；字段类型要 adapter 支持
重复调用返回一模一样结果缓存默认开——实验随机性要 cache=False 或传唯一 rollout_id + 非零 temperature
优化跑完分数反而降数据太少过拟合（官方建议 20/80 反向划分验证）；或 metric 写歪——先手动审计 metric 对 10 条样本的打分再跑优化器
token 账单暴涨开 track_usage=True 定位哪个模块烧钱（GEPA 反思循环、MultiChainComparison 多路采样都是消耗大户）；优化器跑之前先估预算（官方：典型 ~$2/次，上限几十刀）
本地模型不识别工具调用Ollama 走 ollama_chat/ 前缀；小模型 ReAct 能力弱，降级到 ChainOfThought + 手动 ToolCalls，或换支持 function calling 的模型

与 04 节速记的差异：04 讲"选哪个优化器"，本节讲"跑歪了怎么办"——两者合起来覆盖官方 FAQ 里出现频率最高的五类问题。v3.x 迭代快（110 个 release），任何 API 对不上时以 dspy.ai 当前版本文档为准，教程代码先看 repo 内 docs/docs/ 的最新版（本卡所有代码均出自 09-26 的 main 分支文档）。

14进阶机制速览：知道有这回事

ASIMBA 难例挖掘——随机 mini-batch 采样找出"输出方差大"的困难样本，让 LM 内省失败原因再改指令；与 GEPA 的轨迹反思同属"自省系"优化，适合错误模式集中的任务。
BBetterTogether 与串行优化——先 few-shot 后指令的组合优化器；官方"多个优化器串着跑"的正式路径：Bootstrap 出演示 → MIPROv2 精修指令，两阶段各自带着 metric。
CAsyncParallel 与生产化——predict/ 目录实测有 parallel.py（并发调用）；tutorials/ 有 async、cache、deployment、custom_lm_engines、core_development 专题；experimental/ 还有 Citations（引文标注）与 ReAnchor。上线前至少过一遍 cache（省钱）与 async（吞吐）两篇。
DAdapter 决定解析成败——21 个 adapter 文件里，ChatAdapter（默认）/JSONAdapter/XMLAdapter 是三主力，TwoStepAdapter 先生成再解析，BAML Bridge 接 BAML 生态，audio/image 处理多模态，citation 自动加引文。签名类型若解析失败，第一反应是换 adapter 而不是改 prompt。

14.5GEPA 与 MIPROv2 参数级对照

03 节讲了两个旗舰的原理，这里补初学者真正需要的"怎么选参数"。两边的成本结构完全不同：

维度MIPROv2GEPA
预算旋钮auto="light"/"medium"/"heavy" 三档，light 最省按 rollout 预算配置；省 rollout 但单次反思本身是 LM 调用
最小数据0-shot 模式可少到十几条；全量建议 200+（官方防过拟合线）官方"最大化训练集"路线，验证集只需反映分布
擅长指令+示例联合搜索，快出基线从失败轨迹学规则——六任务平均超 GRPO 6%（至高 20%）省 35× rollout、超 MIPROv2 10%+（AIME-2025 +12%）
成本感受官方"典型一次 ~$2/10 分钟"反思调用更贵，但 rollout 数少——贵在单次、省在次数
新手第一跑MIPROv2(metric=my_metric, auto="light")数据 ≥200 再上；先在 MIPROv2 基线上比

注意：推理时的 reasoning efforts（low/medium/high/xhigh，默认 high）是 LM 层参数、与优化器无关——但优化出的程序在生产跑高 effort 会成倍放大 token 成本，上线前用 xhigh/high/low 各测一次质量差再定档。

14.6与手写提示词的直接对比：什么变了

用客服工单分类（8 类）+ 关键信息抽取这个具体任务，说明"编程式"到底省了什么：

环节手写提示词路线DSPy 路线
定义任务在字符串里描述 8 类 + 输出格式，祈祷模型听懂"ticket -> category: Literal[...], urgency: int, entities: list[dict]"——类型即约束
格式稳定JSON 靠 few-shot 哄，偶尔崩adapter 层保证解析；Literal 限死枚举
换模型每个模型重新调措辞（格式偏好不同）改一行 dspy.LM('...')，其余不动
质量提升人工改词 → 跑 → 再改，凭感觉标 20-50 条 + 一个 metric，BootstrapFewShot 自动找演示
多步管道每环节一条提示词，断点自己拼多个 Module 组合成类（如 Hop），compile 一次全优化
沉淀最佳提示词躺在聊天记录里optimized.json 版本化，可 diff 可回滚可审计

这就是推文那句"改需求就是改代码，不是回去抠措辞"的完整展开——每一行收益都对应 DSPy 的一层抽象，没有魔法。

16生态位：什么时候不该用 DSPy

四倍篇幅里必须有这一节——DSPy 不是所有 LLM 应用的默认答案，官方 optimizers 指南自己都说"找对的优化器需要实验，成功仍是迭代过程"。

场景该用 DSPy 吗原因
一次性脚本、单条提示词任务不该四层抽象是 upfront 投资，单次任务手写更快
没有任何评测数据的探索期项目暂时不该优化器全部依赖 metric——先攒 20 条再回来
纯聊天产品（开放式对话）谨慎DSPy 强项是"有明确输入输出契约"的任务；闲聊没有可优化的 metric
多步 RAG / agent / 分类 / 抽取对口可分解、可评测、可组合——正是框架设计目标
频繁换底层模型的团队对口签名/模块/模型解耦，换模型零重写
需要提示词资产化管理对口optimized.json 是版本化资产而非聊天记录碎片

社区坐标系：DSPy（学术系、优化器驱动）之外，LangChain 重连接器生态、LlamaIndex 重 RAG 数据接入、Instructor 重单次结构化输出——DSPy 的独特卖点是程序级优化（"编译"整个管道而非单个调用）。v3.x 的 RLM、CodeAct、Grok Build 式 CLI 等新模块说明它在向 agent 运行时扩展，但核心心智模型始终是：Signature 声明契约 → Module 组织策略 → Optimizer 用数据换质量。

16.5生产部署检查单：上线前 8 项

从"能跑"到"能上线"，按这份清单过一遍（每项都能在前文找到对应机制）：

  1. 缓存策略定型——生产重复请求多：保留默认缓存省成本；A/B 实验环境单独 cache=False。
  2. usage 追踪常开——dspy.configure(track_usage=True) + 每个 Prediction 的 get_lm_usage() 上报到监控，token 是你的电费单。
  3. 优化产物入库——optimized.json 进 git：可 diff、可回滚、code review 时能看到"提示词到底改了什么"。
  4. metric 与线上反馈对齐——离线 metric 分数涨 ≠ 用户满意涨；留一路线上标注回流到训练集（官方评测指南的数据循环）。
  5. 失败路径显式化——ReAct 的 max_iters 到顶、adapter 解析失败、Literal 外输出，都要有兜底分支而非裸异常。
  6. 本地模型压测——Ollama/vLLM 接入后，并发下 latency 与云模型差异巨大；async 教程的 AsyncParallel 先在预发压测。
  7. 成本护栏——LM 配置里 max_tokens 设上限；GEPA/多候选程序只在离线跑，不进请求热路径。
  8. 版本锁定——v3.x 迭代快，pyproject 锁具体版本；升级前先在分支跑一遍 metric 回归。

零数据冷启动三步（评测指南给的路径）：① HuggingFace/StackExchange 找许可兼容的邻近数据集；② 不够就手标最小集（20 条起）；③ 直接上线 demo 收集真实输入当第一批训练数据——DSPy 的优化循环天然欢迎"边跑边攒"。

另一条冷启动路径是 metric 即程序：长文本任务先写一个用大模型打分的小 DSPy 程序当 metric，因为它的输出只是一个分数，"metric 的 metric"几条样本就能优化——先用弱 metric 起步，随数据增长迭代成结构化评分。

17判断

四个折扣点：① 优化器要标注数据和 metric——没有评测集的项目享受不到核心收益，"零成本变强"不存在；② GEPA 的反思循环要跑多次 LM 调用，token 账单比手写一条提示词贵（省的是 rollout 数，不是免费）；③ v3.x 迭代快（110 个 release），教程与 API 版本错位的坑在社区 issue 里常见，跟官方 docs 版本走；④ 抽象有学习成本——Signature/Module/Adapter/Optimizer 四层概念对新手是 upfront 投资，单个一次性提示词任务用 DSPy 是杀鸡用牛刀。

判断：DSPy 是"提示词工程软件化"这条路上最认真的学术系实现——38K★、736 个活跃 issue、三天一个 release 的社区热度是真的。它换来的核心能力是可移植（换模型不重写）和可优化（数据进、质量出），适合：多步管道（RAG/agent）、要长期维护的 AI 功能、频繁换底层模型的团队。不适合：一次性问答、没有评测数据的探索期项目。推文那句话是准的：提示词不该是手艺活，该是能被编译和优化的代码。
