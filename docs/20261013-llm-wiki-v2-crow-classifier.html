JUDGMENT

核心问题不是让 LLM 随意决定文档放哪，而是用一个小型分类器做路由决策，保持维基增长时的一致性。

经典模式 LLM 逐层决策，路由准确率仅 62%；CROW 分类器每步类型化任务，准确率 89%。

§1 CROW 工作原理 · 两条流水线原文
CROW 遵循 CROW: Classifier-Routed Organization of LLM Wikis（Cesarini & Sassarini, 2026）。 两种模式跑同一条流水线，写同一种维基，只有决策者不同。
INGEST PIPELINE
summarize → route → find match → merge or (new folder →) write → relate → link, index, log
ASK PIPELINE
select notes (navigate the tree) → answer from them, with [path.md] citations
§2 经典模式 vs CROW 模式 · 七步逐行对照
步骤 经典模式（OKF_MODE=classic） CROW 模式（OKF_MODE=crow）
① 把来源摘要成笔记 LLM 摘要 LLM（可选，OKF_SUMMARIZE=false 则原样归档）
② 路由：最佳文件夹 LLM，逐层决策 分类器每层 Choice + beam search，LLM 回退
③ 与已有笔记同主题？ LLM 判断 分类器每篇笔记 Noul（是否/Yes-or-No）
④ 合并还是写新笔记？ LLM 决策 分类器 Choice（选哪个），不确定 → 新笔记
⑤ 命名文件夹 · 重写合并笔记 LLM LLM（分类器不写内容）
⑥ 相关笔记（See also） LLM 推理 分类器每篇笔记 Noul
⑦ 为问题找笔记 LLM 导航树 分类器每文件夹每笔记 Noul，LLM 回退
⑧ 写答案 LLM LLM（分类器只决策，不生成）
类型化任务概念区分：Noul（Yes-or-No，判断同主题/是否相关）和 Choice（从候选列表选最佳文件夹）， 是分类器比通用 LLM 更高效的两个任务类型。论文（Cesarini & Sassarini, 2026）定义，代码在 src/llmw2/agents/steps/crow/。
§3 CROW 论文出处
REFERENCE
F. Cesarini, M. Sassarini, CROW: Classifier-Routed Organization of LLM Wikis, version 5, 2026.
DOI: 10.5281/zenodo.22898752
维基格式基于 Google Open Knowledge Format OKF v0.2（Apache-2.0）。
类型化任务：CROW 的核心是两个类型化任务——Noul（Yes-or-No，二分类：同主题/是否相关）和 Choice（从候选列表选最优）。分类器比通用 LLM 在这两个任务上更高效，且 token 消耗更少。 阈值和 LLM 回退机制见 docs/wiki/crow.md。
§4 双账本 Token 计费
LLM 和分类器的 token 消耗分开记账，按模型和按操作统计。调用链中每一步都记录。
账本 内容 查询方式
llm 摘要、命名、答案生成、文件夹描述等所有 LLM 调用 wiki.usage['llm'] / GET /usage
classifier 所有分类器调用（Noul + Choice），独立于 LLM provider wiki.usage['classifier'] / GET /usage
by_model 按模型拆分，列出每个模型各消耗多少 token wiki.usage.to_dict()
OKF_USAGE_LOG 每次模型调用写一行 JSON（可开启用于审计） 文件追加写入 wiki 目录
每次 IngestResult 和 Answer 各自带 usage 字段；wiki.usage / GET /usage 返回总量。 OKF_UPLOAD_MB=25 限制单次上传最大 25 MB（超限返回 413）。

§7 与 OKF v0.2 的关系
维基符合 OKF bundle 规范（§11）：每篇笔记有带 type 的 YAML frontmatter，index.md 和 log.md 遵循 §8 和 §9。 在此之上加了 4 条自己的约定：
  • 每个文件夹都有 index.md，文件夹描述就是它在父索引里的条目（OKF 索引可选）
  • 链接是相对的（OKF 推荐 bundle 绝对路径 /… 链接），check 报告断链
  • raw/ 放来源（type: Source），# See also 放相关笔记，只有根目录一个 log.md
  • 根目录不放笔记：每篇笔记归在主题文件夹里，新主题第一篇笔记开启一个文件夹
不使用
OKF 的信任和生命周期字段（verified、status、stale_after）、 attested computations（§10）或 references/ 约定。维基不做 OKF 后续版本的校验。 项目始于 OKF 的 fork，现已不含其代码。
§8 完整 HTTP API 端点表（13 行）
Web UI 在 http://localhost:8000，显示文件夹树、渲染笔记、带引用的答案和双账本 token 用量。
端点作用
GET /Web UI
POST /ingest {text, title?, resource?, origin?}归档来源（带 origin 时重复提交返回 "unchanged"）；返回笔记、创建的文件夹、链接和 token 用量
POST /upload?filename=…（原始文件体）归档 .txt / .md / .pdf（超过 OKF_UPLOAD_MB=25 返回 413）
POST /ask {question}带引用回答；返回读过的笔记和 token 用量
GET /tree · GET /note?path=…文件夹树 · 单篇笔记（frontmatter + Markdown 正文）
GET /check · GET /graphlint 问题（OKF 一致性、索引漂移、断链） · 维基节点与链接图（JSON）
POST /note/move {path, folder}移动笔记到另一文件夹，链接跟随（返回与 GET /note 相同）
POST /folder/describe {path, description}改文件夹描述（librarian 路由依据的那一行）
POST /audit {min_confidence?, apply?}CROW：分类器今天会把笔记归到别处的清单（apply 为真则移动）
GET /taxonomy按文件夹和月份统计新增子文件夹与 LLM 回退次数（从 log.md）
DELETE /note?path=…删笔记；指向它的链接从其他笔记移除
DELETE /folder?path=/…连内容一起删文件夹；没有笔记再引用的原始副本也移除
DELETE /wiki全删（Empty the wiki）
GET /usage各账本和各模型的 token 总量（llm / classifier / by_model）
GET /health维基状态
GET /settings · POST /settings · POST /settings/testprovider、模型和 key（掩码） · 保存 · 测试连接；改动只来自本机
§9 配置环境变量（12+ 关键变量）
工程默认值比论文保守。 TIMEOUT 默认 8 秒（论文用 60）、ATTEMPTS 默认 1（论文用 3）—— 这是速度 vs 可靠性的工程取舍：论文在受控环境测最大值，工程在真实网络测稳定最低延迟。
变量默认值含义
OKF_BUNDLE~/llm-wiki维基文件夹（CLI）/data/wiki（Docker）
OKF_MODEcrowcrow（分类器路由）或 classic（LLM 决定）
OKF_LLM_PROVIDERopenrouteropenrouter / openai / gemini / ollama / custom
OKF_CLASSIFIER_PROVIDERopenrouter分类器跑在哪，独立于 LLM：openrouter / typesafe / custom
OKF_CLASSIFIER_MODELtypesafe/jev-1.13CROW 分类器，固定版本（❓第三方服务可用性与定价未说明）
OKF_CLASSIFIER_TIMEOUT8每次分类器调用秒数；慢或失败转 LLM（论文用 60，❓）
OKF_CLASSIFIER_ATTEMPTS1转 LLM 前的尝试次数（论文用 3，❓）
OKF_UPLOAD_MB25服务器接受的最大文件或文本（超过返回 413）
OKF_CONCURRENCY4sync、网页和 ingest_many 同时读取摘要的文档数（1–16）；归档仍一次一个
OKF_LLM_READ_CHARS100000 / 16000一次 LLM 请求能装的字符数（OpenRouter/OpenAI/Gemini 100000，Ollama/custom 16000）
OKF_NOTE_CHARS10000笔记正文约多少字符（至少 1000），不超过单次请求容量的一半
OKF_LLM_REASONINGfalsetrue 让模型先思考再答：慢数倍且更贵
OKF_LLM_SEED—每次 LLM 请求带的种子；支持的 provider 对同一 prompt 给出同一答案
OKF_LLM_PIN_PROVIDER—仅 OpenRouter：按顺序允许回答的 provider 列表，逗号分隔，无回退

§11 零 key 路径：Ollama 本地
没有 key？ 选 Ollama：免费、跑在本机、不用账号。 下载 Ollama 后运行 ollama pull gemma4 下载模型。 CROW 分类器有自己的 provider（Settings → Advanced）： OpenRouter、TypeSafe 或本地服务器。没有的话 wiki 自动降级到经典模式（LLM 决定）。 一个 OpenRouter key 通吃所有模型，包括 CROW 分类器。

§15 CROW 专有命令
audit — 分类器路由审查
llmwiki2 audit [--min-confidence 0.7] [--apply]
列出分类器今天会归到别处的笔记（不调 LLM）；加 --apply 才实际移动。 min-confidence 默认 0.7，即置信度 ≥70% 的建议才列入。
health — 维基健康度检查
llmwiki2 health [--min-filed 5] [--max-share 0.3]
从 log.md 显示哪些文件夹持续需要新子文件夹（min-filed=5）或 LLM 回退比例过高（max-share=0.3，即该文件夹 30% 笔记经过 LLM 回退）。
§16 Sync 与 SourceConnector 接口
让维基与来源保持同步。Origin 保留原件位置：未改动的文件不花模型调用，被删的在原始副本里标记而笔记保留。 上次同步的游标保存在维基内 .llmw2/sync/。 
from pathlib import Path
from llmw2 import LocalFolderSource, sync

report = sync(wiki, LocalFolderSource(Path("~/OneDrive")))
print(report.to_dict())   # created, merged, unchanged, removed, skipped, errors
