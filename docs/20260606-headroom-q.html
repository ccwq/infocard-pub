Headroom：给 AI Agent 加一层可逆的上下文压缩层

Headroom 先压缩再送进 LLM：把 tool outputs、logs、RAG chunks、files 和对话历史变成更小的上下文包，同时保留可检索原文，目标是“同样答案，更少 token”。

核心判断：它不是“再一个压缩工具”，而是 AI agent 的上下文基础设施。

与 provider-native compaction 不同，Headroom 以 local-first 的方式接管压缩、检索、记忆和多 agent 共享，强调可逆、可复用、可插入任意框架。

01
一句话结论

把“压缩”从模型内置能力，变成 AI 工作流前面的独立基础设施

Headroom 的价值不在于它会压缩文本，而在于它把压缩做成了可插拔层：库、代理、MCP、跨 agent memory、失败学习都能挂上去。

Headroom compresses everything your AI agent reads — tool outputs, logs, RAG chunks, files, and conversation history — before it reaches the LLM. Same answers, fraction of the tokens.
它解决的痛点

上下文窗口被工具输出、日志、RAG 和历史对话撑爆

对 AI coding agent 来说，最贵的不是“模型调用”，而是被无效上下文吞掉的 token。Headroom 的定位就是在这个成本黑洞前面做截流。

它的边界

它不替代模型，也不替代你的 agent，而是接管输入侧的上下文工程

如果你要的是 provider 自带 compaction，它不是唯一答案；如果你要跨 agent、跨框架、可回取的本地压缩层，它就很合适。

02
它怎么组成

四种入口 + 两个底层能力，拼成同一条压缩链

README 的结构很清楚：先给“你能怎么接”，再给“压缩发生在哪里”，最后给“原文如何可回取”。

Library

compress(messages)

Python / TypeScript 可直接调用，适合把压缩当成应用内部函数，而不是外挂工具。

Proxy

headroom proxy --port 8787

零代码改造，把任意语言接入同一套压缩路径，适合已有系统做低侵入改造。

Wrap

wrap claude / codex / cursor / aider / copilot

把压缩层直接挂到常见 agent 启动命令上，减少额外配置成本。

MCP

headroom_compress / retrieve / stats

让任何 MCP client 都能把压缩、检索和统计接进来，适合工具链生态化。

03
工作原理

关键不是“压短”，而是“按内容类型压对”

Headroom 不是一个黑盒摘要器，而是先识别内容类型，再选择对应压缩器，并保留原始内容以便 later retrieval。

JSONSmartCrusher：适合 tool output、结构化日志、对象数组和混合类型数据。
ASTCodeCompressor：面向 Python / JS / Go / Rust / Java / C++ 等代码语法树。
TextKompress-base：训练在 agentic traces 上，负责 prose / RAG / conversation 压缩。
CacheAligner

让 provider KV cache 真正命中

它不仅压缩，还会稳定前缀，减少无谓的重复 token，提升缓存命中率。

CCR

可逆压缩：原文保留，本地可取回

这是 Headroom 的关键差异点：不是丢失后再猜，而是把原始内容存下来，需要时由 LLM 触发 retrieval。

05
适配矩阵

对多 agent / 多框架 / 多客户端都友好

它的设计目标不是锁死一个生态，而是让压缩层尽量“到处都能插”。

Agent Compatibility

Claude / Codex / Cursor / Aider / Copilot / OpenClaw

README 明确给出 wrap 模式兼容矩阵，说明它已经在常见 agent 启动入口上做了适配。

Frameworks

LangChain / Agno / Strands / ASGI / Vercel AI SDK / LiteLLM

更像基础设施，而不是单一产品：可以嵌入应用层、服务层和工作流层。

适合

当你每天都在跑 agent，且 token 成本已经变成真实痛点

  • 多 agent 共享记忆
  • 需要把原文可回取
  • 希望最小改动接入
不适合

当你只想用 provider 自带的压缩，不需要本地控制层

  • 环境无法运行本地进程
  • 完全不需要跨 agent memory
  • 愿意接受黑盒 provider 策略
06
快速上手

三步就能看见 token 节省，四类 extras 再决定深度接入

README 的使用路径非常直接：安装、选择模式、再跑 perf 观察压缩收益。

最小安装

Python / Node 一次装好

# 1 — Install pip install "headroom-ai[all]" npm install headroom-ai # 2 — Pick your mode headroom wrap claude headroom proxy --port 8787 # 3 — See the savings headroom perf
Extras

按需加载：proxy / mcp / ml / code / memory / relevance / image

它不是“全塞一起”的工具，而是把能力拆成 extras，便于按场景精确接入。

关键链接：GitHub Repo · Docs · Kompress-base
07
最终判断

Headroom 适合被当成“上下文压缩基础层”，而不是单次摘要器

它最大的价值，是把压缩、缓存、检索、记忆和失败学习都放到一个可复用的本地层里，方便多个 agent / 多个框架一起吃到收益。

一句话推荐

如果你已经在日常用 Claude Code、Codex、Cursor 这类 agent，Headroom 很像“给它们统一装一个上下文减重器”。

一句话边界

它不是 provider-native compaction 的替身，而是更偏工程侧、跨生态、可逆的本地压缩层。
