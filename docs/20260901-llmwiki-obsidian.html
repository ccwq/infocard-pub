02

三种模型连接路线

最快、通用、隐私优先；费用与数据边界不同。

A · 最快

ChatGPT Plan / Codex OAuth

插件 Provider 中选择后，用浏览器或设备代码登录。

  • 无需另填 Platform API Key
  • 凭据按插件说明进入 SecretStorage
  • 使用资格与额度遵循 Codex 政策
重要边界

社区插件的实验性第三方兼容功能；不是通用 ChatGPT API，也不是 OpenAI 合作插件。

验收

测试连接＋一篇短 MD 成功。

B · 通用

OpenAI-compatible API

填写 Provider、API Key、模型；自定义端点还需 Base URL。

  • OpenAI、DeepSeek、OpenRouter 等
  • 通常独立按量计费
  • ChatGPT 订阅不抵扣 Platform API
常见错误

模型名、/v1、协议、401/404/429。

验收

先短文件，检查账号用量。

C · 隐私

Ollama / LM Studio

模型在本机运行，适合敏感资料和短 Query。

  • Ollama：localhost:11434
  • LM Studio：localhost:1234/v1
  • 占磁盘、显存/内存
主要代价

小模型长文抽取、中文和 Schema 遵循可能降质。

验收

断网后短 Query 仍成功。

# Ollama 示例（模型按硬件选择） ollama run qwen3:8b # 原生 API 默认 http://localhost:11434/api
# LM Studio Developer 页也可启动 lms server start # OpenAI-compatible http://localhost:1234/v1

04

9 个标准工作流

每张卡都有输入、动作、产物、验收、错误和可复制提示词。

WORKFLOW 01

首次安装与四方协作

输入 / 产物

空测试 Vault＋Provider＋短材料 → sources/entities/concepts/index。

  1. 插件测试连接并摄取
  2. Agent 只建目录与规则
  3. 人工检查 Raw 未改和回链
验收

原文未改、来源可追、Query 有回链。

常错

直接用主库；连接失败仍继续；双方同时写。

只读检查首次摄取结果：Raw 是否不变、生成页面、来源回溯、空页/重复/死链，以及能否进入下一篇。
WORKFLOW 02

单篇 Markdown 最小路径

输入 / 产物

raw/inbox/article.md → 来源页、概念页、实体页、索引。

  1. 打开并 Ingest single source
  2. 查概念颗粒度和别名
  3. Agent 仅提出修正
验收

概念有独立价值，不为普通名词建页。

常错

“摘要流畅”误当“事实可靠”。

审查本次摄取：事实失真、无来源判断、粒度过细、别名缺失、双链错误。给路径和建议，不修改。
WORKFLOW 03

Web Clipper 网页剪藏

输入 / 产物

URL → raw/web/*.md＋raw/assets/＋Wiki 来源页。

  1. 剪藏正文并保留作者/URL/日期
  2. 清导航与广告噪声
  3. 逐篇摄取并检查重复
验收

正文完整、图片有效、来源 URL 存在。

常错

只存链接；整页导航；同文重复。

检查 raw/web/：正文、元数据、重复、失效图片和动态内容。分类为可摄取/需清洗/不完整，不改 Raw。
WORKFLOW 04

PDF／DOCX 转换与摄取

输入 / 产物

原件＋转换 Markdown＋Wiki；Office 原件永久保留。

  1. PDF 原生 Provider 或 MinerU
  2. Office 先转 Markdown
  3. 对照抽查结构、数字、图表
验收

抽查 3 节、1 表、1 数字、1 脚注。

常错

OCR 当无误原文；DOCX 直接摄取。

对照原件与 Markdown，检查标题、遗漏、数字、表格、脚注、图片和不可辨识标记。列差异与阻断项。
WORKFLOW 05

每日 Inbox、去重与审核

输入 / 产物

每日若干 MD → 3–10 篇可控摄取批次。

  1. Agent 先盘点和去重
  2. 用多选文件，不急着整文件夹
  3. 抽查来源页与两个概念页
验收

无重复来源；失败项可单独重试。

常错

数百篇一次跑；失败后整批重跑。

盘点 raw/inbox/：按主题分组，标重复、缺元数据、过短、OCR 失败。建议最多 10 篇顺序。
WORKFLOW 06

多来源研究与冲突

输入 / 产物

独立来源页 → 证据矩阵＋syntheses＋待调查问题。

  1. 逐份摄取，不拼大文件
  2. Agent 建支持/反对证据矩阵
  3. 保留时间与适用条件
验收

关键判断回链；相反观点都保留。

常错

多数票判真伪；新资料覆盖旧资料。

为【主题】建证据矩阵：主张、支持/反对来源、时间、条件、强度、缺口。先输出，不写入。
WORKFLOW 07

Query 与稳定结论写回

输入 / 产物

Vault 内问题 → 带回链回答；有价值才写 syntheses。

  1. Query wiki 并检查 [[links]]
  2. 无匹配源时明确未知
  3. Agent 给写回大纲后再落盘
验收

事实、综合判断、未知分开。

常错

把 Query 当联网搜索；聊天全写回。

基于 wiki/ 回答【问题】。先读 index；关键判断链到来源；区分事实、综合判断、未知。值得写回时先给大纲。
WORKFLOW 08

Lint 与知识保养

顺序

备份 → Lint → 别名 → 重复 → 死链 → 孤立/空页 → 索引 → 再 Lint。

  1. 先看计数与影响
  2. 重要页 reviewed: true
  3. 高风险合并人工确认
验收

二次问题下降，审核页未覆盖。

常错

无备份一键修；孤立页全删。

分析 Lint 报告，分安全自动修复/人工判断/暂时保留；说明影响文件和回滚，不直接修改。
WORKFLOW 09

软件项目知识库

输入 / 产物

PRD＋PDF 调研＋会议 → requirements、architecture、ADR、Backlog、syntheses。

  1. 插件建立来源/实体/概念
  2. Agent 建工程视图与任务
  3. 变更时先影响分析再更新
验收

需求回链；Backlog 指向需求/ADR。

常错

让 LLMWiki 替代 Backlog；冲突静默覆盖。

先输出项目目标、角色、功能、非功能要求、依赖、冲突、风险、待确认项与拟修改文件。确认后再更新并逐文件验收。
05

完整案例：DOCX＋PDF → 结构化 Markdown Web 服务

LLMWiki 提供可追溯知识，Backlog 承担任务管理。

阶段 1

资料变成项目知识

PRD.docx 先转 MD；PDF 调研、DOCX 结构说明、会议纪要分别摄取。

插件产出

角色、组件、格式、OCR、版面分析、AST、来源定位等页面。

阶段 2

Agent 建工程视图

写 requirements、architecture、ADR、Backlog、system overview。

任务字段

角色、输入、输出、依赖、验收、状态、证据链接。

阶段 3

需求变更闭环

新会议纪要 → 插件摄取 → Agent 影响分析 → 人工确认 → 跨文件更新 → Lint。

铁律

旧 PRD 不改；冲突保留日期、来源和条件。

projects/doc-parser/
├─ raw/{PRD.docx, PDF解析调研.pdf, DOCX结构说明.md, meeting.md}
├─ specs/{requirements.md, architecture.md}
├─ decisions/ADR-001-parser-strategy.md
└─ Backlog.md
wiki/syntheses/doc-parser-system-overview.md
06

最小可用 Schema

AGENTS.md 与 CLAUDE.md 可共用这些原则；插件配置仍需单独设置。

# LLMWiki Vault 维护规则

## 所有权
- raw/：只读，禁止改删。
- sources/entities/concepts：插件主写。
- syntheses/projects：Agent 获准后写。

## 并发
- 插件写入时 Agent 不写。
- Agent 批改时不运行插件。
- 大改前保存版本。

## 修改
1. 先只读影响分析。
2. 列拟修改、风险、回滚。
3. 确认后写入。
4. 逐文件报告。
5. 验证来源、链接、索引、Lint。

完成条件

  • Raw 未改变
  • 新结论可回溯 sources
  • index 已同步
  • 无新增死链/无来源断言
  • 冲突和未知显式记录

Schema 不会自动共享

插件使用自己的设置、抽取粒度和标签词表；Agent 使用 AGENTS.md/CLAUDE.md。两边规则需要人工保持一致。

07

排错从症状到根因

先定位连接、格式、模型还是协作冲突。

401 / 404 / 429

401 查 Key/登录；404 查 URL、模型名、协议；429 查额度、速率和批量。

下一步

短文件重试，不整批重跑。

本地模型连不上

确认 Ollama/LM Studio 已启动、端口正确、模型已加载、防火墙未拦截。

下一步

先用本地客户端对话，再测插件。

PDF / DOCX 失败

PDF 查 Provider 是否原生；Office 先转 Markdown；复杂文档查转换后端和 OCR。

下一步

对照原件抽查，不信任一次转换。

页面重复或空洞

查重复来源、别名、抽取粒度、小模型 Schema 漂移。

下一步

Lint 后人工确认合并。

Query 像在胡说

检查回答是否有匹配 Wiki 源和来源页；无信号时允许回答“未知”。

下一步

补来源，不靠提示词强答。

同步冲突

停止双方写入，保留冲突两版，按来源和 Git 历史人工合并。

预防

电脑批改；手机收集/阅读；同页不并发。

✓

L3 费曼检验

能解释职责与后果，才不只是会点按钮。

场景：三个月前 PRD 与今天会议纪要冲突，OCR 验收标准改变。请说明：为什么不能覆盖旧 PRD？插件与 Agent 各做什么？更新哪些文件、保持哪些不变？怎样证明完成且可回滚？

合格信号：Raw 不变；插件摄取新来源；Agent 影响分析后更新 requirements、architecture、ADR、Backlog、syntheses；index/log 同步；修改前保存版本、修改后 Lint；冲突保留来源、时间与条件。
一句话带走：插件把资料编入 Wiki，Agent 把 Wiki 用进真实工作；Obsidian 让你看见和审核，Markdown 让成果持续存在。
