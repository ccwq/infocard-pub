从 CoT 到 ReAct：用 Python 搭一个会规划、用工具、验证和复盘的 LLM Agent

CoT、ReAct、Reflexion、Refinement、Tool Calling——这些概念不是可以互相替代的提示词技巧，而是在解决不同的工程问题。本文用 Python 从零搭出一个最小但完整的 Agent，把每个方法还原成五个独立模块。

一、为什么名词越来越多，系统还是不稳定

很多 LLM 项目一开始很简单：把用户问题放进 Prompt，调用一次模型，返回文本。真正投入使用后，问题才出现：

  • 模型漏掉约束，在错误方向上越想越远
  • 声称查过并不存在的资料
  • 工具失败后重复同一个动作

于是开始接触 CoT、ReAct、Reflection、Reflexion、CoVe——名词越来越多，系统依然不稳定。原因在于：这些概念在解决不同的工程问题，不能互相替代。

二、五个模块的数据流

用户任务
↓
Planner：拆解目标与约束
↓
ReAct Loop：选动作→调用工具→读取观察
↓
Verifier：检查证据、约束和矛盾
↓
Refiner：修改答案
↓
Reflection Memory：保存失败经验

三、第一步：建立直接回答的基线

多步骤工作流一定会增加 Token、延迟和故障点。新方法不能稳定超过单次调用，就是更复杂、不是更好。建议先记录四个指标：

  • 任务成功率
  • 事实/证据错误率
  • 平均响应时间
  • 每个成功任务的平均成本

四、第二步：Plan-and-Solve 代替无限展开的 CoT

CoT 生成一串帮助模型得到答案的中间文字。Plan-and-Solve 则要求模型输出可执行计划：目标是什么、有哪些约束、需要哪些步骤、什么条件代表任务完成。

PLANNER_SYSTEM = """ 你是任务规划器。只返回 JSON： { "goal": "最终目标", "constraints": ["必须满足的约束"], "steps": [{"id":1,"objective":"...","needs_external_info":true,"success_condition":"..."}] } 不要执行任务，不要虚构已经获得的信息。 """

Plan-and-Solve 与 CoT 的核心区别：CoT 生成帮助模型得到答案的文字；Plan-and-Solve 生成系统能够执行和检查的任务步骤。计划应该是状态，不应该只是散落在上下文中的文字。

五、第三步：ReAct 连接外部工具

模型无法通过"继续思考"获得实时网页、数据库或代码执行结果。只要任务依赖外部状态，就需要让模型行动。

def run_react(task: str, plan: dict, max_steps: int = 6) -> dict: history = [] for step_no in range(1, max_steps + 1): action = parse_json(call_model(AGENT_SYSTEM, json.dumps(context))) if action["type"] == "final": return {"status": "completed", "answer": action["answer"], "evidence": action["evidence"]} if action["type"] == "tool": observation = TOOLS[action["tool"]](**action["args"]) history.append({"id": f"observation-{step_no}", "action": action, "result": observation[:6000]}) return {"status": "max_steps_exceeded"}

ReAct 三步循环：Reason（现在应该做什么）→ Act（调用某个工具）→ Observe（读取真实结果）→ 再 Reason……

六、第四步：把"反思"拆成 Verifier 和 Refiner

Verifier：检查约束、证据和矛盾

根据任务、计划、观察和候选答案进行检查，返回 pass / revise / fail。不得用常识替代不存在的工具证据。

Refiner：根据问题修改答案

只根据明确问题修改，不得引入 observations 中没有依据的新事实。如果证据不足，返回 needs_more_tools=true，让 Agent 获取新证据。

Self-Refine 的关键：不要让模型一边维护原答案，一边随手确认自己是否正确。把验证变成一个独立任务。如果任务允许，接入确定性验证器（测试、编译器、Schema 检查）。

七、第五步：Reflexion 保存失败经验

Self-Refine 改进当前答案，Reflexion 解决"为什么 Agent 下次还会犯同样的错"。生成一条简短、可检索、可执行的经验：

REFLECTION_SYSTEM = """ 只返回 JSON： { "trigger": "什么情况下应该想起这条经验", "failure_pattern": "本次失败模式", "lesson": "以后应采用的具体策略", "avoid": "不要重复的动作" } """

只有满足以下条件才值得保留：对应明确失败模式；能转化成未来可执行动作；不依赖已过期的临时状态；没有和现有经验重复或冲突。

八、选型表：失败在哪层，就补哪层

漏掉约束、步骤混乱

→ Plan-and-Solve
✗ 不要直接增加更多 Agent

过早选择错误方案

→ Self-Consistency / ToT
✗ 不要只让同一答案写得更长

缺少实时信息

→ ReAct / Tool Calling
✗ 不要继续要求模型回忆或自编

答案不准确

→ PAL / 执行器 / 测试
✗ 不要依赖自然语言自检

缺少证据

→ CoVe / Verifier
✗ 不要只追加"请确认"

多次任务重复犯错

→ Reflexion Memory
✗ 不要保存全部原始轨迹

九、上线前六项检查

  • 所有循环都有上限：ReAct、Self-Refine、ToT 必须有最大次数或最大 Token，否则 Agent 不可控
  • 工具权限分级：搜索/读取可自动执行；发送消息、修改数据、付款需严格校验和人工确认
  • 工具输出不等于可信指令：网页、邮件中可能含 Prompt Injection，工具结果应被视为不可信数据
  • 验证器尽量外部化：测试、编译器、Schema、数据库约束通常比模型置信度更可靠
  • 记忆可删除和过期：为每条经验保存来源、时间、适用范围；过期经验需淘汰
  • 评价完整任务，而非单次回答：记录工具调用成功率、无效调用比例、验证后修订率、失败恢复成功率

十、核心原则

好的 Agent 不是"思考得最多"的 Agent，而是能在正确的位置获得反馈，并让每一步都可以被观察、验证和停止的系统。先建立直接回答的基线，然后加入计划、工具调用和确定性验证。只有当评测证明某类错误仍然重复出现，再增加搜索或记忆。
