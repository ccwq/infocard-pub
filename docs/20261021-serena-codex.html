深度核查：90% 从哪来，为什么三份实测互相打架

来源：X @goan999999（2026-10-20）· oraios/serena README 与官方文档 · 官方评测 · 三份第三方独立实测

1. 原帖说了什么，缺了什么

原帖的核心是一句「Codex 6.1 接入 Serena，token 消耗直接降低 90%」，配了一段可复制的安装提示词和三条收益说明。它没有给仓库地址、任务集、模型、token 统计口径，也没说这个 90% 是单任务还是多次平均。

我去查了 Serena 的官方 README、官方文档和官方评测页。官方对效果的表述全部是定性的加调用次数表，没有任何一个 token 百分比。这不是官方在回避数字，而是它的评测方法本来就不统计 token——统计的是「同样一件事，Agent 发了几次调用、每次发多少字符」。

拿不到的部分90% 没有仓库、没有任务、没有模型、没有统计口径，也没有可复现的测法。
能拿到的部分官方评测的逐项调用次数与 payload 大小，以及三份第三方实测各自的 token 数字。

2. 官方评测到底测了什么

官方评测用 Claude Code（Opus 4.6，medium）在 Tianshou——一个约 26K 行、43 个源文件的 Python 强化学习库——上跑 20 个日常任务，Serena 侧接的是 JetBrains 后端。它给出的关键对照是这些：

操作Serena内置工具差在哪
跨文件重命名1 次调用9 次（1 Grep + 4 Read + 4 Edit）Serena 原子完成，import 自动改写；内置链路的中间态不一致
跨模块移动符号1 次调用约 8–12 次目标文件需要的依赖 import 也一并补上
结构概览1 次，JSON 树1 次，正则Serena 返回 14 个类的嵌套结构约 2.5KB；正则只给 54 行平铺文本，而且那条正则是 Python 专用启发式
查引用63 个代码文件83 个文件Grep 多出来的是 README、CHANGELOG 和 .ipynb，不是代码
类型继承链1 次，传递闭包2 次以上迭代 Grep内置方式要手工做闭包
改 1 行送约 550 字符送约 120 字符小改动内置更省：Serena 要先取整个函数体
重写整个函数（55 行）送约 2,200 字符约 4,400 字符（旧 63 行 + 新 62 行）Serena 只送替换后的部分，约省一半
官方自己的结论带明确分界：跨文件重构强正向，结构化导航中等正向，小改动「持平或略负」；纯文本搜索、shell、git、非代码文件不在它的能力范围内。

注意这张表里没有 token 数字，只有字符数。把字符换算成 token 要看具体模型和上下文，本卡不做这个换算。

3. 三份第三方实测，各自测到了什么

这三份都不是官方出品，方法各不相同，结论也各不相同。放在一起看，比单看任何一份都诚实。

实测方法结果局限
九工具 token 基准 2026-07-08 9 个工具分四层对照，约 30 文件 Python 应用，8 个理解类任务加 1 个生成任务，tiktoken o200k_base Serena 2,906 token 对无工具基线 8,564，−66.1%；叠加 rtk 与 caveman 到 −69.6% 9 个工具里 2 个是建模不是实跑；同一份报告里另一款同类工具是 +15.7%，说明同一测试床上这类工具会分出胜负

三份实测指向同一条判断：Serena 的价值取决于仓库形态和模型强度，不是一个与两者无关的固定百分比。

4. 为什么强模型用不上它，弱模型反而需要

第三份实测里最强和最弱的模型表现完全相反。强模型本来就能靠 grep 加读文件把事情做对，Serena 给它的只是一份额外的 schema 开销。弱模型的问题恰恰在于文本替换会自信地做错事：重命名 UserRepository.save 时把毫不相关的 Logger.save 一起改掉，波及 8 个文件，而且通过了 typecheck 和 lint 这类检查。Serena 的语义查找在这一步相当于护栏。

换句话说，它更像一道保险，而不是一台加速器。仓库越大、文件越厚、模型越弱，这道保险越值钱。反过来的例子也在第二份实测里：文档齐全的仓库中，CLAUDE.md 已经把定位成本省掉了，作者就是这么解释自己那个结果的。

5. 官方推荐怎么装，以及接进 Codex

README 里有一条被原帖略过的 IMPORTANT：不要通过 MCP 或插件市场安装 Serena，那些市场里的命令已经过期。官方路径是先装 uv，再装 Serena 本体，初始化，然后把 MCP 条目交给客户端。

uv tool install -p 3.13 serena-agent
serena init
serena setup codex

serena init 默认走 LSP 后端；要换 JetBrains 后端就加 -b JetBrains。装完在 Codex 里用 /mcp 确认已连接。不走 setup 命令的话，手工写进 ~/.codex/config.toml 的是这一段：

[mcp_servers.serena]
startup_timeout_sec = 15
command = "serena"
args = ["start-mcp-server", "--project-from-cwd", "--context=codex"]

Codex 用的是全局 MCP 配置，不像 VSCode 和 Claude Code 那样按工作区分开。Codex App 启动时不在项目目录里，所以每个会话开头要让它执行一句「Activate the current dir as project using serena」。

官方还给了 ~/.codex/hooks.json 的六个生命周期钩子，用来解决「工具挂上了但 Agent 不用」这件事：remind、plan-guard、reset、activate、plan-context、cleanup，都带 --client=codex。当前 Codex 版本默认开启生命周期钩子，不需要特性开关。

钩子里的超时值不是随手写的。不写超时，Codex 允许钩子跑 600 秒；官方给提醒和激活各 5 秒、SessionEnd 清理 3 秒，就是为了不让卡住的钩子堵住一次 Bash 调用。SessionEnd 清理钩子需要 Codex 0.145.0 或更新；更老的版本只支持 Stop，而这个组合目前有已知兼容问题。

6. 装之前先知道这几条限制

  • 用默认的 LSP 后端时，跨项目依赖搜索、类型继承、移动符号、内联、传播删除这几项不可用，这些要装 JetBrains 插件（付费，有免费试用），而且 Rider 和 CLion 不支持。
  • 客户端可能找不到 serena 命令，哪怕它在 PATH 里。这种情况把可执行文件的完整路径写进配置。
  • 有些客户端的工具发现实现得不好，Agent 会不去用 Serena 的工具，上面那套 hooks 就是为此准备的。
  • 被客户端拉起的 MCP 进程不一定继承你 shell profile 里的环境变量，这时要在 MCP 条目里显式加 env。
  • 在 Claude Code、Codex 这类已有内置文件、搜索、shell 能力的客户端里，Serena 的基础工具默认关闭，避免重复占上下文。

7. 许可证要说清

Serena 按组件授权：src/solidlsp 下的 SolidLSP 用 MIT，其余部分（也就是 Serena 应用本体）用 GPL-3.0-or-later。把两者合并分发，整体按 GPL 算。这跟原帖那段提示词里「按官方推荐方式安装、保留现有 MCP 配置」没有冲突，但如果你打算把它嵌进闭源工具链，这一点要先确认。

8. 本卡的核查边界

这张卡没有在本机安装或运行 Serena，也没有做任何本地 token 测量。本机实测到的是 codex-cli 0.146.0，Serena 命令在本机不存在。X 原帖附带的视频没有转录。全部事实来自原帖正文、官方 README 与文档、官方评测页，以及上面三份第三方实测。Serena 仓库快照为 2026-10-20：30,498 stars、2,112 forks、99 个 open issues，最新发布 v2.1.0（2026-10-19）。

按官方文档的说法，不同语言的 LSP 成熟度不一样，Ruby 与 Java 官方自己就标了注意事项；这部分本卡没有逐语言枚举。

9. 想自己验一遍，怎么测

官方提供了自己的评测提示词：让 Agent 在你的项目上做约 20 个日常任务，一半用 Serena、一半只用内置工具，逐项比调用次数、payload 大小和改动结果。要测 token，就在这之上把两边的输入与输出 token 分别记下来，并控制住这几项：仓库大小与文件平均行数、模型与推理档位、任务集是否固定、两次运行的改动量是否可比。上面三份实测互相矛盾，很大一部分差异就来自这几项没对齐。
