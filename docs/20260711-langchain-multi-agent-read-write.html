多 Agent 不是越多越好：何时拆、何时合，是架构设计的核心判断。

多 Agent 系统的价值在于高价值且可大量并行的任务。拆分前必须问：这些子任务是否真的需要独立 agent，还是只需独立的函数调用？

01
并行的单位不是

什么时候多 Agent 值得拆？

高价值且可大量并行的任务才值得多 Agent。判断标准：任务是否足够独立、是否需要不同工具或知识域、是否可接受异步执行。

值得拆

多域并行任务

需要不同专业知识域的子任务，如搜索、分析、生成各自调用不同工具链。

值得拆

长生命周期任务

需要压缩、外部记忆、人类介入检查点的任务，agent 需要状态持久化。

先别拆

简单顺序任务

如果一个 LLM 调用就能解决，不要拆成多个 agent，增加延迟和协调成本。

02
Anthropic Claude Research

主 Agent 在一次统一调用中完成

Anthropic 的研究发现：主 agent 在一次统一调用中完成，往往比多次调用更稳定。多 Agent 的价值只在高并行度场景。

核心结论

压缩 · 外部记忆 · 谨慎交接

长生命周期 agent 必须有上下文压缩机制、外部记忆存储、任务交接时的状态同步。

关键陷阱

写会把隐性决策变成冲突

多 Agent 的写操作比读操作危险得多。并发写入同一上下文会引入隐性决策冲突。

03
上下文工程

拆任务不等于拆上下文

多 Agent 系统最常见的错误是把"拆任务"等同于"拆上下文"。实际上，任务可以并行，上下文必须集中管理。

场景推荐方式原因
高并行 + 无状态 多 Agent 并行 任务独立，无冲突风险
需要共享状态 主 Agent + 函数调用 统一上下文管理，减少冲突
长生命周期 + 写操作 谨慎交接机制 防止写操作冲突，引入仲裁层
上下文超长 压缩 + 外部记忆 避免超出上下文窗口
04
长生命周期 agent

设计多 Agent 前的检查清单

在引入多 Agent 架构前，确认以下几点都已评估。

检查项

任务是否真的需要并行？

如果是串行依赖关系，多 Agent 不会带来收益，只增加系统复杂度。

检查项

冲突处理机制是否就绪？

写操作前是否有仲裁层？状态同步机制是否完善？人类介入点在哪里？

检查项

上下文窗口是否足够？

如果任务需要跨长对话，压缩机制和外部记忆存储是否已设计？

检查项

任务可量化的价值？

多 Agent 带来的并行收益是否超过协调开销？只在高价值大量并行任务上有意义。

⚠ 读可并行，写会把隐性决策变成冲突。设计时优先考虑写操作的并发安全。
