LANGCHAIN · AGENT ARCHITECTURE

如何以及何时
构建多 Agent 系统

不是“多 agent 更强”，而是先分清：哪些工作在读，哪些工作在写。读可并行；写会把隐性决策变成冲突。

作者：Harrison Chase2025-06-16官方博客 · 8 min
核心判断：让多个 agent 并行探索独立信息；把需要统一决策、统一语境的综合写作，收敛到一个主 agent。
01 / 读写分界

并行的单位不是“Agent”，而是“可独立的读取”

并行读搜索、阅读、核验多条独立线索；重复成本相对可控。
→
主 agent 收敛接收有边界、有格式的发现，保留全局语境。
→
统一写综合为一份连贯结论，避免互不兼容的输出。
文章转述 Cognition：“Actions carry implicit decisions, and conflicting decisions carry bad results.” 写入冲突通常比读取冲突更难收拾。
02 / 适合

什么时候多 Agent 值得

  • 广度优先：多条独立线索可同时推进
  • 信息量可能超过单一上下文窗口
  • 需要编排多种复杂工具
  • 任务价值足以覆盖额外 token 与工程成本
03 / 不适合

什么时候先别拆

  • 所有 agent 都必须共享同一份完整上下文
  • 子任务之间存在大量强依赖
  • 主要工作是协同写代码或内容
  • 无法为额外调用、观测与恢复成本付费
04 / 案例

Anthropic Claude Research：多 agent 做研究，主 agent 做综合

文中将 Anthropic 的研究系统作为读写分界的例子：主 agent 把问题拆为子任务；子 agent 需要明确的目标、输出格式、工具/来源指引与边界。多 agent 主要承担研究（读取）；最终把发现写成连贯报告，则由主 agent 在一次统一调用中完成。

05 / 上下文工程

拆任务不等于拆上下文

作者强调：系统必须让每个子 agent 获得恰当上下文。任务说明不足会造成重复、遗漏和错误取材；框架应让工程师可控地决定传什么上下文、按什么顺序执行。

06 / 生产配套

长生命周期 agent 的四个底座

  • 持久化/恢复：出错后从卡住处继续
  • 上下文管理：压缩、外部记忆、谨慎交接
  • 可观测：定位查询、来源或工具失败
  • 评估：尽早从小型 eval 集开始，保留人工检查
07 / 落地检查

设计多 Agent 前，先回答 5 个问题

  1. 任务能否拆成真正独立的信息探索？
  2. 每个子 agent 的目标、输出格式、工具与边界是否明确？
  3. 哪些阶段必须由一个主 agent 统一决策与写入？
  4. 失败后能否恢复，而不是全部重跑？
  5. 增量质量是否足以覆盖 token、延迟与运维成本？
