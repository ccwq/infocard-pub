Executive Summary
太长不看（TL;DR）

做出真正能卖钱的业务 Agent，第一步不是调用大模型 API，而是先把业务规则写成 PI 文档（Process Instruction），然后把 PI 和 pi-docs-playbook 一起扔给 Codex/Claude 读对。等模型真的理解了业务边界，再开始构建 Agent 逻辑。PI 的颗粒度决定 Agent 的可靠度——这是比代码更稳定的业务资产。

P·I·K·FPIFK 前置框架
4步PI→喂模型→验证→构建
8类task-reading-matrix
❌ 失败做法
直接封装大模型 API，套个壳就当"业务 Agent"卖给用户。用户不接受——因为 Agent 根本不知道业务的边界在哪里，问什么都答，但答得不一定合规。
✓ 正确起点
先把 PI 文档写清楚、喂给 Codex/Claude 读对，等模型真正理解了业务规则和边界，再开始构建 Agent 逻辑。不是先封装模型，而是先建立业务上下文。

💡 关键洞察：pi 不是终点，是起点

pi（github.com/earendil-works/pi，105,036★，MIT license）是上游的 Agent Harness 框架——它本身就是一个可以自扩展的 coding agent。但 Sunny 的方法不是教你用 pi，而是借用 pi 的文档体系来培养你自己的业务 Agent：先读懂 pi 文档里的流程规范（PI），再让 Codex/Claude 理解你的业务 PI，两套 PI 叠加，才是真正的业务 Agent。

01 · 概念辨析
Two Concepts Clarified
pi（小写）是什么
pi 是上游的一个开源项目全称（earendil-works/pi），它本身是一个 minimal agent harness——即"最小化 Agent 运行框架"。类比一下：它不是某个具体的 AI 能力，而是一个"跑 Agent 的操作系统"。
pi 的核心包：
  • @earendil-works/pi-coding-agent：交互式 CLI，是 pi 的主要入口
  • pi-agent-core：tool calling + 状态管理
  • pi-ai：统一多 provider LLM API（支持 15+ providers）
  • pi-tui：差分渲染终端 UI
  • chord：服务组合运行时
  • pi-telemetry：厂商中立遥测
官网 pi.dev，建仓 2025-08-09，MIT license，105,036★ / 13,189 forks。
PI（大写）是什么
PI = Process Instruction，即"流程规范文档"。这是 Sunny 推文里的核心概念，指的是描述一个业务角色应该做什么、怎么做、边界在哪里的文档。它不是功能列表，而是"有经验的人类员工脑子里装的那套判断逻辑"的结构化表达。
类比：PI 相当于餐厅的 SOP（Standard Operating Procedure）手册——新员工入职先背 SOP，而不是直接上手炒菜。
为什么叫 PI？因为它出现在 pi-docs-playbook 里，playbook 把上游 pi 的 Markdown 文档重新分类整理，供 Agent 导航阅读——所以"PI 文档"特指 pi 项目文档中的流程规范内容。
PI vs 提示词（Prompt）
提示词给模型的是能力：告诉它"你能做什么"。
PI 文档给模型的是判断前提：告诉它"什么情况下该做什么、不该做什么、做到什么程度算完成"。
没有 PI，Agent 就像一个"只有技能但不知道边界"的新员工——能干活，但不知道哪些活该干、哪些不该干，容易产出不合规或无意义的回答。
PI 的四个组成部分
1
角色定义Agent 是什么岗位？处理什么类型的请求？
2
边界规则什么能做，什么不能做，什么需要升级人工？
3
标准流程常见场景的标准处理步骤（SOP）。
4
判断标准什么情况算完成，什么情况算失败，什么情况需要重试。
02 · 原卡方法骨架
Original Method Framework
四步法：从 PI 到业务 Agent
① 写 PI 文档
先写人类能读懂的流程规范
→
② 喂给 Codex/Claude
让模型先把 PI 读对
→
③ 验证理解
用边界用例测试 Agent 理解
→
④ 构建 Agent
基于验证过的 PI 理解构建
PIFK 前置条件
在开始四步法之前，需要确认以下四个前置条件已就位：
P
Process Instruction已有可用的 PI 文档（流程规范），覆盖核心业务场景。
I
Instruction SetAgent 的工具集——它能调用哪些工具（读文档、搜索、执行命令、调用 API 等）。
K
Knowledge Baseline模型对业务领域的基础知识。PI 补充的是"判断前提"，K 是"背景知识"。
F
Feedback Loop持续用真实用例验证 PI 是否完整——PI 不是写完就完，而是随着业务场景迭代更新的活文档。
为什么 PI 是护城河
封装大模型 API 很简单，套个壳就能卖。但用户真正需要的是"帮我处理 XX 业务"，而不是"给我一个 AI 模型"。
不了解业务边界的产品，卖不出去。PI 是对业务逻辑的结构化提取，这个过程本身才是真正的产品价值。
PI 越细，Agent 越准。边界规则写不全，Agent 就容易出错。PI 的颗粒度决定了 Agent 的可靠程度——这是比代码更稳定的业务资产，可以版本化管理、团队共享、被测试覆盖。
⚠ 常见误区
很多人以为"用了大模型就是 AI Agent"，实际上没有 PI 的 Agent 只是换了技术的 FAQ 机器人——能回答，但不能主动判断什么时候该回答、什么时候该拒绝、什么时候该升级人工。
「读对」是怎么发生的：grilling 式追问机制
「让 Agent 先把 PI 读对」不是把文档扔进上下文就完事。playbook 的 AGENTS.md 规定了一套可操作的验证流程，其思想与 Matt Pocock 的 grilling skill 同源：把理解过程变成可逐项核对的问答，而不是凭一次阅读就开跑。
1
先分类任务，再读文档Agent 按 usage/task-reading-matrix.md 把用户问题归类，只读相关 source/ 文件——不是全文硬塞。
2
回答必须引用本地路径每条结论附 source/... 路径，读没读、读的是哪份，一目了然，无法靠记忆蒙混。
3
区分「pi 提供」与「应用自设计」强制把框架能力与业务实现分开陈述，防止把想象的行为说成框架保证。
4
不确定就报快照版本可能过时的结论必须附 snapshot commit（f429ddb），提示核对上游最新文档。
这正是四步法第 2、3 步（喂给 Codex/Claude → 验证理解）的落地细节：「读对」是一套可审计的流程，而非一句口号。边界用例测试（第 3 步）补上行为层的验证，两者合起来构成完整的理解闭环。
03 · pi-docs-playbook 深拆
github.com/enderzcx/pi-docs-playbook
仓库基本信息
★
131 Stars / 11 ForksMIT license（license 字段为 None，实际为公共域），建仓 2026-06-02，作者 enderzcx 唯一贡献者，6 commits。
📍
定位documentation harness / docs navigator——不是 pi 教程，也不是 pi 的 fork。它把上游 pi 的 Markdown 文档做了镜像（commit f429ddb，2026-06-01）+ 重新分类 + 告诉 Agent 不同问题该读哪些文档。
它解决什么问题
pi 文档密度很高，直接把整个 repo 扔给 Agent 会遇到四个典型问题：
①
凭记忆猜行为Agent 可能凭训练记忆猜测 pi 的行为，而不是读文档。
②
漏读关键文档pi 有大量文档，Agent 可能跳过对当前问题最关键的那篇。
③
混淆边界分不清 SDK / RPC / extension / session / compaction 各自的适用场景。
④
搞混责任边界分不清"pi 已提供什么"（harness 层）和"应用必须自己设计什么"（业务层）。
目录结构逐个讲解
文件/目录 类型 作用 重要性
README.md 文件 入口文档，说明 repo 是什么、怎么用、更新机制 必读
AGENTS.md 文件 Agent 使用规则——这是 playbook 的核心，告诉 Agent 如何正确使用本 repo 作为文档导航器 核心
PROMPT.md 文件 可直接复制粘贴给 Codex/Claude 的提示词模板，触发 playbook 工作流 必读
source/ 目录 上游 pi 文档的镜像快照，保留上游路径，禁止手改——这是规范快照，不是草稿 规范
catalog/ 目录 主题索引——按主题分类的文档导航入口，供 Agent 快速定位相关文档 可选
usage/ 目录 repo 自身用法说明，包含 task-reading-matrix（任务-文档矩阵） 必读
examples/ 目录 示例问题集——展示"什么场景问什么问题"的问答样例 参考
skill-draft/ 目录 未来 skill 草案，非正式规范——不要把这里的未文档化行为当作 pi 的保证 草稿
⚠ 重要边界：source/ vs skill-draft/
source/ 是规范快照（上游 pi 文档的镜像），skill-draft/ 是未归档的草稿。Agent 回答问题时应基于 source/ 的内容，不得将 skill-draft/ 中的未文档化行为声称是 pi 的官方保证。如果发现 skill-draft/ 与 source/ 矛盾，以 source/ 为准。
AGENTS.md 工作流详解
AGENTS.md 规定的工作流程（4步）
Step 1
读 README.md了解 repo 定位、更新机制和基本用法。
Step 2
读 usage/task-reading-matrix.md把你的问题映射到 8 大任务类别之一，确定需要读哪些文档。
Step 3
只读相关 source/ 文件根据 matrix 指引，只读与当前问题相关的 source/ 目录下的文档，不要全量扫描。
Step 4
回答并引用本地路径回答时必须点名读了哪些文档，并引用本地 source/... 路径作为论据。
Source Rules（来源规则）
①
source/ 是规范快照source/ 目录里的文档是上游 pi 的镜像快照，是正式的规范依据，禁止手改。
②
catalog/usage 是导航catalog/ 和 usage/ 目录提供导航和元信息，不是规范本身。
③
skill-draft 不是规范未归档的草稿内容不得作为权威依据。
④
不把未文档化行为说成保证如果某个行为没有在 source/ 里找到文档，不要声称它是 pi 的特性。
⑤
可能过时的结论要报 commit如果文档内容可能已经过时，在回答中注明镜像快照的 commit hash（如 f429ddb）。
Answer Style（回答风格）
①
最短有用答案开头第一句话直接给结论或答案，不要铺垫背景（背景在 README 里）。
②
点名读了哪些文档明确引用本地 source/... 路径，让用户可溯源。
③
区分"pi 提供"vs"应用自己设计"分清 harness 层（pi 提供）和业务层（应用必须自己实现）的边界。
④
不抄长段原文不要直接复制粘贴大段文档原文，用自己的话概括关键点，引用关键句即可。
Common Boundaries（常见边界判定）
AGENTS.md 定义了 pi 使用中容易混淆的边界判定规则，这是 playbook 最有价值的实践知识之一：
场景边界结论来源
session JSONL 是审计真相吗？ 不是。session JSONL 是 agent trace（Agent 执行轨迹），不是 application domain audit truth（业务域审计真相）。业务域审计需要自己设计日志和记录机制。 AGENTS.md
extension hooks 能做域校验吗？ extension hooks 能塑形 tool call（影响工具调用的行为），但域校验归应用层负责，harness 层不保证。 AGENTS.md
compaction/branch 摘要是什么？ 不是持久业务事实。是上下文压缩的摘要，用于节省 token，但不适合作为业务状态记录。 AGENTS.md
进程内 TS 集成看哪里？ 先看 sdk.md（pi SDK 文档）。 AGENTS.md
子进程/语言无关集成看哪里？ 先看 rpc.md（RPC 协议文档）。 AGENTS.md
什么时候读 TUI 文档？ 只在需要建终端体验时才读 TUI 文档。不是所有 Agent 都需要 TUI。 AGENTS.md
PROMPT.md：直接可用的提示词模板
短版提示词
Use this repo as a pi docs navigator. Read README.md, AGENTS.md, and usage/task-reading-matrix.md first. Then inspect the relevant source/ files before answering.
如何使用
把 PROMPT.md 的内容复制粘贴给 Codex/Claude（或任何支持 system prompt 的模型），然后把 pi-docs-playbook 的路径或 URL 告诉它，它就会按照 AGENTS.md 的工作流来使用 playbook——先读 README，再看 task matrix，然后只读相关 source/ 文件。
这正是 Sunny 所说的"把 pi 文档喂给 Codex/Claude 读对"的实操方式——不是扔整个 pi repo，而是通过 playbook 做结构化导航。

Beginner's Journey
📖 前置阅读
开始实操之前，请确保你已经理解了第 01 章的概念辨析（pi vs PI）和第 02 章的四步法。这个路线图假设你有基础的命令行使用经验，会用 git clone 和 npm/pnpm。
第 1 天：安装 pi，跑起来
目标：让 pi 在你的机器上正常运行，建立感性认知
  • 安装 pi：运行 curl -fsSL https://pi.dev/install.sh | sh（Linux/macOS）或用 npm add -g @earendil-works/pi-coding-agent
  • 配置 API key：至少配置一个 provider（推荐 Anthropic 或 OpenAI），pi --configure 或设置环境变量
  • 启动交互模式：运行 pi，进入交互式 CLI，随便问几个问题（不要问业务问题，问一些工具类问题如"帮我解释一下什么是 RPC"）
  • 体验会话树：在交互中按 Ctrl+L 切换模型、按 Ctrl+P 轮换 provider，用 /tree 查看会话分支
  • 体验上下文压缩：在长对话中观察 pi 如何管理上下文（compaction），注意不要把 compaction 结果当作业务状态记录
  • 导出一次会话：用 /export 导出 HTML，感受会话格式
  • pi 能正常启动和响应
  • 能切换模型和 provider
  • 能查看会话树和导出

    目标：理解 playbook 的工作流，把 Codex 配置为"pi 文档导航 Agent"
    • 克隆 playbook：git clone https://github.com/enderzcx/pi-docs-playbook.git
    • 读 README.md：了解 repo 定位（documentation harness，不是教程）

    • 验证理解：问 Codex 一个简单问题，比如"如果我要在 pi 里实现一个审批流，该看哪些文档？"，看它是否引用了 source/... 路径

  • AGENTS.md 的 Source Rules 和 Answer Style 能用自己的话复述
  • Codex 能正确引用 source/ 路径回答问题
    • 第 3 天：按 task-reading-matrix 问第一个业务问题
    目标：用 playbook 的 task-reading-matrix，把你的业务问题映射到对应文档类别，然后让 Agent 回答
    • 找你的业务问题：想一个你真正想用 Agent 解决的业务问题（不是 pi 的技术问题，而是"我需要 Agent 帮我做 XX 业务"）
    • 映射到 matrix：参考 task-reading-matrix，把你的问题归类到 8 大类别之一（如果跨多个类别，选最重要的那个）
    • 按 matrix 读文档：根据 Required 文档列表，让 Agent 只读相关 source/ 文件
    • 验证边界：问 Agent"这个需求里，pi 已经提供了什么、应用必须自己实现什么？"——验证它是否分清了 harness 层和业务层
    • 测试边界用例：设计 PI 里没覆盖到的边界场景，看 Agent 如何处理（应该拒绝、降级或升级人工，而不是乱答）
  • 能把业务问题映射到 matrix 的某一类
  • Agent 回答时引用了 source/ 路径
  • Agent 能区分"pi 提供"vs"应用自己实现"
  • 边界用例测试通过（Agent 知道边界在哪里）

    扩展方向 1：自己写 PI
    基于 Sunny 的方法，为你的业务场景写一份 PI 文档（参考第 02 章的四要素），然后用四步法验证 PI 的质量。
    工具：playbook 的 task-reading-matrix 可以帮助你理解"pi 里已有的流程"——先用它搞清楚 pi 提供什么，再写你自己的 PI 补充 pi 没有的部分。
    扩展方向 2：Tool Wrapper Design
    基于 playbook 的 Tool Wrapper Design（task matrix 类别②），设计你的第一个域工具包装器。重点是高危域操作（库存变动、订单变更、支付动作）必须加审批门和幂等校验。
    工具：读 source/hooks.md 和 source/extensions.md，理解 pi 的扩展机制。
    扩展方向 3：容器化安全部署
    如果你打算在生产环境跑 pi，必须处理权限问题。读 pi 的 containerization.md，选择适合你的容器化方案（Gondolin / Plain Docker / OpenShell）。
    注意：playbook 的 source/ 默认镜像不包含 containerization.md，需要直接查上游 pi 仓库。
    扩展方向 4：Pi Packages 打包复用
    当你的 AGENTS.md、skills、prompt templates 成熟后，可以打包成 Pi packages，经 npm 或 git 分享给团队复用。
    对应 task matrix 类别：⑦ Skills/Prompts/Packaging（Required 文档：skills, prompts, packaging）。
    06 · 常见陷阱
    Common Pitfalls
    陷阱 1：凭记忆猜 pi 行为
    Agent 可能基于训练记忆猜测 pi 的行为，而不是读 playbook 的 source/ 文档。这是 playbook 存在的主要原因——通过 task-reading-matrix 强制 Agent 只读相关文档。
    应对：检查 Agent 的回答是否引用了 source/... 路径。如果没引用，要求它重新读文档再回答。
    陷阱 2：把 session JSONL 当审计记录
    session JSONL 是 agent trace（执行轨迹），不是业务审计真相。很多人误以为"只要有了 session 记录就满足了合规要求"——实际上业务域审计需要自己设计专门的日志和记录机制。
    应对：在设计 PI 时，明确区分"Agent 执行记录"（session JSONL）和"业务审计记录"（应用自己设计的日志表）。
    陷阱 3：混淆 compaction 结果与业务事实
    compaction（上下文压缩）生成的摘要是用于节省 token 的，不适合作为持久业务状态记录。如果你的 Agent 依赖 compaction 摘要来做业务判断，可能会出现数据不一致。
    应对：业务状态必须存在独立的持久存储中，不要依赖 pi 的 compaction 结果。
    陷阱 4：把 skill-draft 当官方规范
    skill-draft/ 是未归档的草稿，里面的内容不代表 pi 的官方保证。很多人看了草稿就以为"pi 支持这个功能"，结果在生产环境踩坑。
    应对：只有 source/ 目录里的文档才是规范依据。发现 skill-draft/ 与 source/ 矛盾时，以 source/ 为准。
    陷阱 5：漏容器化导致权限风险
    pi 没有内置权限系统，默认继承启动用户的权限。很多人直接在生产环境用 root 启动 pi，然后发现 Agent 能做的事情远超预期（删数据、执行系统命令等）。
    应对：生产部署必须使用容器化方案（Gondolin / Docker / OpenShell）。开发测试阶段也要养成习惯。
    陷阱 6：直接封装大模型当 Agent 卖
    这是 Sunny 原帖的核心教训：只封装大模型 API 卖"Agent"，用户不接受——因为 Agent 不知道业务边界在哪里。没有 PI 的 Agent，本质上是一个换了技术的 FAQ 机器人。
    应对：先写 PI，再喂模型，再构建 Agent。这是最符合 Sunny 方法论的顺序。
    陷阱 7：选错集成方式（SDK vs RPC）
    进程内 TypeScript 集成应该用 SDK（sdk.md），子进程或语言无关集成应该用 RPC（rpc.md）。很多人搞混了，用 RPC 做进程内集成（性能差）或用 SDK 做跨语言集成（不可能）。
    应对：参考 playbook 的 Common Boundaries 和 task-reading-matrix 类别①（Runtime Topology）。
    陷阱 8：过度依赖 plan mode / sub-agents
    pi 默认不启用 sub-agents 和 plan mode。很多人以为"装个插件就能用"，结果发现这些功能需要自己实现或者找第三方包。
    应对：在开始项目之前，明确你需要哪些高级特性，评估 pi 默认是否支持，不支持的话如何补充。

    原帖观点 vs 官方文档观点区分
    以下内容来自 Sunny（@0xenderzcx）的 X Thread，不代表 pi 官方立场或 pi-docs-playbook 的官方文档：
    Sunny 的核心方法论
    ①
    PI First先写 PI，再喂模型，再构建 Agent。这是 Sunny 的个人方法论，来自一次失败教训的反思，不是 pi 官方推荐的工作流。
    ②
    PI 是护城河Sunny 认为 PI 的颗粒度决定 Agent 可靠度，是比代码更稳定的业务资产。这是 Sunny 的业务洞察，不是 pi 项目的技术断言。
    ③
    PIFK 前置框架P-I-K-F 四要素是 Sunny 提炼的 PI 写作框架，不是 pi 项目或 playbook 的官方术语。
    pi 官方立场
    ①
    pi 是 harness，不是业务框架pi 官方定位是 minimal agent harness，关注点是"如何运行 Agent"，而不是"如何写 PI"。业务规则是应用层的责任，pi 不做预设。
    ②
    pi 不提供权限系统这是官方明确声明的设计选择，不是缺陷。权限边界需要通过容器化或应用层实现。
    ③
    pi 支持多 provider 但不保证每个都稳定15+ providers 是官方声明的接口支持，但不同 provider 的稳定性和功能完整性可能不同。
    "Sunny 的 PI First 方法是应用层的方法论，pi-docs-playbook 是它的工具化实现，上游 pi 是运行层的基础设施。三者组合，才是完整的 Agent 开发栈。"
    — 本卡整理
