01 · 核心观点
Core Point
太长不看

把 pi 文档喂给 Codex/Claude，是做出真正业务 Agent 的起点。先让 Agent 读懂 PI 文档，而不是先写代码。

"别急着写 Agent，先把 pi 文档喂给 Codex 读对"
— Sunny @0xenderzcx
失败教训
一开始接了个业务，只是把大模型封装了一下，以为这样就能当业务 Agent 卖出去了。用户不接受，因为 Agent 并不知道业务的边界在哪里。
正确起点
先喂 PI 文档给 Codex/Claude 读对，让 Agent 真正理解业务规则，再开始构建 Agent 逻辑。不是先封装模型，而是先建立业务上下文。
02 · PI 文档是什么
What is PI
Process Instruction
PI = Process Instruction，即流程规范文档。描述一个业务角色应该做什么、怎么做、边界在哪里。它不是功能列表，而是"有经验的人类员工"脑子里装的那套判断逻辑。
为什么 Agent 需要它
没有 PI，Agent 就只有"输入 → 模型 → 输出"的通路，不知道业务边界在哪里，容易产出不合规或无意义的回答。PI 让 Agent 有了"判断前提"，而不是只会生成文字。
PI 文档应该包含
1
角色定义Agent 是什么岗位，处理什么请求。
2
边界规则什么能做，什么不能做，什么要升级。
3
标准流程常见场景的标准处理步骤。
4
判断标准什么情况算完成，什么情况算失败。
PI vs 提示词
提示词是让模型生成内容。PI 是让 Agent 知道什么时候该生成什么、不该生成什么。提示词给的是能力，PI 给的是判断前提。
03 · pi-docs-playbook 方法
pi-docs-playbook
方法核心
1
写 PI 文档不是写 Agent 代码，是先写人类能读懂的流程规范。
2
喂给 Codex/Claude让模型先把 PI 读对，形成业务理解。
3
验证理解用边界用例测试 Agent 是否真的理解了业务规则。
4
再构建 Agent基于验证过的 PI 理解，再开始构建 Agent 逻辑。
前置条件
P
Process Instruction已有可用的 PI 文档。
I
Instruction SetAgent 的工具集（读文档、搜索、执行命令等）。
K
Knowledge Baseline模型对业务领域的基础知识。
F
Feedback Loop持续用真实用例验证 PI 是否完整。
04 · 为什么 PI 是护城河
Why PI is the Moat
封装模型的局限
封装大模型 API 很简单，套个壳就能卖。但用户真正需要的是"帮我处理 XX 业务"，而不是"给我一个 AI 模型"。不了解业务边界的产品，卖不出去。
PI 文档是壁垒
PI 是对业务逻辑的结构化提取。把 PI 写清楚、把 PI 喂给模型、用 PI 验证 Agent，这个过程本身才是真正的产品价值。不是模型能力，是业务理解深度。
PI 越细，Agent 越准
边界规则写不全，Agent 就容易出错。PI 的颗粒度决定了 Agent 的可靠程度。花时间写 PI 是最有价值的投入。
PI 的生命力
PI 文档可以被版本化管理、被团队共享、被测试覆盖。比起 Agent 代码，PI 是更稳定的业务资产。
