HERMES / VISION / MODEL SELECTION

Hermes 识图默认别走 main

官方文档把 vision 作为 auxiliary 任务，默认会跟着主模型走；但更稳的做法，是显式配置 Gemini Flash 作为默认识图，再用 GPT-4o 兜复杂截图、Qwen2.5-VL 走本地与 OCR。

#1 Gemini Flash #2 GPT-4o #3 Qwen2.5-VL #4 Codex #5 MiniMax

我会这样配

auxiliary:
  vision:
    provider: "openrouter"
    model: "google/gemini-3-flash-preview"

# hard cases:
# model: "openai/gpt-4o"
# local/self-hosted:
# model: "qwen2.5-vl"
关键点：Hermes 的 vision 是 auxiliary 任务，不该默认挂在昂贵的 main 上；显式配置能把成本、延迟和识图质量拆开控制。
官方默认
auto → main
不改配置时，vision 会先走主模型。
默认首选
Gemini Flash
官方文档点名用于 vision / web extraction。
高精度兜底
GPT-4o
官方直接给出“替代 Gemini Flash”的配置例子。
本地/离线
Qwen2.5-VL
适合 OCR、表格、布局与自托管。
01
TOP 5 RANKING

Hermes 识图模型前 5 名

这里按“默认实用度 + 社区可见度 + 识图能力 + 接入成本”综合排序，不是单纯比参数量。

1
Gemini 3 Flash Preview / Gemini 2.5 Flash
Recommended default
最稳的默认解：官方文档明确把 Gemini Flash 作为 vision / web extraction 的推荐路径；社区教程还直接写到 Hermes 的视觉分析模块用 Gemini 3 Flash Preview 走 OpenRouter API。对大多数截图、网页、图文混排，这是最省心的一档。
证据：Hermes docs 的 vision 示例 + 社区教程「Hermes Agent 的视觉分析」里对 Gemini 3 Flash Preview 的直接使用。
2
OpenAI GPT-4o
Accuracy fallback
当截图很脏、版面很乱、OCR 很难、图表很多时，GPT-4o 是最稳的高精度兜底。官方文档直接给它写了 vision 配置例子，说明它是 Hermes 认可的替代方案。
证据：Hermes 官方 docs 明写 “To use GPT-4o instead of Gemini Flash for image analysis”。
3
Qwen2.5-VL
Local / OCR / layout
如果你要自托管，或者主要看中文文档、表格、布局、结构化抽取，Qwen2.5-VL 很合适。它不是“最会聊天”的那类，但在文档识图和结构输出上很有性价比。
证据：社区文章反复强调它对文本、图表、图标、布局和 JSON 输出很强；Hermes 也允许自定义 vision endpoint。
4
Codex / GPT-5.3-Codex
One-login convenience
如果你已经在用 ChatGPT Pro/Plus，Codex 是一个“少折腾”的选择：Hermes docs 明确说它支持 vision。它更偏 agentic coding/workflow，纯识图不是它最强的定位，但接入体验好。
证据：Hermes docs 的 provider 表写明 Codex supports vision；社区讨论集中在编程代理与长流程协作。
5
MiniMax OAuth / MiniMax-M2.7-highspeed
China / no-key convenience
适合你想省去 API Key、偏大陆网络，或者想顺手把 Hermes 跑起来。官方支持没问题，但纯识图口碑与证据密度不如前四个，所以我把它放在第五位。
证据：Hermes docs 直接给出 MiniMax OAuth 的 auxiliary 路线；社区教程更多聚焦接入与 agent/coding，不是专门识图评测。
02
EVIDENCE LAYER

官方怎么说，社区怎么用

这一步是为了把“官方支持”和“社区实际偏好”分开，不把一个人写法当成整个生态的证据。

官方默认：vision 属于 auxiliary
Docs / config
Hermes 的 docs 写得很清楚：vision 不是一个独立主模型，而是 auxiliary 任务；默认 auto 会把它路由到主模型，容易把成本一起抬高。
官方示例：GPT-4o 是明确替代项
Docs / examples
官方直接给出 “use GPT-4o instead of Gemini Flash for image analysis” 的配置样例，说明 GPT-4o 是官方认可的高精度兜底。
社区实用：Gemini 3 Flash Preview
Blogs / tutorials
有教程把 Hermes 的视觉分析实现到 `Gemini 3 Flash Preview` + OpenRouter；这说明社区已经把它当成可复制的默认栈。
社区分工：Qwen / MiniMax / Codex
Blogs / config guides
Qwen2.5-VL 常被拿来做 OCR / 表格 / layout；MiniMax 主要是接入和大陆便利；Codex 的重点则在 agentic coding 与 one-login 体验。
03
RECOMMENDED CONFIG

我给你的实际配置建议

先把默认值设成“省心、便宜、够稳”，再按任务切到更强的模型。不要让 Hermes 的 vision 跟着主模型一起漂。

默认日常栈

用途：网页截图、聊天截图、文图混排、轻量 OCR、日常视觉问答。

auxiliary:
  vision:
    provider: "openrouter"
    model: "google/gemini-3-flash-preview"
如果 preview 供应不稳定，可换成 google/gemini-2.5-flash。

高难兜底 / 本地栈

高难度：复杂 OCR、图表、脏截图，切 openai/gpt-4o。
本地部署：需要自托管时切 qwen2.5-vl。

如果你已经在用 Codex OAuth，也可以直接让 vision 走 Codex；如果只是想省事，MiniMax OAuth 也能用，但不作为纯识图首选。
04
RISK & BOUNDARY

边界与风险

这部分是为了避免你把“能用”误判成“最优”。

COST
  • auto/main 会把 vision 成本跟主模型绑在一起；主模型越贵，识图越贵。
  • 这也是为什么要把 vision 显式拆出来。
MULTIMODAL
  • vision 需要真正支持多模态的 endpoint。
  • 如果你给 Hermes 接的是纯文本模型，图像分析会失败。
LOCAL
  • Qwen2.5-VL 适合自托管，但你要自己承担算力、部署和稳定性。
  • 它更像工程解，不是云端即开即用解。
EASY MODE
  • Codex / MiniMax 更像“账号便利性”方案。
  • 不是纯视觉榜单的冠军，但确实是可落地选项。
一句话结论：Hermes 的识图别默认挂在 main 上；Gemini Flash 是最稳的默认，GPT-4o 是高精度兜底，Qwen2.5-VL 是本地/OCR 解，Codex 和 MiniMax 更偏便利与生态。
