AGENTIC ENGINEERING · 实践笔记

让 AI 持续开发，
先把验证闭环搭起来

dzhng/skills 不是一个“自动写完所有代码”的按钮，而是一组可组合的 Agent Skills：探索未知、写规格、按可验证切片实施，再把 AI 自己做的决定交还给人。

MITClaude Code / Codex规格驱动 · 决策账本
第一次怎么选？

挑一个有现成测试、没有生产数据迁移的小功能。先走通一个切片及其 review，再考虑长时间无人值守。不要从支付、权限或生产发布开始。

长跑时间 ≠ 验收结果

推荐推文的配图记录 3 天 18 分 44 秒；当前 README 文案记录 1 天 16 小时。两种记录来源不同，不能视为同一次运行，也不是质量或成本承诺。

按需阅读：安装入口技能域图四步闭环如何切片检查点审哪些决定最小试用运行边界
01 / ENTRY

先装技能，再确认宿主能力

README 给出的安装入口如下。这是读者操作示例，本文没有安装或运行这些技能。

npx skills add dzhng/skills

# README 建议：添加 --list 查看、选择个别技能
npx skills add dzhng/skills --list

也可以把所需技能目录复制到宿主的技能目录，例如 .claude/skills/。不要把“安装成功”当成“循环执行已就绪”：工具权限、登录、模型可用性、上下文恢复、测试环境，仍由宿主负责。

Skill 定义怎么做；Harness（运行这些指令的宿主）决定能调用什么工具、能否持续运行，以及权限如何审批。
为什么不能把 /goal 当成通用命令？

README 展示 /goal /implement-spec specs/<feature>。这里的循环模式取决于宿主实际支持的入口；不同版本和客户端的命令语法可能不同。先查当前宿主文档并在小任务验证，不要凭技能文件存在就推断所有客户端兼容。

02 / MAP

这不是单个 Skill：按任务选一组

Engineering · 主开发链

explore-unknowns → write-spec → implement-spec → close-spec 负责从需求探索到完成归档。review 串起结构整理、代码评审和文档更新；audit-choices 单独审查实现者代做的决定。

选用：跨文件功能、复杂变更、有明确验证面的大任务。

Visual · 视觉证据

screenshot-critique 用未被实现思路影响的第二双眼睛看图；compare-screenshots 与参考或前版本比较，避免“看起来有变化”却实际没改。

选用：页面、动画、渲染器，或用户报的视觉 bug。

Authoring · 维护技能

write-skills 维护触发和渐进披露，eval-skills 通过独立执行与判定发现缺口。

选用：你要复用团队工作流，而不是只做一个功能。

Graphics · 专门领域

renderer 面向 WebGPU、three.js/TSL、WGSL 和真实浏览器视觉核验。

选用：具体图形任务；一般 CRUD 功能不必加载它。

技能名与用途依据 README。不是要求每个任务加载整套：小改动可以按需调用 review 或 audit-choices。

03 / LOOP

四步闭环：人把时间花在两头

规划阶段 · 人参与

① /explore-unknowns：先地图，后路线

从四象限的已知和未知出发，逐项采访，给出可挑选的草图、选项与决策表。目的不是问更多问题，而是消除会影响实现方向的空白。

② /write-spec：把目标变成小契约

明确结果、非目标、不可破坏的约束、缺失输入和第一个可运行检查点。沿 API 边界切片，让每片都有独立输入、输出和验收方式。

实现与收尾 · 证据先行preview · 内页预览

③ /goal + /implement-spec：持续推进

读取规格及依赖图，执行有界的一轮，验证、评审、记录决定、提交检查点，再推进下一轮。独立切片可并行，有依赖的工作必须串行。

/goal /implement-spec specs/<feature>

④ choices.md：把代做的决定交回来

最终账本必须对照实际最终代码重审、去重，不能还写着“以后再处理”。按判断类别分组、低置信度优先，帮助人先看最值得确认的选择。

README 对人工时间给出的估计是开头与结尾各半小时到数小时；对两天的任务，作者称两端各约 2–3 小时。这些是作者经验，不是本地实测或 SLA。

04 / CONTRACT

切片不是拆 TODO：每片必须能独立否证

“实现后端”“完善 UI”只是活动描述，不是验收契约。write-spec 强调一个问题、一个接口边界、一个可观察产物和一个判定。

坏切法

先做数据库，再做 API，最后接页面。直到最后一片，才发现分页排序不稳定。前三片看似完成，却没有证明用户真正能用。

更可验证的切法

以下是说明性示例，不是仓库自带案例：为列表增加“按更新时间排序”。第一片定义同时间的稳定次序与固定 fixture；第二片验证接口排序；第三片接 UI 并比较前后截图；最后验证分页没有重复或遗漏。

# 示例：一张切片卡应回答
目标：用户切换排序后，列表按更新时间降序显示
接口边界：已有列表查询的排序输入与结果顺序
不变量：原权限过滤保持；同时间记录有稳定顺序
独立证据：固定 fixture + 聚焦测试 + 可操作页面
明确排除：不新增搜索索引，不迁移生产数据
多切片规划为什么要不同偏向的草案？

write-spec 要求复杂计划至少三个独立草案：最少切片、风险优先、接口边界质量。协调者综合而不是选一份当权威。高风险片段还要递归重切，直到下一片能被清晰接受或拒绝。这个过程会增加调用成本，不能当成免费并行。

05 / CHECKPOINT

无人值守靠检查点，不靠“别停”

implement-spec 的单轮是提交检查点，而不是结束点。完整规格才是任务范围。

  1. 读取当前真相：仓库 README、规格 README、下一切片、全局 TODO 与必须保持绿色的门禁。
  2. 对齐计划与代码：实现揭示方案过时，就修改规格与 handoff，而不是保留无意义的兼容包装。
  3. 实施并验证：行为改动先跑聚焦测试；可见页面用真实浏览器与截图。视觉变化需对照基线，不能以“非空截图”代替验收。
  4. review + audit-choices：前者处理结构、差异与文档；后者记下规格未规定的选择。审计发现的问题由实现流程处置。
  5. 提交与更新接力入口：Next Agent Prompt 写明当前状态、下一步、阻塞与门禁变化，下一轮可不依赖聊天历史继续。
什么时候必须重整计划？

失败轮之后、每 2–3 次切片提交之后、恢复或上下文压缩之后、切换功能领域之前，以及证据推翻计划或 handoff 与 TODO/依赖图矛盾时。仍红、过载或模糊的切片要先拆小，不是继续堆代码。

最终完成条件：所有切片和全局 TODO 关闭、门禁绿色、全规格 review 完成并修正、最终账本与最终代码一致、close-spec 归档。还要核对规格中的决定是否真的实现，不能只数切片。

06 / CHOICES

“不审 diff”不是“不审代码质量”

audit-choices 专门回答：AI 在规格没写到的地方替你决定了什么？数据形状、存储位置、依赖、错误行为、并发策略，这些会变成未来维护的负担。

账本每条包含：发生在哪轮、决定是什么、规格留了什么空白、影响哪些未来工作、判断与理由、置信度。判断为 sound / unsound / needs-user；置信度是“审核者认为用户会否做相同选择”的信心，不是测试覆盖率。

账本示例：当上游超时，要不要自动重试？

场景：用户提交一笔动作，上游已经处理，但客户端没收到响应。

规格空白：没有写清动作是否幂等，也没有规定重试语义。

AI 的选择：所有超时都重试。用户可能因此重复提交。

审核结论：示例判定为 unsound；需要先保证重复请求不会产生重复副作用，再决定重试策略。不是简单把重试次数改成 1。

影响：接口、请求身份与错误恢复都受此决定约束。这个例子仅说明审计写法，不是官方项目的真实事故。

审计自身不改代码、不阻塞无人值守流程；needs-user 记录可逆的临时建议，让调用流程继续。这是源项目的运行偏好，不能覆盖生产权限、外部费用、不可逆操作的人工审批。

07 / FIRST RUN

第一次试用：先证明一片，再扩大目标

可照着走的首跑示例：列表排序

以下是沿用第 04 节的说明性示例，不是官方案例，也没有在本文中实际执行。先在项目目录启动已安装技能的宿主；测试命令和允许修改的路径由你按项目实际情况填写，不能直接套用。

  1. 先运行项目已有测试，记下命令和结果；把本次允许的路径、预算、时限及停止条件写进需求。
  2. 调用 /explore-unknowns，说明“给已有列表增加按更新时间降序排序；同时间稳定排序，不改权限过滤，不迁移数据、不发布”，回答它对接口、fixture 和边界的追问。
  3. 调用 /write-spec，要求第一片只固定排序契约与 fixture，并确认生成的实际规格目录、验收命令和门禁。
  4. 确认当前宿主支持循环入口后，再使用下面的 README 命令形式；把占位符换成实际规格目录。首轮先核查测试、review、choices.md 和 handoff，再决定是否扩大运行范围。若宿主不支持 /goal，查该宿主文档，不把它当成跨客户端通用语法。
# README 命令形式：替换为实际规格目录后使用
/goal /implement-spec specs/<feature>

首轮核查：读取该规格目录的 README、切片产物、测试结果、choices.md 和 Next Agent Prompt；确认结果符合排序契约、差异未越界、下一轮与阻塞清晰。门禁变红或涉及新增高风险权限时停止推进，先修正计划或取得人工授权。

试前准备

  • 选择可回退的分支和无敏感数据的开发环境。
  • 确认现有测试命令确实成功，失败基线必须先记清。
  • 明确允许改哪些路径，不允许发布、迁移或外部发送。
  • 设调用预算、最长运行时间和人工停止条件。

一个小功能的验收面

  • 规格中有结果、非目标、契约与独立验证方法。
  • 有真实执行的测试结果，而非“应该通过”。
  • 有视觉改动时，截图身份、视口、基线都正确。
  • choices.md 对照最终代码重审、去重，不以空账本敷衍；允许保留 needs-user，但必须写明待确认问题、可逆临时建议、影响和人工跟进，不能用“以后再处理”替代判断。
  • 最终差异只包含授权范围，能说明新增维护面。
临时修复，没有规格，也能用吗？

README 提供按需路线：超出预期的临时改动先 review，再 audit-choices；头脑风暴之后也可补 explore-unknowns。简单一行修复不必强行变成大型软件工厂。

08 / BOUNDARY

什么适合自动推进，什么必须收紧

适合

有现成测试、可隔离验证、可回退的功能扩展；依赖图明确的前后端独立切片；需要持续 handoff 的多轮开发。

不适合直接放手

没有可信测试的生产变更、费用不可控的服务调用、支付和权限决策、生产数据迁移、未经授权的部署或发送。模型自述“做完了”不是验收。

  1. 默认兼容策略须审：write-spec 默认不带向后兼容或迁移，除非用户选择。对已上线系统，这不是可直接套用的安全默认。
  2. 人类检查是非阻塞：源项目可给约 5 分钟响应窗口，然后记录可逆决定继续。这不意味着默认拥有高风险操作授权。
  3. 并行不是无限：源码提及独立 worktree 以隔离代码写入，这是该库建议，不代表所有使用项目允许。项目规则与用户边界仍优先。
  4. 长期成本未核验：未测 token、费用、重试次数、故障恢复成功率；长跑截图不能回答这些问题。
  5. 安装与供应链：技能可驱动终端和浏览器行为；安装前阅读指令、固定所需版本并限制凭据和工具范围。

真正值得复制的是：每片能证明，每个决定能追溯
