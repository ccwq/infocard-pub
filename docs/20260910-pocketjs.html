01

它是什么：把前端开发体验下沉到非浏览器设备

PocketJS 是一个可移植应用运行时，目标是让现代组件代码在差异很大的硬件上输出原生像素。官方仓库将它描述为 portable application runtime：Solid、Vue Vapor 和 Octane 组件可以编译到同一棵原生 UI 树，再由 QuickJS guest 驱动 Rust core 完成 Flexbox 布局、样式表查找、输入、动画和绘制。

传统 Web 应用依赖浏览器提供 DOM、CSSOM、级联、布局、绘制和合成；PocketJS 把这些职责收回运行时。组件仍然可以使用 JSX 和响应式状态，但运行时不创建 HTML 节点，也不等待浏览器的 CSS 引擎。这个取舍换来了更小、更确定的执行环境，同时也意味着你不能默认使用任意 Web API、CSS 属性或浏览器生态。

先问自己：你要解决的是“同一套组件能不能运行到受限设备”，还是“桌面应用能不能更快开发”？前者更接近 PocketJS 的价值，后者需要把它和 Tauri、Electron 等方案按实际项目约束比较。
02

先跑起来：零安装 Playground 与本地开发

最适合初学者的第一步是打开官方 Playground，先观察组件、样式、动画和交互，而不是立即准备 PSP 或其他旧设备。确认基本编程模型后，再在本地运行浏览器 host。官方 README 给出的本地浏览器路径需要 Bun 和 Rust via rustup。

  1. 安装 Bun 和 Rust；确认 bun --version、rustc --version 能返回版本。
  2. 克隆官方仓库并进入目录，不要在空目录里猜测包名。
  3. 运行 bun install 安装 workspace 依赖。
  4. 为 WebAssembly 添加 wasm32-unknown-unknown 目标。
  5. 运行 bun run dev，等待 WASM、Hero 应用和浏览器 host 启动。
  6. 打开终端输出的本地地址，点击示例组件，确认状态和动画可用。
git clone https://github.com/pocket-stack/pocketjs
cd pocketjs
bun install
rustup target add wasm32-unknown-unknown
bun run dev

这一步的验收不是“命令没有报错”，而是浏览器中能看到组件、点击交互能改变状态，并且开发服务输出了可访问地址。若只完成依赖安装，没有运行页面，就还没有验证运行时链路。

03

写第一个组件：先理解组件树，不要带入浏览器 DOM 习惯

PocketJS 官方示例以 Solid 为例。组件从 solid-js 导入响应式原语，从 @pocketjs/framework/solid 导入 mount，再从 components 导入 Text 和 View。View、Text 是运行时组件，不是自动映射成任意 HTML 元素的浏览器节点。

import { createSignal, Show } from "solid-js";
import { mount } from "@pocketjs/framework/solid";
import { Text, View } from "@pocketjs/framework/solid/components";

function Counter() {
  const [count, setCount] = createSignal(0);

  return (
    <View class="w-full h-full flex-col items-center gap-4 p-4 bg-slate-50">
      <Text class="text-xl text-slate-950 font-bold">
        Count: {count()}
      </Text>
      <View focusable onPress={() => setCount(count() + 1)}>
        <Text>Press Circle</Text>
      </View>
      <Show when={count() > 3}>
        <Text>Reactive on real hardware.</Text>
      </Show>
    </View>
  );
}

mount(() => <Counter />);

练习时先只改三处：初始 count、按钮文案和 Show 的阈值。每次只改一个变量，然后重新运行，观察状态是否在同一组件树内更新。不要一开始引入复杂路由、任意浏览器事件或无法确认被支持的第三方库。

04

三种框架如何共存：改变的是写法，不是底层合同

官方资料列出 Solid、Vue Vapor 和 Octane 三条编程入口。它们最终进入同一 native tree，因此框架选择主要改变应用代码和响应式生命周期，下面的布局、绘制、输入、目标后端和原生边界由该运行时统一管理。

框架状态/生命周期源代码形态选择建议
Solidsolid-jsJSX想使用成熟的细粒度响应式模型时先选它
Vue VaporvueJSX 与单文件组件已有 Vue 经验、希望保留 Vue 开发方式时评估
Octane编译 hooksJSX、无 Virtual DOM按官方当前文档和目标工具链验证，不要凭名称推断兼容性

“三种框架编译到同一棵树”不意味着所有插件、组件库和浏览器 API 都自动兼容。真正需要验证的是：目标框架的编译入口是否存在、组件是否使用 PocketJS 提供的 primitives、样式是否落在固定 Tailwind 子集内、目标 profile 是否满足所需 APIs。

05

样式与动画：构建期固化，运行时少做解释

PocketJS 的 class literal 会在构建期进入 baked style table。运行时通过 class 属性查表，而不是在设备上运行完整 CSS parser、cascade、specificity 或 reflow。官方文档提供固定的 Tailwind 子集，因此初学者要把“能写 class”理解为“能写被 PocketJS 支持的 class”，而不是可以复制任意 Tailwind 配置。

动画也采用类似思想：关键帧时间线和 spring 曲线进入 style table，Rust core 使用自己的时钟推进。这样动画帧不需要 JavaScript 每一帧重新计算，能减少 JS 主线程工作；但动画能力仍取决于当前组件、编译器和目标后端支持。

样式源码
  ↓ 构建期
固定 style table
  ↓ 运行期查表
native tree + layout
  ↓
draw list
  ↓
目标 backend → pixels

调试样式时，优先检查 class 是否属于官方支持的词汇、是否被构建器收录、目标 profile 是否支持所需能力。不要用浏览器 DevTools 中“这条 CSS 有效”来证明它在 PocketJS 设备端有效。

06

渲染链路：从组件到像素究竟经过什么

理解渲染链路，能帮助你判断问题属于组件、核心、后端还是目标工具链。PocketJS 的 guest 发出树变更，Rust core 负责 native tree、Flexbox 布局、baked style table 和 draw list，最后由每个目标的 backend 提交到 GE、GXM、Metal、wgpu、软件栅格或电子墨水更新路径。

层PocketJS 的责任初学者排查问题
Component guest组件、状态、事件和应用逻辑状态是否变化，onPress 是否触发
Native tree组件结构和属性的运行时表示组件是否使用正确的 PocketJS primitives
Layout/styleFlexbox 与构建期 style tableclass 是否在固定词汇内，viewport 是否正确
Draw list把布局结果转换成绘制操作是否有目标后端无法提交的操作
Backend/host把 draw list 送到设备图形系统SDK、固件、ABI 和驱动是否匹配

出现“页面空白”时，不要直接把问题归因于 JSX。可以按顺序确认：guest 是否启动、组件是否 mount、树是否生成、布局是否有有效 viewport、draw list 是否产生、host 是否完成提交。每一层都应有最小日志或可观察结果。

07

目标准入：pocket.json 是跨设备的合同

一套 bundle 可能服务于不同密度的机器，但不是每台机器都满足同样的 viewport 和 APIs。应用在 pocket.json 中声明需要的 viewport 和 APIs，目标 profile 在编译和打包前检查这些要求。这个步骤把“编译成功”和“目标可运行”分开。

npm install -g @pocketjs/cli
pocket doctor
pocket setup
pocket create my-app
pocket check --target psp --manifest apps/my-app/pocket.json
pocket build --target psp --manifest apps/my-app/pocket.json -- --release

官方示例中，pocket check --target psp 可以报告 480x272、baked text glyphs 和 input buttons 等能力；vita 示例还涉及 density 2。你应把 check 当作准入检查，而不是性能测试。它能告诉你目标合同是否满足，不能替你证明真实硬件上的触摸、帧率、内存和发布安装流程。

新手验收：先让一个 target profile check 通过，再逐步加入图片、输入、动画和额外模块。每加入一个能力，就重新检查，不要最后一次性排查所有失败。
08

PSP 与低资源硬件：为什么“能跑”必须拆成多个命题

公众号文章强调 PSP、8MB 内存、60 FPS 和 QuickJS + Rust 的反差；官方 README 也提供 PSP、性能预算和应用案例。但这些结果属于特定应用、特定版本、特定硬件与测试条件，不能自动变成所有 PocketJS 应用的保证。

要判断一个项目是否真的适合低资源设备，至少拆开看五件事：guest 的 JavaScript 工作量、布局和绘制成本、纹理/字体/资源占用、目标 backend 的提交耗时、以及应用在真实输入下是否稳定。一个静态 Demo 能显示，不代表长列表、动画、网络、音频或复杂交互都能在预算内运行。

文章中的说法正确的证据口径实践时怎么用
8MB / 60 FPS官方演示或基准上下文记录应用、设备、版本、测量方法再比较
Electron 内存对比同一类桌面示例的官方报告看进程、冷启动、空闲内存和磁盘等完整指标
已适配很多设备仓库/Release 的 host 与 target 清单核对当前 profile、SDK、固件和真实验收记录
组件跨平台统一应用代码与不同 native host仍需分别通过每个目标的准入和设备测试

最佳实践是先在 WebAssembly host 上建立可重复的行为测试，再在目标设备上验证输入、绘制、帧时间、内存和安装。这样可以把框架逻辑错误与设备移植问题分开。

09

确定性帧合同：为什么测试不应依赖墙上时钟

PocketJS 把时间看成 frame counter。一次 frame(buttons) 调用是一个不可被外部打断的事务；网络回复或异步效果不会在一帧中间插入，而是在帧边界进入。官方资料用 state n+1 = F(state n, input n) 与 pixels n = G(state n) 表达这种关系。

state n+1 = F(state n, input n)
pixels n  = G(state n)

输入 → frame(buttons) → 状态 → draw list → pixels

这对初学者的意义是：写交互测试时记录输入帧，而不是 sleep 100ms 后猜测状态。把网络、定时器和动画都放进明确的帧推进模型后，同一段输入更容易重放、分叉和比较。官方还描述了 tape、时间旅行调试和 chaos mode，但你仍需查看当前版本文档，确认具体命令和支持范围。

10

Native modules：只为应用加载需要的能力

PocketJS 采用游戏引擎式架构，核心能力以独立 native modules 组织。应用选择需要的模块，构建时只带入相关能力。官方 README 举例包括 ui、net、audio、strike、voxel 等方向。模块化可以控制目标体积，也让应用声明自己的能力边界。

  • ui：树、布局、绘制、输入和 focus，是一般界面的基础。
  • net：网络能力需要看具体 host 是否实现和是否有边界限制，不能因为模块名存在就假定所有设备联网。
  • audio：音频输出取决于目标设备的音频 host 与格式支持。
  • voxel、strike 等：更接近应用或游戏场景，不代表每个目标都提供同样的性能。

模块选择的第一原则是“应用实际需要什么”，第二原则是“目标 profile 提供什么”。不要为了让 manifest 看起来完整而声明未使用的模块，也不要把一个模拟 host 的能力当作真实设备能力。

11

原生模块与网络边界：API 能力必须经过 host 合同

在 0.10.0 的 release notes 中，项目描述了 net、db、fs 等模块的合同与限制，例如并发请求、响应大小、数据库数量和应用数据根目录等。对于快速变化的项目，这些数字必须绑定具体 release，不要从旧版本复制成永久默认值。当前 v0.11.0 又加入了新的设备和 backend 变化，使用前应回看最新规范。

能力你应确认的内容不能直接假设
网络目标 host 是否实现、请求是否有大小/并发边界浏览器 fetch 代码可以无修改运行到 PSP
文件应用数据根目录、路径限制、写入权限可以访问任意主机文件
数据库目标 profile 是否注册 db，操作是同步还是异步所有设备都有 SQLite
文本字体表、host 测量方式和语言支持桌面字体渲染结果在所有设备像素一致

如果应用需要网络或文件能力，先在 manifest 中声明，再用 pocket check 确认目标准入；缺失能力时应让构建或挂载明确失败，而不是在运行时静默展示假数据。

12

Vapor 路径：没有 JavaScript 引擎的另一种取舍

Pocket Vapor 是独立的 ahead-of-time compiler 路径，面向无法容纳 JavaScript engine 的机器。它把严格的 Vue Vapor 子集编译成目标原生 C，产出 GBA、GB、NES、ESP32 firmware 和 Playdate .pdx 等结果。它不是任意 PocketJS 应用的低内存模式，不能把普通 PocketJS 项目直接当作 Vapor 项目。

bun run vapor:dev
bun run vapor:test
bun vapor/compiler/cli.ts vapor/examples/todo/todo.tsx --target gb

选择 Vapor 前先确认三件事：你的组件是否属于它支持的 Vue Vapor 子集；目标 board contract 是否满足编译器派生的需求；你是否接受没有 JS runtime、GC 和 allocator 的编程边界。它适合极端资源约束和固定目标，不适合把任意 Web 应用原样搬过去。

13

完整学习路线：从浏览器 Demo 到真实设备

  1. 第 1 阶段：组件认知。在 Playground 修改 Counter，验证状态、事件和条件渲染。
  2. 第 2 阶段：本地 Web host。克隆仓库，运行 Bun + Rust 开发链路，确认自己的组件能构建。
  3. 第 3 阶段：CLI 与 manifest。安装 CLI，运行 doctor、setup、create，阅读 pocket.json。
  4. 第 4 阶段：目标准入。先用 Web 或 PSP profile 做 pocket check，记录 viewport、输入和模块能力。
  5. 第 5 阶段：可重复测试。固定输入帧，检查组件状态、draw list 或 golden 结果。
  6. 第 6 阶段：真实硬件。准备 SDK、固件、连接方式和设备验收脚本，再做 build/package。

每个阶段都要留下一个可复现的成功条件。比如第 2 阶段是浏览器看到可点击组件，第 4 阶段是 check 返回目标能力满足，第 6 阶段则必须是设备真实启动、输入改变应用状态、帧持续推进，而不是仅仅生成了一个文件。

14

常见误区与排查顺序

现象常见误区正确排查
组件不显示以为 JSX 语法正确就一定 mount检查 framework 入口、组件 primitives、mount 与 host 日志
样式失效把 PocketJS 当完整浏览器 CSS检查固定 Tailwind 子集和构建期 style table
目标 check 失败先改组件或删掉声明读取 profile 缺少的 viewport/API，再决定降级或换目标
旧设备卡顿直接归因于 Rust 或 JS分别测 guest、layout、draw、backend 和资源加载
模拟器通过认为真实硬件也必然通过补真实设备输入、帧率、内存和安装验收
想做普通桌面软件只看单一内存数字选型比较生态、原生 API、调试成本、团队技能和目标硬件

推荐的故障顺序是：先确认版本和目标，再确认 manifest，再确认组件编译，再确认 host，再确认真实设备。不要在所有层同时改动，否则你无法知道哪一个变化解决了问题。

15

适合谁、不适合谁：用项目约束做决定

  • 适合：需要把统一 UI 运行到嵌入式、复古设备、电子墨水、游戏主机或浏览器/WASM 的团队；愿意维护目标 profile、native host 和构建合同的开发者；希望组件逻辑不随硬件重复实现的项目。
  • 谨慎评估：需要大量现成 Web 组件、浏览器扩展、复杂 DOM 生态、成熟桌面插件或极短交付周期的产品。
  • 不应直接依赖：把仓库 README 的设备清单当作生产兼容承诺；把官方某个 Demo 的帧率和内存当作自己的 benchmark；把源码 build 成功当作真实设备已验收。

如果你的首要目标是“快速做一个跨平台桌面应用”，Electron、Tauri 或原生 UI 框架可能更符合现成生态；如果你的首要目标是“同一组件模型适配非常规硬件”，PocketJS 才值得进入 POC。最终决策应由最小可行组件在目标设备上的真实结果决定。

16

一个可验收的 POC：不要从复杂产品开始

选择 Counter、Todo 或小型列表作为第一个 POC。它们同时覆盖状态、输入、文本、布局和条件渲染，但不会让网络、音频、复杂资源和设备 SDK 一起进入问题空间。

  1. 写一个单页组件：标题、列表、按钮和一个状态数字。
  2. 只使用官方示例出现过的框架入口、View、Text、class 和 onPress。
  3. 在 Playground 中验证交互。
  4. 本地 Web host 构建并运行。
  5. 添加 pocket.json，写清 viewport 和最低 APIs。
  6. 对一个目标运行 pocket check。
  7. 记录失败项：编译、准入、host、设备还是性能。
  8. 只有 check 和 Web host 都稳定后，才准备真实硬件。
验收记录
目标：psp
viewport：480x272
输入：buttons
样式：固定 Tailwind 子集
状态：点击按钮后 count 改变
Web host：通过 / 未通过
pocket check：通过 / 未通过
真实硬件：未测 / 通过 / 失败
下一步：只修复一个最小失败项
