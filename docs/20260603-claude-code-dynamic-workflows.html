Harness 机制：为什么要“动态”

默认 Claude Code harness 适合编码，但很多任务“长得像编码”，又不完全是编码。

  • 可以在任务开始时生成专用 harness

模型 / worktree 决策

工作流可以决定子 agent 用什么模型、是否独立 worktree
03
这意味着：作者把“智能度”和“隔离度”都交给 workflow 选择。

🎯 关键记忆

  • 工作流可以根据任务选择“便宜/快/强”的不同模型。
  • 需要隔离时，让子 agent 在自己的 worktree 里跑，避免互相污染。
  • 这不是“多 agent”这么简单，而是“多 agent + 多执行域”。
复杂任务不是只要更多 token，而是要更好的执行边界。

三大失败模式

复杂任务里，Agent 很容易在这三件事上翻车
04
作者明确点名：Agentic laziness、Self-preferential bias、Goal drift。
failure taxonomy adversarial tasks ★ ★ ★ ★ ★

⚠️ Agentic laziness

复杂任务没做完就提前宣布完成，常见于多步骤审查只处理了部分条目就停手。

⚠️ Self-preferential bias

当要求它拿自己的结果去对照 rubric 时，它会倾向偏好自己的产出。

⚠️ Goal drift

任务越长，越容易慢慢偏离原始目标，最后做成“很忙但不对题”的结果。

🔁 对策思路

把任务拆成 workflow，把验证与执行分离，把复核动作显式写进流程里。

商业计划拆解

命名 tournament

“用 workflow 头脑风暴工具名，再做淘汰赛选出前三。”

批量重命名

“把 User model 全仓库改成 Account。”

事实核查

“用 workflow 验证博客草稿里的每一个技术主张，我不想发错东西。”

任务即 harness

这些例子共同说明：workflow 的作用不是“多点几下”，而是把任务变成一个可执行的专用系统。

何时该用 workflow

长、杂、需要复核、容易偏题的任务
05
优先处理那些“默认 harness 容易失手”的任务，而不是所有任务都上 workflow。

适用信号

  • 任务多阶段、长时间运行
  • 需要 adversarial 验证或多轮复核
  • 需要模型分配和执行隔离
工作流不是“更花哨的 prompt”，而是“把任务边界写进执行系统”。
