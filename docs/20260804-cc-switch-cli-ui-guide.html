01
IDENTITY

它究竟是什么？

不是“又一个模型 API 平台”，而是本地的跨工具配置控制面。

产品形态

Tauri 2 桌面应用

官方 README 定义为 Windows、macOS、Linux 原生桌面应用；前端 React/TypeScript，原生后端 Rust。主入口启动桌面窗口与 Tauri runtime，而不是 CLI 命令解析器。

管理边界

管理 8 个客户端的配置

官方列出 Claude Code、Claude Desktop、Codex、Gemini CLI、Grok Build、OpenCode、OpenClaw、Hermes Agent。管理≠替代这些工具的安装、登录和运行。

版本快照

v3.19.1 / MIT

本次调研读取的最新 release 为 v3.19.1（2026-07-31）；仓库为 MIT。动态 Star/Release 信息不构成产品功能承诺。

02
CAPABILITY MAP

功能不是“换 Key”那么简单

Provider 切换是入口；SSOT、适配器、路由和同步才是它的工作骨架。

Provider & 模型

50+ preset、应用专属 Provider，以及跨 Claude Code / Codex / Gemini CLI 的 Unified Provider。

配置投影

向 JSON、TOML、YAML、JSON5、.env 写入目标应用所需字段；采用临时文件 + rename 的原子写。

MCP / Prompt / Skills

统一编辑、选择目标应用同步；但支持范围有差异，不能写成八个客户端完全同构。

使用量与保护

可记录请求、token、花费与模型定价；本地代理还提供 health monitoring、circuit breaker、failover。

关键机制：数据库是 SSOT；切换时写 live 文件；编辑已启用 Provider 时再从 live 文件回填。它不消灭不同工具的配置格式，而是把一份选择“投影”成各工具所需格式。
03
THE CLI QUESTION

“命令行模式”到底该怎么理解？

把 CC Switch 自身与它管理的 CLI 分开，才能避免错误安装、错误操作和错误预期。

❌ 不能写的伪命令

ccswitch switch deepseek
cc-switch provider enable codex

README、用户手册、package manifest 与 Tauri 入口均未提供上述面向用户的命令语法。开发命令 pnpm dev / pnpm build 是贡献者命令，不是日常切换方式。

✅ 正确的“CLI 使用”叙述

先在 CC Switch GUI/托盘选 Provider 并启用；它写入 ~/.claude/settings.json、~/.codex/config.toml、~/.gemini/.env 等 live config；用户再运行 claude、codex、gemini 等下游 CLI。

无路由

文件切换模式

UI 选 Provider → 写下游文件 → 多数客户端重启读取。官方说明 Claude Code 是热切换例外；Codex / OpenCode / OpenClaw 等通常应重新打开终端。

有路由

本地接管模式

目标 CLI 的 base URL 指到 127.0.0.1:15721；请求先到 CC Switch router，再按当前 Provider 转发。后续 UI/托盘切换无需重启 CLI。

真正的 CLI 命令

属于被管理客户端

例如 Codex 的 /model 是 Codex 命令：CC Switch 可生成 model_catalog_json 让第三方模型出现，但改表后仍要重启 Codex 加载。

04
UI PLAYBOOK

UI / 托盘的实际操作路径

面向日常配置维护；不需要手工编辑一堆 JSON/TOML/.env。

1
选择目标应用：顶部应用切换器定位 Claude、Codex、Gemini、OpenCode、Hermes 等；Provider 列表随应用变化。
2
添加 Provider：点右上 +，选择预设或自定义配置，填写 endpoint、模型和 API Key；统一 Provider 可勾选同步 Claude Code / Codex / Gemini。
3
启用：点击 Provider 卡“启用”，或从系统托盘点击 Provider 名称；文件模式下按客户端要求重启。
4
需要即时切换时开路由：设置 → 高级 → 路由服务，启动后给 Claude / Codex / Gemini 打开应用接管；从此 UI 选择改变 router 的转发目标。
5
扩展维护：MCP 可用模板/自定义 server，并按 app 同步；Prompts 用 Markdown 编辑后激活；Skills 可浏览 GitHub repo 后一键安装到支持的 app。

同一个选择，如何落到不同工具？

统一界面不意味着所有客户端走同一文件、同一能力、同一重启规则。

06
ROUTER

本地路由：热切换为什么能成立？

它不是云端聚合服务，而是可选的 localhost 代理层；官方“应用接管”明确为 Claude、Codex、Gemini 三项。

入口

固定到本地端口

路由开启后：Claude 的 ANTHROPIC_BASE_URL、Codex 的 base_url、Gemini 的 GOOGLE_GEMINI_BASE_URL 都指向 localhost 默认端口 15721（端口可配置）。

转发

按 app 找当前 Provider

router 识别请求来自 Claude/Codex/Gemini，查找该 app 当前启用 Provider，转发至真实 endpoint，记录日志/用量，再返回响应。

转换

解决 Codex 非原生上游

对于仅支持 Chat Completions 或非 GPT 名称的上游，router 可将 Codex Responses 请求与流式、reasoning、工具调用转换回来；兼容性仍取决于上游实现。

07
CHOICE GUIDE

GUI、托盘、路由：什么时候选哪个？

不是 UI vs CLI 的二选一，而是控制面与消费面的不同组合。

你偶尔换供应商

选：GUI 文件模式

适合先试用、配置不频繁变更、需要看见完整 Provider 参数。接受多数 CLI 重启后生效。

你频繁切账号 / 模型

选：托盘 + 路由

适合会话不断、希望下游 CLI 不重启。要理解代理只在本机监听、需要保持 CC Switch router 运行。

你想写自动化脚本

不要假设 CC Switch 有 shell API

当前官方公开资料没有面向用户的 Provider-switching CLI；应评估目标 CLI 自己的配置方式，或等待项目提供正式自动化接口。

08
BOUNDARIES

优势与限制，要同时写

把“能管理”说清楚，比把产品描绘成万能网关更有用。

它的优势

一处维护、多格式投影；SQLite SSOT + 原子写 + 备份；可视化 Provider/MCP/Prompt/Skill 管理；对于 Claude/Codex/Gemini 可选 router 提供热切、协议转换、健康监控与 failover。

必须保留的限制

不是自身 CLI；统一 Provider 只明示三类 CLI；router 接管也只明示 Claude/Codex/Gemini；Claude Desktop 是独立入口且有平台/同步限制；第三方 endpoint、模型、工具调用与流式兼容不能仅凭“OpenAI-compatible”自动保证。
