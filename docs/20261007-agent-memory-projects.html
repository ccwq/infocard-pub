AI 记忆 · 选型与验证手册

AI 一开新会话就失忆？先分清这十个项目，再跑通一个记忆闭环

不是十个同类数据库：这里有记忆层、时序图谱、上下文文件系统、有状态 Agent、会话迁移和评测工具。先选一个解决具体问题，再用隔离、更正、删除和任务成功率验收；不要把三个项目的名字连成箭头就当成可运行集成。

01一分钟先选一个逐层深入 · 从选择到验收

一分钟先选一个

只想让聊天助手记住偏好：先比较 Mem0 或 Hindsight。希望把多个编程工具的经验积累为可读 wiki：看 memU。要把文档与代码关联起来：看 Cognee。问题重点是“当时与现在分别什么是真的”：看 Graphiti。希望知识、记忆、Skills 都按目录管理：看 OpenViking。要一个自己持有记忆和身份的 Agent 运行时：看 Letta Code。只是换编程工具时搬会话：看 OpenMemory。测方案是否值得：用 AMB 或你自己的固定测试集。

新手先选一个后端，不同时部署三个。写下当前失败案例、主数据存放位置、允许的数据外发范围，以及你愿意维护多少服务。若需求只是一份稳定偏好或项目约定，普通文件可能已足够；只有跨会话检索和更新明显失效时，才引入额外记忆系统。

02记忆不是保存聊天全文逐层深入 · 从选择到验收

记忆不是保存聊天全文

一个实际闭环至少包含：采集可信事件 → 提取与存储 → 关联／更新 → 按问题检索 → 将证据交给 Agent → 验证行动。聊天记录是原始材料，提取出的事实是派生记录，反思是推理产物；三者不能混成同一真值。

记忆后端不能替你保证每次回答都会使用记忆。应用仍要在生成前查询、控制上下文预算、附带来源，并在任务后决定哪些结果值得写回。也不能把失败工具调用记成已完成动作。

03Mem0逐层深入 · 从选择到验收

Mem0

通用记忆层；支持用户、会话与 Agent 相关记忆。

依赖与部署：Python／JS SDK、CLI、云平台或自托管服务。库路线安装 mem0ai；默认推理与 embedding 调用需配置模型凭据。

具体入口：在生成回答前 search，完成可信对话后 add；按 user_id 限定记忆，不把多租户鉴权交给模型选择。

如何验收：测跨会话偏好召回、同名用户隔离、更正信息、检索结果来源和写入成本。

不要误用：不需要知识图谱就不要为了“高级”再叠加一个图系统。README 2026 年新算法分数来自 managed platform，含 OSS 不具备的专有优化，不能承诺 SDK 得到同分。

04Hindsight逐层深入 · 从选择到验收

Hindsight

学习导向记忆系统：retain、recall、reflect；支持 observations、mental models、knowledge pages 和 banks。

依赖与部署：可用 Docker／pip 服务、嵌入模式或云服务；自托管存储包括 PostgreSQL + pgvector，提取与反思依赖模型。

具体入口：retain 提取并归一化事实；recall 并行语义、关键词、图与时间检索并融合排序；reflect 分析已有记忆。

如何验收：先验证一个 bank 中的写入与召回，再验证跨 bank 隔离及反思引用的事实来源。

不要误用：反思不等于确证事实。Mental model 是持续更新的答案文档，不代表无需维护权限。README 独立复现声明不等于本页亲自复现。

05memU逐层深入 · 从选择到验收

memU

跨会话、Agent 与设备的共享 LLM wiki；从历史提炼记忆与可复用 Skills。

依赖与部署：当前 README 提供 memu-cli；Python 3.11+。Local 与 Cloud 可选，Local 支持 SQLite 或 Postgres，并配置 embedding provider。

具体入口：按 host adapter 接入采集与检索；先读对应 install guide，再用 doctor 验证配置、模式及实际检索路径。

如何验收：确认 memorize 与 retrieve 两条接缝都活着，检查记忆文件和检索是否指向同一个 store。

不要误用：不是 Mem0 同组织项目。不要只完成安装就声称全部宿主均可用；后台采集属于持续行为，需按宿主规则确认范围。

06Cognee逐层深入 · 从选择到验收

Cognee

把文本、代码与会话指导转为实体、关系、可检索片段和代码依赖图。

依赖与部署：Python 3.10–3.14；当前本地快速开始使用 cognee[gliner]，首次下载提取与 embedding 模型。

具体入口：当前入口 remember、recall、improve、forget。本地无 LLM key 可提取并返回证据；生成答案与部分媒体处理需额外模型配置。

如何验收：先记住一段文本，检索原始证据，再看图关系是否真的帮助回答；对代码用代码相关检索路径。

不要误用：本地无 LLM 不等于零下载或零计算。多个系统重复提取相同文档会增加成本与冲突，不要把图本身当作业务收益。

07Graphiti逐层深入 · 从选择到验收

Graphiti

构建动态时序上下文图：实体、带有效期的事实／关系、可追溯 episodes。

依赖与部署：Python 3.10+；配置图数据库与推理、embedding。README 推荐 Neo4j／FalkorDB 等；Kuzu 已弃用，新项目不要默认选它。

具体入口：先完成索引约束初始化、写 episodes、查询关系，再检查事实更新后的有效期。官方 quickstart 覆盖不同存储后端。

如何验收：写入“旧负责人”与“新负责人”带时间的事件，分别查当前与历史；检索结果要能回到原始 episode。

不要误用：Graphiti 是 OSS 框架，Zep 是托管上下文平台，运维和业务管理能力不同。事实失效不等于物理删除。小模型不可靠的 Structured Output 可能导致入库失败。

08OpenViking逐层深入 · 从选择到验收

OpenViking

统一知识、记忆与 Skills 的上下文数据库，以 viking:// 虚拟文件系统组织内容。

依赖与部署：部署需 uv、Python 3.10+、embedding 模型与 VLM。可自托管或选择托管服务，不能把浏览器 demo 当作部署成功。

具体入口：目录有 L0 摘要、L1 概览、L2 原始详情；先读摘要判断相关性，再按目录查找。会话提交可归档与提取可读记忆。

如何验收：检查资源 URI、目录摘要是否对应原文件；同一问题比较全索引与限定目录检索，并验证 session commit 的产物。

不要误用：AGPLv3 许可需要结合网络服务和修改场景评估。配置向导需明确模型、工作目录与鉴权；不要自动开放到公网。

09Letta逐层深入 · 从选择到验收

Letta

有状态 Agent 的项目入口；当前主分支指向 Letta Code 的活跃源码。

依赖与部署：当前源码与运行入口在 letta-ai/letta-code；archive 分支保留退役 V1 API server 供历史复现。

具体入口：从当前安装指南进入 CLI、App Server、桌面或 Web；不要以旧 V1 API 教程新建未经核实的运行链。

如何验收：记录使用的源码分支与 npm 包版本，确认重启后恢复的是同一 Agent，而不是新身份。

不要误用：Letta 与 Letta Code 不应在矩阵中被算作两套必须串联的独立后端。原推仍列两个仓库，本文保留链接但说明关系。

10Letta Code逐层深入 · 从选择到验收

Letta Code

有状态 Agent harness：记忆、身份、长期学习；MemFS、Skills、子 Agent、hooks 与调度。

依赖与部署：npm 包 @letta-ai/letta-code；首次运行选择 cloud 或 local，用 /connect 配置模型、/model 选择模型。

具体入口：MemFS 用 Git 跟踪上下文；/palace 查看记忆，/search 查消息。letta server 是当前 App Server 入口，不是旧 V1 server。

如何验收：退出再打开同一 Agent，检查记忆／身份是否恢复；观察生成的 Skills 是否来自可信反馈而不是未经确认推断。

不要误用：运行时会执行工具，风险不止存储。Windows 自动 dreaming 默认关闭；远程与云状态需查实际后端，不能据一个菜单推定数据驻留。

12Agent Memory Benchmark逐层深入 · 从选择到验收

Agent Memory Benchmark

AMB 是开放评测 harness，不是存储后端；同时观察准确率、成本与速度。

依赖与部署：Python ≥3.11；通常需要 GEMINI_API_KEY 用于生成与 judge，某些数据集需本地路径。

具体入口：标准流程 ingest→retrieve→generate→judge；retrieval latency 独立记录。PrecisionMemBench 的 retrieval 模式直接断言返回集合，没有答案 LLM 与 judge。

如何验收：先列 providers 与 datasets，再用少量 query 跑 baseline；固定模型、数据域和预算，保留 outputs 结果与错误。

不要误用：由 Vectorize 建立，不应称为与厂商无关的中立机构。不同数据集、judge、模型和检索预算的分数不能直接排总榜。

uv run amb run --dataset personamem --domain 32k --memory bm25 --query-limit 20
uv run amb view

路线 A：编程记忆怎样分工

Hindsight 可保存经历与反馈，Cognee 可组织文档／代码关联，Letta Code 承担有状态 Agent 运行。现实风险是 Letta Code 已有自己的记忆，Hindsight 与 Cognee 也都可检索，三个系统可能对同一事实给出不同版本。

先用 Letta Code 自带记忆完成一个重复任务。如果问题是历史教训召回，再单独评估 Hindsight；如果问题是代码／文档关系，再单独评估 Cognee。真正组合时，需要自己设计工具适配、输入来源、更新触发和删除传播，不在三个系统无条件双写。

路线 B：个性化与时效事实

Mem0 可承担偏好记忆，Graphiti 适合随时间变化的关系，Letta 当前入口指向 Letta Code。简单“用户喜欢中文”不需要额外图数据库；只有你确实要回答当前职位、历史负责人等时间问题，才评估 Graphiti。

路线 C：企业知识为何不能堆三套

Cognee、Graphiti、Hindsight 都有提取／检索能力，但数据模型和优化目标不同。公司知识库首先需要权限与来源边界：哪些文档可读、谁能读取、政策何时生效、删除请求能否传播。

先固定一个知识源和一类查询：文档与代码关系选 Cognee 试验；政策／组织事实时效选 Graphiti；Agent 的工作经历和反馈选 Hindsight。只有失败案例证明第二套系统补上独立能力，才组合。否则只是重复索引、重复付费和增加排错难度。

从单后端到真实试验

① 建独立测试目录与合成数据，不把生产聊天直接导入。② 固定模型与 embedding，记录安装版本和数据位置。③ 写入三类材料：稳定偏好、带时间更正、工具任务结果。④ 退出并新开会话，检索并检查来源。⑤ 让 Agent 完成一个实际小任务，检查记忆是否改善行动。⑥ 测隔离、删除、噪声和拒答。⑦ 与无记忆 baseline 比较，再决定是否增加组件。

排错按接缝定位：采集是否发生→提取是否正确→索引是否写入→过滤范围是否正确→检索是否命中→生成是否采用→行动是否成功。不要只看到服务启动或一个 recall 返回文本，就宣布全链路成功。

评测：效果和成本一起看

准确率之外，记录 ingest 时间、检索延迟、生成延迟、每次模型调用与 Token、存储增长和失败率。用同一个数据集、同一个回答模型、同一个 judge、相同检索预算做 baseline；同时测不应该召回的记录。

Mem0 README 的新算法表明确属于托管平台，不能当 OSS 的保证；OpenViking 与 Hindsight 的公开评测也有特定模型与配置。本文没有安装十套后端或复现公开分数，所以不提供伪造排名或“固定省多少 Token”的承诺。先用 AMB 的 providers 与少量 query 验证实验可运行，再扩展规模。

从一次成功，走向可重复验收

下列是工程验收建议，不是本页宣称已经跑出的结果。不要只测“喜欢深色模式”这一条召回；先固定模型、检索预算和数据集，再测试错误记忆会不会继续污染行动。

  1. 跨会话：在会话 A 写入“测试用户偏好中文回答”，退出后用会话 B 检索；同时记录返回的来源，不用聊天缓存冒充持久记忆。
  2. 更正：先写“项目使用 Flask”，再写带新时间的“已迁移到 FastAPI”；分别问当前与历史技术栈，检查旧事实的有效期和新事实的优先级。
  3. 隔离：给两个合成用户不同偏好，从服务端绑定用户身份后查询；用户文本不能自行选择他人的 bank、group 或 user_id。索引过滤并不自动提供业务鉴权。
  4. 删除：删除一条记录后分别查原文、向量、图边、生成摘要与缓存；“旧事实失效”不等于“敏感数据彻底删除”，备份留存也应有明确策略。
  5. 噪声：添加与当前问题无关的记忆，再查目标事实；既看正确召回，也看不该返回的记录是否混入。
  6. 拒答：问一个从未写入的事实。系统应明确没有证据，而不是把 reflect 的推断包装成用户说过的话。
  7. 行动：让 Agent 基于记忆完成一个小任务，检查是否真正应用偏好、保留权限限制，而不只在回答中复述事实。
组合之前，先定义数据契约

这不是任何一个项目现成的统一 API，而是你需要设计的接入边界：每条候选记忆至少带主体标识、项目范围、原始来源引用、事件时间、写入时间、事实／推断类型与删除关联标识。记忆原文是数据，不是更高权限指令；跨系统复制不得把普通历史文字升级成 system prompt。

只指定一个主写入者和一个“当前事实”权威源。其余层接收带版本的派生数据，保留可回溯的 source_id；重试要幂等，删除必须能传播，权限要在每一层检查。出现冲突时，先查证据和有效时间，而不是让三个模型投票。只有单后端的测量结果确实暴露知识关联或时间查询缺口，才增加第二个系统。

隐私与许可：记住更多也意味着保留更多

不要保存真实 API key、完整客户隐私或未获许可的聊天记录。确认推理、embedding、judge 各环节实际收到哪些数据；自托管数据库不代表模型请求不外发。记忆数据与系统指令分开，执行前仍检查用户权限。删除需要覆盖原文、派生摘要、图边、向量和备份策略。
