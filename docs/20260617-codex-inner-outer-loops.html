Codex 自动化的 Inner / Outer Loop

Codex 每两小时给我准备一批邮件草稿，大多写得不错，但我仍然要改。改的不是智能，是缺失的上下文——而那些修改本身，又恰好是下一次跑的最佳上下文。

Codex Automation Inner / Outer Loop context engineering
INNER LOOP ≠ OUTER LOOP
两个循环，两种上下文，两种节奏。
Inner

把上下文带到任务

分类、检索、起草、检查、产生可复审的草稿；任何动作都可逆，never send。

Outer

把评审里的上下文回收

看 send / edit / delete / pending 的差异，提炼成下一次能用的写作指引或检索步骤。

“没有这份记录，评审只是轶事；有了它，评审就成了证据。”
大多数自动化不会保留这份证据，所以下一次启动时，它们仍然从同一张不完整的图开始。Inner / Outer Loop 的目标，就是把每次评审的差异沉淀成下次运行可以读到的事实。
1 Inner · 取上下文 history、facts、constraints、relationships、prior decisions。
2 Inner · 出草稿 分类、检索、起草、检查；只产出 draft，永远不直接发送。
3 Outer · 读评审 send / edited / deleted / pending — 每一类结果都是不同的证据。
4 Outer · 回写规则 把可复用的修改沉到 markdown，让下次 Inner Loop 第一时间读到。

INNER LOOP

把上下文带到任务

1

检索是写作的一部分

一封回信可能依赖一封类似邮件、半年前的决策、当前项目状态或一份可信来源；目标不是“全部检索”，而是用最少的事实让回信准确具体。

2

固定流程或自由编排都行

Inner Loop 既可以写成代码工作流，也可以是“每天 9 点给我准备草稿”的 prompt 让 Codex 自己决定步骤；关键是产生 reviewable draft。

3

动作必须可逆

create the draft, never send it。把草稿、来源、Prompt 与写作指引版本一起留下；少了这份记录，评审就只是轶事。

4

检查是写作的一部分

对承诺、事实和敏感语气做轻量校验；让 Codex 主动把不确定项 surface 给人，而不是直接生成漂亮但虚假的句子。

5

子任务可外包给 subagent

当某段上下文需要更深的检索（如查项目状态），交给 subagent 单独跑一轮，Inner Loop 自身保持紧凑。

OUTER LOOP

把评审反向变成上下文

四种结果

send / edited / deleted / pending

原样发出说明草稿成立；编辑后发出给出 before/after 对照；删除可能是写偏，也可能是“本来就不该回”；pending 信息最少。

Diff 是证据，不是结论

读懂差异，才是 Outer Loop 的真活

开头变短可能只是写作偏好；补一段事实可能说明 Inner 的检索找错位置；删去一个承诺可能在喊“这里需要一道检查”。

三类常见补丁

writing guidance · 新来源 · 新检查

不是每次修改都该变成规则；Outer Loop 找模式，提议“最小有用变更”，最终由人决定保留与否。

写回 markdown

让下次 Inner Loop 立刻读到

把通过的 lesson 沉到一份简单 md 文件；Inner 在起草之前先读它——“今天纠正的，就是明天起草的上下文”。

CADENCE · BEYOND EMAIL

两套循环，两种节奏

Inner 节拍

快节奏，例如每两小时一次

Inner Loop 的目标是“随手能用”，所以频率高、单次轻；它不需要等待评审反馈，先产出可被审阅的最佳猜测。

Outer 节拍

慢节奏，每天 / 每 10 条 / 每周

Outer Loop 必须等到样本够多才动手；过早会被异常案例带偏，过晚会让有用的修改随下次草稿一起消失。

不止于邮件

同样适用于演示、报告、issue triage

任何“先生成草稿、再人工审阅”的工作，都能套用这个双循环；模型已经够强，机会在于工作流不要让它每次都重发现同一份上下文。

一句话收束

Inner 带上下文进来，Outer 把上下文留下来

两条循环各管一头，组合起来，自动化就从“每次重新开始”，变成“每次都比上次更接近你想要的回信”。
