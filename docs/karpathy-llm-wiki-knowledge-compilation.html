01
ARCHITECTURE · 架构

三层架构：Raw / Wiki / Schema

所有原始资料进入 Raw/（不可变）→ LLM 编译输出至 Wiki/（LLM 全权维护）→ Schema（CLAUDE.md）定义系统行为规范

Layer 1

Raw/ · 原始资料库

存放所有输入源：PDF、文章、推文、论文、网页。原始资料一旦写入，永不修改——这是知识溯源的锚点。

  • 不可变（immutable）存储
  • LLM 不得直接读取原始文件回答问题
  • 质量边界：源文件质量决定 Wiki 上限
Layer 2

Wiki/ · 编译产物库

LLM 全权维护的「复合工件」—— 编译后的概念页、摘要、交叉引用。用户几乎从不直接写入 Wiki/。

  • LLM 编译一次，持续保持最新
  • Wiki 内各页面之间形成语义关联
  • "You almost never write to the wiki"
Layer 3 ⭐

Schema · 系统灵魂

CLAUDE.md（或 SYSTEM.md）定义 Wiki 维护的规范与原则——决定 LLM 是「有纪律的维基管理员」还是「泛泛的聊天机器人」。

  • Gist 最核心、最重要的文件
  • 定义 LLM 的角色边界与行为准则
  • Schema 驱动编译，非用户指令
核心准则

"The wiki is a persistent, compounding artifact"

Wiki 是一个持久累积的复合工件——知识不需要在每次查询时重新发现，LLM 持续维护，索引随时间增值而非重置。这是 llm-wiki 与传统 RAG 的根本区别。

设计原则

Schema-first，不是 Query-first

传统 RAG 每次查询都从零发现知识。llm-wiki 先定义 Schema（LLM 的行为规范），再让 LLM 持续按规范维护 Wiki——从被动响应变成主动管理。

02
OPERATIONS · 操作

三个操作：Ingest / Query / Lint

⚠️ 用户描述的「六个环节」在 Gist 原文未出现，原文明确列出的是三类操作

INGEST

摄入（Ingest）

将新的原始资料（网页、PDF、推文等）放入 Raw/，LLM 根据 Schema 自动提取概念、生成摘要、建立关联。

  • 原始资料 → 不可变 Raw/
  • LLM 自动分析 → 写入 Wiki/
  • 增量更新，不重写历史
QUERY

查询（Query）

用户向 Wiki/ 提问，LLM 基于 Wiki 内容作答——Wiki 是唯一的信任源，用户几乎从不读 Raw/。

  • "You almost never read the raw sources, you read the wiki."
  • Wiki 是唯一的事实锚点
  • 跨页交叉引用驱动综合回答
LINT

检查（Lint）

定期对 Wiki/ 运行一致性检查——概念是否过时？引用是否断裂？内容是否重复？维护 Wiki 的长期健康度。

  • 质量门禁与健康检查
  • 防止知识蒸发与碎片化
  • 建议定期（定时）运行

COMPARISON · 对比

不用 RAG：根本范式差异

Gist 原文明确对比传统 RAG（如 NotebookLM、Google AI Studio 文件上传），指出 RAG 的核心缺陷

关键区别

RAG = 检索增强，LLM Wiki = 知识编译

RAG 是「把知识放进向量库，查询时召回相关片段」；LLM Wiki 是「LLM 持续将原始资料编译成结构化知识网络」。前者是工具，后者是系统。

05
SCHEMA · 灵魂

Schema：LLM 从聊天机器人到维基管理员的跃迁

Schema（CLAUDE.md）是 llm-wiki 系统的核心——它将 LLM 从被动响应的聊天机器人转变为主动维护知识库的纪律管理员

⭐ 核心文件

Schema 驱动整个系统

Schema 定义了 LLM 维护 Wiki 的所有规范：页面命名规则、概念提取标准、引用格式、更新策略。它是 LLM 行为的宪法。

  • LLM 按 Schema 编译 Raw/ → Wiki/
  • LLM 按 Schema 响应 Query
  • LLM 按 Schema 运行 Lint
设计洞察

「系统 prompt」比「用户 prompt」重要

Schema 是系统级定义，优先于任何用户查询。好的 Schema 让 LLM 在无人监督下保持一致性；差的 Schema 让 Wiki 逐渐碎片化。

  • Schema 质量决定编译质量
  • 用户只需问问题，无需管理 Wiki
  • LLM 是管理员，不是工具
06
IMPLEMENTATION · 项目实现

从方法论到工具：pi-llm-wiki 的落地方式

它不是 Karpathy 本人的项目，而是面向 pi 的开源扩展：把“持续维护 Markdown Wiki”的思路落实为可执行工具与目录契约。

SOURCE PACKETS

先冻结来源，再生成知识页

URL、PDF、Markdown、JSON、XML 等资料会先进入不可变来源包；之后再生成来源摘要、概念/实体页与综合分析，避免让原始资料被直接改写。

LAYERED VAULTS

个人积累 + 项目上下文

个人 vault 位于 ~/.llm-wiki/，项目 vault 位于 .llm-wiki/。召回时可跨两层检索并去重，让通用经验和项目专属知识分层共存。

OBSIDIAN / OKF

保持文件可读与可迁移

Wiki 仍是 Markdown vault，可在 Obsidian 中查看与编辑；项目声明支持 OKF v0.2，目标是让知识不被单一客户端或专有数据库锁定。

MCP

把 Wiki 接进 Agent 工作流

项目提供 stdio MCP Server，文档列出 Claude Code、Cursor、Windsurf 等 MCP 客户端接入场景。实际兼容性仍取决于客户端的 MCP 配置与运行环境。

MAINTENANCE

“自维护”不是无人值守

wiki_lint 可检查断链、孤立页、重复别名和覆盖缺口；wiki_watch 只生成定时任务命令，不会自动安装。持续维护仍需要模型调用与运维配置。

OPT-IN

Agent 轨迹与“技能”沉淀：默认关闭

任务轨迹捕获、模式提炼和相似案例召回属于可选能力，需要显式启用；其中生成的 skills/ 页面是该项目自己的 Wiki 内容，不等同于其他 Agent 平台的 Skill 机制。
