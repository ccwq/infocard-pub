多 Agent 省 Token：
共享状态，而非重复同步

把任务分工、接口约定、已定事项和阻塞写成一份短文件。消息只发“哪里变了、谁需要行动”，不再逐个转述整段背景。

适合：多方反复同步 不承诺固定节省比例

01 / 一分钟开始

先选一件正在反复解释的事

  1. 确定共享入口。在项目根目录建 AGENT_STATUS.md；如果已有可信的产物或接口文档，就复用它，不复制第二份。
  2. 只写当前事实。目标、角色、接口、已定事项、阻塞。不要把全部聊天搬进文件。
  3. 告诉参与者读取规则。查当前进度和接口先读文件；消息只包含变更摘要、位置、受影响角色和动作。
  4. 完成后删除失效状态。历史讨论移出当前入口；若团队需要审计，历史放到独立记录中。
可直接给 Agent 的协作约定（实践建议）

“以根目录 AGENT_STATUS.md 为当前协作状态。修改职责范围内事实后更新对应段落；接口变更先写契约，再通知受影响角色。不要转述整份文件，也不要向无关角色广播确认。无法确认的信息写为待决，不当作已定事项。”

02 / Token 花在哪里

不是读文件免费，而是少讲几遍

重复背景

后端分别向前端、测试解释同一字段变化；协调者又把同一信息收集并转述。

无效确认

多个角色回复“收到”，却没有更新实现或验证结果。产生文本不等于完成交接。

按需查证

共享文件让需要行动的角色读取同一约定。读取仍计入输入 Token；文件过长、重复全量读取也会增加成本。

原文强调减少来回沟通，并未给出“文件读取不计费”的规则。总费用不能直接从输出 Token 减少推断。

03 / 可复制模板

一份能用于交接的当前状态

以下模板与版本号、验收字段是本文的实践补充，不是论文的原始实验配置。字段能删则删，不为模板而填模板。

# 当前协作状态
更新：2026-10-06 / 契约版本：login-v2

## 目标
完成登录页字段迁移，前后端与测试一致。

## 分工
- 后端：维护接口响应契约
- 前端：迁移字段读取与显示
- 测试：更新断言，记录结果

## 接口契约
POST /login
旧响应：{ "name": "demo" }
新响应：{ "username": "demo" }
此处为简化示例，非真实接口实测。

## 已定事项
统一读取 username；是否兼容 name 仍待决定。

## 当前进度 / 验收
后端：已更新契约，待实现验证
前端：待迁移，完成后记录引用检查结果
测试：待更新断言，完成后记录运行结果

## 阻塞 / 下一步
兼容策略未定：负责人确认后更新本节。

避免写“全部完成”却无对应证据。没有运行测试就写“待验证”，不要填虚构日志。

04 / 一次具体交接

登录字段 name → username

不推荐：逐人讲完整背景

后端向前端解释字段变化，向测试再解释一遍；协调者重新广播，每个人再回复确认。

风险：上下文重复、版本混淆；“收到”无法证明消费者已经迁移。

推荐：契约更新 + 定向通知

后端先把新响应写进状态文件。只通知前端与测试：“login-v2 已更新，见接口契约段；前端迁移读取，测试更新断言。完成后写验收结果。”

协调者只检查是否还有未完成消费者，不再次转述全文。

  1. 后端：更新契约，说明兼容策略是否已决定。
  2. 前端：读取同一版本，修改字段使用处，记录结果。
  3. 测试：按同一版本更新断言，真实运行并登记通过或失败。
  4. 协调者：发现未闭环交接时才介入，明确责任与下一步。
多写者注意（实践建议）

约定段落归属；不要多个 Agent 同时覆盖整份文件。接口段由维护者更新，冲突先协调；版本标识用于发现旧约定，不代替实际检查。

05 / 决策边界

哪些场景值得用，哪些不值得

场景建议原因
多角色反复转述同一接口/进度共享短状态 + 定向通知减少重复解释，统一当前事实
只有两个 Agent，单条消息可交清楚直接消息维护文件的成本可能不划算
结果已经保存在可信文件里直接读原文件避免复制后产生两个“真相”
紧急阻塞或需要明确确认短通知并记录行动结果文件存在不等于对方及时读取
状态文件越写越长删旧状态，保留当前事实降低输入与查找负担
06 / 原文研究主张

数字要连同条件一起读

1,902

实验次数

论文主数据集包含 1,902 次运行：Claude Code 2.1.x，固定 claude-sonnet-4-6，合成 Python 任务；另有 244 次隔离环境复验。

约 42%

输出 Token 减少

分布式规格任务、8 Agent，强制文件策略对比允许文件默认策略，汇总结构与分割条件后输出约少 42%；两批范围 36%–49%。链式任务反而约多 10%。

9/10 vs 0/10

一个八步骤任务

compute_invoices 八步骤链：2/4 Agent 为 9/10，8 Agent 为 0/10。第 7 步税额不应舍入，第 8 步才统一舍入；拆给不同角色后交接失败，不代表 8 Agent 必然失败。

证据边界

研究出处已核对：Giuseppe Destefanis 与 Tomaso Aste，When Agents Coordinate: Measuring Coordination in Multi-Agent AI Coding，arXiv:2608.16801，第 3、6、7 节。42% 是输出指标而非总账单；主实验隐藏评分材料曾可访问，作者追加隔离复验。合成任务和小样本不能直接替代真实项目评测。

07 / 自己验证

做一次可对照的小试验

这是实践测量建议，并非本卡已完成的基准测试。选一个重复沟通明显的任务，比较消息同步与共享文件两种方式。

  • 保持条件一致：相同任务、模型、Agent 数量、工具和成功标准；只改变协作信息的传递方式。
  • 分开记账：输入 Token、输出 Token、文件读取次数、往返消息次数、耗时、任务成功与返工次数。
  • 不要只看一轮：多次重复，保留失败；不要以一次最好结果宣称普遍降幅。
  • 先确认交付正确：如果少聊但接口交接失败，不能算协作优化成功。
下一次协作先做什么？

不要先把两个 Agent 拆成八个。先找一条被反复转述的事实，让它有一个短而可信的共享入口，再验证相关角色是否真的完成了交接。
