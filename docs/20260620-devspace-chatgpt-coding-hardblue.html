01核心定位
DevSpace 不是云端代理，而是“把本地机器变成 ChatGPT 可审查、可批准、可执行的工作区”。它的关键不是聊天，而是把读写文件、搜索代码、运行命令、git 乃至工作树管理都变成受控工具。
02工作流链路
01

本地初始化

devspace init 设定允许打开的项目根目录、端口和 owner password。

02

安全连接

通过你控制的 HTTPS tunnel 暴露 /mcp，再由 MCP 客户端连接。

03

审批授权

连接后需要 Owner password，确保 ChatGPT 不能绕过你的本机授权。

04

工作区执行

在已批准的 workspace 中读写文件、跑命令、用 git worktree 并行工作。

03README 暴露的关键能力

读写本地项目

在已打开的工作区里，ChatGPT 可以检查仓库结构、编辑文件和查看改动。

执行本地命令

支持 shell 执行，用于测试、构建、搜索和 git 流程。

隔离工作树

能为并行编码会话创建独立 worktree，减少互相污染。

加载项目规则

会读取 AGENTS.md / CLAUDE.md，让项目约定自动进入工作流。

本地技能发现

能够从技能目录发现本地 agent skills，把流程带进 ChatGPT。

变更摘要

在兼容宿主中展示工具卡与改动摘要，便于复核。

04安装与门槛

最低安装路径

npm install -g @waishnav/devspace，然后 devspace init + devspace serve。

Node 22 推荐owner password

连接方式

默认本地端点是 http://127.0.0.1:7676/mcp；实际使用通常通过你控制的 HTTPS tunnel 暴露。

/mcptunnel-controlled
05安全边界与风险
项目判断说明
安全模型明确你决定允许哪些 root，权限边界是可见的，不是黑盒。
风险点较高一旦连接，MCP 客户端在已打开工作区内拥有很强本地能力，要把它视为可信 coding partner。
适用范围局部、受控最适合你希望 ChatGPT 直接操作本地项目但又不想把文件上传到第三方的场景。
不适用纯云端协作如果你不想管理 tunnel、owner password 和本机权限，这套方案会偏重。
06一句话总结
DevSpace 的本质是：把“对本地项目的受控访问”产品化，再把它包装成 ChatGPT 的 代码工作流入口。它更像一个本机权限与工作区控制层，而不只是一个 MCP demo。
