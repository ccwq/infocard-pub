# LLM Wiki 是什么、和 Hermes 什么关系、值不值得装？

**调查日期**：2026-05-29  
**协作角色**：尼克（统筹） / 王记者（主调查） / 希尔（环境与可安装性核查） / 转哥（信息卡结构与可读性把关）  
**调查主题**：围绕提示信息 `No LLM Wiki directory was found. Set WIKI_PATH or skills.config.wiki.path to enable status visibility.`，回答四个问题：

1. LLM Wiki 到底是干嘛的
2. 它和 Hermes 是什么关系
3. 两者结合能带来什么提升
4. 对系统要求如何、当前电脑能否安装

---

## 0. 结论先行

**LLM Wiki 不是另一个大模型产品，而是一种“把知识长期沉淀成互相链接的 Markdown Wiki”的工作模式。**

它和 Hermes 的关系不是竞争关系，而是：

> **Hermes 负责采集、整理、更新、回答；LLM Wiki 负责把这些结果存成结构化、可追溯、可持续复用的知识库。**

因此，两者结合的本质提升是：

- 从“一次性问答”升级为“持续积累的知识系统”
- 从“聊天记录里反复翻旧账”升级为“按主题组织的长期知识资产”
- 从“每次重新搜索、重新总结”升级为“增量更新、交叉链接、持续复用”

**对系统要求很低。** 它本质上只需要一个目录来存放 Markdown 文件；如果想和 Obsidian 结合，再额外装一个 Obsidian 即可。对 Hermes 的要求也不高，主要是把 `WIKI_PATH` 或 `skills.config.wiki.path` 配好。

**本机结论：可以安装，而且当前机器已经具备基本条件；现在缺的不是硬件或依赖，而是“尚未创建 wiki 目录、尚未配置路径”。**

---

## 1. 触发这条提示的真正含义

用户看到的提示是：

> `No LLM Wiki directory was found. Set WIKI_PATH or skills.config.wiki.path to enable status visibility.`

这句话的意思不是“功能坏了”或“系统缺依赖”，而是：

- Hermes / 相关技能尝试查看一个 LLM Wiki 的目录状态
- 但当前没有发现可用的 wiki 目录
- 所以无法展示“这个 wiki 现在有哪些页面、结构是否存在、是否可见”这类状态信息

换句话说，这更接近“**未配置**”而不是“**安装失败**”。

---

## 2. LLM Wiki 到底是干嘛的

根据 `llm-wiki` 技能定义，LLM Wiki 的核心目标是：

> **把知识编译成一个长期存在、持续更新、互相交叉引用的 Markdown Wiki。**

它强调三层结构：

### 2.1 原始资料层（raw/）
保存网页、论文、访谈、截图、PDF 等原始材料。强调：

- 原始资料不可随意改写
- 用于回溯来源、验证结论、比较版本变化

### 2.2 Wiki 页面层（entities / concepts / comparisons / queries）
把原始材料转成结构化页面：

- `entities/`：人物、组织、产品、模型
- `concepts/`：概念、方法、主题
- `comparisons/`：横向对比
- `queries/`：值得长期保留的问答结果

### 2.3 结构规则层（SCHEMA.md / index.md / log.md）
负责约束整个知识库的行为：

- `SCHEMA.md`：定义命名、标签、页面标准、更新规则
- `index.md`：做总目录，告诉你有哪些页面
- `log.md`：记录每次 ingest / query / update / lint 的动作

### 2.4 它解决的不是“搜索不到”，而是“知识无法复用”
普通聊天式问答的典型问题是：

- 结论会散落在多次会话里
- 下次问同一主题还要重新梳理
- 源头证据和后续结论容易断开
- 相关概念之间缺少链接

LLM Wiki 试图把这些内容变成**可持续维护的知识结构**。

---

## 3. 它和 Hermes 到底什么关系

### 3.1 关系定位
Hermes 是 **Agent 平台 / 执行层**，LLM Wiki 是 **知识沉淀层 / 外部长期记忆载体**。

可以这样理解：

| 组件 | 主要职责 |
|---|---|
| Hermes | 搜索、抓取、整理、提炼、回答、更新 |
| LLM Wiki | 存储、链接、索引、追溯、复用 |

Hermes 擅长“干活”，LLM Wiki 擅长“把干过的活变成资产”。

### 3.2 和 Hermes 自带 memory / fact_store 的区别
Hermes 其实已经有几层记忆：

- `memory`：短小、常驻、面向偏好/稳定事实
- `fact_store`：结构化事实层，适合实体和关系
- `session_search`：历史会话检索
- `skills`：可复用方法论

而 LLM Wiki 的定位不同：

| 能力 | 更适合放在哪里 |
|---|---|
| 用户偏好、环境事实 | memory / fact_store |
| 某次复杂调查的完整知识结构 | LLM Wiki |
| 可重复的流程 | skills |
| 历史对话回看 | session_search |

所以 LLM Wiki 不是替代 Hermes 内存，而是补一层“**长文档型、跨来源、可浏览的知识库**”。

### 3.3 为什么两者天然互补
因为 Hermes 很会：

- 抓网页
- 读文档
- 生成结构化摘要
- 更新页面
- 做 lint / audit

而 LLM Wiki 恰好需要一个代理来做这些持续维护工作。

所以它们结合时最自然的模式是：

> 人负责决定主题和质量门槛；Hermes 负责持续 ingest、更新、链接、巡检；Wiki 负责长期保存成果。

---

## 4. 两者结合后，具体能带来什么提升

### 4.1 从“问完就散”变成“越用越值钱”
如果没有 Wiki：

- 这次调查做完就停在聊天记录里
- 下次同主题又要重搜
- 旧结论很难系统复用

如果有 Wiki：

- 本次结果可以落成主题页面
- 下次只需增量补资料
- Hermes 可以基于既有页面回答更快、更稳定

### 4.2 减少重复劳动
这对调研、技术选型、人物画像、项目知识库尤其有价值：

- 一次 ingest，多次复用
- 一次 cross-link，后续所有相关问题都能受益
- 一次查证，后续不必每轮从零核实

### 4.3 让“证据”和“结论”不脱节
LLM Wiki 设计里很强调来源和 provenance：

- 原始材料保留在 `raw/`
- 页面 frontmatter 记录 sources
- 必要时段落级别可回指来源

这比只看聊天总结更适合长期知识管理，也更适合调查和研究工作。

### 4.4 更适合 Obsidian / Markdown 工作流
因为它本质就是目录 + Markdown 文件：

- 可以直接用 Obsidian 打开
- 可以用 VS Code 管
- 可以配 Git 做版本历史
- 可以和你现有笔记系统并存

### 4.5 比临时 RAG 更接近“编译后的知识库”
技能描述里明确强调：

- 传统 RAG 往往每次查询都重新检索
- LLM Wiki 更像先把知识“编译”进 Wiki
- 交叉引用、矛盾标记、索引都提前整理好

这意味着：

> 它更像长期运营的知识库，而不是一次性的问答缓存。

## 5. 适合哪些场景，不适合哪些场景

### 5.1 适合

1. **长期技术调研**
   - 比如模型、框架、Agent 工具、浏览器自动化方案
2. **人物 / 公司 / 赛道知识库**
   - 人物档案、公司竞争格局、赛道地图
3. **项目型知识沉淀**
   - 文档、规范、设计决策、架构取舍
4. **调查型任务**
   - 一次次线索补充，逐渐汇成完整页
5. **需要人和 Agent 协作维护的知识库**
   - 人定标准，Agent 持续更新

### 5.2 不太适合

1. **只查一次、以后不会再看的问题**
2. **极短生命周期的信息**
   - 比如只活 1-2 天的碎片动态
3. **完全不想维护结构和索引的用户**
4. **只想要即时回答、不关心资料资产化的场景**

换句话说：

- 如果你只要“现在给我答案”，未必需要 LLM Wiki
- 如果你要“以后也能持续复用这些知识”，LLM Wiki 就很有意义

## 6. 对系统要求如何

### 6.1 最低要求
从技能定义看，最低要求其实非常克制：

- 一个文件目录
- 普通文件系统读写
- Markdown 文本文件

也就是说，**它不是数据库系统，不依赖向量库，不强制依赖图数据库，不需要专门后端服务。**

### 6.2 可选增强
如果你想体验更好，可以额外加：

- **Obsidian**：图谱视图、双链浏览、Dataview
- **Git**：版本控制
- **Node.js 22+**：如果你还要用 `obsidian-headless` 同步
- **Hermes 定时任务 / 自动 ingest**：做持续维护

### 6.3 对硬件的要求
从设计目标看，它不是重推理系统，对硬件要求远低于本地大模型：

- CPU：普通桌面 CPU 即可
- RAM：日常文档级知识库不高
- 磁盘：取决于 raw 资料多少，Markdown 本身占用很小

真正会吃空间的是：

- PDF
- 截图
- 原始网页归档
- 资产文件

所以它更像“文档仓库”负担，而不是“模型推理”负担。

## 8. 如果现在要启用，大概需要做什么

### 8.1 最小可用方案
1. 选一个路径，比如：
   - `~/wiki`
   - 或你的知识库专用目录
2. 创建基础结构：
   - `raw/`
   - `entities/`
   - `concepts/`
   - `comparisons/`
   - `queries/`
   - `SCHEMA.md`
   - `index.md`
   - `log.md`
3. 配置 `WIKI_PATH`
4. 让 Hermes 后续 ingest / query / lint 时都用这个目录

### 8.2 如果要和 Obsidian 结合
只要把同一个目录作为 Obsidian vault 打开即可。

### 8.3 如果要做持续更新
可以进一步让 Hermes：

- 定期 ingest 新资料
- 定期 lint wiki
- 重要查询自动回填到 `queries/`
- 主题页面持续增量更新

## 9. 风险与注意事项

### 9.1 结构纪律比“写进去”更重要
LLM Wiki 容易失败在两个地方：

- 页面命名混乱
- 新内容不断堆积但不更新 `index.md` / `log.md`

如果没有规则，它会从“知识库”退化成“Markdown 垃圾堆”。

### 9.2 不要什么都塞进去
它最适合长期价值高的知识。太碎、太短、太容易过期的信息，不一定值得写成正式页面。

### 9.3 要区分“原始资料”和“整理后的结论”
raw 不应乱改；修改和判断应该落在 wiki 页面层。

### 9.4 不是替代 memory，而是补充 memory
用户偏好、环境事实、简短稳定事实，还是应该放 Hermes 自己的记忆系统；Wiki 则适合系统化长内容。

---

## 10. 最终判断

如果你问：

> **LLM Wiki 值不值得和 Hermes 结合？**

我的判断是：**值得，前提是你真的想把调研、调查、知识沉淀做成长期资产。**

如果你只是想临时问几个问题，它的价值不会特别高；但如果你有下面这些需求，它会明显提升 Hermes 的上限：

- 长期跟踪一个主题
- 做连续调查
- 把多次问答沉淀成知识网络
- 需要可回溯、可浏览、可维护的 Markdown 知识库
- 想把 Hermes 从“回答器”升级成“研究与维护助手”

**本机可以装。现在缺的只是目录和配置，不缺安装条件。**

## 11. 给当前问题的最短回答版本

如果只用一句话回答用户最初的问题：

> **LLM Wiki 是一个把知识沉淀成互相链接 Markdown 页面的方法；Hermes 负责帮你采集、整理、更新这套知识库。两者结合能把一次性问答升级成长期知识资产。系统要求很低，而你这台电脑已经具备安装条件，目前只是还没创建 wiki 目录、也没配置 `WIKI_PATH`。**
