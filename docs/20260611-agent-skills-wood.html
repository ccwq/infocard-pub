01 / 这套仓库到底在卖什么

结论
一句话判断

它把“资深工程师的工作习惯”拆成可安装、可调用、可自动触发的技能包；你得到的不只是技能文本，而是围绕开发生命周期组织起来的一整套工作流入口。

Why it matters

从聊天助手，变成工程系统

README 里最有价值的信息不是“有多少个 skill”，而是它把 skills、slash commands、自动激活、平台接入做成统一体验：你在做什么，系统就能切到对应工作流。

What you get

24 个 skill + 7 个命令 + 多平台插件/扩展

核心不是单条命令，而是“在不同开发阶段都能找到对应动作”：定义、计划、构建、测试、审查、简化、发布，各自有清晰入口。

02 / 开发生命周期怎么被组织

流程
1
Define

定义阶段

先明确要构建什么，使用 /spec 把目标、结构、代码风格、测试和边界写清楚。

2
Plan

计划阶段

用 /plan 把任务拆成原子粒度，减少一次性大改造成的失控。

3
Build

构建阶段

通过 /build 逐片实现，保留验证点，避免“写一大坨后才发现错了”。

4
Verify

验证阶段

用 /test 把测试当成证明，要求每个改动都有证据链。

5
Review

审查阶段

通过 /review 改善代码健康，而不是只看“能不能跑”。

6
Ship

发布阶段

用 /ship 把安全、监控、回滚思路一起带上，速度越快越要稳。

04 / 谁该用，谁别急着用

边界
Best fit

适合做工程协作的人

如果你在乎 PRD、任务拆解、测试、审查、发布门禁，而不只是在乎“先出代码”，这套系统会很有用。

Caution

不适合把 agent 当魔法按钮

它不能替你做工程判断，只是把工程判断、流程和门禁标准化；如果输入本来就模糊，仍然会得到模糊输出。

Core value

真正的价值是“可持续复用”

一旦把定义、计划、构建、验证、审查、发布都拆成技能，agent 的行为就不再靠临时 prompt 碰运气，而是靠可重复的工程路径。
