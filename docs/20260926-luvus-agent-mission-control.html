01推文四主张逐条对账

推文说实测（09-26）
开一堆 tmux 窗口肉眼盯盘是真实痛点场景成立：README 功能清单逐条对应——blocked/working/done/idle 状态、session 标题、token、花费、context 占用、可选声音提醒，全部自动探测无需接线
纯 Rust 打造属实：299 个 .rs 文件 9.0MB；单二进制四角色——无命令=TUI 客户端、detached server 拥有全部状态、CLI 发有界 JSON 即退、web 起浏览器桥
解决多 Agent 跑飞、窗口爆炸、互相踩脚机制在但要读细：跑飞=状态面板+声音告警；窗口爆炸=workspace/tab/pane 持久化+命名会话；踩脚=worktree 编排 + path leases 按项目隔离——是提供机制，不是自动免疫
"超级 tmux"类比一半：交互层确有 split/zoom/copy-mode/mouse；但本质差异是 server 常驻 + agent 语义 + UHP 自动化契约——tmux 没有"agent 在等确认"这个概念

03架构读法：server 是唯一写入者

A单二进制多角色——无命令起/附着 TUI；detached server 拥有 workspaces/tabs/panes/PTY/终端网格/agent 状态/持久化/编排/API；CLI 发完 JSON 就退；--session name 切命名会话（按需冷启动，不断开其他客户端）；--local 是开发用的单体模式。
B可抛弃客户端——detach 留活 pane；杀 server 才杀 PTY，但下一个 server 会恢复布局并尽可能恢复支持的 agent 原生会话。"断线重连"是第一公民，不是补丁。
C安全边界写进了产品——Luvus Web 默认 loopback 只读，--control 才开控制，QR/链接配对手机，停桥只撤销授权不停 server/PTY；uhp access 网关默认只读，控制显式配对且带 authority.expires_at 有限期（--no-expiry 也只是进程绑定、关闸即失效）。
D编排层——worktrees 创建、依赖任务协调、任务队列与 path leases 按项目隔离、时区感知定时任务、quality gates、完成后合并（merge completed work）。这一层是它区别于"tmux+肉眼"的真正增量。

04上手五步与 UHP 自动化契约

  1. 装：curl -fsSL https://luvus.dev/install.sh | sh（macOS/Linux/FreeBSD）或 brew install RizRiyz/luvus/luvus；Windows 走 PowerShell 脚本。
  2. 体检：luvus doctor 查 git/gh/ssh 三件套；luvus update 自更新。
  3. 开跑：项目目录里敲 luvus，分屏起 agent，自动探测；macOS 记得关"选择上一个输入源"释放 Ctrl+Space。
  4. 指挥：Commander 底部 composer 向精确的 agent pane 发 prompt、向精确 shell pane 发命令，支持多目标同发且不动当前焦点；ORCH 任务可不带焦点启动、失败可安全重试不丢队列（v0.14.2）。
  5. 自动化：UHP 1.0 是版本化公共契约——luvus uhp schema / capabilities / snapshot 自省；NDJSON over loopback、owner-only IPC；兼容承诺：加法兼容，破坏性变更必须升 major。harness/编排器该建在这上面而不是 screen-scraping。

连仓库自己的 skills/ 目录都带 SKILL.md（luvus + luvus-module 两枚）——给 Agent 用的说明书由项目自己养，和 libraries.dev 是同一时代做法。

05五分钟心智模型：五个概念撑起全部

官方 concepts 文档说"五个想法解释 Luvus 的一切"，照录并翻译：

1server 拥有会话，client 只是显示——luvus 一敲发生两件事：后台 server（只起一次）拥有所有 pane/shell/agent，薄 client 附上去看。Ctrl+Space d 或关终端 → client 脱离、会话活着；再敲 luvus → 新 client 附回，什么都不重启。真正结束一切只有 luvus server stop（快照保留）。server 死了（重启/升级/被杀）会保存会话形状，下次启动重建：workspaces/tabs/布局/每 pane 的目录与最后屏幕，以及能原生恢复的 agent 对话——恢复的 pane 直接进入该 agent，不会在你面前重新打一遍提示词。
2Workspace → Tab → Pane 三层——Session 含多个 workspace（一个项目文件夹一个，固定项目根、显示 git 分支）；tab 持有分屏布局（两个特殊 tab：git tab、orchestration board）；pane 是真终端。层级是"会话/项目/布局"，对应 tmux 的 session/window/pane 但语义按项目组织。
3prefix 键——默认 Ctrl+Space，按下松开再按功能键；Ctrl+Space ? 列出全部；每个绑定可在 Settings → Keys 重映射，prefix 本身可换成 Ctrl+b 或直接套 tmux preset——tmux 老用户零迁移成本。两个刻意例外：全鼠标操作、Shift+↑ 进滚动模式。
4Agent 是"被观察"不是"被包裹"——Luvus 不注入自己进 agent；它们在普通 pane 里原样跑。检测读屏幕：这是哪个 agent、是否权限提示（blocked）、是否有输出流（working）、是否刚安静（done）。这就是任何 agent 零配置可用的原因，hook 只是加精度。
5一切皆命令——UI 与 CLI 是同一表面：能点到的，luvus <verb> 都能通过本地 socket 做到；每个 pane 内注入 $LUVUS_PANE_ID 和 socket 路径，pane 里的 agent 自己也能驱动 Luvus——脚本化与编排是自然生长而非外挂。

06第一个会话：官方五分钟教程照抄

  1. 在项目里启动——cd ~/code/my-project && luvus。窗口三区：侧栏（workspaces + 实时 AGENTS 列表）、tab 栏、pane 区（shell 已在你的项目目录跑着）。以后在其他文件夹再敲 luvus，会把该文件夹加为同一会话的另一个 workspace——一个 Luvus 装下所有项目。
  2. 分屏跑 agent——Ctrl+Space v 左右分（s 上下），一个 pane 里 claude（或 copilot/codex/opencode/aider…）。看侧栏 AGENTS 区：🟠 working 正在输出 / 🔴 blocked 等你批权限 / 🟢 done 你没看时跑完了 / idle 安静。点行跳转；Settings → General 选 Retro/Soft/Pulse 提示音并勾触发事件。
  3. 移动——鼠标优先：点击聚焦、拖边缩放、滚轮翻历史；键盘镜像：Ctrl+Space+箭头/hjkl 聚焦、c 新 tab、z 放大、? 全表。滚动模式 Shift+↑ 里 1–9 跳历史、q 回实时。
  4. Detach：见证魔法——Ctrl+Space q。client 退出，什么都没停：pane/shell/agent 在后台 server 里继续跑。合上终端去买杯咖啡，回来敲 luvus，一切原地等你。
  5. 挺过真重启——连 server 停了（重启/luvus server stop）也不怕：会话快照持续保存，下次 luvus 恢复 workspaces/tabs/布局，并通过各 agent 自己的原生会话存储恢复对话——Claude Code pane 回来还是同一段 Claude Code 对话，不用记 --resume。注意：保存的终端画面是活屏幕的有界副本（同尺寸下宽字符/组合符/样式保留），它不是完整 scrollback 备份。

07会话恢复与 Fork：flagship 功能拆解

各 agent 怎么恢复（官方表）：Claude Code 读项目 transcript store、Copilot CLI 读 session-state store、Codex 读 rollout 文件、Antigravity 读 ~/.gemini/antigravity-cli/cache/last_conversations.json、Kimi 读 ~/.kimi-code/session_index.jsonl、Grok 读 ~/.grok/sessions……有稳定原生存储的 agent 按 pane 所在文件夹自动发现、零配置；目录匹配不够的用集成提供精确归属，Luvus 代跑该 agent 自己的 resume 命令。

Fork to New Pane 是多方案试验的杀手锏：把当前 pane 的 agent 会话连同全部上下文分支到旁边新 pane，但用新 session id——左右两份独立演化互不干扰。三个触发方式：右键 pane 选 Fork to New Pane；Ctrl+Space f；CLI luvus agent fork <target> --name 别名 --no-focus。典型用法：左边保留主线程继续跑，右边分叉试激进方案，试错零风险。

自定义识别：agent 不在名册显示成 zsh？写 ~/.luvus/manifests/myagent.toml 教它——agent 名、匹配特征、状态规则都 TOML 化；generic 规则对所有 agent 生效但 identity 必须具体到某个 agent。

08ORCH 编排六概念：多人协作的正确姿势

这是"解决互相踩脚"的真正答案——官方 orchestration 指南的六个概念：

概念定义（官方）
Task工作单元：标题 + 将触碰的文件 glob + 依赖 + 可选 quality-gate 命令；分配 id 如 t1
Automation持久的一次性/周期定义；到期生成新 ORCH task 并启动配置的 agent——未来任务到期前不占 pane/lease/worktree
Lease文件路径预约。两个 worker 不能持有重叠 glob——冲突工作从一开始就分派不出去，而不是写完了才发现
Worker任务专属 pane。worktree 模式用独立分支+checkout（默认）；workspace 模式在共享 checkout 里开独立任务 tab
Quality gate任务标 done 时跑的命令（如 cargo test）；必须通过才能合并
Merge gate把完成分支集成进 luvus/integration——在专用 worktree 里做，永不碰你的工作 checkout；冲突会阻塞任务而不是弄脏任何东西

任务生命周期：queued → claimed/running → gate 通过后 done。CLI 全程可驱动（agent 也能）：task create/inspect、task start（worktree 默认）、task stage（不离开当前视线开 worker）、task run --in-place（直接在现有 checkout 跑，免分支合并）、task merge、task retry、lease 查询、IANA 时区定时、NDJSON 实时事件流。

安全模型三要点：① 只有arm 过的 automation 才无人值守 spawn，手动任务必须按 s 或 task start；② task retry 归档有界尝试摘要、释放 lease、脱开旧 worker、排新尝试——不关 pane 不删分支/worktree/输出/笔记；依赖任务已开跑则拒绝 retry，merging/merged 不可变；③ automation 重试从原 run 捕获的契约新建 run，原记录保留。重试分支默认 luvus/<task-id>-retry-<attempt>。

12与 tmux / zellij 的正面对比

"超级 tmux"这个说法值得一张对照表——三者定位不同，迁移决策才不会错：

维度tmuxzellijLuvus
核心抽象session/window/panesession/tab/pane + 内置 UIsession/workspace(项目)/tab/pane + agent 实体

一句话：tmux 是"终端复用器"，Luvus 是"agent 复用器"——如果你的窗口里跑的是 claude/codex 而不是 htop/vim，前者的抽象就不够用了；反过来只开两三个纯 shell，tmux 二十年的稳定无可替代。

13安全模型深读：三个入口各自的边界

TTUI/CLI（本机）——控制走本地 socket 的 NDJSON；owner-only 权限。风险面最小，默认即可。
WLuvus Web（手机/平板）——luvus web 起 loopback 桥：默认只读看实时终端与 agent 状态；web --control 才开控制。配对走链接/QR。官方明确：手机访问需要可信 TLS 隧道（如 Tailscale/自建反代），停桥即撤销授权且不影响 server/PTY。
UUHP access（程序化）——uhp access 起临时 NDJSON 网关给第三方传输端：默认只读，控制显式、配对、scoped；有限期授权广告 authority.expires_at，--no-expiry 也仅进程绑定且广告 expires_on_close:true——两种模式关闭都即刻吊销。给自动化脚本权限时按"最小寿命"原则选 expires_at。

对照着看，"server 唯一写入者 + 可抛弃客户端"不只是架构洁癖——它是权限模型的根：所有控制面都是 server 的租户，租约到期即失效。

14五类真实场景的落地方案（照抄即用）

把功能翻译成场景——每个方案只用官方文档出现过的机制：

  1. 场景一：主项目 + 两个侧项目并行——三个文件夹各敲一次 luvus 加为 workspace；w/W 或侧栏切换，Shift+1..9 跳转；每个 workspace 的 git 分支显示在标题，互不串台。比开三个终端窗口省掉的是"哪个窗口在哪个项目"的心智负担。
  2. 场景二：一个 repo 多 agent 分工——ORCH 面板建任务（写清文件 glob）→ lease 自动防重叠 → worker 默认各占 worktree 分支 → quality gate（如 cargo test）把关 → merge gate 合入 luvus/integration。冲突在分派时被挡，不是合并时爆炸。
  3. 场景三：方案分叉对比——agent 跑到一半想试另一种实现：Ctrl+Space f fork 出完整上下文的副本，左原始右实验；两边对话互不污染，看完关掉实验 pane 即可。
  4. 场景四：远程服务器上的项目——luvus --remote <host> 直连或保存 machine profile；远程命名会话的 pane 在你切走后仍活着；SSH 连接与 Luvus Web 配对是两套独立通道。
  5. 场景五：手机盯盘——桌面 luvus web，手机扫码/点链接：看实时终端、agent 状态与 session 标题；默认只读，要遥控才 --control。地铁上瞄一眼 🔴 blocked 列表，回家再批权限。
性能预期（AGENTS.md 有专节）：Rust 单二进制 + 快照差分渲染的设计目标是"薄客户端也流畅"；但 WebGL/巨型 scrollback 等 term 场景仍受终端引擎保守行数限制——scrollback 显示的用量是估算值。低配 VPS（1 核 1GB）建议先跑 luvus doctor 观察，再决定要不要常驻多会话。

18UHP 入门：给自动化玩家的第一段代码

UHP（Universal Harness Protocol）v1 是 Luvus 的公共自动化契约，也是它区别于一切"人肉盯盘"方案的护城河。入门三步（官方 uhp/getting-started 路径）：

  1. 自省——不读源码、直接问二进制：luvus uhp schema 拿完整 schema、luvus uhp capabilities 看当前 server 支持哪些方法、luvus uhp snapshot 取会话快照。schema 即文档，永远与所装版本一致。
  2. 第一个调用——uhp access 起临时网关（默认只读）后，任何 NDJSON 客户端（nc/Python/Node）连上即可发方法请求、收事件流；terminal.backend.* 是 UHP 内的方法命名空间而非第二个协议。
  3. 写 harness——基于方法注册表编排：查 agent 状态 → blocked 则投递确认 → done 则触发 quality gate。兼容承诺白纸黑字：加法改动必须保持旧请求有效，破坏性变更必须升 UHP major——你的自动化脚本不会被静默破坏。conformance 测试集与 fixture 也随协议发布，第三方实现可对表验证。

意义一句话：tmux 时代自动化 = send-keys 盲打文本 + 屏幕抓取；UHP 时代自动化 = 带 schema 的结构化调用 + 语义等待（"等 agent 进入 done"而非"等 30 秒"）。这是给 harness/编排器作者的基础设施级区别。

19冷静面与判断

四个折扣点：① README 挂 crates.io 徽章但实际停留在占位 v0.1.0（21 下载）——cargo install luvus 装到的是空壳，认准 install.sh/brew；② 0.x 快跑期：v0.12→v0.14.2 一个多月六版，稳定性承诺只覆盖 UHP 1.0 契约本身，TUI/CLI 仍在变（45 open issues）；③ "解决踩脚"是提供 worktree/lease 机制，多 agent 写同一 worktree 照样踩；④ 单人项目（作者 bio "Your favorite Agent | Maker"，292 followers）——878★ 三个月增速可观，但巴士系数与长期维护要打折观察。

判断：如果 tmux 是"终端复用"，Luvus 是"agent 复用"——它把 哪个 agent 在哪个 pane、跑到第几步、花了多少 token、卡在等确认还是已完工 变成了一等公民数据，再用 UHP 把这一切开放给程序化消费。"超级 tmux"的叫法传播效率高但低估了它：编排层（worktree/队列/lease/quality gate/合并）和 UHP 契约才是护城河。多 agent 重度用户的尝鲜顺序建议：先单会话跑熟 → 上 Commander 多目标 → 再碰 ORCH 编排。观望者盯两个信号：v1.0 何时切、crates.io 何时真发版。
