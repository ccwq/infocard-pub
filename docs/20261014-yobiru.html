AG雷达 / Agent 工具通信与权限0.5.0
yobiru · 跨机器协作

让 Agent 互相说话，
不替你决定谁有执行权

yobiru 把消息、附件、请求回执与可选唤醒接到已有 Agent 上。Tailscale 负责机器网络与身份；接收端负责访问策略；任务是否完成，仍需看实际产物。

从两台获准通信的机器开始，先验证普通消息和附件，再增加请求生命周期，最后才配置 wake 与 Codex bridge。不要一次把网络、常驻服务、自动回复和任务执行全部放开。

先判断是否适用

两端都需 Python、可用的 tailnet、执行 CLI 的权限和持续可用的 receiver。只有聊天界面、不能运行脚本或访问私网的云端 Agent，无法直接使用这一套。

01 / 它补的是通信层，不是任务调度器

已有 Agent 界面
↓
6 个 Skill + Python CLI
↓
Tailscale 网络与机器身份
↓
接收端策略 → 本地 inbox → 可选 wake adapter
↓
Agent 处理获准事项 → 上报结果 → 人或调用方验收

消息使用 host/agent 寻址。receiver 通常监听 Tailscale 地址的 tcp:7766，通过 tailscale whois 核对连接机器，再检查本地访问规则。Agent 名称用于路由，不是机器内部不同 Agent 的安全隔离。

它使用 tailmsg protocol v1；不提供 MCP server、新聊天群组 UI、调度器或“别人已经完成工作”的证明。通知、请求、已存储回执和验收结果是不同对象。

02 / 装插件之前，检查四个前置条件

Python 与 shell

文档要求 Python 3.8+，运行时使用标准库。宿主需允许执行 CLI；Skill 文本已加载，不等于捆绑脚本已经可用。

可达的 tailnet

Tailscale 已安装并登录，网络策略允许对端访问 receiver 端口。接收节点需要合适的 shields-up 设置，但 yobiru 不会自行修改 ACL 或 shields-up。

receiver 常驻

两端都运行 receiver 才方便双向回执与回复。附件由接收方从发送机器拉取，文件取走之前发送端也要保持服务可达。

wake 执行环境

自动唤醒需接收方设置本地程序或 webhook。安装 Skill 不会自动叫醒一个休眠 Agent，也不会授予它远程执行权限。

手机可以只是 Agent 的用户界面，不必充当执行节点。容器缺少相应网络能力、权限或持久服务条件时，应报告阻塞，不能用“能安装插件”代替“能运行完整链路”。

03 / 六个 Skill 按问题选，不要全部当安装步骤

Skill什么时候用

Codex 文档安装入口

codex plugin marketplace add chekusu/yobiru
codex plugin add yobiru@yobiru

新建会话后说“Set up Yobiru on this machine”。安装没有 install hook，不会自动配对机器、启动服务或发送消息。

这是仓库 marketplace 路线，不代表已经进入公开 Codex 插件目录。Cursor 可加载本地插件目录或经团队 marketplace 导入；公开 Cursor Marketplace listing 尚未提交。

04 / 最小试验：先普通通知，再带结果的请求

以下是根据官方命令组织的教学试验，不是本文已运行的记录。只用于你已授权的两台机器、虚构测试数据和指定对端。先让 Y 指向实际插件启动器；示例中的 research-node/grok、消息 ID 与文件名都要替换为自己的对象。

# 从项目根目录解析实际启动器
Y="$PWD/plugins/yobiru/scripts/yobiru"
sh "$Y" paths
sh "$Y" onboard
sh "$Y" doctor

onboard 与 doctor 是只读诊断入口。预期是得到环境、配置与服务状态，以及由谁完成下一步。未安装或没有 receiver 时出现缺项并不代表诊断命令失败。

A / 身份和策略

按 setup 指引先预览，再经授权用 apply。新安装默认 tailnet 模式：网络策略放行的认证机器可发送，除非本地 deny 命中。需要收紧时选 allowlist；deny 优先于 allow。

B / 双端接收

sh "$Y" serve

在每台机器独立终端保持运行，再从另一终端诊断。先验证前台链路，再生成 systemd-user、launchd 或 Windows 服务模板；模板本身不等于服务已启动。

C / 普通通知

sh "$Y" send research-node/grok \
  "The brief is available." --kind notice

接收方用 inbox/show 核对消息 ID 与正文。通知不要求回复；HTTP 202 只证明接收端接受并存储。

D / 请求与附件

sh "$Y" request send research-node/grok \
  "Please review this brief." --file ./brief.md \
  --timeout-seconds 900 --wake none

先创建不含秘密的测试文件。此处显式不请求唤醒，便于先排除 wake 配置变量。接收方应先取得消息与附件，再只处理已有授权范围的事项。

# 接收端：用实际消息 ID 替换 MESSAGE_ID
sh "$Y" show MESSAGE_ID
sh "$Y" fetch MESSAGE_ID
sh "$Y" request respond MESSAGE_ID "Started reviewing." --state running
sh "$Y" request respond MESSAGE_ID "Reviewed; see evidence." --state completed
sh "$Y" ack MESSAGE_ID

# 发送端：用实际请求 ID 替换 REQUEST_ID
sh "$Y" request status REQUEST_ID --refresh --json

验收要同时包含发送记录、接收正文、附件内容与结果证据。接收方先上报终态，再 ack；没有回复权限或执行条件，应上报 blocked，不用“消息收到了”冒充任务完成。

05 / 六个状态，别读成六种成功

信号证明了什么没有证明什么
HTTP 202 / received对端接受并持久保存消息Agent 已经开始或完成任务
runningAgent 上报已开始正在正确执行、最终一定完成
completedAgent 上报终态为完成代码、文件或外部变更验收通过
failed / rejected / blocked明确的失败、拒绝或阻塞结果自动获得修复或扩大权限的授权
timed_out期限内未收到终态，实际结果未知任务已取消，或者可安全重新执行
late原请求之后收到迟到终态重复发送的新请求已被去重执行
ack / wake 成功本地标记处理；或通知 adapter 接受发送者已获完成通知；或 Agent 产出正确

无 refresh 时读本地账本；有 refresh 时向原认证接收方对账。超时先查询与核对副作用，不要立刻重发。请求响应通过稳定 ID 的 durable outbox 重试，不等于普通消息自动重投，也不是 exactly-once 任务执行。

结果响应不进入普通任务 inbox，不触发新的 wake 或回复循环。要取结果文件，从 request status 中找到 response.id，再 show/fetch；不要把协议回执当成新任务。

06 / 文件不进中央存储，但链路可能使用中继

附件在发送端暂存，接收方通过 tailnet 拉取，核对大小与 SHA-256。文档默认下载链接有效期为 24 小时，且限定接收机器。大内容走附件；消息 envelope 默认上限 256 KiB。

纠正推文里的绝对说法

“yobiru 不运营中央消息或附件存储”有官方依据；“文件不经过任何中转服务器”过于绝对。Tailscale 可以直连，也可能经加密中继传输。应用没有集中存储与网络路径绝不经 relay，是两个问题。

SHA-256 和大小校验只证明传输完整性，不保证内容安全；到期链接也不会撤销已经下载的副本。数据 home 默认 ~/.tailmsg，也可指定 home；项目不增加静态存储加密，需保护主机和文件系统。

你的 Agent 服务商仍可能处理你交给 Agent 的内容。不要通过报告、日志或 JSON 顺带发送密钥和无关私有文件；先确定接收方、用途、保存期限与可分享范围。

07 / 接收、唤醒、回复、执行是四道边界

消息访问策略

Tailscale ACL/grants 与本地策略共同作用。agent 名称不是独立安全主体；同机多 Agent 或共用 home 时，不要把路由名称当成隔离保证。

唤醒由接收方决定

发送方请求 now、batch 或 none，接收端还会检查允许的发送者、目标 Agent、静默时段和限频。wake-config 默认预览，apply 才写入。

自动回复不默认开放

新的 Codex bridge 安装默认关闭业务自动回复。allow_replies=false 会记录最小 blocked 结果而不运行模型；开启回复仍只覆盖用户已有授权。

收到文字不是执行许可

对端消息和文件是待处理数据，不授权命令、购买、配置变更或披露其他资料。唤醒一个 Agent，不等于让它按远程提示任意执行。

08 / Codex、Grok Bot、DOTS 的支持要分层看

Codex bridge 用已有会话做 dispatcher：macOS 走桌面端；Linux 需要你已运行的 app-server、同用户本地 Unix socket、明确会话 UUID 与可用的用户 systemd。它不替你启动 Codex，不自动新建会话，也不使用“最近一个会话”替代精确身份。Windows 不套用这套桥。

enqueued 表示 Codex queue 接受通知，不表示工作完成。uncertain 表示可能已投递，不自动重发；先核对原会话。插件升级也不会自动升级持久 receiver，需分别核对 plugin、runtime 与正在运行的服务。

README 的 Grok Bot / DOTS / Codex 配图标为 AI 生成概念展示，不是真实截图或完整集成实测。Grok Bot 的账号级完整运行与 wake 循环仍需验证；DOTS 是有条件示例，仓库没有经过验证的 DOTS connector。

09 / 故障按层查，别一律重装

现象先核对
插件装上却不能通信脚本是否可用、Tailscale登录、端口策略和 receiver 常驻；安装不会启动服务
403认证与访问策略拒绝，不先按网络故障重试
发现旧端 receiver 显示 legacy旧版本 /info 能力未知，不能直接判离线
收到了但没有 wakeadapter、允许发送者、静默时段、限频与宿主运行条件
请求超时本地账本与原对端 refresh，检查是否已有副作用或迟到结果，不盲目重发
插件已更新但行为没变持久 runtime 和 running receiver 是否也升级并重启

10 / 文档测试不等于你的两机部署验收

docs/VERIFICATION.md 报告 0.5.0 在 Python 3.12.3 下通过 220 项 plugin 与 146 项 bridge/resident/installer 测试，共 366 项。Python 3.8 语法解析通过不等于在 3.8 解释器执行测试；fake Tailscale 与 loopback HTTP 测试不替代真实 tailnet 两机验证。

官方历史验证表与详细验证段落有滞后差异，阅读时按具体场景、测试环境与尚未验证项拆开，不汇总成“全平台已验证”。项目没有正式独立安全审计；本文只做材料核查，未安装、配置、发送消息或复现这些测试。

  • 基础验收：双向消息 ID 与正文一致，测试附件大小/哈希/内容一致。
  • 生命周期验收：received → running → 终态可关联，终态前不 ack；timeout 与 late 对账无重复执行。
  • 权限负例：被拒访问、被拒 wake、未经授权的执行请求均没有越界副作用。
  • 扩展验收：receiver 重启、离线结果恢复、真实 Codex/Grok 宿主能力各自单独记录。
