Windows-Use：让大模型直接操作 Windows 图形界面

它不是“看图猜按钮”的演示，而是把 Windows UI Automation 作为操作层：让模型读取可访问性结构，再执行窗口、输入、拖拽、命令与文件操作。

Windows UIAPython 3.10+MITWindows 7–11
先说边界：这是能动手的 Agent，不是安全沙箱。

官方 README 警告它可以修改文件和系统设置，可能造成不可逆变化；项目没有 sandbox / isolation layer。优先在 VM、Windows Sandbox 或专用测试机运行。

no sandbox可禁用 telemetry先做最小权限测试
结论：Windows-Use 把 GUI Agent 的“手”接到 Windows UIA，但部署安全与任务可靠性仍由使用者负责。

本卡把一条社交平台传播快照与官方仓库事实拆开：传播内容指出 Windows-Use 可操作窗口、点击/输入/拖拽、系统命令、文件、虚拟桌面与语音，并提及 Claude、GPT、Gemini、Ollama 和 Windows 7–11；仓库 README/API 则负责确认项目身份、机制、安装面、provider 示例与安全警告。涉及“支持”时，优先采用 README 的明确表述，不把示例配置扩大成完整兼容性承诺。

02
MECHANISM

它究竟如何操作 Windows

关键差异不是“模型更会看”，而是操作接口从像素坐标转向 UI Automation 语义结构。

输入层UI Automation

读取可访问性结构，再定位控件

README 将 Windows UI Automation API 作为核心机制，并说明不需要 computer vision model。对标准窗口、控件和浏览器 accessibility tree，这种结构化输入可减少视觉猜控件的脆弱性。

不要过度解读可靠性边界

UIA ≠ 所有 GUI 任务都可靠

自绘界面、游戏、画布、远程桌面、缺少可访问性语义的控件，仍可能需要视觉或其他适配层。no computer vision model required 是项目机制说明，不是“无需视觉即可完成任何任务”的保证。

建议读法：把 Windows-Use 看成“UIA-first 的 GUI Agent”。它可能补充视觉，而不是宣称视觉永远没有价值。

06
SAFETY

安全边界：执行力越强，隔离越重要

这是本卡最重要的使用前提：Windows-Use 不是安全沙箱。

R1

可修改真实系统

官方警告它可以修改文件和系统设置，可能造成不可逆变化。先用无关测试账户与最小权限。

R2

没有 sandbox / isolation layer

不要把项目本身描述成隔离运行环境。官方建议 VM、Windows Sandbox 或专用测试机。

R3

Telemetry 可关闭

README 提供 ANONYMIZED_TELEMETRY=false 作为禁用匿名 telemetry 的方式；仍需自行核对当前版本实现。

ANONYMIZED_TELEMETRY=false
