🚀 痛点与解法

Core Problem
1
传统框架的性能代价

Next.js / Nuxt 默认全量 hydrated JS：一个纯文章页面也要加载 120–412 KB 的 React runtime + 路由。实测 Next.js App Router 首屏 JS 84–90 KB，Next.js Pages Router 120+ KB，Gatsby 更重（112 KB + GraphQL 层）。

框架初始 JSMobile LighthouseTBT
Astro（无 island）~9 KB98–100<50ms
Next.js 15 RSC70–90 KB75–90150–400ms
Next.js Pages Router120+ KB65–80400ms+
Gatsby112 KB+81280ms
2
Astro 的解法：Islands

Astro 默认输出 纯 HTML + 0 JS。交互组件单独标记为「岛屿」，通过 client:* 指令精确控制 hydrate 时机。实测文章页 TBT <50ms，Lighthouse Performance 98–100。

client:load client:visible client:idle client:offline

client:load — 页面加载即 hydrate
client:visible — 进入视口才加载（图片轮播推荐）
client:idle — 浏览器空闲时 hydrate
client:offline — 网络恢复后才 hydrate

📁 项目结构

src/pages/

每个 .astro 文件自动映射为 URL 路由（文件即路由，无需配置）：index.astro → /，about.astro → /about，blog/[slug].astro → /blog/任意slug

File-based Routing

src/components/

可复用 UI 组件，支持所有框架。纯 Astro 组件默认零 JS 输出，React/Vue 组件需 client:* 才 hydrate。

Framework Agnostic

src/layouts/

页面模板，用 <slot /> 插槽注入子页面内容。典型用法：BaseLayout 包裹所有页面，统一 head、nav、footer。

DRY Layouts

src/content/

Content Collections：Markdown/MDX/Markdoc 内容用 Zod schema 校验类型安全，支持 getCollection() 查询、getStaticPaths() 生成静态路由。

Type-safe Content
src/pages/blog/[slug].astro — 动态路由 + Content Collection
--- import { getCollection, render } from 'astro:content'; // 生成每篇博文的静态页面 export async function getStaticPaths() { const posts = await getCollection('blog'); return posts.map(post => ({ params: { slug: post.id }, props: { post }, })); } const { post } = Astro.props; const { Content } = await render(post); --- <h1>{post.data.title}</h1> <Content />

🗂 Content Collections 与路由

Zod Schema 校验

在 src/content.config.ts 定义集合 schema，自动校验 frontmatter 类型。字段错误在构建期暴露，而非运行时。

Build-time Validation

pagination() 分页

paginate() 从 getStaticPaths() 返回，内置 page.currentPage、page.total、page.data、上一页/下一页 URL。

Built-in Pagination

重定向配置

astro.config.mjs 中 redirects 字段映射旧路径到新路径，支持动态参数路径（参数名相同即可）。

redirects

Server Islands（Astro 5+）

静态页中嵌入 server:defer 的动态岛屿（需适配器），如用户头像、商品价格，独立并行渲染，主页壳可提前缓存。

server:defer
src/content.config.ts — Content Collection 定义
import { defineCollection, z } from 'astro:content'; import { glob } from 'astro/loaders'; const blog = defineCollection({ loader: glob({ base: './src/content/blog', pattern: '**/*.{md,mdx}' }), schema: z.object({ title: z.string(), pubDate: z.coerce.date(), description: z.string(), tags: z.array(z.string()).optional(), }), }); export const collections = { blog };

🔄 三种输出模式

output: 'static'（默认）

全站预渲染为静态 HTML，构建时生成所有路由，无服务器依赖，可部署到任意 CDN/静态主机（Cloudflare Pages / GitHub Pages / Netlify）。

Static · 零服务器

output: 'hybrid'

默认静态，特定页面加 export const prerender = false 按需渲染。需要适配器，但只处理少量动态路由（如带 cookie 的页面）。

Hybrid · 少量 SSR

output: 'server'

全站按需渲染，默认所有路由 SSR。特定页面可 export const prerender = true 静态化。适合高度动态应用（电商、仪表盘）。

Server · 全动态

📊 性能实测对比（2025 真实项目数据）

LCP（Largest Contentful Paint）

在诊所/营销页实测：Astro 0.8s vs Next.js SSG 1.4s vs Gatsby 1.9s。差距在中低端 Android 设备更明显。

Astro 领先

TBT（Total Blocking Time）

Astro <50ms（主线程无 JS 阻塞），Next.js 150–400ms，Gatsby 280ms。TBT >200ms 直接影响 Google Lighthouse 评分。

JS=0 → TBT=0

CLS（Cumulative Layout Shift）

Astro 平均 0.02，Next.js 0.02–0.08，Gatsby 0.05。静态 HTML 无动态注入，布局稳定性天然更好。

静态 = 无偏移

✅ 何时选 Astro

✅ 选 Astro 的场景

博客、文档站、作品集、营销页、内容型站点。内容更新频率低或可通过 CMS API 触发增量构建。团队熟悉 HTML/CSS/JS 但不熟悉 React 深度概念。

Content-first

✅ 选 Next.js 的场景

需要用户认证、购物车、实时数据、API 路由、Streaming SSR。高度交互的 SaaS 仪表盘、电商详情页、社交平台。

App-first

⚠ 迁移路径

Gatsby → Astro 最简单（都是文件路由，都偏静态）。Next.js → Astro 需要确认站点没有大量 use client 边界，否则失去意义。

Gatsby → Astro 容易
