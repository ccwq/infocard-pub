01
PROBLEM · 问题

Agent 失忆：长任务的最大瓶颈

Agent 能力早就够了，缺的一直是「让它记住上一轮的那个东西」。

Agent 断档的典型场景

  • 换窗口重新开：这个会话里 Agent 刚确认方案 B 走不通，换个会话它又兴冲冲去试方案 B
  • 上下文窗口耗尽：长任务导致 context 溢出，重要决定随对话历史一起消失
  • 人肉记事本：用户每次开场先复述一遍上下文，充当 Agent 的外部记忆
  • 多 Agent 协作：A Agent 的结论 B Agent 不知道，每次交接都要重新对齐

现有方案的局限

  • Chat 记忆：只在本会话内有效，换窗口即丢失
  • Timer / 提醒：只能触发，不能保留决策和证据
  • Provider 原生 Goal：跨运行时不通用；LHTB 基准显示比 Plain Codex 仅高 +10.6%
  • 外部笔记：需要人工维护，Agent 无法自动写入和查询
核心矛盾

Agent runtime（Codex/Claude Code）执行具体工作，但它们不持久化目标状态。Agent 换运行时，工作进度也跟着丢失。LoopX 的解法：在 runtime 与工作目录之间加一层本地优先的控制面。

02
SOLUTION · 方案

LoopX：本地优先的 Agent 控制面

不是又一个 Agent 框架，也不是特定云厂商的编排运行时——是跨运行时通用的状态治理层。

LoopX 在本地立一个控制面，目标、任务、文件、日程这些状态存在你自己机器上，Agent 换了运行时也接得上。

工作原理

Agent runtimes 执行工作，LoopX 治理状态。一个 turn 是一个受治理的状态转换，而不只是计时器。

Harness Neutral

Agent 运行时执行工作，LoopX 携带工作进度。控制面与具体 runtime 解耦。

控制面板

一个 turn 是受治理的状态转换，不是计时器。Goals / attention / conversations / tasks / files / schedules / recovery 全部持久化。

Agent 原生 Kanban

卡片携带身份、权限、证据和继续信息。操作（claim / gate / monitor / writeback）经过验证，防止越权。

控制面覆盖的状态

状态类型说明跨会话
Goals（目标）长期任务目标与子目标✓
Attention（注意力）当前优先项与等待项✓
Conversations（对话）与用户的通信历史与决策✓
Tasks（任务）待办项与进度追踪✓
Files（文件）交付物与证据文件✓
Schedules（日程）计划任务与触发条件✓
Recovery（恢复）断点与回退策略✓

BENCHMARK · LHTB 实测

46 个长时程任务 · GPT-5.6 Sol · 三模式横向对比

LHTB（Long-Horizon Terminal-Bench）超越纯编码，涵盖研究复现、科学模拟、多模态分析、专业工作流、游戏和系统任务。

执行模式均值 Reward ↑严格通过率（≥0.95）通过率（≥0.80）相对 Heartbeat
Plain Codex0.42187/46（15.2%）12/46（26.1%）基准
Native Codex Goal0.44754/46（8.7%）14/46（30.4%）+6.1%
LoopX 1.0.3 Heartbeat0.49487/46（15.2%）15/46（32.6%）+17.3%

vs Native Codex Goal

  • Task 级别：23 个提升，13 个持平，10 个回退
  • 均值 +10.6%（0.4475 → 0.4948）
  • 严格通过率匹配 Plain Codex（7/46），高于 Native Goal（4/46）
  • 通过率（≥0.80）最高（15/46 = 32.6%）

方法论说明（原文）

  • 每任务每模式各跑一次（one effective trial）
  • 预算不完全对等，部分 Heartbeat 替换有更长预算
  • 这些是观测结果，不是等预算效率结果或隔离因果估计
  • 均值奖励也计入部分进展，不是全对才算分
✓ 基准透明性

项目方主动标明了「每个任务只跑一次、预算不完全对等」，属于观测结果而非严格对比。这种老实话在跑分里不常见——值得参考。

05
CAPABILITIES · 核心能力

8 大内置能力：目标追踪 / 证据管理 / 多 Agent 协作 / 自改进

LoopX 将常用工作模式封装为独立能力模块（capabilities），可按需启用。

① Goal & Task Tracking

长期目标分解为子任务，追踪每步进展。Claim / gate / monitor / writeback 四大操作符。

② Heartbeat Mode

LHTB 基准实测 +17.3% 的核心机制。定时上报 Agent 存活状态，防止长任务中途断连。

③ Issue-Fix

Issue → PR → review → merge 完整链路，保留修订戳记与复用知识。OpenViking 案例超 200 实际小时。

④ Reward Memory

将反馈连接到下一次尝试，支持自我改进工作流。可选模块，非必须启用。

⑤ Explore

通过 Explore 评估候选变更。配合 Reward Memory 形成 propose → test → review → retain 循环。

⑥ Cross-Runtime Collaboration

多 Agent 共享目标但不消除 Worker 所有权。Claim / evidence / explicit returns 让实现与审查保持连接。

⑦ Personal Workspace

Goals / attention / conversations / tasks / files / schedules / recovery 跨运行时持久化。Dashboard 可视化。

⑧ Scheduler & Watch

定时任务与条件触发器。Owner 决策出现时通知，scheduler 在无有效转换时停止消耗。

关于 Self-Improving（自我改进）

Reward Memory + Explore 形成「工程循环」（propose / test / review / retain），但这连接的是 Agent 工作流自改进，不是「模型自主改进或复合能力增长」。LoopX 不声称已演示自主模型改进。

COLLABORATION · 多 Agent 协作

三 Agent 协作：Claim / Evidence / Explicit Returns

多个 Agent 共享目标，但不消除 Worker 所有权。证据链和明确返回让实现与审查保持连接。

协作三原则

  • Claim（认领）：Agent 声明负责某任务，状态标记为已认领
  • Evidence（证据）：每步输出附带证据文件，review 可追溯
  • Explicit Returns（明确返回）：任务完成后明确交接给下一个 Agent

bounded 协作示例

示例 examples/collaboration-delivery 演示含纠错和两轮 review 的完整协作流程。

  • Worker Agent 执行
  • Review Agent 审查，发现问题
  • Worker Agent 修正（一轮）
  • Review Agent 再次审查（二轮）
  • 确认通过，explicit return 给 owner
