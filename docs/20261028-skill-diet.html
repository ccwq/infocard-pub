Skill Diet 把技能资料拆成“入口说明、主流程、按需参考”，再用同一任务对照验证：更少上下文，是否仍能完成工作？

核心判断短入口 ≠ 弱能力
先分层，再测结果
先把常驻上下文减到只够选路；细节留在需要时读取。节省量是作者报告，不是本卡复测结论。
01 · 找重复与低频信息
02 · 拆主流程 / 参考页
03 · 校准三组同任务对照
04 · 决定保留或回退
信息架构

三层各司其职

  • description：触发判断，说明何时该用。
  • SKILL.md：最短可执行主流程与导航。
  • references：细节按任务加载，例如帮助说明、错误排查。

把罕见分支从常驻文本移出；不要把主流程关键约束也藏起来。

验证设计

比三种版本，不凭感觉

选代表性任务，分别跑：

  • 原始版本
  • 拆分后的版本
  • 不加载技能

同时记录任务结果与上下文消耗。只有精简版保持结果，才有依据保留改动。

使用场景

先挑高收益候选

适合内容很长、参考材料多、触发范围明确的技能。若技能本来很短、每步都关键，拆分可能只增加查找成本。

从一个高频任务和一个容易失败的边界任务开始，不要一次重写整套技能库。

跑评测前，先校准适配器：每个版本使用互相隔离的副本；确认“不加载技能”组确实没有读到技能文件；shell/执行环境与目标 agent 保持一致。任何一项混淆，比较就不可信。

评测脚本与适配器

对同一任务分别运行原始技能、分层技能与不加载技能三组；每组使用隔离副本，记录任务是否满足同一成功标准、结果质量与 token 消耗。

  • 启动前确认版本/模型/工具权限一致，并清空或隔离历史上下文与缓存。
  • 不加载组须验证没有读取技能文件；运行日志记录实际加载文件、输入任务与产物。
  • 逐任务保存成功判据、评分依据、耗时/token 与失败原因；先用少量代表任务试跑，异常组作废重跑。
  • 该项目给出评测方法与适配器入口；本次没有实际运行其脚本，命令、产物格式与统计实现不作推断。

结果怎么判

  • 任务成功标准一致，且结果质量未退步：可继续采用。
  • 精简版漏约束或失败：把必要规则移回主文件，或保留对应参考内容。
  • 基线组意外读到技能：该轮作废，修正隔离后重跑。

别把数字当保证

作者自报 token 用量减少约 70–80%，并称测试结果相同；这是作者报告，不代表所有模型、任务或技能都能达到。

真实对照会消耗时间与 token；少量样例也覆盖不了全部使用情境。

安装入口

按你的 agent 选择一种即可，勿重复安装：

npx skills add nicobailon/skill-diet -g

Claude：/plugin install skill-diet --marketplace nicobailon/skill-diet

Pi：pi install npm:skill-diet

先备份技能目录，再从一项技能试跑。

速览结论：先对长且分支多的技能做小范围、可回退的分层试验；只有隔离对照显示任务质量不退步，才保留精简版。阅读分流：想快速判断看“结果怎么判”；要落地看“评测适配器”和安装入口；评测尚未执行，不能把作者报告当作本次结论。来源：github.com/nicobailon/skill-diet项目：github.com/nicobailon/skill-diet原帖：X / Shao Meng
