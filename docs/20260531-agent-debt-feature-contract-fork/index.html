1核心判断
prompts are debt
先钉死边界：这篇文章最值钱的地方，是把 prompt 从"个人技巧"升级成可维护工程资产的组织方式：feature contract 负责产品承诺，model-specific fork 负责当前模型的适配补丁，eval 决定是否发布。
01 · 文章在反对什么
Problem
core quote

"prompts are technical debt too." —— 不是在说 prompt 没用，而是在说：如果你把模型补丁写进产品承诺里，你就把未来的升级成本提前锁死了。

三层痛点
1
模型每 6-8 周就会变边界、可靠性和擅长任务会重新洗牌。
2
长 prompt 锁死今天的 workaround为旧模型写的补丁，可能阻碍新模型发挥。
3
产品功能不能靠临场适配用户侧功能需要 eval、测试和更高置信度。
个人工作流 vs 产品功能
✓
个人工作流大体能随模型更新快速调整。
✗
产品功能必须评测、测试、守住回归边界。
⚠
风险本质补丁越多，升级越难，债务越重。
02 · 正确拆法：contract + fork
Solution
feature contract
1
写产品承诺用户要完成什么，描述成功标准、边界、证据和目标。
2
尽量模型无关必须长期稳定，不绑定特定模型的弱点。
3
可验证有明确的 eval 通过条件。
model-specific fork
1
只在当前模型需要时加最小脚手架，最小必要改动。
2
内容来源当前 prompt、eval failures、production issues、vendor guide。
3
原则不是继续堆补丁，而是补新模型真的需要的东西。
核心分界：契约负责"做什么"，fork 负责"当前模型怎么更稳地做到"。二者分开，才能在新模型到来时从契约重新开始，而不是背着旧补丁升级。
03 · 工作流闭环
Workflow
1
先测新模型
直接拿 feature contract 跑新模型，不要默认带旧补丁。
2
通过就直接 ship
达到质量门槛，说明 contract 足够好，不需要 fork。
3
不过就最小 fork
保留有帮助的旧部分，删掉过时 scaffolding，只补需要的东西。
4
再跑 evals
把失败样例和 vendor guide 作为输入，验证 fork 是否真的提质。
为什么这比"继续写长 prompt"更稳：评测成为唯一发布门槛，减少拍脑袋升级；模型升级时先回到 contract，而不是在旧 fork 上打补丁。

05 · 一句话判断
Verdict
适合谁

AI 产品经理、Agent / Prompt 工程、频繁跟模型升级的团队。

边界

不是完全消灭 scaffolding，而是不把 scaffolding 写进产品契约。

记住一句

Keep the contract pure. Build the fork only when evals say you need it.

原文金句"prompts are technical debt too." 把这句话当成日常检查项：每次想往 prompt 里加规则时，先问这是"契约"还是"补丁"。
