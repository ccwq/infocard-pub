### 推断性技术原理（基于社区讨论，非官方确认）

SeaweedFS 的删除流程（推断性描述，非官方确认）：

1. **标记删除**：Filer 收到删除请求后，在元数据层标记文件为"已删除"
2. **延迟窗口**：物理数据在 Volume 中暂存，未被覆写，恢复窗口依赖 GC 配置
3. **GC 触发**：Master 调度 Volume Garbage Collection，`garbageThreshold` 控制触发时机

S3 兼容模式下可能存在类似 AWS S3 的 Delete Marker 行为，但需官方文档确认。

## Agent 误删风险矩阵

| 风险维度 | 传统本地磁盘 | 具备延迟删除的分布式存储 |
|----------|-------------|----------------------|
| rm -rf 后果 | 永久消失 | GC 触发前可恢复（取决于窗口期） |
| Agent 误操作容错 | ❌ 无保护 | ⚠ 部分保护（依赖 GC 配置） |
| 性能影响 | 无额外开销 | GC 阶段有额外 I/O |
| 运维复杂度 | 低 | 中（需配置 GC 策略） |

## 风险边界（已核实）

1. 延迟删除依赖 Filer 或 S3 网关层实现，纯 Volume 层删除可能是即时的
2. GC 触发后数据不可恢复（不同于 AWS S3 版本控制的即时性）
3. 多副本场景下，GC 时机可能不同步，恢复窗口存在不一致风险
4. 配置不当（过小 GC threshold）可能导致存储空间快速耗尽
5. **本卡信息不构成技术选型建议，实际部署前请阅读官方文档**

## Agent 安全最佳实践

无论存储系统是否支持延迟删除，以下原则均适用：

1. **最小权限原则**：Agent 仅应具备必要的文件操作权限，避免直接 shell 访问根目录
2. **API 层隔离**：Agent 通过有安全防护的 API 操作存储，而非直接执行系统命令
3. **备份策略**：延迟删除不等同于备份，需配合定期备份策略
4. **审计日志**：记录所有删除操作，支持事后追溯

## 收口结论

- **已核实**：SeaweedFS 是 Apache-2.0 分布式存储系统，架构为 Master+Volume+Filer，支持 S3/Filer/Iceberg
- **待核验**：延迟删除 / GC 延迟回收的具体行为、参数配置、恢复窗口时长
- **建议**：生产部署前必须测试实际删除行为，并结合备份策略，不将延迟删除作为唯一数据保护手段
