01

它是什么，以及今天该怎么开始

awesome-design-md 是 VoltAgent 整理的设计规范集合，不是一套可以直接导入页面的 React 组件。项目按站点组织目录，把颜色、文字、间距、形状、组件规则与视觉意图写在 DESIGN.md 中。这里的“design”不是你的业务需求，“md”则是 Markdown 文档的扩展名。它解决的是“把参考风格讲清楚并重复引用”的问题，而不是替你完成产品设计、交互开发和浏览器测试。

本次读取的线上仓库树中有 84 份位于 design-md/ 下的 DESIGN.md。这个数字是文件数量，不是八十四家公司官方授权的设计系统，也不意味着每份质量和完整程度相同。名字相近的规范可能关注不同页面类型；一个站点的营销首页也不能代表它整个后台产品。挑选时先问“我要什么页面”，再问“喜欢哪家品牌”，通常更不容易走偏。

三种读者，三条入口

  • 第一次让 AI 写页面：先选一个规范，做一页虚构产品的介绍页。用文档约束风格，不加登录、支付、真实用户数据等复杂功能。先学会判断配色和布局有没有落实，再增加业务。
  • 已经有项目，但界面不统一：先读自己的现有规范，列出重复色号、卡片圆角和间距的冲突。把外部规范当参考，不要直接覆盖团队已有的 DESIGN.md。现有品牌、无障碍要求和组件 API 应优先。
  • 想比较不同设计语言：用同一段业务文案、同一组内容结构分别试 Linear 与 Vercel，比较层级、按钮和留白；不要同时换文案、功能和风格，否则难以知道差异从哪里来。

最短成功路径不是“克隆成功”，而是：拿到一份正确文本 → 确认工具确实读取 → 让工具解释三条约束 → 做一个小页面 → 人工检查。下文给出的是可复用练习路径，本卡没有实际运行 Claude Code、Cursor 或 v0，也没有把生成界面效果当作已验证结论。

不用终端：网页直接获得单个文件

  1. 进入 GitHub 仓库，打开 design-md，再打开 linear.app，最后点 DESIGN.md。不要把该目录的 README.md 当成设计规范。
  2. 点文件页的 Raw，或直接打开 Linear 原始文本。使用浏览器“另存为”，保存到自己项目中，文件名应是 DESIGN.md，不是 DESIGN.md.txt，也不是 GitHub 页面 HTML。
  3. 如果项目里已有同名文件，先复制为 DESIGN.before-awesome.md 并检查内容，再决定合并还是另存为参考文件。没有明确合并方案时，可暂时使用 reference-linear-DESIGN.md，提示 Agent 读取这个完整文件名。
  4. 用文本编辑器打开下载结果。开头应能看到三条短横线包围的 frontmatter，后面有 Markdown 标题和说明；如果开头是网页标签、登录提示或报错页，就没有拿到正确文件。

下载保存到哪个目录由你选择，网页不会自动知道你的“项目根目录”。项目根目录指这次开发任务的工作目录，不是电脑桌面、个人主目录，也不是规范集合仓库自身。复制之后还要告诉 Agent 读哪份文件，根目录存在文件并不等于所有工具会自动装载。

02

选规范：先看页面任务，不先看品牌热度

规范集合的价值在于可比较，不在于给每个项目套同一种“高级感”。对初学者，能解释选择理由比收集更多文件更重要：你的主要读者是开发者、普通消费者还是公司采购者？页面的核心是展示软件截图、解释技术流程还是填写表单？内容以长中文、短英文还是代码为主？这些问题会决定字阶、密度和组件需求。

当前任务优先检查什么合理选择与边界
软件产品介绍画布、产品截图容器、主次 CTA、功能卡片Linear 文件强调暗色画布和产品截图，可以作为相关任务的参考；并不意味着项目管理后台要照搬营销页。
开发者平台首页技术标签、代码区、浅色表面、主按钮、宽屏留白Vercel 文件包含对应描述，适合用来理解浅色开发者品牌；装饰渐变不应盖过信息与操作。
长中文教程正文行高、长标题换行、目录、链接可辨识度先保证阅读，不要机械沿用英文标题的负字距和极大字号。可以沿用色彩角色，再调整文字规则并记录原因。
已有品牌的业务表单错误、禁用、成功状态与交互说明优先现有团队规范；外部文件缺失的业务状态应补设计，不能借一个色号就声称形成了完整表单系统。
准备直接上线的界面许可证、依赖字体、键盘操作、实际内容、设备表现文档只是输入。需要实现与测试，不能把仓库目录数量或流行度当成上线质量证据。

选择时至少读 Overview、Components、Do's and Don'ts，以及响应式相关章节。只截取 colors 一段，会漏掉“强调色只能少量使用”“营销 CTA 和导航按钮是两种圆角尺度”等规则，最终页面可能有正确色号却是错误风格。读完后写一句自己的选择理由，例如“产品截图是主要证据，所以采用深色画布和弱边框，不做满屏装饰渐变”。这是阅读结果，不是品牌官方背书。

如果文件中正好没有你需要的组件，不必强行套用名称。规范的功能卡片可以帮助决定背景和内边距，但不能替代数据表格的排序语义；营销按钮的规则可以帮助确定颜色，但不能替代提交表单时的加载、重复提交和错误恢复逻辑。先标出缺口，再由项目补上，不要让模型把不知道的部分包装成“原规范要求”。

03

读懂 DESIGN.md：数值、角色与规则是一体的

这两份真实文件都以 YAML frontmatter 开头，后接 Markdown 正文；版本字段为 alpha。frontmatter 可以把键和值组织得比较清楚，但没有自动加载或自动生成 CSS 的魔法。浏览器不会直接执行它，前端框架也不会因为根目录多了 DESIGN.md 就改变按钮样式。需要人或 Agent 把文字约定翻译成实现，并检查翻译是否符合原意。

术语初学者解释读文件时的动作
token给可重复设计决策起一个名字。例如 colors.canvas 是画布角色，而非某个特定 div。找出名称、数值、使用范围，避免把任何相近色号都当成同一角色。
语义颜色按用途命名的颜色，如正文、弱文字、错误、主操作。换主题时用途尽量不变。先确认“哪个角色”，再抄色号。primary 不必等于蓝色，Vercel 的 primary 是近黑色。
typography文字系统，包含字体族、字号、字重、行高与字距；不是只有 font-size。整组读 body 与 display，不要拿大标题参数给普通段落。
spacing内容间距离的尺度。内边距是盒子里留白，gap 是兄弟元素的间隔。区分卡片内部间距和页面分区间距，不能用一个 24px 覆盖全部。
rounded边角的曲率。按钮、表单和卡片可能使用不同 token。查具体组件引用；“这家网站圆角 8px”通常过于粗糙。
elevation层级与深度，不一定靠阴影，也可用表面亮度、细边框或前后关系。理解升一层的视觉变化；暗色页面堆黑阴影可能几乎看不出来。
component组合了若干 token 的可复用界面单位。这里是文字描述，不是已导出的组件源码。读取默认、hover、pressed、focused 等条目，检查实现覆盖哪些状态。
响应式宽度变化后，列数、字号、导航、图片与内容次序的调整。查移动端策略，不要只把桌面整页按比例缩小。

README 介绍的内容分成九个方面：氛围与总体意图、颜色、文字、组件、布局、层级深度、该做与不该做、响应式、给 Agent 的提示指导。这是阅读地图，并非所有文件都必须拥有完全相同的标题或同样详细的内容。实际使用应以选中的文件为准，发现缺少错误状态、字体分发或素材许可时，不要用“九类内容齐全”替它作担保。

components:
  button-primary:
    backgroundColor: "{colors.primary}"
    textColor: "{colors.on-primary}"
    typography: "{typography.button}"
    rounded: "{rounded.md}"
    padding: 8px 14px

上面摘自 Linear 文件的按钮条目。花括号里的 colors.primary 表示对同文件 token 的引用，不是 JavaScript 插值，也不是可直接写进 CSS 的颜色。Agent 应把它解析为 #5e6ad2，把 on-primary 解析为 #ffffff，再结合正文中的按钮状态说明实现。若最终 CSS 原样出现 {colors.primary}，说明翻译没有完成。最好让 Agent 先列一张“原 token → 项目变量 → 使用组件”的映射表，再改代码。

YAML 与正文可能强调不同细节，甚至存在表述不一致；例如 Vercel 正文同时描述营销大按钮与小导航按钮，另有不要混用尺度的提示。遇到这类情况要根据具体页面语境解释，必要时列出待确认点，而不是让模型任选一条。alpha 也是提醒：适合审阅和试验，不应把所有字段理解为稳定跨工具接口。

04

实例一：逐字段读 Linear 的暗色营销规范

读取路径是 design-md/linear.app/DESIGN.md，名称字段为 Linear-design-analysis。它描述的是以软件产品展示为中心的深色营销画布，不是 Linear 内部产品界面的完整设计系统。正文提到来源页面包括首页、intake、pricing、contact/sales 和 build；这些是该规范作者的取样说明。本卡直接核对的是仓库里的文档，并未重新测量 Linear 官网的所有 CSS。

真实字段文件取值如何落实到页面
colors.canvas#010102页面底色是带极弱色倾向的近黑，不要偷换成纯 #000000，也不要将画布误当主按钮颜色。
colors.ink#f7f8f8标题和正文的主要浅色文字；不是所有次要信息都要同样亮。
colors.primary#5e6ad2薰衣草蓝用于主 CTA、焦点和有限强调，不能把每张功能卡片都填成紫蓝色。
colors.surface-1#0f1011默认功能卡片与定价卡片比画布稍亮，建立微妙层级。
colors.hairline#23252a细边框和分隔。边界应在真实背景上检查，不用肉眼记忆推断可见性。
rounded.md / lg8px / 12px按钮、输入使用 md；功能、定价、引言卡片通常使用 lg。产品截图容器另外使用 xl 16px。
spacing4 / 8 / 12 / 16 / 24 / 32 / 48px；section 96px小元素间隙与章节距离属于不同尺度，按角色选择，避免全页面一种间距。

从文字系统读起，display-xl 在文件里是 80px、字重 600、行高 1.05、字距 -3.0px；body 是 16px、400、1.50、-0.05px。两者不是换一个字号那么简单。字号增大后，行高和字距同步调整，标题才能形成紧凑轮廓。中文标题不应机械套用英文负字距：先用真实标题测试，不要为了“像 Linear”挤压字形。

组件的状态也有真实条目。button-primary-hover 的背景引用 primary-hover，取值 #828fff；button-primary-pressed 引用 primary-focus，取值 #5e69d1。输入有 text-input-focused，正文描述焦点环。因而把这份文档说成“没有交互状态”不准确；正确边界是有状态规格，但没有状态实现。是否能通过键盘激活、焦点是否可见、表单错误是否读得出来，仍需要你实现和测试。

卡片层级主要通过 surface-1、surface-2 及边框建立，而非通用大阴影。普通功能卡片内边距 24px、圆角 12px；testimonial-card 内边距 32px；cta-banner 内边距 48px。问 Agent“做一个卡片”还太模糊，可以改成“做 feature-card，引用 surface-1、rounded.lg、24px padding；只把推荐方案升到 surface-2”。这样组件角色和例外更明确。

移动策略在 Responsive Behavior 中有明确指导：桌面网格三列、平板两列、窄屏一列；导航在相应宽度折叠；定价比较改成折叠式内容，标题尺度缩小。文件给出多个参考宽度，并在正文说明 1024px、768px 等变化。实际实现仍需决定媒体查询边界、长中文标题和菜单行为，不能只把这些宽度复制到 CSS 就认为体验一致。

深入看：文件自己承认哪些缺口？

Known Gaps 说表单错误与校验样式在取样页面不可见，营销亮色主题没有记录，产品内优先级与标签使用更丰富的色板；专有字体允许找替代。对你而言，这意味着做一个包含大量状态的项目管理列表，需要额外设计优先级、选中、批量操作、错误恢复等细节。营销规范不能自动覆盖业务后台。

文件的 Iteration Guide 还提到一个 lint 命令，但本卡没有安装或验证该工具的当前可用性，因此不把它设为首次使用必需步骤。先理解并核对文档、再决定引入额外工具，避免把可选检查变成隐藏安装依赖。单份规范能读懂，比一次装齐未知工具更有价值。

本次线上目录树显示 linear.app 目录只有 DESIGN.md 与 README.md，没有 preview.html 或 preview-dark.html。因此不能据 README 的总体介绍保证每个站点都附预览，也不要把“没找到预览”当作下载失败。原始文本本身足以完成这张卡的第一次阅读练习。

05

实例二：Vercel 不是“把 Linear 背景改白”

第二份路径是 design-md/vercel/DESIGN.md，名称为 Vercel-Inspired-design-analysis，description 明确是 inspired interpretation，即启发式解读，而非该公司官方发布的全部规范。它强调近白画布、深色文字、开发者技术标签与大尺度装饰渐变。与 Linear 对比时，关键不是“黑和白”两个颜色，而是按钮形状、字体角色、层级手段与内容节奏的整体变化。

真实字段文件取值阅读重点
colors.canvas#ffffff白色表面；正文另说 canvas-soft #fafafa 常作页面背景，需根据页面角色选择。
colors.ink / primary#171717 / #171717正文主色和主 CTA 背景同色，但仍是不同语义角色；不是“primary 一定是彩色”。
colors.link#0070f3链接蓝与主按钮近黑分开，不能把所有操作都强行改成蓝色。
colors.hairline#ebebeb浅色细边框，应该结合真实背景检查边界，不等于任何灰色都能替代。
rounded.sm / md / pill6px / 8px / 100px导航小按钮、营销卡片、大 CTA 用不同尺度；不存在“全站只用一个圆角”。
spacing.section192px文件中的大章节节奏比 Linear 更宽松，但不是小屏所有区块固定留 192px 空白。

文字部分 display-xl 是 48px、600、48px 行高、-2.4px 字距；body-md 是 16px、400、24px 行高。技术标签与代码使用等宽字体，而普通长段落不使用等宽字体。这给初学者一个很具体的判断方法：一个开发者页面不需要“全站终端风”。等宽字用于代码和技术层，正文仍应该服务连续阅读。

组件部分 button-primary 的营销形态使用 rounded.pill，近黑底、白字；nav-cta-signup 则使用 rounded.sm，文件记录高度 28px；form-input 使用 6px 圆角、高度 40px。不能拿导航按钮的高度代表所有主操作的触达区域，尤其在触屏上。文件正文提到移动端扩展点击范围，这属于应落实的指导，而不是已存在于你的项目里的机制。

它的层级采用细边线与轻微叠加阴影，和 Linear 的暗色表面升阶不同。hero 里的多色渐变是大尺度氛围，不是给每个图标一块彩色渐变；主按钮仍用近黑，把转换操作保留下来。若你的产品不需要这种氛围，可以明确记录去掉装饰的变体，而不是说“原文要求每页都要有渐变”。业务优先级高于复制品牌形象。

Vercel 文件包含自动派生的 ex-* 示例条目，其中描述说明是 illustrative。它们可帮助理解同一组原生 token 如何用于定价、空状态、表单卡片、toast 等表面，却不是你已安装的组件套件，也不能直接推断对应功能可以运行。出现 TO_FILL 或类似标记时，应作为待补齐线索，不能原样带入用户可见界面。

把两份规范比较成可执行选择，而不是审美投票

如果一个功能模块主要展示软件界面截图，Linear 的画布与截图容器描述较直接；如果主要解释部署、代码和平台能力，Vercel 的技术标签与代码表面描述提供更贴近的参考。这个选择规则是本卡作者依据文件内容的建议，不是仓库给出的官方任务分类。两种风格都不能替代你的信息架构。

切换规范时至少列出四类变动：画布与文字极性、主操作与链接色、按钮与卡片形状、卡片与章节间距。再列出不能变的项目：业务文案、输入标签、导航目标、操作语义、键盘顺序。这样你可以只检查视觉改变，不会把“换皮”误变成“重新做产品”。

文件中关于字体专有性和替代方案的描述不能代替字体许可证。本卡只确认文件如何写，不替每款字体的授权下结论。若选择 Geist、Inter 或其他字体，单独核对实际下载来源、字体版本和许可；首次练习用系统字体就能减少额外依赖，也更容易发现长中文布局的问题。

安全复制：只拿 DESIGN.md，不用星号通配

网页下载已经足够完成入门。下面的 Git 路线只是另一种获得文件的方法，适合希望保留来源版本的人。命令中的路径是示例，你必须替换为自己电脑上的真实位置。先分清“集合仓库”和“目标项目”，再执行复制。以下命令为教学示例，未在你的电脑运行；复制操作不会安装组件，也不会启动服务。

07

接入工具：先证明“读到了”，再让它写页面

仓库提供的是通用纯文本输入，工具如何附加文件、维护长期规则、限制工作目录，是各工具自己的能力。最保守且可迁移的方法，是在任务中显式指定 DESIGN.md 并要求先阅读。不要假设每个聊天工具都有访问本地磁盘的权限，也不要把模型回复“我会遵循”当成它真的拿到了完整文档。

第一次对话先发这段，不立刻改代码

先只读项目根目录的 DESIGN.md，不修改任何文件。
请说明这份文件的 name / version，列出 canvas、ink、primary，
并解释一个主按钮、一个卡片、一个移动端布局约束。
每项注明来自 frontmatter 还是正文；没有找到就说没有找到。
最后列出与本项目原有规范可能冲突的地方，再等待我确认。

预期是得到可核对的字段和出处，不是得到漂亮的赞美。以 Linear 为例，若它回答 canvas 是 #000000 或把 button-primary 当成胶囊按钮，就应该回到阅读步骤排查。这个核对提示由本卡作者编写，不是仓库自带测试套件，也不能保证所有模型都会正确读文件。

Claude Code：显式阅读与官方导入语法分开理解

一次性任务可直接要求读取文件。需要长期引用时，Claude Code 官方 memory 文档支持在 CLAUDE.md 中使用 @DESIGN.md 导入。这个导入写在普通文本中才有效，放在反引号或代码围栏里不会被当成导入。下面展示的是应放入文件的普通文本；本卡页面为了方便复制把它显示在代码区域，你写入 CLAUDE.md 时不要保留围栏。

界面任务开始前阅读设计规范：
@DESIGN.md
先核对与现有业务约束的冲突，不要擅自改品牌或删除无障碍行为。

不要为了加入三行提示就重写已有 CLAUDE.md。先人工阅读原文件，了解项目目录、测试命令和团队规则，再追加或合并；确保相对路径指向希望引用的文件。导入会增加上下文，不等于文件里所有描述都优先于用户要求。比如原规范强调装饰动效，而用户要求降低动态效果，应明确选择符合当前任务的行为。

Cursor：显式附加文件，不猜规则自动加载

在当前工具版本的任务或聊天里附加 DESIGN.md，并明确要求先读取。规则文件的目录、扩展名、元数据与触发范围属于 Cursor 的版本化约定；本次没有确认最新完整 schema，因此不声称把 DESIGN.md 复制到 .cursor/rules/design.md 就会自动生效。想做长期规则时，请先核对当前官方规则文档，再建立只指向适用任务的规则。不要同时存两份不同内容却同名的规范，让模型随机选择。

v0 与其他网页工具：附件是输入，不是本地访问授权

把文档作为附件，或将所需内容粘贴进工具支持的上下文输入，并写明使用范围。网页工具通常不能凭“根目录文件名”读取你的电脑项目；如果没有附件功能，应确认粘贴内容完整，尤其不要只贴色号漏掉 Do's and Don'ts。附加规范后仍要告诉它要做什么页面、使用什么内容、哪些功能不实现，以及怎样验收。

所有工具共同的判定是：能复述准确取值与规则，只能说明输入读取大致正确；实现是否符合，必须看实际文件与页面。模型可能理解规则但生成时偏离，也可能第一轮符合、第二轮添加组件时漂移。每次重要修改后保留一个小检查清单，比只在开场要求“严格遵守”更有效。

首个练习：做一页虚构软件介绍，不做整套产品

下面是可复制的完整任务提示。建议第一次选择 Linear 规范，使用虚构项目“轻舟任务台”，只做展示页面。它不使用 Linear 品牌标志，也不假装是某公司官方产品。练习的目的，是把文件中的设计决策转成可检查的界面；业务规模小，才容易定位错误。

任务：用当前项目已有技术栈做一页中文“轻舟任务台”软件介绍页。
先读取 DESIGN.md，汇报 name/version、canvas/ink/primary；未经确认先不要写代码。
不要安装新框架，不修改登录、支付、数据库或部署设置；不使用真实品牌 logo。

确认后实现：
1. 页头：产品名、功能/方案/联系导航，主按钮“试用演示”。
2. 首屏：标题“把零散任务收进一个清晰的工作台”，两句说明，
   主按钮“查看功能”、次按钮“了解方案”。
3. 功能区：三张 feature-card，内容分别为任务整理、项目进度、团队协作。
4. 方案区：两张方案卡，仅说明“个人练习”“团队试用”，不接真实支付。
5. 末尾 CTA 和页脚：说明“这是界面练习，不收集个人资料”。
6. 没有合法截图素材时，以明确标注的“界面示意”容器替代，不捏造客户评价。

视觉约束：按 DESIGN.md 的语义角色映射画布、正文、主按钮、卡片和边框。
按钮/卡片圆角按对应组件定义，不为好看而统一成胶囊。
落实 hover、pressed、focus；没有明确的错误状态则注明待设计。
中文标题允许自然换行，不机械照抄英文负字距。
移动端一列，导航可用，代码或长链接不撑破整页。

交付：列出改动文件、token 映射、实际实现的交互、未实现项。
给出本项目已有的启动/检查命令，不猜不存在的脚本。
验收：核对三色与两个圆角；390px 和桌面无页面横向溢出；
Tab 可依次到达链接和按钮，焦点可见；所有 CTA 到达说明的目标。
若没有实际启动浏览器，必须直说“未做运行与视觉验收”。

这里的 390px 是本卡建议的检查宽度，不是仓库规定的唯一断点。两张方案卡也是练习选择，不是照搬某个真实产品定价。你可以改业务内容，但初次不要增加真实表单提交，否则需要另外处理数据收集、校验、网络失败和隐私提示，容易把视觉练习变成后端项目。

你应拿到什么，而不应期待什么

  • 文件层：沿用现有技术栈的页面与样式改动，以及一个清楚的 token 映射。框架没有必要统一，如果项目原本用 Vue，就不该为了规范文件强行改 React。
  • 交互层：按钮目标明确、导航可到对应区块、键盘焦点可见。展示页面的 CTA 可以跳到功能区或说明区，但不能点了毫无反应却标“试用”。
  • 边界层：示意图、未接后端、未实现支付、未验证表单状态等都要写明。假截图、假推荐语和真实公司 Logo 不应作为练习默认素材。
  • 检查层：只有真的运行过项目命令、打开过页面并检查，才能报测试结果。模型写了一份“测试通过”段落，不是浏览器证据。

第一次验收后，用第二轮小提示只修一个问题，例如“主按钮用了 pill，按 button-primary 改成 rounded.md，不改文案和布局”。如果第一轮问题很多，先修读取或 token 映射，别再堆二十条审美指令。范围越小，越能判断模型是否理解规范；批量要求“更专业更高级”只会让它重新自由发挥。

进阶：把语义 token 映射成项目样式

下面是本卡作者编写的教学 CSS，不是仓库自带的可安装样式，也不是完整页面。它只展示如何把 Linear 文档中的角色转换为浏览器认识的变量。变量名可以按团队习惯改变，但角色对应应留下记录；组件优先引用变量，避免在十个文件里散落同一个色号。

展开最小 CSS 映射与按钮示例
/* 教学映射：源为 Linear DESIGN.md；并非仓库原文件 */
:root {
  --page-bg: #010102;       /* colors.canvas */
  --text-main: #f7f8f8;     /* colors.ink */
  --action-bg: #5e6ad2;    /* colors.primary */
  --action-hover: #828fff; /* colors.primary-hover */
  --action-pressed: #5e69d1; /* colors.primary-focus */
  --on-action: #ffffff;   /* colors.on-primary */
  --panel-bg: #0f1011;    /* colors.surface-1 */
  --border-soft: #23252a; /* colors.hairline */
  --radius-control: 8px;  /* rounded.md */
  --radius-card: 12px;    /* rounded.lg */
  --space-card: 24px;     /* spacing.lg */
}
body { background: var(--page-bg); color: var(--text-main); }
.feature-card {
  background: var(--panel-bg);
  border: 1px solid var(--border-soft);
  border-radius: var(--radius-card);
  padding: var(--space-card);
}
.primary-action {
  background: var(--action-bg); color: var(--on-action);
  border: 0; border-radius: var(--radius-control);
  padding: 8px 14px; font: 500 14px/1.2 system-ui, sans-serif;
}
.primary-action:hover { background: var(--action-hover); }
.primary-action:active { background: var(--action-pressed); }
/* 作者建议：强调焦点可见；不是逐像素复刻文件的半透明焦点环 */
.primary-action:focus-visible {
  outline: 2px solid var(--action-hover); outline-offset: 3px;
}
.practice-grid { display: grid; grid-template-columns: repeat(3, 1fr); gap: 24px; }
@media (max-width: 1024px) { .practice-grid { grid-template-columns: repeat(2, 1fr); } }
@media (max-width: 767px) { .practice-grid { grid-template-columns: 1fr; } }

示例用了系统字体，目的在于避免默认依赖专有字体；正式页面仍应定义中文回退、标题和正文的完整文字系统。focus-visible 的轮廓是可检查性建议，不是声称完全复刻原文。媒体查询只是从文件布局指导抽出的练习实现，原规范没有强制你使用这个类名，也没有替你处理菜单和定价折叠。

映射最容易犯的错是只换变量值、不看组件语义。把这组变量替成 Vercel 色号，卡片和按钮形状仍然是 Linear 的，层级手段也未改变；那是“改色版”，不是完整切换规范。要换风格，应逐项检查组件对 rounded、spacing、typography 的引用，并检查暗色/浅色下边框和焦点是否可辨识。

项目已有组件库时，不必重新造每个按钮。可以通过它支持的主题变量、class 或样式接口应用 token，但保留它的语义 HTML、键盘行为与状态 API。设计规范不应成为删掉原库无障碍机制的理由。如果组件库的圆角或阴影接口难以覆盖，记录妥协与原因，别宣称“完全遵循”。

同名 token 不等于相同 schema。Linear 有 typography.body，Vercel 有 typography.body-md；spacing 的较大阶梯名称也不同。写自动转换脚本前先逐文件核对字段、引用和缺口，再定义自己的稳定角色层。本卡没有验证通用解析器，不建议初学者第一次就把全部八十四份文件作为统一配置批量转 CSS。

10

人工验收：规范符合、页面可用、运行已验证，分别检查

“读对文件”和“页面可用”是不同阶段。下面是作者建议的验收清单，不是仓库保证，也不是本卡生成效果的测试报告。检查时用实际业务内容，不只看模型填的短英文；长中文按钮、长产品名、空数据和加载失败都会暴露样式与交互缺口。

检查层操作通过现象 / 失败信号
输入读取让 Agent 回报文件 name、version 与三种角色色。能逐项对应原文件；若只复述提示里的颜色，仍要检查它是否读取其他规则。
token 落实在浏览器开发工具查看主按钮、卡片的计算样式。背景、文字、圆角与映射一致；CSS 写了变量但被后续规则覆盖，仍算未落实。
内容层级先扫一遍页面，不逐字读，找标题、主要行动和支持信息。主要行动清楚，次要内容不抢注意力；所有卡片都用强调色通常是层级失衡。
窄屏在 390px 与更窄窗口检查长标题、导航、卡片和表格。页面不整体横向滚动；表格与代码可局部横滚；卡片不要挤成不可读窄列。
键盘不使用鼠标，用 Tab、Shift+Tab 与 Enter 访问所有操作。焦点可见、顺序合理，原生按钮能激活；菜单如果打开，应能关闭，不把焦点留在遮挡内容后。
对比度用对比度工具检查真实前景与背景，覆盖默认与状态色。不能只看色号“像原站”；小文字、hover、禁用和透明叠加尤其需要检查。
真实操作逐个点导航与 CTA，输入错误值或空值（若页面有表单）。目标明确，有反馈；没有后端时明确说明，不能把演示成功伪装成真实提交成功。
运行证据使用项目已存在的脚本启动或检查，记下命令、退出结果与未覆盖内容。成功命令只证明对应检查，不能代替浏览器视觉和键盘验收。

对比度检查建议可参考常用 WCAG AA 文字要求：普通文字通常至少 4.5:1，大字通常至少 3:1。这个建议不是从仓库的每个 token 推导出“全部达标”，也不意味着满足两个比率就完整满足无障碍标准。具体页面还需要检查操作目标、非颜色提示、错误说明、结构和辅助技术行为；不清楚文本是否符合大字分类时，先按更严格的普通文字要求检查。

鼠标 hover 不是键盘 focus 的替代品，颜色变化也不是操作语义。链接用来去一个目标，按钮用来执行一个动作，别为了方便给所有元素加 onClick 而丢失键盘行为。表单输入要有标签，报错不能只有红框。规范没有说明错误样式时，可以按项目要求补设计并标为变体，不要捏造一条原文不存在的“官方错误组件”。

移动端还要检查内容次序。桌面左右两列变一列时，主要介绍应先于辅助装饰；重要按钮不能滑到一大段空白之后。触屏不存在持续 hover，不能把说明只放在悬停浮层。若使用动画，应考虑减少动态效果偏好。以上是实施建议，规范文件并不会自动提供焦点管理、减少动态效果或屏幕阅读器支持。

验收记录可以很短：本次读取哪份文件；核对哪些 token；检查哪些宽度和操作；具体发现什么问题；哪些未测试。不要写“所有设备完美通过”。一次 390px 检查只代表这个宽度的观察，不能代表所有手机、浏览器和真实设备。清楚的范围说明比漂亮的通过标记更可信。

11

排错：按输入 → 映射 → 实现 → 运行的顺序查

出现问题时，不要先追加“严格、极致、像素级”这种空泛形容词。先定位是哪一层失败：文件没拿对、模型没读到、token 转换错误、CSS 被覆盖，还是功能根本没有实现。每次只改一个原因，保留可以人工核对的字段或页面现象。

现象可能原因下一步动作
文件内容是 GitHub 网页保存了文件展示页而非 Raw。重新打开原始文本链接，确认 frontmatter 与 Markdown 标题，不把 HTML 当 DESIGN.md。
复制命令报多个来源使用 *.md，同时选中 README 与 DESIGN。来源改成精确的 /linear.app/DESIGN.md，先确认目标项目目录。
目标已有规范团队原本就定义了业务与品牌约束。先备份、阅读与比较；另存参考或人工合并，不用外部文件直接替掉。
Agent 色号答错没读到文件、附件截断或读取了同名旧文件。明确完整路径或重新附加，让它回报 name/version 与一个正文规则。
变量是 {colors.primary}把 token 引用当成浏览器可执行值。要求生成映射表，替换为具体值或有效 CSS 变量，检查计算样式。
颜色对，气质仍不同只复制 colors，漏了字阶、圆角、间距、层级和禁止项。从一个主按钮和一个卡片开始核对完整组件规则，再看章节节奏。
每次改页面又换风格当前任务没引用规范，或多个规则互相冲突。显式说明唯一规范与优先级，要求每轮列出修改涉及的 token。
Cursor 不自动遵循误以为任意 .md 放规则目录都能生效。先走显式附加路线，再按当前版本官方文档确认规则格式与触发范围。
手机标题或表格撑破页面固定宽度、不可断词字符串、多列没有收拢。查真实溢出元素；网格改单列，表格/代码容器局部滚动，长标题允许换行。
按 Tab 找不到按钮用普通容器模拟按钮或删除了焦点样式。恢复语义元素与可见焦点，验证键盘激活，不只加 hover 颜色。
错误状态毫无反馈把未记录的状态误当“无需处理”。补项目级校验与错误说明，并注明它是本项目设计，不是源规范自带。
找不到 preview 文件把 README 总体描述误读成每个站点保证。核对该目录真实文件；Linear 本次只有 DESIGN 与 README，直接读文本即可。
字体显示不同或加载失败专有字体未分发、文件路径错误、中文回退不完整。用许可明确的字体或系统回退，重新检查文字宽度与换行，不从原站搬字体。
模型声称已测试却没命令把预期现象写成运行结果。要求列出真实执行命令、退出结果、浏览器检查范围；没有则标未测。
第二轮提示范例：修一个可观察问题
只处理主 CTA 的 token 映射，不改文案、结构和其他组件。
当前计算样式圆角是 9999px，但 Linear 的 button-primary 引用 rounded.md=8px。
请找到覆盖来源并修复；保留键盘 focus-visible 与当前跳转目标。
完成后列出修改文件、修复依据、实际检查，以及没做的运行检查。

“当前计算样式”应由你检查后填入，不要照抄示例并冒充测量。若问题其实来自选错文件，就回到输入阶段；如果来自业务组件库的约束，要权衡覆盖方式，不应删掉成熟组件行为只求样式一致。排错的目标是可解释，而非无限提示直到出现一张好看的截图。

12

维护变体：记录来源与改动，不追着 main 自动覆盖

当练习开始变成真实项目，最重要的不是每天同步所有新规范，而是让团队知道自己用了哪一份、为什么修改、哪些内容没有照搬。main 分支会变化，源站也会变化，下载到项目里的文件却不会自动更新。把规范当作有来源的快照，才容易解释几个月后“为什么这个按钮是这样”。

展开推荐的版本记录方式

在项目文档里记录：来源仓库链接、选中文件路径、来源提交标识（如有）、下载日期、文件原始 name/version、适用页面类型、项目覆盖项。提交标识应来自实际仓库或 GitHub 页面，不要凭空写一个看起来像哈希的字符串。本卡只读取了运行目录保存的线上证据，没有为你的目标项目创建版本锁。

# 教学记录模板：将占位项换成真实信息

如果未来更新源文件，先做文本差异审阅，再检查项目映射；不要让新版本直接覆盖旧文件并批量换 CSS。只想锁定获得时的内容，可以使用 GitHub 的固定提交文件链接；确认真实提交后再替换 main 路径。固定版本提高可重复性，不说明该版本永远正确，也不代表源站之后没有变化。

变体怎么写才不与上游混淆

保留上游参考时，另建 PROJECT-DESIGN.md 或在现有规范中清楚区分“来源规则”和“项目调整”。例如你为了中文阅读取消了标题负字距，应记录原因，而非悄悄改源文件再继续称其为原版 Linear。任何额外错误、加载和禁用状态，也应说明是项目补充。Agent 后续读规范时才知道哪些规则不能被同步覆盖。

团队评审时可以只讨论具体变体：这个 24px 卡片内边距在长中文里是否过密？浅色细边框在当前屏幕上是否足够可见？主按钮的形状是否与导航按钮混淆？不要把意见全部包装成“原站就是这样”。仓库是公开页面解读，文件中的强措辞也需要回到取样范围判断。

贡献上游：先问维护者，别承诺一定能提交规范 PR

本次读取的 CONTRIBUTING.md 一方面列出“先开 issue、比较线上网站、修错误色值或缺失 token、必要时更新预览、给出前后解释”的改进步骤，另一方面又明确写了不接受 DESIGN.md pull requests。这是当前原文中的张力，不能替维护者消解成“欢迎提交新规范”。合理做法是先开 issue 说明问题和证据，询问当前允许的贡献方式，再按回复行动。

其中更新 preview.html 和 preview-dark.html 的步骤，也不能推导成每个目录都存在这两个文件。先核对被修改目录，有预览则问是否需要同步，没有则不要随意新增并声称符合标准。对初学者而言，把发现的错误字段、来源页面与理由整理成清楚 issue，通常比一次大范围重写更容易交流。

许可、信任与来源：什么可以借，什么不能保证

正确的边界：有规范，不等于有实现和授权

  • 它不是各品牌官方内部规范。这是集合项目对公开站点的分析，Vercel 文件名称与描述也明确是 inspired。没有线上证据能让本卡声称各公司背书。
  • 它并非没有状态和响应式。真实文件包含按钮状态、焦点和响应式指导；但没有替你运行组件、菜单、校验、无障碍或测试。
  • 它不是免审核的提示输入。外部 Markdown 可能包含操作建议。首次先只读，审查需要安装或执行的内容，不授权 Agent 因文档一句话就安装未知包或改系统。
  • MIT 不等于品牌素材许可。项目许可不自动授予商标、Logo、截图、客户评价或专有字体的权利。公开使用前仍需逐素材核对。
  • 流行度不是验收结果。本卡不重新测星标，不用旧卡热度当当前质量证明；文件数也不代表实现覆盖率。

使用 MIT 项目时应保留适用的版权与许可声明，尤其当你分发原文或其重要部分时。不要把“开源”误读为“无需署名、可以冒充官方”。如果只是借鉴设计语言，仍应避免让名称、Logo、页面文案或整体呈现使用户误以为你与某家公司存在合作。法律与品牌风险不是换一个配色就自动消失。

字体尤其要单独判断。文件中列出的 fontFamily 可以是作者观察、推荐回退或品牌专有字体名，并不代表仓库提供了字体文件或你已取得分发权。先使用系统字体完成阅读与布局验收，再引入来源明确的字体，是更稳的初学者顺序。实际字体改变后，应重新检查换行、按钮宽度、字号和中文回退，而不是仅看下载是否成功。

让 Agent 读取文档的权限应与任务匹配。做展示页不需要云平台密钥、支付权限或真实客户资料；你也不必把整个私有仓库附加到网页工具，只需规范与必要的匿名业务信息。文档里出现命令时先理解作用，任何涉及安装、网络传输和文件覆盖的操作都需要核对范围。这是作者的安全使用建议，不是该仓库提供的沙箱能力。
