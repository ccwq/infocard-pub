HARD BLUE / WORKFLOW MANUAL

HAR-derived
API Client

把真实浏览器捕获的网络请求，提炼成可读、可验证、可重复运行的普通 HTTP 客户端。

真实浏览器捕获JSON API不绕过认证
一句话判断
它不是“破解接口”的工具，而是一条从浏览器行为到客户端代码的证据链：捕获 → 筛选 → 转换 → 验证。
01
WHY THIS EXISTS

问题不是“有没有 API”，而是浏览器到底调用了什么

私有 JSON API 往往没有稳定文档；浏览器却必须把请求、参数和响应交给服务器。HAR 把这段可观察行为保存下来。

输入

浏览器网络记录

先在用户有权访问的真实浏览器会话中操作，再导出 HAR。记录请求方法、URL、headers、cookies、query、body 和响应。

提炼

只挑目标请求

从噪声中找出 JSON/XHR/fetch 请求，确认它属于目标动作，而不是分析、埋点、静态资源或登录跳转。

验证

最小化并复现

删除无关 headers，保留必要参数，再用普通 HTTP 发出请求；失败时回到浏览器检查会话与过期认证。

02
THREE SCRIPTS

三个脚本，分别负责观察、连接与转换

技能把浏览器侧的证据处理拆成清晰步骤，而不是把“抓包”和“调用”混成一个黑盒。

har_capture.py

面向可落盘的 HAR 捕获流程。适合先保存完整网络证据，再离线筛选。

har_capture_cdp.py

通过 Chrome DevTools Protocol 连接真实浏览器，适合需要浏览器上下文的捕获场景。

har_to_client.py

读取 HAR，提炼候选请求，生成普通 HTTP 客户端草稿，供人工审阅和验证。

03
RUNBOOK

从 HAR 到客户端：一条可回滚的路径

每一步都保留人工确认点；不要把一次成功请求误当成永久稳定的接口契约。

安装
hermes skills install official/web-development/har-derived-api-client

安装的是可复用技能，不会替你登录目标站点，也不会替你运行目标 API。

筛选清单
  • 请求是否由目标用户动作触发？
  • 响应是否为目标 JSON 数据？
  • 哪些 headers/cookies 真正必要？
  • 是否含 CSRF、短期 token 或分页游标？
验证清单
  • 先用最小参数请求一次
  • 检查 HTTP 状态和 JSON 形状
  • 记录失败响应，不重试绕过认证
  • 认证过期就回浏览器重新捕获
维护策略

把生成的客户端当“经验证的快照”，不是官方 SDK。为字段、错误码、分页和登录状态写测试；站点变化时重新捕获。

04
BOUNDARIES & RISKS

能做什么，也明确不能做什么

这条工作流的价值来自边界清楚：在授权范围内复用浏览器已经完成的动作。

认证不是永久凭证

headers、cookies、CSRF token 可能短期有效；不要把 HAR 中的秘密提交到仓库或分享给他人。

不要绕过防护

不绕过 CAPTCHA、bot detection、访问控制或登录流程。遇到拦截，停止并回到合法的浏览器操作。

私有 API 会变化

接口没有稳定契约。保留原始 HAR、生成代码和验证日期，发生回归时重新观察。

适合：内部自动化、测试、个人工作流、已获授权的站点集成。不适合：窃取会话、批量绕过限制、伪造身份或把过期认证材料当作密钥管理方案。
