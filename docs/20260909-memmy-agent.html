跨 Agent 上下文基础设施

PERSONAL MEMORY HUB

A LOCAL MEMORY LAYER FOR AI AGENTS

让多个 AI Agent 共享一层可控的长期记忆

从安装、初始化、扫描历史，到接入第一个 Agent、验证召回和排查故障，一步步建立跨工具连续工作的最小闭环。

共享上下文

多个 Agent 通过同一个本地 Memory 层访问项目历史。

本地优先

默认数据目录、SQLite 记忆库和运行时文件在 ~/.memmy。

三种入口

桌面应用、Linux CLI/TUI 与 OpenAI-compatible API。

可验证召回

记忆是线索，不是事实；来源和原始材料需要核对。

核心判断：先用一个非敏感项目完成“安装 → 写入 → 检索 → 接入 → 验收”闭环，再扩大历史范围。
01

先做判断：Memmy 解决的是什么问题

如果你只使用一个 Agent、一个项目目录、一个会话窗口，普通的项目说明文件往往已经够用。Memmy 面向的是另一种工作方式：你同时使用 Claude Code、Codex、Cursor、OpenClaw、Hermes、Pi 或其他工具，并且希望这些工具共享一层可检索、可持续的个人上下文。它把对话历史、项目背景、规则、偏好、判断和产物线索放进一个记忆中枢，让不同 Agent 不必每次从零认识你。

它不是把所有历史机械地堆进数据库，也不是保证 Agent 永远给出正确答案的外挂大脑。实际工作链路是：先扫描或捕获历史，再写入本地 Memory 服务；新一轮任务开始时，Hook、插件或 Skill 召回相关上下文；任务结束后，再把回合保存下来。你得到的是跨工具连续性，而不是事实核验的替代品。

适合你的信号：你曾经在不同工具之间重复粘贴项目摘要，忘记某个决定为什么做出，或者知道以前做过，却找不到目标、产物和下一步。
02

它的工作模型：共享记忆层，而不是替换原有 Agent

可以把 Memmy 想成位于多个 Agent 旁边的一层本地上下文基础设施。Claude Code、Codex 或 Cursor 仍然负责执行任务；Memmy 负责从过去的会话中找出相关线索，并在适当入口提供给当前 Agent。不同接入方式的自动化程度不同，但都围绕三个动作展开：读取已有历史、在任务开始时召回、在任务结束时捕获。

阶段发生什么你应该如何理解
历史扫描读取本机已有 Agent 会话并导入 Memory 服务这是回填，不等于之后会自动接入
任务召回Hook 或插件搜索相关记忆并注入上下文结果是线索，不是不可质疑的事实
任务捕获回合结束后写入请求、回答、状态和工具痕迹捕获成功才形成可继续使用的历史
主动查询通过 memmy-memory search/get 或 Skill 查找适合自动召回不足时人工指定关键词
项目恢复围绕目标、判断、产物和下一步重组材料必须检查来源和时间
03

安装前准备：先选桌面、CLI 还是源码

官方提供三条主要路径。桌面应用适合希望少处理命令和服务生命周期的初学者；Linux CLI/TUI 适合终端工作流；源码路径适合开发、调试或需要理解服务组成的人。三条路径都可以使用本地记忆，但操作入口和默认服务管理不同。

路径适合谁前置条件第一次建议
桌面应用不想手动管理 Node 与服务macOS 或 Windows，使用官方应用或 Release先用账户模式完成首次体验
Linux CLI/TUI习惯终端、希望本地常驻服务Linux x64/arm64、Node.js 22+、npm、systemd user session安装后先检查两个 systemd 服务
源码构建需要开发、修改或排查Node.js、npm、Git 和完整构建工具链先只启动 Memory 服务

本文以下以 Linux CLI 为主，因为它最能展示 Memmy 的组成；桌面端的概念相同：选择账户模式或 API Key 模式，初始化配置和工作区，启动 Memory 与 Gateway，再连接 Agent。

04

Linux CLI 第一次安装：从零到打开 TUI

官方 Linux 入口要求 Node.js 22 或更高版本、npm，以及可用的 systemd 用户会话。安装脚本会启用本地 Memory 服务；第一次运行 memmy 时，如果没有可用模型配置，会进入模型设置向导。完成保存后，它再启用 Gateway 并进入 TUI。服务绑定在 localhost，退出 TUI 或终端后仍可运行，并在之后登录时启动。

node --version
npm --version
systemctl --user status

curl -fsSL https://raw.githubusercontent.com/MemTensor/memmy-agent/main/scripts/install.sh | bash
memmy

安装后先不要急着接入所有 Agent，先确认服务状态：

systemctl --user status memmy-memory.service
systemctl --user status memmy-gateway.service

安装器不会自动修改 Codex、Claude Code、Cursor 等外部 Agent；需要你明确运行初始化命令，才会安装对应的 Memory Skill 或 Hook/plugin。

05

首次配置：账户模式与 BYOK 怎么选

账户模式通过平台账户和试用额度快速体验完整的 Memory 与 Agent Runtime；API Key 模式则由你提供模型供应商凭据，数据和用量控制更直接。两者都以本地优先为主要数据路径，但模型调用、账户额度和云端能力应以当前官方文档为准。

选择优点需要注意适合的第一步
账户模式少填配置，较快体验完整流程试用额度会消耗，政策可能变化先验证扫描、召回和项目恢复
API Key / BYOK模型供应商、额度和凭据由自己控制需要配置主模型、Embedding 和记忆相关模型用环境变量保存密钥并测试连接
源码开发模式可理解服务和工作区组成依赖、构建和桌面组件更多先构建 Memory，再逐个启动

默认配置文件位于 ~/.memmy/config.yaml。provider 的 apiKey 不要直接写入明文，而是引用环境变量：

agents:
  defaults:
    model: openai/gpt-4.1
    provider: openai
    timezone: "+08:00"
providers:
  openai:
    apiKey: ${OPENAI_API_KEY}

配置完成后运行 memmy onboard 初始化工作区，运行 memmy status 检查模型、provider 和运行状态；需要菜单式配置时使用 memmy onboard --wizard。

06

先做一个最小闭环：初始化、写入、检索、核对

初学者最容易犯的错误，是一次性扫描多年历史、连接全部 Agent，然后无法判断哪一环出问题。更稳的方式是做一个最小闭环：初始化，写入一条明确记忆，搜索这条记忆，再用一个真实项目问题验证召回。

  1. 运行 memmy onboard，确认工作区和配置已建立。
  2. 运行 memmy status，记录服务、模型和 provider 状态。
  3. 用 memmy-memory health 确认 Memory HTTP 服务可访问。
  4. 添加一条不敏感、可验证的测试知识。
  5. 用 search 搜索同一关键词，检查结果、来源和时间。
  6. 询问项目目标、当前状态和下一步，对照原始项目文件检查是否漏项。
memmy onboard
memmy status
memmy-memory health
memmy-memory add "本项目的 staging 部署入口是 deploy.sh，发布前必须先运行 npm test"
memmy-memory search "staging 部署入口"
memmy-memory get <memory-id>

测试数据不要包含 API key、token、password、Cookie、私有连接字符串或客户资料。先验证服务链路，再导入真实项目。

07

把一个 Agent 接进来：扫描历史与实时集成是两件事

历史扫描会读取 Agent 已经写在本机的历史，帮助你把过去的项目导入 Memory；Hook、插件或 Skill 则负责新对话的自动召回与自动捕获。只扫描而不安装集成，不能保证下一轮对话自动带上记忆；只安装集成而没有历史，也没有过去的材料可以召回。

Agent 类型历史扫描实时方式初学者建议
Cursor / Claude Code / Codex本地会话文件Hook先扫描一个项目，再安装 Hook
OpenCode本地数据库原生 plugin确认插件事件和来源标识
OpenClaw会话与记忆数据库Memory plugin先检查本地数据目录
Hermessessions 与 state 数据Memory Provider plugin先做只读扫描和健康检查
WorkBuddy / Pi / qwenwork对应会话Skill 按需访问先学会 search/get，再考虑自动化

在桌面端打开 Memory → Cross-Agent access，选择已检测到的 Agent。先选择只扫描，确认历史来源和数据量，再决定是否安装 Hook、plugin 或 Skill。

08

理解自动召回：为什么找回项目仍需人工验收

当实时集成正常工作时，任务大致经过以下链路：用户提出请求，Hook 或 plugin 打开会话并搜索相关记忆，Memmy 将历史上下文注入 Agent，Agent 完成任务，结束时再把回合写回 Memory。这个闭环能减少重复说明，但召回结果仍可能过时、片段化或混入相似项目。

用户请求
  ↓
Hook / plugin / Skill
  ↓
搜索相关历史
  ↓
注入当前上下文
  ↓
Agent 执行任务
  ↓
捕获回答、状态与工具痕迹
  ↓
写入本地 Memory

“帮我把这个项目找回来”应该被当作调查任务，而不是神奇口令。继续追问：记忆来自哪个 Agent、什么时候产生、是原文确认还是推断、对应产物路径是什么、下一步是否完成。输出应把确认事实、合理推断和待验证项分开。

09

memmy-memory CLI：把记忆服务变成可操作工具

memmy-memory 是给 Agent、脚本和调试流程使用的命令行入口，默认连接本机 18960 端口。它适合初始化连接、检查健康、按关键词搜索、读取或写入具体记忆。

memmy-memory init
memmy-memory health
memmy-memory search "memory policies in this project"
memmy-memory add "a piece of knowledge worth saving"
memmy-memory get <id>
命令/参数作用使用建议
health检查服务是否可访问服务异常时先跑它，不要直接重装
search按自然语言关键词查找组合项目名、目标、产物、决定
get读取某条记忆详情核对来源、时间和完整内容
add显式保存一条知识只写长期有用且不敏感的事实
--source标记来源命名空间区分不同 Agent 来源
--user-id选择用户命名空间多人或多环境时显式指定

记忆条数不等于消息条数。完整回合可能包含用户消息、工具消息和 Agent 回答，但导入时会整理成一个 L1 memory；不完整、过大或写入失败的回合可能被跳过。

10

用 memmy serve 暴露本地 OpenAI-compatible API

运行 memmy serve 后，兼容 OpenAI Chat Completions 协议的工具可以通过本地 HTTP 使用 Memmy 的 Agent 能力。官方默认监听 127.0.0.1:18990，提供健康检查、模型列表和 chat completions 接口。这个入口适合脚本、桌面工具或内部实验，不应未经认证暴露到公网。

memmy serve
curl http://127.0.0.1:18990/health
curl http://127.0.0.1:18990/v1/models
端点方法用途
/healthGET检查 API 服务是否在线
/v1/modelsGET查看可用模型或运行时信息
/v1/chat/completionsPOST使用兼容协议发起对话请求

默认端口还包括 Memory HTTP 18960、Gateway health 18970、WebUI/WebSocket/admin HTTP 18980、桌面开发前端 19000 和 Vite HMR 19010。端口冲突时先确认实际监听者，再让客户端和服务端使用同一个地址。

11

常见故障：按现象定位，不要盲目重装

现象先检查处理方向
health 失败服务状态、18960、配置路径检查 service 日志和 ~/.memmy
TUI 能开但模型无响应status、provider、环境变量重新运行 wizard 并测试连接
扫描不到 Agent历史路径和产品检测先产生一条新记录再扫描
扫描有数据但新对话不召回是否只扫描、集成是否安装安装 Hook/plugin/Skill 并重启 Agent
记忆少于消息回合完整性和大小限制检查跳过/失败记录
源码启动卡住是否在无图形服务器运行桌面脚本服务器先只启动 Memory 服务

源码一键脚本适合有图形会话的开发机。无桌面的 VPS 不要直接启动 Electron/Vite 桌面壳，应先使用 memory:serve:dev 启动 Memory，再按实际需要启动后端。

12

安全与隐私：本地优先不等于无需检查

默认数据目录是 ~/.memmy，其中包含配置、工作区、本地 SQLite 数据库和运行时文件。Memory HTTP 可以通过 MEMMY_MEMORY_TOKEN 或 MEMORY_SERVICE_TOKEN 设置 Bearer token；配置文件支持 ${ENV_NAME} 引用，以避免把 API key 直接写入 YAML。

  • 默认只绑定 localhost，不要把 18960、18980 或 18990 直接映射到公网。
  • API key、token、password、Cookie、私有仓库凭据和连接字符串不得写入测试记忆、截图或公开信息卡。
  • 安装 Hook、plugin 或 Skill 前先查看它会写入哪些 Agent 配置文件。
  • 移除集成不会自动删除已导入历史；清空本地数据是另一个显式动作。
  • 共享电脑或多人环境要区分 user-id、配置路径和数据库目录。
  • 自动召回内容只当线索：来源、时间、项目绑定和原始文件都要能回查。

不要因为本地两个字就把所有工作区、客户项目和私人对话一次性导入。先选择一个非敏感项目，确认数据路径、来源标记和删除方式后再扩大范围。

13

从一个项目开始的 30 分钟实践

  1. 准备一个不含凭据的示例项目，写下目标、当前状态、关键决定、产物路径和下一步。
  2. 完成安装和 onboard，确认 status 与 health 均正常。
  3. 用 memmy-memory add 写入一条项目规则，再用 search 验证。
  4. 在 Cross-Agent access 中只扫描一个 Agent 来源。
  5. 安装该 Agent 的 Hook 或 plugin，重新打开新会话。
  6. 提出一个需要历史上下文的问题。
  7. 打开记忆详情，检查来源、时间、原始内容与推断内容。
  8. 把错误召回、重复记录、漏掉的产物和错误绑定写入复盘表。
项目恢复问题模板：
请只基于可回溯的历史，整理：
1. 原始目标；
2. 已确认的关键判断及其变化；
3. 已产生的文件、文档或发布物；
4. 当前未完成项；
5. 下一步建议。
请把历史明确写过的内容和根据上下文推断的内容分开，并标注来源与时间。

这个模板强制 Agent 把事实、推断和行动分层。你可以逐项对照仓库、文档、任务记录和发布页面。

14

如何判断 Memmy 值不值得长期使用

问题如果答案是“是”建议
经常切换 Agent是验证跨 Agent 扫描和来源标记
需要恢复旧项目是测试 search/get 与恢复模板
在意数据本地可控是检查 ~/.memmy、SQLite、token 和删除流程
只想要简单单机笔记是先比较普通项目文档是否够用
需要公网共享记忆是先审查安全模型，localhost 不等于多端同步
不愿维护 Hook/plugin是从按需 Skill 和手动 search 开始

Memmy 的价值随着工具数量、项目数量和时间跨度增长而增加，但复杂度也增加。它最值得投入的场景，是你已有大量分散在不同 Agent 中的工作历史，并且愿意为来源、权限、清理和验收建立规则。若只是保存几条稳定偏好，一个项目级 README 或版本化知识库可能更简单。

把记忆当成基础设施，而不是魔法

  • 先验证服务、来源、端口和数据路径，再相信召回内容。
  • 先接一个 Agent，再逐步增加扫描源和实时集成。
  • 本地优先不代表可以忽略密钥、权限和删除流程。
  • 把来源、时间、原始文件和下一步一起记录下来。
