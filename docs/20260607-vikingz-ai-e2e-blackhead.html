01 · 核心洞察
why spec-first
✗ 不行
先写 E2E 再做 UI
  • E2E 依赖真实 DOM 结构（选择器在 UI 成型前根本写不了）
  • 三个框架渲染方式不同，同一选择器可能只在一个框架有效
  • 界面前改了，选择器白写
✓ 正确
BDD 思维 + UI 后写
  • 先想清楚验收标准（Spec）
  • UI 成型后用 agent-browser 拿可靠选择器
  • Playwright 一次成功，三框架高度复用
结论：E2E 测试是"核心流程必须 100% 覆盖"的保障，不是"先写测试再倒推 UI"的驱动方式。顺序反了就是浪费。
02 · agent-browser 的价值
why agent-browser
问题

传统 Playwright 给 AI 喂 DOM 树太重了。

  • DOM 树几千到上万 token，极快占满上下文
  • 选择器（CSS selector）常脆，一改就挂
  • token 消耗大，每次跑都浪费
解法

agent-browser（Vercel Labs）：语义化 Accessibility Tree。

  • 只保留交互元素，压缩 80%+ token
  • 用 `@E_1`、`@E_4` 简洁引用代替 CSS 选择器
  • 自然语言指令理解好，AI-First 设计
# agent-browser 返回示例——只有交互元素，无 DOM 树 - textbox "输入提示词" [ref=E_1] - button "选择文件" [ref=E_2] (上传按钮) - combobox "模型选择" [ref=E_3] (下拉框) - button "开始生成" [ref=E_4] # 交互采用 ref，不写 CSS 选择器 agent-browser click @E_4
03 · 为什么 E2E 不在 CI 上跑
local-only
慢

全量 E2E 跑完一个 app ≈ 6 分钟。

  • 三个 app → 18 分钟
  • 再加两个 DB → 36 分钟
  • CI 排队这么久不划算
依赖多

支付测试需要 Stripe CLI 等环境变量。

  • 多平台环境变量配置麻烦
  • CI 上配这些要么麻烦，要么不安全
分工

CI 管"快反馈"，E2E 管"流程完整性"。

  • CI：typecheck + build 够快
  • E2E：本地跑，发版前全量检

05 · 完整流程图（原文复刻）
original flow
┌─────────┐ ┌─────────┐ ┌──────────┐ ┌─────────┐ ┌─────────┐ │ SPEC │──▶│ CODE │──▶│ VERIFY │──▶│ TEST │──▶│ GREEN │ │ 定义验收 │ │ 实现功能 │ │ 视觉确认 │ │ 写 E2E │ │ 全通过 │ │ 标准 │ │ │ │ │ │ 测试 │ │ │ └─────────┘ └─────────┘ └──────────┘ └─────────┘ └─────────┘
SPEC

在 tests/e2e/TEST-CATALOG.md 写验收标准

  • 自然语言描述：打开哪页 → 点哪里 → 期望什么
  • 结构化字段补充：优先级、文件路径、上下文依赖
  • BDD 思维，但不写测试代码
CODE

按清单实现功能，保持三个 app 一致

  • 互相复用逻辑放 libs/*
  • 路由层尽量薄
  • 三个 app 的测试代码基本一样
VERIFY

agent-browser 走完真实流程

  • 拿到可靠的元素引用和 DOM 结构
  • 选择器成功率极高，一次稳定
TEST

写 Playwright E2E，UI 已确认再动手

  • 选择器从 VERIFY 阶段获取
  • 三个框架复用，只需少量调整
