01 · POSITIONING

它解决的不是“有没有任务”，而是“AI 是否理解并正确完成任务”

最适合代码仓库内的需求拆解与实施控制；用清晰任务边界缩小 Agent 的上下文和代码改动范围。

A

任务成为项目资产

每个任务都是版本化的 Markdown 文件，需求背景、验收标准、计划、评论和完成摘要可长期回溯，不埋在聊天记录里。

B

实施前先纠偏

先审任务定义，再审代码库研究后的实施计划。误解仍是一句话时就修正，避免做完大批代码后返工。

C

一任务一上下文

鼓励把工作切成单个会话可完成的尺寸：一个任务、一个上下文窗口、一个 PR，便于验证、重跑和审查。

02 · REVIEW LOOP

推荐的人机协作闭环

关键原则：Agent 不能从模糊想法直接跳到编码；每一阶段都要形成可检查工件。

① 描述目标业务问题、用户、边界
② 拆分任务描述、依赖、里程碑
③ 审验收标准结果是否明确可测
④ 审实施计划研究代码后再批准
⑤ 实现与验收测试、PR、总结、归档

05 · COMPETITOR LENS

竞品最值得借鉴的能力

如果用 Backlog.md 建立方案，下面这些能力应通过规则、脚本或外部平台补齐。

Task Master AI

PRD 自动任务化

从需求文档生成任务、依赖、优先级、测试策略；对复杂任务继续展开，并随方案变化更新后续任务。

Beads

依赖图与任务领取

自动识别无阻塞任务，多 Agent 领取、关闭后释放阻塞，降低并行重复和长周期上下文丢失。

GitHub Projects

Issue—PR 闭环

父子 Issue、阻塞关系、自定义字段、Roadmap、自动化、评论通知与 PR 状态双向同步。

Plane / OpenProject

周期与治理

Cycle、Intake、跨项目路线图、甘特图、关键依赖、工时成本及正式汇报，覆盖管理层视角。

06 · DECISION ROUTER

按真实工作方式选，而不是按功能数量选

功能越多并不等于越适合；先判断任务数据放在哪里、谁在使用、需要管理到哪一层。

01

想让 Codex / Claude Code 按任务稳定执行

重视 Markdown、本地文件、Git 审查、验收标准和低维护成本。

→ 选择 Backlog.md
02

有 PRD，希望 AI 自动规划和深度拆解

重视复杂度分析、自动展开子任务、测试策略和动态更新后续计划。

→ 选择 Task Master AI
03

多个 Agent 长期并行，依赖关系非常复杂

重视任务图、可执行队列、任务领取、跨机器同步与持久记忆。

→ 选择 Beads
04

多人协作，需要路线图、权限、通知或成本

研发协作用 GitHub Projects / Plane；企业周期、资源与预算治理用 OpenProject / Jira。

→ 选择团队项目平台

08 · ADOPTION PATH

推荐采用路径

先建立任务质量，再增加自动化；不要在流程尚未稳定时引入最重的工具链。

阶段一：最小闭环 1–2 周

  • Backlog.md + Git + 一个 Agent
  • 统一任务模板、验收标准和 DoD
  • 一任务一会话、一任务一 PR
  • 记录依赖、计划和完成摘要

阶段二：自动化 复杂后

  • 增加任务拆解提示词与检查规则
  • CI 校验任务字段与验收完成情况
  • 必要时接入 Task Master 或 Beads
  • 生成周期报告和依赖视图

阶段三：团队治理 多人后

  • 高层任务同步 GitHub Projects / Plane
  • 建立负责人、周期、优先级与里程碑
  • 保留 Backlog.md 作为 Agent 执行账本
  • 需要预算资源时再引入企业平台
结论基于公开官方资料整理；能力为资料证据，未在你的具体项目环境中实测。
