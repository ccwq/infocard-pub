让 Agent 画出可读、可验收的 SVG 架构图

svg-diagram 不是自动布局库，而是一套给 coding agent 的手工 SVG 规范：用字号推导框高，用 C/Q 曲线代替直角折线，用固定间距和箭头清除规则避免“字跑偏、线穿框、箭头贴边”。完成后的 SVG 再由零依赖 svg-lint 检查。

几何规则：把“看起来差不多”变成数字

GEOMETRY
对象规则为什么验收
viewBox上下左右推荐留 20–25px；标题也算内容防止嵌入文档时贴边或被裁剪边界距在范围内且左右/上下合理

04

连线规则：直线只服务于共轴关系

CONNECTORS

用 L 的情况

两个端点水平或垂直共轴，使用直线 L。例如同一行的服务 A → 服务 B。

<path d="M185,70 L 209,70" marker-end="url(#arrow)"/>

用 C / Q 的情况

路线需要转弯、绕开框或表达回环，使用平滑的 C / Q 曲线，禁止直角 elbow。

<path d="M100,100 C 100,150 150,200 200,200"/>

控制箭头方向

orient="auto" 会跟随路径末端切线；想让箭头向右，曲线第二控制点的 y 应与终点 y 对齐。

cp2.y = end.y cp2.x < end.x
回环线要后画：普通连线在框之前画；必须跨越多个框的 iteration loop-back 线最后画，否则会被框遮住。
05

文字、颜色与 XML：最容易被忽略的三道门

SAFETY

估算 CJK 宽度

12px CJK 字符可按约 12px 估算，不能沿用拉丁字母约 7px 的宽度。放置前先算右边界，确认不会侵入邻框。

语义色而非随手取色

输入/主流程、处理中、数据输出、AI/分析、敏感/警告各使用一组 fill/stroke/text 三元色。颜色表达状态，不只是装饰。

外部文本先转义

SVG 是 XML。来自 API、数据库或用户输入的 &、<、> 必须转义，否则整张图可能无法解析。

Load &amp; Save x &lt; 10
06

lint gate：从最终 SVG 找到可修复的具体错误

VERIFY

运行命令

node tools/svg-lint/bin/svg-lint.mjs diagram.svg node tools/svg-lint/bin/svg-lint.mjs diagram.svg --json

工具零依赖，读取完成后的 SVG，而不是中间结构。

检查什么

  • XML escaping
  • viewBox clipping
  • font stack
  • box height / baseline
  • arrow markers
  • text overflow / overlap

什么才算通过

0 errors, 0 warnings。README 的示例说明：警告也算失败；每条 finding 会给出检查 ID 和建议修复值。

# 维护者检查（仓库 package.json） npm run lint:svg:all npm test

08

适用边界、许可证与维护成本

BOUNDARIES
它不是自动布局引擎：坐标由 Agent 按规范手工放置，复杂图仍需要人检查语义、密度和视觉平衡。

它不是业务事实校验器：linter 能发现几何、转义和样式问题，但不能判断“服务 A 是否真的调用服务 B”。

它不是全自动门禁：README 明确 svg-lint 需要维护者手动运行；仓库测试脚本也要求显式执行。

许可：仓库 MIT。仓库代码许可不自动覆盖你放入图中的 Logo、字体、第三方图片、数据或文档内容。

适合：架构图、流程图、时序图、数据流、生命周期和 A/B 基准流程；不适合仅有两三步的简单列表，除非你确实需要图形关系。
09

迁移到自己的团队：把一次修图变成规则资产

ADOPTION

第一周

只选一个真实文档图，要求 Agent 先给内容模型，再画 SVG；把 lint 输出和人工修改点记录下来。

第二周

把团队常用字体、颜色三元组、目录和命名写进项目约定；让 CI 对正式 SVG 执行 lint:svg:all。

持续维护

业务结构改变时同步更新图；不要保留与正文矛盾的旧 SVG。用文本 diff 审查坐标改动，而不是只看重新渲染的图片。

最终动作：先让 Agent 画一张 3–5 节点图，确认它能通过 lint，再逐步增加分组框、回环线、CJK 长标签和失败分支。
