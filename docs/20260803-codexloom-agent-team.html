CodexLoom：把 Codex Thread 织成长驻 Domain Agent 组织

不是“再开几个聊天窗口”，而是把线程、身份、上下文、协作与产物，编排成可长期驻留的个人 Owner 组织层。

结论先行Go + Reactlocal-first / self-hostedactive development
一句话结论 / BOTTOM LINE

CodexLoom 是建立在 Codex 之上的组织化工作台：它试图把一次性的 Codex Thread 变成长驻、可识别、可协作的 Domain Agent 空间；方向清晰，但当前仍受 Codex experimental APIs 与项目自身 active development 状态约束，不能据此宣称生产就绪。

03

CodexLoom 解决什么PROBLEM FRAME

Codex 的 Thread 适合完成一次任务；Domain Agent 需要的是“持续可找、持续可交接、持续有边界”的工作空间。

从线程到身份

稳定 ID、名称与 Profile，让一个长期角色不再只存在于某个聊天记录里。

从上下文到组织

Primary Thread、Messages、Topics、Needs You 与 Artifacts 形成可回看的工作面。

从个人到协作

Organization、Collaboration、Activity maps 与 Interface Agents 提供跨入口协作层。

安全边界：这些是项目 README / Owner Guide 描述的产品机制，不等于已经验证了多租户隔离、权限模型、可靠性、审计性或企业级 SLA。
04

长期 Domain Agent 机制OBJECT MODEL / LONG-LIVED WORKSPACE

Domain Agent长期驻留的组织单元
Profile稳定身份与角色设定
Primary Thread主工作线程
Team协作边界与成员
Message沟通与事件记录
Topic主题化组织上下文
Artifact工作产物与交付物
Interface AgentFeishu / Slack / Parall 接口
对象项目叙述中的作用读者应如何理解
Domain Agent长驻的领域工作空间与组织单元不是“人格已经自主运行”的证明，而是长期任务容器。
Profile / ID / Name为 Agent 提供稳定识别与配置入口支持找回、管理、复用；具体持久化细节以实现为准。
Primary Thread每个 Agent 的主要工作线程把持续上下文锚定在一个主线，而非散落在临时会话。
Team / Message / Topic团队协作、消息沟通、主题归档把“谁在做什么、讨论过什么”变成可导航结构。
Artifact承载 Agent 产出的文件或结果适合交付追踪，但不自动等同于版本控制或质量验收。
Interface Agent对接 Feishu、Slack、Parall 等外部接口是连接器/接口层的产品方向；权限、失败重试与数据边界仍需实测。

从创建到协作：工作流WORKFLOW / OPERATIONAL LOOP

1

启动本地服务

构建 release 后运行二进制，默认 WebUI 地址为 localhost:4870。

2

创建 Agent

以 Domain 为单位创建长期工作空间，为它设置名称、稳定身份与 Profile。

3

绑定主线程

设置 primary Thread，把任务上下文、Messages 与 Topics 聚合到持续工作线上。

4

组织团队与接口

通过 Team、Collaboration 与 Interface Agents，把人和外部消息入口接入 Agent 组织。

5

沉淀产物与活动

把 Artifacts、Activity maps 与 Needs You 作为交接、追踪和下一步行动的可见层。

风险

部分能力依赖 experimental APIs

项目 README 明示部分能力依赖 Codex experimental APIs。这意味着上游 API 变动可能影响功能、兼容性与维护成本。

  • 当前应把 Codex 看作必要基础设施，而不是可被 CodexLoom 完全隐藏的实现细节。
  • 需要进一步核实的项目级问题包括：版本矩阵、API 兼容策略、升级回滚、离线能力、凭据存储与跨入口状态一致性。
  • 不要把“能启动 WebUI”解释为“已经具备生产级运行保障”。
