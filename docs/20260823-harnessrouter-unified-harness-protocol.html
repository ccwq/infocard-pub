核心思想：上层只面向稳定的“会话 + 事件 + 工具能力”语义；下层再把同一请求翻译成各 Harness 的命令、SDK 或远程 API。新增 Harness 时，扩展 adapter，不重写业务编排。

02 / 问题

每个 Harness 有不同的启动方式、参数、事件格式和认证边界。

流式输出、取消、文件传输、超时与失败重试常被散落在业务代码里。

多代理编排被“分别对接”锁死：换工具等于重做集成。

03 / 方案

统一请求面：创建/恢复 session，发送 prompt，订阅事件。

统一控制面：files、cancellation、failure handling 作为一等能力。

适配器隔离：各 Harness 的怪异性留在边界内。

05 / 核心能力

Sessions

统一创建、恢复、关联上下文，避免调用方理解各家 session id。

Streaming

把增量文本、工具事件、状态变化规整为可订阅事件流。

Files + Cancellation

文件输入输出与主动终止走同一生命周期，不再依赖私有 hack。

06 / 分别对接 vs 统一协议

分别对接

n 个 Harness × m 个业务

重复认证、事件转换、重试与观测；升级成本随组合数增长。

VS

UHP + Router

n 个 adapter + 1 个稳定契约

业务只实现一次；接入新 Harness 主要集中在适配层。

07 / 安装与使用：先把入口跑通

确认项目与版本
访问 harnessrouter.ai，按仓库 README 选择对应发行方式。
配置 Harness adapter
为 Codex / Claude Code / Hermes / OpenClaw 配置 endpoint、认证与工作目录，保持 provider 密钥在服务端或安全环境。
以 UHP 语义调用
客户端只关心 session、prompt、event stream、file 与 cancel；不要把某个 Harness 的私有参数泄漏到业务层。
// 概念调用（字段名以当前发行版 API 为准） const session = await router.sessions.create({ harness: "codex" }); await router.sessions.prompt(session.id, { text: "inspect this repo" }); for await (const event of router.events(session.id)) { if (event.type === "delta") process.stdout.write(event.text); if (event.type === "failure") await router.sessions.retry(session.id); }

08 / 适用边界

适合：需要同时编排多个 coding / agent harness、统一观测与中止控制、或希望把 provider 切换从业务中隔离的团队。

注意：统一协议统一的是生命周期与交互语义，不会抹平模型能力差异、权限策略和每个 Harness 的独特工具集；上线前应逐项核对 adapter 的版本、权限和失败语义。
