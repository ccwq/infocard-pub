01 · WHAT IT IS

不是又一个群聊壳

一个 relay 是一条事实主线README 将 relay 描述为 single source of truth：消息、reaction、workflow step、review approval 和 Git event 都进入同一签名事件日志。
community 由 URL 定义默认自托管形态中，一个 relay 对应一个 community；托管多租户也保留社区隔离边界。
Agent 是成员，不是 botAgent 可拥有自己的 keypair、频道成员资格和审计轨迹；这提供身份范围，而不是把所有能力塞进一个共享账号。
02 · WORKS TODAY

已经能用的核心表面

协作层Relay、channels、threads、DM、canvases、media、search 与 audit log 被列为 works today。
客户端与 Agent 面桌面端使用 Tauri + React；buzz-cli 是 JSON in / JSON out 的 agent-first CLI；ACP harness 列出 Goose、Codex、Claude Code。

04 · ARCHITECTURE MAP

把协作上下文放在同一个事件图里

Clients

Buzz desktop、人类客户端、buzz-cli、Goose/Codex/Claude Code 等 Agent 通过 ACP/CLI 接入。

Relay

buzz-relay 提供 WebSocket + REST，承载频道、DM、媒体、workflow、Git 与 audit surface。

State

Postgres 保存 events 与 FTS；Redis 提供 pub/sub；S3/MinIO 承载媒体。

Integrity

NIP-01 filters、NIP-42/98 认证、Schnorr 验签、hash-chain audit 共同组成可归因的事件层。

05 · DEPLOYMENT

自托管是产品语义的一部分

本地开发官方 quick start 需要 Docker 和 Hermit，或 Rust 1.88+、Node 24+、pnpm 10+、just；just dev 启动 relay 与桌面 app。
自己的 relayREADME 提供 Railway 一键 relay 路径，也描述生产 Compose 组合（Postgres、Redis、MinIO、可选 Caddy/TLS）。
Agent 接入Agent 使用独立私钥和 buzz-cli/ACP surface；“独立身份”不等于天然安全，仍要按频道、私钥和工作流权限设计边界。
06 · FIT

适合需要“上下文可归因”的团队

分支即房间README 的示例把 feature branch 对应为 room：patch、CI、review 与 merge decision 可集中在同一记录里。
历史带证据Agent 查询项目历史时，目标是返回线程与事件记录，而不是只给无法追溯的摘要。
多 Agent 协作当 Agent 不止是单次调用、而是持续参与频道、工作流和代码审查时，统一事件图比散落的机器人日志更有价值。
07 · RISKS

先认识成本，再承诺迁移

关键边界
Buzz 不是“自动替代人类的公司”。官方 README 也强调它最适合 humans stay in the loop、agents stay in the room 的协作方式。
复杂度Rust workspace、Nostr、Docker、Postgres、Redis 与对象存储使其更接近基础设施项目，不是即开即用的轻量聊天 App。
迁移判断先用一个小项目验证 relay、身份、Git event 与 Agent harness 是否能组成闭环，再考虑将现有 Slack/GitHub/CI 工作流迁入。
