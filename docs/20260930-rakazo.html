COMPUTER · 电脑机制
PAGE 02

COMPUTER 电脑机制

Team 电脑共享干活，私有电脑隔离隐私

01
Team Computer（默认）

每个工作区一台，bot 共享文件与工具。Team bot 起始于 bots/<bot-id>/、共享件放 shared/——文档原话：这些文件夹「组织工作但不是安全边界」，每个 Team bot 都能访问整个工作区。

02
Private Computer

整个工作区就是它的 home；涉隐私的活（私人邮箱/账务）文档建议单独配。

浏览器持久化：每个活跃 bot 独立 X display + Chrome 进程 + 按 bot 身份隔离的持久 profile——登录、cookie、历史互不可见，不克隆不合并；重开 bot 沿用原 profile。并发靠 per-bot 数据库租约：多 bot 可同时干活，一个 bot 同时只有一个 driver。单机可承载 100+ bot profiles。

SECURITY · 边界
PAGE 03

SECURITY 边界

默认全通，敏感场景要手动收紧

Docker 电脑默认全出站：公网 + Docker 宿主地址 + 局域网 + 云厂商的链路本地元数据端点（link-local metadata endpoint）——最后这条在云 VM 上等于把实例凭证暴露给 bot 跑的任何东西。

Restricted 模式（opt-in）：保留公网出站（浏览/DNS/apt/git over SSH），切断所有非公网目的地与主机流量。

资源上限每台默认 2g 内存 / 2 CPU / 2048 PIDs，可调可解除；配错了启动时就报错，不会变成 bot 跑着跑着才炸。

INSTALL · 四条命令
PAGE 07

INSTALL 四条命令

装好 Docker 就够了，不用 clone 不用 Node

mkdir -p rakazo && cd rakazo && curl -fsSLO https://raw.githubusercontent.com/elie222/rakazo/main/infra/compose/install-images.sh && bash install-images.sh

安装脚本下载 Compose 文件、生成带随机密钥的 .env（重跑保留已有配置）、启动服务。前置只有 Docker Engine + Compose 插件 + curl + OpenSSL。打开 http://127.0.0.1:5173 注册账号、连模型即用；本地 Docker 电脑默认开启。

源码开发路线才需要 Node 22.22+/24.x/26+（23/25 不支持）+ pnpm 9 + Postgres。镜像默认 tag edge，amd64+arm64 双架构。

SERVER · 24 小时在线
PAGE 08

SERVER 24 小时在线

bot 要常驻，后端就得在服务器上

同一脚本三步变生产部署：--prepare-only 生成配置 → 编辑 .env（SANDBOX_PROVIDER、RAKAZO_HOST=你的域名）→ 正式启动。桌面/手机端选 Existing instance 填 https 地址连回去。

硬要求：公网服务必须 HTTPS（文档给了 Caddy 配置与主机加固清单），HTTP 只接受本机回环与私网地址。备份一条命令 ./scripts/backup.sh（pg_dump + data/ 归档，失败即非零）；升级按 tag 拉镜像 up -d --wait。警告：docker compose down -v 会删光全部 Postgres 状态。

DEPLOY 七步跑通

从空机器到能用的完整序列

① 装前置Docker Engine + Compose 插件 + curl + OpenSSL，四样齐再往下

KEYS · 五个必填键
PAGE 12

KEYS 五个必填键

脚本替你生成的，别自己抄重

POSTGRES_PASSWORDopenssl rand -hex 16 · Compose 内 Postgres 密码，必须 URI 安全
BETTER_AUTH_SECRETrand -hex 32 · 会话签名
ENCRYPTION_KEYrand -hex 32 · 落库凭据的加密钥匙
SCREEN_PROXY_SECRETrand -hex 32 · 签发短时 /novnc/* 看屏能力
SANDBOX_SUPERVISOR_TOKENrand -hex 32 · API ↔ 沙箱监督进程互认

四条铁律：上面这几个必须各自独立（含可选的 RAKAZO_UPDATER_TOKEN，≥32 字符且与前面都不同）；.env 永不入库、永不贴进 issue/PR；没有备份和操作者同意不得覆盖已有 .env；存过凭据之后再轮换 ENCRYPTION_KEY，旧密文直接读不出来。空键会在 Compose 校验阶段 fail closed（${VAR:?Set …}）。

PROVIDER · 电脑放哪
PAGE 13

PROVIDER 电脑放哪

一个环境变量决定 bot 的电脑住哪

docker（默认）栈内监督进程按 RAKAZO_COMPUTER_IMAGE 起兄弟容器；要 Docker socket
none只跑 API/Web，不给 bot 配电脑；仍要 SANDBOX_SUPERVISOR_TOKEN
e2b托管沙箱，需 E2B_API_KEY
daytona需 DAYTONA_API_KEY，可选 DAYTONA_API_URL/_TARGET/_SNAPSHOT
box需 BOX_API_KEY，可选 BOX_API_URL

验证方式只有一条：curl -fsS http://127.0.0.1:3100/internal/health 里看到 sandbox: docker。文档明说——监督令牌缺失属于 setup failure，不能把 sandbox: "none" 当成这条路径成功。远端 provider 也不能替代 Postgres 与 Web UI。补充：注册和本地 Docker 电脑不需要任何 E2B 类账号。

LIMITS · 每台电脑的硬上限
PAGE 14

LIMITS 每台电脑的硬上限

三行环境变量管住一台电脑

RAKAZO_COMPUTER_MEMORY默认 2g，写法 1536m 或字节数；下限 6m；同时给 swap 封顶，所以天花板是真的
RAKAZO_COMPUTER_CPUS默认 2，可以是小数如 1.5
RAKAZO_COMPUTER_PIDS_LIMIT默认 2048，正整数

配套还有两条出网开关：默认全开（含云厂商链路本地元数据端点）；云 VM 上建议跑 sudo bash infra/compose/restrict-computer-egress.sh 切到 Restricted egress，撤掉这些规则用同脚本 --remove。规则按接口名匹配而不是网段——所以不会因为改子网而意外放开。

OFFLINE · 镜像与断网环境
PAGE 15

OFFLINE 镜像与断网环境

GitHub 和镜像仓库拉不动怎么办

这套脚本专门为受限网络做了开关：换源用 RAKAZO_INSTALLER_URL（脚本本身）+ RAKAZO_DOWNLOAD_BASE（Compose 文件）；只收非 HTTPS 会被拒、尾部斜杠自动裁、下载带有界重试。

镜像拉不动就逐个覆盖：应用 RAKAZO_IMAGE/RAKAZO_IMAGE_TAG、电脑 RAKAZO_COMPUTER_IMAGE/RAKAZO_COMPUTER_IMAGE_TAG、Postgres 与 busybox 走 POSTGRES_IMAGE/BUSYBOX_IMAGE 或给 Docker 守护进程配 registry-mirrors。想复用已下好的文件：把 docker-compose.images.yml 与 .env.images.example 放进目录后跑 bash install-images.sh --local --prepare-only，等价于 RAKAZO_DOWNLOAD_SKIP_EXISTING=1；缺什么仍会自动补下。注意：模型与远端电脑 provider 依旧需要出网。

UPDATE · 升级与回滚
PAGE 16

UPDATE 升级与回滚

升级不留半条命

手动路线：按 tag 拉镜像后 up -d --wait——它要等新 API 健康、worker 与 web 容器也起来才算成功。updater 是可选的侧车 profile（独立镜像与 tag，跑在私有 control 网络，暴露 /health /state /plan /apply /rollback，除 /health 外全部要求共享 bearer 令牌并做常量时间比较）：它会重启栈、等 https://$RAKAZO_HOST/health、失败就回滚。两个坑：CLI 重建失败不会自动回滚，得自己用上一个 tag 恢复；sidecar 持有 Docker socket 等于宿主机 root 权限，所以只给它专属令牌与最小文件清单。GIT_SHA 传了，/internal/health 才会报 revision。

SECRETS · 可复用凭据
PAGE 17

SECRETS 可复用凭据

让 bot 自己用 key，但看不见 key

你对 bot 说「连一下这个 API」，它调 request_secret 并给出引用名和 HTTPS 服务 origin——受保护的卡片会先把 origin 亮给你看，再让你填值。Web、桌面、手机共用同一后端；提交开始后输入框即清空，值不进消息、事件与模型输入。

值用部署的 ENCRYPTION_KEY（AES-256-GCM，记录级认证）加密存在 Postgres 的 bot_secrets；只有这个 run 的用户能提交，凭据归属该用户/空间/bot，跨 run 存活，随三者删除而删除。list_secrets 只返回名称、目标与鉴权配置这些元数据，不含值。

鉴权三型Bearer · 自定义头（{"type":"header","name":"X-Api-Key"}）· Basic（受保护值当密码，用户名自填）
调用约束origin 必须精确匹配含端口；重定向与不安全网络目标一律拒绝；30 秒超时；响应 ≤1 MB；只回 20,000 字符脱敏正文且不带响应头
配额每个用户、每个 bot 最多 100 条；单值上限 16,384 字符；换 origin 或鉴权方式前必须先删旧值；同名同配置再调 request_secret 直接返回已存引用，加 "replace": true 才换值
LOGIN · 网站登录代持
PAGE 18

LOGIN 网站登录代持

账号密码存一次，之后它自己登

登录用 request_secret 且 auth.type = "login"，卡片收用户名 + 密码，同样加密落库、模型两者都看不到。登录时 bot 先用 browser_snapshot 找到输入框，再用 fill_secret 依次填 username / password 后点提交。

防串站后端解密后，只有页面此刻仍在保存的 origin 上才键入——登录不可能被填进别站或跳转后的页面
强制 HTTPS网站登录的 origin 必须 https；RAKAZO_SECRETS_ALLOW_PRIVATE_HTTP 对它不生效
传递通道值经 stdin 送到电脑（不落命令行参数，避免出现在进程列表）；字段只填 type 为 text/email/password/tel 的输入框
脱敏快照永不上报持有登录的字段值；页面文本里的密码会被洗掉，用户名 ≥6 字符也洗（短用户名不洗，因为替换会波及正常文本）
审批填表不需要额外审批——保存登录本身就是审批，且绑定单一站点；登录值不能用于 secret_request

二次验证码、CAPTCHA、passkey，以及你想自己登的站点，统一走 request_takeover——就是推文里说的「卡住会主动停下来找你」。

BOUNDARY · 边界别误读
PAGE 19

BOUNDARY 边界别误读

三条它做不到的防护

① 模型没有读值的工具，后端也会剥掉直接与常见编码的回声，但被授权的服务端仍会收到真值——redaction 挡不住一个刻意变换凭据的恶意服务，所以密钥要按最小权限签发。② 值最终键入真实浏览器，任何能读那个浏览器的东西（包括 bot 自己的 shell 经页面或调试端口）都可能读到已填字段——不进模型输入只防误泄，不防一个被策反的 bot。③ 这套机制只覆盖「认证类 HTTP 请求」：把凭据注入任意 shell 命令、文件或环境变量被明确排除，因为那些命令能直接读走。自托管可开 RAKAZO_SECRETS_ALLOW_PRIVATE_HTTP=1 允许私网/回环的 http:// origin（默认关，明文，同网谁都能读），但链路本地与云元数据地址始终封禁、公网 origin 始终要求 HTTPS。

PITFALLS 自建最容易踩的八个坑

上手前先读这八条

① 少写 SANDBOX_SUPERVISOR_TOKEN → 栈起不来，别把 sandbox:"none" 当通过；② 把几个密钥抄成同一个值 → 违反独立性规则；③ 存了凭据再轮换 ENCRYPTION_KEY → 旧密文永久读不出；④ 公网裸 HTTP → 只有回环与私网地址被接受，公网必须 HTTPS 反代；⑤ 以为 Team 电脑的文件夹分工是隔离 → 每个 bot 都能读整个团队工作区，私密任务另配 Private Computer；⑥ Docker 电脑默认出网全开 → 云 VM 上记得切 Restricted egress，否则等于把实例凭证摆在 bot 面前；⑦ 开了桌面版 SANDBOX_PROVIDER=desktop 却忘了它的命令跑在你自己的 OS 账户下；⑧ 把 .env 提交进仓库或贴进 issue。

FIXED · 值得记的修复

FIXED 值得记的修复

beta 里被修掉的真实故障

Bedrock 全崩走 Amazon Bedrock 的 Claude 模型每轮都失败，报 input_schema does not support oneOf, allOf, or anyOf at the top level——工具入参 schema 的顶层联合类型不被接受
工具太多被拒挂 20 个以上 MCP 工具、又用 Claude Pro/Max/Team 登录时会报「You're out of extra usage」；Pipedream 一次性暴露所有已连应用的工具，超过 20 个后连接器改为按需开放
推理模型空回推理模型的思考会占用与输出同一个上限，难题上可能出现「No response. Try again.」（32k 输出问题一并修掉）
开场静默新建 bot 的线程开局是空的且一直不吭声，导致 title/description/instructions 被读错也发现不了——现在会先自我介绍；介绍语运行期间发来的消息也不再由不能调工具的介绍语回答，而是排队等它结束
消息被吞同一线程里例程或入站 webhook 正在跑时发出的消息，会被折算进那一轮当 steering——现在独立处理
图片失忆早前消息里附的图片，在后续轮次提问时对能看图的模型不可见；现在只有当前轮次之外的也可见
CLOUD AGENT · 云端编码代理
PAGE 26

CLOUD AGENT 云端编码代理

把仓库任务外包给云端编码代理

这是和「bot 电脑」「线程内 subagents」并列的第三种执行路径：把仓库任务丢给托管编码代理，结果以状态与 PR 链接的形式回到 bot 会话里——Web、桌面、移动端看到的是同一份状态。默认 CLOUD_AGENT_PROVIDER=none，核心工作流不依赖 Cursor 或任何托管编码服务。

开启条件CLOUD_AGENT_PROVIDER=cursor + CLOUD_AGENT_SPACE_ID + CURSOR_API_KEY，API 与 worker 必须配同一份；key 与显式 Space ID 缺一不可
四个工具cloud_agent_launch / cloud_agent_status / cloud_agent_reply / cloud_agent_cancel；三个变更类走既有审批规则与自动审查策略——空规则集加关闭自动审查等于默认放行
发起参数prompt、可选仓库、图片、openPr；故意不支持传环境变量——把密钥放进模型生成的工具参数会把它留在普通历史里，远端密钥请在 provider 侧直接配
归属隔离每个 agent 额外绑定发起用户，别人拿到 agent ID 也查不到、回不了、取消不了；部署 key 永不作为模型工具参数传入
断线恢复归属与待办操作存在数据库里，与聊天卡片无关；worker 与对账器会恢复队列失败与中断的启动。Cursor 用稳定的 client agent ID，重试已接受的创建不会造出第二个远端 agent
不假装成功后续回复丢失时观察最新 run 而不是重发 prompt；在能区分出新 run 之前状态保持 pending，绝不说「旧 run 已完成」；取消同样在远端确认前保持 pending。结果长期不明就直接去 provider 站点看
自动收尾清空会话、删除或归档 bot、移除主人的 Space 成员身份，都会在下次对账时取消待办远端工作；终态通知按持久记录去重；key 或 provider 变化时凭据绑定 fail closed
VERIFY · 七层验收与性能基准
PAGE 27

VERIFY 七层验收与性能基准

确定性与真实模型分开测

仓库把「确定性执行回归」和「真实模型任务质量」明确分层：脚本化回应只能证明工具调用会正确执行，只有真模型才能证明它会为一句自然语言挑对动作。

pnpm test现有快测：产品函数与契约真实，agent、服务、沙箱用脚本替身
pnpm test:piPi 协议回归：agent 循环、HTTP/SSE 解析、工具派发，模型端点走回环
pnpm test:integrationPi 产品旅程：API、已保存的模型连接、Postgres、executor 全真
pnpm test:computer-replayDocker 电脑回放：supervisor + Chromium + 页面助手 + 下载与文件，对本地样例站点
pnpm test:evals --live真模型任务质量（需要显式本地命令）
pnpm test:computer视觉验收：真视觉模型 + Box 或 E2B 桌面

纪律：默认与 PR 测试永不需要付费推理；夜间只跑 web 测试且用仿真 provider；Docker 拓扑与浏览器回放走手动工作流；夜间验收绝不启动电脑沙箱、也绝不索取模型或沙箱凭证。桌面性能另有基准：pnpm perf:desktop -- --label=before（报告只落本地 .context/performance/，--samples=2 快速迭代、--asset-delay=80 配 --remote-renderer/--skip-build 对比打包与远端加载、macOS 用 --disable-warm-window 对比销毁重建与保留热窗），改完一处性能敏感行为再用 pnpm perf:compare 做前后对照。它测的是打包 Electron 里的生产 Vite 渲染器 + 一次性 Postgres + 脚本化运行时 + 假沙箱，既不碰 provider 账号也不碰生产数据。

MOBILE · 移动端数据同意
PAGE 28

MOBILE 移动端数据同意

手机端上传前先拿授权

移动客户端在上传附件、提交消息、启动例程或发送语音内容之前会先取得许可，同意记录按账号 + Space + 接收方 + 披露版本分别保存；只读的披露/授权端点不改变 provider 的执行路径，Web、桌面、worker、辅助模型选择与自托管服务端行为都维持原样。

覆盖范围许可包含从手机端显式启动的后台工作；撤回只对新的移动端操作生效，不会取消已授权的工作——要停正在跑的任务请用既有控件＋关例程
它不是不是全局数据访问或运行撤销系统；也没有引入网关黑名单、provider 路由覆盖或外部元数据请求
自建者开关自托管可用 PRIVACY_POLICY_URL 指向自己的绝对 HTTP(S) 政策页；不设则链接 Rakazo 的政策（该页会区分托管与自托管运营方）。未知的自定义 provider 不会凭空生成 provider 政策链接
发布顺序先迁移同意记录并部署 API，再放移动客户端——旧服务端没有披露端点就撑不起新流程，但既有 Web/桌面客户端与 provider 执行不受影响

文件里还有一条值得学的工程态度：发布门禁要求核对评审账号实际的模型、语音、记忆与云代理配置，并验证所选 provider 的协议、留存、删除与安全措施是否达到「同等或更强保护」——只有一个隐私链接不算证据；涉及 OpenRouter/Vercel AI Gateway 时要核实真实下游路由，因为对方的驳回要求的是「披露接收方并取得许可」，而不是一律禁用这类网关。
