为 AI 编程助手打造的本地上下文压缩代理。当你在 VS Code 里连续工作几小时后，Claude Code 或 Cursor 的对话历史已经膨胀到几十万 Token，模型 API 按输入 Token 计费，成本失控。更糟的是，超过上下文窗口上限后模型质量断崖下跌，摘要能力丧失，指令退化。billion-context 在请求到达真实模型前插入五步处理管线：解析请求 → 识别消息结构 → 压缩历史 → 注入压缩工具 → 转发并重写响应，将上下文稳定在 ~150K tokens，实测 Token 开销降低约 5 倍。内置 acp-kernel 压缩引擎（3 层 LSM-tree + 模型生成摘要），零运行时外部依赖，MIT 许可证。

痛点：长会话的上下文危机
编程助手在长时间任务中积累大量历史消息，Token 消耗呈非线性增长，而模型 API 按输入 Token 计费，成本失控。
超过上下文窗口上限后，模型输出质量显著下降，出现截断、遗忘早期需求、指令退化等问题。
Claude Code、ChatGPT Plus、Claude 订阅等硬编码端点的客户端无法修改 baseURL，无法直接指向压缩代理。

两种接入模式详解
模式一 · 零配置前缀（推荐）
在客户端将 baseURL 前缀改为 http://localhost:8787/bili/，代理自动识别 /bili/ 路径并启用压缩。前缀同时是自我检测信号——当客户端已内置压缩功能时，代理自动静默，避免双重压缩导致上下文损坏。
支持已验证的客户端：OpenCode（通过 x-session-affinity 标头识别会话）、Codex（API-key 模式，通过 body.session_id 识别）、Pi（无会话标识，存在碰撞风险 ⚠️）、Cursor、Aider、Continue。
OpenCode ✅Codex (API-key) ✅ Pi ⚠️Cursor ✅ Aider ✅Continue ✅
模式二 · MITM 透明代理
生成自签名根 CA 证书（存放于 ~/.local/share/billion-context/ca/root-ca.pem），对白名单内的 HTTPS 域名进行中间人解密，注入压缩逻辑。适用场景：硬编码端点的客户端。
白名单域名：open.bigmodel.cn / api.anthropic.com / api.openai.com / chatgpt.com。仅白名单内域名被解密，其他流量直接透传。ZCode 已实测可用；Claude Code 模式尚未测试。
ZCode ✅ 已实测 Claude Code ❓ 未实测 ChatGPT Plus/Pro Claude 订阅
压缩引擎 acp-kernel
核心架构：3 层 LSM-tree。第一层接收原始对话，第二层执行增长驱动的 Nudge 策略（上下文接近阈值时提示模型主动压缩），第三层由模型生成增量摘要替代原始消息，实现有损压缩。框架无关，零运行时外部依赖，23 个模块，acp-kernel 仓库另有 208 个独立测试，MIT 许可证。
三级调参优先级：全局 compress 配置块（最低）→ providers[url] 按提供商（中）→ models[model] 按模型（最高），最深层级配置优先覆盖。上下文窗口自动从 models.dev 注册表获取，回退内置表，全局默认 200K。
关键参数：nudgeGrowthTokens（触发 Nudge 的增量阈值）、modelContextLimit（单模型上下文上限）、maxContextLimit（全局上限）、preserveRecentMessages（保留最近 N 条不压缩）、minCompressRange（最小压缩窗口）、tiers（LSM 层数配置）。
注入控制：injectTool 控制是否向对话注入 4 个压缩工具（默认开启；ACP_COMPRESS_TOOL=0 禁用）；injectNudge 控制是否注入增长提示语（默认开启；ACP_COMPRESS_NUDGE=0 禁用）。

核心能力解析
Token 节省效果
3 层 LSM-tree 压缩将上下文稳定在 ~150K tokens；若放任膨胀至 1M Token，上游计费约增加 5 倍。压缩后 Token 量级降低一个数量级。
上游模型支持
Anthropic / OpenAI / DeepSeek / 智谱 (GLM) / 任意 OpenAI 兼容端点。支持 per-URL proxy 配置；mitm:// 与 https:// scheme 分流代理流量。
上下文窗口检测
自动从 models.dev 注册表获取各模型上下文上限；无匹配时回退内置表；全无匹配时使用全局默认值 200K。支持按模型覆盖：context = "70%" 或绝对数字。
持久化与会话
会话默认持久化至磁盘（BILI_PERSIST=1），LRU 驱逐上限 256 会话。磁盘为真相源，重启后会话历史不丢失。

常见问题
Q: 与 opencode-dynamic-context-pruning 有何区别？
acp-kernel 是独立的 MIT 实现，不源自 opencode-dynamic-context-pruning，拥有自己的 PipelineNode / processTurn / CompressionCore 架构。
Q: 压缩会导致信息丢失吗？
LSM-tree 第三层用模型生成摘要替代原始消息，属于有损压缩。最近 preserveRecentMessages 条消息保持不压缩以保护最新上下文。
Q: Pi 客户端为何存在碰撞风险？
Pi 没有会话标识字段，多个会话的请求可能被视为同一会话，导致上下文混淆。⚠️ 生产环境建议使用 OpenCode 或 Codex。
Q: 会话数据保存在哪里？
默认保存在 ~/.local/state/billion-context/（XDG 规范路径），磁盘为真相源，重启后不丢失。可通过 BILI_PERSIST=0 关闭持久化。
Q: 如何调试压缩行为？
设置环境变量 ACP_DEBUG=1 开启详细日志输出（写入 ~/.local/state/billion-context/bili.log，10MB 自动轮转）；或访问 Web UI http://localhost:8787/__bili/ 查看实时状态。
Q: 支持 DeepSeek 和智谱 GLM 吗？
支持。billion-context 通过 /bili/ 前缀或 MITM 模式均可代理 DeepSeek 和智谱 GLM 的 API 请求，只需将 baseURL 前缀指向本地代理即可。
Q: auto-update 机制安全吗？
启动时和每 3 分钟检查 npm 是否有新版本，检测到后自动全局安装。可通过 ACP_AUTO_UPDATE=0 完全禁用自动更新，或使用 bili update 手动触发。
