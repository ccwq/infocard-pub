痛点：长会话的上下文危机
成本失控：编程助手在长时间任务中积累大量历史消息，Token 消耗呈非线性增长，而模型 API 按输入 Token 计费。以一个 1M Token 上下文为例，放任膨胀后上游计费约是压缩状态的 5 倍。
质量断崖：超过上下文窗口上限后，模型输出质量显著下降：摘要能力丧失、遗忘早期需求、指令退化、截断频发。在 GPT-5.1-codex（400K）或 GLM-5.2（1M）等大窗口模型上同样存在，只是上限更高。
端点锁定：Claude Code、ChatGPT Plus、Claude 订阅等硬编码端点的客户端无法修改 baseURL，无法直接指向压缩代理，必须借助 MITM 透明代理模式。
会话混淆风险：部分客户端（如 Pi）没有会话标识字段，多会话并发时存在上下文碰撞风险，需手动传 x-acp-session 标头规避。

两种接入模式详解
模式一 · 零配置前缀（推荐）
在客户端将 baseURL 前缀改为 http://localhost:8787/bili/，代理自动识别 /bili/ 路径并启用压缩。前缀同时是自我检测信号——当客户端已内置压缩功能时（如 billion-context-pi），代理自动静默，避免双重压缩导致上下文损坏。
会话识别：Codex 通过 body.session_id（per-conversation UUID，最可靠）、OpenCode 通过 x-session-affinity 标头（ses_… 格式，安全）、Pi 无标识字段（碰撞风险 ⚠️，多并发建议手动传 x-acp-session）。

模式二 · MITM 透明代理
适用场景：硬编码端点的登录类客户端（ChatGPT Plus/Pro、Claude 订阅、ZCode 编程计划）。这类客户端通过 OAuth 登录，端点被写死在代码里，无法改 baseURL，只能靠 MITM 截获 HTTPS 流量注入压缩逻辑。
工作原理：生成自签名根 CA 证书（存放于 ~/.local/share/billion-context/ca/root-ca.pem），代理对白名单内的 HTTPS 域名进行 TLS 中间人解密，注入压缩逻辑后重新加密转发。OAuth token 仍在 Authorization 头中，订阅折扣完整保留。
白名单域名：open.bigmodel.cn · api.anthropic.com · api.openai.com · chatgpt.com。仅白名单内域名被解密，其他流量直接盲传（blind-tunnel），billion-context 永不解密非模型流量。

Plugin 插件模式（原生工具体验）
原理：在客户端安装一个 ~5KB 的薄插件（零外部依赖），它从代理获取工具 schema（GET /__bili/plugin/manifest），向客户端注册原生 MCP 工具，同时将执行请求转发回代理。代理仍是唯一的压缩权威（状态管理、历史折叠、nudge 策略），plugin 和 proxy 版本永远对齐，不会漂移。

压缩引擎 acp-kernel
核心架构：3 层 LSM-tree。第一层接收原始对话消息；第二层执行增长驱动的 Nudge 策略——当上下文接近阈值时，注入增长提示语提示模型主动压缩；第三层由模型生成增量摘要替代原始消息，实现有损压缩但保留关键语义。三层逐级蒸馏，上下文膨胀被压制在稳定区间。
框架无关，零外部依赖：acp-kernel 不依赖任何外部服务，23 个模块内聚完整，另有 208 个独立测试用例（位于 acp-kernel 仓库）验证各组件行为。MIT 许可证。
压缩增量由 nudgeGrowthTokens 控制：默认值 50000 tokens（1M 上下文窗口下），每次压缩触发后，模型生成新摘要，历史膨胀积累至此步长后再触发下次压缩，平滑阶梯式增长，而非瞬时压缩。
前缀缓存友好：摘要写入小范围块，可按需解压，cache prefix 完整保留。这意味着压缩后的上下文仍能利用模型的上下文缓存加速下一轮推理，不会因压缩而丧失已有的缓存收益。
上下文窗口自动检测：自动从 models.dev 注册表获取各模型上下文上限（GPT-5.1-codex=400K、GLM-5.2=1M、Claude Opus 4=200K……）；无匹配时回退内置前缀表；全无匹配时使用全局默认值 200K。可通过 context = "70%" 或绝对数字按模型覆盖。
调参三层级 · 字段详解
配置优先级（最深层级胜出）：全局 compress（最低）→ providers[url].compress（中）→ models[model].compress（最高）。每个字段独立合并，子级未设置的字段继承父级值（永不清除）。
字段 默认值 说明
modelContextLimit 注册表值 模型上下文窗口上限（压缩决策的分母）。接受绝对数字（200000）或百分比字符串（"70%"→140K）。⚠️ 缩小此值会将所有阈值（emergency/maxContext）同步下压，建议改 emergencyThresholdPercent 留 headroom 而非直接改此值。此字段优先级最高，覆盖注册表、内置表和 legacy context 字段。
maxContextLimit 0.75 (75%) 强制压缩触发阈值（使用率 = tokens / contextLimit）。超过此比例后无论增长量如何都会注入 nudge。接受数字（0.75）或百分比字符串（"75%"）。调低 → 更早压缩、更激进；调高 → 延迟压缩、更激进利用大窗口。
nudgeGrowthTokens 50000 每次 Nudge 的增量步长（tokens）。压缩约每积累这么多可压缩 tokens 触发一次。将此值调高 → 压缩频率降低、每次压缩幅度更大；调低 → 压缩更频繁、每次压缩更细粒度。1M 上下文下默认 50000，约 20 步走完一个完整窗口。
emergencyThresholdPercent 0.95 (95%) 紧急压缩阈值。超过此比例后，工具输出被硬截断以保会话存活（强制保命压缩）。必须 ≥ maxContextLimit。调低此值可提前进入紧急保命模式，但可能导致摘要质量下降。
preserveRecentMessages （无默认值） 最近 N 条消息永不进入压缩候选区。保护最新上下文不被误压缩。Pi 等无会话标识的客户端建议设高此值（如 8-12）以降低碰撞影响。
preserveRecentTokens （无默认值） 以 token 数为单位保护最近消息（与 preserveRecentMessages 二选一或叠加）。适合 token 量波动大的长会话场景。
minCompressRange （无默认值） 最小可压缩范围（tokens）。小于此值的压缩候选区直接跳过，避免无谓的压缩调用浪费 Token。
tiers true 启用多级蒸馏（T2/T2→T3）。设为 false 时退化为单级压缩，省去中间层但摘要质量可能下降。跨层级晋升由 nudgeGrowthTokens 驱动（token 累积量），而非按块数单独控制。
injectTool true 向对话注入 compress/decompress/search_context 工具 + 压缩系统提示语，使模型可手动触发压缩。设为 false → 完全自动压缩，无手动工具入口（env: ACP_COMPRESS_TOOL=0）。
injectNudge true 注入自动增长提示语（nudge 消息），提示模型在上下文增长时压缩。设为 false → 仅工具触发，适合安静的自动化环境（env: ACP_COMPRESS_NUDGE=0）。

会话识别机制与多并发
会话 ID 由四维哈希构成：协议 × 上游源 × API key × 会话标识。前三维防止跨账户/跨服务商污染，第四维来自客户端请求。
Codex (0.147+) ✅ body.session_id OpenCode ✅ x-session-affinity Pi ⚠️ 无标识 · 碰撞风险
Pi 的碰撞处理：Pi 没有会话标识字段，代理退化为对首条用户消息做哈希来合成会话 ID。如果两个会话以相同开场白启动，会被合并到同一压缩状态。这不会损坏数据（每条消息的内容指纹独立稳定），但会偏移压缩时机和偶尔过度回收区块。自愈设计：最坏情况是压缩效率降低，从不丢数据。多并发场景建议手动传 x-acp-session 标头。
Codex 子代理隔离：Codex 子代理（如 guardian_subagent 审批审核者）与主会话共用 session_id，线路上看起来是同一会话。billion-context 通过 instructions 字段区分：首个 instructions 值锚定主命名空间，后续不同 instructions 值映射到独立的 |sub: 子命名空间（拥有独立空压缩状态），Web UI 中显示为共用同一客户端标签的两个独立会话。
代理依赖性与会话迁移
关键事实：压缩状态（压缩块、摘要、原始消息缓存）存储在代理侧，不在客户端。客户端本地的历史记录是完整未压缩视图。
两个直接后果：
① 停代理或切回直连后，客户端回放本地全量历史 → 可能超过模型上下文窗口（context_window_exceeded）。长期会话不要突然中断代理。
② 无法将压缩块"解压"回填到客户端本地历史——客户端从未见过压缩形态。
迁移出代理的正确方式：用 bili export 将压缩状态导出为 Markdown 交接文档，再粘贴到新会话开头作为上下文：
bili export # 列出所有持久化会话（id / label / 块数） bili export <id> # 打印 Markdown 交接（摘要块） bili export <id> --full # 含原始消息的完整交接 bili export <id> --full --output handoff.md # 导出到文件
然后在客户端新建直连对话（无代理），将 handoff.md 粘贴为开场上下文即可完整迁移。
compress 工具执行流程详解
当对话上下文增长到阈值时，模型调用 compress 工具。工具执行发生在代理侧，流程如下：
①
范围识别：代理扫描对话历史，识别可压缩的消息范围（排除 preserveRecentMessages 保护的最近 N 条和 minCompressRange 以下的短范围）。
②
摘要生成：代理向同一模型发送摘要请求（in-process，不走网络），模型将指定范围内的消息序列压缩为一段摘要文本。摘要保留了关键决策、文件路径、工具调用参数、错误修复等核心信息。
③
历史回填：压缩后的摘要替代原始消息块写入对话历史。原始消息存入压缩缓存（供 search_context 和 decompress 按需还原）。
④
前缀保护：cache prefix 完整保留——因为摘要写入位置在已压缩区块，不破坏模型已缓存的前缀范围，下一轮推理仍可利用上下文缓存加速。
为什么在代理侧执行：如果把压缩决策交给客户端，客户端需要自行管理摘要状态、与代理的状态同步，且不同客户端实现各异。代理作为单一压缩权威，所有客户端共享同一状态源，版本一致，永不漂移。
decompress 工具：按需将压缩块还原为原始消息。当需要引用早期对话细节时（如用户追问"之前那个 bug 我们是怎么修的"），模型可调用 decompress 精确还原相关区块，而非扫描整个摘要。
search_context 工具：在压缩历史中语义搜索。当对话被大量压缩后，直接回顾历史变得困难，search_context 允许模型检索压缩块中的相关内容，找到后通过 decompress 精确还原。
acp_status 工具：查询当前压缩状态：已压缩区块数、各区块 token 统计、当前上下文使用率、距离下次压缩的剩余空间等。模型可据此决定是否主动压缩（而非被动等待 nudge 触发）。
Nudge 增长策略工作原理
Nudge（增长提示语注入）是 acp-kernel 的第二层核心机制，在模型还未主动调用 compress 时，提前告知模型"上下文已接近阈值，请考虑压缩"。这是一个预防性策略，而非应急性策略。
触发条件（两者满足其一即注入）：
A
增长驱动：自上次压缩以来，新消耗的可压缩 tokens 累计超过 nudgeGrowthTokens（默认 50000）时触发。每次触发后计数器归零，重新累积。
B
使用率驱动：当前上下文使用率超过 maxContextLimit（默认 75%）时强制注入 nudge，无论增长量如何。
nudge 内容：代理注入一条系统级提示语，告诉模型上下文正在增长、压缩工具可用，并给出压缩哲学指导（压缩原则、要保留的信息类型）。这不是普通对话消息，而是系统提示级别的注入。
为什么需要 Nudge：模型自身不会自发压缩——除非被显式告知压缩工具存在。Nudge 解决了"信息不对称"问题：代理知道上下文大小，模型不知道（除非被告知）。Nudge 让模型在上下文失控前主动介入。
emergency 阈值（95%）：当使用率超过 emergencyThresholdPercent（默认 95%）时，进入紧急模式——模型输出的工具调用结果被硬截断，强制为会话"续命"。这是最后的兜底机制，避免会话因 context_window_exceeded 而死亡。

可能原因：模型上下文窗口设置错误（如 GLM-5.2 1M 被当成 128K）；preserveRecentMessages 设太低；maxContextLimit 默认 75% 对小窗口模型太激进。
排查：在 config 中为该模型显式设置正确的 context 值；增大 nudgeGrowthTokens 或 preserveRecentMessages。
!
症状：Pi 多会话上下文互相混淆
可能原因：Pi 无会话标识，相同开场白的多会话哈希碰撞。
排查：为每个 Pi 会话手动传不同 x-acp-session 标头（UUID 或递增 ID）；或切换到 OpenCode / Codex 等有可靠会话标识的客户端。
!
症状：Claude Code MITM 模式不确定是否生效
可能原因：Claude Code MITM 模式尚未经过实测验证（README 标注 ❓）。
处理：设置 ACP_DEBUG=1 并观察日志中的 mitm:443 tunnel established；若未出现，优先考虑 Launcher 模式（bili claude）或零配置前缀模式。
!
症状：Codex 内的 pip / git / curl 请求报证书错误
可能原因：codex 用 SSL_CERT_FILE 替换了整个 CA 包，codex 环境内的非模型请求也因此失去系统根证书信任。
处理：确保 SSL_CERT_FILE 指向 combined-ca.pem（MITM 根 + 系统根合并包），而非单独的 root-ca.pem。
!
症状：代理更新后行为异常
可能原因：自动更新后新版本与旧版配置不兼容；代理版本与客户端插件版本不同步。
排查：bili --version 确认版本；bili update 再次触发确保最新；ACP_AUTO_UPDATE=0 暂时禁用自动更新回退旧版；检查 CHANGELOG.md 是否有破坏性变更。
!
症状：会话历史在代理重启后丢失
可能原因：BILI_PERSIST=0（纯内存模式）或会话数超 BILI_MAX_SESSIONS（默认 256）被 LRU 驱逐到磁盘。
处理：默认 BILI_PERSIST=1，确认未显式关闭；BILI_MAX_SESSIONS 增大可增加内存中保留的会话数；磁盘文件在 BILI_SESSIONS_DIR 中。
!
症状：日志中出现 context_window_exceeded
可能原因：代理被停止后客户端回放全量未压缩历史导致超限；会话切换到直连上游后同样问题。
处理：保持代理运行；如需迁移，用 bili export <id> --full --output handoff.md 导出后在新会话中粘贴。

acp-kernel 内部架构概览
acp-kernel 是 billion-context 的压缩引擎核心，包含 23 个内聚模块，零外部运行时依赖。关键组件：
1
PipelineNode：管道节点，对应 LSM-tree 的每一层（T1 原始接收 → T2 nudge 决策 → T3 摘要生成）。节点按序处理，支持热插拔替换。
2
processTurn：每次请求的入口函数。解析请求 → 判断压缩时机 → 注入工具/nudge → 转发上游 → 接收响应 → 更新会话状态 → 重写 SSE 流。
3
CompressionCore：核心压缩逻辑。管理压缩块生命周期（创建/更新/合并）、摘要生成调用、压缩缓存（原始消息的指纹索引）。
4
SessionStore：会话持久化层。负责会话状态序列化/反序列化、LRU 驱逐、磁盘写入防抖（BILI_PERSIST_DEBOUNCE_MS）。磁盘为真相源。
5
SSE Rewriter：SSE 流重写器。将代理→客户端的流式响应中的压缩元数据剥离或改写，确保客户端看到的响应格式与直连上游一致。
6
UPSTREAM_PROXY Handler：上游代理路由。处理 http:// CONNECT 隧道透传，将代理→上游的连接路由经过配置的 HTTP 代理（含 GFW 穿透）。
7
MITM Engine：中间人引擎。TLS 终止、证书动态生成、白名单路由、blind-tunnel 非白名单流量。
8
Plugin Server：插件服务。提供 GET /__bili/plugin/manifest 和 GET /__bili/plugin/status，驱动 Plugin 模式下的原生 MCP 工具注册。
会话状态内部结构
每个会话在代理侧维护的状态（对客户端透明）：
SessionState { id: string // 四维哈希: protocol × upstream × apiKey × sessionId label: string // 人类可读标签 (来自 x-session-affinity / session_id) namespace: string // 压缩命名空间 (主会话或 |sub: 子代理) turns: Turn[] // 回合历史 (压缩块 + 未压缩消息混合) compressionBlocks: Block[] // 压缩块列表 (摘要 + 原始消息指纹) pendingT1: number // T1 待压缩 tokens 累积量 pendingT2: number // T2 待晋升 T3 的 tokens 量 usageRatio: number // 当前使用率 (tokens / contextLimit) lastNudgeTokens: number // 上次 nudge 后的 token 计数 createdAt: number // 创建时间戳 lastAccessedAt: number // 最后访问时间 (LRU 驱逐用) }
当代理重启时，SessionStore 从磁盘反序列化所有持久化会话。客户端的本地历史（全量未压缩）是完全独立的视图，代理的压缩状态不依赖客户端存在。
models.dev 注册表与上下文窗口回退机制
billion-context 需要知道每个模型的上下文窗口上限才能计算使用率（tokens / contextLimit），进而决定何时触发压缩。上下文窗口数据来自三层回退机制：
①
最高优先：config 文件中的 models[model].context 声明。在 ~/.config/billion-context/billion-context.json 中显式设置的值优先级最高，用于覆盖注册表错误或支持注册表未收录的模型。例如 "glm-5.2": { "context": 1000000 } 确保 GLM-5.2 的 1M 窗口被正确识别。
②
次优先：models.dev 注册表。这是一个第三方社区维护的模型参数数据库，包含各模型的已知上下文窗口、输入/输出价格等信息。billion-context 启动时从 models.dev 获取数据作为主要数据源。注册表覆盖主流模型（GPT-5.1-codex=400K、GLM-5.2=1M、Claude Opus 4=200K、Claude Sonnet 4=200K、Claude Haiku 3=200K、DeepSeek 系列等）。
③
兜底：内置前缀表 + ACP_MODEL_CONTEXT_LIMIT。当注册表无匹配时，使用内置硬编码的前缀表（覆盖最常用模型）。如果前缀表也没有，ACP_MODEL_CONTEXT_LIMIT 环境变量（默认 200000）作为全局回退值。
为什么要手动声明 context window？因为 /models API 不返回这个字段（各主流 API 均已验证），模型提供商的 API 文档也不包含此信息。如果用错误值（如把 GLM-5.2 的 1M 当成 128K），压缩会过于频繁（使用率计算错误），严重影响使用体验。显式声明是确保精确的唯一方式。
per-URL 覆盖的意义：同一模型在不同服务商背后可能有不同实现。例如某 relay 服务商在 200K 模型上加了一层封装使其表现为 400K 窗口。在 providers 中按 upstream URL 分别声明可以让代理匹配正确的窗口值。
Plugin 模式与 MCP 工具体系
Plugin 模式提供了一种比 wire-injected 工具更高质量的工具体验。在 wire-injected 模式下，压缩工具作为普通对话消息注入到模型请求中，模型的工具调用通过请求体传递，由代理在后台处理。在 Plugin 模式下：
①
插件向客户端注册原生 MCP 工具（compress / decompress / search_context / acp_status），这些工具以标准 MCP 协议暴露，客户端将它们当作原生内置工具处理（工具选择器、参数填充、调用反馈均与内置工具一致）。
②
插件从代理获取工具 schema（GET /__bili/plugin/manifest），schema 由代理动态生成，与当前会话的压缩状态精确匹配（工具参数中包含当前使用率等实时信息），plugin 和 proxy 版本永远对齐，不会漂移。
③
插件执行请求转发回代理（POST /__bili/plugin/execute），代理在会话锁下执行压缩操作，结果返回插件，插件再返回客户端。整个链路完全在 MCP 协议内，工具体验与内置工具无异。
④
代理可通过 GET /__bili/plugin/status 获取会话实时信息（当前使用率、已压缩块数等），插件可以将这些信息用于工具参数的动态填充。
工具 schema 服务端化的意义：工具定义不在客户端硬编码，而在代理侧动态生成。这意味着压缩工具的参数可以包含会话特定的动态信息（如当前上下文使用率），而无需客户端每次重新安装或更新插件版本。代理更新后，客户端立即获得新的工具 schema，无需手动重新配置。
双工具体验共存：Plugin 模式和 wire-injected 模式可以共存于同一代理——已安装插件的客户端走 Plugin 路径，未安装插件的客户端走 wire-injected 路径。代理通过请求头自动检测：带有插件标识的请求走 Plugin 路径并抑制 wire-injected 注入，避免双重工具定义。

Responses API 与 reasoning 压缩处理
当上游使用 Anthropic Responses API（包含 reasoning 思考块）时，billion-context 对 reasoning 内容有特殊处理机制：
默认
默认行为：reasoning 块经压缩管线传递。reasoning 内容被保留在压缩状态中，当包含它的压缩块被摘要时，reasoning 随原始消息一起被压缩进摘要。这会导致一个问题：长会话中 reasoning 块在 prompt-cache 前缀中无限累积（因为它们在 cache prefix 范围内），最终填满缓存导致压缩效率下降。
none
设置 ACP_REASONING_KEEP=none：丢弃所有 reasoning 块，完全不进入压缩管线。这样 reasoning 内容不会污染前缀缓存，但意味着用户看不到模型的思考过程摘要。适合不需要透明思考过程的场景。
为什么 Codex 特别需要关注这个？Codex 的 prompt-cache 前缀机制对缓存内容大小非常敏感。reasoning 块如果不经处理就进入缓存，几十轮对话后缓存前缀会被 reasoning 内容填满，导致新消息几乎没有缓存收益。设置 ACP_REASONING_KEEP=none 可以彻底解决这个问题。

billion-context-pi 关联项目
billion-context-pi（83 ⭐，独立仓库）是 billion-context 在 Pi 客户端上的深度集成扩展。与 billion-context 的关系：
①
进程内集成：billion-context-pi 将压缩引擎直接集成到 Pi 进程内部，而非作为独立代理运行。这意味着压缩决策和执行在 Pi 进程中同步进行，无需网络往返，延迟更低。
②
更紧密的集成：Pi 的消息处理管道直接调用 acp-kernel，压缩状态与 Pi 的会话状态在同一进程内共存，不需要外部 HTTP 调用来触发压缩。
③
共存策略：billion-context-pi 作为 Pi 的插件（bili plugin install pi）安装时，会检测 /bili/ 前缀并自动自我禁用，让外部代理接管压缩，避免双重压缩。
④
适用场景：如果你的团队已经在使用 Pi，billion-context-pi 提供了开箱即用的零配置体验；如果需要跨客户端（Pi + Codex + OpenCode）统一压缩策略，外部 billion-context 代理是更好的选择。
与同类工具的定位差异
billion-context vs 客户端内置摘要：大多数 AI 编程助手内置了简单的摘要功能（通常是一次性压缩当前对话）。billion-context 的压缩是增量的（可逆）、可搜索的（search_context）、分层级的（3 层 LSM-tree）、且前缀缓存友好。内置摘要是一次性操作，billion-context 是持续性维护。
billion-context vs prompt-cache 工具：Claude Code 和 Codex 的 prompt-cache 功能将部分对话历史缓存以降低 Token 成本。但 cache 前缀会随对话膨胀而增长，最终仍会填满。billion-context 的压缩通过减少 cache 前缀中的内容总量从根本上解决此问题，与 prompt-cache 是互补关系而非竞争关系。
billion-context vs API 层面的批量压缩：部分 API 提供商提供服务端批量压缩（如将多轮对话压缩为单次请求）。billion-context 在请求层面工作，不依赖特定 API 提供商，支持任何 OpenAI / Anthropic 兼容端点，且压缩逻辑完全透明可控。
核心能力一览
Token 节省效果
3 层 LSM-tree 压缩将上下文稳定在约 150K tokens；若放任膨胀至 1M，上游计费约增加 5 倍。压缩后 Token 量级降低一个数量级，同时保持关键语义完整。
上游模型支持
Anthropic / OpenAI / DeepSeek / 智谱 GLM / 任意 OpenAI 兼容端点。支持 per-URL proxy 配置；mitm:// 与 https:// scheme 分流登录客户端与 API-key 客户端的代理流量。
上下文窗口检测
自动从 models.dev 注册表获取各模型上下文上限（GPT-5.1-codex=400K、GLM-5.2=1M、Claude Opus 4=200K……）；无匹配时回退内置前缀表；全无匹配时使用全局默认值 200K。支持按模型覆盖：context = "70%" 或绝对数字。
持久化与会话
会话默认持久化至磁盘（BILI_PERSIST=1），LRU 驱逐上限 256 会话。磁盘为真相源，重启代理后会话历史不丢失。可通过 BILI_PERSIST=0 关闭持久化（内存模式，重启丢数据）。

GFW 环境下游代理配置
当代理自身的出站连接被防火墙阻断时（如 GFW 内访问 api.openai.com），配置上游 HTTP 代理（本地 v2rayA / Clash 等）让代理通过代理连接模型提供商。
配置方式（优先级从高到低）：
1. 环境变量BILI_UPSTREAM_PROXY=http://127.0.0.1:20172
2. Web UI 手动设置优先级次高
3. 顶层 proxy（config 文件）所有 providers 共用
4. HTTPS_PROXY / HTTP_PROXY / ALL_PROXY系统环境变量
5. Windows 系统代理自动发现
6. 直连兜底
per-URL 覆盖：可在 config 中对特定 host 指定不同代理，或用空字符串 "" 显式直连（覆盖上层全局代理）：
{ "proxy": "http://127.0.0.1:20172", "providers": { "https://api.openai.com/v1": { "proxy": "http://127.0.0.1:20173" }, "https://open.bigmodel.cn/api/anthropic": { "proxy": "", "models": { "glm-5.2": { "context": 1000000 } } } } }
⚠️ SOCKS5 暂不支持：当前版本仅支持 HTTP / HTTPS 代理起源，不支持 SOCKS5 协议。如需 SOCKS5，可在前端用 privoxy / polipo 等将 SOCKS5 转为 HTTP 代理。
mitm:// vs https:// 分流：登录客户端走 MITM（ZCode 等）和 API-key 客户端走 /bili/ 前缀的流量，在 config 中使用不同 scheme 的 key 可以独立配置：
{ "providers": { "mitm://open.bigmodel.cn": { "proxy": "http://127.0.0.1:20173" }, "https://open.bigmodel.cn/api/anthropic": { "proxy": "http://127.0.0.1:20172" } } }
⚠️ --host 参数注意：127.0.0.1 是 IPv4 仅限且仅本机可达。如果客户端的 /etc/hosts 将 ::1（IPv6 loopback）排在 127.0.0.1 之前，客户端解析 localhost 到 IPv6 地址时会连接失败。解决方案：bili --host ::（同时监听 IPv4 + IPv6）。容器内使用 --host 0.0.0.0 绑定所有网卡（⚠️ 暴露所有网络接口，仅在可信网络内使用）。

URL key 匹配规则
1
最长键胜出：请求匹配时，代理选择最长前缀匹配的 key（深度 key 优先于浅 key）。
2
不跨 host：key 匹配不会跨域——https://x.com 不会匹配 https://x.com.evil（边界检查要求 key 末尾是 / 或字符串结尾）。
3
bare host key：如 https://open.bigmodel.cn 覆盖该 host 下所有路径；精确路径 key 如 https://open.bigmodel.cn/api/anthropic 只覆盖该端点。

API key 不存储：代理从不存储 API key，客户端发来的 key 原样透传给上游。
Launcher 模式详细说明
①
代理生命周期：Launcher 绑定了代理与客户端的退出——客户端退出时，Launcher 启动的代理也停止。如果复用你之前用 bili 手动启动的代理，那个代理继续运行不受影响。
②
配置只读不改：Launcher 读取客户端配置文件（pi 读 ~/.pi/agent/models.json、codex 读 ~/.codex/config.toml、claude 硬编码 api.anthropic.com）来发现 HTTPS 上游主机并加入 MITM 白名单，客户端自身配置完全不动。
③
双协议覆盖：HTTPS 上游走证书 MITM（CA 路径：pi/claude → NODE_EXTRA_CA_CERTS、codex → SSL_CERT_FILE 指向 combined-ca.pem 即 MITM CA + 系统根的合并包），HTTP / localhost / 127.0.0.1 上游走 /bili/ 前缀重写。
④
--mitm-domain 扩展白名单：bili pi --mitm-domain api.foo.com 将额外域名加入 MITM 白名单（可重复指定多个），适合客户端运行时动态请求的非配置文件内的 host。
⑤
端口自动选择：
默认 8787；端口被占用时自动选空闲端口。可用 --port / --debug / --passthrough / --no-auto-update 覆盖行为。

常见问题
Q: 与 opencode-dynamic-context-pruning 有何区别？
acp-kernel 是独立的 MIT 实现，不源自 opencode-dynamic-context-pruning，拥有自己的 PipelineNode / processTurn / CompressionCore 架构。billion-context-pi（83 ⭐）是基于本项目的 pi 集成扩展。
Q: 压缩会导致信息丢失吗？
LSM-tree 第三层用模型生成摘要替代原始消息，属于有损压缩。最近 preserveRecentMessages 条消息保持不压缩以保护最新上下文。压缩是增量的、可逆的（通过 decompress 工具按需还原），且前缀缓存友好。
Q: Pi 客户端为何存在碰撞风险？
Pi 没有会话标识字段，多个会话的请求可能被视为同一会话，导致上下文混淆。⚠️ 生产环境建议使用 OpenCode 或 Codex；Pi 多并发场景建议手动传 x-acp-session 标头。
Q: 会话数据保存在哪里？
默认保存在 ~/.local/state/billion-context/（XDG 规范路径），磁盘为真相源，重启后不丢失。可通过 BILI_PERSIST=0 关闭持久化（纯内存模式）。
Q: 如何调试压缩行为？
设置 ACP_DEBUG=1 开启详细日志（写入 ~/.local/state/billion-context/bili.log，10MB 自动轮转）；或访问 Web UI http://localhost:8787/__bili/ 查看实时状态；也可设 ACP_DUMP_SSE=/path 将每个请求的 SSE 流存入文件。
Q: 支持 DeepSeek 和智谱 GLM 吗？
支持。两者都走 OpenAI 兼容 API，billion-context 通过 /bili/ 前缀或 MITM 模式均可代理，只需将 baseURL 前缀指向本地代理即可。GLM-5.2 上下文 1M，建议在 config 中显式声明以覆盖注册表。
Q: auto-update 机制安全吗？
启动时和每 3 分钟检查 npm 是否有新版本，检测到后自动全局安装。可通过 ACP_AUTO_UPDATE=0 完全禁用，或用 bili --no-auto-update 单次禁用，或 bili update 手动触发（跳过节流）。
Q: 为什么需要声明上下文窗口？LLM /models API 不返回这个值吗？
经验证，OpenAI、Anthropic、智谱、Comfly 的 /models API 均不返回 context window 字段——这是文档级信息，不在 API 响应里。如果用错误值（如 GLM-5.2 被猜测为 128K 而非 1M），压缩会过于频繁，严重影响使用体验。per-URL + per-model 声明是确保精确的唯一方式。
Q: 为什么 Codex 子代理需要独立命名空间？
Codex 子代理（如 guardian_subagent）与主会话共用 session_id，若不隔离，子代理的压缩状态会与主会话混在一起，可能导致主会话上下文被误折叠（丢失审批所需的原始用户消息）。通过 instructions 字段区分后，各方拥有独立压缩状态，Web UI 中显示为两个独立会话。
Q: 停代理后为什么不能直接继续？
压缩状态存储在代理侧，客户端本地只有完整未压缩历史。停代理后客户端回放全量历史，超过模型上下文窗口会报错 context_window_exceeded。正确迁移方式：先用 bili export <id> --full --output handoff.md 导出，再在新会话中粘贴为开场上下文。
Q: 为什么 codex 需要 combined-ca.pem 而不是直接用 root-ca.pem？
NODE_EXTRA_CA_CERTS 是追加到系统默认信任库的，指向 root-ca.pem 即可。但 SSL_CERT_FILE 是替换默认 CA 包，codex 内部 pip / git / curl 等组件也用同一份证书包，所以 SSL_CERT_FILE 需要指向 combined-ca.pem（MITM 根 + 系统/Node 公共根的合并包），否则 codex 环境内的非模型 HTTPS 请求（包安装等）会因证书不受信任而失败。
性能指标与预期收益
基于 README 和项目测试数据，以下是可量化的关键指标：
上下文稳定性
LSM-tree 3 层压缩后，上下文稳定在约 150K tokens（无论原始膨胀到多大规模）。相比放任膨胀至 1M Token 的场景，Token 消耗约降低 5 倍。
前缀缓存健康度
压缩摘要写入小范围块，cache prefix 完整保留。日志中 [acp-usage] round N cached=Y (cache hit Z%) 字段直接反映缓存命中率，可用于评估当前配置是否最优。
压缩步长
nudgeGrowthTokens 默认 50000 tokens（1M 上下文），约每积累 50000 可压缩 tokens 触发一次压缩。在 1M 上下文上约需 20 次压缩步走完整个生命周期。
会话持久化性能
默认防抖窗口 500ms（BILI_PERSIST_DEBOUNCE_MS），降低高频写入磁盘的 IO 压力。LRU 驱逐上限 256 会话，超出后最旧会话写出到磁盘。重启后完整恢复。
启动性能
首次启动时懒生成 CA 证书（约 1 秒）。代理冷启动 + 会话反序列化约 2-3 秒（取决于会话数）。自动更新检查在后台异步进行，不阻塞启动。
测试覆盖
146 个 mock 测试（billion-context 仓库）+ 208 个独立测试（acp-kernel 仓库）。真实模型集成测试是当前下阶段里程碑。
安全考量
!
CA 证书仅本地有效：根 CA 证书在本地机器生成，从不外传。只有显式导入该 CA 的客户端才会信任它，其他应用程序不受影响。删除 CA 文件并重启代理可随时撤销。
✓
API key 从不存储：代理透传客户端的 API key，既不记录也不修改。上游看到的就是客户端直接发送的内容。
✓
OAuth token 完整透传：登录客户端的 OAuth token 在 Authorization 头中流动，MITM 模式下代理只做 TLS 终止和压缩注入，不触碰 auth token。订阅折扣完整保留。
✓

✓

✓
代理自环保护：检测到代理连接指向自身端口时自动拒绝，防止 BILI_UPSTREAM_PROXY 误配置为本地 bili 端口导致死循环。
⚠️
0.0.0.0 暴露风险：bili --host 0.0.0.0 将代理暴露在所有网卡接口，同一网络的其他设备可通过 http://<your-ip>:8787/bili/... 访问你的代理。仅在可信网络内使用，或配合防火墙限制来源 IP。

高级问题
Q: 为什么 /models API 无法获取 context window 信息？
各模型提供商的 /models REST API（OpenAI / Anthropic / 智谱 / Comfly）均只返回模型 ID、创建日期、支持的功能列表等元数据，不包含 context window 字段。这是文档级信息，不在 API 规范内。因此 billion-context 依赖 models.dev 第三方注册表获取该数据——这是一个由社区维护的模型参数数据库，定时同步各模型的已知上下文窗口。
Q: 如何为大模型调优 nudgeGrowthTokens？
基本原则：上下文越大，nudgeGrowthTokens 可以越大。1M 上下文默认 50000（每步约 5% 窗口增长）；200K 上下文建议降至 20000-30000（每步约 10-15%）；32K 小窗口模型建议 5000-10000。另一个维度是任务类型：需要频繁回顾历史的调试任务建议设低（更频繁压缩、保留更多近期上下文），纯生成任务可设高（延迟压缩、减少摘要开销）。
Q: tiers: false 和 tiers: true 有什么区别？实际选哪个？
tiers: true 启用完整 3 层 LSM-tree（T1→T2→T3 多级蒸馏），压缩质量最高但计算开销稍大；tiers: false 退化为单级压缩（直接 T1→T3），配置简单但摘要质量可能下降。对于大多数场景保持 tiers: true（默认）；如果对压缩延迟敏感且上下文窗口小于 200K，可试 tiers: false 降低延迟。
Q: combined-ca.pem 是什么？和 root-ca.pem 有何区别？
root-ca.pem 是 billion-context 生成的 MITM 根证书（自签名，仅本地有效）。combined-ca.pem 是合并包：包含 MITM 根证书 + 系统/Node.js 公共根证书。仅 codex 需要 combined-ca.pem（因为 SSL_CERT_FILE 是替换模式而非追加模式）。pi / claude 用 NODE_EXTRA_CA_CERTS（追加模式），只需指向 root-ca.pem。
Q: 如果模型调用 compress 时代理已经崩溃了怎么办？
压缩状态在代理侧，代理崩溃会导致当次压缩未完成（压缩块未写入磁盘），但不会损坏已压缩的历史（已写入磁盘的块完好）。代理重启后 SessionStore 从磁盘恢复最近持久化状态，最坏情况是重启前最后一次防抖写入之后的状态丢失（最多 500ms 的数据）。模型侧会因为代理无响应而收到连接错误，重试即可。
Q: 会话 ID 的四维哈希具体包含哪些字段？
会话 ID = SHA256(protocol + upstreamOrigin + apiKey + clientSessionId)。protocol 区分 HTTP vs HTTPS vs MITM；upstreamOrigin 是目标 API 源（防止跨服务商）；apiKey 是请求头中的 key 哈希（防止跨账户）；clientSessionId 来自客户端（session_id / x-session-affinity / 哈希首条消息）。任何一维不同都会生成不同会话 ID。
Q: 如何监控 billion-context 的健康状态？
三种方式：① HTTP 健康检查 curl http://localhost:8787/__bili/health（适合外部监控 / healthchecks.io）；② curl http://localhost:8787/__bili/stats 查看实时会话数和 Token 统计（适合人工巡检）；③ 日志文件 ~/.local/state/billion-context/bili.log 中的 processTurn / acp-usage 记录（适合性能分析）。可将健康检查接入 systemd timer 或 cron 定期巡检。
Q: 如何为特定模型禁用压缩？
在对应模型的 compress 块中设置 tiers: false + injectTool: false + injectNudge: false，这样该模型的流量会透传不压缩。或者更简单：在 providers 中为该 URL 不设置任何 compress 覆盖，同时确保 models.dev 注册表中该模型上下文窗口足够大（超过实际使用量，压缩永远不会被触发）。
Q: 为什么 Codex ChatGPT 登录版可以用 /bili/ 前缀而其他登录客户端不行？
因为 Codex 的 config.toml 提供了一个顶层 openai_base_url 字段，允许用户显式指定上游 URL（绕过 provider 配置）。其他登录客户端（ChatGPT Plus、Claude 订阅）的 baseURL 是硬编码在代码里的，配置文件无法修改。Codex 的这个设计让登录版也享受零配置前缀的便利。
Q: 压缩后的摘要内容能否自定义？
当前版本摘要由模型生成，内容由模型的压缩理解决定。代理注入压缩哲学指导（compress 系统提示），模型据此决定摘要中保留哪些信息。如需自定义摘要策略（如强制保留所有文件名、强制移除某些格式），可通过调整 injectTool 注入的系统提示内容来实现（需要修改代理源码或通过环境变量扩展）。
Q: BILI_LAUNCHER_DIRECT=1 和默认 MITM 模式有何区别？
默认模式下，Launcher 对 HTTPS 上游走 MITM 透明代理（TLS 终止），对 HTTP 上游走 /bili/ 前缀重写。BILI_LAUNCHER_DIRECT=1 则完全跳过 MITM/CA 机制，改为让客户端的 baseURL（ANTHROPIC_BASE_URL / provider base_url）直接指向 /bili/ 前缀前缀路径。DIRECT 模式改变了流量路由（不再经过 MITM），代理会打印警告。此模式适合不需要 MITM 的 API-key 客户端，避免 CA 配置的复杂度。
Q: 如何在不停止代理的情况下导出特定会话的压缩状态？
bili export 支持在线导出（不需要停止代理）。列出所有持久化会话：bili export（输出 id / label / 块数）；按 ID 或 label 导出：bili export <id>（摘要级）或 bili export <id> --full（含原始消息）。导出是只读操作，不影响代理运行。导出的 Markdown 文件可直接粘贴到任何客户端的新会话中。
