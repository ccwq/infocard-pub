Browser Harness：把 LLM 接到真实浏览器

它的定位不是“再造一个浏览器”，而是提供一层很薄、可编辑的 CDP harness：一条 websocket 连到 Chrome，LLM 在执行中补缺失的辅助代码与站点技能，适合需要真实浏览器、需要持续自我修复的任务。

01一句话结论
结论：Browser Harness 的核心价值，是把 LLM 直接接到真实浏览器和 CDP 上，同时保留一个很薄的、可编辑的执行壳，让 agent 在运行中补 helper、补 site skill、补它自己欠缺的那部分。

02安装流程

推荐安装方式

先把仓库克隆到一个稳定路径，再用 editable 模式安装，这样命令全局可用，但修改仓库里的 helper 后，下一次运行会立即生效。

安装命令

git clone ... → cd browser-harness → uv tool install -e . → command -v browser-harness。稳定目录比临时目录更适合长期维护。

权限与依赖

Python 需要 3.11+；核心依赖是 cdp-use、fetch-use、pillow 和 websockets。API key 不是必需，只有使用云浏览器时才需要。

首次校验

安装后先跑 browser-harness --doctor 或 stdin demo，先确认命令能启动，再进入浏览器连接流程，避免一上来就调复杂任务。

03连接浏览器的两条路
方式 怎么连 适合什么
方式一：连接现有 Chrome 在 `chrome://inspect/#remote-debugging` 勾选允许远程调试；Chrome 144+ 首次连接可能弹确认窗。 适合真实日常浏览器、已有登录状态、需要复用个人配置
方式二：命令行启动独立 Chrome 用 `--remote-debugging-port=9222 --user-data-dir=<非默认路径>` 启动；再用 `BU_CDP_URL` 指向该端口。 适合自动化、无弹窗、无头或 CI 场景
云浏览器 用 Browser Use Cloud 和 `BROWSER_USE_API_KEY`，可同步 cookies，适合分布式或 headless 任务。 适合更稳的托管执行
本地 Chrome 优先 云浏览器可选 cookies 可同步 默认不需要 key
04日常使用方法

最短起步

用 heredoc 喂给 browser-harness，先执行一个很小的页面操作，确认 daemon、浏览器和 CDP 三者已经连上。

先看再点

这套工具强调截图先行：先看页面，再判断是点坐标、写 selector，还是直接用 DOM 读取。它偏向真实浏览器行为，不偏向抽象 UI 测试框架。

任务外编排

任务相关代码放在 `agent-workspace/agent_helpers.py` 和 `domain-skills/`，让站点专用经验沉淀下来，而不是写死在主流程里。

05底层原理

执行链路

仓库的架构非常短：Chrome 或 Browser Use Cloud → CDP websocket → daemon → IPC → run.py。run.py 负责入口，daemon 负责持久会话，helpers 负责动作原语。

为什么叫“薄壳”

它不内建一堆管理层；反而把最少的控制逻辑保留下来，把复杂度丢给浏览器本身和 agent 自己学到的技能。这样更容易自我修复，也更容易被编辑。

为什么能“自我修复”

agent 可以在运行过程中写 helper、写 domain skill，下一次执行就能利用新代码。这意味着它会把成功的动作模式沉淀到工作区，而不是每次重新摸索。

协议与状态

IPC 走单行 JSON；状态上区分 session、target、events 和 dialog。daemon 负责让页面会话不至于每次都重来，从而更适合长任务。

06边界与风险

适合

真实浏览器里需要登录态、页面交互、重复任务、站点特例和持续学习的场景；尤其适合你愿意让 agent 越跑越懂的工作流。

不适合

你只想做一次性静态抓取、或者想要一个大而全的自动化框架时，它可能太薄了；它更像浏览器控制面，不像万能中间件。

注意

Chrome 版本、远程调试开关、popup 确认窗、云 key、默认 profile 限制，都会影响连接体验。先诊断连接，再谈复杂任务。

维护建议

把共通 helper 保持短，把站点技能沉到 domain-skills；这样更新不会互相污染，任务也更容易复用。
