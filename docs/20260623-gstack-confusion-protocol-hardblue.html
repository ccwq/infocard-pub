01
问题是什么

AI 编码 Agent 最致命的失败模式：在模糊决策点自信选错路

困惑协议要解决的不是"AI 能力不够"，而是"AI 不知道自己不知道"——在架构选型、数据建模、破坏性操作这类高代价模糊点，Agent 往往自信地选了一条错路，后续整个工作链都被带偏。

失败模式自信走错

不是能力问题，是元认知问题

AI 编码 Agent 最致命的失败不在于代码写错，而在于它面对模糊决策点时"自信地选错路"。它不知道自己不知道，还以为选的是对的。

  • 自信 ≠ 正确
  • 模糊点最危险
  • 走错一步 → 后续全盘返工
典型场景高代价模糊点

三个最容易出事的地方

架构选型、数据建模、破坏性操作——这三个点一旦走错，后续修复成本呈指数级增长，而 Agent 往往在这些点上最"自信"。

  • 架构选型：选错技术栈
  • 数据建模：改崩 schema
  • 破坏性操作：误删 / 覆盖数据
后果大返工

十分钟改崩 schema 的故事

"倒杯水回来，AI 已经把 schema 改崩了"——这不是段子，是日常。Agent 在你不在的时候自信地做了破坏性决策，等回来发现整个数据模型已经被带偏。

  • 修复成本远超决策成本
  • 半小时甚至几小时返工
  • 信任被反复消耗
02
困惑协议怎么工作

ambiguity gate 模糊门 → 遇到分叉立即停止 → 精准提问

困惑协议的核心机制是"模糊门"（ambiguity gate）：Agent 在执行过程中遇到分叉决策点时，不是继续硬干，而是立即刹车、精准提问、等待人类确认。

核心机制ambiguity gate

模糊门：分叉即刹车

遇到分叉 → 立即停止 → 精准提问 → 等待确认

模糊门不是"降低 AI 速度"，而是"在正确的地方减速"。它只在高代价模糊点触发，日常简单任务不受影响。关键是：停下来不是为了偷懒，而是为了精准提问。

  • 分叉识别：判断当前是否为高代价决策点
  • 立即停止：不继续硬干、不猜测路径
  • 精准提问：给出具体选项和上下文，而非泛泛求助
约束高代价触发

不是处处停，只在关键点停

困惑协议必须内置于 GStack 工作流，且仅在高代价模糊点触发。如果每个小决策都停下来问，反而会拖垮效率——协议的精髓在于"该停的停，不该停的不停"。

  • 架构选型 → 触发
  • 数据建模 → 触发
  • 破坏性操作 → 触发
  • 日常简单任务 → 不触发，正常执行
触发点为什么危险协议行为
架构选型选错技术栈影响全局停下 → 列出备选方案 → 等确认
数据建模schema 改崩后续全盘返工停下 → 说明改动影响 → 等确认
破坏性操作误删 / 覆盖不可逆停下 → 明确操作范围 → 等确认

模糊门的设计哲学：宁可多停 30 秒确认，也不要花半小时修一个自信走错的决定。

03
防护升级

CEO 评审强化 + GBrain 知识库自动读写，构成元认知双保险

困惑协议不只是一个"停下来问"的机制，它还叠加了两层防护：CEO 评审强化确保"只评审不写代码"，GBrain 知识库让 Agent 执行前自动搜索、执行后自动写回。

CEO 评审只评审不写

CEO 评审强化：每个停止点反复强调"只评审，不写代码"

在困惑协议的每个停止点，CEO 评审模式会反复强调一个铁律：只评审，不写代码。Agent 可以分析、可以建议、可以提问，但绝不擅自动手——这切断了"停下来又自作主张继续干"的回路。

  • 只评审 → 不写代码
  • 可以分析、建议、提问
  • 绝不擅自继续执行
  • 等人类明确指令后才动手
GBrain知识库读写

GBrain 集成：执行前搜索，执行后写回

GBrain 知识库让 Agent 具备"记忆"：执行前自动搜索个人知识库，看看以前有没有处理过类似问题；执行后自动把结果写回，形成可复用的经验沉淀。

  • 执行前 → 自动搜索知识库
  • 执行后 → 自动写回结果
  • 仅限本地 / 私有实例
  • 经验可复用，避免重复踩坑
防护链闭环： 模糊门刹车 → CEO 评审强化（只看不写）→ 人类确认 → GBrain 搜索历史经验 → 按确认路径执行 → GBrain 写回结果。每一步都有护栏，不让 Agent 在模糊点"自由发挥"。
04
模式区分

评审模式 vs 实现模式：严格区分，绝不混用

困惑协议要求严格区分两种模式：评审模式下 Agent 只看不动，实现模式下 Agent 才真正写代码。两种模式不能同时存在，切换必须由人类显式触发。

评审模式Review Only

评审模式：只看、只分析、只提问

评审模式下，Agent 的职责是理解代码、分析问题、提出建议和精准提问——但绝不写一行代码。这是困惑协议每个停止点的默认状态。

  • 理解现有代码与架构
  • 分析问题根因
  • 提出方案建议
  • 精准提问，等待人类决策
实现模式Implement

实现模式：人类确认后才动手写代码

实现模式下，Agent 才真正执行编码操作。进入实现模式的前提是人类已经确认了方向——模糊门已通过、CEO 评审已完成、GBrain 已搜索过历史经验。

  • 人类明确确认方向后才进入
  • 按确认路径执行编码
  • 执行后 GBrain 自动写回
  • 遇到新模糊点 → 退回评审模式
关键原则： 两种模式不能并存。Agent 不会在"评审"的同时偷偷"实现"——每一次从评审到实现的切换，都必须由人类显式触发。遇到新的模糊点，自动退回评审模式。

效率对比

以前 10 分钟改崩 schema → 现在 30 秒确认省半小时返工

困惑协议不是拖慢 Agent，而是用极低的确认成本避免极高的返工成本。效率对比的核心逻辑：多花 30 秒问清楚，省下半小时甚至几小时的修复时间。

1

以前：自信走错 → 大返工

Agent 在模糊决策点自信选错路，倒杯水的功夫 schema 已经改崩。修复成本：半小时到几小时，甚至全盘重来。

2

现在：30 秒确认 → 方向正确

模糊门触发，Agent 停下来精准提问。人类花 30 秒确认方向，Agent 按正确路径继续执行，避免后续返工。

3

净收益：信任提升 + 效率提升

不是每个模糊点都需要停，但高代价模糊点停一次的收益远超成本。Agent 从"自作主张"变成"聪明搭档"。

困惑协议的效率逻辑不是"处处减速"，而是"在高代价点用 30 秒换半小时"。整体效率反而提升。
