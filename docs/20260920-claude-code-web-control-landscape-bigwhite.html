Claude Code Web 控制方案全景

先选“谁拥有会话”，再选 Web UI——官方 Remote Control 接管已有会话且不开放端口，是默认首选；PTY/WebSocket 把终端执行权交给浏览器，能力最大但安全自负；Agent SDK 重建控制面，适合做成产品。

SESSION 层Remote Control / Agent SDK：控制 Claude 会话与消息。
TTY 层PTY + WebSocket：控制终端进程的画面与按键。
平台现实没有成熟方案可无条件 attach 任意已打开的 Windows Terminal。

TL;DR · 核心要点
SCOPE 01

四条要点，各自独立成立

1
三条路线控制的东西不同

Remote Control 接管已有 Claude 会话（消息层）；PTY/WebSocket 接管终端进程（TTY 层）；Agent SDK Web UI 重建控制面（生命周期层）。混称“同一个 Web UI”会导致选型错误。

2
官方 Remote Control 是默认首选

一行命令、出站 HTTPS、不开放入站端口；代价是需要 claude.ai 订阅登录，且看不到原始终端画面。能用它就不要自建。

3
PTY 路线的执行边界在后端

xterm.js 只是渲染组件；谁持有 node-pty / ConPTY / tmux，谁就拥有命令执行权。选型看四维：PTY/TUI 适配度、Windows 友好度、维护成熟度、部署成本。

4
Windows 先选宿主再选工具

原生 ConPTY、psmux、WSL2 三条宿主路线成熟度差异极大；多数 tmux 系项目在原生 Windows 不可用或仅 WSL2。

三条路线辨析与官方上手

对应要点 1 与要点 2。评价标准只有一条：控制对象。会话层方案改不了你的终端，TTY 层方案不懂 Claude 的会话语义，SDK 层方案根本不连现有终端。每条路线给出机制、能力边界与从零到可用的完整步骤。

1.1路线 A：官方 Remote Control（会话层）
# 三种启动方式
claude remote-control        # 服务器模式：托管最多 32 个会话
claude --remote-control      # 交互式会话 + 远程可用（可加会话名）
# 或在已有会话内：
/remote-control              # 携带当前对话历史接入

# 常用 flags（服务器模式，置于 remote-control 之后）
claude remote-control \
  --name "My Project" \       # 会话列表显示名
  --spawn worktree \          # same-dir | worktree | session
  --capacity 8 \              # 并发上限，默认 32
  --permission-mode acceptEdits
前置Pro/Max/Team/Enterprise 订阅，claude 已 /login；不支持纯 API Key；Bedrock / Vertex / Foundry / 自定义 ANTHROPIC_BASE_URL 不可用；DISABLE_TELEMETRY 等变量会阻断 feature-flag 检查；从项目目录启动（workspace trust）。
首次上手项目目录运行 claude remote-control → 首次确认 Enable Remote Control? y → 终端显示会话 URL，按空格出二维码 → 手机/浏览器打开 claude.ai/code 即接管。
关键配置--spawn 决定会话隔离方式（worktree 需 git 仓库）；运行时按 w 切换 same-dir/worktree；--sandbox 开文件/网络隔离（默认关）。
验证成功终端出现 /rc active 指示器（链接到 claude.ai 会话）；浏览器端能看到本地 subagent 与 workflow 的实时状态。
排障报“requires a claude.ai subscription”→ 检查 ANTHROPIC_API_KEY/AUTH_TOKEN 是否覆盖了登录态；报 403 超三分钟 → VPN/代理变更后用 /remote-control 重连；本地进程退出 → 会话离线，长任务放 tmux/screen 里跑。
# 浏览器看到的是结构化会话，
# 不是终端画面
claude.ai/code  ─┐
Claude 手机 App ─┤  Anthropic API (TLS)
                 ▼
        本机 Claude Code 进程
                 ▼
     本地文件 / MCP / 工具 / 配置

本机不开放入站端口：进程只发起出站 HTTPS，注册到 Anthropic API 后轮询取工作。transcript 在 Remote Control 期间同步到服务端以支持多设备与断线恢复，保留策略遵循其数据条款。协议细节（握手、token 语义、多端写入策略）未公开，不应自行假设。部分命令仍为本地专属：/plugin、/resume 需在终端执行；/model、/effort 等 Web 端仅接受参数形式。

1.2路线 B：PTY / WebSocket（TTY 层）
# 浏览器永远只连 Broker，
# 不直连 PTY 或 tmux socket
xterm.js ── WebSocket ── Auth Broker
                          ├─ node-pty / ConPTY
                          ├─ tmux / psmux
                          └─ claude / claude --resume

xterm.js 官方定位是终端渲染组件，不是 shell；执行权在持有 PTY 的后端进程。自建 Broker 至少要承担：认证、Origin 校验、会话注册表、单 writer 串行输入、断线重连与输出缓冲。下面用 ttyd 演示最小链路——它是这条路线的“参考实现”，也是理解所有 PTY 系项目的透镜。

# ttyd：把任意命令变成网页终端
# macOS: brew install ttyd
# Linux: apt install ttyd
# Win:   winget install tsl0922.ttyd

ttyd -W bash   # -W 才允许写入！默认只读
# → http://localhost:7681

# 生产级收紧：认证 + origin + 限客户端
ttyd -W -c user:pass -O -m 1 \
  -i 127.0.0.1 claude
前置任一平台；Windows 用 releases 预编译二进制或 winget/scoop。
关键选项-p 端口（默认 7681）、-c Basic 认证、-W 开写入（默认只读）、-O 校验 Origin、-m 最大客户端、-o 单客户端、-i 绑定网卡或 UNIX socket。
验证成功浏览器打开 7681 端口看到 bash 提示符；用 -w 指定工作目录后在其中跑 claude 即得最小 Web TUI。
边界ttyd 不管 Claude 会话语义——没有 JSONL 解析、没有权限卡片，纯粹是“终端上网页”。它是理解 purplemux / Studio 等项目加了什么的关键基线。
1.3路线 C：Agent SDK Web UI（生命周期层）
# 官方 quickstart（TypeScript）
npm init -y && npm pkg set type=module
npm install @anthropic-ai/claude-agent-sdk
npm install --save-dev tsx

# agent.ts —— 最小可用 agent
import { query } from
  "@anthropic-ai/claude-agent-sdk";

for await (const message of query({
  prompt: "Review utils.py for bugs.",
  options: {
    allowedTools: ["Read","Edit","Glob"],
    permissionMode: "acceptEdits"
  }
})) {
  if (message.type === "result")
    console.log(`Done: ${message.subtype}`);
}
前置Node 20+（或 Python + uv/pip）；API key 认证——官方明确不允许第三方产品走 claude.ai 登录或订阅额度。
辨析Agent SDK ≠ Client SDK（后者是你自己写工具循环的裸 API）；≠ Managed Agents（Anthropic 托管沙箱的独立 REST 产品）；≠ CLI（终端交互面）。SDK 把 Claude Code 的工具、循环、上下文管理做成库。
验证成功tsx agent.ts 输出流式 assistant 消息与最终 result.subtype；Web UI 化即把该循环接到 Fastify/Express WebSocket 上（第 3 章的 fafawlf 是完整范例）。

vultuk/claude-code-web

PTY 直桥 · 排序 A

npx claude-code-web
# → 启动即打印随机 token：

npx claude-code-web --plan max5     # pro|max5|max20

tlive

hooks 旁路 + PTY 包装 · 排序 A
npm install -g tlive
tlive setup   # 向导：经 claude plugin CLI 注册插件
              # （hooks + skill + /tlive:* 命令），
              # IM 凭据可跳过
tlive start   # daemon 启动，打印 web URL + 二维码
tlive run claude   # 可选：包装模式 → 真·web 终端

tlive mode full   # 开远程审批（默认 notify 只通知）
tlive status      # 查看生效模式
tlive mode off    # 总开关（kill switch）
机制hooks/companion 模式骑在 Claude Code 官方 hook 机制上：默认 notify 只推送状态，永不阻塞工具调用；full 模式持有工具调用，让你在手机 Allow/Deny（与本地对话框并行，先答先赢）。wrapped 模式额外持有 PTY，提供 xterm web 终端与 IM 注入。
关键配置~/.tlive/config.json：web.bind 默认 0.0.0.0（局域网手机可达，token 是唯一门），建议改 127.0.0.1；web token 在 ~/.tlive/web-token（0600）；卡片永不携带 dashboard 链接（防 token 入 IM 服务器）。
验证成功普通 claude 会话运行时 dashboard 出现会话卡片（hooks 模式已生效）；wrapped 会话环境变量有 TLIVE_SESSION=<id>。
边界v2 全新重写不兼容 v1 配置，直接 tlive setup 重来；Windows 设计支持（named pipes + ConPTY）但官方自述“less battle-tested”。

# 桌面版（mac/win/linux 安装包，或 brew cask）

purplemux

tmux 持久多会话 · 排序 B
# 前置：Node 20+、tmux；仅 macOS / Linux
npx purplemux@latest
# → http://localhost:8022，Done.

# 全局安装

DEPTH · 同名辨析

fafawlf/claude-code-web 不是 PTY

两个 claude-code-web 同名不同物：vultuk 版是 PTY 直桥（第 2.1 节），fafawlf 版是 Agent SDK 路线（路线 C）的完整参考实现。混淆两者是这条赛道最常见的选型错误。

# 前置：Node 20+；服务器所在机器已有 claude 且已认证
# （claude login 或与 CLI 相同的环境变量）
git clone https://github.com/fafawlf/claude-code-web.git
cd claude-code-web
npm install && npm run build

node server/dist/bin/claudecode-web.js
# → 打印带 token 的 URL：
#   http://localhost:8080/?t=<token>

# CLI 选项
# --port/-p <n>    默认 8080
# --host <addr>    默认 127.0.0.1（保持不动！）
# --cwd <path>     默认当前目录

# 远程机场景：本机起服务 + SSH 隧道
ssh -L 8080:127.0.0.1:8080 user@remote-host
机制ClaudeSession.ts import SDK 的 query()，按 cwd / resume / permissionMode 构造 options，把 SDKMessage 流推给 Fastify WebSocket；permission / plan broker 在浏览器端出审批卡。
与 vultuk 的对照不 attach 现有终端、不显示 TUI 画面；控制的是 Agent 能力面（diff 卡片 approve/reject、plan mode、事件重放、历史 viewer 显式 takeover）。
验证成功浏览器刷新后事件重放恢复现场；diff 卡片可逐个 approve/reject。
边界单用户定位；SSH 多节点执行在 roadmap/受限状态；README 明确非 Anthropic 官方项目。

DEPTH · 平台适配

Windows：先选宿主，再选工具

对应要点 4。Windows 不是“换一套命令”的问题：ConPTY 与 Linux PTY 行为不同、Ctrl-C 与进程树终止语义不同、PowerShell 输出编码影响 WebSocket 数据。三条宿主路线按成熟度排序如下。

DEPTH · 安全边界

WebSocket 可写 ≈ 远程终端输入

对应要点 4 的安全面。PTY Web UI 一旦被未授权访问，等价于远程命令执行入口——这不是“有没有加密”的问题，而是“谁拿到了 stdin”。基线来自 OWASP WebSocket Cheat Sheet 与 ttyd 的默认设计（默认只读、显式开写）。

RISK · 红线
D5-01

这四条不满足就不要部署

· 默认只监听 127.0.0.1；远程访问走 Tailscale / WireGuard / SSH 隧道，绝不 0.0.0.0 裸奔公网；
· WebSocket 校验精确 Origin + 认证（token 至少 0600 权限落盘，参照 tlive 的 web-token 模型）；
· 每个 session 默认单 writer，其余连接只读 observer（多端同时打字 = 输入流污染）；
· 限制连接数、消息大小与 PTY 数量——无界输入可打爆后端。

CHECK · 部署前 checklist
D5-02

照着核对一遍

· 凭证、环境变量、.env 永不进浏览器（fafawlf 与 tlive 都把 token 留在服务端）；
· 日志不记录 token、完整 prompt 与敏感输出（tlive 卡片不携带 dashboard 链接就是这条）；
· 默认拒绝：认证失败即断链，超时回退到本地终端对话框（tlive 的 fail-closed / fallback-is-silence 模式）；
· 自动审批是特权：/trust、Always-allow 类开关必须显式开启、可随时关闭、重启即清；
· 审计：谁在何时连接、谁批准了什么。
