前提检查：你的客户端能读 SKILL.md 吗

这 6 个推荐全部是Agent Skills 形态——交付物是一个文件夹，里面最重要的一份是 SKILL.md。装之前先确认三件事，否则你会装完了发现「没反应」。

装前检查（三条，逐条过）
① 客户端
确认你的 Agent 客户端支持技能目录：Claude Code 系原生支持；Codex、Cursor、OpenCode 等按各自机制接入；纯聊天网页端不支持
② 目录
本机看技能是否落在用户级技能目录，例如 ls ~/.claude/skills/，能列出目录名才算装上
③ 触发
技能不会自己启动，必须由你的话触发：输入是什么、产物交付到哪这两句写不清，技能就退化成普通问答
判断标准很简单：装完之后，你给它的第一句话里如果没有任何具体输入，产出必然是泛泛而谈——这不是技能的问题。
容易踩的三个前提坑
  • Cursor 是另一条路：GSAP 官方 README 给的 Cursor 接法是 Settings → Rules → Add Rule → Remote Rule (GitHub)，也就是说落地在「规则」而不是技能目录，两边内容会各走各的，改一处不会同步另一处。
  • 别一次装 6 个：源文明确提醒，装太多 Skill 会抢占上下文、抬高调用成本；本卡建议按当前任务只装 1-2 个。
  • monorepo 别整包拿：meeting-notes 所在的仓库收录 137 个技能目录（目录树快照），整包装进去会带进大量用不到的技能，只取子目录。

三条安装路径的差别：CLI、插件市场、还是手动复制

同一个 Skill，装法不同决定了你以后能不能干净卸载、能不能审计来源。下表按「落盘位置 / 优点 / 风险」逐条对照，命令均取自仓库原文。

路径命令（原文）落盘位置优点风险 / 代价
skills CLInpx skills add <repo-url>用户级技能目录（由 CLI 决定）一条命令搞定，跨客户端通用通过 npx 拉取执行，供应链要自己确认来源
plugin 市场/plugin marketplace add ...
/plugin install <name>@<market>		由客户端管理，独立于技能目录可版本管理，卸载干净依赖客户端支持插件市场；换客户端要重装

gsap-skills 的 8 个子技能：什么需求该命中哪一个

这是本批里唯一「拆成多个子技能」的仓库。子技能名取自仓库 skills/ 目录实测（8 个目录 + 一份 llms.txt）。你不需要背，但需要知道它的覆盖边界——命中不了的需求，它会给你一个能跑但不好看的动效。

子技能负责什么什么需求会命中它
gsap-core核心 API 与缓动基础「让这个元素动起来」这类最基础的需求
gsap-timeline时间轴编排与序列多元素先后出场、循环、编排节奏
gsap-scrolltrigger滚动驱动动画「往下滚才出现」「滚动过程中变形」
gsap-plugins官方插件用法需要 SplitText、MorphSVG、Draggable 这类能力
gsap-reactReact 集成Next.js / React 项目里挂动画与清理副作用
gsap-frameworks其他框架接入Vue、Svelte 等非 React 技术栈
gsap-performance性能与掉帧动画卡、移动端发热、要上 transform 优化
gsap-utils工具函数随机、插值、单位换算等辅助逻辑
llms.txt给模型读的摘要索引不是给机器执行的技能，而是让模型快速对齐 GSAP 知识面
读法：如果你只是让 Agent「加个动效」，它可能只命中 core；想要滚动叙事就明确说「滚动驱动」，想要 React 集成就在需求里点名技术栈——命中哪个子技能，直接决定产出质量。

guizang 产品视频：7 步流程拆开看，哪一步最花时间

这是本批唯一「进不了开源许可舒适区」的技能：仓库许可是 AGPL-3.0，仓内另有 COMMERCIAL_LICENSING.md。流程与模式取自该仓库 README。

7 步流程（README 原文顺序）
  1. 定范围：先选定要讲哪个产品、哪个版本，范围不定后面全是返工
  2. 找真实内容：从代码库、文档、截图里取素材，避免编造卖点
  3. 定方向：在 repo / default / hybrid 三种风格里选一种
  4. 逐镜头搭建：以 GSAP 主时间轴串起每个镜头
  5. 配声音：音乐与音效，决定成片的完成度
  6. 审片导出：逐帧检查后导出成片
  7. 出封面：同时给 3:4 / 4:3 / 16:9 三种比例
技术栈与产物（官方声明）
主时间轴
GSAP，负责镜头串接与节奏
背景
Three.js / canvas 层，做视觉纵深
驱动
真实组件驱动，而不是套模板抽卡
产物
产品介绍视频 + 三种比例封面
风格
repo（贴代码仓库）/ default（通用介绍）/ hybrid（混合）
许可
AGPL-3.0；商用前先读 COMMERCIAL_LICENSING.md
最花时间的是第 1、2 步。仓库状态显示它最后提交在 2026-09-25，是本批里最活跃的项目之一；但流程把「范围 + 真实素材」放在最前面，说明作者认为返工主要来自这两步，而不是渲染。

执行成本对照：什么时候调用、输入要写多细

同一句话丢给不同的技能，成本差一个量级。下表把「触发语 / 输入粒度 / 一次产出 / 上下文开销」并排，用来决定当下开哪个技能。

技能触发语怎么写输入要写多细一次产出上下文开销
gsap-skills「给这个页面加滚动驱动动效」页面结构 + 想要的感觉 + 技术栈动效代码与参数中（会读多个子技能）
research-to-diagram「把某某做成一张关系图 / 研究报告」一句问题 + 期望视角（人物、体系、时间线）图谱 + 研究报告 + PDF高（搜索 + 绘图长链条）
copywriting「写这个产品的首屏文案 / 10 个标题」产品定位 + 受众 + 可用的数据口径标题群 + 首屏文案低-中
lieflat「这篇有 AI 味，按清单清一遍」成稿文本（它只清稿，不写作）只改命中清单的句子低
guizang「把这个产品做成介绍视频」产品仓库 / 文档 / 截图 + 时长与比例HTML 视频 + 三比例封面高（多镜头渲染）
meeting-notes「把这段会议转写整理成纪要」转写原文（有角色名更好）结构化纪要低
排序建议：先把「低开销、当天就能验证」的两个装上（lieflat、meeting-notes），用一周确认它们真的省时间；再考虑 research-to-diagram 与 guizang 这类长链条、高开销的技能。

一页速查：装、用、退

装（三选一）
# A. 通用 CLI
npx skills add <repo-url>

# B. Claude Code 插件市场

用
  • 说清三件事：输入（你手里有什么）、产物（要什么格式交付）、边界（不要什么）
  • GSAP 类要顺手说明技术栈（React / Vue / 原生），否则它只能给通用写法

退（卸载与回滚）
手动 / cp 装法
rm -rf ~/.claude/skills/<name> # 删目录即回滚
插件市场装法
用客户端的卸载指令移出插件，再在 marketplace 里移除来源
CLI 装法
按该 CLI 的移除提示操作；留在目录里的副本要手工确认
通用原则
同一个技能不要混装两份；装之前先记下装到哪，退的时候才知道删什么

装上之后的第一周：怎么判断它值得留着

技能装上不会自动产生价值，前七天是它最容易变成「装了但从来不用」的阶段。下面五条是可在一天内做完的检查，做完你就有依据决定留、改、还是删。

五条检查（按顺序做）
  1. 装对了吗：确认技能落在你的技能目录里，能列出目录名；插件装法在客户端里能看到条目
  2. 触发一次真实的活：用你当天本来就要做的一件事去触发它，不要用「随便试一下」的任务——试不出价值
  3. 记下三行：输入写了什么、产物是什么、你改了多少。第三行最关键：改得越少，说明它真的懂这件事
  4. 换一个变量再跑：同一技能换一个输入（不同项目、不同文档），看它是稳定输出，还是只对第一次的样例有效
  5. 一周后裁决：连续用不到两次的技能直接卸掉；它占的不只是磁盘，还有每次对话的上下文预算
判断标准（别凭感觉）
值得留
同一类任务连续两次都能直接用，或把你的返工时间从小时级压到分钟级
需要改
流程对、细节不对（比如输出格式、维度划分）——直接改它的 SKILL.md，别每次在对话里重述要求
该删掉
需要你反复解释前提才能用；或它做的事你自己三句话就能说清
常见误判
把「第一次演示效果好」当成长期可用；把「装了很多」当成能力强
一条经验：技能的价值不在安装数，而在你能否说清「我在什么场景下会想起调用它」。说不清的那几个，卸掉之后你的 Agent 反而更准。
