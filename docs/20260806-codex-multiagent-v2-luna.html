Codex MultiAgent V2 与 GPT-5.6 Luna 兼容性限制

根因：V2 主动通信能力门槛 · 官方明确排除 Luna 子 Agent 角色 · Thread 编排成为事实标准方案

根因明确 官方确认 Workaround 稳定
GitHub Issue #34301 ↗ Issue #36294 ↗
01

问题定义与影响

当用户以 GPT-5.6 Sol 或 GPT-5.6 Terra 作为主 Agent，通过原生 spawn_agent 创建 GPT-5.6 Luna 子 Agent 时，系统统一返回：

⚠
Unknown model gpt-5.6-luna for spawn_agent.
Available models: gpt-5.6-sol, gpt-5.6-terra

该限制自 MultiAgent V2（2026 年 7 月中下旬）稳定后集中爆发，核心影响：

  • 边界清晰、可并行的小任务被迫使用更昂贵的 Sol/Terra 作为子 Agent，额度快速消耗
  • 与 Luna 降价 80% 后的定位严重冲突
  • 破坏"主模型规划 + 便宜模型执行"的分层使用模式
02

技术根因

2.1 模型目录静态标记

通过 codex debug models 直接观察：

模型multi_agent_version
gpt-5.6-solv2
gpt-5.6-terrav2
gpt-5.6-lunav1

2.2 V2 兼容性过滤逻辑

PR #32751 引入了严格的后端兼容检查（相关代码引用自 GitHub Issue #34301）：

pub(crate) fn model_supports_multi_agent_backend(...) -> bool {
    multi_agent_version != MultiAgentVersion::V2
    || model.multi_agent_version == Some(multi_agent_version)
}

父会话运行在 V2 时，只允许 spawn 同样标记为 V2 的模型。Luna 作为顶级会话时可正常工作（runtime 实际为 v2），但 spawn_agent 使用静态 catalog 标记过滤，导致被拒绝。

2.3 关键不一致（Issue #36294）

  • Luna 在模型选择器中可见，也能作为顶级会话运行
  • 错误信息"Unknown model"具有误导性——并非 Luna 不存在
  • 强制开启 features.multi_agent_v2 = true 后，顶级 Luna 的 turn_context.multi_agent_version 可以变为 "v2"，但子 Agent 仍被过滤
03

官方立场

Codex DX 工程师 @pvncher（Eric Provencher）在 2026 年 7 月 30 日–8 月 2 日多次公开表态：

💬

"It's because Luna is not multi-agents v2 compatible, which is required for it to be used as a sub agent."

"Multi agents v2 requires proactive inter agent communication, which only Sol and Terra do well."

"Terra and sol are certified to do it well."

对强制修改的态度：

⚡
"I do not recommend messing with your model catalog to force capabilities that are not natively exposed."

当前推荐方案（Thread 编排）：

✓
"A workaround is to use the thread orchestration tools to launch standalone luna threads and wait for them. The workaround right now is the app's thread automation tools."

官方逻辑：MultiAgent V2 要求 Agent 之间具备主动、可靠、路径式身份的通信能力（send_message、followup_task、mailbox 等）。官方测试认为 Luna 在这种协作质量上不足，因此刻意排除。

04

解决方案评估

方案占比官方态度稳定性核心评价
Thread 编排55–65%明确推荐高稳定，透明、官方背书、完全支持 Luna
强制修改 Catalog15–20%明确不推荐中低能恢复原生 spawn，但有兼容与更新风险
Custom Agent TOML10–15%中立中结构化，但常无法真正绕过 V2 过滤
回退 V1 / 外部工具8–12%—中简单，但失去 V2 新特性

Thread 编排最小可运行 Prompt

请使用独立线程方式处理以下工作：
1. 创建 1 个 gpt-5.6-luna max 线程，负责：[任务A完整描述，包含文件路径、范围、验收标准]
2. 创建 1 个 gpt-5.6-luna max 线程，负责：[任务B完整描述]
要求：
- 每个线程的任务描述必须完全自包含（它们看不到当前对话）
- 创建后立即发送任务并启动
- 你负责监控进度，必要时直接给对应线程发送修正指令
- 全部完成后统一汇总结果给我

进阶分工模式

  • 主线程：Sol High/Max 做规划与最终审查
  • 执行层：统一使用 Luna Max 独立线程
  • 在 AGENTS.md 中固化规则，让主 Agent 自动采用此模式
05

推荐结论

短期最佳实践
  1. 接受当前限制，不强制修改 catalog
  2. 采用 Sol 主控 + Luna Max 独立 Thread 分工模式
  3. 在 AGENTS.md 或技能中固化 Thread 派发习惯
  4. 边界清晰任务 → Luna Max 线程；强协作任务 → Sol/Terra 原生子 Agent
中长期展望

官方已公开表示"团队知晓并在考虑更好方案"。若未来将 Luna 升级为支持 V2 主动通信，该问题有望从根源解决。

在此之前，Thread 编排是当前最稳健、最受官方支持的路径。
