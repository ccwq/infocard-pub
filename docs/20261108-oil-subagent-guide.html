会产生大量中间过程信息、但最终只需要一份精简摘要或改动结果的任务——交给子 Agent。
要点 1

判断标准只有一句

大范围代码检索、只读 code review、测试日志分析、多方案并行评估，全都符合"过程信息多、回传结果少"。

要点 2

三层配置架构

全局配置管边界（并发、嵌套层级）→ 角色配置文件放 ~/.claude/agents/ 或 ~/.codex/agents/ → 调度 Skill 管什么时候派谁。

要点 3

四个角色各配各的模型

Explorer 用最便宜快档吃检索，Executor 用执行型，Reviewer 保持无历史上下文的独立视角，专项长板按需加专家顾问。

要点 4

Skill 管调度，配置文件管执行

执行规范写进子 Agent 自己的配置文件；写进 Skill 则主 Agent 每次派发都要把整段规范重新输出一遍。

要点 5

子 Agent 不天然省钱

派发本身有额外 Token 开销；划算的前提是用便宜得多的模型差价把它抵消掉。

要点 6

派不派由主 Agent 决定

作者的经验做法：提前配好角色与调度规则，让主 Agent 按任务复杂度自己判断，很少下强令。

01判断标准与适用边界
如果一个任务会产生大量的中间过程信息，但最终只需要一个精简的摘要或改动结果，那它就非常适合交给子 Agent。

子 Agent 不直接和你对话：它只接收主 Agent 分配的任务，在自己独立的上下文里执行完，再把结果汇报给主 Agent。单窗口从头干到尾的问题是上下文膨胀——探索代码、读文件、看日志几轮下来话题就塞满了，触发压缩后最早谈好的需求和约束会变模糊。

适合派发的四类场景

过程信息多、回传结果少

① 大范围代码搜索：子 Agent 翻十几个文件，只把文件路径、行号和结构摘要交回；② 只读 code review：没有历史对话包袱，只盯本次变更；③ 测试日志分析：子 Agent 先在日志里定位核心报错再返回；④ 多方案并行评估：各评各的，结论汇总给主 Agent 决策。

不要并行的三类任务

会互相覆盖、必须串行、高风险

① 多个子 Agent 同时改同一片文件，容易互相覆盖难以合并；② 下一步完全依赖上一步结果（先改表结构才能写接口）；③ 部署、删数据、改核心配置这类高风险动作，留在主话题由主 Agent 配合你谨慎执行。

谁来决定派不派？作者的日常做法是把角色和调度规则提前配好，由主 Agent 根据任务复杂度自己判断；只有当它一直不主动派发、而作者确实需要提速或并行时，才明确提醒它调用。

02三层配置架构

不管用哪款支持子 Agent 的工具，管好自定义子 Agent 都遵循同一套三层架构：

第一层 · 全局配置默认模型 / 最大并发 / 嵌套层级
→
第二层 · 角色配置文件~/.claude/agents/ 或 ~/.codex/agents/
→
第三层 · 调度 Skill什么时候派谁
全局配置

控制运行边界

设置面板的 Configuration 或主目录全局配置文件里，定默认模型、最大并发数（作者举例默认同时 6 个）和最大嵌套层级。嵌套保持最多一层：只让主 Agent 派发，禁止子 Agent 再套娃。想改可以直接让主 Agent 帮你改。

角色配置文件

放角色专属知识与模型

每个角色一个独立配置文件，存放在 ~/.codex/agents/ 或 ~/.claude/agents/，定义名字、模型、思考强度和内置系统提示词。格式因工具而异（Markdown 或 .toml），不用手写——让主 Agent 自己生成（见第 04 节）。

调度 Skill

约束主 Agent 的调度行为

告诉主 Agent：什么规模的任务派哪类子 Agent、什么时候把对话历史带给子 Agent、什么时候复用已启动的子 Agent。作者在 Codex 里用的是开源调度 Skill codex-team-mode，按需触发而非塞进每次必读的全局规则文件。

关键原则：Skill 管调度，子 Agent 配置文件管执行

Skill 是给主 Agent 读的。把执行规范（前端规范、审查清单）全写进 Skill，主 Agent 每次派发都要把整段提示词重新输出一遍给子 Agent，输出和上下文双涨。写进角色配置文件后，前端子 Agent 内置前端规范、后端子 Agent 内置后端规范，主 Agent 派活只需一句"看一下某位置的代码"。

为什么值得定制？作者经验：不同主 Agent 调度能力差异明显——Claude Code 需要探索时会较积极地调用子 Agent，Codex 默认往往不主动调用，需要提前预定规则和角色。另外子 Agent 可以单独指定系统提示词和模型，专项场景配刚好够用的便宜模型，既省主 Agent 上下文又省额度。

03四个角色与模型策略

作者不按任务难度切细碎角色，而是按专项职责与模型长板划分四个角色。下表模型档位均为作者举的自己日常在用的例子（GPT Luna、GPT-6 Astra、Gemini 等），他本人强调：掌握分工理念即可，不绑定模型名。

角色职责模型策略理由
Explorer 探索者只读，在代码仓库定位文件与行号、动手前调研最便宜、响应最快档（Codex 用 GPT Luna 档开快速模式；Claude Code 对应 Haiku 档）探索只靠检索与整理报告，对推理要求低；放心并行扫几十个文件
Executor 执行者修改代码等边界明确的执行任务执行型模型，不强求规划与沟通能力作者经验：轻量模型单独当主 Agent 召回弱，但主 Agent 已把要读的规范、要改的文件交代清楚，短板正好被避开，成本极低
Reviewer 审查者代码审查：过度复杂化、多余防御分支、组件拆分、重复造轮子独立启动，不带主 Agent 的历史上下文同一话题里聊了很久的 Agent 会顺着思维惯性走；子 Agent 上下文独立，只盯本次变更，判断更准
专项长板 / 专家顾问写文案、疑难攻坚文案用文笔自然的模型（作者举例 Gemini）；疑难 Bug 连改几轮未修好或跨模块架构设计，才唤起最贵档专家顾问（作者举例 GPT-6 Astra）最贵模型全程挂主话题额度很快见底；按需唤起才划算

把角色串成协作闭环

开发前 Explore并行派 Explorer 摸清路径，只带回关键位置与结构摘要
→
主 Agent 定方案基于精简摘要制定计划
→
Executor 落地边界明确的执行
→
完成后 Simplify拉起 Reviewer 独立审查，砍掉冗余后再交付

这套"开发前探索 + 完成后审查精简"的闭环，作者已直接集成在开源的 codex-team-mode 里。

04动手任务 · 一分钟创建只读 explorer

配置文件格式不用你手写——直接在对话框对主 Agent 说清楚三件事：名字、职责与规范、模型与思考档位。照下面五步跑一遍：

  1. 发一句话：在 Claude Code 或 Codex 的对话框里，对主 Agent 原样说（可改名字与职责）：
// 对主 Agent 说
帮我创建一个名叫 explorer 的自定义子 Agent，权限设为只读，专门用来在代码仓库里快速定位相关文件和行号并汇总成简短报告，模型请配置为你支持的最便宜一档的轻量模型。
  1. 等主 Agent 自动生成配置：它会自己查内置配置文档，在 ~/.claude/agents/ 或 ~/.codex/agents/ 目录下生成配置文件，不用你翻格式文档。
  2. 预期观察：创建完成后，在输入框输入 @，角色列表里应出现刚建好的 explorer。
  3. 验证生效：对主 Agent 说"用刚创建的 explorer 子 Agent 帮我看一下项目的目录结构"，确认它真的派发并回传了简短报告。
  4. 失败时的下一步：若 @ 列表里没有它，先确认配置文件确实生成在上面的 agents 目录、角色名没写错，再把名字、只读权限、模型档位三件事补交代清楚，让主 Agent 重新配置一次。
05进阶 · 派发外部 Agent 当子 Agent

原生子 Agent 通常只能调用自家体系的模型。想让主 Agent 派发另一个独立 Agent（比如在 Claude Code 里派 Codex 写代码），最简单的方式是利用"Agent 能执行命令"这一点，按三层递进封装：

① 直接调 CLIClaude Code、Codex、Kimi CLI 等都支持终端传一句提示词执行任务
→
② 封装成 SkillSKILL.md 写清调用格式与触发场景，主 Agent 见到即会用
→
③ scripts/ 封装脚本屏蔽权限参数、工作目录、session_id 差异，过滤日志噪音

第三层是关键：各家 CLI 的只读/权限参数与会话续接写法各不相同，现场拼命令容易错；命令行还会打印一大串读取文件和 JSON 事件流，直接返回会塞满主话题上下文。把复杂度收进脚本内部，主 Agent 只需说"用 cc 检查这个仓库的登录流程"或"让 codex 修复这个测试"。

06避坑三条 + 边界与行动
避坑 1

别用贵模型探索代码

只让主 Agent 上下文膨胀慢一点，子 Agent 照样高价大口吃几十个文件的 Token。创建角色时务必检查模型配置——作者早期就踩过子 Agent 默认继承主话题高价模型的坑。

避坑 2

派发本身有额外开销

每个新子 Agent 往往要重读项目规范和背景，派活要输出提示词，干完还要输出报告。同时启动三个，基础读取叠加三次。划算的前提：模型差价足以抵消多出的 Token。

避坑 3

简单任务直接主 Agent

顺手改一两个已知文件的文案或样式，启动子 Agent 反而费时：组织派发提示词、拉起、等待返回。把它留给真正会产生大量中间信息或需要并行的任务。
