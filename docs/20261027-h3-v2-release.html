它是什么

构建在 Web 标准（Request、Response、URL、Headers）之上的 TypeScript HTTP 框架；v2 是完整重写，官方声明与多数 v1 工具保持兼容。

① v2 改了什么：Web 标准重写

v2 把 handler 建立在标准 Request / Response 之上：handler 收到 event.req（标准 Request）与 event.url，响应头经 event.res 设置。返回值可以直接是字符串、对象、Response、流、Blob 等，由 H3 负责转成 Response。

import { H3, serve } from "h3";

const app = new H3();

app.get("/hello", defineHandler(async (event) => {
  event.res.headers.set("x-powered-by", "h3-v2");
  return { ok: true, url: event.url.pathname };  // 对象自动转 Response
}));

serve(app, { port: 3000 });

约定与示例依据官方 v2 公告 h3.dev/blog/v2（handler/event/返回值）。

② 性能数字怎么读：基准表 + 官方 caveat

数字来自官方 v2 beta 公告（h3.dev/blog/v2-beta）的基准表格，测的是「请求处理耗时」即框架自身开销：

运行时v1 耗时v2 耗时官方倍率
Node36 µs7 µs5x
Bun27 µs3 µs9x
Deno7 ms1.2 µs156x

体积：min 101 kB → 9.1 kB（官方标 91% smaller）；min+gzip 39.6 kB → 3.6 kB（90% smaller）；fetchable handlers 形态 5.2 kB / min+gzip 2.1 kB。

官方 caveat（与上表同框阅读）：基准只测 H3 core 的 Web Standard target，不含 adapters；目的是内部优化参考。官方 TIP：v2 的性能与「裸 fetch handler + new URL(req.url).pathname 路由」几乎相同——也就是说优化空间来自贴近平台原生能力，而不是框架黑科技。

Node 场景的桥接成本由 srvx 兜底：官方 bench-node 标称最高达到原生 node:http 性能的 96.98%。

以上均为官方基准口径，本文未在本机复测；引用时请带上同一段 caveat。

③ 路由、中间件与内置能力

路由基于 rou3 v1，采用 URLPattern 风格语法（命名参数、正则约束、可选与重复参数、分组、通配符），按段树匹配；与 URLPattern 的有意差异是忽略单个尾部斜杠：

app.get("/users/:id(\\d+)", ...);        // 正则约束
app.get("/blog/:id(\\d+){-:title}?", ...); // 可选参数
app.get("/files/:path+", ...);            // 重复参数（通配）

中间件是 (event, next) 签名，内置 onRequest / onResponse / onError / basicAuth / bodyLimit 等 helpers，用 definePlugin() 封装可复用插件：

const logger = defineHandler((event, next) => {
  console.log(event.req.method, event.url.pathname);
  return next();
});

一组路由的横切配置走 h3/rules 的 routeRules()，一个对象同时给 headers、redirect、CORS、缓存、代理：

routeRules({
  "/old/**":   { redirect: "/new/**" },
  "/assets/**":{ headers: { "cache-control": "s-maxage=31536000" } },
  "/api/**":   { cors: true },
});

内置工具清单：cookies（含 chunked cookies）、sessions、CORS、代理、静态文件、缓存头、SSE、经 crossws 的 WebSockets、JSON-RPC / MCP helpers、h3/tracing 插件。类型安全覆盖 handler、响应与 HTTPError；validated handlers 兼容 Standard Schema 校验库（Zod、Valibot 等）。

依据 h3.dev/blog/v2 路由 / 中间件 / rules / 内置工具各节。

④ 十分钟上手：从 install 到 curl 验证

前置条件只有一个：Node >= 20.19.0（package.json engines.node 与官方公告一致）。

npm install h3

新建 server.mjs，贴入官方公告的最小服务：

import { H3, serve } from "h3";
const app = new H3().get("/", () => "⚡️ Tadaa!");
serve(app, { port: 3000 });
node server.mjs curl http://localhost:3000

curl 返回 ⚡️ Tadaa! 即验证通过。从 v1 升级：多数 v1 工具继续可用，已废弃的 v1 名称仍导出以便迁移；升级前先对照 h3.dev/migration 过一遍现有用例。

安装与代码来自 h3.dev/blog/v2 快速开始；版本要求来自仓库 package.json（v2.0.8）。

⑤ 与 Hono 怎么选：观点归属

来源文章观点（微信文章《尤雨溪力荐的 H3，v2 正式发布！性能狂飙 9 倍！》，前端开发爱好者，作者 xy）：Hono 偏向直接开发 API 与 Web 应用、中间件生态成熟；H3 偏向可组合的底层 HTTP 引擎，适合 Nuxt / Nitro 生态与跨运行时部署。

官方生态定位（v2 beta 公告）：Nuxt 的服务端能力经 Nitro 实现，H3 是 Nitro 的 HTTP 底层，且有 H3 + Nitro 在 worker 环境的部署历史。

两条口径一个来自第三方文章、一个来自官方页面，本文不替读者下结论；选型时建议各自跑一遍自己的典型路由再定。

来源文章：mp.weixin.qq.com/s/OmruxRmnTwUb0arQE0aC8A（发现渠道）；官方：h3.dev/blog/v2-beta。

⑥ 边界与行动

适用
  • 多运行时 / 边缘函数部署（Node、Bun、Deno、Cloudflare Workers 同一份代码）
  • Nuxt · Nitro 生态的服务端开发
  • 希望贴近 Web 标准、少依赖运行时专有 API 的新项目
暂不适用
  • Node 版本低于 20.19 的运行环境
  • 深度依赖 Node 专有 API 且短期迁移不了的旧服务
  • 把官方基准数字（如 156x）当作业务收益预期的决策
验证方法
  • 新项目：按第④节跑最小服务，用 curl http://localhost:3000 确认
  • 升级项目：先在 v1 上固化测试用例，再对照 h3.dev/migration 逐项迁移并复跑用例

兼容性边界依据官方公告与 package.json engines 字段。
