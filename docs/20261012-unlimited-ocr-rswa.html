01 · 问题背景：LLM-OCR 的速度衰减困境

传统 LLM-OCR 的瓶颈

  • KV cache 随输出 token 数持续积累，显存 O(n²) 增长
  • 每生成一个 token 都需与全部历史 token 做注意力计算
  • 文档越长，生成速度越慢，显存消耗越大
  • 长文档（40+ 页）OCR 实际不可用

人类的抄写优势

  • 翻页时只记住当前页内容，无需「记住」已翻过的每一行
  • 阅读速度不随书页增加而衰减
  • 工作记忆容量有限但稳定
R-SWA 的核心洞察：视觉 token（图像侧）只编码一次，全程静态；文本 token（解码侧）只看最近的 128 个，其余存入固定容量队列。KV cache 容量恒定，注意力计算开销恒定。
实验数据：10K 视觉 token（≈20-30 页）解码 100K+ text token 时，传统方案已崩溃，R-SWA 仍匀速运行。

02 · R-SWA 工作原理

DeepEncoder（冻结）

SAM-ViT + CLIP-ViT 级联
1024×1024 → 256 token
视觉 token 一次性编码，静态不变
不参与解码状态转移

→

R-SWA Decoder（训练）

3B MoE（激活 500M）
看全部视觉 token
文本只看最近 128 个
KV cache = 固定容量队列

文本 token 的固定窗口（宽度 n=128）

  • 每个新 token 生成时，参考窗口覆盖最近 128 个已生成文本 token
  • 历史信息通过固定缓冲区「软遗忘」地持续流入
  • 模型学会在有限窗口内定位自己的「抄写进度」
  • 实验证明：在密集 OCR 任务上，128 宽度足够且无损

视觉 token 的全局注意力

  • 生成每个文本 token 时，始终可以「看到」全部图像视觉 token
  • 图像信息一次性编码，解码全程引用，无需重复计算
  • DeepEncoder 将 1024×1024 图像压缩为 256 token（16×32 窗口压缩）
  • 预填充阶段（prefill）显存极低

04 · 模型架构详解

编码器：DeepEncoder（来自 DeepSeek OCR）

  • SAM-ViT + CLIP-ViT 级联架构
  • 桥接层 16×32 token 压缩
  • 窗口注意力处理原图 token，全局注意力仅用于压缩 token
  • 原生两种分辨率模式：Base（1024×1024，多页）/ Gundam（动态分辨率，单页）
  • 冻结训练，仅微调解码器

解码器：3B MoE LLM + R-SWA

  • 总参数量：3B
  • 激活参数量：500M（MoE 稀疏激活）
  • 所有标准 MHA 替换为 R-SWA
  • 参考 KV cache（视觉侧）+ 固定容量输出缓冲区（文本侧，宽度 n）
  • 输出格式：Markdown / JSON / 表格（数学公式支持）

08 · R-SWA 的技术细节

R-SWA 与标准滑动窗口注意力的区别

  • 标准 SWA：每个 token 只看局部窗口，历史信息完全丢失
  • R-SWA：每个 token 仍可「看到」全部视觉 token（参考 KV cache），同时用固定窗口处理文本 token
  • 视觉侧：参考 KV cache（静态，一次编码）
  • 文本侧：固定容量输出缓冲区（宽度 n，宽度=128）
  • 两者结合：保持全局感知的同时，将 KV cache 固定在常量级别

为什么 n=128 是最优的？

  • 实验覆盖 n=64, 128, 256，128 在准确率和效率上平衡最佳
  • TEDS（表格识别）提升 5.96%：证明历史信息通过窗口持续流入
  • 文本编辑距离下降 0.035：模型在有限窗口内能清晰定位「抄写到哪了」
  • 注意力计算从 O(n²) 降低到 O(n)（n=固定窗口宽度）

10 · KV Cache 的数学：为什么传统方案会崩溃

标准 Transformer 的 KV cache 复杂度

  • 输出第 N 个 token 时，注意力矩阵为 N×N（N = 已生成的 token 数）
  • KV cache 存储历史所有 key 和 value 向量：O(N) 空间
  • 注意力计算：O(N²) 时间（与所有历史 token 计算点积）
  • 当 N=100,000（长文档），KV cache 体积巨大，GPU 显存溢出
  • 计算量也随 N 平方增长，生成速度越来越慢

R-SWA 的复杂度分析

  • KV cache 分为两部分：视觉侧（静态，编码一次）和文本侧（固定容量 n）
  • 视觉侧 KV cache：恒定大小 = 图像 token 数 × hidden_dim × 2（K+V）
  • 文本侧 KV cache：固定大小 = n × hidden_dim × 2（宽度 n=128）
  • 注意力计算：O(1) 而非 O(N)——每步只与固定窗口交互
  • 显存恒定，计算恒定，生成速度不随文档长度衰减
与 MoE（混合专家）架构的协同：Unlimited OCR 选择 3B MoE（激活 500M）而非 dense 模型，正是为了在固定注意力开销下最大化模型容量。MoE 的稀疏激活确保每步只激活 500M 参数，而 R-SWA 保证这些激活的计算量恒定——两者结合实现「又大又快的 OCR」。

12 · 典型 Pipeline 示例：从 PDF 到 Markdown

完整工作流：PDF → PDF 渲染为图像 → DeepEncoder 编码 → R-SWA Decoder 生成 Markdown/JSON → 后处理（表格格式化 / 公式渲染）

Step 1: PDF 渲染

  • 使用 pdf2image / PyMuPDF 将每页转为 1024×1024 PNG
  • Base 模式适合多页批量，Gundam 模式适合动态分辨率单页
  • 渲染 DPI 建议 ≥ 150，否则小字体会模糊

Step 2: 模型推理

  • DeepEncoder 将图像压缩为 256 个视觉 token
  • R-SWA Decoder 从空 KV cache 开始，逐步生成文本
  • KV cache 全程恒定，显存不随生成增长
  • 输出格式可选：Markdown、JSON（结构化）、原始文本
