03 · 一句话总结

anatomy 是什么

给 Claude 一句话，直接生成会动的复杂机械解构图。

——Ryan（@wheresryan22）开发 · GitHub 418★ · MIT 协议 · npm 包名 anatomy-figures · 2026-10-09 发布 33 张图

anatomy 官网的首页标语原文是：

"Name an idea in one line, and Claude draws the machine that does it."
——用一句话命名一个想法，Claude 画出真正做这件事的机器。

核心理念写在 SKILL.md 最顶部，是整个技能的设计原点：

The object is the explanation.（对象即解释）

这意味着：Claude 不能生成一张「标注了各部分名称的方块图」，而必须发明一台真实工作的机械——它的运转本身就是概念的解释。如果机器不工作，解释就失效。官网列举了两个失败模式：「太抽象」（堆叠的板块和漂浮的标签）和「太扁平」（一个大板块上画几条线，没有体积感），两者的解药是同一剂：一台由许多小型零件构成的可识别机器，每个零件都有具体功能。

04 · 震撼点拆解

「会动的」意味着什么

「会动的」不是 CSS 补间动画（tween animation），也不是简单的旋转或缩放。anatomy 的动效系统有三个技术层次：

层次一：逐帧渲染（Frame-by-frame）

每一帧都是 Claude 根据物理模型精确计算出的独立状态快照。不是两帧之间的时间点由浏览器自动插值，而是每一个时间点都有 Claude 实际计算出的机械位置。官网机械表例子：38 秒 × 30fps ≈ 1,140 个独立帧状态，每一帧的齿轮角度都来自真实的传动比计算 ❓

层次二：画家序算法（Painter's Algorithm）

零件按深度从远到近渲染，确保近处零件正确遮挡远处零件。官网明确说明零件按深度排序（byDepth），这保证了等轴测投影的视觉正确性——齿轮的啮合面看起来是「啮合」而非「穿模」。

层次三：SVG + WebGL shader 混合

主体机械结构是精确的 SVG 路径，在其上叠加 WebGL 着色器（fire / water / plasma / moving air / light）。两层叠加使用同一套等轴测相机视角，shader 特效不会破坏机械的几何精度。

官网原文：「Every number it shows comes from the same model that moves them」——每个数字都来自驱动运动的同一套数学模型，数字与运动始终保持物理一致。这不是伪随机数值模拟，而是真实的物理计算结果。

Ian 所说的「逐帧动效细节做得太讲究了」，指的正是这种「每一帧都精确」而非「视觉上凑合过得去」的工程水准。对于一个在 AI 工具生态见多不怪的资深开发者来说，这种细节精度是触发「震撼」的直接原因。

05 · 震撼点拆解

「复杂机械」意味着什么

「复杂」不是形容词，而是可量化的数字。anatomy 将输出分为三个可预期的尺寸级别，官网明确给出了每级的零件数和时间预算：

尺寸级别零件数渲染要求典型耗时构建方式
Figure 40–80 个 SVG，最多一个 shader 30–90 分钟 Claude 自动构建，无需确认
Hero 80–150 个 多 shader 或一个转动件 2–4 小时 Claude 先报估算，再构建
Epic 整车 / 建筑 / 工厂级 整体机器概念 6 小时以上 必须用户确认后开始

官网展示的机械表机芯属于 Hero 级别，包含的零件有：发条盒（mainspring barrel）、中心轮（centre wheel）、第三轮（third wheel）、第四轮 / 分轮（fourth wheel / minute wheel）、擒纵轮（escape wheel）、擒纵叉（pallet fork）、摆轮游丝（balance wheel and hairspring）……每个都是独立建模的实体零件，齿轮精确遵循真实传动比（如第四轮每分钟转一圈，中心轮每小时转一圈）。

官网原文：「Every figure is made of dozens to hundreds of small solid parts, and every number it shows comes from the same model that moves them.」——每张图由数十到数百个小型固体零件构成，每个数字都来自驱动它们的同一套模型。

Ian 推文附图展示的正是这种级别的细节：齿轮的几何精度、连杆的运动轨迹、整体等轴测视角的立体感——这些视觉细节共同支撑了「太讲究了」的判断。

官网在「Objects, not diagrams」章节还展示了多张其他概念的解释图：队列（弹珠滑道）、LRU 缓存（书架）、DNS 解析（气动管）、消息队列（弹珠跑道）、TCP 握手（缆车索道）、Bloom filter（水果机）——每一个都是将抽象概念发明成真实机械，并精确渲染 ❓

06 · 视觉震撼

「网页图标和逐帧动效细节」——官网视觉系统

anatomy 官网的 33 张图全部采用等轴测投影（isometric projection）——三维物体在二维平面上的精确投影，保持长度和角度不变，产生「立体感 + 精确感」的双重视觉效果。每个表面的四调明暗系统：

色调层含义浅色主题暗色主题
Top（亮面）面光源正上方#ffffff#1c1c1c
Shade 3（亮侧）面朝光源的侧面#f4f4f1#181818
Shade 1（暗侧）略背光的侧面#e5e5e2#121212
Shade 0（最深）最远离光源的侧面#dcdcd9#0f0f0f

配色系统还包括线条层（六种粗细和透明度：hi / mid / lo / faint / dot / halo）和强调色（红 #e5484d / 绿 #30a46c / 蓝 #3e63dd，官网明确写道「used only where colour is the subject」——只有在颜色是主题本身时才使用）。SVG 路径精确渲染每个零件轮廓，官网写道：

None of these were drawn by hand. Each one started from a single line naming the idea.

没有一张图是手绘的，全部由 Claude 代码生成。这意味着：无论你要求生成什么概念，Claude 都会从头「发明」这台机器（而非从素材库调取模板）。官网的设计系统还提供了大量可自定义的 CSS 变量（如 --anatomy-weight: 0.6px 统一线宽、--anatomy-halo-opacity 控制阴影透明度），让每张图在嵌入其他网站时可以保持视觉一致性。

anatomy 与普通 SVG 图表的区别

普通 SVG 图表 = 手绘或模板 → 零件数量有限 → 视觉一致性差；anatomy = 代码生成 → 零件数量可精确控制 → 所有图共享同一套视觉系统 → 嵌入任意网页均可保持一致的等轴测风格。

07 · 稀缺性分析

为什么这类 skill 稀缺

Claude Code 本身是什么

Claude Code 是一个 Agent harness（智能体驾驭系统）。它的核心能力是「操作代码、运行命令、操作文件系统」——面向的是软件开发者的执行层，而非表达层。

大多数 Claude Code skill 都在扩展这个执行维度：代码补全、终端命令、文件读写、项目脚手架……它们让 AI 更会干活，但没有改变 AI 的「表达语言」。

在此之前，Claude Code 的输出天花板是「写文字」或「写代码」，无论多复杂，形态都是文本或文件。

anatomy 做了什么不同

anatomy 扩展了 Claude Code 的输出维度：从文字变成可交互的等轴测机械图。

它让 Claude 从「写代码」升级到「发明一台真机器并画出来」——这是前所未有的表达层扩展。

Ian 的震撼正是来自这个维度跨越：「网页里的图标和逐帧动效细节做得太讲究了」——这不是一个干活型 skill，这是一台图纸打印机。Claude 的「表达语言」从文字扩展到了精密机械图。

Claude Code 本身是 harness（驾驭工具），anatomy 扩展了它的输出维度。

这种表达层的 skill 目前凤毛麟角。大多数 skill 都在回答「AI 能帮你做什么」，而 anatomy 回答的是「AI 能替你表达什么」——后者比前者稀缺得多，因为后者需要真正的工程美学积累，而非仅仅调用 LLM API。

prompt 写作原则

官网建议：prompt 是「想法」而非「画法」。「Explain how an LRU cache evicts entries」就够了，决定它应该是一台书架是 Claude 的任务。三个修饰词（interactive / WebGL / 3D）改变输出形态，但不要在 prompt 里描述「怎么画」。
