pi-subagents 模型分配指南：按角色定位给每个子代理配对模型

一句话结论：pi-subagents 的子代理默认全部继承父会话模型；通过 settings.json 的分层配置，把 6 个内置角色按各自任务定位分配到不同档位的模型与 thinking 级别，就能在经济、性能、效率之间取得平衡。

核心要点

  1. 一切调整都作用于同一条优先级链：单次覆盖 > 角色覆盖 > agent 定义 > 全局默认 > 继承父会话。改任何一处，先想清楚它在链上的位置。
  2. 分配的第一依据是角色定位，模型只是参数：侦察、实现、评审、咨询的任务形状不同，需要的档位不同；换模型目录时只需重排档位，角色定位不变。
  3. thinking 级别是独立于模型的第二成本旋钮：同一个模型，thinking 从 low 调到 high，成本和深度都会显著变化。
  4. 调整有闭环：/subagents-models 看实际生效的映射，配合"症状→调整"对照表定位问题。
  5. 预算与故障各有兜底：modelScope 兜住模型范围上限，fallbackModels 兜住供应商偶发故障。

速览结论

如果你已装好 pi 和 pi-subagents，只想快速配一个合理默认：在 ~/.pi/agent/settings.json 写入 subagents.defaultModel（便宜的主力模型）和 subagents.defaultThinking（low 或 medium），这一步就能覆盖所有角色。之后按第 3 节给 reviewer、oracle 两个高杠杆角色单独升档即可。改完重启 pi，用 /subagents-models 验证。完整的分角色推荐见第 2 节表格，真实配置实例见附录 A。

快速阅读到此结束。 以下逐项展开：从零的环境自查清单、优先级链的工作机制、每个角色的定位与档位推荐、配置步骤、验证命令、排障对照表与兜底策略。模型分档建议标注了证据性质——其中档位划分是推断，第 5 节给出了实测校准路径。

0. 前置条件：从零检查清单

本文假设你已安装 pi（@earendil-works/pi-coding-agent），但尚未安装 pi-subagents、未配置自定义模型。按顺序完成以下四项。

0.1 安装 pi-subagents

pi install npm:pi-subagents

注意：后台（async）子代理要求 pi 以 npm 包形式安装（有包目录供 detached runner 引用）；单文件二进制版 pi 只能跑前台子代理。

0.2 配置自定义 provider（models.json）

pi 的自定义 OpenAI 兼容 provider 配置在 ~/.pi/agent/models.json，结构如下（完整真实实例见附录 A）：

{
  "providers": {
    "lin": {
      "api": "openai-responses",
      "baseUrl": "http://localhost:8310/v1",
      "apiKey": "sk-****",
      "models": [
        { "id": "glm-5.3-flash", "reasoning": true, "input": ["text", "image"] }
      ]
    }
  }
}

关键字段：api 选协议（openai-responses / openai-completions 等）、baseUrl 网关地址、models[].id 决定你在配置里引用什么名字、reasoning 声明该模型是否支持 thinking。详见参考文献 [7]。

0.3 确认默认指向

~/.pi/agent/settings.json 中的 defaultModel / defaultProvider 决定父会话模型和裸模型 id 的解析归属。自查项：如果你改过 provider 名字，检查 defaultProvider 是否还指向旧名字——指向不存在的 provider 会让裸 id（如 glm-5.3）解析失败。

0.4 重启并体检

配置改动需重启 pi 才生效。启动后运行：

/subagents-doctor

检查子代理扩展与依赖是否正常。

1. 模型解析优先级链（一切调整的基础）

出处：pi-subagents docs/models.md（参考文献 [1]）

子代理启动时按以下顺序解析模型，强者优先：

优先级来源配置位置
1（最强）单次运行覆盖/run reviewer[model=lin/gpt-5.6-luna:high] "..." 或工具调用的 model 参数
2provider 作用域角色覆盖subagents.agentOverridesByProvider.<provider>.<name>.model
3角色覆盖subagents.agentOverrides.<name>.model
4agent 定义自定义 agent frontmatter 的 model（builtin 角色不设置）
5全局默认subagents.defaultModel
6（最弱）继承父会话你当前 pi 会话的模型

两条解析规则需要特别注意：

  • defaultProvider 只解决歧义，不参与优先级：当裸 id（glm-5.3）在多个 provider 下重名时，用它决定归属；全限定写法 lin/glm-5.3 永远精确命中。多 provider 环境下建议全部用全限定写法。
  • model: "inherit" 是显式继承：写在哪一层就继承"启动那一刻"的直接父会话模型，嵌套子代理继承的是它的直接父，而非最初的顶层会话。

2. 分配依据：六个内置角色的定位

角色职责出处：pi-subagents README 与 docs/agents.md；档位推荐为推断（依据模型命名与通用分档经验，未经实测），校准方法见第 5 节。

角色定位是稳定的设计判断，模型档位是可以随时重排的参数：

角色职责任务形状推荐档位【推断】推荐 thinking
scout本地代码侦察：找文件、入口、数据流、风险大量小请求，容错高工兵档：glm-5.3-flash / gpt-5.3-codex-sparklow
researcher外部/文档调研，产出带来源的简报大量小请求工兵档：glm-5.3-flashlow
delegate轻量通用代理，行为接近父会话混合主力档：glm-5.3medium
worker实现工作：改文件、验证、上报未授权决策中等复杂度多文件编辑主力档：glm-5.3 / MiniMax-M3medium
reviewer代码评审：测试、边界、简洁性需要细读和判断评审档：gpt-5.6-lunahigh
oracle决策前的第二意见，挑战假设难题攻关，高杠杆低频次深度档：gpt-5.6-sol / gpt-5.6-terrahigh

分档逻辑（对应"经济 × 性能 × 效率"三个轴）：

  • 工兵档 = 经济：工作流场景下侦察类子代理数量最多（几十个），单价是第一变量。便宜模型 + 低 thinking 足够，因为它们的产出会被下游核验。
  • 主力档 = 效率：worker 覆盖大部分 token 消耗，选"能一次改对"的性价比模型，medium thinking 防止在常规任务上欠思考。
  • 评审/深度档 = 性能：reviewer 和 oracle 出场次数少但决策杠杆高，漏掉一个 bug 的代价远高于省下的 token。注意：强推理模型在模糊目标上容易空转循环，oracle 类角色接到的任务必须有明确目标和完成标准。

3. 三步配置

参数出处：pi-subagents docs/models.md（参考文献 [1]）。配置写在 ~/.pi/agent/settings.json（用户级）或项目 .pi/settings.json（项目级，优先）。

第一步：全局默认（覆盖所有未单独设置的角色）

{
  "defaultModel": "lin/glm-5.3-flash",
  "subagents": {
    "defaultModel": "lin/glm-5.3-flash",
    "defaultThinking": "low"
  }
}

外层 defaultModel 是父会话模型；subagents.defaultModel 只填充"没有自己 model"的子代理。如果你的 provider 拒绝带 thinking 后缀的模型 id，加 "disableThinking": true 一次清掉内置默认。

第二步：角色覆盖（把高杠杆角色升档）

{
  "subagents": {
    "defaultModel": "lin/glm-5.3-flash",
    "defaultThinking": "low",
    "maxThinking": "high",
    "agentOverrides": {
      "worker":   { "model": "lin/glm-5.3",      "thinking": "medium" },
      "reviewer": { "model": "lin/gpt-5.6-luna", "thinking": "high",
                    "fallbackModels": ["lin/gpt-5.5"] },
      "oracle":   { "model": "lin/gpt-5.6-sol",  "thinking": "high" }
    }
  }
}
  • maxThinking 是硬顶（级别从低到高：off < minimal < low < medium < high < xhigh < max），超限的请求在启动前直接失败，防止某个角色的配置失控烧 token。
  • 同一个 agentOverrides 块还可以改角色的 tools、skills、prompt 等，但那超出本文范围。
  • 多 provider 环境可用 agentOverridesByProvider 让同一角色在不同 provider 下用不同模型，见参考文献 [1]。

第三步：单次覆盖（不写死配置的临时调整）

/run reviewer[model=lin/gpt-5.6-luna:high] "Review this diff"

模型串尾的 :high 是 thinking 后缀，只作用于这一次运行。工作流脚本里每个子代理也可单独传 model。

4. 验证

/subagents-models              # 查看所有角色实际生效的模型+thinking 映射
/subagents-models reviewer     # 只看一个角色

注意它报告的是运行时映射——磁盘上的 settings.json 改了但没重启 pi 时，两者会不一致。最后用一个小任务实跑验证（如 Use scout to list the entry points of this project），确认子代理正常启动、无模型解析报错。

5. 校准推断档位：用 profile 实测

第 2 节的分档是推断。pi-subagents 提供了从 provider 真实目录生成并探活校准的工具链：

/subagents-refresh-provider-models lin   # 拉取目录 + 小请求探活每个模型
/subagents-generate-profiles lin          # 生成 quota（省钱）和 quality（效果）两套角色→模型映射
/subagents-load-profile lin.quota         # 加载
/subagents-check-profile                           # 之后随时复查模型是否被移除/失效

quota 和 quality 两套 profile 的差异本身就是对你推断档位的一次实证校准。

6. 排障：症状 → 调整对照表

症状先查调整动作
子代理报"模型不存在/provider 解析失败"是否用了裸 id 且多 provider 重名改全限定写法 lin/模型名；核对 defaultProvider 指向
reviewer 评审太浅、漏问题/subagents-models reviewerthinking 升 high；仍不足则升评审档模型
worker 反复试错改不动任务描述是否明确先升主力档模型；仍不行说明任务定义模糊，先派 scout
oracle 空转循环、迟迟不收敛任务有无明确目标+完成标准强推理模型的天性：给明确目标，或降为 gpt-5.6-luna
token 消耗超预期/subagents-models 看各角色档位defaultThinking 降档、maxThinking 设顶、工兵角色降档、加 modelScope（第 7 节）
provider 偶发限流/失败失败是否发生在任何工具调用之前给角色加 fallbackModels（第 7 节）
改了配置不生效是否重启过 pi重启；用 /subagents-models 对比磁盘配置与运行时映射

7. 兜底：预算上限与故障转移

预算上限——modelScope（防止某次覆盖或 fallback 意外跑出预算范围）：

"modelScope": {
  "enforce": true,
  "allow": ["lin/glm-5.3*", "lin/gpt-5.6-*", "inherit"]
}

allow 是 glob 列表，匹配解析后的 provider/id；字面量 inherit 代表父会话模型。默认只警告，strict: true 时越界即失败。它只是策略闸门，不会替你选更便宜的模型——选型仍靠第 3 节。

故障转移——fallbackModels：角色覆盖里附带的候选链，在可重试的供应商错误（限流、过载、模型不可用、provider 超时）且发生在任何工具活动之前时自动切换。工具活动开始后的失败是终态，不会自动重放任务。

8. 何时该上工作流

单个子代理能完成的事，直接 /run 或自然语言委派即可，不需要编排。当出现以下信号时再考虑 scripted workflow（workflowScript）：需要几十个子代理、中间结果不想挤占你的上下文窗口、编排逻辑想固化为可重跑的脚本。这与 Claude Code 的 dynamic workflows 是同构设计，概念对照与用法另见参考文献 [9][10]。

边界与行动

适用条件：pi + pi-subagents + OpenAI 兼容自定义 provider；单文件版 pi 仅支持前台子代理；thinking 相关配置要求模型声明了 reasoning: true。

风险：① token 消耗随子代理数量线性放大，工作流场景尤其明显——先配好第 7 节再上规模；② 档位划分是推断，以第 5 节实测校准为准；③ provider 的模型目录可能增删，/subagents-check-profile 定期复查。

下一步：跑通本文配置后，可延伸至自定义 agent（frontmatter 定义新角色，见 docs/agents.md）、成本观测（docs/observability.md）与工作流编排（docs/workflows.md）。

验证方法：改配置 → 重启 → /subagents-models 核对 → 小任务实跑 → 观察 token 用量变化。

附录 A：lin 真实配置实例

API key 已脱敏。此实例对应 http://localhost:8310/v1 网关。注意：这是推荐的目标配置；你的 settings.json 中 defaultProvider 若仍是历史残留值（如改名前的旧 provider 名），需按 §0.3 自查后手动修正为 "lin"。

~/.pi/agent/models.json：

{
  "providers": {
    "lin": {
      "api": "openai-responses",
      "baseUrl": "http://localhost:8310/v1",
      "apiKey": "sk-****",
      "models": [
        { "id": "glm-5.3",           "reasoning": true, "input": ["text", "image"] },
        { "id": "glm-5.3-flash",     "reasoning": true, "input": ["text", "image"] },
        { "id": "gpt-5.2" },
        { "id": "gpt-5.3-codex-spark" },
        { "id": "gpt-5.5" },
        { "id": "gpt-5.6-luna",      "reasoning": true, "input": ["text", "image"] },
        { "id": "gpt-5.6-sol" },
        { "id": "gpt-5.6-terra" },
        { "id": "gpt-6-astra" },
        { "id": "gpt-image-2" },
        { "id": "MiniMax-M2.7" },
        { "id": "MiniMax-M3" }
      ]
    }
  }
}

~/.pi/agent/settings.json（子代理相关部分）：

{
  "defaultProvider": "lin",
  "defaultModel": "glm-5.3-flash",
  "subagents": {
    "defaultModel": "lin/glm-5.3-flash",
    "defaultThinking": "low",
    "maxThinking": "high",
    "agentOverrides": {
      "scout":      { "model": "lin/glm-5.3-flash", "thinking": "low" },
      "researcher": { "model": "lin/glm-5.3-flash", "thinking": "low" },
      "delegate":   { "model": "lin/glm-5.3",       "thinking": "medium" },
      "worker":     { "model": "lin/glm-5.3",       "thinking": "medium" },
      "reviewer":   { "model": "lin/gpt-5.6-luna",  "thinking": "high",
                      "fallbackModels": ["lin/gpt-5.5"] },
      "oracle":     { "model": "lin/gpt-5.6-sol",   "thinking": "high" }
    }
  }
}
