复杂分析为什么不该默认用 Multi-Agent Pipeline

Control Plane Pattern：确定性信号先排队，知识图谱约束搜索，再由一个中央推理引擎保持整条分析链的一致性。

一句话判断

多 Agent 的问题不一定是模型不够强，而是把“信号检测、状态共享、权属、假设空间和最终综合”拆给多个上下文后，失去了单一事实与单一责任链。

01 · 作者主张 / 不是项目事实

HANDOFF DECAY作者认为每次上下文交接都会丢失细节与权重；后续 Agent 只能基于压缩后的摘要继续推理，造成结论漂移。
TOKEN / OWNERSHIP多个 Agent 各自维护局部上下文，带来 token 放大、缺少“谁负责全局”的 ownership，以及跨阶段 coherence 下降。
50+ TURNS文章将“50+ turns 的复杂分析”作为需要重新考虑架构的场景；这是作者的经验性叙述，不是独立 benchmark。
身份核验结果：未找到文章明确指向的官方仓库、产品官网或可独立确认的项目名。因此本卡命名为“Multi-Agent Analytics Control Plane Pattern”，不冒认某个真实项目。

02 · 失败模式

把分析任务误画成流水线

传统形态是 Agent A → Agent B → Agent C：发现、调查、建议、展望各交一份结果。问题在于后一步接收的是“交接物”，而不是完整、可追溯的共享状态。

  • 确定性统计信号被 LLM 重新解释
  • 交接摘要压缩掉关键上下文
  • 各 Agent 局部最优，没人拥有全局一致性
  • 重复检索与 token 成本随 turns 增长

03 · Control Plane 替代形态

让确定性系统管边界，让一个引擎负责连贯推理

Control Plane 不是另一个“会聊天的协调 Agent”，而是把队列、知识、约束和状态放到模型之外；模型只在有意义的信号上进行端到端分析。

deterministic signals → queue → one reasoning engine → coherent packet

04 · 四阶段分析流程（作者文章主张）

01 / SIGNAL

信号检测

统计规则、阈值、趋势与异常检测先运行；不要让 LLM 判断“是否有信号”。

02 / ROOT CAUSE

根因调查

中央推理引擎接收队列信号，沿知识图谱中的实体与关系测试假设。

03 / ACTION

行动建议

在同一条推理链里把支持证据、排除项与可执行杠杆连起来。

04 / OUTLOOK

未来展望

基于已验证的原因和业务关系，给出影响、风险与后续观察点。

05 · Knowledge Graph 作为控制面

作者的定义不是“把图谱当作资料库”，而是让图谱约束可探索的实体、关系和假设路径。Agent 可以测试边，但不能无边界地编造关系。

  • 实体：地域、账户、付款方、品牌、KPI
  • 边：业务上允许验证的关系或因果假设
  • 输出：signal → cause → action → outlook

06 · 什么时候才值得 Multi-Agent

文章给出的反向门槛是：任务确实超过单一上下文窗口；子任务是真正独立、可并行；产出价值足以覆盖额外 token 与协调成本。

avoid by default

顺序依赖强、共享同一业务模型、最终需要一条连贯解释的分析任务。

consider

需要独立视角并行探索，且有外部状态、明确边界与可审计的汇合机制。

07 · 读者可复用的架构检查清单

  • 确定性先行：阈值、统计、排序、去重、信号队列是否已经移出 Agent 层？
  • 单一事实：多个执行者是否读写同一个可追溯状态，而不是互传摘要？
  • 单一责任：谁对最终综合和 coherence 负责？
  • 受限搜索：知识图谱或 schema 是否限定实体、关系与可验证路径？
  • 证据边界：“3–4周→20–30分钟”是否有原始运行记录、数据集和可复现实验？目前在本卡中仅标为作者声称。
