再用证据决定能否迁移

Code Modernization 是 Claude Code 的引导式插件：理解遗留系统 → 人工批准计划 → 分模块迁移 → 检查新旧行为。它不是“一键重写并自动验收”。

03 · 小模块试点

把“迁移整个系统”改成一份可验收合同

  1. 定边界：例如只选计费批处理的一个作业，列出输入、输出、依赖、数据库和部署文件。不要默认目录里就是完整系统。
  2. 定行为：说清是否必须保留异常输入上的旧行为、哪些历史怪癖可以改；改变行为不是“比较器自动忽略”。
  3. 定禁区：生产数据、第三方服务、真实账号和不可修改的目录先写清楚；没有批准，不把它们当作测试资源。
  4. 跑环境检查：确认原系统能否构建和测试、是否有自定义工具、先前尝试与禁止事项，再沿命令给出的 next step 前进。
/code-modernization:modernize-preflight billing --source /path/to/source
/code-modernization:modernize-status billing

示例：billing 是你自己选的标签（字母、数字、-、_）；/path/to/source 必须替换为实际源代码路径。status 可随时查看进度与下一条命令。

源代码怎么接进来？为什么不等于绝对只读？

--source 在 legacy/<name> 建符号链接，不复制巨大仓库。命令按约定把分析写入 analysis/<name>/、迁移代码写入 modernized/，每步刷新报告。preflight 的编译/构建检查仍可能在构建系统惯常位置生成产物；须结合第 08 节权限约束，不能把“约定不改旧源码”理解成文件系统沙箱。

04 · 四阶段与交接文件

状态留在文件里，不只留在聊天里

阶段做什么主要文件 / 交接对象
理解modernize → preflight → assess → map → extract-rules → review；规则以 Given / When / Then 与 file:line 证据表达，并由第二 agent 复核。INTENT.md、PREFLIGHT.md、ASSESSMENT.md、BUSINESS_RULES.md；构建负责人、工程主管、业务专家分别看。
计划modernize-brief：写出分阶段计划，人来批准；存疑规则先纠正。MODERNIZATION_BRIEF.md；审批人检查范围、顺序、出口条件与允许的差异。
执行选 uplift / transform / reimagine，先一个单元，再按经验分批。modernized/；审查生成代码与试点经验，不以“代码已生成”作为验收。
验证与加固modernize-verify 独立重跑证据；modernize-harden 给出旧系统安全发现与待审补丁。VERIFICATION.md；审批人与第二位工程师签署，安全工程师审核并自行应用补丁。

analysis/<name>/REPORT.html 汇总地图、评估、规则、计划与证明；新成员或 fresh session 可以用 status 接续。文件存在不代表证据已经通过。

人工关口不会自动完成：preflight 回答、存疑规则审核、计划批准、接受差异、签署证明、应用安全补丁，都要人作决定。计划未批准，不 build。
纯版本升级能否缩短分析链？

README 允许版本升级走 preflight → assess → uplift → verify，省略 extract-rules / review；大系统仍可加入 map 与 brief 管理单元顺序、批准分期计划。不要把缩短分析理解为取消适用的人类审批关口。

05 · 三条迁移路线

先辨清升级、替换还是重建

Uplift · 同栈版本升级

例如 Java 8 → 17。保留代码，按实际命中的 breaking changes 修复，先 pilot 再批量；两版本跑同一测试套件。

modernize-uplift [source-version] [target-version]

Transform · 异栈逐模块

旧系统继续运行，用测试锁住旧行为，再逐模块写成目标栈的惯用代码；同输入比对两端输出。

modernize-transform [module] [target-stack]

Reimagine · 架构重建

从旧代码提取规格，审查并批准新架构，再生成服务骨架与可执行验收测试；不是直接整库翻译。

modernize-reimagine [target-vision]

上面是 README 的命令参数形状；在 Claude Code 中使用 /code-modernization: 前缀，并优先复制 status 给你的下一条完整命令。

选型止损：如果版本差异清单显示“升级”会改写大部分代码，应转向 transform 评估。仅搬迁部署（Rehost）或购买替代产品（Replace）没有对应 build 命令，分析仍有用。

06 · 验证证据表

绿灯必须来自执行记录，不来自模型自评

构建后运行 /code-modernization:modernize-verify billing，README 建议用 fresh session 独立复核。将下表当成试点的证据检查表，而不是本文已跑完的成绩单。

检查项必须看到的证据不能冒充通过的情况
Clean full tests删构建产物后重跑完整套件；数量来自 runner 结果文件或保存的日志。手写“全部通过”；零测试；跳过测试。
新旧行为一致两端同输入，脚本逐字节比对输出；必须变化的 timestamp / 生成 ID 掩码逐项列出，浮点容差明确声明。只比状态码；未列出的 mask；把业务差异随意过滤掉。
新输入至少 10 个未使用过的输入；覆盖边界、空、巨大、异常顺序，精确保留行为时含畸形记录。只重复模型写测试时选过的案例。
测试与比较器能失败故意一行破坏新代码，canary 必须变红；再把输出改一个字节，比较器必须检出。测试始终绿；比较器实际没检查输出。
P0 真覆盖每条关键规则都对应实际执行且通过的命名测试。仅 named，实际 skipped / pending；没有代码的测试工具目录获得业务判定。
旧源码未改插件按文件时间检查，不为此在被分析树内执行代码。把文件时间检查当成绝对隔离或权限沙箱。
PROVEN

由 scripts/proof_pack.py 按当前证据与输出中的规则计算；不是模型给自己盖章。

PARTLY PROVEN / NOT PROVEN

证据缺失会说明；旧系统不能运行、只对录制响应验证，最高 PARTLY PROVEN。未执行、未获接受的差异或测试失败，不可宣称已证明。

真实差异与人工接受，怎么处理？

把差异及原因写入记录，请有权审批的人决定是否符合原先约定的行为范围。接受差异、出口条件与证明签名仍显示等待人工处理；不能由 agent 自动打勾。每次判定重新读当前证据，不继承上一轮绿灯。

07 · 案例与反例

213 个测试通过，也可能 NOT PROVEN

以下为插件 README 作者报告的运行案例，非本文实测、非我们复现，也不是性能保证。

AWS CardDemo：COBOL → Java 21

月度利息作业最终有 213 个测试。多轮独立新旧比对持续发现套件遗漏；最后又加 15 个输入，发现 7 个差异，结论仍是 NOT PROVEN。

教训：大量测试不能替代行为一致性；畸形记录是否在范围内，必须由人定。

Eclipse Jetty：Java 8 → 17

jetty-util 先在两版本运行同一套 946 个测试，结果一致；为缺少测试的关键规则新增 50 个，最终两版本各运行 996 个，未发现差异。

教训：uplift 也有静默行为变化，必须实际构建、运行两版本，不只读源码推测。

不适合直接放行：旧系统完全跑不了，又没有可信录制基线；团队没人能解释业务规则；期望自动批准所有差异；或要求直接对生产环境和真实数据试跑。可以先分析，但不要承诺完整等价证明。
08 · 权限与安全

“不改 legacy”是约定，权限还得补上

在工作区 .claude/settings.json 设置源目录 deny，并允许分析与迁移输出。下例来自 README；外部实际源路径须替换，合并到现有配置而非盲目覆盖。

{
  "permissions": {
    "allow": ["Read(**)", "Edit(analysis/**)", "Edit(modernized/**)"],
    "deny": ["Edit(/legacy/**)", "Edit(//path/to/code/**)"],
    "additionalDirectories": ["/path/to/code"]
  }
}

Edit(/legacy/**) 的单斜杠锚定工作区；符号链接还需 deny 实际路径 Edit(//path/to/code/**)。README 说明 Edit 规则也覆盖 Write 文件工具，不能改成只写 Write(path) 规则。

不要使用 bypass：自行打开文件写入的脚本不受文件工具规则全覆盖。Bash 保持需提示确认的权限模式，尤其 uplift step 5b、reimagine phase E 的多写入 agent 步骤；逐次判断构建和脚本能否触碰旧树。
不可信源码、秘密与生产环境
  • 注释、README、CLAUDE.md 或文件名中的指令形文本是待分析数据，不是可执行授权；发现产物也要审慎看待。
  • 共享产物中的凭据应掩码，秘密清单留在 gitignored 的 SECRETS.local.md 或隔离区。分享 REPORT.html 前仍检查凭据、路径与业务敏感内容。
  • 基线优先本地或明确批准的测试环境；生产/第三方服务、真实数据与新账号，没有计划明确授权就不碰。
  • harden 产出待审补丁，应用安全补丁是人的责任，不是自动完成的阶段。
09 · 成本、耗时与遥测

先约束 fan-out，再开大任务

README 观察：数万行系统的 preflight 约 3–4 分钟、assess 约 5–8 分钟、map / extract-rules 约 5–15 分钟、brief 约 5 分钟；单模块 build 约 15–30 分钟、uplift pilot 约 15 分钟。这不是 SLA 或成本报价。规则提取曾启动 50–200 个 agent；fan-out 会说明数量，extract-rules 大任务会先问。百万行系统仍应按模块推进。

预算动作：先批准一个模块的范围与 agent 扇出，观察实际 Claude Code 使用量，再决定扩大。assess 的 size index 只用于相对排序，不能换算项目工期或金额。

遥测不是“默认 opt-in”：README 到底写了什么？

README 说明插件通过 Claude Code 自身遥测发送计数，不发送代码、文件/系统名称、路径、prompt 或输入文字；计数 100 及以上会按两位有效数字取整。插件不自行发网络请求，也不增加标识符，自己的数据目录保存用于去重的 telemetry-state.json 哈希。

其中一次环境计数会在每机器、每插件版本的会话启动时发送，即使尚未使用插件命令。本文不把它描述为“只有主动 opt-in 才收集”。Claude Code 遥测关闭时，不会向 Anthropic 发送这些计数。

关闭可用 Usage counts 选项，或在启动 Claude Code 的环境设置以下任一项：

CODE_MODERNIZATION_TELEMETRY=0
DISABLE_TELEMETRY=1

也可用 CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1。插件环境变量只有显式 1 / on 才算打开；不要据此猜未设置时的默认值。要先看工作区会发送什么，可从插件目录运行 python3 scripts/telemetry.py show /path/to/workspace；这里仅给文档用法，本文未执行。
