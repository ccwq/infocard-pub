Engineering Skills · User-Invoked
User-Invoked · 用户触发 · Build Chain: grill-with-docs → to-spec → to-tickets → implement → code-review
Skill 技能描述
/ask-matt 路由器：哪个 skill 或流程适合当前情况
适用场景：刚接手需求，不知道走 grill-with-docs 还是 to-spec → implement；不确定当前卡在哪一步 → 直接问路由
/grill-with-docs 核心 逐分支穷举决策树，留下 ADR + CONTEXT.md glossary
适用场景A：新项目开荒，计划模糊、术语未对齐 → 写代码前先对齐领域词汇和硬决策
适用场景B：大重构前，想把模糊的设计原则显式化为 ADR → grill 出决策立即写文档，不遗漏
/triage 按状态机将 issue 流经分类角色（bug/enhancement）
适用场景：GitHub issue 积压，需要批量分类打标签 → 自动推荐类别+状态，每条等待确认，不乱贴
/improve-codebase-architecture 找浅层模块（接口≈复杂度）深化机会，生成可视化 HTML 报告，YAGNI 范围限定
适用场景：接手遗留代码库，想找最有价值的重构机会 → 通过"删除测试"过滤，只展示集中复杂度的模块
/setup-matt-pocock-skills 配置 issue tracker（GitHub/Linear/本地文件）和分类标签
适用场景：首次安装 skills，首次配置 tracker → 一次配置，后续所有 skill 自动写入指定 tracker
/to-spec 把对话和代码理解合成 spec，发布到 issue tracker，不需再面试
适用场景：grill-with-docs 对齐后 → 直接合成文档，无需重复提问；接他人方案时直接生成 spec
/to-tickets 将 plan/spec/对话拆分为 tracer-bullet tickets，含阻塞边
适用场景：已有 spec，需要分配给不同 agent 或人执行 → 每张 ticket 必须是垂直切片（端到端可验证），含依赖关系
/implement 按 spec 或 tickets 构建，驱动 /tdd 在预定接缝，/code-review 收尾后提交
适用场景：spec 已定、tickets 已拆分，交给 agent 执行 → TDD 红环 + 类型检查 + 全测试套件，subagent 不污染主 context
/wayfinder 规划大量工作为调查 tickets 图谱，subagents 燃尽 research tickets 直到路径清晰
适用场景A：新功能开发，路径不清晰 → 先画决策地图，理清先做什么再做什么
适用场景B：接手大项目，context 太大 → subagents 并行燃尽 research tickets，路径清晰后再回主流程
/prototype 构建可丢弃原型回答设计问题，不写测试/错误处理/持久化
适用场景A：不确定某个 API 好不好用 → 快速写一个 throwaway 脚本验证
适用场景B：UI 设计不确定 → 搭一个无测试无错误处理的 demo，从第一天就标记为可丢弃
/diagnosing-bugs 严格 bug 诊断循环：复现→最小化→假设→检测→修复→回归测试
适用场景A：用户报告偶发 bug → 先建立 tight feedback loop（一个命令复现），才能开始诊断
适用场景B：性能回归 → 先量化再诊断，不能凭直觉猜测
/research 调查问题并以引用 Markdown 形式捕获发现，只用一手来源（官方文档/源码/API）
适用场景：需要正确理解某库用法或某协议细节 → 只看一手来源，生成可溯源的 cited Markdown，不靠二手总结
/tdd 测试驱动开发，red-green-refactor 循环，垂直切片构建，不批量写测试
适用场景A：修复 bug → 先写一个会失败的测试，复现 bug，再修复
适用场景B：写新功能 → 垂直切片：一次只写一个行为的测试和代码
/domain-modeling 构建和深化项目领域模型，用术语挑战 glossary，压力测试 CONTEXT.md 和 ADR
适用场景A：团队对某个概念理解不一致 → 主动挑战模糊术语，写入 CONTEXT.md
适用场景B：设计新模块前 → 先对齐 ubiquitous language，再开始写接口
/codebase-design 深度模块设计规范：行为背后小接口，放置在干净接缝，通过接口可测试
适用场景A：设计新服务/模块 → 先确认接口边界：接口=复杂度？是否符合"删除测试"？
适用场景B：审查他人设计提案 → 用 codebase-design 词汇（module/deep/seam/adapter）统一讨论语言
/code-review 双轴审查：Standards + Spec，并行 sub-agent 运行互不污染，从不合并两轴
适用场景A：审查 PR → Standards 维度（代码风格/规范）+ Spec 维度（是否实现了需求），并行独立输出
适用场景B：想确认 PR 同时满足规范和需求 → 两轴分开，避免一个掩盖另一个
/resolving-merge-conflicts 逐 hunk 处理 git merge/rebase 冲突，按意图追踪到每方 primary source，从不 --abort
适用场景A：rebase 遇到冲突 → 逐 hunk 确认每方意图，不盲目接受 ours/theirs
适用场景B：合并分支有大量冲突 → 还原到双方 primary source，理清意图再合并
Productivity Skills · User-Invoked
User-Invoked · 用户触发
Skill 技能描述
/grill-me 非代码场景：决策树穷尽式面试，逐分支暴露未解决决策，v1.2 重写通用化所有场景，无状态不留痕
适用场景A：写代码前感觉方案差不多，但有隐藏的决策点 → 逐分支穷举，让隐式假设全部显式化
适用场景B：设计讨论各方理解不一致 → 一个一个决策来，每题带推荐答案等待确认，不批量轰炸
/handoff 将会话压缩为交接文档，供其他 agent 继续工作
适用场景A：下班前交接给队友/另一 agent → 只写活的线索，不重复已存在于 spec/ADR/commit 的内容
适用场景B：多 agent 并行中需要汇总 → 写 OS 临时目录，不污染 workspace
/teach 跨多 session 教授新技能/概念，用当前目录作为有状态教学空间，从一手来源引证
适用场景A：学习某新框架/语言 → 跨 session 追踪进度，每个 session 承接上一节，不从头开始
适用场景B：团队内部分享技术实践 → 有状态 workspace，记住你学了什么，下次继续深入
/writing-great-skills skill 编写规范参考：词汇、原则使 skill 可预测；目标=相同过程而非相同输出
适用场景：编写新的 agent skill 时 → 先对齐词汇（model-invoked / user-invoked / trigger phrases），确保 skill 可预测而非随机
/grilling /grill-me 和 /grill-with-docs 的底层复用逻辑，model-invoked primitive，triage 和 improve-codebase-architecture 也依赖它
适用场景：作为底层被调用，不需要手动触发 → /grill-me = 无状态门面；/grill-with-docs = 加了文档写入；grilling = 实际引擎
Misc Skills
Skill 技能描述
/git-guardrails-claude-code Git 安全护栏，防止误操作
适用场景：担心 Claude Code 执行破坏性 git 操作 → 强制安全确认，防止 rm -rf 或强制 push
/migrate-to-shoehorn 迁移到 shoehorn 模式
适用场景：现有项目想统一 agent 调用模式时 → 按 shoehorn 规范重构 agent 调用路径
/scaffold-exercises 脚手架练习生成
适用场景：需要生成练习题给团队或学生学习时 → 自动生成脚手架代码和测试用例
/setup-pre-commit pre-commit 配置
适用场景：新项目初始化，需要配置 git hooks 时 → 自动配置 pre-commit 工具链和检查项
核心心智：User-invoked = 需要手动触发（编排层）；Model-invoked = 可由 agent 自动调用（复用纪律层）。skill 可调用 model-invoked，但不可调用其他 user-invoked skill。
