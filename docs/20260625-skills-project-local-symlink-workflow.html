Skills 只装在项目里：
用软链接管理 Agent Skills 的极客工作流

这套方法的核心不是“花哨”，而是把 Skills 当成项目级依赖来管理：只在当前项目暴露需要的能力，把上下文窗口、更新成本和 bug 修复路径都收紧到一条更可控的链路里。

核心选择项目内安装
安装方式软链接
目标省上下文
维护收益单点更新
适合已经同时维护多个项目、多个技能仓、并且愿意把 Agent 当工程工具来管理的人；不一定适合所有人，但非常适合作为一套“低复制、低漂移”的思路。
一句话结论：把 Skills 全装全局，看起来方便；但从上下文成本、误触发概率和后续维护来看，把真正需要的 Skills 只挂进当前项目，往往更像一个可长期扩展的工程化方案。

这套链路到底怎么跑

step 01 统一存放原件 把开源 skills 仓库集中放进 `~/GitHub`，原件只保留一份，避免每个项目复制一套。
step 02 项目内创建软链接 在 `.agents/skills/` 下把需要的 skill 链进来，让项目只暴露当前真正用得到的能力。
step 03 再给 Claude Code 一个入口 用 `.claude/skills -> .agents/skills` 再接一层，让 Agent 顺着链找到项目内技能。
01

为什么不装全局

最直接的理由是节约上下文窗口。Skill 默认不会一开始就把全文全部塞进去，但名称、描述、触发条件这些摘要会一直存在；全局装得越多，工作台上就越容易堆满“现在不需要但一直占地方”的资料。

更麻烦的是误触发。全局 skills 越多，模型越容易把边缘相关的 skill 也拉进来；一旦完整内容被加载，消耗的就不是几个 token 的摘要，而是一大块真正的上下文预算。

context budget 误触发成本 只留当前项目需要的资料
02

软链接方案的三层结构

原件仓

`~/GitHub/baoyu-skills`、`~/GitHub/baoyu-design` 这类目录，负责保存可更新的原始 skill 内容。

项目层

在项目里建 `.agents/skills/baoyu-comic -> ~/GitHub/baoyu-skills/skills/baoyu-comic` 这种链接，把项目依赖显式写出来。

Agent 入口

再做 `.claude/skills -> .agents/skills`，让 Claude Code 顺着这层入口读取项目技能集合。

03

真正省心的是后续维护

  1. 更新只做一次：所有项目都指向同一份原件，拉一次最新代码，就等于所有项目同步升级。
  2. 修 bug 可以直接反哺：在某个项目里发现 skill 有问题，修掉的其实就是原始仓库文件，顺手就能提交回上游。
  3. 降低复制漂移：如果每个项目都复制一份 skill，半年后通常会出现“同名 skill 在 4 个地方各不相同”的灾难。
04

命令记不住怎么办

这套工作流很适合交给 Agent 自己处理。你不需要手记 `ln -s` 这种命令，只要用自然语言说清楚“把哪个 skill 从哪里链接到哪里”，让 Claude Code / Codex 去干脏活就行。

例如：
“帮我把 `~/GitHub/baoyu-skills/skills/baoyu-comic` 软链接到 `.agents/skills/baoyu-comic`。”
或者更口语化一点：
“帮我把 baoyu-skills 项目里的 baoyu-comic 这个 skill 链接到当前项目。”

05

这套方法最适合谁

适合同时满足以下几个条件的人：

  • 你会同时维护多个项目，而不是只在一个全局沙箱里玩。
  • 你会长期复用技能仓，关心“更新一次、全局生效”的维护效率。
  • 你在意 Agent 的上下文窗口，不想让一堆全局技能摘要长期占台面。

如果你只是偶尔试几个 skill、项目数量也少，直接全局安装其实更省事。

06

可复用的判断标准

优先项目内

当前项目依赖明确、技能数量多、上下文预算紧、后续希望集中更新。

优先全局

个人常驻小工具、几乎任何项目都会用、触发边界非常明确、摘要数量很少。

关键取舍

全局更省初次安装时间；项目内更省长期维护和上下文空间。

可转述版结论：把 Skills 当成项目依赖，而不是全局插件。原件集中放仓库里，项目内用软链接暴露真正需要的部分，最后再给 Claude Code 一个统一入口。这会让上下文更干净，更新更轻，修 bug 还能顺手回馈上游。

边界：这是偏极客、偏工程化的管理方式；如果你不在意上下文预算，也不维护多个项目，全局安装依然可能是更低摩擦的选择。
