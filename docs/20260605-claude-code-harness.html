01
一句话结论

这条帖的重心：把 Claude Code 从“聊天壳”推到“任务执行器”

作者的观点不是“更会问答”，而是“更会替每个任务生成一套 harness”。这意味着工作流的单位从 prompt 变成了 task-specific pipeline：可分流、可并行、可验证、可复用。

如果一个任务需要你手写多个步骤、重复验证、并行跑多个分支，那就不该只靠一个静态 prompt；它更需要一套临时生成的 harness。

图像证据

图片里的结构，不是装饰，是论证本身

这张图用最少元素表达了动态工作流的四步逻辑：task 进入后，系统按任务类型编排流程，分出多个分支并行处理，最后回到 verify 做结果确认。它证明的是“流程可以现场写出来”。

A

主标题：A harness for every task

POSTER
主张

“每个任务都能有自己的 harness”不是比喻修辞，而是产品化方向：同一套 Claude Code 能力，不再固定成一条通用脚本，而是根据任务临场生成执行器。

  • 适合：多步骤、重复验证、并行处理、任务差异大
  • 不适合：一句话就能回答的短问短答
B

副标题：Dynamic workflows in Claude Code

FLOW
结构

“Dynamic workflows” 指向的是一种更高层的执行方式：先根据任务临时写编排脚本，再把并行/验证/收口纳进一个会话内的控制流。

  • 核心不是模型更强，而是流程更可控
  • 核心不是一次性输出，而是可追踪的执行链
03
工作流拆解

把这套 harness 拆成 4 段，才能看懂它为什么有用

下面这四段不是“教程步骤”，而是作者在图里表达的控制流：先定义任务，再生成 harness，再跑并行分支，最后 verify。这个顺序很关键。

1

定义 task：先把目标说清

动态工作流的前提不是“全自动”，而是先把当前任务类型、约束和验收条件说出来。没有任务边界，就没有 harness 的生成依据。

2

生成 harness：按任务写脚本骨架

作者强调的不是通用 prompt，而是临场编写编排脚本。换句话说，Claude Code 先搭流程，再执行内容。

3

并行执行：把子任务拆成分支

图里右侧的分叉说明，harness 可以把一个复杂任务拆成多个并行路径，让不同步骤同时推进，而不是串行等结果。

4

verify 收口：最后统一验证

verify 不是可选项，而是工作流的收口动作。它确保动态生成的过程不是“跑完就算”，而是“跑完要验”。

04
工程意义

为什么这类动态 workflow 值得关注

它把 agent 的能力重点从“会回答”转成“会组织执行”。当任务复杂度上升时，最贵的不是 token，而是重复切换、人工协调和最后补救。

降低固定脚本脆弱性

同一套 harness 可以随任务变化而改变，不必让所有工作都挤进一个固定模板里。

把并行能力变成默认能力

复杂任务不再强迫串行执行，分支可以按需要并行跑，减少等待和反复往返。

把 verify 变成流程内建约束

验证不是事后补丁，而是 harness 里的一步；这会显著提高可交付性。

一句话概括：这条帖展示的是“任务驱动编排”而不是“回答驱动聊天”。 如果你要在 Claude Code 里真正做复杂活，重点不是把 prompt 写得更像命令，而是让每个任务都有自己的控制流和验收点。
05
适用边界

哪些场景适合，哪些场景不值得上 harness

不是所有任务都需要动态工作流。它最适合“结构清晰但步骤多”的任务；如果问题本身很短、很线性，额外的 harness 反而会增加复杂度。

适合

多步骤、可验证、可并行的任务

YES
推荐
  • 研究型任务：先收集证据，再归纳，再对照验证
  • 工程型任务：拆分子任务、并行执行、统一验收
  • 工作流型任务：有固定流程，但每次输入不同
不适合

一句话就能结束的轻任务

NO
边界
  • 简单问答：不需要动态编排
  • 一次性短命令：直接执行更快
  • 没有验收标准的任务：harness 会失去收口意义
