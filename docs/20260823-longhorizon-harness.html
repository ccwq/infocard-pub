现有 Harness 的两个结构缺陷

01

Context 腐烂

任务执行和状态管理共用同一个不断膨胀的 context，历史越长，关键信息越难检索，性能急剧下降。

02

自我评估耦合

任务执行和完成评估耦合在同一 session，Agent 自己判断是否完成——错误判断会污染后续所有决策。

03

错误累积

未验证的前提一旦进入记录，每个后续步骤都继承它。早期小错误逐渐放大，最终任务完全偏离原始目标。

MEA 循环 · Manage · Execute · Audit

Manager
读取任务状态，定义下一子任务
含依赖 / 约束 / 验收标准
→
Executor
全新干净 context
执行当前子任务
→
Auditor
只读检查环境
确定完成/未完成项
↺
核心原则：任务状态作为外部明确记录，只用独立验证过的事实更新。
每次 round 后 Executor 交互历史被丢弃，只保留紧凑的验证报告。

定位区分 · 与 PRO-LONG / SWE-MeM 的差异

PRO-LONG

程序化记忆框架，解决 context 管理 tradeoff，目标场景为 ARC-AGI-3 游戏任务。

程序化记忆 · 游戏任务

SWE-MeM

自适应记忆管理训练框架，针对 SWE-Bench Verified 进行微调训练，不适用通用场景。

LongHorizon-Harness

通用 MEA 循环，跨 GUI-CLI 桌面工作流、命令行、跨界面协调，无需训练，开箱即用。

通用 · MEA循环 · 开箱即用

关键概念

Fresh-Context Execution
Executor 每次在全新干净 context 中执行子任务，执行历史在 round 结束后丢弃，不向下一轮传递。
Durable Verified State
任务状态作为外部明确记录存在于执行之外，只接受 Auditor 独立验证过的事实，不接受 Agent 自我报告。
Independent Auditing
Auditor 只读检查环境，从不看到 Executor 的推理或自我评估，验证不能改变被检查的结果。
Recoverable Progress
每次执行错误要么被下次审计暴露，要么永远不会进入记录，错误被限制在单轮内，不向后续轮次扩散。

安装与运行

# 安装（需要 Python 3.10+） uv tool install lh-harness
# 一行命令运行任务（--dashboard 可视化 MEA 循环） lh-harness run --task "Summarise the files in this directory." \ --agent claude_code --model qwen3.7-plus --max-rounds 2 --dashboard
# 支持多种 Agent 后端和模型混搭 lh-harness run --task @task.md \ --manager claude --executor codex --auditor openclaw \ --manager-model qwen3.7-plus --executor-model gpt-5.6-luna
