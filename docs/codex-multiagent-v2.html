Codex Multi-agent V2 的核心不是"多开几个 Agent"，而是把任务图跑成流水线。

主智能体按任务复杂度动态决定是否派生 Subagent；每个 Subagent 拥有独立上下文、模型、推理层级和工具绑定；主智能体最后负责汇总与冲突裁决。配合 CC Switch 转接第三方 API，整个调度可运行在 Graph Engineering 任务图上，控制 Token 消耗。

01
CHAPTER · 核心功能

多智能体调度系统

不是多 Agent 同时跑，而是调度器把任务图拆给可独立执行的 Subagent。

核

核心目标

把复杂任务拆成可独立执行、可汇总的子任务图，而不是堆线性 Prompt。

结

结构

主智能体（调度器）+ 多个 Subagent（执行器）+ 结果汇总与冲突合并。

边

适用边界

适合跨探索、设计、测试、审查的多阶段任务；不适合一次性的小修小补。

02
CHAPTER · 工作模式 · 主智能体职责

三件事：拆 · 派 · 合

主调度器的职责边界。

拆

任务拆解与分发

把目标拆成代码探索、方案设计、开发测试、代码审查四类子任务。

派

动态派生 Subagent

按任务复杂度决定是否新建 Subagent，或调度已存在的 Subagent 实例。

合

结果收集与汇总

统一判断、合并冲突，输出最终解决方案。

03
CHAPTER · 工作模式 · Subagent 配置

每个 Subagent 都是独立单元

模型、推理、工具、嵌套都可以独立配。

多模型

多模型混用

GPT、Kimi、MiniMax 等不同模型独立配置。

推理

推理层级 + 并发

自定义思考级别与并发数量控制。

工具

工具 / Skill 绑定

独立绑定 Pi Agent 或特定 Skill 扩展功能。

嵌套

嵌套与并行

Subagent 可再派生孙级 agent；多轨道并行审查。

上下文

独立上下文

每个 Subagent 独立上下文窗口，避免主线程污染。

04
CHAPTER · 辅助工具集成 · CC Switch

第三方 API 转接

CC Switch 把非标准 API 格式转成 Codex 兼容。

作用

格式转接

转换第三方非标准 API 格式以兼容 Codex 接口。

配置项

必填字段

提供商名称、模型映射、API 链接、Prompt Caching。

场景

为何需要

Codex 本身只对官方响应格式友好；第三方 KIMI / DeepSeek 等需要中转。

收益

节省成本

把昂贵的主模型任务和便宜的 Subagent 任务分开。

05
CHAPTER · 最佳实践与约束

Graph Engineering 任务图编排

目标 + 约束条件。

目标

协作 + Token

提高协作效率并降低 Token 消耗；任务图结构降低重复 Prompt。

主模型

必须强模型

主模型建议 GPT-5.6S 等强模型，保证精确调度与冲突裁决。

第三方

格式与限流

第三方 API 注意接口格式兼容性和 API 调用速率限制。

06
CHAPTER · 实际落地链路

从配置到运行的 5 步

工程化推进流程。

Step 1

配置主模型

主调度器接入 GPT-5.6S 等强模型。

Step 2

配置 CC Switch

提供商名称、模型映射、API 链接、Prompt Caching。

Step 3

Subagent 编排

为每个阶段指定模型、推理层级、并发数。

Step 4

任务拆解

把需求拆为代码探索 / 设计 / 测试 / 审查。

Step 5

运行与汇总

观察 Subagent 日志与 Token 用量；主智能体裁决输出。

后续

迭代与限流

记录每个 Subagent 的实际 Token；按限流配置错峰。
