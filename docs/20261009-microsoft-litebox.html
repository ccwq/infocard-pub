01
Beginner Introduction · 初学者引入

为什么需要沙箱？先搞清楚「攻击面」

传统程序直接运行在操作系统上，操作系统又直接跑在硬件上。层越多，可以被攻击的「接口」就越多。LiteBox 的思路是：把应用程序关进一个小笼子，让它只能看到被允许的东西。

🕳 什么是攻击面？

攻击面（Attack Surface）指的是一个系统所有可以被攻击者利用来发起攻击的「入口点」的总和。入口越多，危险越大。

  • 操作系统提供几百个系统调用（system calls）
  • 普通应用只需其中 10~20 个就能正常工作
  • 多余的调用就是浪费的攻击入口

🔒 什么是沙箱？

沙箱（Sandbox）是一种安全隔离机制：把程序关在一个受控环境里运行，即使程序被恶意代码攻破，损失也限制在笼子里，不会波及宿主系统。

  • 浏览器：JS 沙箱，防止网页恶意代码访问本地文件
  • 容器（Docker）：进程级隔离
  • LiteBox：库 OS 级隔离，粒度更细
LiteBox 的核心思路 与其逐个堵漏洞，不如直接削减「程序与外界的接口」。接口少了，漏洞自然也少了——这是一条根本性的安全路线。
02
Core Concept · 核心概念

什么是库操作系统（Library OS）？

Library OS 的思路和传统操作系统完全不同：不是「程序调用系统」，而是「把操作系统功能打包成库，链接进程序」——程序自己「长出」一个精简的 OS，不需要依赖宿主操作系统内核。

维度 传统操作系统（Monolithic Kernel） 库操作系统（Library OS）
架构 Linux / Windows 内核是一个独立的大型软件，程序通过系统调用与内核通信 OS 功能作为库直接编译进应用程序，程序自带精简的运行时环境
接口数量 Linux 有 400+ 系统调用，全部暴露给程序 LiteBox 只暴露必要的少数接口，大幅减少攻击面
与宿主关系 程序直接依赖宿主内核，内核漏洞直接威胁程序 程序与宿主解耦，通过定义的 Platform 接口交互，不依赖内核细节
隔离能力 依赖进程/容器隔离 库 OS 本身提供语义层面的隔离，Platform 实现决定底层硬件隔离
缺点 攻击面大，但生态成熟 需要针对不同平台实现 Platform 层，跨平台适配成本高
LiteBox 的 Library OS 不是要取代 Linux/Windows，而是为特定安全场景提供一个可信的、受控的执行环境——它可以跑在 Linux 上、Windows 上，甚至 TEE（可信执行环境）上。
03
Architecture · 架构设计

LiteBox 架构：North × South 两层解耦

LiteBox 的核心设计哲学是「接口解耦」：用 North（北向）Shim 层和 South（南向）Platform 层，把「应用」和「硬件平台」完全分开，两层都可以自由替换组合。

⬆ North：Shim 适配层（面向应用）

应用不是直接调用系统调用，而是调用 LiteBox 提供的统一 API。这个 API 设计参考了 Rust 生态中的 nix 和 rustix 库风格——语义清晰、类型安全、纯 Rust。

  • 提供文件、网络、进程等基础 POSIX 语义
  • 采用 Rust-y API 风格（类型驱动、安全）
  • 应用代码可移植，不绑定具体 OS

⬇ South：Platform 接口层（面向硬件）

Platform 是抽象接口，注入具体实现。不同的 Platform 适配不同底层硬件或虚拟化环境，North Shim 完全不需要关心。

  • Platform 负责与底层硬件交互
  • SEV SNP / OP-TEE / Linux / Windows 各自实现 Platform
  • 任意 North × South 组合均可工作
📐 为什么这样设计？

传统方案换一个平台（比如从 Linux 迁移到 SEV）意味着重写大量代码。LiteBox 的两层分离让「换平台」只需要实现/替换 Platform 层，North Shim 完全复用——这是经典的分层架构思想在安全操作系统领域的应用。

04
Official Use Cases · 官方场景拆解

五大官方场景：每个怎么用？为什么难？

README 原文列举了五个官方支持的场景，从跨平台运行到可信执行环境，覆盖了从通用到高安全等级的不同需求。

①

Windows 上运行未修改的 Linux 程序

在 Windows 主机上，通过 LiteBox 的 North Shim + Linux Platform，让 Linux ELF 二进制文件不需要 Linux 内核就能运行。

对谁有用：跨平台开发者 / Windows 用户需要 Linux 工具 难点：二进制兼容与系统调用翻译
②

Linux 上沙箱化运行 Linux 应用

在 Linux 上用 LiteBox 沙箱化运行普通 Linux 应用程序，降低其权限和攻击面，类似于轻量级容器化但粒度更细。

对谁有用：安全敏感的应用 / 服务器加固 难点：与宿主 Linux 的资源协调
③

AMD SEV SNP 上运行程序

SEV SNP（Secure Nested Paging）是 AMD 的硬件级内存加密技术，LiteBox 在其上提供可信执行环境，保护程序免受物理攻击和虚拟机逃逸。

对谁有用：云服务商 / 机密计算场景 难点：硬件级安全 + 库 OS 内存布局需专门适配
④

Linux 上运行 OP-TEE 程序

OP-TEE（Open Portable Trusted Execution Environment）是 ARM 的开源 TEE 实现。LiteBox 提供在 Linux 环境中运行 OP-TEE 安全小程序的能力。

对谁有用：嵌入式 / IoT / 移动设备安全应用 难点：TEE 环境资源受限，API 需极度精简
⑤

LVBS 上运行程序

LVBS（Lightweight Virtualization Barrier System）是一个轻量级虚拟化隔离方案。LiteBox 通过其 Platform 接口在 LVBS 上运行。

对谁有用：需要轻量隔离但不需要完整 VM 的场景 难点：❓ LVBS 具体实现细节尚待官方进一步披露

Security Model · 安全模型

安全模型：削减接口 = 削减攻击面

LiteBox 的安全策略聚焦在一个核心主张：大幅削减应用程序与宿主之间的接口数量，从而从根本上压缩攻击面。这是一种「最小权限」思想的工程实现。

🔑 削减接口的安全意义

  • 减少暴露面：Linux 有 400+ 系统调用，LiteBox 只暴露应用真正需要的少数接口
  • 减少漏洞窗口：每减少一个系统调用绑定，就减少一类潜在的 CVE 路径
  • 可控性提升：通过 Platform 接口，宿主对应用可见资源有精确控制

⚙ 双模式执行

  • Kernel-mode：在内核态直接执行，安全检查更早，权限更大，⚠ 风险也更高
  • User-mode：在用户态执行，轻量隔离，适合普通沙箱场景
  • 两种模式由 Platform 实现决定，North Shim 无感知
⚠ 重要限制 LiteBox 本身是安全工具，但并非银弹。其安全性依赖：① Rust 语言内存安全特性；② North Shim 实现是否完整；③ Platform 层是否正确配置。❓ 具体安全审计报告尚未公开发布（2026-10-09 状态）。

Glossary · 术语表

术语表：LiteBox 相关的核心概念

收录本文中出现的技术术语，方便初学者查阅。

Library OS / 库操作系统

将操作系统功能打包为库，链接到应用程序中的架构范式。应用程序自带运行时 OS，不依赖宿主内核。

Attack Surface / 攻击面

系统所有可被攻击者利用的入口点总和（系统调用、网络端口、API 接口等）。削减攻击面是安全加固的核心策略。

Sandbox / 沙箱

安全隔离环境，将程序限制在受控资源集合内运行，防止恶意行为波及外部系统。

Shim（North Shim）

适配层代码，将应用程序的标准调用翻译/代理为库 OS 内部接口。LiteBox 的 North Shim 采用 Rust-y nix/rustix 风格。

Platform（South Platform）

LiteBox 的平台抽象层接口，由具体硬件/虚拟化环境实现。Platform 接口注入使 LiteBox 与硬件解耦。

SEV SNP

AMD Secure Encrypted Virtualization with Secure Nested Paging，硬件级内存加密技术，保护虚拟机免受物理攻击和 VM 逃逸。

OP-TEE

Open Portable Trusted Execution Environment，ARM 的开源 TEE 实现，提供安全隔离的「安全世界」运行环境。

LVBS

Lightweight Virtualization Barrier System，轻量级虚拟化隔离方案。❓ 具体技术细节尚待官方披露。

nix / rustix

Rust 生态的两个著名库，提供类型安全、符合人体工程学的 Unix 系统调用绑定。LiteBox North API 参考其风格。

Kernel-mode / User-mode

CPU 特权级别。Kernel-mode 权限最高可直接访问硬件；User-mode 权限受限，受 OS 调度保护。LiteBox 支持两种执行模式。
