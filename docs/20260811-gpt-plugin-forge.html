THE ARCHITECTURE

Plugin Forge 的桥层模型

官方确认的是 MCP 接入机制；下图对 Plugin Forge 的细节是根据原帖描述还原的概念模型。

01 · Prompt用户在聊天或手机端提出自然语言问题。
02 · MCP URLChatGPT 连接一个远程 MCP server URL。
03 · BridgeREST 转 MCP；注入密钥；聚合多个端点。
04 · Upstream高德、携程、知识库或其他服务响应。
05 · Result结构化结果回到 ChatGPT，必要时带引用。
部署

Cloudflare Worker

作者声称使用 Cloudflare 免费额度部署，不买服务器、不买域名；评论补充可用默认 workers.dev 地址。具体配额、冷启动、超时与出站限制仍需按当前 Cloudflare 账户实测。

输入

普通 REST API

把 API 文档交给支持技能的 AI，再生成一层 MCP 工具。API 的认证方式、分页、限流、错误结构不能靠模型“猜”，必须对照上游文档。

聚合

多个端点收束

北大法宝被作者描述为 9 个端点聚合；截图和正文都没有公开端点清单，因此只能作为作者自述，不能复现为已验证 API。

03
OFFICIAL CHECK

OpenAI 文档能确认哪些边界

调研结果把“笔记里的经验”与“官方当前支持”分开。

L1 · OpenAIDeveloper mode

官方支持远程 MCP

  • ChatGPT Developer mode 可连接远程 MCP。
  • 支持 SSE 与 streaming HTTP。
  • 认证支持 OAuth、无认证与混合认证。
  • Pro、Plus、Business、Enterprise、Education 网页账户可用，具体能力仍受产品界面和工作区设置影响。
L1 · OpenAISafety

“能连上”不等于“安全可用”

  • 自定义 MCP 不由 OpenAI 审查或背书。
  • 服务端可能看到 ChatGPT 发送的查询上下文。
  • 写操作默认需要确认；没有 readOnlyHint 的工具可能被当作写操作。
  • 只连接你信任的服务；不要把敏感信息塞进工具定义或服务端日志。
04
OPERATING GUIDE

最稳的分工方式

不是“所有事情都塞进 GPT”，而是按任务的副作用、上下文和验证成本分层。

适合 GPT + 插件

读取型轻任务

查交通、查地图、查公开资料、翻自己的阅读进度、查知识库。返回结果后仍要核对来源、时间和权限。

适合 Codex

工程型重任务

读仓库、改文件、跑测试、修复构建、提交审查。需要工作区上下文、diff、回滚点和验收闭环。

先别接

高风险写操作

发消息、改权限、删数据、创建凭据、支付或批量写入。先看 MCP 工具定义和审批卡，必要时不要接入。

05
RISK REGISTER

这套方法最容易踩的 5 个坑

评论区的“封号”说法不能当结论，但确实提示了需要审计的风险面。

01 · 数据外发

查询内容可能经过自建 Worker、上游 API 和第三方服务。健康、阅读、法律、微信数据不应默认视为普通文本。

02 · Token 注入错位

“桥层帮你注入 Token”意味着密钥会进入部署配置或请求链路。不要把上游密钥硬编码进公开 Worker 或工具描述。

03 · 只认一个 URL 的限制

一个入口便于使用，但会把多服务的认证、限流、错误处理和权限边界压进同一层，排错成本会上升。

04 · 数据结果不等于事实

地图评分、法条版本、列车时刻、知识库摘录都有时间和来源边界。插件只负责取数，不能替代核验。

07
FINAL TAKE

适合把它当成“个人工具层”，别当成魔法

从 Codex 额度管理出发，真正可迁移的是任务分流和权限审计。

先问：这是读取、写入，还是不可逆动作？再问：数据经过谁、凭据放在哪、结果如何核验？最后才决定把它放进 ChatGPT 插件，还是交给 Codex 做完整工程任务。

推荐使用

个人、低风险、只读、来源可追溯的 API 查询。

谨慎使用

涉及健康、法律、私域消息、知识库和账号数据的服务。

不建议默认开启

删除、发送、授权、支付、改权限等写操作。
