证据口径
本文是架构 playbook。文中 omp² 方案部分可能仍在推进，不能等同于已经发布、可安装的完整产品。

先给结论：复杂性必须有人拥有

如果一个 Harness 把状态藏在闭包、把策略散在插件、把每次工具调用拆成互不相识的阶段，系统短期看起来简单，长期却会让每个扩展和用户各自承担一份不一致的复杂性。

适合采用这套思路：你要支持多 Agent、远程驱动、可回放会话、插件生态、沙箱执行或多个实时界面。

第一步不要先加功能。先找出唯一权威状态、可信控制面和可取消的工作原语；否则 rewind、fork、resume、远程复制和 UI 投影都会产生第二个真相。

Agent Harness 是系统软件：状态要可重放，执行要有边界，复杂性要被模块拥有。

01 · 为什么简单外壳会裂开

ORIENTATION

表面模型：循环 + 请求

最小实现可以是“读取消息 → 请求模型 → 执行工具 → 把结果放回上下文”。这个模型适合单人、单会话、少工具的早期实验。

  • 状态常被放在调用点或闭包里
  • 工具协议靠字符串和分支拼接
  • 插件自行决定重试、后台化和取消

真实职责：一台小型引擎

一旦产品扩展，Harness 需要维护权威世界状态、记录变更日志、运行不可信动作、向多个视图复制状态、调度 actor、解释命令、适配不兼容协议并渲染实时界面。

这正是游戏引擎长期解决的复杂性类别。

02 · 先定设计包线，再设计子系统

DESIGN ENVELOPE

Playbook 要求先假设四种产品同时依赖同一个 Harness。它们不是用户画像，而是架构压力测试：只为一种场景设计的系统，会把控制器偷运进 TUI、把状态藏进闭包，最后无法复制和回放。

运行模式它要求 Harness 具备什么暴露的错误设计
Multiplexed workspace同一工作区内多个 Agent / subagent，拥有清晰的隔离和调度边界。共享可变状态；子 Agent 修改父会话的权威。
Remote driver远程客户端只消费状态流，不另造一份“远程真相”。Web、TUI 各自维护状态，断线后无法恢复。
Headless automation无人值守时仍有取消、限额、审批、日志和失败回收。后台任务无限运行，输出撑爆宿主。
Interactive product用户能检视、暂停、恢复、fork 和回放同一会话。UI 状态与日志状态分叉，rewind 只是视觉假象。
五条架构推论：唯一权威会话、可信控制面、有界工作、显式兼容性、视图即投影。

03 · State：只有一个真相来源

STATE

失败模式：日志不包含权威状态

消息树可能被记录了，但 todo、重试计数、子 Agent 注册表、流式标志等却活在日志之外。这样就出现两个真相：回放消息看起来正确，实际运行状态却已经改变。

典型后果是闭包计数器在 rewind 后错乱、死分支的存档复活、fork 前 checkpoint 被清空。

目标模型：物化会话 + patch 流

把整个会话物化为一棵可查询的树，日志记录属性变更。运行时可以缓存、索引，但不拥有第二份权威状态。

  • Rewind = 对状态树做 diff
  • 提示词 = 从同一状态树投影
  • 远程复制 = 订阅 patch 流
  • 渲染 = 组件注册表的投影

04 · Runtime：沙箱只执行，不决策

RUNTIME

干净的边界是：宿主拥有状态、推理、策略、审批、限额和日志；沙箱只接收有界的执行请求，并返回有界结果。把控制器放入 VM 会导致工具分裂和双向网关；把整个应用放入 VM 又会泄露提示词、源码或控制权。

HOST

可信控制面

决定谁能做什么、何时审批、资源上限是多少，以及所有结果如何进入会话状态。

BOUNDARY

执行请求

明确输入、超时、输出大小、信号和退出码；不把宿主的可变权威直接暴露给扩展。

SANDBOX

愚忠的 stub

只执行被允许的动作。子 Agent 通过隔离文件系统视图返回 diff，而不是共享父级权威。

边界检查

一次误用的 Read 不能返回 2GB 撑爆宿主；取消不能只依赖协作式 AbortSignal；进程死亡不能带走会话权威。

05 · Control Plane：Convar 管值，Director 管行为

CONTROL

值 → Convar

每个设置在声明处写清类型、默认值、帮助文本、作用域与标志位。持久化、复制、脏跟踪和会话继承由声明内生，不再由一个 god object 到处转手 setter。

判断规则：如果同一个配置的默认值、持久化和作用域散落在多个模块，它还没有真正拥有自己的复杂性。

行为 → Director 栈

Plan、Goal、todo 提醒和 force 不应各自拥有一套循环。候选 yield 沿 Director 栈流动，每层只做一种组合。

  • Pass：交给下一个
  • Continue：消费后再跑
  • Yield：交还用户
  • Push / Done / Fail：压入、弹出或带错返回
INPUT模型或用户产生候选动作
DIRECTOR策略层决定继续、暂停或交接
EXECUTE受边界约束的工作原语
STATE结果写回同一权威会话

06 · Inference / Tool / Interface / Stack

LAYER MAP
层不要怎么做建议拥有的复杂性可验收信号
Inference在五六个调用点复制 isXxxModel 分支。taxonomy 识别型号，classes 陈述事实，providers 声明宿主差异；未知返回 unknown。新模型接入只增加声明和测试，不复制分支。
Tool surfacerenderCall / execute / renderResult 三套互不相识的阶段。一次调用是带 input、result、diag、usage 子元素的状态流。模型、用户、日志和远程端看到同一调用的不同投影。
InterfaceTUI、Web、远程客户端各自成为权威。所有界面都是同一会话状态的投影。换视图不会改变会话语义，断线可从 patch 恢复。
Stack扩展跨越两个文件系统和多个语言边界手写 RPC。用统一工作原语、结构化配置和清晰 SDK 承担适配。扩展作者不必重新实现取消、限额、日志和序列化。

07 · 最小 POC：先证明边界，不先造全平台

IMPLEMENT

不要从“重写整个 Agent”开始。先做一个能够证明唯一权威、状态流和取消边界的窄 POC。以下是验证思路，不是 omp² 官方安装命令，也不是本机已执行结果。

08 · 失败边界：文档无法修复表达层面的漏洞

FAILURE MODES

可通过规则解决的问题

  • 状态只能通过事件或 patch 推导
  • 工具输出默认有上限，显式选项才解除
  • 所有后台工作都是可取消的流
  • 模型兼容知识由声明式层拥有
  • UI 不得写回自己的第二份权威

不能靠口头约定解决的问题

  • 扩展作者“记得”在 rewind 时清理闭包
  • 每个插件自己实现一套 mutex
  • 每个界面自己猜测当前 actor
  • 沙箱返回大小由调用者自觉控制
  • 新协议差异复制到所有调用点

证据边界

Playbook 中的失败统计和 omp² 架构描述属于作者文章语境；卡片没有把它们当作本机 benchmark。omp² 的目标设计、分支状态、公开安装方式和生产成熟度必须在实际使用前重新查官方仓库与发行版。

09 · 你现在该不该采用这套重构

ROUTING

适合：复杂性已经外溢

你需要多视图实时同步、可靠 rewind/fork、多个 Agent、远程驱动、沙箱、插件生态、资源治理或跨供应商模型适配。

不适合：仍在验证单一闭环

你只有一个 Agent、少量工具、单一界面，尚未遇到回放、取消、并发、权限和协议兼容问题。此时可以保持简单，但要预留状态与执行边界。

决策顺序：先问“谁拥有这份复杂性？”再问“我还要不要加一个功能？”
