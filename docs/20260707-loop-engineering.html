Claude Code 官方 Loop Engineering 设计指南定义了四类 Agent 循环模式。核心洞察：与其写一个完美的 Prompt，不如设计一个循环，让 Agent 在其中自主判断、验证、迭代。把"什么时候停"编码进系统，比告诉 Agent"做什么"更重要。

01 FOUR LOOPS · 四类循环对比
循环类型 触发方式 停止条件 最佳场景 核心命令
Turn-based 用户 Prompt Claude 自己判断完成 日常开发探索、短任务 claude 直接对话
Goal-based 实时 Prompt + 目标 目标达成 或 达到最大轮次 可量化目标（Lighthouse ≥90） /goal … stop after N tries
Time-based 时间间隔 手动取消 或 任务完成 定时检查 CI / PR / Slack /loop N m · /schedule
Proactive Loop 事件 / 定时，无人实时介入 各任务达目标后退出；例程本身直到手动关闭 长期 Bug / Issue / 依赖升级 /schedule + /goal + Dynamic Workflows
02 TURN-BASED · 对话驱动

触发：用户发送一个 Prompt，Claude 执行一轮后等待下一条指令。

停止：Claude 自己判断任务完成，无需继续。

最佳场景：短任务、日常开发探索、一次性修改。

关键技巧：

  • 把验证流程写成 Skill，让 Agent 自己验证自己的输出
  • Skill = 编码进文件的验收标准，不靠对话传递
  • 适合：需要 Claude 独立完成并自行判断完成的工作
SKILL.md 示例：内嵌验证 Skill
---
name: verify-api-contract
description: 验证 API contract 与实现是否对齐
---

# verify-api-contract

## 执行步骤
1. 读取 `src/api.ts` 中的 export 列表
2. 读取 `docs/openapi.yaml` 中的 paths
3. 逐个对比：export 但未定义 → ERROR；定义但未 export → WARN
4. 运行测试：`npm test -- --grep "api"`
5. 若有 ERROR → 报错退出；WARN → 输出警告；通过 → 输出 PASS

## 验收标准
- 所有 export 均有对应 openapi.yaml 定义
- 测试覆盖率 ≥ 90%
03 GOAL-BASED · /goal 目标驱动

触发：用户发一条带目标的实时 Prompt。

停止：目标达成 OR 达到最大轮次。

最佳场景：有可验证退出条件的工作。

典型命令
/goal get the homepage Lighthouse score to 90 or above, stop after 5 tries.

关键原则：

  • 确定性标准（测试通过数、分数阈值）最有效
  • 模糊目标（"让网站更好"）→ 模糊停止 → 浪费 Token
  • 指定最大轮次防止无限循环
  • 目标越具体，Agent 越少跑偏
04 TIME-BASED · /loop /schedule 定时循环
A /loop

本地运行，关机即停。适合：你还在开发机前、需要多轮迭代的工作。

  • 最短间隔：1 分钟
  • 能看到本地文件
  • 会话关闭即停止
  • 适合：本地 dev server 监控、代码审查循环
B /schedule

云端例程，持续运行。适合：机器不在也能跑、跨设备/定时触发的工作。

  • 最长间隔：1 小时（云端限制）
  • 看不到本地文件（需要接 GitHub 等）
  • 持续运行直到手动关闭
  • 适合：凌晨扫 GitHub Issue、CI 失败告警
C 对比

判别规则：

  • 这活离不开我这台笔记本吗？→ /loop
  • 机器不在也必须跑？→ /schedule
  • 需要每分钟跑？→ 只能 /loop（云端最低 1 小时）
  • 需要看到本地文件？→ /loop
典型命令
/loop 5m check my PR, address review comments, and fix failing CI
05 PROACTIVE LOOP · 主动循环

触发：事件或定时触发，无人实时介入。Agent 自主监控、决策、执行，无需人在旁边。

停止：各子任务达目标后退出；例程本身持续运行，直到手动关闭。

最佳场景：长期自动化流——Bug 报告处理、Issue 分类、代码迁移、依赖升级。

1 触发层
  • /schedule 定时触发
  • GitHub webhook 事件触发
  • GitHub Actions cron job
  • Auto Mode 自动轮询
2 工作层
  • /goal 定义可量化目标
  • Dynamic Workflows 编排多步骤
  • Skill 内嵌验证标准
  • worktree 隔离并行任务
3 保障层
  • Sub-agent 做 maker-checker
  • Memory 写磁盘持久状态
  • MCP 接外部系统（Jira/Slack）
  • 人工审核 + 批准 Gate
完整示例：Proactive Bug Triage Loop
# 每天 9:00 扫描未分类 Bug，自动分类并标记
/schedule "Every day at 9am UTC"

# 若发现新的 unclassified issue，自动运行：
/goal "Classify all unclassified GitHub issues by reading their content and labels, assign priority (P0-P3), add labels, and post a summary to Slack. Stop after 3 rounds if not complete."

# 每轮完成后，第二个 Agent 审查：
/goal "Review the triage output for accuracy, fix any mislabeled issues, and confirm the Slack message is correct."
06 CODE QUALITY · 代码质量维护
PILLAR 1 保持代码库干净
原则Claude 遵循现有模式，减少熵增
方法在 Skill 中写入项目的 lint / format / 架构规范
PILLAR 2 让 Claude 验证自己
原则把验收标准编码进 Skill，而不是对话
方法Skill = 测试命令 + 通过标准，Agent 自跑自检
PILLAR 3 文档易获取
原则框架 / 库文档有最新最佳实践
方法维护一份项目内 docs/ 或在 Skill 中内嵌参考
PILLAR 4 第二个 Agent 做审查
原则用另一个 Agent 做 code review，减少偏见
方法generator + evaluator 结构性分离
系统思维：单次结果不达标 → 改进系统（Skill / 验证标准 / 工作流），不只是修单个问题。把问题的根因当成"系统需要改进的地方"来处理。
07 TOKEN MANAGEMENT · Token 消耗管理
策略 说明
选对工具和模型 小任务不用多 Agent / 循环；简单脚本 vs. LLM 推理，成本差 10-100 倍
定义清晰的停止条件 模糊目标 = 无限循环 = 爆炸性 Token 消耗。/goal 必须带最大轮次
大规模前先小范围试点 用 /goal 先跑 1-2 次，验证 Token 消耗是否合理，再扩大规模
确定性工作交给脚本 LLM 做推理，脚本做执行。脚本比模型推理便宜 100 倍以上
不要比需要更频繁运行 CI 检查：每天 1 次 vs. 每次 commit，Token 节省 10-50 倍
用 /usage 审查消耗 定期运行 /usage 查看 Token 报告，识别异常高消耗的循环
08 DECISION GUIDE · 选型速查表
你想交给 Agent 的是 使用场景 优先用
检查步骤 探索或决策中，需要判断"这行不行" 自定义验证 Skill
停止条件 你知道什么叫"完成"，有量化标准 /goal
触发时机 工作在你的项目外定时发生 /loop · /schedule
完整 Prompt 重复性且定义清晰的工作 以上全部 + Dynamic Workflows
09 GETTING STARTED · 入门建议
01 从瓶颈开始

从你已是瓶颈的工作开始：

  • 哪些任务你每次都要重复做？
  • 哪些 Code Review / CI 检查占了你大量时间？
  • 哪些探索性调试让你反复查文档？
02 三个核心问题

拿到一个工作，先问：

  • 能写验证检查吗？→ 是 → /goal
  • 目标够清晰吗？→ 是 → 编码进 Skill
  • 工作定时来吗？→ 是 → /loop /schedule
03 迭代改进

不要等完美再开始：

  • 先跑起来，观察哪里卡住
  • 哪里越界了 → 加 Skill 限制
  • 哪里没停 → 加 /goal 轮次
  • 迭代改进，比想清楚再动更重要
KEY INSIGHT

"Stop asking the AI to do everything in one shot — design a loop where it can try, verify, and retry. The loop is the product."

— Loop Engineering 的核心转变：从"写一个完美的 Prompt"到"设计一个让 Agent 自己迭代的系统"
