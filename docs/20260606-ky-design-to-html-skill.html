核心判断 · 一句话先钉住
KY Design to HTML 不是“看图写 HTML”。它的价值在于把设计还原拆成可重复的工作流：先画页面地图，再把视觉资产和代码结构分开，最后用浏览器截图反复校准误差。
适合
UI 截图还原、SaaS 页面、后台页面、空状态页面、landing page 设计稿转静态网页。
不适合
没有视觉参考的纯文本需求、普通前端功能开发、把技能当作通用设计引擎的场景。
边界
它解决的是“还原流程”和“视觉误差修正”，不是替你凭空设计页面。

01它解决什么问题
Problem

为什么直接让 AI“根据图生成 HTML”容易翻车

因为它会同时承担结构理解、视觉复刻和复杂资产绘制三件事，最后常见结果是：布局挤形、比例跑偏、资产糊掉。

Fix

这个 skill 的修复策略

先把设计图拆成页面地图，再决定哪些是代码渲染，哪些必须当作图片资产，最后用浏览器截图做误差修正。

Outcome

结果不是“一次做对”，而是“能反复校准”

它的目标不是让模型一次生成完美页面，而是让页面可以按正确流程持续逼近参考稿。

02核心工作流
6-step loop

把任务拆成可执行的六步

  1. 先拆解页面地图
  2. 分离代码结构和视觉资产
  3. 设置设计稿画布和浏览器展示比例
  4. 写 HTML/CSS
  5. 浏览器截图验证
  6. 对比并修正视觉误差
Why it works

它把“复杂问题”改写成“逐步减误差”

这样做的好处是：每一步的偏差都可被单独定位，模型不再被迫在一次输出里同时解决布局、素材、比例和像素级视觉误差。

03资产分离
Render with HTML/CSS

哪些应该写进代码

导航、侧栏、卡片、按钮、标签、表格、表单、简单图标，以及页面骨架本身——这些东西删掉以后 UI 结构会明显变化，因此应由代码渲染。

Treat as asset

哪些应当视为图片资产

Logo、复杂插图、产品截图、3D 视觉、人物照片、复杂装饰图等。它们的形状与细节密度会决定页面品质，不要用 CSS 硬画。

判断分类原因
删掉后 UI 骨架还在资产适合用图片保存品牌与细节
删掉后布局就断了代码渲染说明它属于结构而不是装饰
复杂视觉细节资产不要用临时 SVG / CSS 硬画
简单图标 / 卡片 / 标签代码渲染能提高响应式与可维护性
04画布与验证
Reference canvas vs viewport

先分清“参考画布”和“浏览器窗口”

很多还原翻车不是样式错，而是把 artboard 与浏览器 viewport 混成一件事，最后页面被挤小、裁边或漂浮在角落里。

Validation loop

截图对比是最终裁判

先在真实浏览器里渲染，再拿截图和原图逐区域比对：整体画布、头部、主体、资产、页脚，按区域修正，而不是只盯某个 pixel。

Common failure modes
Canvas fit  → 页面缩在角落 / 被裁切 / 空白边太大
Layout      → 列比例不对 / 内容错位 / 卡片换行异常
Asset       → logo 失真 / 插图太糊 / 截图裁错
Responsive  → 桌面对了，移动端溢出或按钮压字

07适用边界
Best fit

最适合的任务类型

有明确视觉参考的设计还原任务：UI 截图、SaaS 页面、后台界面、空状态、landing page mockup。

Not fit

别把它当通用前端 skill

它不是普通功能开发、不是纯文本策划、也不是让 AI 无参考直接设计页面的工具。没有视觉参考时，应该走正常产品设计/前端流程。
