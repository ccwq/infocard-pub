Clone 是 Agent
的新瓶颈

Agent 越来越多跑在临时 sandbox 里，所有提供商都在优化"启动到能执行命令"的时间。但真正被忽视的瓶颈不是启动——是把代码 clone 进去。

git clone 一个普通仓库需要好几秒，等于好几次 sandbox 启动。Matt Rickard 正在做一个叫 Corigin 的解决方案，从头重建 git 读路径，把 clone 降到 184–646ms。

🔍 核心问题
TTI（Time To Interactive）只衡量 sandbox 能执行命令的时间。它不算把代码弄进去的时间。

对大多数仓库，从头 git clone 需要好几秒——相当于好几次 sandbox 启动。
如果 agent 工作流的标准是"每任务一个临时 sandbox"，clone 延迟就是每个 agent session 的固定入场费。

💡 洞察：Sandbox 启动优化已逼近极限，clone 还有数量级优化空间
690ms 的 TTI 已经很难再压，但 clone 有一个数量级的优化空间。Sandbox 提供商卷的是启动时间，而真正的瓶颈在数据搬运。这不是一个大市场，但对任何认真对待 agent 基础设施的人来说，这是一个该解决的问题。
⚖️
方案对比 · 为什么不直接挂载
❌ 挂载磁盘 / NFS
挂载时间几乎为零，文件操作很快。但问题是：

• 磁盘是共享的、可变的状态
• 每个 sandbox 都在同一个文件系统上工作
• 并行 agent 需要隔离
• 一旦用快照或"分支"磁盘，就是在重新发明版本控制
✅ 快速 Clone（Corigin）
每个 sandbox 在本地磁盘上物化自己的隔离副本：

• 仓库仍然是真正的 Git remote
• 每个 agent 有独立隔离的工作目录
• 完成后用正常的 git push 推回去
• 享受 Git 全部能力（分支、合并、历史、跨提供商）
🔧
Corigin 工作原理
优化 1 · 预计算
在 sandbox 外部预计算出 clone 计划，节省一次往返和约 155–370ms
优化 2 · 自定义协议
用自定义 clone 协议代替标准 git，但最终产物是完全相同的 git 仓库（语义等价）
优化 3 · 读路径重建
为 2026 年 agent sandbox 工作负载从头重建了 git 读路径程序化 git 服务器
结果
中位数 184–646ms 完成完整 clone —— 比 sandbox 启动还快
⚠️
Corigin 放弃了什么
往返节省的代价
预计算 clone 计划节省了约 155–370ms 的往返时间，但需要 sandbox 外额外的预计算步骤。
非标准协议
用自定义 clone 协议代替标准 git，最终产物相同，但 push 端稍慢（预计算加速的时间来自 push 端）。
push 变慢
预计算 clone 加速制品的时刻，就是 push 稍微变慢的时刻——读写性能需要权衡。
暂不支持优化
基准只测试了全量 clone，暂不支持 shallow、blobless、treeless 等 clone 优化策略。
