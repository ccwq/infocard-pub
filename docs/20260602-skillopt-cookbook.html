01 · 一句话判断
Core Take
core definition

把"如何写一个好 skill"从手工经验变成可优化流程：优化器模型先根据打分轨迹提出 bounded 的 add / delete / replace 编辑，再用持出验证集严格门控，只有真正提升才接受。这样得到的 skill 可以在不同模型、不同 harness 之间迁移。

SkillOpt 解决什么问题
把 skill 文档看成"冻结 agent 的可训练状态"，validation gate 看成"编辑是否进入模型"的硬阀门。训练期产出一串 skill snapshot、step patch、slow update、meta skill，最终收敛到一个可直接部署的 Markdown 工件。
关键判断SkillOpt 的价值不在于生成更多文本，而在于让 skill 的改进过程像训练神经网络一样可复现、可比较、可回滚。
你可以怎么理解它
它训练的不是模型权重，而是 best_skill.md 文档本身。部署时零推理开销，只挂到未改动的 target model 上。
文档级优化 验证门控 可部署 artifact 跨 harness 迁移
02 · 训练闭环架构
Loop Architecture
skillopt loop · rollout → reflect → gate → update
current_skill.md
初始 skill + 历史片段 + epoch 更新 + 拒绝编辑缓冲SKILL
↓ 作为系统提示 + 行为规范输入
ROLL OUT
跑 harness 收集分
REFLECT
bounded edits
↓ 生成候选 patch
VALIDATION GATE hard
SLOW UPDATE
epoch 边界
↓ 输出
best_skill.md
300–2,000 tokens · 直接挂载到 target model
rejected-edit buffer
每轮被验证拒绝的编辑进入 buffer，被接受的更新 skills/skill_vXXXX.md。你可以通过检查 skills/ 目录看到演变历史，随时回滚。
关键不是"多写几轮"
而是"每轮都比上一轮更严格"：训练数据来自 rollouts，编辑来自 reflect，接收来自 validation gate，稳定性来自 slow-update 和 rejected-edit buffer。
03 · Validation Gate 三型
Gate Types
hard gate default
候选 skill 必须在 held-out split 上每个样本都优于或等于当前 best，否则直接拒绝。零妥协，适合最终收敛。
soft gate
看平均分是否提升，允许少量样本暂时落后。适合训练早期探索，不容易卡在局部最优。
mixed gate
前 N 轮用 soft，后期切换 hard。兼顾探索效率和最终质量，是 ckpt 快照默认方案。
gate_metric: hard # hard | soft | mixed gate_threshold: 0.0 # soft 模式最小提升量
04 · Cookbook ① 最短训练路径
Train
最小命令
python scripts/train.py \ --config configs/searchqa/default.yaml \ --split_dir /path/to/searchqa_split \ --azure_openai_endpoint https://your-resource.openai.azure.com/ \ --optimizer_model gpt-5.5 \ --target_model gpt-5.5
这条命令在做什么
1
读 configbenchmark、batch、epoch、gate、skill_init 都从 YAML 拉起。
2
跑 rollout把 current skill 喂给 target model，拿到预测与分数。
3
反思 + 过滤optimizer 只建议 bounded edit，validate 后再接受。
epochs
训练轮数
默认 4 轮；太少学不够，太多容易在无效编辑上打转。
batch
rollout batch 40
轨迹太少 gate 不稳，太多则优化器成本飙升。
learning rate
文本学习率 4
控制每次文档改动幅度，不是模型参数学习率。
05 · Cookbook ② 只做评估
Eval-Only
评估已有 skill
python scripts/eval_only.py \ --config configs/searchqa/default.yaml \ --skill ckpt/searchqa/gpt5.5_skill.md \ --split valid_unseen \ --split_dir /path/to/searchqa_split \ --azure_openai_endpoint https://your-resource.openai.azure.com/
什么时候用它
A
复核论文结果直接评估 ckpt/ 里已清洗好的 GPT-5.5 技能。
B
对比自己训出的 skill把 `--skill` 换成 `outputs/.../best_skill.md` 即可。
C
验证迁移性同一 skill 在不同 split、不同 harness 下复测。
valid_unseen
测试集
论文与评估常用目标。
valid_seen
验证集
选技能、做门控的持出集。
all
全量评估
训练/验证/测试一起看。
06 · Cookbook ③ 扩展 backend / benchmark
Extend
加新 backend 四步
1
新建 skillopt/model/your_backend.py实现 generate() / generate_with_tools()，继承 ModelBackend。参考 base.py 定义抽象接口。
2
注册到 skillopt/model/__init__.py把 backend 放进 registry，才会被路由选到。
3
用环境变量塞凭据通过 .env / export 管理 API key，代码里用 os.environ.get('YOUR_API_KEY', '')。
4
YAML 指定 backendmodel_backend: your_backend，或在 CLI 里 --model_backend your_backend。
加新 benchmark 四件套
1
SplitDataLoader负责从 train / val / test 目录加载 item dict，只强制实现 load_split_items(split_path)。
2
rollout helper跑 target model 并打分，输出 hard / soft 分。
3
EnvAdapter接入 SkillOpt 生命周期：build_*_env、rollout、reflect、get_task_types。
4
YAML config把 benchmark 接到默认训练协议上。
docs/guide/new-backend.md
模板：先实现 backend，再注册 registry，再用 YAML 选择。已有：base.py、azure_openai.py、openai_model.py、claude.py、qwen.py。

07 · Cookbook ④ YAML 配置全字段
Config
参数作用默认/要点
gate_metric验证门控分数类型hard / soft / mixed
gate_thresholdsoft 模式最小提升量默认 0.0
learning_rate文本编辑步长默认 4，不是模型 LR
minibatch_size反思阶段每批样本数默认 8
num_epochs总训练轮数默认 4
rollout_batch_size每次 rollout batch 大小默认 40
skill_init训练起点 skill 文件空 skill 或种子文档
slow_update_gate_with_selectionepoch 边界慢更新是否走 gatefalse 对齐 main；true 对齐 ckpt
optimizer_model担任优化器的模型如 gpt-5.5、claude-3
target_model被训练的目标模型skill 最终要能服务这个模型
model_backend模型后端类型azure_openai / openai / claude / qwen / your_backend
⚠ 最易踩的坑如果只是"觉得 skill 写得还行"就扩大编辑，通常会把验证集冲坏。SkillOpt 的 cookbook 不是"多写点"，而是"每次改动都要过门"。
08 · Cookbook ⑤ 输出物完整解析
Artifact
训练目录文件清单
outputs/<run_name>/ ├── config.json # 训练配置快照 ├── history.json # 每 epoch score 轨迹 ├── runtime_state.json # 断点恢复用 ├── best_skill.md # ← 唯一要部署的文件 ├── skills/ │ └── skill_vXXXX.md # 各版本 snapshot ├── steps/step_XXXX/ # 单步输出 ├── slow_update/epoch_XX/ # epoch 边界结果 └── meta_skill/epoch_XX/ # meta skill（实验性）
如何判断有没有真提升
✓
看 best_skill.md 而不是只看日志真正要部署的是最终技能文件，不是训练历史。
✓
看 held-out score 是否严格更高gate 不通过，编辑就不算有效。
✓
看 history.json 的 score 曲线应该逐步上升或趋于稳定，不是剧烈震荡。
✓
看跨模型 / 跨 harness 迁移能从 Codex 迁到 Claude Code 等执行面。
09 · Cookbook ⑥ 断点恢复与复训
Resume
断点恢复训练
python scripts/train.py \ --config outputs/<run_name>/config.json \ --resume_from outputs/<run_name>/runtime_state.json \ --split_dir /path/to/searchqa_split
resume 时最容易踩的坑
1
runtime_state.json 版本不匹配代码更新后结构可能变，检查 history.json 的 epoch 字段是否连续。
2
split 数据路径变了--split_dir 必须和原始训练一致，否则 gate 评估数据分布不同。
3
optimizer model 变了resume 时默认复用 config.json 里的 optimizer model，换模型可能不兼容。

11 · 适合谁 / 不适合谁
Boundary
适合
1
想把 skill 变成可优化资产而不是每次靠手写 prompt 祈祷。
2
想复现论文结果 / 做 ablation需要严谨比较不同 gate、不同 harness、不同模型。
3
想要可部署、低推理成本的技能训练期复杂，部署期干净，适合生产化技能资产。
不适合
1
只想要一次性 prompt 模板那不需要这套优化器闭环。
2
不想准备验证集 / split没有 hold-out gate，SkillOpt 的核心价值会塌掉。
3
想让模型权重自己学会一切这套方法明确训练的是文本资产，不是参数。
