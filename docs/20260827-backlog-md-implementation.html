设计原则

单向数据流

机制

所有状态、依赖和审批记录只在文本事实源中维护；Excel、Word、图表均自动生成。

收益

避免多人、多 Agent 在多个文件里产生“哪个才是真的”这一类冲突。

审批边界

半自动协作

自动

读取、分析、拆解草案、校验、生成报表、执行已批准任务。

人工确认

范围、需求批准、关键写入、依赖删除、任务关闭、发布决定。

03

三层数据模型

需求定义“为什么”，功能定义“系统做什么”，任务定义“怎么实现”。

REQ

需求

Frontmatter：id、title、status、priority、owner、features、success_metrics。

正文必须包含
  • 问题与目标
  • 用户场景
  • 范围 / 非范围
  • 约束与成功指标
  • 验收标准
  • 变更历史
核心规则

未批准需求不能进入执行队列；变更后必须触发影响分析。

FEAT

功能

Frontmatter：id、title、requirement_ids、depends_on、status、milestone、task_ids。

正文必须包含
  • 行为边界与输入输出
  • 独立验证方式
  • 上游 / 下游依赖
  • 任务映射
拆解标准

每项功能可独立描述、验证、追溯；依赖必须显式而非藏在描述中。

TASK

执行任务

字段：title、description、parent、dependencies、status、priority、milestone、agent。

执行信息
  • REQ / FEAT 追溯链接
  • 实施计划与验收标准
  • 测试策略与证据
  • 最终总结
标签约定

req:、feature:、type:、risk:

--- id: REQ-001 title: 用户登录 status: Approved priority: P0 owner: product-owner features: [FEAT-001, FEAT-002] success_metrics: - 登录成功率 >= 99% ---
--- id: FEAT-001 title: 密码登录 requirement_ids: [REQ-001] depends_on: [] status: Ready milestone: MVP task_ids: [TASK-001, TASK-002] ---
04

状态机与硬规则

状态不是标签，而是可被校验的授权边界。

需求状态

Draft → Review → Approved → Changed → Retired

Approved 才允许下游正式排期；Changed 会重新打开影响评估。

功能状态

Proposed → Ready → In Progress → Verified → Done

任一未满足的上游依赖可进入 Blocked，解除后回到原合法状态。

任务状态

Draft → Ready → In Progress → Review → Done

执行中与评审中都可能进入 Blocked；恢复必须记录原因和证据。

不可绕过的约束
  • Draft 不可执行；只有审批通过才能进入 Ready。
  • 依赖未完成时，不得进入 In Progress。
  • 没有验收证据、测试结果和完成摘要，不得 Done。
  • Agent 不得自行扩大范围、删除依赖或降低验收标准。
  • 需求发生变更时，所有关联功能与任务重新评估。
05

六个阶段门：从想法到发布

每个 Gate 都有输入、动作、输出和人工决策点。

Gate 1
需求确认
动作
Agent 整理原始需求，补齐目标、场景、范围、非范围、约束、成功指标与验收标准；识别歧义和冲突。
输出 / 审批
REQ-*.md 草案与待确认问题；产品负责人批准后状态变为 Approved。
Gate 2
功能拆解
动作
将需求拆为可独立验证的功能；建立 REQ→FEAT 追溯，识别前置条件、共享能力、技术约束与依赖关系。
输出 / 审批
FEAT-*.md、功能依赖图、里程碑建议；人工确认边界和依赖。
Gate 3
任务拆解
动作
将功能拆成实现、测试、文档、迁移等任务；补齐 DoD、验收、测试策略、风险、估算和可并行组。
输出 / 审批
Backlog.md 任务、任务依赖图与候选分工；PM 确认优先级、里程碑和负责人。
Gate 4
计划批准
动作
执行 Agent 在写代码前形成实施计划：影响文件、接口、迁移、测试、回滚与风险；Reviewer 检查遗漏。
输出 / 审批
任务内的 Implementation Plan；关键写入必须由人批准后才能执行。
Gate 5
实施验证
动作
Agent 在独立分支/worktree 实施；持续更新状态和证据；Reviewer 对照验收标准检查代码、测试与范围。
输出 / 审批
代码、测试结果、证据、评审结论、完成摘要；人工确认关闭关键任务。
Gate 6
发布复盘
动作
聚合里程碑完成度、未决阻塞、风险、缺陷、测试和变更；执行 release-check；形成经验与后续行动。
输出 / 审批
Release Note、Excel 状态表、Word 报告、复盘记录；发布负责人做 Go/No-Go。
06

多 Agent 角色与协作协议

角色分工解决“谁能做什么”，集中调度解决“何时做”。

PM Agent

规划与编排

允许
  • 需求澄清与草案
  • 功能/任务拆解
  • 依赖、风险和里程碑分析
  • 生成报表与状态摘要
禁止

越权批准需求、擅自改范围、删除依赖、替人做发布决定。

Execution Agent

执行已批准任务

允许
  • 读取上下文与依赖
  • 提交实施计划
  • 代码、测试、文档
  • 附加证据和总结
禁止

领取未 Ready 的任务、绕过阻塞、扩大任务范围、自行关闭关键任务。

Reviewer Agent

独立质量检查

检查
  • 范围与追溯一致性
  • 验收和测试覆盖
  • 依赖是否满足
  • 回归与发布风险
输出

通过、要求修改或阻塞；结论必须关联证据，不直接代替人工批准。

并行执行纪律

集中分配任务；每个 Agent 同时只持有一个主任务；使用独立分支或 worktree；尽量避免编辑同一文件；严格服从依赖顺序；所有状态变化经 CLI/MCP 完成，不直接随意改元数据。

07

本地 pm CLI：把规则变成自动检查

先以脚本封装稳定操作；只有跨工具实时集成真正需要时才升级为 MCP。

pm validate pm graph pm ready pm assign TASK-12 codex pm release-check MVP pm export excel pm export word pm export all
validate

一致性校验

  • ID 重复与引用缺失
  • 循环依赖和孤儿节点
  • 验收标准是否完整
  • Done 是否有验证证据
  • 非法状态迁移
  • 下游是否提前启动
graph & ready

可执行性分析

  • 生成功能依赖图和任务依赖图
  • 列出当前阻塞链
  • 识别可并行任务组
  • 仅返回依赖已满足的 Ready 任务
  • 按优先级、里程碑和能力匹配 Agent

09

四阶段实施路线

先跑通真实 POC，再把稳定做法固化为通用 Skill 与 CLI。

Stage 1

最小 POC

目标：验证真实闭环。

  • 1 个需求
  • 3–5 个功能
  • 8–15 个任务
  • 至少 2 条依赖
  • Codex / Claude 各执行任务
  • 导出 Excel / Word
Stage 2

核心闭环

  • Backlog 配置
  • REQ/FEAT 模板
  • 项目管理 Skill
  • 状态机和审批规则
  • 依赖校验
  • 分配规则与报表导出
Stage 3

工程化

  • pre-commit 校验
  • CI 只读检查
  • 变更影响分析
  • release-check
  • 历史快照报告
  • 备份与迁移
Stage 4

可选 MCP

仅在多客户端实时读写、权限审计、统一原子操作或外部系统接入成为刚需时建设。

10

POC 验收标准

不是“页面能打开”，而是端到端可追溯、可阻塞、可验证。

场景配置

一个真实小项目

  • 选择边界清晰但包含依赖的需求。
  • 拆为 3–5 个可独立验收功能。
  • 形成 8–15 个实现/测试/文档任务。
  • 设计至少两条真实依赖和一个可并行组。
6 项通过条件

必须全部满足

  • REQ→FEAT→TASK 全链路可追溯。
  • 循环、缺失引用和非法状态可被阻止。
  • 被阻塞任务不会被 Agent 领取。
  • Codex 与 Claude 可按同一协议工作。
  • Done 任务都有测试与验收证据。
  • Excel/Word 与文本事实源一致且可重复生成。
11

V1 明确不做什么

主动收窄系统边界，避免一开始就构建第二套项目管理平台。

不引入第二事实源

不同时使用 Beads / Task Master 维护同一批任务，不做 Excel/Word 反向编辑。

不做无监督自治

不自动关闭关键任务，不让 Agent 改范围，不做无人监督的自动排期。

不先做重集成

不在 V1 同步 Jira/Linear 等 SaaS，不先写自定义 MCP。

不做虚假精确

不做复杂工期预测；先积累实际周期、阻塞和返工数据。

12

启动顺序与最终建议

用真实项目校正模型，再沉淀为可复用能力。

选择 POC真实、边界清晰、有依赖
建最小目录REQ / FEAT / TASK
跑双 Agent计划、审批、执行、评审
验收闭环校验、证据、报表
固化复用Skill + CLI + 模板
建议从一个真实 POC 开始。先证明需求拆解、依赖阻塞、双 Agent 执行、验收证据和 Excel/Word 导出能够闭环；随后再正式固化 Project Management Skill、CLI 与模板。只有当跨客户端实时协作成为明确瓶颈时，再引入 MCP。
