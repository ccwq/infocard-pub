💅 AI 界面外挂：让 AI 自己盯设计细节

jakubkrehel/skills 是 AI 界面质量提升 skill 集。AI 生成页面后，以前要设计师一处处挑的毛病——圆角不同心、图标没对齐、字号层级乱、对比度不够——现在可以让 AI 自己完成。

它适合三类人：用 AI 写前端的开发者（生成的页面自己看不出毛病）、没有专职设计师的团队（把设计审查标准化进 code review）、设计工程师（把个人经验沉淀成团队可复用的检查流程）。

🧩 它解决什么问题

没有它
AI 生成的页面「能跑但不好用」：按钮忽大忽小、圆角标准不一、正文挤成一团、错误提示各写各的。你隐约觉得丑，但说不出具体哪里错、该怎么改。
有了它
AI 按设计工程清单逐项自查：每个发现都带具体证据（哪个元素、违反什么规则），你按严重程度排序逐条修，或者直接让 AI 修完再复检。
知识来源：这些 skill 的内容沉淀自作者的 design engineering 博客（jakub.kr）与 Interfaces 杂志文章，不是泛泛的通用提示词。

⚡ 安装（两种方式）

方式一：npx 通用安装（任何 AI Coding 工具均可用，机器上需有 Node.js 环境） 
npx skills add jakubkrehel/skills
方式二：Claude Code 插件市场（推荐，体验最完整） 
/plugin marketplace add jakubkrehel/skills
/plugin install interfaces@interfaces
怎么确认装好了：安装完成后在对话里让 AI「列出当前可用的 skills」，应能看到 better-interface、better-ui 等 11 个名字。也可以在新的项目目录里直接说「帮我检查这个页面的 UI」，AI 若能识别并调用对应 skill，即安装生效。

💬 初学者怎么触发：不用记命令

这些 skill 走 自然语言路由：对话里描述需求，AI 自己匹配对应 skill。常用说法直接抄：

你想做什么对 AI 说
全面体检一个页面「用 better-interface 全面审查这个页面」
只查排版问题「检查这个页面的字号层级和换行」（better-typography）
只查配色「检查对比度和颜色 token」（better-colors）
给按钮做压力测试「break 这个按钮组件」（渲染全部状态）
看别人网站怎么做的「解释一下这个界面的实现方式」（explain-interface）
改完代码后复查「review 这次的界面改动」（interface-review）
记住一个分工：better-* 是「给现有页面挑毛病」，break / variant / explain-interface 是「主动探索新方案」，interface-review 是「改完之后的守门员」。

✅ 典型使用流程

1

写完页面后，在 Claude Code 里喊 /better-interface

2

它自动路由到 6 个分项 skill，收集界面、排版、配色、无障碍、布局、文案的证据

3

综合评级，输出最多 15 条有证据的发现，按严重程度排序。每条会指到具体元素和违反的规则，不是泛泛的「建议优化」

4

按优先级修复，或用 /break 组件名 单独压力测试某个组件

报告怎么读：每条发现 = 位置（哪个组件/哪一行）+ 规则（违反了什么设计工程标准）+ 严重程度。先修「所有用户都受影响」的（对比度不足、点击区域过小），再修「观感层」的（圆角不一致、字距松散）。存疑时把那条发现原样抛回给 AI 问「这条的依据是什么」，让它给出规则出处。

🧪 完整练习：给你的按钮做一次体检（约 10 分钟）

  • 第 1 步 · 准备样本：打开任意一个你有 AI 生成的页面项目（哪怕只有一个表单页）。没有现成项目？让 Claude Code 现场生成一个含注册表单的简单页面即可。
  • 第 2 步 · 跑全面审查：输入「/better-interface」，等它跑完 6 个分项检查。首次运行通常几十秒到几分钟，取决于页面复杂度。
  • 第 3 步 · 只读不改：通读报告，注意每条发现的三要素——哪个元素、违反什么规则（如「点击区域不足 44px」）、严重程度。把看不懂的规则名丢回给 AI 问「这条为什么重要」。
  • 第 4 步 · 修两条再复检：只挑严重程度最高的 1–2 条让 AI 修，修完重新跑一次审查，对比发现数量是否下降。这个「修前 vs 修后」的对比能帮你建立对检查标准的手感。
  • 第 5 步 · 试一次主动探索：对着页面里最核心的组件（比如提交按钮）说「break 这个组件」，观察它渲染出的全部状态——这是理解「组件该覆盖哪些状态」最直观的方式。

    • 🚧 常见坑与排查

    现象原因与处理
    AI 说「没有这个 skill」安装目录不对：skill 装进了别的项目。回到目标项目目录重新执行安装命令，或确认全局安装配置。
    报告太长不知从哪改起只看排序最前的 2–3 条。严重程度靠前的问题通常影响所有用户；后面的小问题等大问题清零再回头。
    AI 修完又引入新毛病修复后立刻复跑审查。把「修 → 复检」当成固定循环，不要连续修 5 条才检查一次。
    建议和团队规范冲突skill 输出的是设计工程通行标准，不是唯一标准。团队有明确设计系统时，以团队规范为准，把冲突项当作讨论起点。
    同一个问题反复出现说明是模式性问题（如全局字号混乱）。让 AI 给出统一的 token / 规范方案，而不是逐个元素修。
    报了「正确」的建议但不想改记录下来并在团队内对齐。skill 的标准是通用设计工程实践，接受或拒绝都应是有意识的决定，而不是忽略。

    🔬 逐 skill 深度解读

    六个 better-* 各管一个设计维度。知道每个具体查什么，才能挑对工具、看懂报告。

    Skill查什么（举例）什么信号该用它
    better-ui圆角是否同心（外圆角 = 内圆角 + 边框宽）、图标与文字的语义匹配、点击区域够不够大、过渡动画是否恰当页面「说不上来的别扭」，元素间不协调
    better-typography字号是否有清晰层级、行高与字距、长文本换行/截断策略、可变字体与 OpenType 特性是否用上正文难读、标题不突出、中英混排发虚
    better-colors颜色是否成体系、有没有语义 token（而非随手写色值）、文字对比度是否达标、格式互相转换颜色像「随手选的」，深色底看不清字
    better-accessibility无障碍标准合规、纯键盘能否走完流程、焦点环是否可见、ARIA 标签是否正确要发布面向公众的产品前
    better-layout相关元素是否分组、对齐是否一致、阅读顺序是否符合直觉、响应式断点行为信息密度一高就乱、窄屏下布局散架
    better-writing按钮/提示/错误文案风格是否统一、同一概念是否前后叫法一致有的地方写「确定」有的写「OK」

    🚀 进阶：三个高价值用法

  • ① 设计规范落地器：团队约定了规范但没人执行？把规范相关的检查项交给对应 better-* 在 code review 中把关。interface-review 会审查「这次改动对界面的影响」，区分真实缺陷与设计偏好，适合作为合并前的固定环节。
  • ② 竞品界面拆解：看到一个漂亮页面的效果（如某个悬停动画、某种渐变卡片），用 explain-interface 让 AI 解析它是怎么实现的——返回的是实现思路与代码逻辑，比肉眼猜快得多，适合做竞品分析或学习。
  • ③ 变体式方案比稿：犹豫某个组件的形态时（按钮放哪、卡片怎么布局），用 variant 一次生成多个变体放在一起比，避免「改一版看一版」的串行拉锯。
    • skill 内容是活的：这些 skill 的检查知识来自作者持续更新的博客与 Interfaces 杂志，仓库活跃（63 天 6,280★），定期更新安装即可拿到最新的检查标准。

    ⚠️ 边界：什么时候不适合用

    ❌ 不适合
    纯逻辑后端界面（无 UI）
    游戏 / 3D 界面（技能覆盖范围外）
    全新品牌设计（设计偏好非缺陷）
    已有成熟设计系统（已过此阶段）
    ✅ 适合
    AI 生成页面的质量审查
    设计工程流程标准化
    团队代码 review 中的界面检查
    组件变体探索与对比
