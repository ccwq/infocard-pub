01为什么工程师的感受如此分裂？

两阵营 vs 三元素

Agent 时代，工程师分成了泾渭分明的两派：有人觉得终于有了全明星阵容相助，工作效率倍增；有人哀嚎「craft 之死」，感到一切变得空洞（hollow）。

Addy Osmani 认为这是 gross oversimplification（粗暴简化）。他不站队，而是引导你问自己一个更根本的问题：

你工作中最 nourishing（滋养身心）的元素是什么？

答案不在「爱编码」和「爱发布」之间二选一，而是识别三种不同的快乐来源。Addy 本人在 X 上写道：「too often we see two camps: people who love the joy of coding and people who love the joy of shipping. I think this is a gross oversimplification.」

这三种快乐并非静态——它们在不同时刻、不同阶段交织于同一个人的工作中，权重也在不断变化。理解它们的差异，才是理解 Agent 影响的钥匙。

「I've seen engineers say many conflicting things about agents: some are bubbling with excitement and for the first time ever, they feel like they're in an all-star lineup, while others mourn for the death of their craft, leaving them feeling hollow.」
— Addy Osmani，2026-10-09，X 长推
02三种快乐的原文定义

Addy Osmani 的三分框架

Making

亲手塑造的快乐：代码从空白到成形，一切咔哒对上的瞬间。一种心流状态。

Knowing

洞悉的快乐：系统心智模型强到瞥一眼文件就知道 bug 在哪。直觉判断力。

Mattering

重要的快乐：知道自己就是那个大家依赖的专家。你的判断不可或缺。

Making：原文

「The joy of making (or "flow"): the joy of molding things in our hand and feeling that sweet moment when it all clicks into place.」

Making 的核心是亲手塑造（molding）——把东西握在手里，看着它从无形到有形，从模糊到精准。Addy 将其与「心流」（flow）并列，强调这是一种身体性（physical）的快乐：你的手指落在键盘上，代码咔哒一声对齐，那种感觉。

Knowing：原文

「The joy of knowing: the joy of having such a strong mental model of our systems that we sense where a bug will be just by glancing at files.」

Knowing 的核心是心智模型的深度（mental model）。不是记忆，不是搜索，而是直觉：系统出了什么问题，你瞥一眼文件就知道。这是多年沉浸在一个 codebase 里才能建立起来的东西。

Mattering：原文

「The joy of mattering: the joy of knowing that you are the expert that it all relied on.」

Mattering 的核心是不可替代感——你知道团队离了你的判断就会出错，你的决策是系统运转的锚点。这是一种存在感的快乐，而非技能性的。

三种快乐并非互相排斥，同一个人在不同时刻、不同阶段需要不同的快乐来源。初学者可能极度依赖 making（通过动手来学习），而资深工程师可能更依赖 knowing（凭直觉快速定位问题）和 mattering（承担战略判断）。
03Making：上移一层的心流

不再塑造每一行，而是塑造系统或工厂

Addy 的判断是：Agent 对 making 的冲击最小，且本质是「层次上移」。原文表述精准：

「The joy of making is easy to maintain. it just moves up a level. You're not shaping every line anymore. You're shaping the system or factory, in a loop fast enough that flow still happens. And when you miss the old flow, nothing stops you from writing the code yourself.」

翻译：造物之乐很容易维持。它只是上移了一个层次。你不再塑造每一行了——你在塑造系统或工厂，以足够快的循环让心流继续存在。想念旧心流时，没有任何东西阻止你自己写代码。

Making 的层次迁移

以前现在（Agent 辅助）快乐是否仍在？
亲手写每一行代码，找心流设计架构、定义接口、配置 Agent → 造工厂✅ 心流仍在，但入口不同
一行行调试，盯着屏幕描述目标 → Agent 写 → Review → 调整 → 再描述✅ 循环够快，仍有心流
闭门造车 2 小时完成一个功能描述清楚 → Agent 10 分钟 → 验收 30 分钟✅ 你的判断仍在心流里
想念自己写的纯粹感关掉 Agent，自己写个小模块练手✅ 完全可行

为什么 making 是三种快乐里最安全的

  • Agent 不知道你要造什么：方向、品味、优先级永远来自你
  • 循环速度是关键：Addy 强调「in a loop fast enough」——如果你的 Agent 对话响应太慢，心流会断；这说明工具链优化也是 making 的前提
  • 随时可以回去：「nothing stops you from writing the code yourself」——这是 making 独有的特权，knowing 和 mattering 都没有这个后备选项
Agent 时代 making 的快乐并未消失，只是入口从「一行行写」移到了「一层层搭」。只要你喜欢搭系统，making 就还在。

初学者特别提示

对于刚入行的工程师，making 的层次迁移带来一个风险：如果太早依赖 Agent 生成代码，你可能永远无法建立「亲手塑造」的心流感。建议：前 1-2 年刻意自己写大量代码，把 making 的基础打扎实，再逐步引入 Agent 作为架构设计的加速器，而非代码生成的替代品。

04Knowing：被低估的侵蚀危机

直觉枯竭的三个预警信号

这是 Addy 框架里最令人不安的部分，也是他认为需要「特别关注」的。

「Sometimes you'll realize you're reaching for a design you should be able to conjure automatically, but your intuition comes up with nothing. Picking an option from an agent's suggestions is a different skill than conjuring an idea in the first place. If you always pick and never conjure, the ability to conjure will erode.」

什么是 Conjure？

Conjure 在 Addy 的框架里是核心词，意为「凭直觉凭空构想」——无需外部提示，凭内化能力想出解决方案。这与「从选项中挑选」是完全不同的认知动作。

动作认知类型Agent 替代程度退化风险
Conjure（构想）创造 / 生成低——这是最难自动化的部分高——不用就会退化
Evaluate（评估）判断 / 决策中——Agent 可以给建议中——需要主动练
Select（选择）挑选 / 排序高——Agent 选项往往够用低——这是 Agent 放大的能力

⚠ 推导：三个 knowing 退化信号

  • 信号 A：该自动浮现的设计直觉不再浮现，需要等 agent 生成后才「恍然大悟」
  • 信号 B：无法在没有 agent 提示的情况下，从零描述一个模块的架构选择理由
  • 信号 C：看到 agent 的建议时，无法快速判断「这是对还是错」——因为你已经没有自己的 baseline mental model

最深的危机：谁在指挥谁？

不能指挥自己不理解的东西。
如果你不理解自己的 codebase，就是 agent 在指挥你。

这不是危言耸听，而是 ownership 的根本问题：当你对系统失去了内化的理解，你就不再是掌舵者，而只是 agent 输出的审批人。

相关研究：认知投降（Cognitive Surrender）

Addy 在 2026 年 5 月的博客文章《Cognitive Surrender》中引用了宾大沃顿商学院 Steven Shaw 和 Gideon Nave 的研究《Thinking - Fast, Slow, and Artificial: How AI is Reshaping Human Reasoning》（来源：addyosmani.com/blog/cognitive-surrender/）：

  • 在 1,372 名参与者的实验中，仅 AI 可用这一事实就足以让人投降——即使 AI 的答案错误，仍有 73% 的人接受
  • 更糟的是：当 AI 可用时，人们的自信度反而上升，尽管有一半答案是故意错误的
  • 他们在借用模型的自信（confidence borrowing），并把它当成自己的

相关研究：Agentic Skill Decay（技能衰减）

Addy 在 2026 年 8 月的博客《Agentic Skill Decay》中进一步阐述了这个问题（来源：addyosmani.com/blog/agentic-skill-decay/）：

  • 「Agent 可以完成任务，但不会教你任何东西」——这是刻意建立专业能力的新要求
  • Anthropic 的技能形成论文量化了这一点：用 AI 生成代码学习新库的工程师，在后续理解测验中得分低 17%；而用 AI 做概念探索（提问、权衡利弊）的工程师表现持平
  • 同一工具，不同使用姿势，结果截然不同
一项已完成的任务 ≠ 一次训练
如果你用 Agent 完成工作却没有主动学习，任务的完成和技能的建立是两件毫无关系的事。

保持 knowing 的策略

  • 在让 Agent 写之前，先形成自己的假设：「这个问题我认为应该这样解决」
  • 对比 Agent 输出与你的假设——差异才是真正的学习机会
  • 每周至少一次，关掉 Agent，从零自己写一个小模块，然后对比
  • 把 Agent 当作「会做笔记的同事」，而不是「代替思考的机器」
05Mattering：重心转移到判断与 Ownership

你的判断从未如此重要

「我的价值会不会被 agent 替代？」Addy 的回答直接：

You matter.
过时（being outpaced）确实影响你，但你的判断、尤其是「对判断的需求」从未更重要。
「You matter. Obsolescence does affect you, but, you, your judgment, and especially your need for judgment, has never been more important. You get to decide what problems to solve, and you get to bring your taste and judgment to the work you do. You get to take ownership of it, all of it, whatever ships.」

判断的两层过滤器

Addy 在另一篇关于 taste and judgment 的文章中，对「判断」做了更精细的拆解（来源：@addyosmani X 推文整理）：

过滤器定义在 Agent 时代的状态
Taste（品味）感受什么是好的能力——在能说出为什么之前就能感知好坏需要大量接触好作品才能建立，Agent 可以加速产出，但无法替代你建立品味的过程
Judgment（判断力）理解质量是有代价的——知道在什么时间、承担什么风险来交付来自领域知识和过往决策经验，Agent 不会替你做

Addy 的原话：「People with great taste but poor judgement make beautiful work too late. People with judgement but no taste make on time but don't make things people love.」

mattering 的新重心

旧重心新重心为什么更重要了
亲手写代码决定解决什么问题Agent 可以执行任何问题，但「什么问题值得解决」永远是你的判断
产出代码量带上品味（taste）与判断代码产量已经不再稀缺，稀缺的是有品味的代码
技术执行承担全部 ownership无论 ship 什么，最终都是你的名字在上面
我是那个写代码的人我是那个负责的人Agent 扩大了执行半径，但 ownership 永远是你的
Agent 时代 mattering 的本质是：你的责任边界没有缩小，反而扩大了。以前你只对「自己写的代码」负责，现在你要对「通过 Agent 建造的系统」负全部责任。

Outer Loop（外层循环）

Addy 在 2026 年 7 月的博客《Own the Outer Loop》中明确提出（来源：addyosmani.com/blog/own-the-outer-loop/）：工程师需要拥有「外层循环」——对系统的 Accountability。外层循环包括：质量控制、最终判断、安全影响、用户体验影响。这是 Agent 无法替代的领域。

06给哀悼者的信：Grief 是依恋，不是失败

悲伤不是适应失败的信号

Addy 专门对「哀悼 craft 之死」的人说了一段温柔的话，这可能是全文最有人文关怀的部分：

「That feeling of sadness isn't a sign of failure to adapt. Grief means that you're attached to something, and that it's natural to feel grief when you see your work changing in ways that feel unfamiliar. Lean into the things that make your work yours, and work on them more.」

翻译：那种悲伤感不是适应失败的信号。Grief（悲伤）意味着你在依恋某样东西，而当你的工作以陌生方式变化时感到 grief，是完全自然的。去投入那些让你的工作属于你的部分，在那些事情上花更多功夫。

这不是「接受现实往前走」的鸡汤

Addy 的处方不是让你强行适应，而是：找到变化中仍然属于你的、让你感到滋养的部分，然后投入更多。这比强行「接受」更可持续，也更诚实。

  • 如果你热爱 making——投入架构设计和系统塑造
  • 如果你热爱 knowing——刻意维护你的直觉肌肉（从零构建、关掉 Agent 的时间）
  • 如果你热爱 mattering——主动承担更多判断和 ownership 的责任
Grief 不是软弱，是诚实的信号——它告诉你：你真正珍视的是什么。顺着这个信号去找，而不是对抗情绪。

Addy 的亲身经历

在《Agentic Skill Decay》中，Addy 回忆了自己如何从零开始建立工程判断力：

「When I got started in software engineering, I very much felt like I had no idea what I was doing. I was having a lot of fun building, a lot of fun trying things out, failing, learning from my mistakes, and each time getting a little further and further in my journey.」

他强调：正是那些「试错-学习-再试」的重复循环，建立了他后来赖以判断的心智模型。这些循环现在可以被 Agent 加速，但建立模型的过程不会自动发生。

07三种快乐的职业阶段差异

不同阶段的人，感受截然不同

三种快乐的相对权重，随职业阶段变化而变化。理解这一点，可以避免用错误的标准评估自己。

职业阶段主导快乐Agent 对主导快乐的影响需要特别警惕的
在校生 / 入门 1-2 年Making（大量练习中）如果太早引入 Agent → making 基础不扎实 → knowing 后继乏力建立 making 基础优先，Agent 辅助但不要替代
初级工程师（1-3 年）Making + Knowing（混合）Agent 可以加速 making，但 knowing 需要刻意练习用 Agent 做产出，不做练习；主动维护直觉
中级工程师（3-7 年）Knowing（主导）+ Making（补充）最危险的阶段：knowing 最容易被 Agent 悄悄侵蚀每周「关 Agent 从零构建」练习；维护自己的 mental model
高级工程师 / 架构师Mattering（主导）+ Knowing（支撑）Agent 放大执行半径，mattering 的责任边界扩大警惕「审批人」陷阱；主动掌控 outer loop
技术管理者Mattering（决策影响）Agent 无法替代判断和 ownership，但可以放大信息处理用 Agent 处理信息，不处理判断
初学者特别提示：如果你处于前两个阶段，你的 knowing 基础还没有建立——不要被 Agent 的高效输出迷惑。making 的快乐来自「亲手做」，knowing 的快乐来自「彻底理解」。两者都需要时间和重复来建立，Agent 可以加速，但不能替代。
08自检清单：初学者可操作

每周一次，3 分钟检测 knowing 状态

问题正常警告
Agent 给建议前，我能大概预判方向吗？ ✅ 能，且经常猜对 ❌ 完全没有预期，完全等 agent
能不用 agent 独立描述最近改的模块的架构选择吗？ ✅ 能，清楚讲出「为什么这样」 ❌ 讲不清楚，只知道「agent 这么写的」
review agent 代码时，能快速判断对错吗？ ✅ 能，有自己的 baseline ❌ 逐条接受，不敢质疑
遇到新问题时，能「凭空」构想出 2-3 种方案吗？ ✅ 能，conjecture 能力在线 ❌ 完全没有想法，要等 agent 给
用完 Agent 后，我能用自己的话复述它做了什么吗？ ✅ 能，理解了才复述 ❌ 复述不了，只知道「它说这样改」

3 题以上变警告 → 你正在失去 knowing。应对策略：每周至少一次，关掉 agent，从零自己写一个小模块，然后对比。

日常操作清单（可直接执行）

  • 在让 Agent 写代码之前，先写下自己的假设（哪怕只有一句话）
  • Agent 输出后，对比假设与结果的差异，记录学到的点
  • 每周选一个小功能，不用 Agent，从零构建（哪怕粗糙）
  • 定期向非技术人员解释你最近做的系统架构（费曼技巧）
  • 看到 Agent 的「神奇」输出时，追问「它为什么这样做」而非仅接受
  • 维护一个「我理解了什么」的笔记（与「我做了什么」分开）
  • 遇到 bug 时，先自己分析再问 Agent（哪怕分析是错的）
自检清单 knowing 检测 初学者友好 行动指引
09Agent 时代工程师的 10 项特质

Addy Osmani 的「有效工程师」框架

Addy 在 addyosmani.com 上有一篇持续更新的文章《What makes an effective software engineer?》（来源：addyosmani.com/blog/），列出了有效工程师的 10 项关键特质。在 Agent 时代，这些特质中哪些更稀缺了？

01 · 好奇心（Curiosity）

愿意深究每件事为什么是这样，而非仅接受表面答案。在 Agent 时代尤为重要——Agent 给出的答案往往是「最短路径」，追问为什么可以建立更深的理解。

02 · 成长心态（Growth mindset）

把错误视为学习机会。Addy 在 Agentic Skill Decay 中写道：「Every time I failed, I tried to take that as another building block in becoming a better engineer.」

03 · 所有权意识（Ownership）

对结果负全责，不甩锅给工具。这是 mattering 的核心——Agent 可以执行，但 ownership 永远是人的。

04 · 沟通能力（Communication）

向 Agent 描述清楚问题，和向人类描述清楚问题，本质是同一技能。模糊的需求 = 模糊的输出。

05 · 品味（ Taste）

感受什么是好的——在能论证之前就能感知。Agent 可以生成大量选项，品味是筛选的标准。

06 · 判断力（Judgment）

理解质量是有代价的——知道在什么时间点交付什么质量的产出。这是 Agent 无法替代的决策能力。

07 · 专注力（Focus）

在碎片化 Agent 对话中保持深度思考的能力。认知的连续性是 Agent 难以替代人类的关键。

08 · 效率（Efficiency）

知道什么时候用手工，什么时候用 Agent——不是非此即彼，而是有策略地分配认知资源。

09 · 战略思维（Strategic thinking）

决定解决什么问题，比知道怎么解决更重要。Agent 时代「做什么」比「怎么做」稀缺得多。

10 · 学习能力（Learning ability）

在信息过载和 Agent 输出过量的时代，筛选什么值得学、什么值得深入的能力，比以往任何时候都重要。

11Addy Osmani 的工程人生轨迹

理解一个人说了什么，先理解他走过了什么

Addy 的《Joys of Engineering》之所以有分量，不只是因为论点是好的，更因为他有 25 年从业经验、亲手建造过被数十亿人使用的系统。以下是他的人生轨迹（来源：addyosmani.com/bio、yespress.io/addy-osmani）：

16 岁（约 2000 年代初）

在爱尔兰 Mullingar 的 St. Finian's College，以中学生身份独自用 C++ 编写了一个叫「XWebs」的浏览器原型，获得爱尔兰国家青年科学家奖（Esat BT Young Scientist of the Year，一等奖，€3,000）。这个浏览器包含下载管理、内置媒体播放器、网页编辑器，甚至能朗读网页内容的动画助手，并使用了他自己设计的「chunking」技术来并行加载网页——这个思路与后来 HTTP/1.1 的 pipelining 和现代浏览器的并发连接高度相关。

大学阶段

在 Sheffield Hallam University 获得计算机科学学士学位，后在 University of Warwick 获得计算机科学研究型硕士学位，并完成了 University of Oxford 的安全设计研究生认证。爱尔兰微软 MVP，参与 Imagine Cup 并进入决赛。

jQuery 社区时期

jQuery Bug Triage Team、API Documentation Team、Core Team 成员。与 Dave Methvin（jQuery 项目负责人）、Yehuda Katz、Paul Irish 共同工作。创建了 jQuery UI Bootstrap，解决了 Twitter Bootstrap 与 jQuery UI 的 CSS 冲突问题。共同创建了 UMD（Universal Module Definition）模式。

2012 年 · 加入 Google

加入 Chrome 团队（14 年 Google 之旅的起点）。共同创建了 Yeoman（Web 脚手架工具），最终积累了 9,000+ 个生成器模板。出版《Learning JavaScript Design Patterns》（ O'Reilly），成为前端开发者的必读标准。

Chrome DevEx 领导期（2012-2024）

领导 Chrome 开发者体验团队，负责 DevTools、Lighthouse、PageSpeed Insights、Puppeteer、Chrome Headless、Chrome for Testing 以及 Aurora 框架合作（React、Angular、Next.js）。创建了 TodoMVC——这个项目后来成为 Apple、Intel 和所有浏览器厂商优化芯片和引擎的工作负载基准（通过 Speedometer）。2019 年推动 Speedometer 2.0 的跨浏览器协作。2022 年 Chrome 成为首个在 Speedometer 上得分达到 300 的浏览器（后达 360）。

2022 年

出版《Leading Effective Engineering Teams》（ O'Reilly）——基于 10 年 Google 管理经验写成。

2023 年

与 Lydia Hallie 共同创建 Learning Patterns（patterns.dev）——至今吸引超过 500 万独立读者。

2024-2025 年

转任 Google Cloud AI 总监，领导 Cloud AI 开发者体验和技术布道，帮助推出 Google 的 Agent 开发者平台。领导 Gemini 与 Chrome DevTools 的 AI 功能集成。与 Google DeepMind 团队合作，让 Gemini 更擅长全栈 Web 开发。

2025 年

出版《Beyond Vibe Coding》和《Building Web Apps with Bolt》（ O'Reilly）。共同撰写 Google 白皮书系列《The New SDLC With Vibe Coding》。出版《Web Performance Engineering in the Age of AI》。

2026 年（现在）

离开 Google，加入 Anthropic，任 Member of Technical Staff，负责 Claude Code 产品开发。密集发布 Agentic Engineering 系列文章（本文的源头）。

读完这条时间线，你或许能更好地理解为什么 Addy 说「you matter」——这不是鸡汤，而是一个亲手建造了亿级影响系统的人，对工程本质的判断。
12边界与局限

这张卡的边界

  • ❓ 无量化数据：三种快乐感受程度的分布、knowing 退化的发生率均无公开研究数据，本文全为定性分析
  • ❓ 个体差异：making/knowing/mattering 的相对权重因人而异，本文不构成普适公式
  • ❓ 时间维度：三种快乐随职业阶段变化，初学者与资深工程师的需求重心可能相反
  • ❓ Agent 质量差异：不同 Agent 的能力边界差异巨大，Addy 的判断基于他使用的 Agent 能力（Claude Code），能力更强的 Agent 可能改变结论
  • ❓ 工程领域差异：Addy 的背景以 Web 开发和 AI 工程为主，其他工程领域（嵌入式、操作系统、游戏）的 making/knowing 模式可能有显著差异
  • 本文为 Addy Osmani 观点的忠实转述，不代表本卡立场

14快速参考：三分钟总结

Addy Osmani · The Joys of Engineering · 一句话版本

「Agent 时代工程师有三种快乐：making（造物）、knowing（洞悉）、mattering（重要）。Making 最安全，Knowing 最危险（不用就会退化），Mattering 的责任边界反而在扩大。」

一句话行动建议

  • 初学者：先建立 making 基础，不要过早用 Agent 替代自己的构建过程
  • 中级工程师：维护 knowing 肌肉——每周一次关 Agent 从零构建
  • 所有工程师：mattering 的时代已经来了，主动承担 outer loop 的 ownership
Grief 是诚实的信号，不是失败的信号。顺着它找到让你感到滋养的部分，然后投入更多。
15工程的长回报曲线：深度工作与延迟满足

为什么 making 和 knowing 需要时间才能建立

Addy 在多篇文章里都暗示了一个前提：工程的长回报曲线（long feedback loop）。与 Agent 提供的「即时满足」不同，真正的工程能力需要时间积累。这个话题值得专门展开。

什么是「长回报曲线」？

软件工程有一个独特的经济学特征：你今天的投入，往往要在数月甚至数年后才能得到回报。举例：

  • 花一周理解一个系统的底层设计 → 未来 2 年里每次调试都节省 2 小时
  • 花一个月建立数据库索引优化的直觉 → 未来每次性能问题都能快速定位
  • 花 6 个月深度参与一个大型重构 → 未来对任何系统的重构决策都有了参照系

这种回报曲线与 Agent 的工作模式存在结构性张力：Agent 优化的是「这一次」的产出速度，而不是「你作为工程师」的长期积累速度。

深度工作（Deep Work）与 Agent 的冲突

Cal Newport 在《深度工作》（Deep Work）中定义的「深度工作」是：无干扰状态下专注进行的认知活动，产生高认知价值。而 Agent 的工作模式天然是碎片化的：对话式、多轮次、上下文窗口驱动的。这两种模式对大脑的要求截然不同。

深度工作的能力，是一种需要维护的专业能力。
如果你长期依赖 Agent 的碎片化对话，深度工作的肌肉会退化——就像长期用计算器的人，心算能力会退化一样。

Addy 在 Agentic Skill Decay 中的建议与此呼应：刻意保留「不用 Agent 自己构建」的时间块。这本质上是在维护深度工作的能力。

写作与分享：另一种长回报

Addy 本人是「工程写作」的深度实践者。从《Learning JavaScript Design Patterns》（2012）到《Beyond Vibe Coding》（2025），他的书籍和博客文章构成了一个持续 14 年的知识积累体系。这个体系的价值是什么？

  • 外化心智模型：写出来的知识，比脑子里的更清晰、更可检验
  • 建立品味：要写出好的解释，你必须先理解得足够透彻——写作是深度学习的副产品
  • 长期复利：2012 年的书至今仍在帮助开发者，产生了远超写作时间的回报

对于工程师来说，写作和分享（博客、演讲、内部文档）是一种「深度工作 + 长回报曲线」的完美结合。

初学者的长回报策略

短期行为（今天）长期回报（未来）如何衡量
关 Agent 写一个完整小功能建立 making 基础，直觉肌肉能独立描述自己的设计选择
写博客记录今天学到的外化模型，发现逻辑漏洞能向非技术人员解释清楚
深度阅读一个系统设计建立 knowing 的底层积累遇到问题时能快速定位
主动承担一个判断决策建立 mattering 和 ownership决策后能说出为什么
每周一次「无 Agent 工作日」维护深度工作能力能连续专注 3 小时以上
Agent 是「短回报」的高手——它可以让你今天完成更多工作。但「长回报」的事（建立能力、深度学习、积累判断力）永远是你自己的事。用 Agent 优化短回报，用自己的时间投资长回报。
16Agent 与工程的哲学反思：工程师到底是什么

一个值得经常追问的问题

当 Agent 可以写代码时，「工程师」到底意味着什么？这个问题不只是哲学讨论——它直接影响你如何分配自己的时间和精力。

历史上「工程师」的定义

从词源看，「engineer」来自拉丁语「ingenium」（天资、聪明），最初指「发明者」或「制造者」。现代工程学的核心是：用系统化的方法，把资源变成满足人类需求的功能系统。

这一定义里，「资源」的形式可以变化（人力、机械、数字），但「系统化方法」和「满足人类需求」从未改变。

那么 Agent 在这个定义里是什么？

Agent 是执行资源（execution resource）——它可以完成「系统化方法」中大量的技术执行工作。但它无法替代：

  • 定义问题：用户真正需要的是什么？技术问题背后的人类需求是什么？
  • 设定边界：在时间、成本、质量的三角约束下，什么是「足够好」？
  • 承担后果：系统失败了，谁来负责？谁能修复？
  • 积累智慧：从这次经验中学到了什么，下次如何改进？

三种「工程师」类型在 Agent 时代的变化

类型典型描述Agent 影响未来价值
代码执行者「我写代码，需求别人给」直接替代风险高需要升级到架构或判断层
系统思考者「我设计系统，也写核心代码」部分增强（执行加速）高，且更稀缺
问题定义者「我搞清楚什么值得解决」几乎不受影响最高，且越来越稀缺

Addy 的立场：不做虚无主义者，也别做工具恐惧者

「I've seen engineers say many conflicting things about agents: some are bubbling with excitement and for the first time ever, they feel like they're in an all-star lineup, while others mourn for the death of their craft, leaving them feeling hollow. I'm someone who works with agents every day, so I understand these sentiments.」

Addy 的话里有一个关键细节：「我每天都在用 Agent 工作」——这不是一个旁观者的分析，而是一个深度实践者的观察。这让他的框架比大多数讨论更有参考价值。

实用主义的建议

与其争论「Agent 是否会让工程师失业」，不如问一个更具体的问题：

在我的工作中，哪些部分被 Agent 替代后，我会变得更强？哪些部分被替代后，我会变得更弱？

前者值得放手给 Agent（重复性执行、信息检索）。后者值得自己保留并刻意练习（判断、决策、创造、深度理解）。

工程师的进化路径不是「学会用 Agent」，而是「在 Agent 可以替代的地方放手，在 Agent 无法替代的地方加倍投入」。这才是 Addy 的框架真正想说的。
