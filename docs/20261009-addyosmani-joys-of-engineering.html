Agent 时代的工程快乐

The Joys of Engineering in the Age of AI Agents

Addy Osmani · 2026-10-09

来源：@addyosmani 原推 · 2026-10-09

Agent 带来解放还是失落？取决于你 leaning on 哪种工程快乐：making（造物）、knowing（洞悉）、mattering（重要）。
三种快乐在 Agent 时代受到的影响并不均等——有一种正在悄悄流失。
making造物之乐 / 心流
knowing洞悉之乐 / 直觉
mattering重要之乐 / 价值感
01为什么工程师的感受如此分裂？

两阵营 vs 三元素

Agent 时代，工程师分成了泾渭分明的两派：有人觉得终于有了全明星阵容相助，工作效率倍增；有人哀嚎「craft 之死」，感到一切变得空洞（hollow）。

Addy Osmani 认为这是 gross oversimplification（粗暴简化）。他不站队，而是引导你问自己一个更根本的问题：

你工作中最 nourishing（滋养身心）的元素是什么？

答案不在「爱编码」和「爱发布」之间二选一，而是识别三种不同的快乐来源。

02三种快乐的原文定义

Addy Osmani 的三分框架

Making

亲手塑造的快乐：代码从空白到成形，一切咔哒对上的瞬间。一种心流状态。

Knowing

洞悉的快乐：系统心智模型强到瞥一眼文件就知道 bug 在哪。直觉判断力。

Mattering

重要的快乐：知道自己就是那个大家依赖的专家。你的判断不可或缺。

三种快乐并非互相排斥，同一个人可能在不同时刻、不同阶段需要不同的快乐来源。

03Making：上移一层的心流

不再塑造每一行，而是塑造系统或工厂

Agent 对 making 的冲击最小，且本质是「层次上移」：

  • 以前：亲手写每一行代码，找心流
  • 现在：让 Agent 写代码，你塑造架构、定义接口、设计工厂——循环快到心流仍在
  • 想念旧心流时：随时可以自己写几行，Agent 不拦你
Agent 时代 making 的快乐并未消失，只是入口从「一行行写」移到了「一层层搭」。只要你喜欢搭系统，making 就还在。
04Knowing：被低估的侵蚀危机

直觉枯竭的三个预警信号（推导）

Agent 对 knowing 的冲击最隐蔽，也最危险。Addy 原文的原文表述是：

「从 agent 建议中挑选」≠「自己 conjure」
只挑不 conjure，conjure 能力会退化。

Conjure = 无需外部提示，凭直觉「凭空」构想出解决方案的能力。这种能力一旦退化，判断力随之萎缩。

⚠ 推导：三个 knowing 退化信号

  • 信号 A：该自动浮现的设计直觉不再浮现，需要等 agent 生成后才「恍然大悟」
  • 信号 B：无法在没有 agent 提示的情况下，从零描述一个模块的架构选择理由
  • 信号 C：看到 agent 的建议时，无法快速判断「这是对还是错」——因为你已经没有自己的 baseline mental model

更深层的危机：

不能指挥自己不理解的东西。
如果你不理解自己的 codebase，就是 agent 在指挥你。

这不是危言耸听，而是 ownership 的根本问题：当你对系统失去了内化的理解，你就不再是掌舵者，而只是 agent 输出的审批人。

05Mattering：重心转移到判断与 Ownership

你的判断从未如此重要

「我的价值会不会被 agent 替代？」Addy 的回答直接：

You matter.
过时（being outpaced）确实影响你，但你的判断、尤其是「对判断的需求」从未更重要。

Agent 时代 mattering 的新重心：

旧重心新重心
亲手写代码决定解决什么问题
产出代码量带上品味（taste）与判断
技术执行承担全部 ownership

无论 ship 什么，最终都是你的名字在上面。Agent 扩大了你的执行半径，但 ownership 永远是你的。

06给哀悼者的信：Grief 是依恋，不是失败

悲伤不是适应失败的信号

Addy 专门对「哀悼 craft 之死」的人说了一段温柔的话：

Grief 意味着依恋（attachment）。
看着工作以陌生方式变化时感到 grief，是完全自然的。

他的处方不是「接受现实往前走」，而是：

Lean into 让工作属于你的部分，
更多地投入它们。

不是对抗变化，而是找到变化中那些仍然属于你的、让你感到滋养的部分，然后投入更多。这比强行适应更可持续。

07自检清单：初学者可操作

每周一次，3 分钟检测 knowing 状态

问题正常警告
Agent 给建议前，我能大概预判方向吗？ ✅ 能，且经常猜对 ❌ 完全没有预期，完全等 agent
能不用 agent 独立描述最近改的模块的架构选择吗？ ✅ 能，清楚讲出「为什么这样」 ❌ 讲不清楚，只知道「agent 这么写的」
review agent 代码时，能快速判断对错吗？ ✅ 能，有自己的 baseline ❌ 逐条接受，不敢质疑

3 题都变警告 → 你正在失去 knowing。应对策略：每周至少一次，关掉 agent，从零自己写一个小模块，然后对比。

推导自检 knowing 检测 初学者友好
08边界与局限

这张卡的边界

  • ❓ 无量化数据：三种快乐感受程度的分布、knowing 退化的发生率均无公开研究数据，本文全为定性分析
  • ❓ 个体差异：making/knowing/mattering 的相对权重因人而异，本文不构成普适公式
  • ❓ 时间维度：三种快乐随职业阶段变化，初学者与资深工程师的需求重心可能相反
  • 本文为 Addy Osmani 观点的忠实转述，不代表本卡立场
