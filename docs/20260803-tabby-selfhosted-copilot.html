01
定位

为什么需要 Tabby？

开源的自托管代码补全引擎，提供接近 Copilot 的实时补全体验，数据处理在自有服务器完成。

适用场景

  • 企业内网，禁止代码出境
  • 金融、医疗、政务等高合规行业
  • 团队需要私有化部署或定制模型
  • 希望降低云端订阅费用

不适用的场景

  • 个人用户只想即开即用
  • 必须追求顶级闭源模型效果
  • 没有 GPU、服务器或运维能力

04
部署

从 Docker 到生产环境

以下命令只说明部署路径，不代表在本机执行。

Docker 单机部署

# 拉取镜像 docker pull tabbyml/tabby # 启动服务 docker run -it \ --publish 8080:8080 \ --volume ~/.tabby:/tabby \ tabbyml/tabby \ serve --model StarCoder-1B

GPU / Kubernetes

# GPU 部署 docker run --gpus all \ --publish 8080:8080 \ --volume ~/.tabby:/tabby \ tabbyml/tabby \ serve --model TabbyML/DeepSeek-Coder-1.3B # Helm helm install tabby tabbyml/tabby
05
接入

IDE 与推荐组合

先验证端点，再把 Tabby 接入编辑器；后端可以按隐私与吞吐需求替换。

VS Code

code --install-extension tabbyml.tabby

在设置中填写 Endpoint 与 API Key。

JetBrains

在 Plugins 中搜索 Tabby，配置服务端点与凭据。

Neovim

use { "TabbyML/tabby.nvim" }

适合希望完全掌控编辑器与服务端的用户。

推荐组合：Tabby（补全）+ Ollama 或 vLLM（本地推理）。这样可以在兼容 API 的前提下切换后端。
06
风险

使用前必须接受的代价

自托管的优势来自控制权，成本也正来自控制权。

模型质量

小型本地模型与顶级闭源模型存在差距，补全质量取决于模型、上下文和任务类型。

硬件要求

1B 模型门槛较低，7B 及以上模型通常需要更多显存；无 GPU 时延迟可能明显上升。

运维成本

需要维护 GPU 服务器、模型文件、Tabby 实例、权限和升级策略。
