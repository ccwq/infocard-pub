高密度页面怎么组织：先定任务与信息模型，再选表达骨架

这份指南处理的不是“把后台做得更漂亮”，而是当一屏里同时存在多个对象、状态和关系时，用户能否准确理解、判断并继续行动。它把页面设计拆成：页面塑形 → 页面编排 → 实现验收；配套 demo 用 19 个可运行骨架展示同一套判断如何落到 Ant Design。

01

先判断：页面要帮助用户做什么？

不要从 API 返回了数组就做表格，也不要从路由有 ID 就做详情页。

01 / Domain系统里有什么？对象、关系、事件、规则，以及权限模型。
02 / Task用户要完成什么？找、懂、比、处理、协作、追踪，还是安排时间。
03 / Expression什么结构最少转换？表格、列表、树、看板、时间线、日历、文档或画布。
适用范围

信息密集型页面

管理后台、监控与可观测性、数据分析、运维控制台、评审/工单系统、交易与排期终端。

不适用

不是所有页面都要套

营销落地页、内容消费页、单一转化表单不在指南范围；它们的成功标准不同。

硬约束

一个首屏主模型

标题、状态、主操作和核心判断信息要组成清楚顺序；Tabs、Card、Drawer、Modal 只是编排容器。

02

三工作流：先塑形，再编排，最后验收

三个阶段有回退关系：实现问题回到编排，模型或骨架错误回到塑形。

阶段先回答输出不要用来掩盖什么
Workflow 1 / Page shaping主任务、主信息模型是什么？页面类型、表达模式、骨架不要用 Card、颜色或 overlay 掩盖信息层级错误
Workflow 2 / Page orchestration用户先看什么、接着判断什么、在哪里行动？优先级、注意顺序、密度、反馈计划不要靠增加容器隐藏不相关字段
Workflow 3 / Implementation acceptance组件映射后，任务和信息关系是否仍成立？组件、响应式/键盘适配、验收结果不要用自定义样式掩盖编排错误
回退发现窄屏、权限、错误恢复问题回到正确的上游阶段修正不要只补一个局部红色提示

04

可运行 Demo：用同一套技术栈对照 19 种骨架

demo 不是生产模板，而是把结构差异变成可以打开的页面。

git clone https://github.com/alswl/guides.git cd guides/fe-page-guide-antd-demo npm install npm run dev # http://localhost:5173 npm run build # tsc + vite build

技术栈

Vite + React 18 + TypeScript + Refine + Ant Design v5 + ProComponents；package.json 同时列出 react-router-dom、dayjs、icons 和 plots。

目录如何对应

src/pages/ 放 19 个 skeleton 实现；src/data/ 是 seed 与内存数据；components/ 放共享壳与标签。

数据边界

README 明确是 in-memory mock；提交、处理、保存等写入只改内存，刷新页面恢复 seed data。

05

Demo 路由不是目录：用反例感受结构差异

选择骨架时，必须看用户动作；业务内容只是可比较的概念填充。

/board vs /runs

Kanban 是“移动对象推进阶段”；Trace Drill-Down 是“查看执行链与失败原因”。一个可操作，一个偏追踪，不要只因都用了步骤感就混用。

/calendar vs /activity

Calendar 判断谁占用哪个时间段、哪里冲突；Timeline 表示已经发生的事件顺序。两者的时间语义不同。

/relations vs /regions

关系只是上下游邻接时用分组列表；空间分布本身影响判断时，才值得用自定义画布。

不要把 Demo 当现成业务系统：README 明确说明零售业务数据是 conceptual filler，骨架与组件关系才是项目要展示的对象。
06

实现验收：只检查会不会破坏理解、判断与行动

视觉样式不是验收终点，窄屏、键盘、错误恢复和权限状态都属于结构的一部分。

首屏

  • 5 秒内说清对象、状态、主操作
  • 主模型只有一个
  • 关联信息跟随主任务

操作

  • 筛选条件可见且可清除
  • 长操作显示进度
  • 高风险变更可取消/撤销/确认

适配

  • 窄屏不打乱信息顺序
  • 键盘焦点可追踪
  • 错误、权限和异常有恢复路径
验收问题只有一个方向：用户能否沿着页面的信息关系，直接完成主要任务，而不是记住上一屏的字段、ID 或比较结果。
