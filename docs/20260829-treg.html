一句话定位：Treg 是面向 Agent 工具的 OpenRouter——统一发现、定价、凭证和调用，但不替你做隐式供应商路由。

它将可调用工具整理为 catalog endpoint，并把团队自有 API、CLI、SKILL.md / bundle 与 MCP 接入放到同一套入口中。README 的研究时快照为 2,896 个 endpoints、60 个 providers；数量会变化，不应当作永久承诺。

01MODEL · 三层定位

工具目录 / 凭证代理 / 按次计费

01 / CATALOG

先发现，再调用

搜索 catalog，查看 endpoint 能力与价格，再决定要调用哪个工具。目录把分散的 Agent 工具变成可检索的选择面。

02 / PROXY

凭证由服务端注入

调用方不必持有上游 provider secret；Treg 代理转发请求并在服务端完成凭证注入，减少 secret 进入 Agent 上下文的机会。

03 / PRICING

按次计费，不做免费猜测

README 记录 per-call pricing。没有公开价格的 endpoint 会拒绝调用，而不是悄悄按免费服务提供。

边界提醒：Treg ≠ 自动智能路由

通常由用户或 Agent 选择具体 provider / endpoint；只有明确标注为 capability-routed 的 routed endpoint 才是例外。不要把统一入口误读成“系统会自动替你挑供应商”。

03SHARING · API · CLI · SKILL

把“会用工具”变成团队可复用资产

TEAM API

共享自有 API

团队可以登记自己的工具 endpoint；它与公共 catalog 工具分开管理，成员按组织权限获得调用入口。

CLI + SKILL.MD

共享 CLI 与 skill/bundle

CLI 用于登录、搜索、调用、余额查询和分享；SKILL.md 或 bundle 则把调用说明、参数和工作流交给 Agent 复用。

MCP

MCP 安装路径

README 提供 MCP 安装说明，让兼容 MCP 的客户端把 Treg 工具接入自己的工具面；仍需遵循组织权限与计费边界。

ORGANIZATION

团队组织与成员权限

组织角色负责管理共享工具和 provider secret；每位成员的工具访问可以按权限控制，而不是默认全员可用。

04CREDENTIALS · SECURITY

凭证注入与优先级：谁的 secret 生效？

调用 Agent 不直接持有上游凭证；代理在服务端注入可用 secret。README 给出的优先级可理解为以下顺序：

优先级凭证来源含义
1团队登记的 tool credential该团队工具自身配置的凭证优先
2团队保存的 provider secret组织级 provider 凭证作为下一层
3Treg 自有 relay key前两者不可用时使用 Treg relay key（若该 endpoint 支持）
安全边界

代理降低了把 secret 交给调用 Agent 的需要，但不等于自动授予权限。仍应最小化组织成员访问范围，并在 provider、endpoint 和余额层面做审计。

06FIT · DECISION

适合什么，不适合什么？

适合不适合 / 需谨慎
✓ 需要为 Agent 统一发现和调用多家工具 provider✗ 期待系统默默替你做最佳供应商路由
✓ 想把凭证留在服务端，并用一次 token 接入工具✗ 没有可核对公开价格却要求强行调用
✓ 团队需要共享 API、CLI、SKILL.md、MCP 与成员权限✗ 需要把所有 secret 直接暴露给客户端 Agent
✓ 接受按次计费，并愿意监控余额与 HTTP 402✗ 只接受单一 provider、完全离线且不愿维护代理层
