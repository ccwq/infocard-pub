01
PROBLEM · 痛点

旅行规划三座大山：攻略散、路线乱、分享难

攻略散

景点、餐厅、酒店散在备忘录、收藏夹、地图里，排路线时要在地图上一个个对。

路线乱

好不容易排好路线，同行人看不懂；改日期全部重来；机酒和行程对不上。

JourniOne 解法

告诉 AI 想去哪、喜欢什么、跟谁一起去 → AI 排好每天路线 → 生成一本 Travel Journal（图文旅手账）→ 分享链接，同行人直接看每天怎么玩，不需要任何账号。

同行人打开链接就能看每天怎么玩，不需要注册账号、下载 App 或安装任何东西。

Step 1：场景感知

  • 判断：个人为自己规划 / 旅行顾问为客户创作
  • 判断：灵感探索 / 目的地已明确 / 已有路书
  • 无明确偏好时用自然对话确认，不走问卷式盘问
  • 已有路书/照片/行程直接承接，不重走从零规划

Step 2：兴趣发现

  • 围绕目的地范围与偏好做轻量联网搜索
  • 先发现、后核实：比较少量候选 → 核验主办方/餐厅官网
  • 每次只问一个偏好（最多三问），已有答案不重问
  • 选好体验就直接开始排每天，不额外增加前置流程

Step 3：排每天

  • 骨架阶段：片区、天数分配、核心体验可行性
  • 具体路线阶段：首批建议时间 → 核验开放日/内容/交通/餐厅
  • 全程具体时间表必须在生成前给用户看过
  • 主题行程要平衡体验类型，不让每天排满同一种活动

Step 4：确认 + 服务

  • 先展示全程骨架和首批具体时间线
  • 全程确认后提供入口：生成 Journal / 先看机酒 / 继续调整
  • 机酒只在用户选择时查询，不主动追问
  • 日期未知时用 Day 1/Day N，保留具体周末/场次待定

HOTELS · 酒店搜索

TourMind 聚合 100+ 渠道：Ctrip / 飞猪 / 美团 / Agoda / Booking.com / …

维度详情
聚合渠道数100+（含 Ctrip/飞猪/美团/同程/去哪儿/Agoda/Expedia/Booking.com）
技术接口tourmind-booking Skill（v1.0.6 对接契约，官方已至 v1.0.7）
无 Token 查询通过宿主 HTTPS 使用 https://api.tourmind.com/skill/toc/* 公开通道，无需登录/注册
推荐展示策略首次只展示排名第一首选（含房型/价格口径/取消政策/距离/2-3条可验证理由）；其余 4 家缓存，按需返回
价格含房型、含餐情况、税费、取消政策、库存状态，不只比挂牌价
推荐逻辑按路线/偏好/预算匹配；说明为什么适合、总体费用、预订前要核对什么
预订触发用户明确选择后才跳转渠道；创建/付款/取消必须单独确认，不阻塞 Journal 生成
坐标问题GCJ-02 坐标在交给 WGS-84 地图前须转换；不确定时标记待核实，不猜测
首次推荐只展示一家

TourMind 保留完整候选池，但首次只向用户展示排名第一的首选，不同时铺开另外四家。追问「还有别的选择吗」时才按缓存返回——避免信息过载。

05
FLIGHTS · 航班搜索

Kiwi.com MCP 免登录搜索：内部比 3 个方案，只展示 1 个主选

搜索机制

  • 接口：https://mcp.kiwi.com 免登录 search-flight
  • 日期格式：dd/mm/yyyy
  • 不索取、传递或共享任何用户或开发者凭证
  • 内部比较不超过 3 个真正影响选择的方案
  • 只向用户展示 1 个主选（含航司/起降机场/当地时间/经停/总时长/行李/总价/bookingUrl）

展示逻辑

  • 出发地缺失时只追问出发城市/机场，不凭 IP/时区/语言猜测
  • 舱等/直飞/航司要求按用户表达传参，未表达不擅自添加
  • 默认按 quality 搜索
  • 往返机场不同时分别保留
  • 价格失效条件：行程结构变更后重新搜索，旧报价标记失效
⚠ 航班不主动询问

只在用户路线就绪后选择「先补机酒」、Journal 交付后接受补全邀请，或另外明确要求时，才进入航班流程。生成 Travel Journal 时不得为航班追问出发地/日期/人数。

THEME · 主题平衡

主题行程的体验平衡：不把爵士旅行排成每天都是现场

⚠ 主题不是数量配额

主题是叙事线索，不是把每天排满同一类活动。规划主题行程时，保留真正的主题锚点，再加入与它共享气质、感官、文化语境但类型不同的体验。

✓ 正确做法

  • 爵士旅行：Day 1 听现场 + Day 2 唱片店 + Day 3 街区散步 + Day 4 博物馆（文化背景）+ Day 5 咖啡馆
  • 咖啡旅行：咖啡巡礼 + 独立书店 + 公园 + 特色餐厅 + 休息日
  • 亲子旅行：高刺激活动日后优先切换为全家共享或松弛体验

✗ 错误做法

  • 爵士旅行：5 天每天晚上都听现场演出
  • 咖啡旅行：每天连喝 5 家咖啡
  • 亲子旅行：连续 5 天全是儿童项目
  • 向用户解释时不得使用「一天一个重点」「每天最多一个」等配额措辞
城市内主题路线

Citywalk、建筑巡礼、咖啡巡礼、书店巡礼、博物馆路线等城市内主题路线，有目的地、天数和主题即可规划并确认——不需要出发地、出发机场、往返日期、同行人数或房间数。

EXAMPLES · 实际示例

5 个真实对话示例：从「还没决定去哪」到「生成 Travel Journal」

场景示例 prompt
还没决定去哪「想请两天假出去走走，喜欢海边小城和好吃的，不想一直赶路。先给我两三个不同方向。」
围绕兴趣规划「东京四天，想听爵士，也喜欢书店、咖啡和散步。不要每天排同一种活动，先看看每天怎么玩。」
为家人安排「和父母去京都三天，走路别太多，下午安排休息。先给我每天的主线，酒店之后再看。」
承接已有资料「按这份行程做一份给客户看的旅行日志。已经订好的酒店和演出都保留，没写时间的地方先给建议，不要当成已确认预约。」
只补充服务「路线保留，先帮我按每天的动线找住处，给我最合适的一家和理由；先不要预订。」

PRIVACY · 隐私与分享

分享链接无需登录 / 登录后自动保存个人副本 / 生成前排除敏感内容

场景行为
未登录打开分享链接显示公开 Preview，可浏览 Journal + Map，不提供编辑权限
登录后打开分享链接自动创建或复用个人日志，仅账号本人可编辑
退出登录回到公开 Preview；重新打开原链接仍能找到自己的副本
私人媒体（回忆/照片）生成前确认当前 JourniOne 部署的可见性；按「获得链接者可能访问」处理
敏感内容生成前让用户排除：证件号、精确住址、健康信息、未获许可的私密照片
人脸处理默认排除原图；只有 Agent 具备图像编辑能力时才生成脱敏副本并让用户确认
⚠ 私人回忆与照片

没有明确的私密或权限标识时，按「获得链接者可能访问」处理。生成前必须让用户确认排除敏感内容，不得把未获许可的私密照片写入路书。
