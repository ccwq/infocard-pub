01 / 推文逐条核查

推文声称核查结果
"Docker 发布 Sandbox Kit 规范 v3"属实docker/sandbox-kit-spec（Apache-2.0，2026-09-16 建仓），仓库自述逐字："Docker Sandbox Kit Specification v3 — the kit descriptor grammar, the OCI artifact, the build frontend, and the conformance suites"。规范文档 53.7KB、12 节、33 处 RFC 2119 MUST
"联合 Linux Foundation/CNCF 推为中立开放标准"方向属实，注意时态官宣原话是"bringing the spec to CNCF, under their neutral governance"（带入 CNCF 治理），CNCF CTO Chris Aniszczyk 公开背书；但这是 Docker 主导捐赠的开始阶段，与当年 OCI 正式成立尚有流程距离
"网络规则、凭据、卷、工具、指令打包成普通 OCI 镜像"属实实测规范仓库 15 个 capability 类型页：network-policy(@1+@2)、credential、volume、port、privileged、resources、usb-device、lifecycle、agent-context、agent-sessions、agent-skills、kit-registry、long-running、sbx；声明放在 manifest annotation vnd.docker.sandbox.kit.descriptor，无自定义 mediaType，普通 docker buildx build/docker pull/扫描/签名工具全兼容
"可版本化、可审查、可复现、可跨运行时移植"属实且是点题规范作者 Christian Dupuis 的总结句："Dockerfiles made software reproducible. Kits make authority reproducible." 两套 conformance 套件分别判定"这是否合法 Kit"与"runtime 是否按规范行为"，runtime 以适配器可执行文件受测（"可以是 shell 脚本"）

推文没讲的背景：Kits 不是新概念——v1/v2 早已是 Docker Sandboxes 的打包格式；v3 的变化恰恰是"产物变了"：从自有格式变成普通 OCI 镜像。发布场合是 WeAreDevelopers 大会主题演讲，同日还发布了 Docker Cloud Sandboxes（同一套 Kit 跑在弹性云容量上）。合作方名单：AWS、Box、Datadog、Dynatrace、JFrog、NanoClaw、OpenClaw、Palo Alto Networks、Snyk。

02 / 关键设计一：Kit 不授权，只"请求"

这是整份规范最容易被误读的地方。官方示例 gh Kit（GitHub CLI mixin）的声明：

# com.docker.sandbox/network-policy@2（节选）
runtime:
  allow:
    - github.com
    - hosts: [api.github.com]
      methods: [GET, HEAD, POST, PATCH, PUT, DELETE]
  deny:
    - hosts: [api.github.com]
      methods: [DELETE]
      paths: [/repos/**]
# com.docker.sandbox/credential@1（节选）
service: github
proxyManaged: true
inject: - {domain: api.github.com, header: Authorization, format: "Bearer %s"}

规范作者的原话解读："把这份声明读成一张许可申请。这个 Kit 申请访问 GitHub 且仅 GitHub；API 大部分方法可用但 /repos/** 的 DELETE 被拒——deny 优先。能开 PR 的 token 删不了仓库。"两个关键词：asks（Kit 给自己授不了权，每条都是请求，宿主决定）与 conforming（实现规范行为的 runtime 会拦截清单外主机）。没有 conforming runtime，annotation 是惰性的——那只是一个带注释的镜像，没有任何强制力。

credential 的工程细节：默认 proxyManaged——沙箱内部只有一个 sentinel 占位符，真实 token 由 runtime 在代理层注入到指定域名的请求头。Agent 进程从头到尾摸不到真凭据，泄露面从"整个文件系统"缩到"单域 HTTP 出口"。

03 / 关键设计二：组合是函数，不是命令序列

两种 Kit：workload（提供根文件系统，一次组合恰好一个）与 mixin（覆盖层，零或多个——一个带网络规则的 CLI、一个凭据绑定、一段 agent 上下文）。组合规则是硬性的：

规则行为
依赖解析按 provides/requires 声明的依赖图排序，不是你敲参数的顺序；同一集合永远组成同一镜像
严格解析每个 requires 必须由集合内部满足，缺一个就整体失败，不会悄悄去拉东西补洞
同名冲突两个 Kit provide 同名能力 → 报错而非静默遮蔽（官方点名经典错误：Claude workload 配 Claude mixin）
声明合并网络规则取并集、hook 按依赖序执行、指引文档合一、许可证并集；不兼容请求是错误，不是抛硬币
kind: set描述符可以打包引用其他 Kit；发布时在构建期跑同一套一致性检查——不合法的集合在你自己的构建就失败，不是在别人的启动时

04 / 关键设计三：diff 就是审查，还有不靠人的第二道门

因为声明在镜像里，pin 住 digest 就同时 pin 住了内容与权限请求。Claude Code Kit 升级时多要一个域名、第二个凭据——那不是"软件更新"，是权限变更，在 PR 里以新增行的形式出现，人可以拒绝。但规范没把宝押在"有人读 diff"上，它定义了第二道不依赖人的门：

  1. 每个 descriptor 归约为一个规范化授权集合（宿主必须授予的全部内容）。
  2. runtime 记录当前版本的这个集合，与下一版本对比。
  3. 集合内的版本变更静默应用；任何扩权暂停并询问。
  4. 删 deny 规则也算扩权：若新版 gh Kit 掉了 DELETE /repos/** 的拒绝项，runtime 扣住升级。
"这正是声明必须住在 artifact 里而不是旁边的理由。" —— SPEC 作者 Christian Dupuis

05 / 怎么上手：官方示例实测清单

规范仓库 examples/ 目录实测 28 个 Kit：claude、codex、gemini、cursor、devin、opencode 六大 agent 及各自 mixin/ACP-set，加上 gh、wordpress、hello、shell、team 等。三条命令起步：

# sbx 是沙箱 CLI
brew install docker/tap/sbx

# 从仓库 checkout 跑第一个 Kit（hello workload + gh mixin）
cd examples && sbx run ./hello --kit ./gh

# 编辑 descriptor 后只有该 Kit 重建；发布走普通 buildx
docker buildx build --push .

claude.yaml 值得当模板抄：args 版本号默认 2.1.282 且正则校验、provides: ["claude@${{ kit.args.version }}"]、network-policy 精确到六七个域名（api.anthropic.com:443 等）、credential 同时声明 apiKey 与 oauth（由宿主凭据状态决定模式，v3 默认反转为 required，除非显式 opt-out）。

两个冷静剂：① 目前只有 Docker Sandboxes 自己是 conforming runtime——生态承诺还处在"第一个实现"阶段，官方自己承认"它不应是唯一一个"；② Docker 捐 OCI 的历史剧本很动人，但"带到 CNCF"与"CNCF 正式接管"之间隔着 TOC 投票与孵化流程，把今天当成"已成中立标准"为时过早。

06 / 判断

这是 Agent 基础设施里少见的"先想清楚授权语义再写 YAML"的规范：请求/执行分离（Kit asks, runtime enforces）、组合作为纯函数、授权 diff 化与二阶自动门禁，三层设计直接命中"Agent 权限散落在 shell history 和某人的记忆里"这个真实痛点。把能力清单装进普通 OCI 镜像借力现有供应链（扫描/签名/注册表零改造），是教科书级的生态打法——官方那句"MCP 给了 Agent 与工具对话的标准方式，Kits 给了生态发布整套安排的标准方式"定位准确。

观察点：非 Docker runtime 何时通过 conformance 套件（Kubernetes 侧若有 runtime 接入才是标准成真的信号）、CNCF 治理流程走到哪一步、以及 15 个 capability 类型里 agent-sessions/agent-skills 这类尚新的类型会不会被社区挑战。给做 Agent 平台的团队：现在读 SPEC-v3 与两个官方博客，把现有 agent 的权限整理成 descriptor 草稿，成本一周以内；等生态投票后再迁移，代价会大得多。
