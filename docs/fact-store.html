HERMES · MEMORY PROVIDER

fact_store
Holographic 外挂记忆实战手册

把零散事实变成可检索、可推理、可纠错、可反馈的本地知识层：SQLite + FTS5 + trust score + 实体关联检索。它不是聊天摘要，而是可长期使用的结构化事实仓库。

定位：本地优先 / 无外部依赖
核心：9 个 actions + fact_feedback
能力：检索 / 关联 / 推理 / 冲突检测
配置：plugins.hermes-memory-store

它是什么、不是什麼

是什么 Hermes 的 Holographic memory provider，底层是 SQLite + FTS5，支持 trust score、实体解析与 HRR 结构化检索。

不是 会话摘要工具、聊天记录仓库、无限自动记忆，也不是把所有原文塞进去的日志桶。

适合存

  • 用户长期偏好、项目约定、工具参数、环境事实。
  • 已经确认且会反复引用的稳定结论。
  • 需要跨会话复用的事实、规则、工作流、实体关系。

不适合存

  • 一次性聊天、临时任务、原始长日志。
  • 未确认的猜测、模糊线索、会过期的短期上下文。
  • 本该放在 built-in memory 或 session_search 的短期内容。

接入 Hermes 的方式

  • 在 config.yaml 中设置 memory.provider: holographic。
  • 插件配置写在 plugins.hermes-memory-store 下。
  • 默认数据库：$HERMES_HOME/memory_store.db。
  • 确认状态：hermes memory status。
  • built-in memory 继续生效，fact_store 是增量能力，不替代短记忆。
验证口诀： 配置写入 → memory status 显示 active → 新会话可用 fact_store → add/search 成功。

常用工作流

1
先写入，再验证：先 add 存一个事实，再用 search / probe 把它找回来。
2
先 probe，再扩展：围绕一个实体看全貌，再用 related / reason 继续扩展。
3
先 search，再整理：关键词找到旧记录，再决定 update 还是 remove。
4
发现冲突时用 contradict：先查矛盾，再判断是旧事实失效、还是新事实需修正。
5
最后做信任反馈：用 fact_feedback 给 helpful / unhelpful，训练 trust 排序。

9 个 actions 怎么用

动作作用典型用法
add新增事实把用户偏好、工具约定、环境事实写入库中。
search关键词检索按词找“chrome / cdp / trust / deploy process”等主题。
probe实体召回问“关于这个人/项目/工具，我都知道什么”。
related结构关联找与某实体相连的周边事实。
reason多实体组合检索找同时与 A、B、C 相关的交集事实。
contradict冲突检测找互相矛盾、时序冲突、版本冲突的事实。
update修订事实事实内容更正、tags 修订、trust 调整。
remove删除事实清理过时、错误、已失效的记录。
list列出现有事实盘点当前条目、审计、清理前检查。

使用技巧

  • 优先写 实体 + 断言 + 条件/时间，后续 probe / reason 更稳。
  • 高价值事实单独存：偏好、约定、配置、决策，不要和任务噪音混在一起。
  • 低置信信息先保守存储，必要时降低 trust，不要一开始就“盖章真相”。
  • 实体名保持统一写法；别名太多会让检索变得松散。
  • 事实变更优先 update / remove，不要让冲突版本长期共存。
  • 把 fact_store 当“事实数据库”，不是“聊天备忘录”。

什么时候不用 fact_store

适合
  • 长期偏好
  • 项目规则
  • 工具 workaround
  • 已验证事实
  • 会反复引用的知识
不适合
  • 临时聊天
  • 未确认猜测
  • 一次性日志
  • 长原文复制
  • 短期上下文碎片

真实可用的命令示例

add

{"action":"add","content":"用户默认使用 uv 管理 Python 依赖","category":"user_pref","tags":"python,package-manager"}

search / probe

{"action":"search","query":"Chrome CDP","limit":5}

{"action":"probe","entity":"chrome","limit":10}

related / reason / contradict

{"action":"related","entity":"SQLite","limit":10}

{"action":"reason","entities":["Hermes Agent","SQLite","FTS5"],"limit":10}

{"action":"contradict","entity":"chrome","limit":10}

update / remove / list / feedback

{"action":"update","fact_id":123,"trust_delta":0.2}

{"action":"remove","fact_id":123}

{"action":"list","category":"user_pref","limit":20}

{"action":"helpful","fact_id":123}

新用户上手顺序 & 排错顺序

上手顺序

  • 1) hermes memory status 确认 holographic active。
  • 2) 先写 3–5 条最有价值的事实。
  • 3) 立刻用 search / probe 验证能不能查回来。
  • 4) 用 fact_feedback 校正 trust。
  • 5) 有冲突就 contradict / update / remove。

排错顺序

  • 先看配置是否写对。
  • 再看 provider 是否 active。
  • 再看数据库路径是否落在当前 Hermes Home。
  • 再看实体名和 category 是否一致。
  • 最后检查 trust 门槛与检索词是否合理。
一句话理解：fact_store 不是“聊天记录仓库”，而是把 Hermes 的长期事实做成可搜索、可推理、可修正的本地知识层。
项目要点
存储本地 SQLite，默认路径 $HERMES_HOME/memory_store.db
检索FTS5 全文检索 + 实体回忆 + 组合推理
信任机制默认 trust 0.5，可通过 fact_feedback 调整
配置db_path / auto_extract / default_trust / hrr_dim
