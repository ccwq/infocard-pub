⚡ 核心洞察：模型能力提升后，单步生成的边际差距会缩小。真正拉开差距的地方，会转到 runtime engineering，而不是 prompt engineering。
01
分水岭：从对话响应到异步任务托管

Async Agent 和普通 Agent 的分水岭，不在"会不会调用工具"，而在它能不能用异步的方式对话响应、持续任务、保持状态、跑验证、回到 review，再把结果交还给人。

普通 Agent 解决的是一次交互里的智能。Async Agent 解决的是一段执行周期里的状态、验证、权限、回放和交付。

02
四阶段演进路径
  • 早期 Copilot — 同步补全：人写主线，模型补局部。停留在"行级建议"，没有独立的执行上下文。
  • Tool Agent — 单次调用：能查资料、跑命令、调 API，但多数还停留在一个 turn 或一个 session 内。每次交互完成后上下文即释放。
  • Coding Agent — 任务闭环：进入 repo、改文件、跑测试、提 PR。OpenAI Codex 官方描述的云端隔离环境就是这一层的典型形态——有持久执行环境，但仍以单次任务为主。
  • Async Agent — 生命周期托管：处理的是"这个任务在接下来几十分钟、几小时甚至几天里怎么被托管和推进"。它是长任务 Agent 架构的稳定性胜利。
03
完整工作流：Context → Plan → Tool Use → Code → Test → Review
Context → Plan → Tool Use → Code → Test → Review

Task Timeline：Spec → Triage → PR → Review → Merge。Async Agent 面向的是软件生命周期，不是单次代码生成。任务会跨阶段，每个阶段都有不同的上下文、权限和验证门槛。

"同步 Agent 的上下文通常靠当前窗口维持；Async Agent 必须把 context 变成可管理资产。plan 改了，tool state 要同步；代码改了，test 要可复现；review comment 回来后，agent 要知道自己在原任务里的位置。"

Anthropic 在 long-running agents 里讲的 harness，就是为了解决这种跨阶段推进问题。

04
Control Plane：Orchestrator / Scheduler

普通 Agent 可以靠用户一句一句推着走。Async Agent 需要调度层：什么时候启动 worker，什么时候暂停，什么时候重试，什么时候把结果交给人。这里开始出现 control plane 问题。

多 agent 一跑久，坏掉的经常不是 reasoning，而是 registry、stream state、conversation state。真实工程病例可看 OpenAI Codex issue #24475：subagent tasks 触发重连循环和流断开。

Anthropic 把这个问题进一步拆成 brain、hands、session 的分离，适合用来理解 Async Agent 的底层结构。

05
六大工程差异：Async Agent 的工程支柱

这一组是 Async Agent 跟普通 Agent 最大的工程差异：

  • Knowledge：解决进入项目时的局部先验不足。不靠上下文窗口里塞入所有背景，而是通过结构化知识库让 agent 了解项目上下文。
  • Playbooks：把团队反复出现的操作沉淀成执行策略，而不是每次靠模型从头推理怎么做。
  • Checkpoint：让长任务可以恢复，而不是靠模型"记得"之前做了什么。这是 Async 和 sync 的根本区别之一。
  • Scoped Secrets：决定 agent 能碰什么资源。不是"有权限就能用"，而是按任务粒度的最小权限原则。
  • VM Sandbox：给它一个可隔离、可销毁、可复现的手。执行环境是 disposable 的，而非长连会话。

* Devin docs 里的 Knowledge / Playbooks / Review 设计，虽带产品语境，但机制上很值得拆开看。

06
可观测性：让"做过什么"变成可回放证据

Async Agent 越长，越需要把"它做过什么"变成可回放证据。很多失败不是最后一步错了，而是中间某个状态写歪了，后面所有步骤都在错误轨道上继续推进。

方向：event-sourced agent runtime

  • 如果 log 只是事后审计，debug 仍然很难
  • 如果 log 成为 runtime 的状态来源，replay、fork、diff、lineage 才有机会变成原生能力

对应论文：The Log is the Agent (arxiv:2605.21997)

07
为什么 Async Agent 会成为趋势

模型能力提升以后，单步生成的边际差距会缩小。真正拉开差距的地方，会转到这些更工程化的面：

  • 长任务保持 session continuity — 对话窗口之外，状态不能丢
  • memory 写入、修订、遗忘 — 不是无限堆积，而是可管理的知识生命周期
    → Is Agent Memory a Database? (arxiv:2605.26252)
  • harness 拆解为可验证 trajectory — 把目标分解，每步可验证可追溯
    → Harnesses for Inference-Time Alignment (arxiv:2605.21516)
  • trace 服务训练、回放和质量控制 — 不只是监控，而是训练数据的来源
  • review 从人工兜底变 workflow 一环 — 不是人在循环外审核，而是 agent workflow 的集成阶段
  • permission boundary 防越权 — 防止 agent 把"能做"误解成"该做"
"所以我现在看 Async Agent，不会把它理解成'后台跑的 Agent'。更准确的说法是：Async Agent 是 Agent 从 chat interface 进入 software production runtime 的过渡形态。"
"普通 Agent 解决的是一次交互里的智能。Async Agent 解决的是一段执行周期里的状态、验证、权限、回放和交付。"
"AI Coding 真正进入工程现场以后，竞争会越来越像 runtime engineering，而不是 prompt engineering。"
