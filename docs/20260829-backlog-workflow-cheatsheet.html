Backlog.md 人员化项目管理 Cheatsheet

一句话结论：先冻结需求与责任，再放行单任务执行；所有计划、沟通、变更与验收都写回 Backlog 和 Git，用三次人工审批切断 Agent 失控。

核心要点

  • 需求先行：brief不是PRD，PRD批准后才拆功能。
  • 单一责任：一个任务只有一个主要执行人。
  • 计划审批：Ready不等于允许编码，Plan批准后才开始。
  • 独立Review：执行人不能审查并关闭自己的任务。
  • 变更隔离：新发现进入Draft，不污染进行中任务。
  • 证据闭环：Done必须具备AC、测试和Final Summary。

今天就能执行的5步

  1. 初始化Backlog与Agent指令。
  2. 写一页brief并定义人员实体。
  3. 让PM Agent生成PRD和FEAT草稿。
  4. 审查后创建第一批Draft任务。
  5. 选一张任务跑通Plan→Review→Done。

三次人工检查点#

  1. 审需求：做的东西是不是对的？
  2. 审计划：准备怎么做？影响哪些文件？怎么验证？
  3. 审结果：验收标准、测试证据、代码差异是否一致？

    wip_limit: 3
    status: active

  - id: PER-002
    handle: "@codex-pm"
    kind: agent
    roles: [project-manager]
    wip_limit: 2
    status: active

  - id: PER-003
    handle: "@codex-dev"
    kind: agent
    roles: [developer]
    skills: [python, api, testing]
    wip_limit: 1
    status: active

  - id: PER-004
    handle: "@reviewer"
    kind: agent
    roles: [reviewer, qa]
    wip_limit: 2
    status: active

任务责任约定#

字段 表示什么 推荐写法
assignee 唯一执行人 -a @codex-dev
reviewer 独立审查人 标签reviewer-PER-004
approver 最终批准人 标签approver-PER-001
role 所需岗位 标签role-backend
person 人员实体映射 标签person-PER-003

即使Backlog支持多人负责人，也建议每个任务只设一个主要assignee。Reviewer和Approver不要混入负责人列表。

4. 状态机与进入条件#

状态 进入条件 允许操作的人 离开条件
Draft 尚未批准 @codex-pm 范围、AC、依赖、责任人已确认
Ready 已批准且无未完成依赖 @owner设定 执行人提交计划
In Progress 计划已批准 唯一assignee 实现、测试、证据完成
Blocked 存在明确阻塞 assignee 阻塞原因消失并有记录
Review 执行人已完成 @reviewer Review通过或退回修改
Done Review通过 仅@owner 已关闭，不继续塞新范围

强制规则#

  • Draft不能编码。
  • Ready必须有唯一执行人、Reviewer、验收标准和显式依赖。
  • 依赖未完成不能进入In Progress。
  • 实施计划未批准不能改代码。
  • 执行人只能把任务移到Review，不能自行Done。
  • Reviewer不能审查自己实现的任务。
  • Done任务出现新需求时，创建新任务，不重新打开并偷偷扩张。

6. 合格任务卡模板#

# TASK-xxx：动词＋可交付结果

## 目标
一句话说明完成后新增什么可观察能力。

## 来源
- PRD：PRD-001
- 功能：FEAT-003
- 决策：DEC-002

## 范围
- 本任务包含什么

## 非范围
- 明确不做什么

## 责任
- Responsible：PER-003 / @codex-dev
- Reviewer：PER-004 / @reviewer
- Approver：PER-001 / @owner

## 输入与输出
- 输入：统一文档节点
- 输出：Markdown字符串和警告列表

## 验收标准
- [ ] 输入标题节点时输出对应Markdown标题
- [ ] 嵌套列表层级保持正确
- [ ] 不支持的节点产生警告而不是静默丢失

## 依赖
- TASK-008：统一文档模型

## 预计修改文件
- 待执行人调查后写入

## 实施计划
- 待执行人调查后写入并等待批准

## 测试证据
- 待完成后填写

## Final Summary
- 待完成后填写

任务是否拆得足够小#

满足以下条件才算合格：

  • 一个Agent会话可以完成。
  • 一个PR可以审完。
  • 只有一个主要交付结果。
  • 修改文件边界相对集中。
  • AC可以通过测试、命令或样例验证。
  • 不依赖未写明的隐藏前置条件。
  • 失败时可以单独回退。

出现以下词语通常说明任务过大：

  • “完成整个系统”
  • “实现所有解析能力”
  • “前后端全部开发”
  • “优化性能和安全”
  • “处理各种异常”

7. Agent提示词速查#

A. 整理PRD，不创建任务#

本轮只整理需求，不写代码，不创建Backlog任务。

读取project/brief.md和samples目录。
区分：已明确需求、合理推断、未决问题。
检查目标用户、范围、非范围、输入输出、异常场景和验收标准。
最多向我提出两轮关键问题。
生成project/PRD.md草稿后等待批准。
不得自行补充未确认的产品需求。

B. 拆分功能，不写技术任务#

读取已批准的project/PRD.md。

拆成可独立验收的FEAT文件，每个功能必须包含：
来源需求、用户或系统行为、输入输出、范围、非范围、验收标准、depends_on。

输出REQ→FEAT覆盖矩阵、依赖边、并行组和遗漏风险。
不要写代码，不要创建Backlog任务，等待我批准。

C. 生成Backlog Draft#

先运行backlog instructions overview和backlog instructions task-creation。

读取所有已批准的PRD和FEAT。
通过Backlog CLI创建Draft任务，不直接编辑Backlog Markdown。
每个任务必须有唯一执行人、Reviewer、Approver、验收标准、依赖和文档引用。
设计、实现、测试、文档任务分开。
完成后输出TASK映射、依赖边、并行批次和过大任务。
不得开始实现。

D. 只写实施计划#

只处理TASK-012。

先运行backlog instructions task-execution。
读取关联PRD、FEAT、依赖和人员权限，调查代码库。
把实施步骤、预计修改文件、验证命令、风险和假设写入任务Plan。
不要修改代码，完成后等待我批准。

E. 实现已批准任务#

TASK-012计划已批准。

严格按批准范围实现并验证。
完成后写入实际修改文件、测试命令、测试结果、AC逐项结果、已知限制和Final Summary。
将任务移动到Review，不得设置为Done。
发现新需求时只记录并提出新任务，不扩大当前任务。

F. 独立审查#

只审查TASK-012，不实现新功能。

对照PRD、FEAT、任务AC、代码差异和测试证据检查：
功能正确性、错误处理、回归风险、范围扩张、测试充分性。

通过时给出“建议Done”；不通过时给出逐项修改请求。
你不能直接关闭任务。

8. 沟通SOP与模板#

8.1 需求不清楚#

不要猜测。使用“问题＋影响＋选项＋建议”。

问题：扫描型PDF是否属于MVP？
影响：如果支持，需要OCR、语言模型选择和独立质量指标，会增加功能域和测试样例。
选项：A. MVP不支持；B. 仅支持中英文OCR；C. 所有扫描件作为后续里程碑。
建议：选择A，MVP只支持文本型PDF。

8.2 执行中发现范围外工作#

backlog task edit TASK-12 \
  --comment "发现合并单元格需要新的中间模型结构，超出当前AC。建议创建独立Draft，不在本任务实现。" \
  --comment-author @codex-dev

8.3 遇到阻塞#

backlog task edit TASK-12 -s "Blocked"
backlog task edit TASK-12 \
  --comment "阻塞：TASK-8的统一节点接口尚未确定。需要：字段定义和示例。解除条件：TASK-8进入Done。" \
  --comment-author @codex-dev

阻塞说明必须包含：

  • 阻塞事实；
  • 受影响任务；
  • 需要谁做什么；
  • 解除条件；
  • 是否有可继续的非阻塞部分。

8.4 Review不通过#

结论：暂不建议Done。

阻断问题：
1. AC-2要求嵌套列表保持层级，当前三级列表被压平。
2. 缺少空文档和非法节点测试。

建议修改：
- 修复嵌套列表缩进；
- 补充两个回归样例；
- 更新测试结果和Final Summary。

不要求：
- 本轮不处理表格合并单元格。

8.5 完成说明#

完成内容：标题、段落、粗体和列表转换。
修改文件：src/renderer.py、tests/test_renderer.py。
验证命令：pytest tests/test_renderer.py -q。
验证结果：18 passed。
AC：3/3满足。
已知限制：不支持合并单元格；对应新Draft为TASK-19。
建议状态：Review。

backlog task edit TASK-12 \

9. 变更SOP#

9.1 小修正：不改变范围#

例如修正错字、补充一个原本已经隐含的验收例子。

backlog task edit TASK-12 --ac "空文档返回空Markdown和明确警告"
backlog task edit TASK-12 \
  --comment "补充边界验收样例，不改变功能范围。" \
  --comment-author @owner

9.2 范围改变：退回Draft重新审批#

例如原本只支持文本PDF，现在要求扫描PDF＋OCR。

backlog task demote TASK-12
backlog task edit TASK-12 \
  --comment "范围变化：新增OCR。需要重新评估PRD、依赖、工期和验收标准。" \
  --comment-author @owner

然后依次更新：

PRD → FEAT → TASK → 依赖 → 人员 → 里程碑 → 重新批准

9.3 任务过大：拆成子任务#

原任务：“完成DOCX解析器”。拆为：

backlog task create -p TASK-10 "解析标题和段落"
backlog task create -p TASK-10 "解析有序和无序列表"
backlog task create -p TASK-10 "提取图片并生成资源引用"
backlog task create -p TASK-10 "解析表格"
backlog task create -p TASK-10 "建立DOCX回归样例集"

父任务作为交付能力汇总；子任务各自拥有执行人、AC、Reviewer和依赖。

9.4 新发现：创建新Draft#

backlog task create "支持DOCX合并单元格" \
  --draft \
  -l discovered-during-TASK-12,feat-FEAT-003 \
  --dep TASK-12 \
  --ac "合并单元格具有确定的Markdown降级规则"

不要把新发现直接塞进进行中的TASK-12。

9.5 更换执行人#

backlog task edit TASK-12 -a @claude-pdf

更换前检查：

  • 新执行人存在于people.yml；
  • 技能匹配；
  • 未超过WIP限制；
  • 原执行人已留下完整Notes；
  • Reviewer没有与新执行人重合。

10. 完整SOP演示：DOCX转Markdown Mini#

10.1 项目范围#

开发一个最小Web服务：用户上传单个DOCX，系统返回Markdown文件。

MVP包含：

  • 标题、段落、粗体、列表；
  • 单文件上传；
  • 文件格式和大小校验；
  • 转换结果下载；
  • 明确错误提示。

MVP不包含：

  • PDF；
  • OCR；
  • 表格；
  • 图片；
  • 用户账号；
  • 批量转换。

10.2 从项目想法拆成需求#

PRD-001 上传DOCX
PRD-002 解析文档结构
PRD-003 生成Markdown
PRD-004 下载结果
PRD-005 错误和警告

每项需求都要能回答：

  • 谁触发？
  • 输入是什么？
  • 系统行为是什么？
  • 输出是什么？
  • 失败时发生什么？
  • 怎样算通过？

10.3 从需求拆成功能#

FEAT 功能 依赖 验收核心
FEAT-001 文件上传与校验 无 非DOCX拒绝；超限拒绝
FEAT-002 DOCX结构提取 FEAT-001 输出统一节点序列
FEAT-003 Markdown渲染 FEAT-002 标题、段落、粗体、列表正确
FEAT-004 转换接口与下载 FEAT-001、003 上传后获得可下载结果
FEAT-005 错误与质量报告 FEAT-002、003 不支持内容产生警告

拆解检查：

  • 功能描述的是可观察能力，不是某个类或某个文件；
  • 每个功能可以单独验收；
  • 依赖方向清晰；
  • 非范围没有被偷偷加入。

10.4 从功能拆成任务#

Task 类型 执行人 依赖 批次
TASK-1 定义MVP样例与期望输出 测试设计 @reviewer 无 1

10.5 创建任务示例#

# 第一批：先定义可验证样例
backlog task create "定义DOCX MVP样例与期望输出" \
  --draft \
  -a @reviewer \
  -l feat-FEAT-001,type-test,reviewer-PER-001,approver-PER-001 \
  --ac "至少包含标题、段落、粗体和两级列表样例" \
  --ac "每个输入文件都有对应期望Markdown"

# 记录上一条命令返回的真实ID，再建立下游依赖
backlog task create "定义统一文档节点模型" \
  --draft \
  -a @codex-dev \
  --dep TASK-1 \
  -l feat-FEAT-002,type-design,reviewer-PER-004,approver-PER-001 \
  --ac "模型能够表达标题、段落、粗体和列表" \
  --ac "节点顺序保持稳定"

示例中的TASK编号仅用于演示。实际操作必须使用Backlog命令返回的真实ID。

10.6 审批和执行一张任务#

项目负责人先回复：

批准TASK-4的范围、验收标准、依赖和责任分配。
允许进入Ready；暂不允许修改代码，先提交实施计划。

执行Agent：

backlog task edit TASK-4 -s "Ready"
backlog task edit TASK-4 --plan "读取统一节点模型；定位DOCX解析入口；实现标题和段落映射；补充样例测试；运行目标测试和全量测试"

负责人批准计划：

TASK-4实施计划批准。只允许修改计划列出的文件和测试；发现表格、图片或PDF需求时创建新Draft。

Agent开始执行：

backlog task edit TASK-4 -s "In Progress"

完成后：

backlog task edit TASK-4 --notes "已完成标题和段落提取；新增6个样例测试"
backlog task edit TASK-4 --check-ac 1 --check-ac 2
backlog task edit TASK-4 --final-summary "完成标题和段落到统一节点的映射；目标测试6/6通过；未处理列表、表格和图片"
backlog task edit TASK-4 -s "Review"

Reviewer审查后留言：

backlog task edit TASK-4 \
  --comment "Review通过：AC全部满足，测试证据充分，未发现范围扩张。建议Done。" \
  --comment-author @reviewer

最后由负责人关闭：

backlog task edit TASK-4 -s "Done"

11. SOP演示：需求变更#

场景#

MVP开发到一半，提出“还要支持PDF”。

错误处理#

直接修改正在进行的DOCX任务，把PDF也塞进去。

正确处理#

  1. 记录变更，不立即实现。
  2. 判断是否改变产品范围。
  3. 更新PRD并重新审批。
  4. 新建PDF功能和Draft任务。
  5. 重新计算依赖、人员和里程碑。

沟通模板：

变更请求：MVP新增文本型PDF。

影响分析：
- 新增PDF结构提取功能域；
- 需要独立样例和质量标准；
- 统一文档模型可能需要位置信息；
- 当前DOCX任务可以继续，不应混入PDF实现；
- MVP里程碑需要重新评估。

建议：保留DOCX MVP，PDF进入MVP-2；若坚持并入当前MVP，先暂停FEAT-004之后的下游任务。

创建变更Draft：

backlog task create "评估文本型PDF支持范围" \
  --draft \
  -a @codex-pm \
  -l type-change-request,scope-pdf,approver-PER-001 \
  --ac "明确PDF支持与非支持内容" \
  --ac "给出对现有模型、任务依赖和里程碑的影响"

12. SOP演示：缺陷修复#

场景#

用户上传包含三级列表的DOCX，输出Markdown被压平成一级列表。

缺陷拆解#

观察结果：三级列表层级丢失
期望结果：输出保持三级嵌套
最小复现：samples/bugs/nested-list-3-level.docx
影响范围：DOCX列表提取或Markdown渲染
回归风险：一级、二级列表；有序/无序列表切换

创建缺陷任务：

backlog task create "修复三级DOCX列表被压平" \
  --draft \
  -a @codex-dev \
  -l type-bug,feat-FEAT-003,reviewer-PER-004,approver-PER-001 \
  --ref samples/bugs/nested-list-3-level.docx \
  --ac "三级列表输出保持三级缩进" \
  --ac "一级和二级列表现有测试继续通过" \
  --ac "新增最小回归测试"

缺陷修复SOP：

复现 → 定位责任层 → 写失败测试 → 最小修复 → 回归测试 → Review → Done

不要在缺陷任务里顺便重构整个解析器。需要重构时，单独创建设计或技术债Draft。

13. 每日、每周和里程碑节奏#

每日开始#

backlog overview
backlog task list --status "Ready" --plain
backlog task list --status "Blocked" --plain

检查：

  • 哪些任务解除阻塞？
  • 每个人是否超过WIP限制？
  • 是否有Ready任务没有责任人？
  • 是否有Review任务长时间无人处理？

每个任务开始#

读PRD/FEAT/TASK → 检查依赖 → 提交Plan → 人工批准 → In Progress

每个任务结束#

写Notes → 跑测试 → 勾AC/DoD → 写Final Summary → Review → 人工Done

每周#

backlog board export reports/weekly-status.md --force
git diff -- project backlog

周检内容：

  • 需求覆盖率；
  • 功能和任务完成率；
  • 阻塞链；
  • 人员负载；
  • 新增范围；
  • Review积压；
  • 已知风险；
  • 下一周Ready批次。

每个里程碑#

  • 所有范围内功能已经验收；
  • 没有未解释的失败测试；
  • 阻塞和延期项有明确处置；
  • 发布说明和已知限制完成；
  • PRD、任务和实际代码保持一致；
  • 生成状态报告和复盘。

14. 十条防失控规则#

  1. 不从一句模糊想法直接开始编码。
  2. 不把PRD、功能和技术任务混写在一层。
  3. 不让多个任务拥有同一个模糊交付结果。
  4. 不让执行人批准自己的任务。
  5. 不让Agent自行删除依赖或扩大范围。
  6. 不把聊天记录当成唯一决策记录。
  7. 不让无测试证据的任务进入Done。
  8. 不在进行中的任务里不断追加新需求。
  9. 不让Excel、Word或看板导出反向成为事实来源。
  10. 不为了自动化而过早引入第二套任务数据库。

15. 一页式操作检查单#

创建前#

  • PRD已经批准
  • FEAT已经批准
  • 任务没有重复
  • 任务粒度适合一个会话/PR
  • 验收标准可验证
  • 依赖明确
  • 唯一执行人已指定
  • Reviewer和Approver已指定

开始前#

  • 依赖已Done
  • 人员状态为active
  • 未超过WIP限制
  • 已调查代码库
  • 实施计划已写入
  • 修改文件和验证命令已列出
  • 计划已批准

Review前#

  • 代码范围与计划一致
  • 自动化测试通过
  • AC逐项说明
  • DoD逐项说明
  • 实际修改文件已记录
  • 已知限制已记录
  • 新发现已创建独立Draft
  • Final Summary完成

Done前#

  • Reviewer与执行人不同
  • Review结论明确
  • 阻断问题全部关闭
  • 负责人完成最终批准
  • 状态和Git实际结果一致
