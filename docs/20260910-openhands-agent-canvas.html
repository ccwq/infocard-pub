01 · Agent Canvas 是什么

Agent Canvas 是 OpenHands 系统里的浏览器控制中心，不是单独的模型，也不是替代所有 coding agent 的新模型。它负责提供一个界面，让你启动对话、查看文件和状态、选择后端，并创建按计划或事件触发的自动化。真正执行代码、调用工具和访问工作区的是 Agent Server 或外部 ACP Agent；工作区或沙箱决定它能触碰哪些文件、进程、凭据和网络。

它的关键变化是把“我打开几个终端盯着不同 Agent”变成“我在一个 Canvas 管理多个后端”。这些后端可以在本机、Docker、虚拟机、公司基础设施、OpenHands Cloud 或 Enterprise 中运行。前端可以在一个界面切换它们，但切换界面不会改变后端的权限边界。

组件负责什么初学者要记住
Agent Canvas浏览器控制中心、对话界面、文件/设置/后端和自动化入口它本身不是执行沙箱
Agent Server运行对话、Agent、工具、工作区操作并发送事件流它所在的机器才是执行边界
Automation Server保存计划、webhook、运行历史并派发任务自动触发不等于自动安全
Workspace/Sandbox限制文件、进程、网络和凭据范围挂载目录决定 Agent 能看什么

02 · 安装前先选执行边界

官方提供 npm、本机直接运行、Docker、VM/自托管和源码等路径。初学者推荐先在本机或 Docker 中做一次无副作用体验。不要把“本地默认运行”理解成“没有权限风险”：无沙箱路径中的 agent-server 直接运行在主机上，Agent 可以访问主机文件系统并执行命令。

方式启动形态文件权限适合
本机无沙箱npm 全局安装后运行 agent-canvas直接拥有安装机器权限个人可信机器、快速试用
Docker 沙箱镜像 + 显式挂载项目目录主要访问挂载的 /projects想先建立清楚的文件边界
VM 后端backend-only 或 full CanvasVM 是真实执行和凭据边界常驻运行、远程访问、更多算力
源码clone、npm install、npm run dev开发机直接运行贡献代码或修改前后端
风险提示：正式公开部署前，至少设置强随机的 LOCAL_BACKEND_API_KEY、限制网络入口、使用 HTTPS 或可信隧道，并把运行 Agent 的机器当作存有生产凭据的主机来保护。

03 · 第一次启动：本机 npm 路径

本机路径适合先理解 Canvas 的界面和后端切换。官方 Quickstart 要求 Node.js 22.12.x 或更高版本和 uv。安装全局包后运行 agent-canvas，默认界面在 localhost:8000。

node --version
npm --version
uv --version

npm install -g @openhands/agent-canvas
agent-canvas
  1. 打开 http://localhost:8000；如果浏览器没有自动打开，手动访问。
  2. 完成首次设置，先选内置 OpenHands agent，避免一开始同时排查多个 ACP provider。
  3. 创建一个不含密钥的示例工作区，先做只读任务或生成一个简单文本文件。
  4. 确认对话事件、文件变更和执行结果都能在 Canvas 中看到。
  5. 再进入 Settings → Agent，评估是否切换到 Claude Code、Codex 或 Gemini CLI。

拆分启动时可以使用：

agent-canvas --frontend-only
agent-canvas --backend-only
agent-canvas --port 8000

frontend-only 只提供界面和 ingress；backend-only 启动 Agent Server、Automation backend 和 ingress。不要把 frontend-only 当成完整可执行环境。

04 · Docker 路径：先把项目目录隔离清楚

Docker 适合希望明确控制 Agent 可见文件的初学者。官方示例将 ~/.openhands 挂载为持久化设置目录，将一个明确的 PROJECTS_PATH 挂载到容器的 /projects。Agent 只能访问你选择挂载的项目范围，但容器网络、镜像版本和环境变量仍需要审查。

export PROJECTS_PATH="$HOME/projects"
mkdir -p "$PROJECTS_PATH" "$HOME/.openhands"

docker run -it --rm \
  -p 8000:8000 \
  -v "$HOME/.openhands:/home/openhands/.openhands" \
  -v "${PROJECTS_PATH}:/projects" \
  ghcr.io/openhands/agent-canvas:1.17.0

第一次运行建议创建单独的演示目录，不要直接挂载整个 HOME。确认 Canvas 能打开、Agent 能读取演示项目、不能读取未挂载目录后，再考虑接入真实仓库。若镜像版本更新，重新核对官方文档中的镜像标签、数据迁移和兼容要求。

05 · 后端模型：为什么同一个 Canvas 能切换多个环境

Agent Canvas 通过 Agent Server API 连接后端。一个 Agent Server 通常对应一台主机和一个端口；Canvas 可以登记多个后端，并在界面中切换。你可以把个人 Agent 放在本机，把需要更强算力或常驻运行的 Agent 放在 VM，再从同一个浏览器界面切换。

部署模式启动使用方式注意
Local all-in-oneagent-canvasCanvas 和 backend 同机适合可信本机，权限直接
Backend-onlyagent-canvas --backend-only --public本地 UI 登记远程 backend远程机器执行，不是浏览器机器执行
Full Canvas VMagent-canvas --publicVM 同时提供 UI 和 backend必须加 API key、网络控制和 TLS
Docker/Kubernetes容器或 Helm 部署由挂载和集群网络定义边界单租户部署不等于多租户隔离

新增后端时，在 Canvas 中打开 Manage Backends → Add Backend，填写名称、Host/Base URL 和 Session API key。使用 SSH tunnel 时可填 localhost:8000；直接远程访问则使用 TLS 反向代理或受控隧道地址。

06 · ACP：把 Claude Code、Codex、Gemini CLI 接到 Canvas

Agent Client Protocol（ACP）是通过 stdio 上的 JSON-RPC 与 coding agent 通信的协议。Agent Server 启动外部 CLI 子进程并转发每一轮消息；外部 Agent 自己管理模型、工具和执行，Canvas 负责展示和发送消息。这样可以在不把所有 provider 逻辑重写进 Canvas 的情况下切换 Agent。

Provider官方默认命令认证提示
Claude Codenpx -y @agentclientprotocol/claude-agent-acp可复用同机订阅登录，也可使用相应密钥
Codexnpx -y @zed-industries/codex-acp本机登录和容器凭据边界不同
Gemini CLInpx -y @google/gemini-cli --acp按 CLI 当前认证方式配置
Custom任何 stdio ACP server 启动命令需手动写模型和环境变量

首次接入通常有四步：Choose agent、Check backend、Set up credentials、Say hello。若 Agent Server 和 provider CLI 在同一台已登录机器上，可能直接复用订阅登录；干净 Docker 或云端环境没有主机登录状态，通常需要把凭据通过设置页的 Secrets 传给子进程。

不要混淆：切换 Settings → Agent 只影响之后新开的对话；已经运行的对话继续使用它启动时的 Agent。

07 · Secrets 与模型配置：凭据跟着 backend 走

Agent Canvas 会把 provider 选择和密钥保存在具体 backend 的设置中。ACP onboarding 的 credential 字段可以为空：同机已有 provider 登录时，CLI 可能自动复用；容器没有登录状态时，则需要提供对应环境变量或文件型凭据。

  • API key、OAuth token 和认证 JSON 只放在受控 Secrets 存储，不放进仓库、Prompt、截图或公开卡片。
  • 保存密钥时，secret 名称必须与 provider CLI 读取的环境变量一致，否则“已保存”不等于子进程真的拿到了凭据。
  • 自定义 ACP server 没有 curated model list，需要自己填写 server 期望的 model ID。
  • 如果使用远程 backend，要确认密钥实际存储和使用在远程机器，不要误以为浏览器本地承担了模型调用。
  • 更换模型、provider 或命令后，新选择只对新会话生效；把旧会话的执行环境单独记录。
Settings → Agent
  Agent: OpenHands / ACP
  Preset: Claude Code / Codex / Gemini CLI / Custom
  Command: provider 的 stdio 启动命令
  Model: provider 接受的模型 ID

Settings → Secrets
  provider 需要的环境变量名 → [REDACTED]

08 · 自动化：从手动对话到按事件排队

Agent Canvas 的自动化服务可以按计划或外部事件触发 Agent。官方预置方向包括 GitHub PR Review Assistant、GitHub Repository Monitor 和 Slack Channel Monitor。它的正确使用顺序不是“接上所有账号让 Agent 自己做”，而是先建立一个无副作用的只读流程，再逐步开放写入。

  1. 先选择一个 backend，确认它的模型、工作区和权限范围。
  2. 在 Customize → MCP Servers 中显式添加 GitHub、Slack、Notion 等服务。
  3. 保存所需 secrets，并验证服务只能访问目标仓库、频道或空间。
  4. 从 Automate 中选择一个预置流程，先把结果写到测试位置。
  5. 用一次手动测试事件检查输入、过滤器、Agent 行为和输出。
  6. 最后再设置 schedule 或 webhook，并记录暂停、重试和删除方法。
自动化触发方式适合初学者的安全动作
GitHub PR Review新 PR 或手动运行先只生成建议，不自动合并
Repository Monitor仓库事件或定时检查先写内部报告，不直接改代码
Slack Monitor关键词、mention 或频道消息先总结，不自动回复全员
自定义 webhook外部服务 POST 事件先验证签名和事件字段

09 · Webhook 与第三方工具：事件链路必须可解释

对于 Linear、Stripe、Slack 等非内置 GitHub 事件，官方文档建议先注册 webhook，再创建 automation。注册阶段需要你自己保护 signing secret；Agent 可以帮助生成命令或配置，但不要把真实 secret 粘到公开 Prompt。创建后必须用测试 payload 验证 event key、签名 header、过滤条件和目标动作。

事件源 → webhook 注册
      → 签名校验
      → event_key 提取
      → automation 过滤
      → Agent 对话
      → 只读报告 / 受控写入

事件自动化的常见误区是把“收到事件”当成“应该立即执行”。生产事件可能重复、乱序或重试；动作可能有副作用。给每个流程写清幂等策略、去重键、最大重试次数、失败通知和人工接管入口。

10 · 自托管 VM：让任务在电脑关机后继续

VM 适合常驻任务、远程访问和更强算力。官方提供 backend-only 和 full Canvas 两种形态。backend-only 让 UI 留在你的电脑，VM 只运行 Agent Server 和 Automation；full Canvas 则让 VM 同时提供浏览器 UI 和 backend。

# 远程 backend-only
export LOCAL_BACKEND_API_KEY='[REDACTED]'
agent-canvas --backend-only --public

# full Canvas
export LOCAL_BACKEND_API_KEY='[REDACTED]'
agent-canvas --public

公开模式要求 API key；远程部署还要配置防火墙、HTTPS、VPN、ngrok 或身份代理。SSH tunnel 适合个人临时访问；如果使用域名，推荐反向代理终止 TLS 并把流量转给 localhost:8000。不要直接把 8000 暴露到没有认证的公网。

最高风险边界：Agent Server 能读写 VM 文件、执行命令、访问网络和使用保存的 secrets。任何能调用它的人，理论上都可能获得同等执行能力。把 VM 按生产主机保护。

11 · 30 分钟安全上手练习

  1. 创建一个只包含 README 和测试数据的 demo 项目。
  2. 用 npm 或 Docker 启动 Canvas，打开 localhost:8000。
  3. 让内置 OpenHands 只读项目并输出目录说明。
  4. 让 Agent 创建一个非敏感的 TODO 文件，确认变更可见。
  5. 注册一个 ACP provider，但先不授予生产仓库权限。
  6. 开一个新会话，发送“介绍当前工作区并列出风险”，检查 provider 是否正确。
  7. 创建一个只读 GitHub 或 Slack automation 草稿，不接生产写入。
  8. 手动触发一次，检查截图/日志/运行历史和失败处理。
  9. 记录 backend、agent、model、workspace、secrets 和允许的动作。
验收记录

Backend: local / docker / vm
Agent: OpenHands / ACP provider
Workspace: demo-only
Allowed actions: read + create demo file
Blocked actions: production write, send message, merge PR
Result: pass / fail

12 · 什么时候值得用，什么时候先别用

场景建议原因
多个 coding agents 同时运行值得评估统一状态、对话和后端切换
需要常驻自动化值得评估 VM/Automation电脑关机后仍可执行，但安全成本增加
只想偶尔问一个 Agent先用原生 CLI/IDECanvas 的后端和权限管理可能是额外复杂度
生产仓库自动改动先不要全自动需要审批、隔离、审计和回滚
多人多租户共享谨慎评估 Enterprise 或隔离方案自托管 Canvas 默认不是完整多租户系统
容器化隔离需求优先 Docker/VM比主机直跑更容易明确文件边界

OpenHands Agent Canvas 的核心价值不是让 Agent 更聪明，而是把 Agent 的执行入口、后端、工作区和自动化排队起来。它最适合已经有多个 Agent、多个项目和持续任务的人。若你还没有稳定的单 Agent 工作流，先把权限、项目目录、验收和回滚习惯建立起来，再上统一控制中心。

让 Agent 排队上工，但不要让权限也自动扩张

  • 先本地、后远程；先只读、后写入；先一个 Agent、后多个后端。
  • 把 Canvas、Agent Server、Automation 和 Workspace 的职责分开看。
  • ACP 解决连接协议，不自动解决凭据、沙箱或生产安全。
  • 任何事件触发的写入动作，都要有范围、幂等、审计和人工接管。
