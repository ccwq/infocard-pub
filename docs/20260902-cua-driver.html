能力边界与使用提醒

把社区经验和官方事实分开，才能避免“能演示”被误读成“处处可靠”。

发布前必须知道

  • 权限是前置条件；权限未授予时，driver 无法观察或驱动桌面。
  • 后台执行是 best-effort，实际效果取决于平台、目标应用和窗口支持。
  • 原帖关于 GPT-5.6 luna、OpenAI 与其他模型的比较属于作者个人实测，未作为官方 benchmark。
  • 先从 Calculator 这类可验证任务开始，再把流程扩展到真实业务应用。

Windows：安装、交互式会话与 SSH

Windows 的关键限制不是安装权限，而是 driver 是否位于能看到目标桌面的交互式 Session。

安装与验证

PowerShell 执行官方安装器，自动识别 x64/arm64，默认不需要管理员权限，并配置用户级 PATH。

# PowerShell
irm https://cua.ai/driver/install.ps1 | iex
cua-driver --version
cua-driver doctor
cua-driver call list_apps

安装布局

发行版位于 %USERPROFILE%\.cua-driver\packages\releases\，命令入口位于 %LOCALAPPDATA%\Programs\Cua\cua-driver\bin。新 PowerShell 窗口才能稳定读取更新后的用户 PATH。

SSH 不要直接驱动 Session 0

  • Windows OpenSSH 通常在 Session 0 运行；它没有 RDP/控制台用户的交互式桌面。
  • 从本地控制台或 RDP 执行 cua-driver autostart enable 与 cua-driver autostart kick。
  • SSH 侧通过 --socket \\.\pipe\cua-driver 连接交互式 daemon。
# 交互式会话中
cua-driver autostart enable
cua-driver autostart kick
query session

# SSH 侧
cua-driver status
cua-driver call list_apps --socket \\.\pipe\cua-driver
claude mcp add --transport stdio cua-driver -- cua-driver.exe mcp --socket \\.\pipe\cua-driver

Linux：X11、XWayland 与 Wayland

Linux 的安装成功不等于桌面可驱动；显示服务器、AT-SPI 和 compositor 必须分别确认。

X11 / XWayland：优先验证

最小系统先安装 libxi6 与 at-spi2-core，再执行官方安装脚本。

# Debian/Ubuntu 示例
sudo apt update
sudo apt install libxi6 at-spi2-core
/bin/bash -c "$(curl -fsSL https://cua.ai/driver/install.sh)"
cua-driver doctor
cua-driver call list_apps

无物理显示器

服务器或容器需要先提供桌面会话和显示服务器，例如 XFCE + Xvfb；仅设置 DISPLAY 不会自动产生完整 AT-SPI 树。

# 仅示意，按发行版调整
sudo apt install xvfb xfce4
Xvfb :99 -screen 0 1280x800x24
export DISPLAY=:99

Wayland 不是统一能力层

  • X11/Xorg：窗口发现、截图、AT-SPI 和部分后台动作较完整，但目标工具包可能拒绝合成输入。
  • XWayland：应用暴露真实 X11 窗口时可使用 X11 路径。
  • Sway：支持但有边界；GNOME/Mutter 需要维护中的 WinRects helper；KDE/KWin 仍属 experimental。
  • 原生 Wayland 下优先使用 AT-SPI 语义动作；任意遮挡窗口的原始后台键盘/像素输入不能默认成立。
# 可选：启用 native Wayland 路径
export CUA_DRIVER_RS_ENABLE_WAYLAND=1
cua-driver doctor

# 让部分应用走 X11 后端
GDK_BACKEND=x11 <your-app>
QT_QPA_PLATFORM=xcb <your-app>

权限、daemon 与 MCP 配置

先决定运行模式，再启动 daemon；运行中不能通过 Agent 工具修改权限模式。

01standard本地 CLI/MCP 默认模式，适合低风险试用。
02bounded绑定工具、应用、origin 与目录清单。
03unrestricted只适合隔离实验机，需危险确认。
04共享 daemonWindows/Linux 显式使用 --socket。
# bounded daemon
cua-driver serve \\
--permission-mode bounded \\
--capability-manifest ~/cua-session.yaml \\
--approve-capability-manifest

# MCP 配置优先让工具生成
cua-driver mcp-config --client claude
cua-driver mcp-config --client codex
cua-driver skills install
cua-driver skills status

客户端注册 ≠ 桌面可用

MCP 注册只说明客户端知道如何启动 server。仍需分别检查 doctor、status 和 call list_apps。

权限配置是启动配置

systemd unit、Scheduled Task、客户端环境变量或 embedding host 的修改者，都可能改变 driver 的能力边界。

07

故障排查与安全边界

结构化拒绝优于静默成功；每次动作都要从最新窗口状态开始并重新读取结果。

常见诊断顺序

  1. cua-driver --version
  2. cua-driver doctor
  3. cua-driver status
  4. cua-driver call list_apps
  5. 再检查窗口系统、用户、Session、DISPLAY、AT-SPI 和 socket。

background_unavailable

它表示 driver 在执行前拒绝了不安全或未证明的后台路径。可改用语义 element action、最新窗口坐标、受控 foreground，或在 Linux 尝试 XWayland；不要无限重试相同动作。

不应默认自动执行

  • 发送邮件、消息或社交平台内容；
  • 写入生产数据库、线上配置或支付系统；
  • 删除、发布、审批等不可逆动作；
  • 含敏感个人信息的窗口；
  • 没有回读验证的提交动作。
