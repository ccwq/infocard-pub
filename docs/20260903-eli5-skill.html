ELI5

不是把技术讲幼稚，而是让没参与实现的人也能准确复述它。

dzhng / skills · engineering

把技术变更讲成人话，但不丢精度

一个可显式调用的 Agent Skill：从问题、解决方案一路讲到 schema 变化，让规格说明不再只对作者自己清楚。

1

走完一个场景

WALK THE SCENARIO

从触发事件、当前行为到变更后的结果，不停留在抽象属性。

2

术语先定义

DEFINE TERMS

第一次出现就解释术语，避免读者依赖 spec 或会话里自创的标签。

3

控制流显式化

USE PSEUDOCODE

遇到“只有当”“除非”“下一次”这类顺序关系，用伪代码把条件写出来。

4

盘点持久化契约

INVENTORY SCHEMA

新增、改变、删除、重置、兼容和迁移都要说清楚，不能只讲表面行为。

核心判断：白话不是删掉细节，而是把细节放进可跟随的阅读路径。
01

Problem

问题：为什么技术说明读完仍然不懂

一个常见场景

团队说“把用户资料从本地缓存迁到远端存储”。熟悉代码的人知道大概怎么做，但新加入的评审者不知道：什么时候写入？旧数据怎么办？第二次请求会读哪里？失败时是否回滚？

抽象描述的盲区

如果只写“增加持久化层并保持兼容”，读者会把自己的假设填进去。ELI5 要求把现状与提议分开，沿着一个真实请求走到底。

02

Solution

解决：先建立心智模型，再看实现名词

01触发用户提交资料，系统收到一次请求。
02现状当前只写本地缓存，进程重启后数据消失。
03变更新方案先写远端，再更新本地索引。
04结果下一次请求可从远端恢复，失败路径也有定义。
// 说明控制流，而不是假装这是项目真实代码 if (remote_write_succeeds) { update_local_index(); } else { keep_old_value(); report("远端写入失败，未改变现有数据"); }
03

Schema changes

契约盘点：数据结构到底有没有变

问题必须说明的内容读者要得到的答案
新增了什么字段、记录、事件或存储位置新数据从哪里来、由谁写入
改变了什么类型、默认值、读取顺序或 wire format旧读者还能不能读
删除或重置什么旧字段、缓存、游标或历史数据是否需要迁移、是否有意丢失
保持不变什么兼容行为与明确不变的边界升级后用户无需改变什么
本 Skill 自身的边界

它负责解释规格，不负责实现变更。仓库元数据还声明了 disable-model-invocation: true，因此需要显式调用；解释结果不代表代码已经写完、测试已经通过或方案适合直接上线。

04

如何使用

从仓库安装，再把阅读路径交给 Skill

安装

使用 npx skills add dzhng/skills 安装技能集合；需要时再用 --list 选择单个 Skill。

固定输出

输出标题顺序固定为 Problem、Solution、Schema changes。读者可以据此快速定位：问题是什么、怎么解决、数据契约是否改变。

把“我懂了”变成可验证的复述

PLAIN LANGUAGE · NO HAND-WAVING

  • 具体：一个场景贯穿始终，不靠抽象口号。
  • 精确：定义术语，保留条件、顺序和边界。
  • 可评审：schema、迁移与兼容问题被单独列出。
  • 可复用：其他 Skill 也能引用这一套 ELI5 表达规范。
