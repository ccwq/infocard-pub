Codex 只讲 OpenAI Responses，Claude Code 只讲 Anthropic Messages，Gemini CLI 只讲 Gemini API——想让每个 Agent 用上别家的模型，过去只能手改 baseURL、写代理脚本、反复编辑配置文件。Magpie（yetone/magpie，2026-09-23 开源）把这件事压缩成一个菜单栏应用 + 一个本地网关：点一下换模型，所有 Agent 共用一个模型目录、共用你已付费的订阅，配置文件的注释和缩进一根毫毛都不动。

TL;DR

Magpie 是一个菜单栏常驻的模型切换器 + 本地 API 网关，可以拆成两层理解。配置平面：它列出机器上每个 AI Agent 及其当前模型，点值即改，且只改你动的那一个键（原子写入，原值存入 stash.json 可回滚）；Profile 把整套 Agent 配置快照成一键切换。数据平面：本地网关监听 127.0.0.1:3425，同时讲 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Google Gemini 四种 API 并双向翻译（含流式、工具调用、reasoning），Agent 们全部指向这一个端点，从同一个目录挑模型。

它的差异化在订阅复用与多账号路由：Claude Code、Codex（ChatGPT）、Copilot、Devin、Qoder、SuperGrok 的登录直接变成 Provider，模型以 claude/claude-sonnet-5 这样的拼写出现在所有其他 Agent 里；多个账号、多把 key 一起挂，网关按「谁快重置谁先上」的 smart 策略逐请求调度，欠费歇 30 分钟、限流遵守 Retry-After、故障指数退避——在回复第一个字节抵达 Agent 之前完成切换。本卡与 2026-09-27 的入门卡互补：那张回答「这是什么」，这张回答「它到底怎么运转、怎么用透」。

01

问题与方案：两层拆掉 N × M 死结

Problem & Architecture

没有 Magpie 的世界是一个 N×M 死结：N 个 Agent 各有各的配置格式（settings.json、config.toml、config.yaml、opencode.jsonc…），M 个模型供应商各有各的 API 方言。想给 Codex 挂 DeepSeek、给 Claude Code 挂 Kimi，你得手写 [model_providers.*] 表、抢注环境变量、甚至自己架一层代理——改坏了注释没了，改错了原值找不回来，不同 Agent 的模型清单还互相不知道。更现实的痛是额度碎片化：Claude Max 的额度快重置了还剩一大截，ChatGPT Pro 已经限流，Copilot 席位闲着——没有任何原生机制让它们互相救场。

配置平面

每个 Agent 一行，模型一目了然；点值即改，手术式编辑只触碰你改的那一个键，注释、顺序、缩进原样存活，写入原子完成。被替换的原值存进 ~/.config/magpie/stash.json，切回原生模型时原样放回。

数据平面

本地网关 127.0.0.1:3425 承接所有请求，按需在四种 API 间翻译；供应商本来就说这个 API 时直接透传，不做无谓转译。Agent 永远看不到供应商的 key 和 URL，密钥全部留在 Magpie 手里。

目录平面

模型列表不是编译进去的：Magpie 拿着你的 key 实时询问每家供应商「你到底伺候哪些模型」，早上发布的模型下一次刷新就出现在 picker 里；models.dev 目录兜底补全名称与 reasoning 档位，后台自动刷新。

入口平面

同一套能力的四种形态：菜单栏弹出面板（magpie）、终端 TUI（magpie tui）、纯 CLI 脚本化、浏览器 UI（magpie web，WSL/SSH 服务器场景）。菜单栏图标 + 独立窗口 + 托盘菜单三处可达。

03

网关架构：一个端点讲四种方言

Gateway Internals

网关随应用启动，监听 127.0.0.1:3425（MAGPIE_ADDR 可改），无头场景用 magpie serve 单独跑，反向代理/容器部署用 MAGPIE_PUBLIC_URL 对外公布基地址。API key 随便填（约定 magpie）——网关只听 loopback，这是它的默认信任模型。供应商本身就说 Agent 的 API 时请求直接透传；说不通时在网关内翻译，流式、工具调用、reasoning 全程保留。模型一律拼作 provider/model。

网关路径对应的 API
/v1/chat/completionsOpenAI Chat Completions
/v1/responsesOpenAI Responses
/v1/messagesAnthropic Messages
/v1/messages/count_tokensAnthropic token 计数
/v1beta/models/{model}:generateContentGoogle Gemini（含 :streamGenerateContent / :countTokens）
/v1/models · /v1beta/models统一模型目录（含 reasoning 档位）

每个 /v1/models 条目自带 reasoning 与 supported_reasoning_levels；routing group 只列出全体成员都支持的档位。native_endpoints 字段标明哪些 API 对该模型是原样直通。Gateway 标签页把这些做成复制按钮和现成代码片段（shell / curl / Python / Node），MAGPIE_DEBUG=1 则在终端打印每次调用。

任何带 baseURL 的工具都能接入

三个标准环境变量即插即用，key 都填 magpie：

OPENAI_BASE_URL=http://127.0.0.1:3425/v1 ANTHROPIC_BASE_URL=http://127.0.0.1:3425 GOOGLE_GEMINI_BASE_URL=http://127.0.0.1:3425
两个观测/控制头

X-Magpie-Account: 把请求钉在多账号订阅里的某一个账号上（邮箱或 Routing 页 id）；账号不存在、plan 不含该模型或正在休息时报错而不漂移。

X-Magpie-Session: 配合 GET /v1/magpie/route?session=… 在首 token 抵达前看到这一轮路由给了谁；带 after=/wait= 参数（最长 60 秒）可以一条请求挂住等路由变化，UI 便能逐步跟进一整轮 turn。

一次请求的完整生命周期——以「Claude Code 收到 group/opus 模型的一个请求」为例：

1

接收：Claude Code 向 ANTHROPIC_BASE_URL 发 Anthropic Messages 请求，key 是无意义的 magpie；网关按模型字段认出这是一个 routing group。

2

路由决策：按组的策略（smart/order/rotate/usage）与每个成员账号的余额、重置时间、限流状态选出一个成员（provider + model + effort）；决策发生在向供应商发问之前，可通过 /v1/magpie/route 观测。

3

翻译或透传：成员是 copilot/claude-opus-5.5 这类「同 API 不同上游」时原样转发；跨 API 时做协议翻译——流式分片、工具调用 schema、reasoning 字段一一映射。Claude 订阅成员则走特殊路径：驱动本机真实 claude 二进制发起这一代。

4

失败换人：成员失败则指数退避拉黑片刻，立即换下一个成员重试——这一切发生在回复第一个字节返回给 Agent 之前，Agent 只看到一次成功。

5

记账：本次调用的 agent、provider、model、token 数（含缓存与 reasoning）、时延、实际应答的 served_model、实际服务的上游 key 指纹与保存名写入本地账本；OTLP 开启时异步导出元数据（正文永不导出）。

6

会话粘性：按 stays= 规则把这条会话与应答账号绑定一段时间，保住供应商侧的 prompt cache；下一条请求到来时回到第 2 步。

04

订阅即供应商：已付费的登录，全员可用

Subscriptions as Providers

Magpie 最锋利的一点：你在某个 Agent 里的登录本身就是一份订阅资产。Claude Code（Keychain 或 ~/.claude/.credentials.json 的 OAuth）、Codex（~/.codex/auth.json 的 ChatGPT 登录）、Copilot、Devin、Qoder、SuperGrok、Cursor 订阅的登录出现在 magpie providers 里，模型以 claude/claude-sonnet-5、codex/gpt-5.5、copilot/claude-sonnet-4.5 的拼写进入所有其他 Agent 的 picker。不复制凭据、不粘贴 key，token 按各家 Agent 自己的方式刷新（轮换后的 token 会写回 Agent 找得到的位置），登出即消失。模型清单也是供应商官方的——用同一登录去问 Anthropic / Copilot / Codex 的 API，上游加了新模型下次刷新就有。

各家背后的实现并不一样，这正是深度使用前该看清的部分：

订阅模型拼写Magpie 的接入方式
Claude Pro / Maxclaude/claude-sonnet-5Anthropic 会把其他 Agent 的 system prompt 归类为第三方流量，因此 Magpie 驱动本机真实的 claude 二进制发起每一代请求；调用方的工具经 MCP 桥接进同一次 turn，tool result 唤醒同一个 Claude Code 进程。Pi、OpenCode 等全部自动走这条路。需要本机装有并登录 Claude Code。
ChatGPT Plus / Procodex/gpt-5.5ChatGPT 后端只支持流式且拒绝少量参数——Magpie 把非流式请求改写为流式、剔除对方不收的参数。

SuperGrokgrok 系列直连 grok CLI 用的 Responses API，用 CLI 自己的登录，调用方工具透传。
Cursor 订阅cursor 系列走 cursor-agent 的 Agent API；Cursor 模型把调用方工具当 MCP 工具调用，Cursor 自带工具不运行。

订阅复用的边界，用前必读

  • Claude 订阅路径要求本机安装并登录 Claude Code，本质是借真客户端发起请求；跨 Agent 共享订阅请自行确认与供应商条款的相容性。
  • Qoder CN（qoder.cn，阿里云/手机号账号）与 Qoder（qoder.com）账号互通但套餐独立，均需 BYOK 套餐。
05

多账号路由：把所有余量吃干榨净

Multi-Account Routing

把手里所有账号和 key 全挂上——几个 Claude、几个 ChatGPT、几个 Copilot 或 Grok 账号、同一供应商的多把 key——每个请求由网关决定谁来接。核心目标只有一个：不浪费任何一份即将过期的额度，且 Agent 永远看不到失败。账号状态机全自动：欠费 key 歇 30 分钟；被限流的账号按供应商响应头（Retry-After / reset）精确回避，不猜测不硬撞；故障账号指数退避（一次比一次久），请求在回复第一个字节到达 Agent 之前就换下家重试。

路由策略行为
smart（默认）有余额的订阅里，最快重置的先用——重置就清零的余量先烧掉，同时保持其 prompt cache 温热。
order第一个模型用到不能答，再轮到下一个。
rotate每一轮换下一个成员。
usage用量最小的先用。

stays= 控制会话粘性：auto（默认，供应商缓存还值钱就粘住）、session、turn、off。还有一条容易被忽略的硬规则：上下文窗口是路由输入——某个成员被用到 95% 窗口时，请求自动转向装得下的成员，所以虚报窗口会让转移来得太晚。reply limit 则会写进 Agent 配置并公告在 /models；网关自身不截断回复。

Routing 页按请求或按会话查看每一次调度；展开会话可见每条请求在有效价格下的成本估算（含缓存读写，未定价模型显示 —）。同一 route id 的多次尝试共享一个 trace id，方便和 OTLP 侧对账。

# 三订阅日常驾驶配置 # 1) 挂账号（登录过 Agent 即自动出现） magpie providers # claude me@work.dev Claude Max serving # claude me@home.dev Claude Pro 38% · 2d # codex me@home.dev ChatGPT Pro 30% · 4d # copilot octo-dev Business 24% · 12d # 2) 组一个跨订阅的 opus 组 magpie group add opus \ models=claude/claude-opus-5-5,copilot/claude-opus-5.5 \ routing=order stays=session magpie claude group/opus # 3) 追加成员 / 换策略 magpie group set opus \ models+=openrouter/anthropic/claude-opus-5.5 \ routing=usage # 4) 看每一步路由去了哪 curl 'http://127.0.0.1:3425/v1/magpie/route?session=…'

导入旧配置也是一条命令的事：App 的 Import 对话框能读 Claude Code 的 settings.json 与 Codex 的 config.toml（自定义 provider、固定 header、profiles 模型目录一并导入），导入前逐条审查，指向 Magpie 自身或纯 env_key 的条目自动跳过。

06

配置手术：只动一个键的编辑器

Surgical Config Editing

Magpie 编辑 Agent 配置的方式是「手术式」的：只改你点的那一个键，注释、键序、缩进原样保留，写入是原子的。被替换的值存进 ~/.config/magpie/stash.json——选回原生模型时，原来的环境变量、[model_providers.*] 表、auth 配置会被原样放回，不留残骸。这是它与「生成一版新配置文件覆盖掉」类工具的本质区别：你的配置文件始终是你的。

每家 Agent 被写入的字段各有讲究：Claude Code 收到 env 块里的 ANTHROPIC_BASE_URL/ANTHROPIC_AUTH_TOKEN 与模型变量，选回原生 opus/sonnet 时全部移除还原；Codex 收到 [model_providers.magpie] 表加一份 model_catalog_json（从统一目录写出，模型直接出现在 Codex 自己的 /model 里），ChatGPT 登录永不触碰；Gemini CLI 的 auth 在 API key / Google 账号 / Vertex 间切换，key 落在 ~/.gemini/.env；OpenCode、Pi、Crush 收到一个 magpie provider 条目；Claude Desktop 走第三方网关模式（Code 与 Cowork 指向 Magpie，重启生效）。手动改坏了也不用怕——切回原生模型即触发 stash 还原。

每个 Agent 还有自己的「模型可见性」：Agent 名下 Showing 5 / 32 models 打开它的清单，点掉不想要的模型（连 Codex 的 /model 连 ChatGPT 官方模型一起管），别的 Agent 不受影响。上下文窗口 / 回复上限的声明（magpie model context / output）也会写进 Pi 的 contextWindow/maxTokens、OpenCode 的 limit 等字段——已运行的会话保持启动时的值，网关侧立即生效。

# 每个字段都可以独立驱动 magpie codex effort high magpie codex xhigh # 裸 effort 也认识 magpie claude haiku deepseek/deepseek-v4-flash magpie claude haiku "" # 单档位回归主模型 magpie gemini auth api-key # 供应商管理 magpie presets # 已知供应商分组列出 magpie providers # host/key/暴露模型/谁在用 magpie provider test deepseek # 每个 API 探一针带延迟 magpie provider models deepseek # 重拉模型清单 magpie model context relay-a/gpt-5.5 262144 magpie model wire relay-b/m2 vendor-c/m2-preview magpie sync # 刷新目录与所有实时清单

08

供应商目录与密钥治理

Providers & Key Hygiene

内置 20+ preset，覆盖国内外主要供应商与中转：Anthropic、OpenAI、Gemini、DeepSeek、Kimi (Moonshot)、GLM (智谱)、MiniMax、StepFun、Qwen、百度千帆（含个人/企业 Token Plans 与按量付费，各自独立端点）、腾讯云 Token Plan、华为云 MaaS、火山方舟、Mistral、Groq、xAI、OpenRouter、Together、Fireworks、SiliconFlow、NVIDIA NIM、ModelScope、AiHubMix、PipeLLM、302.AI、Ollama、LM Studio。preset 之外的自定义供应商参数齐全：url=（OpenAI 兼容 base）、anthropic=（Anthropic 兼容 base）、responses=（独立 Responses 端点）、catalog=（借 models.dev 的模型清单）、models=（指定暴露哪些）；preset 不认识的字段都能用同样的方式覆盖。

密钥治理是显式设计而非附带特性：Magpie 从不读 shell 环境变量里的 API key——你添加什么就用什么，杜绝「环境里躺着一把不知道哪来的 key」的隐性风险。供应商 key 存 ~/.config/magpie/providers.json（权限 0600），Agent 永远看不到供应商 key 与 URL。网关对客户端另发gateway key（与上游 key 分离）：开启 LAN 共享后，远程请求必须携带启用的 gateway key（Bearer / x-api-key / x-goog-api-key / ?key= 均可），loopback 保持宽松；key 可命名、停用、轮换、删除，轮换保留名称、启用状态与用量历史，删除需确认。凭据存 caller-keys.json（0600），永不进账本或列表响应。

# 无头网关先发钥匙再开门 magpie gateway-key add "Remote laptop" magpie gateway-key list magpie gateway-key rotate <id> magpie gateway-key remove <id>

导入链路也照顾到了：供应商可以把 magpie://import?preset=deepseek&key=… 链接或 usemagpie.ai/import#… 页面链接递给用户，打开即预填（名称、host、模型一览），不按 Add 不落盘，参数留在 fragment 里浏览器不会发给服务器。一家 Magpie 还可以服务多台电脑：Settings 里开 LAN 共享，其他电脑把它加成 Remote magpie provider（magpie provider add remote-magpie sk-magpie-… url=http://192.168.1.20:3425 id=office），providers、routing group（office/group/…）、用量都在共享实例上；每台电脑自己的 Magpie 仍然管理各自的 Agent，跨 API 的翻译只做一次，不会两台机器各翻一遍。

插件生态：OpenCode 的 provider 插件（npm 包，自带 auth hook 的那种）可以直接装进 Magpie（magpie plugin add …），由 Magpie 首次按需下载的 Bun 运行——插件负责登录、列模型、发请求，Magpie 把它当普通 provider 服务给所有 Agent。没有订阅 Magpie 自身也能借插件登录（例如 opencode-gemini-auth）。给插件作者的扩展：auth hook 里加 icon 字段定义供应商图标（https 图像或 data URI，≤1 MB），label/placeholder 定制 key 输入框文案，prompts 先行问答再进 authorize(inputs)。

计费、改名与可观测性

Cost, Wire Names & Telemetry

有效价格：成本按「你为该 provider×model 设的价格 → 该 provider 自己目录的价 → models.dev 的厂商价」三级解析。中转商打折或加价时，默认计价是错的——主动声明四元组（input / output / cache read / cache write，USD 每百万 token，0 也是价格不是缺失）后，账本与 session 总额按有效价重述。注意两条语义：价格是按 provider 分档的（同一模型两家供应商两份价，/* 可整档覆盖），且账本是读取时重估的估算而非结算值——补录价格会改写历史数字。

wire 名字：中转商常用自己的 id 伺服模型（加前缀、带日期、-latest 后缀）。magpie model wire relay-b/model-2 vendor-c/model-2-preview 告诉网关「对外问 vendor 时用这个名字」，对内目录、分组、计费仍用 Magpie 认识的名字；通配 'relay-b/*' 'vendor-c/*' 一条规则管全档（zsh 记得引号）。账本里的 served_model 记录供应商实际应答的名字用于对照，上游改名不会被误判成偷换。

用量账本：按 Agent / 模型记录 token、缓存命中与成本；上游供应商 key 的指纹与保存名也入账（CSV 加 provider_key_id/provider_key_name 列），方便对上游账单——但原始凭据永不入账，删除的 key 保留历史身份，旧记录显示 key not recorded 而非拿今天的配置倒推。图片调用、账号/key 故障转移、System One 调用同样归因。调用方的 gateway key 也单独归因（caller_key_*）。

OTLP 导出：Settings → Observability 可把网关请求元数据经 OTLP/HTTP (JSON) 导出（默认关，metrics 单独开关，改设置无需重启；magpie serve 可用 MAGPIE_OTEL_* 环境变量覆盖）。trace 含 agent、provider、model、token 数（含缓存与 reasoning）、HTTP 状态、时延、route id；Langfuse 走其 OTLP 摄取端点即可。红线清晰：prompt/回复正文、工具参数、会话、账号名/key 永不导出。工程细节对齐生产标准：有界队列 128 条、批量 32、5 秒 flush，队列满直接丢弃不拖累网关；429/502/503/504 重试两次封顶 60 秒；每次尝试 3 秒超时；SIGTERM 时网关最多 drain 3 秒。

定位对照：与自建 API 网关怎么选

Positioning, Not Benchmarks

社区里常见的另一类方案是自建统一网关（LiteLLM Proxy、one-api / New API 等）。以下只是定位层面的定性对照——帮你想清楚「要解决的是谁的问题」，各家具体能力以官方文档为准，本卡不做功能基准：

维度Magpie（本地优先）自建网关（服务器优先）
部署形态菜单栏应用 / 单二进制 / Docker，默认 loopback常驻服务器进程 + 数据库，面向多客户端
Agent 配置核心能力：手术式写入 30+ Agent 的配置文件，stash 可回滚，per-agent 模型可见性一般只提供统一 baseURL，Agent 侧配置仍需手改
订阅复用核心能力：Claude / ChatGPT / Copilot 等订阅登录即 Provider，token 代刷新通常面向 API key 池，订阅 OAuth 非标配
多账号调度smart 重置感知 / 限流尊重 / 字节级 failover，GUI 可观测通道权重、优先级等策略，多在配置文件定义
共享面LAN 共享 + gateway key，服务自己的多台电脑天然多用户 / 多团队，计费与配额体系更重
适用判断「我一个人的机器们要共享所有模型与订阅」「一个团队 / 一组服务要统一模型出入口」

两者并不互斥：Magpie 的 Remote magpie 模式已经能覆盖「几台私人电脑共享」的轻量场景；再往上走团队级计费、配额、审计，才是自建网关的主场。选型先问部署位置和信任边界，再比功能清单。

备份、同步与服务器部署

Backup, Sync & Docker

备份：magpie backup 生成 magpie.magpie-backup——providers（含 key，除非 --no-keys）、为 provider 选的图片、设置、profiles、每个 Agent 的模型与 library（指令集、MCP server、skills 及其文件；单文件超 2 MB 除外），端到端加密 AES-256-GCM，密钥经 PBKDF2-SHA256 从口令派生，服务器上只存得密文。恢复侧颗粒度够细：magpie restore --no-agents 只搬 provider 与设置不动 Agent 配置；--no-library 保留目标机 library；无 key 的 provider 保留目标机已有 key；piped 输入口令取 stdin 第一行。Subscriptions 不进备份——每台机器各自登录。

多机同步：Settings → Sync 走 WebDAV（坚果云 / Nextcloud / 群晖）或 S3（AWS / Cloudflare R2 / B2 / MinIO / Garage / NAS），网关运行期间每 3 分钟对齐一次；每台机器只在「读到的版本」之上条件写入，另一台机器插进来的更新会被合并而不是覆盖。bucket 需已存在，access key 需读写 /magpie/ 前缀（AWS 还需 list）；secret 交互式录入且只对录入时的 endpoint + access key 生效；不支持条件写的服务器退化为写前 ETag 校验。

Docker 部署：官方镜像把纯终端二进制放进 distroless（nonroot，带 glibc 供插件的 Bun 使用），一切状态落在 /config 卷（Magpie 自身文件 + 各 Agent 的登录 + Bun 插件缓存；旧卷自动兼容），自带 HEALTHCHECK（magpie healthcheck），Compose 可用 depends_on: condition: service_healthy。端口发布纪律写得很硬：共享未开启前网关接受任意 key，所以 3425（网关）与 3430（Web UI）只准发布在宿主机 loopback；要跨机访问，先开 Settings 共享（生成命名 Magpie key）或在容器里 magpie gateway-key add，再放开端口。容器内 OAuth 回调落在 localhost 时把地址栏整段复制进 Callback URL 字段即可；Web UI 的 key 可用 MAGPIE_WEB_KEY 固定。

docker build -t magpie . docker run -d --name magpie \ -p 127.0.0.1:3425:3425 \ -p 127.0.0.1:3430:3430 \ -v magpie-config:/config magpie # 浏览器 UI 形态 docker exec -it magpie \ /magpie web --addr 0.0.0.0:3430 --no-open

高频疑问

FAQ
我的 key 会被上传到云上吗？
不会。供应商 key 只存本机 providers.json（0600）；Magpie 不读 shell 环境变量里的 key；备份走口令加密（AES-256-GCM）；每日遥测只有随机 install-id + 版本 + 系统/架构，可用 DO_NOT_TRACK=1 关闭；源码构建永不发送。
切了模型，Agent 怎么还在用旧的？
Agent 在启动时读取自己的配置，运行中的会话保持旧模型。新开会话即可；Codex 官方说明要求切换后重启。先用 magpie ls 确认写入已生效，再重启会话。
Claude 订阅共享给别的 Agent，账号会有风险吗？
Magpie 的实现方式是驱动本机真实 claude 二进制发起请求，让流量落在 Anthropic 对 Claude Code 的既有分类内，而不是伪造客户端头；但「订阅能否跨工具使用」最终取决于你与供应商的条款，Google 对 Antigravity 登录的域外使用已明确警告会封号——共享订阅请自担条款风险，敏感账号用丢得起的。
和 one-api / LiteLLM 这类自建网关比，选哪个？
看部署位置：Magpie 是本地优先的个人路由层（自动写 Agent 配置 + 订阅复用 + 菜单栏体验），自建网关是服务器优先的团队出入口（多用户、计费、配额）。个人多机用 Remote magpie 就够，团队级审计计费才需要后者。详见第 10 节定性对照。
中转商的模型名和官方对不上、价格也乱报怎么办？
两个专门机制：magpie model wire 声明「对 vendor 用什么名字问」；magpie model price 按供应商×模型声明真实四元组价格，账本按有效价重估。窗口/输出上限也能声明（model context / output），窗口还参与路由决策，别虚报。
Linux 无桌面环境 / 服务器上怎么用？
三条路：纯终端二进制（make cli 或 release 里的 cli 构建）+ magpie serve 跑无头网关；Docker 镜像（自带健康检查，状态全在 /config 卷）；magpie web 把完整 App 窗口开进浏览器（WSL / SSH 场景，MAGPIE_WEB_KEY 固定访问 key）。桌面 WebKitGTK 缺失时 Linux 自动只有 CLI 形态。

隐私姿态与已知边界

Privacy & Caveats

遥测极简且可关：运行中的 Magpie 每天向 PostHog 发一条计数事件（本机随机 install-id、版本、系统与架构），不含账号、key、provider、模型、prompt 或用量。关闭方式三选一：Settings → Privacy、DO_NOT_TRACK=1、MAGPIE_NO_STATS=1；从源码构建的版本永不发送。文件布局全部 XDG 规矩、各就各位：

路径内容
~/.config/magpie/profiles.json已保存的 profiles
~/.config/magpie/providers.json供应商与 key（0600）
~/.config/magpie/stash.json被替换的原值，切回即还原
~/.config/magpie/caller-keys.jsongateway key（0600）
~/.config/magpie/plugins.json + plugins/插件与其包
~/.cache/magpie/models.jsonmodels.dev 目录缓存
已知边界与工程注意
  • magpie serve 收 SIGTERM 直接退出不做 drain，最后一批 OTLP 记录可能丢失（best-effort 导出，本地账本不受影响）。
  • 反向代理部署时代理必须自己鉴权，或启用 LAN 共享 + gateway key；代理经 loopback 转发的请求被视作本地请求，代理须自行把关。
  • 手动编辑 settings 时若文件只读，默认 key 变更会失败而不半改——保证可写后重试；旧版遗留的 lanKey 镜像在禁用/删除默认 key 后被随机空值替换。
  • 价格估算基于有效价，同一供应商内多把 key 差异定价仍无法从 provider 级价格精确核算。
  • ChatGPT 后端只支持流式——非流式请求由 Magpie 改写，个别参数被上游拒绝时会剔除。
  • Windows/Linux 构建未签名（SmartScreen 首次运行可能提示）。

适配判断：谁该上，谁不必

Fit / Non-fit
强适配场景
  • 同时跑 3 个以上 Coding Agent，且每个都想用「别家最强」的模型——配置平面一次到位。
  • 手上压着多份订阅（Claude Max + ChatGPT Pro + Copilot 席位）——smart 路由把重置前的余量吃干净。
  • 重度中转/聚合 API 用户——wire 名字、有效价格、按 provider 分档计费都是为此设计的。
  • 小团队/多机器——一台 Magpie LAN 共享 + gateway key，providers 与路由全队复用。
  • 在意配置文件洁净度的人——手术式编辑 + stash 回滚，注释与缩进不受伤。
  • 需要无头网关的服务器玩家——CLI / serve / Docker / web UI 四形态齐备，HEALTHCHECK 进 Compose。
可以绕开的场景
  • 只用一个 Agent、一家供应商、一把 key——切换器与网关都是冗余。
  • 环境禁止安装本地常驻进程（严格受管的公司机器）——网关必须本地跑。
  • 期望「官方 GUI 全功能」的 Linux 用户——Linux 桌面版依赖 WebKitGTK 4.1，未装则只有 CLI 形态；Windows/Linux 构建未签名。
  • 要团队级计费、配额、多租户审计的——这是自建网关的主场（见第 10 节）。
  • 想绕开供应商条款共享账号的——Magpie 的实现（如 Claude 走真客户端）恰恰是在条款框架内做事，不做绕过。

一句话收束：Magpie 把「模型选择」从每个 Agent 的配置难题变成一个操作系统级的选择器——配置平面负责指哪个模型，数据平面负责把请求送到那个模型，而订阅复用与多账号路由让已付费的额度在你的全部工具链里流动。4,108★（2026-10-02 快照）、开源五天、README 已写成小型产品手册——迭代速度本身就是它当前状态的注脚。
