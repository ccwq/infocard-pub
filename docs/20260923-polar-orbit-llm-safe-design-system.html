2026-09-22，@ricouii 在 X 发布 Polar 博客《Building an LLM safe design system》中文全译。背景：Polar 大部分 UI 代码已有 LLM 参与，团队发现问题不是 LLM 不会写 CSS——而是它不知道样式背后的设计决策：p-4、bg-gray-100、dark: 变体、text-[#3b82f6] 全部合法可编译，却在几千次生成后累积成"大量略有差异的灰色"。Polar 正在构建的设计系统 Orbit 的对策：① Token 按设计意图（Intent）命名（background-card 而非色号）；② 用 Meta 的 StyleX 构建 <Box /> 原语，Props 类型只接受预定义 token；③ 禁止裸 <div>，用 Oxlint 规则 'polar/no-raw-html-layout' 强制；④ 颜色 token 用 CSS light-dark() 内置双值，dark: 变体从源头消失。效果：Code Review 从抓 Style Drift 转向讨论行为与布局。文章同时明确：不是批评 Tailwind——是人类还是 LLM 在写代码，决定了开放性是优势还是风险。

01 问题：LLM 的写法全都"合法"，但全都不属于你的系统

文章的起点是一个精确的观察：LLM 写 Card 时会自然产出 p-4、rounded-lg、bg-gray-100、dark:bg-zinc-900、text-gray-500——单独看每个值都合理，但"它们不一定属于你的设计系统"。即使 CLAUDE.md 里明确写过不要这么做，效果也不可靠。

LLM 的写法为什么"合法"实际错在哪
p-4 / p-5 / p-[17px] / px-4 py-3全部通过编译，代表不同间距没有任何一个天然是你的间距标准
bg-gray-100 / bg-zinc-100 / bg-neutral-100全部是合法的灰色没有一个天然是项目标准色
漏写 dark: 变体lint 和编译都不报错Dark Mode 坏掉，渲染后才能发现
text-[#3b82f6]（arbitrary value）完全绕过调色板off-system：脱离设计系统

最麻烦的是：这些都不是语法错误——能过 lint、能编译、能渲染。传统静态分析很难发现"脱离设计系统"这类错误。而且为字符串写 lint rule 是场无休止的追逐：不断加规则、补 regex，总有漏网的特殊情况。LLM 还特别喜欢 escape hatch（裸 className / inline style），因为训练数据里到处都是这种写法。

02 核心洞察：Class 是一个值，不是一个设计决策

文章先把 LLM 放到一边，指出一个更基础的问题：设计系统不是一堆数值的集合，而是一组设计决策——Card 用哪种 Surface、弱化信息用什么颜色、两个元素之间保持多大间距。具体数值只是决策产生的结果，不是决策本身。

p-4 只表达"这里有 16px 的 Padding"，完全没有告诉你为什么是 16px、哪些地方允许用、该和哪些组件保持一致。换成 CSS Variable 也一样：--color-gray-100: #f3f4f6; 只是把名字管理得更好，依然不包含"这个颜色用来做什么"。后果是：六个月后代码里有 40 处 bg-gray-100，你已经分不清哪些当初想表达"这是 Card 的背景"——要改 Card Background 只能全局搜颜色，而不是改一个明确的设计决策。

按数值命名（旧）

bg-gray-100 / p-4

LLM 面对的是货架上几百个看起来都合理的选项，要选对需要具备设计判断和"品味"。

按意图命名（Orbit）

background-card / padding="l"

LLM 是在一组提前做好的设计决策中选择。m/l/xl 表示 Spacing Scale 中的角色，不是碰巧喜欢的几个像素值。

"我们不是要求 LLM 自己拥有设计品味。我们只是要求它正确说出：它现在正在构建什么。"

03 文档只是建议，CI 才是契约

最自然的第一反应是把规则写进 CLAUDE.md / Style Guide / System Prompt。文章的判断很直接：任何写在文档里的规范，本质上都只是一个概率，而不是保证。LLM 会把规范和 Context 里的其他信息一起权衡，"大多数情况下遵守"——但生成次数到几千次后，偶尔的遗漏不断累积，你还是要人工检查每一个 Diff。文章金句：

"Make it hard to express an off-brand decision in code in the first place. Ideally close to impossible."（让偏离品牌的决策在一开始就很难用代码表达，最好接近不可能。）

Polar Orbit 的设计原则

Polar 的落地方式是把规则写成 Oxlint Rule，得到一份确定性 Contract：PR 绿了就能安全合并。同时接受一个反向原则——如果错误设计通过了检查，那是规则有缺口，不是作者违规。只有两个选择：把它写成规则，或接受结果。不存在"但是 Guidelines 明明写了不要这样做"。这改变了"谁需要小心"：约束从"每个作者每次都要记住规范"转移到一个"不会被忘记、跳过、或被 Prompt 说服忽略"的检查机制。

04 Orbit 实现：Token 成为唯一的设计词汇

Orbit 用 Meta 的编译时类型安全 Styling 库 StyleX 替代 Tailwind——但文章强调 StyleX 不是重点，只是手段。真正重要的是在其上构建统一原语 <Box />：Props 类型直接来自 Token Definitions（API 受 Shopify Restyle 启发）。padding 不能接收 16px，只能从预定义尺寸中选；backgroundColor 不能接 hex，只能用定义过的颜色名。

// Orbit 写法：每个值都来自已定义的设计决策
<Box
  backgroundColor="background-card"
  padding="l"
  borderRadius="m"
>
  {children}
</Box>

/* Token 定义（Intent 命名 + light-dark 双值） */
background-card: light-dark(
  hsl(233, 4%, 81%),
  hsl(233, 4%, 3.5%)
)

效果：LLM 生成 Orbit 代码时面对的不再是整个 CSS 世界，而是一个小菜单——Autocomplete 直接告诉它哪些 token 可用；名字写错是 Type Error，而不是三周后才被偶然发现的 Visual Regression。

05 最激进的一步：禁止直接使用 <div>

这是全文讨论最多、也是团队"越来越确信应该坚持"的决定：即使 <Box /> 的 Props 再严格，只要旁边还放着一个完全不受限的裸 <div>（可接任何 className、inline style、attribute），所有约束都形同虚设。只有不存在绕过 Token 的方式时，Token 的约束才真正成立。这一点对 LLM 比对人更重要：人类看一遍 Contribution Guide 就记住了，而 LLM 每次新 Prompt 都要重新认识整个代码库，且天然倾向阻力最小的路径——训练数据会不断把它拉回 <div className="...">。想改变默认选择，可靠的方法不是劝，而是让原始 Element 不可用。

Semantic HTML 怎么办？文章的答案：Box 是 Polymorphic 的，被禁的元素都能通过 as Prop 渲染——最终 DOM 里依然是真正的 <nav>、<ul>，DOM Props 依然有类型并向下传递。拿掉的不是 HTML 语义，是那个完全开放的 String Surface。as 是封闭的 Allowed Elements 集合；直接写 <nav> 则重新打开一扇不受约束的门。执行靠 Oxlint：

// oxlint 配置 + 违规报错原文
'polar/no-raw-html-layout': 'error'

// 直接使用 <div /> 时：
Use <Box /> from @polar-sh/orbit instead of <div />.
This ensures we follow the Orbit design system.

"真正能够穿过 LLM 每一次全新 Context Window、依然稳定生效的指令只有一种：让错误的写法直接无法通过编译。"

06 不可能被忘记的 Dark Mode

每个颜色 Token 内置 Light / Dark 两个值（见 04 节代码），由浏览器原生 CSS light-dark() 函数决定当前用哪个。这意味着：根本不存在需要 LLM 记住的 dark: 变体，也不存在第二遍 Dark Mode Styling。写一次 backgroundColor="background-card"，两个主题自动解析。LLM 没有机会生成"Light Mode 正常、Dark Mode 全坏"的组件——因为那类 bug 在代码层面无法被表达出来。文章称之为最常见的一类 Theme Bug 被"从代码层面根本无法被表达出来"消灭。

07 已观察到的变化与诚实边界
Code Review 转向

不再抓 Style Drift

过去审生成 UI 要找错误灰色、错误间距、漏掉的 dark:、arbitrary value；现在讨论转向行为与布局等真问题。

正确性来源

Correct by Construction

开发者不需要熟悉整套 Design System——正确性从代码结构上保证，而不是靠人记住规范。

渐进迁移

不做大规模 Rewrite

App 大部分仍是 Legacy Tailwind；每次改文件时顺带一个文件一个文件迁移。

文章同时保持诚实：Orbit 还在早期，判断可能被推翻。已知问题：封闭 Token Set 对某些实际 UI 还太小——几乎每周都在加新 token，同时观察"约束成本什么时候大于节省的成本"；每允许一个 escape hatch 都是在保证体系上开一条裂缝，所以持续审查所有 oxlint-disable——例外变多会被视为设计系统自身的 Bug，而不是开发者违规。

"过去，设计系统是一组你希望大家遵守的设计决策。但当大部分代码开始由 LLM 编写之后，'希望它遵守'已经不能算是一种策略。设计系统需要变成：一组在代码中唯一能够被表达出来的设计决策。"

08 读法：与 DESIGN.md 路线互补，不是对立
文档层 · 上一张卡：Refero Styles

DESIGN.md：给 Agent 一份规范去读

零成本起步，适合任何能读文件的 Agent。约束方式是上下文——文档是概率，大多数时候遵守。适合独立开发者、Vibe Coding、没有 CI 体系的项目。

机制层 · 本卡：Polar Orbit

Type + CI：让违规代码无法通过

需要 StyleX/Oxlint 基建投入。约束方式是编译与 CI——保证而非概率。适合有工程团队、代码由 LLM 大量生成的生产代码库。

两条路线回应同一个问题（AI 生成的 UI 跑偏），处在约束强度的两端：DESIGN.md 改善第一稿的质量分布，Orbit 式机制保证合入线的确定性。Polar 自己也两者都用——他们有 CLAUDE.md，只是不再指望它兜底。对个人开发者的可操作建议：先用文档层约束拿到 80 分的初稿；如果项目开始规模化、多人或多 Agent 协作，把最重要的 5–8 条规范升级为 lint 规则进 CI。
