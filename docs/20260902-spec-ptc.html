AGENT RUNTIME / SPECULATIVE EXECUTION
sPTC

让等待发生在代码生成期间

Speculative programmatic tool calling

让工具调用与代码生成重叠

spec-ptc 是面向 RLM、CodeAct 等 programmatic tool-calling harness 的小型库与示例：模型还在生成 REPL 代码时，系统就尝试提前启动可推测工具调用。

核心判断：它不是把所有工具都“并行化”，而是只对可安全推测的调用提前计算，并在真实 REPL 执行时复用结果。
01 / MECHANISM

从完整调用，变成“预测—命中—执行”

01
模型流式生成 REPL 代码
02
Shadow REPL 解析已闭合调用
03
异步启动可推测工具，保存 Future
04
真实 exec 到调用点时命中结果
tokens → 解析部分代码 → 提前启动 llm_query(prompt)
                     ↓
真实 REPL 执行 → resolve 命中缓存结果 → 继续后续逻辑
02 / PYTHON API

最小接入方式

from spec_ptc import Speculator

spec = Speculator()

@spec.tool(speculatable=True, pure=True)
def llm_query(prompt: str) -> str:
    return sub_lm.complete(prompt)

@spec.tool()  # 有副作用：不提前推测
def send_report(text: str) -> str:
    return mail.send(text)

ns.update(spec.hooks())
with spec.turn(repl_locals=ns) as t:
    for delta in model_stream:
        t.feed(delta)
exec(code, ns)

关键标记是 `speculatable=True` 与 `pure=True`。发送邮件、写数据库、付款或改变外部状态的函数不应因为“可能会被调用”而提前执行。

03 / INTERFACE

适配不同 harness

Python 库

用 Speculator 管理 shadow REPL、工具注册、token feed 和最终执行。

Daemon

`spec-ptc-daemon` 用 JSON-lines 提供 turn_begin、feed、resolve、turn_end 四步接口。

现成 wrapper

仓库提供 Claude Code、OpenCode、Pi-mono 的插件方向示例。

依赖前提

需要 harness 能把工具作为 REPL 函数暴露，并能接受 claim-or-run 的返回语义。

04 / SAFETY & BOUNDARY

推测的边界比速度更重要

调用类型是否适合推测原因
纯函数、可重复查询适合结果可缓存，提前执行不会改变外部世界。
子 LLM / sub-agent 查询条件适合潜在收益大，但需处理非确定性和重复调用编号。
写数据库、发消息、付款不适合提前执行可能造成不可逆副作用。
依赖未计算变量或不安全库默认不推测shadow REPL 无法确认输入或副作用。
05 / EVIDENCE

收益应按场景验证

作者将 sPTC 描述为受 speculative execution 和 speculative decoding 启发的 harness 技巧。代码仓库与博客展示了机制、接口和示例；任何速度收益都依赖工具延迟、生成/执行重叠窗口、调用确定性与 harness 实现，不能外推成普遍加速保证。

把等待藏进生成窗口

当代码本身成为 Agent 的主要动作空间，工具调用就不必等完整程序生成后才开始。但越激进的推测，越需要纯度、依赖和副作用边界；sPTC 的工程价值首先是把这些边界显式化。
