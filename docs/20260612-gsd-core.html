GSD Core

Git · Ship · Done

解决 AI 编程的上下文腐化（Context Rot）：用新鲜上下文子代理 + 5 阶段工作循环 + .planning/ 持久化，让任意 Agent 在长时间项目中持续保持高质量输出。

v1.4.4 MIT License Node.js ≥22 12 平台支持 Context Engineering Spec-Driven Multi-Agent
核心理念：Context Rot 不是模型 Bug，是注意力机制的基本属性。

当上下文窗口被历史积累填满，模型不是"忘记"，而是信噪比下降。GSD Core 的解法不是清空重来，而是把重活全部移到有干净上下文的新鲜子代理里执行，主会话只做编排。

PHASE LOOP — 每个里程碑重复同样的五步循环
1
DISCUSS
在规划前捕获实现决策。adaptive questioning 收集上下文，写入讨论记录。
2
PLAN
research + decompose + verify plan fits fresh context window。researcher 和 planner 分工。
3
EXECUTE
并行 waves 执行计划。每个 executor 从干净的 200K token 上下文启动。
4
VERIFY
逐项走查产出，诊断并修复问题，再宣布完成。
5
SHIP
创建 PR，归档阶段，进入下一个里程碑。

DESIGN PRINCIPLES

5 条核心原则

① Fresh Context Per Agent
每个子代理从干净上下文启动，消除 context rot 的结构性根因。
② Thin Orchestrators
workflow 文件只做编排，不做重活。上下文通过 gsd-tools.cjs init 注入。
③ File-Based State
所有状态在 .planning/ 中的人类可读 Markdown/JSON，不依赖数据库。
④ Absent = Enabled
config.json 缺少的 key 默认 true，显式禁用才关闭，降低配置负担。
⑤ Defense in Depth
多层防护覆盖常见失败模式，spec 驱动的验证在执行前拦截低质量产出。

VS CLAUDE.MD / AGENTS.MD — 增量在哪里
❌ CLAUDE.md / AGENTS.md
入口文件容易变成大而全的文档，缺少任务级上下文
没有任务级的 PRD 和工作流关卡
没有 workspace memory，跨会话依赖上下文记忆
没有子代理新鲜上下文机制，context rot 随会话线性累积
平台绑定工作流，换工具需要重新配置
✓ GSD Core
作用域明确的 SPEC，每个阶段有独立 artifact
任务级 PRD：DISCUSS → PLAN → EXECUTE → VERIFY → SHIP 闭环
.planning/ 持久化，/clear 不会丢失工程上下文
fresh-context 子代理，主会话永远保持精简
跨 12 个 Agent 平台统一工作流，一套规范，多平台复用
