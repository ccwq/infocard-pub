优先级视图
P1 — 优先修复
统一认证错误模型

route 层和 request 层对同一次失败可能做出相反判断 — 这是误放行与误登出的共同根源。

P1 — 优先修复
拆开网络错误与认证失效

普通网络抖动被当成登录过期处理，容易误踢正常用户下线。

P1 — 优先修复
统一 route/request 恢复职责

"能进页面，但首个请求就掉线" — 恢复触发条件不同导致体验割裂。

9 项关键问题一览
1
错误对象与分类不统一
认证链路可能抛对象也可能抛字符串，导致 route 层识别不出认证失败。
→ P1 根因
2
双轨恢复职责不一致
route 层与 request 层各行其是，同一 token 状态在不同入口得到不同处理。
→ P1 根因
3
20秒缓存存在错误放行窗口
缓存期间 token 被清空或失效，路由守卫仍直接放行，用户感知极差。
→ P2 调整缓存条件
4
route 层将协议错误当可放行
refresh/check-refresh 协议异常也被静默放行，问题被推迟暴露，排查成本更高。
→ P2 细化错误分类
5
request 层对 refresh 失败过于激进
token过期/后端不可达/网关抖动/接口结构异常全被压成"请重新登录"。
→ P2 区分失败类型
6
网络错误与认证失效耦合
普通网络错误（如断网/网关抖动）也会清理登录态并跳首页。
→ P1 拆开处理
7
tokenInvalid 职责不清
route 层已允许通过，request 层却立即认定不可用，最终刚进页面就被打回首页。
→ P2 收敛判断职责
8
白名单匹配策略模糊
startsWith(prefix) 和 url.includes(item) 容易因巧合导致错误放行或错误豁免。
→ P3 精确匹配
9
文档与实现已出现不一致
refresh-poli.md 描述的行为与实际代码逻辑多处不符，会误导后续维护者。
→ P3 同步修正文档

"当前这套 refresh token 策略最大的问题不是'有没有 refresh'，而是 refresh 成功/失败的语义边界不稳定，route 层与 request 层职责交叉，网络异常与认证过期混在一起。"

— 核心判断 · 原文第三节
建议改造方向
Route 层
只做进入前最小会话判定

是否有 refresh token → 当前 access token 是否可直接用 → 是否需要一次受控恢复。

不再做完整的 refresh 尝试，不在进页前等待网络请求。

Request 层
唯一 refresh single-flight + 重试

首个失败请求触发 refresh，并发请求共享同一 refresh promise。

refresh 成功后统一回放，失败后再统一登出。

错误模型
统一鉴权错误对象

结构化对象：{code: 'AUTH_EXPIRED'|'AUTH_NETWORK_ERROR'|'AUTH_PROTOCOL_ERROR', message, source}。

不再让 refresh/check-refresh 抛裸字符串，route 和 request 各猜各的。

关键约束
网络错误 ≠ 认证失效

网络抖动时保留登录态，仅做网络错误提示，不清 token，不跳首页。

协议异常提示"系统异常"并记录日志，避免静默清退。
