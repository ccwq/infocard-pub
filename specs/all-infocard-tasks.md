# 所有信息卡任务的统一发布与验收规格

## Problem Statement

当前信息卡任务是批量并行推进的，但缺少一个统一、可验收、可统计的本地规格来描述“所有信息卡任务”的完整生命周期。结果是：

- 任务来源分散，难以快速回答“有哪些卡要创建、哪些已创建、哪些已完成”。
- 子智能体 authoring、主线程 promotion、build、verify、视觉、commit/push、公网验收容易被混在一起。
- 候选稿、正式发布、已上线这三个阶段经常被误认为同一个状态。
- 返工主要出现在 manifest、theme、hash、taxonomy、视觉门禁和 build/verify 时序上。
- 用户关注的是效率、时间和成本是否改善，而不是中间过程是否繁忙。

本规格要解决的是：**把所有信息卡任务纳入同一套状态机和批次账本，明确每张卡的当前状态、阻塞点、已完成证据和最终验收标准。**

## Solution

建立一个本地、批次化、状态机化的信息卡发布规格，统一管理所有信息卡任务。

### 核心原则

1. **每张卡独立状态机**
   - discovered
   - researching
   - theme_frozen
   - authoring
   - candidate_ready
   - promoted
   - visual_pending
   - visual_passed
   - built
   - verified
   - committed
   - pushed
   - public_verified
   - done
   - blocked

2. **批次总账**
   - 记录所有卡的创建状态、完成状态、阻塞状态和证据链。
   - 允许批次内不同卡并行 authoring，但正式发布链路保持串行。

3. **职责分离**
   - 子智能体只负责 authoring。
   - 主线程负责 promotion、视觉、build、verify、leak、commit、push、公网验收。
   - 子智能体输出只能作为候选输入，不能直接当作完成结果。

4. **证据驱动**
   - 文件存在。
   - hash 一致。
   - manifest 合法。
   - 主题一致。
   - 漏泄检查通过。
   - 公网页面 200。
   - 视觉结果真实可验收。

5. **完成定义明确**
   - 候选稿完成不是完成。
   - promotion 成功不是完成。
   - build 成功不是完成。
   - commit/push 成功也不是完成。
   - 只有公网页面、索引和必要视觉证据都通过，才算完成。

## User Stories

1. 作为发布协调者，我希望看到所有信息卡任务的统一状态，以便快速判断哪张卡完成、哪张卡阻塞、哪张卡需要接管。
2. 作为发布协调者，我希望知道每张卡当前处于 research、authoring、promotion 还是 public verify 阶段，以便只处理最小缺口。
3. 作为发布协调者，我希望区分“子智能体已返回”与“卡片已发布”，以避免误报完成。
4. 作为发布协调者，我希望知道哪些卡已经创建候选稿，哪些卡还没开始，以便安排优先级。
5. 作为发布协调者，我希望知道每张卡阻塞在 manifest、主题、hash、taxonomy、视觉还是公网验证，以便精准修复。
6. 作为发布协调者，我希望从批次视角看到已创建、未创建、已完成、未完成的总数，以便评估吞吐。
7. 作为发布协调者，我希望知道每张卡是新卡还是更新卡，以便使用正确的时间戳规则。
8. 作为发布协调者，我希望知道哪些卡已 commit/push，哪些还停留在本地候选目录，以便避免误判上线。
9. 作为发布协调者，我希望知道哪些卡已经公网 200，哪些还在 Pages/CDN 传播中，以便区分失败和延迟。
10. 作为发布协调者，我希望在失败时看到准确的失败原因，而不是泛泛地说“没完成”。
11. 作为发布协调者，我希望每张卡都遵循同一套门禁顺序，以便减少流程漂移。
12. 作为发布协调者，我希望保留每张卡的证据链，以便后续复盘和回滚。
13. 作为发布协调者，我希望批次里多张卡可以并行推进，但状态互不污染，以便提高效率。
14. 作为发布协调者，我希望子智能体只操作 `.docs/` 目录，以避免误写正式路径。
15. 作为发布协调者，我希望正式发布与候选稿彻底分离，以避免把草稿当成正式结果。
16. 作为发布协调者，我希望最终报告按卡片逐条列出真实状态，而不是乐观推断。
17. 作为发布协调者，我希望看到这批卡的总效率、总耗时和总成本变化，以便判断 SOP 是否真的改善。
18. 作为发布协调者，我希望比较旧 SOP 和新 SOP 的结果，以便决定是否保留新流程。
19. 作为发布协调者，我希望知道哪些任务根本没创建，以便区分“没做”和“做了但没成”。
20. 作为发布协调者，我希望把“完成”定义成终态，以便以后所有批次都按同一标准验收。

## Implementation Decisions

- 引入批次级状态机，而不是只靠聊天上下文判断任务进度。
- 每张卡必须有唯一 slug 和唯一 authoring 目录。
- 子智能体只允许产出候选稿文件，不允许触碰正式发布目录。
- 发布主链路固定为：research → authoring → promotion → visual → build → verify → leak → commit → push → public verify。
- 任何 HTML / sidecar / manifest 修改后都必须重新计算 hash。
- 更新卡必须刷新 `updated`，新卡必须保持 `date = updated`。
- 视觉门禁必须基于真实桌面/移动截图，不接受只看 DOM 或只看 HTTP 200。
- manifest 必须保持当前仓库 schema，不允许旧字段混入。
- 批次报告必须同时给出：已创建、未创建、进行中、已发布、阻塞中和阻塞原因。
- 最终“完成”定义必须以公网页面和索引都验收通过为准。
- 所有卡的执行证据要可追溯到具体文件、hash、commit 和 URL。

## Testing Decisions

- 测试应覆盖外部行为，而不是内部实现细节。
- 需要测试的对象：批次状态机、单卡状态转移、manifest 校验、主题一致性、漏泄检查、公网验收判断、新卡/更新卡时间戳规则、子智能体接管规则。
- 好测试标准：
  - 只看输入输出和状态变化。
  - 能复现“未创建 / 已创建 / 已发布 / 已阻塞”的边界。
  - 能区分草稿成功与正式发布成功。
  - 能区分构建成功与公网成功。
- 重点回归测试：
  - 子智能体只产出 `.docs/`，不能写 `docs/`。
  - promotion manifest schema 正确。
  - hash 回填后不漂移。
  - verify 不会把候选稿误认成完成。
  - 公网验证要检查详情页和索引同时成立。
- 建议保留一组代表性任务作为基准样本，用于对比新旧 SOP 的效率、时间和成本。

## Out of Scope

- 不重写信息卡内容规范本身。
- 不改变主题注册系统的整体设计。
- 不讨论单张卡的文案润色细节。
- 不把公众号发布流程混进信息卡主流程。
- 不把临时验证卡、废弃卡、已删除卡算作正式成果。
- 不以“子智能体返回了”作为完成标准。
- 不在本 spec 中定义具体某一张卡的最终文案。

## Further Notes

这份 spec 的目标不是把流程写得更长，而是把**所有信息卡任务**变成一个可管理、可验收、可统计的发布系统。

它要回答的不是“我大概做了多少”，而是：

- 哪些卡创建了
- 哪些卡没创建
- 哪些卡卡在什么门禁
- 哪些卡已经真正完成
- 这套 SOP 到底有没有提高效率、节约时间、降低成本

当前已将该 spec 落盘为本地文件，未发布到 issue tracker。
