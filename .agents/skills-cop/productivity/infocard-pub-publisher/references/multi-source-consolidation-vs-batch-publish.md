# 多来源合并 vs 批量发布：决策规则（2026-06-26）

## 两种模式的核心区别

| | 多来源合并（Consolidate） | 批量发布（Batch） |
|---|---|---|
| 输入 | 多张图，同一来源（同一公众号/工具的不同维度） | 多张图，不同来源（不同仓库/不同工具） |
| 输出 | **1 张综合卡** | **N 张独立卡** |
| 触发 | 用户说"做成一张卡"或未明确要求分开 | 用户明确要求各自发卡 |
| 风格 | graph-paper（四面板/多栏目） | 按各自内容类型路由 |

## 合并判断树

```
用户发来多张图
├── 同一来源 + 可以合并叙事
│   ├── 用户明确说"一张卡" → 直接合并
│   └── 用户没说 → 默认合并（保守策略）
├── 同一来源 + 各自独立叙事（如不同工具评测）
│   └── 拆成 N 张卡
└── 不同来源
    └── 批量发布（各自独立卡）
```

## 合并卡结构（graph-paper 风格）

2026-06-26 验证：公众号·技术洋 Claude Code Skill 清单（4榜）

```
Hero：总标题 + 来源 + 概览统计
Graph Section：四榜节点图（01 必装 / 02 进阶 / 03 自动化 / 04 团队）
Panels：2×2 网格，每个 panel = 一张来源图的内容
Footer：来源署名
```

**关键设计决策**：
- slug 用综合性名称（如 `claude-code-skill清单-full`），不保留单榜 slug
- category/tags 覆盖所有维度
- 四面板网格比 Tab 切换更直观，适合四等分内容
- graph-paper 的方格纹理 + 等宽字体天然适合"研究手册总览"

## 坑点

- **meta.yaml 的 `path`**: 合并后只有一张 HTML，`path: docs/<slug>.html`，不要写多行
- **wiki 同步**: 合并卡只写一张 raw + 一张 concept，与批量发布的 N 张不同
- **先问再合（已纠正）**: 如果用户说"4张图 做成信息卡"且没有风格指定，**不要主动拆成4张**——先问"合并成一张还是分四张"，而不是默认拆散。用户说"发布信息卡"时倾向于出结果。
- **⚠️ 合并卡内容不丢失（2026-06-26 实录）**: 第一版合并卡只放了技能名称，丢失了描述文字（用户原图每条都有描述）。修复：每个 skill-row 必须包含完整四元组 `[名称, 分类标签, 维度, 描述]`，缺一不可。第一次合卡返工教训：描述字段比名称更重要，合并结构必须逐条核对原始图的完整信息。
