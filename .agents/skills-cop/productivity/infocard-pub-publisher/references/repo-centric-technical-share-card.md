# Repo-centric technical-share card workflow

Session note distilled from the CacheCloud publish.

## When a repo URL arrives with a strong user narrative
- Treat the user text as the opening hook and framing thesis.
- Use GitHub API as the verification anchor for stars, forks, license, topics, language, issues, updated time.
- Do not force the page into a pure evidence-card posture; make it a repo-centered technical share.

## Practical layout rule
- Hero / overview: user’s strongest claim in one sentence.
- Right meta stack: repo stats and license.
- Middle sections: what it is / how it works / deployment or usage / why it matters.
- Evidence / source notes: support, not the main story.

## Fact hygiene
- Marketing or “内部扛过” claims need a source label if not directly verified.
- If the repo description and user narration differ, keep the distinction explicit.
- Prefer concise, high-signal facts over long README copy.

## Useful checks
- GitHub API: stars, forks, watchers, license, topics, language, updated.
- README / docs: deployment steps, architecture, supported modes.
- Final page: can a reader understand the project in the first fold without scrolling?
