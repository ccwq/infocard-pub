# 2026-05-30 Qwen3.6-35B 信息卡移动端复盘

## 场景
页面：`docs/20260526-qwen36-35b-local-deploy.html`

用户指出的主问题不是“裁切”或“字号太小”，而是：
- 左右边距过大
- 首屏过松
- 卡片内部留白过多
- 整体像桌面海报/PPT 缩到手机，而不是高密度手机信息卡

## 关键教训

### 1. 移动端验收不能只看“能不能显示”
本次第一轮修复只解决了：
- 根字号过小
- 局部横向溢出风险

但没有解决：
- 左右 padding 仍偏大
- section / title / card spacing 仍偏松
- 首屏信息密度不足

结论：
**手机端信息卡的失败模式不止是裁切和缩放，视觉密度不足同样应判 FAIL / NEEDS WORK。**

### 2. 边距过大需要用 DOM/CSS 指标直接量
本次用户指出“边距过大”后，直接在手机视口下读取：
- `.banner` padding
- `.section` padding
- `.card-grid` gap
- `.card` padding
- `grid-template-columns`

读数帮助快速定位：
- 大左右 padding
- 大 card padding
- 大 gap
- 仍像窄双列的内容宽度

这比仅凭截图印象更可靠。

### 3. 必须区分三层状态
不能把它们混成一句“已经修好了”：

1. **仓库源码已更新**
2. **Pages 返回的 HTML 已更新**
3. **当前浏览器/真机实际渲染已更新**

本次一度出现：
- GitHub main 已是新 CSS
- Pages 源文件也已新
- 但当前浏览器会话仍显示旧样式

说明：
**视觉验收需要把 service worker / 浏览器缓存 / CDN 缓存当成独立环节。**

### 4. 验收语言要严谨
当出现“源码已新，但当前会话仍旧”的情况时，正确结论应是：
- 发布已完成
- 当前验收环境仍被缓存污染
- 不能报 PASS
- 必须要求干净会话/真机复看

错误做法：
- 仅因为代码已 push 就宣称“已修复完成”

## 本次适合的移动端收紧方向
适用于高密度信息卡：
- 压缩左右 padding
- 压缩头图上下 padding
- 压缩 section 上下间距
- 压缩 title 与 card 之间的 margin
- 压缩 card gap 和 card padding
- 必要时把窄双列改成单列，优先保证内容宽度和首屏密度

## 建议的复验顺序
1. 看用户真机截图，先判断主诉是裁切、字号还是“过松”
2. 在 390px 下读取 CSS 指标，不要只靠肉眼
3. 修改移动端 spacing，而不是只改 font-size
4. 核对 raw / GitHub Pages HTML 是否已更新
5. 若当前浏览器仍旧，排查 service worker / 缓存
6. 只在干净会话或真机截图通过后，才给 PASS
