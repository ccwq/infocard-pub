## X / Twitter tool-list posts
When the source is a tool list or resource roundup, do *not* stop at naming tools.
Always add:
- **Visible replies / comments summary**: pull 1–3 representative replies when the page exposes them.
- **Per-tool micro-notes**: for each tool, include:
  - original post’s role for it
  - best-fit use case
  - one concrete thing to watch or verify
- **Workflow bundles**: regroup long tool lists into 3–4 practical stacks (e.g. zero-budget test, dialogue flow, creative visual flow).
- **Conclusion line**: turn the card into a decision aid (“best to try first”, “how to combine them”), not a bare directory.

## GitHub repo cards
When the source is a repository landing page / README, extract the structure in this order:
1. **One-line positioning** from the hero / opening paragraph.
2. **Core modules / pillars** from README headings.
3. **Quick start** prerequisites and first-run path.
4. **Differentiators**: what makes it distinct from adjacent tools.
5. **Boundary / non-goals**: what it is *not* trying to be.
6. **Verification hints**: health checks, example commands, or benchmark sections.

Good repo cards usually read like:
- what it is
- who it is for
- how to start
- what makes it different
- where the edge cases are
