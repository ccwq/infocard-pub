# 发布验证与厚卡扩写闭环

这份参考文件记录了本次会话中反复出现、且对后续信息卡交付有价值的两个经验：**薄卡扩写** 与 **发布后验证**。

## 触发条件
当用户出现以下任一表述时，默认使用本清单：
- “内容太单薄”“信息匮乏”“再充实一点”“扩到 3 倍”
- “提交和验证”“直接提交”“给我线上地址截图”“我不信你传上去了”
- 调查卡、澄清卡、风险解释卡、舆情核查卡需要发布到 infocard-pub

## 厚卡扩写顺序
优先按以下顺序补厚，而不是只把结论段拉长：
1. **背景/起点**：这件事最早从哪来，为什么会被讨论。
2. **时间线**：按关键日期串起演变，不只写一句结论。
3. **概念拆分**：把术语、监管分工、风险/危害、分类/结论拆开。
4. **证据矩阵**：把已证实、部分存疑、不能推出分层。
5. **常见误读**：列出最容易被误传的 3–5 种版本。
6. **实用判断**：给普通人可复述的说法。
7. **下一步补查**：告诉用户后续还能补什么，而不是只停在摘要。

## 发布验证闭环
当任务涉及“提交 / 发布 / 写文件 / 上线”时，必须在报告完成前做完以下验证：
- **本地写入**：确认文件确实被改写
- **提交成功**：确认 git commit 或等价提交已生成
- **推送成功**：确认远端接收到了提交
- **线上可访问**：直接打开公开 URL，不只看本地文件
- **索引命中**：如果是 infocard-pub，确认 `_index.yaml` / 首页列表真的包含 slug
- **截图验收**：必要时截取线上页面，确认标题、正文、按钮、排版都已呈现

## 常见坑
- **本地成功 ≠ 线上成功**：文件写了不代表部署到了公开地址。
- **提交成功 ≠ 首页可见**：可能还没触发索引更新或页面部署。
- **首页数量不对**：先区分缓存、索引未同步、或部署延迟，再下结论。
- **不能只说“已完成”**：如果没有实际验证，就不要向用户报告完成。

## 简短原则
> 先写厚，再验证；先验真，再汇报。
