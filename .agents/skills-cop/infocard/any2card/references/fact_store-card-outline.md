# fact_store 信息卡内容构造参考

本文件记录一类常见的技术产品介绍卡结构：**工具/能力类信息卡**。适用于像 fact_store、memory provider、CLI 工具、插件系统、API 能力等“让用户快速上手”的内容。

## 推荐结构

### 1. 开头：一句话定义
- 先说明“它是什么”
- 再说明“它解决什么问题”
- 不要上来就讲细节

示例结构：
- fact_store 是什么
- 它和 memory / session_search 的区别
- 它最适合存什么

### 2. 常用工作流
按“用户最先会怎么用”排序，而不是按 API 文档顺序排序。
常见四段：
- 先记住，再验证
- 先 probe，再扩展
- 先 search，再整理
- 冲突出现时用 contradict

### 3. 使用技巧
把“会用”和“用得顺”区分开。
建议覆盖：
- 如何写更好的事实
- 如何节省空间
- 如何用 entity 组织
- 如何处理冲突与过期信息
- 如何用 trust / feedback 逐步提高质量

### 4. 能力全景
需要把工具的子能力全部列出来，并给出一行用途。
对于 fact_store，至少要解释：
- add
- search
- probe
- related
- reason
- contradict
- update
- remove
- list
- fact_feedback

### 5. 场景与例子
给 3-4 个真实场景：
- 用户偏好
- 环境事实
- 工具 workaround
- 项目约定

再给最小上手命令或对话示例。

### 6. 一句话总结
用一句话帮助用户形成心智模型：
- memory 记上下文
- fact_store 记结构化真相
- session_search 记历史

## 视觉组织建议

- 适合高信息密度的单栏结构
- 标题区先定义对象，再用分隔线进入正文
- “常用工作流 / 技巧 / 能力全景 / 场景例子”四段是最稳的骨架
- 如果内容偏工具说明，优先技术简报或文档扫描风格；如果要更有冲击力，可以切瑞士红黑

## 常见坑

- 只讲 API 名字，不讲用户会怎么用
- 只列能力，不列工作流
- 内容太像 README，读者看完不知道先做什么
- 把临时验证步骤写成长期规则
