# X 技术观点/论证帖信息卡扩写阶梯

## 触发条件

当输入是 X/Twitter 上的一篇**密集技术观点帖**（非工具清单、非热点快评、非转发引用），且：
- 帖子有清晰的论证推进线（提出分水岭 → 展开演进 → 剖析工程差异 → 给出趋势判断）
- 帖子包含多个可区分的概念层次（不仅是一个观点反复说）
- 发帖者以"我系统的梳理了相关的内容"之类的自述开头

## 一刀规则

**不要按"要点 4-6 条"标准来压缩。** 论证帖的提炼目标不是"用最短的话概括结论"，而是"保留推理结构的可读提炼"。

## 检查清单（生成前过一遍）

- [ ] 原文的论证起点是否保留（它从哪里开始推理？）
- [ ] 原文的演进/分类框架是否保留（它是怎么组织信息的？）
- [ ] 原文的关键区分是否保留（Async vs sync 的分水岭是什么？）
- [ ] 原文的精确措辞是否保留（不是替换成近似词）
- [ ] 每个链接的名称+完整URL是否在引用处内联显示
- [ ] 配图是否放在标题/stats之后的显要位置
- [ ] 每章内容是否≥3层（角色/判断/连接）
- [ ] Quote Block 是否承载了作者观点

### 初版失败模式
初始卡把原文压缩为：
- 6 节结构、每节 1-2 行
- 链接沉底在尾部统一列出
- 丢失了原文中"用异步的方式"/"可管理资产"等精确措辞
- 演进路径被简化为 4 行列表，丢失了各阶段的特征描述
- Control Plane 问题被合并进"核心架构组件"，失去独立性
- 用户反馈："内容有些薄弱"

### 扩写版修复方式
1. 将 Control Plane 从"架构组件"中拆出独立成章
2. 每阶段演进增加典型形态描述（Copilot 行级建议 → Tool Agent 上下文释放 → Coding Agent 云端隔离环境 → Async Agent 生命周期托管）
3. 恢复原文措辞："用异步的方式"、"可管理资产"、"局部先验不足"、"可隔离可销毁可复现的手"
4. 添加 Context 管理引用块（原文整段话的精确引用）
5. 链接内联到对应章节：arxiv 论文链接嵌入"为什么 Async Agent 会成为趋势"章节
6. 原文金句以独立 Quote Block 呈现（2 条结尾金句 + 1 条 Context 管理引用）
7. 章节数量从 6 增加到 7，每节内容厚度从 1-2 行增加到 2-4 段

### 验收标准
用户未再反馈薄弱问题，说明扩写方向正确。

## 扩写优先序（当用户反馈"薄弱"/"内容不够"时）

1. **结构补齐** — 检查是否丢失了论证环节。技术观点帖通常有：分水岭定义 → 演进历史 → 对比分析 → 架构拆解 → 工程建议 → 趋势判断。缺了哪个补哪个，不要只往现有节里堆文字。
2. **措辞恢复** — 检查原文精确表述是否被替换成了泛化版本。恢复原文用词，如"局部先验不足"比"knowledge 很重要"携带更多信息。
3. **分层展开** — 检查每节是否只有一层。每节应有：原文判断 + 展开解释 + 与上下文的连接 +（如适用）引用链接。
4. **Quote Block 嵌入** — 原文中携带核心判断的完整语句应以引用块形式呈现，不重述。
5. **链接内联** — 链接不应作为"附录"沉底，应嵌入到引用的章节内。
