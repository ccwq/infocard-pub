# GitHub Role-Library Repo Card Pattern

Session note: use this pattern when the input repo is a **team/agent/role library** rather than a single tool.

## Core framing
- Treat the repo as an **AI agency operating system**.
- Title strategy should lead with the **organizational promise**, not the repo name.
- The most useful angle is: **who the roles are, what they do, and how they are installed/activated**.

## What to surface first
1. One-sentence repo promise from README.
2. The highest-signal role families / divisions.
3. 3-6 representative roles spanning different functions.
4. Installation / activation path.
5. Where the role files live and how they are grouped.

## Role selection heuristic
Pick roles that cover distinct organizational functions, for example:
- execution / build
- review / QA
- incident / reliability
- design / brand
- security / intelligence
- growth / marketing

Avoid filling the card with too many adjacent roles from the same family.

## Layout guidance
- Use a **team diagram / division map** as the hero visual.
- Then split the body into:
  - core positioning
  - representative roles
  - when to use / when not to use
  - minimum install / activation path
- Keep role blurbs concrete: **role + specialty + typical output**.

## Pitfalls
- Do not reduce the repo to a generic “prompt pack”.
- Do not list every file equally; organize by division and use case.
- Do not let the card become a directory page; the reader should leave knowing how to turn the repo into a working team.
