# Long-form engineering guide card pattern

Use this pattern when the source is a **long-form engineering guide** about coding agents, workflows, runtime mechanics, or agentic engineering.

## When to use
- The source is a tutorial, guide, or essay about how to use coding agents well.
- The article is structured around recurring engineering layers rather than a single product pitch.
- The strongest value is the workflow spine, not a single novelty claim.

## Default routing
- Prefer **hardblue** for technical guides on agent workflows, Git, testing, and browser QA.
- Use a red-black investigation frame only when the source is an incident, rebuttal, or adversarial investigation.
- Use Q-style only when the content is a broad framework/course/knowledge map with many sections and learning paths.

## Recommended section spine
1. Principles
2. Working with agents / runtime mechanics
3. Git and subagents
4. Testing and QA
5. Appendix / prompts / artifacts

## Title strategy
- Convert the article into a **conclusion title**, not a source-title clone.
- The title should say what the guide teaches the reader to do.

## Pitfalls
- Do not compress the guide into 4–6 isolated bullets; preserve the workflow sequence.
- Do not treat a workflow guide like a repo card just because it references tools and code.
- Do not flatten the guide into a quote card; the section structure is part of the signal.

## Verification cues
- The card should visibly expose the workflow spine on the first read.
- The first screen should make the engineering loop legible before the details.
- Section headings should map to the source outline rather than inventing a new narrative.
