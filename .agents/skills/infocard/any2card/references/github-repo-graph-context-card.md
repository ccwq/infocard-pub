# GitHub 仓库技术分享卡：local-first graph context / 证据层模式

适用仓库：把代码仓库、符号、调用、导入、变量流等索引成图，再通过 MCP / dashboard / viewer 给 AI 代理做“先取证据、后生成”的项目。

## 叙事主轴

- 不要把它写成普通搜索工具；核心表述应是 **local-first evidence layer / context service**。
- 一句话结论优先：它解决的是“上下文太散、token 太贵、关系不清”，不是“再做一个索引器”。
- 标题应突出“把仓库图谱变成 AI 编码的局部证据层”这类结果型表达，而不是仓库名本身。

## 首屏要素

1. 一句话判断。
2. 2–4 个关键收益：关系路径、局部摘录、MCP 取证、图谱浏览。
3. 1 张首屏代表图：优先仓库官方 graph viewer / dashboard 截图，必要时本地化后再引用。
4. 1 句边界：local-first、需要图数据库 / 本地运维，不是通用搜索框。

## 推荐章节顺序

- 核心判断 / 核心定位
- 为什么需要它
- 架构总览（repo → graph DB → MCP tools → agent）
- 你实际能拿到什么（dashboard / viewer / API / relay）
- Benchmark 证据（必须写 nuanace：平均收益 + 个别反例/边界）
- 快速上手
- 适用边界
- 资源与来源

## Benchmark 书写规则

- 保留原始数值和样本数。
- 用“平均值 + 边界”讲，不要把结果写成无条件胜利。
- 如果 README 明确提到个别项目在保守上下文下表现变差，要在卡片里保留这一句。
- 结论要表达“平均收益明显，但不是所有项目都自动变好”。

## 资产处理

- repo hero / UI 截图优先本地化后引用，避免热链失效。
- 以官方 README / benchmark / docs 为主，截图只负责证明产品形态，不替代文字证据。

## 适用场景提示

- 适合 AI-assisted development、代码审查、仓库问答、符号定位、依赖追踪。
- 不适合被写成“万能搜索引擎”或“全仓库暴力投喂器”。
