# X 多帖批量信息卡：插入 / 引用 / 配图融入

适用场景：用户一次给多条 X/Twitter 链接，要求“依次创建高信息容量/高密度信息卡并发布”，并补充“把插入融入信息卡”。

## 核心规则

1. **逐条成卡，不合并主题**
   - 每条 X status 默认独立成卡。
   - 即使同属 GitHub / Agent 主题，也不要把多个 status 合成一张总览卡，除非用户明确要求合集卡。

2. **“插入”优先理解为 quoted / embedded / attached content**
   - 如果 vxtwitter 返回 `qrt` / `qrtURL`，把被引用帖作为背景层、对照层或“引用帖融入”章节写入卡内。
   - 如果 status 带 `mediaURLs`，配图不是装饰：应作为证据层融入信息结构，放在 stats 后的显要位置，并在正文中解释图片贡献了什么信息。
   - 如果原帖正文被截断而图片包含主要内容，明确标注“正文接口截断，完整信息在配图中”，不要凭空补缺失正文。

3. **高密度卡不是链接复刻**
   - 工具/仓库清单帖：提炼成“用途定位 + 首试顺序 + 工作流分组 + 边界”。
   - 技术观点帖：保留论证链条，不压成孤立要点。
   - 多图帖：每张图都要有“这张图提供了什么证据/结构”的说明，而不是只把图片贴进去。

4. **不虚构缺失项**
   - 如果 API 只返回部分正文，且图片也无法确认剩余仓库/链接，写“未完整取得”，不要补造所谓 10 个仓库。
   - 可从图片 OCR/视觉分析提取可见系统、模块、流程，但要区分“可见内容”与“推断补充”。

## 交付结构建议

每张卡建议包含：
- 首屏：结论标题 + 原帖作者/互动数据 + 发布时区转换后的时间
- 证据区：原帖配图 / 引用帖 / 链接预览本地化图片
- 主体区：3–6 个高密度章节，按“是什么 → 怎么用 → 为什么重要 → 边界”组织
- 来源区：原 status URL、引用 status URL、图片本地化说明

## 发布注意

批量发布时不要用一个超长 shell 命令同时完成“写文件 + 复制素材 + 重建索引 + commit + push”。更稳的做法：
1. 先生成/写入每张卡和 sidecar。
2. 再统一运行 `python3 scripts/rebuild_index.py && python3 scripts/verify_index.py`。
3. 本地验收后再 commit/push。
4. Pages 验证每个详情 URL 和首页索引。
