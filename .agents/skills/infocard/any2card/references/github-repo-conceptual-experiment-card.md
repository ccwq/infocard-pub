# GitHub 仓库“概念实验”卡模式

## 适用场景

当仓库看起来像“工具”但 README 的真实表达方式更像：
- 数学梗 / 反讽命题 / 概念实验
- 证明一个极限想法可挂载、可执行、可编译
- 核心价值在叙事与系统边界，而不是日常实用性

例如：把文件映射到 π、把不存在的空间当地址层、把抽象命题工程化。

## 卡片写法

1. **标题要先给结论，再给概念**
   - 先说它“到底在做什么机制”
   - 再点出它“为什么像一个概念实验”

2. **核心定位要分成两层**
   - 表层：README 里那个最响亮的主张
   - 深层：真正可运行的系统部件（FUSE / parser / runtime / generator / metadata）

3. **正文必须回答三个问题**
   - 它靠什么机制成立？
   - 它的概念前提是什么？
   - 为什么说它更像实验，而不是常规产品？

4. **优先抓实现文件，而不是只读 README**
   - README 负责讲故事
   - `src/` / `INSTALL` / `configure.ac` 负责告诉你故事怎么落地
   - 如果 README 的说法很夸张，优先用源码部件校准边界

5. **结论要把“可用性”和“趣味性”分开**
   - 可能很好玩
   - 可能可运行
   - 但不一定适合当通用工具

## 常见标题模板

- `X：把 A 映射到 B 的 C 实验`
- `X：用 Y 做 Z 的概念工程`
- `X：真正可运行的概念梗`

## 参考案例

- `philipl/pifs`：把文件映射到 π 的 FUSE 实验
- `README` 口号很强，但机制层是 FUSE + 元数据目录 + BBP 位生成器
- 这类卡应把“概念命题”与“实现部件”并置，而不是只写成工具介绍
