# 信息卡发布泄漏检查误报修复记录

## 问题现象

`check-info-leak.js` 的中文手机号正则 `/(\+?86)?[1][3-9]\d{9}/g` 会匹配 URL 中的长数字串。

**典型误报案例**：X 帖子链接中的 post ID（如 `2078318406424793326`）包含子串 `18406424793`，恰好符合手机号格式（1开头+后续9位数字），被标记为 `[HIGH]` 泄漏。

## 根因

正则扫描整个文本内容，不区分数字出现在：
- 普通正文 → 可能是手机号（应检）
- URL 路径/参数（如 `/status/2078318406424793326`）→ 是 ID，不是手机号（误报）

`urlContextExclude` 检查的是**匹配值本身**（固定 11 位），无法排除 URL 路径中的超长数字串。

## 修复方案

**方案 A（推荐）**：在 HTML/文章中，将 X 帖子链接改为纯展示文本，不含完整 URL 数字串。

```html
<!-- 修复前（误报） -->
<a href="https://x.com/i/status/2078318406424793326">x.com/i/status/2078318406424793326</a>

<!-- 修复后（正常） -->
<span style="color:var(--blue)">源帖链接（X 站内访问）</span>
```

**方案 B（脚本级修复）**：在 leak checker 中增加 URL 路径排除规则——将包含 `/status/`、`photo/` 等 X 典型路径模式的数字串加入排除列表。但当前 `urlContextExclude` 实现不支持上下文感知排除，需重构正则逻辑。

## 经验

- 涉及长数字 ID（微博 CID、X post ID、GitHub number 等）的信息卡，优先使用方案 A
- 此问题会在每次出现 X/微博链接时复现，直到 leak checker 重构上下文感知逻辑
- 2026-07-19 实测：`check-info-leak.js` v1 对 16+ 位数字串无防护
