# 三轮决策树示例：时间戳工具链设计（2026-07-11）

## 背景问题

meta.yaml 时间戳（date/updated）被写了两次，第一次是 agent2 伪造的裸日期，第二次是主线程以"build 校验"的名义覆盖。用户问"为什么修了两次"，经调查是 SOP 流程缺口。

## 对齐过程（三轮）

**用户问题**：调查为什么时间问题修复了 2 次，并进行多轮 grill-me 对齐，次数不大于 3。

### 第一轮

| 选项 | 描述 |
|------|------|
| A | agent2 必须正确写入；主线程只验证，错误则退回 agent2 |
| B | agent2 必须写入；主线程可修复这类机械格式错误后继续发布 |
| C | 由 build 脚本自动回填所有 date/updated，agent2 不负责时间戳 |

**推荐：B**。时间戳是机械的发布元数据；agent2 应负责首次写对，主线程发现格式错误时做最小修复不退回整卡。

**用户选：C**（build 脚本自动回填，agent2 不写时间戳）

---

### 第二轮

| 选项 | 描述 |
|------|------|
| A | build 开始时刻：HTML/meta 已完成，索引生成前回填 |
| B | commit 时刻：提交后再回填并产生一次补充提交 |
| C | push 后公网 200 时刻：最接近"实际发布完成"，但需二次提交 |

**推荐：A**。同一发布 bundle 内一次生成、一次提交，避免为时间本身制造二次 commit 或推送。

**用户选：A**（build 开始时刻）

---

### 第三轮

| 选项 | 描述 |
|------|------|
| A | 每次 build 都同时覆盖 date 和 updated 为本次 build 时刻 |
| B | 新卡：date = updated = build 时刻；既有卡修改：保留原 date，仅更新 updated |
| C | 既有卡完全不改时间；只有新卡自动写入两个字段 |

**推荐：B**。date 保留首次发布时点，updated 反映本次重建或内容更新；不会把历史卡伪装成新发布。

**用户选：B**（新卡全写，既有卡只更新 updated）

---

## 最终决策

| 场景 | date | updated | 写入者 |
|------|------|---------|--------|
| 新卡 | build 开始时刻（Asia/Shanghai） | 同 date | 工具链自动回填 |
| 已有卡更新 | 保留原首次发布时间 | 本次 build 时刻 | 工具链自动回填 |
| agent2 | 不写 | 不写 | 禁止写入 |

## 关键原则

1. **三轮上限**：无论用户多想要更深的讨论，达到 3 轮后停止并总结剩余未知量 + 推荐默认值。
2. **每轮只问一件事**：不把多个分支合并成一个选项题。
3. **推荐答案**：每个问题都附带推荐答案，用户选 A/B/C 后再进入下一轮。
4. **终止条件**：三轮后若仍有分歧，停止追问，直接总结当前状态和推荐方案。
