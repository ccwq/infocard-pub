# 前端组件库基准调查笔记

> 用于 Vue / React / 其他前端组件库的选型对比、发布报告与信息卡。目标是把“口碑感受”压缩成可核查证据链，而不是只看单一指标。

## 推荐证据链

1. **活跃度门槛**
   - 先过滤最近 3 个月没有更新的仓库。
   - 若仓库长期无更新，不纳入“最新可选项”。

2. **GitHub 公开页优先**
   - 当 GitHub API 限流 / 403 时，改用仓库公开 HTML 页面读取：
     - stars / social count
     - latest push / relative time
     - release / tag 入口是否仍可见
   - 公开页足以支撑多数选型结论，不必被 API 阻断。

3. **源码目录规模**
   - 组件数量采用“源码一级组件目录数”口径，便于横向比较。
   - Vue 组件库常见口径：
     - 以 `packages/components/*` 作为组件池
     - 若仓库结构不同，则用最稳定的组件根目录做一级目录统计
   - 记录统计口径，避免不同仓库混用“导出数 / 文件数 / 组件目录数”。

4. **近一年提交数**
   - 用 shallow clone 后的 git log 统计近 1 年提交数。
   - 这是比“最近一次 push”更能反映工程持续投入的指标。

5. **npm 采用度**
   - 读取 npm registry 的周下载量或类似可公开的采用指标。
   - 对于不同包名，先核对官方包名再查询，避免旧包名 404。

6. **社区评价的合成口径**
   - 不把 star 数当作唯一结论。
   - 建议合成：
     - stars（曝光/关注度）
     - 近一年提交数（维护活跃）
     - 组件目录数（能力覆盖面）
     - npm 周下载（真实采用度）
   - 最终结论应写成“适合什么场景”，而不是“谁一定更好”。

## Vue 组件库对比时的常用结论模板

- **中文后台默认项**：文档、案例、生态和交付稳定性优先。
- **设计系统感**：视觉一致性、交互打磨、品牌气质优先。
- **开发体验**：组件 API、类型体验、源码可读性优先。
- **企业标准化**：统一规范、工程治理、配套能力优先。
- **移动端 / H5**：轻量、触控体验、移动端适配优先。
- **国际化 / 大组件池**：多语言、场景覆盖、生态成熟度优先。

## 经验坑点

- GitHub API 403 不等于数据拿不到；优先切换到网页 HTML / clone / registry。
- 组件数量不要拿“导出名列表”凑数，容易失真；尽量统计源码一级组件目录。
- 近一年提交数要和“最近更新”一起看：一个看持续投入，一个看是否还活跃。
- npm 下载量会受包名口径影响，先确认官方包名。
- 最终报告要把“数据表”翻译成“选型建议”，否则读者只会看到一堆数字。

## 交付建议

- 报告正文写清：筛选条件、数据口径、结论和边界。
- 信息卡突出：主结论、关键对比项、推荐场景、风险提示。
- 如需发布信息卡，和 `report.md` 一起放入同一 slug 目录，再走 `rebuild_index.py` + `verify_index.py`。
- 发布后做 390px 视口验收，确认无横向溢出、无按钮遮挡、字号可读。
