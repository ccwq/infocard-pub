# Website card: DOM-first public-source pattern

适用：用户给的是公开网站 URL（不是 GitHub repo），但要求直接发布 infocard。

## 目标

只基于**公开可见信号**写卡，避免把前端页面猜成后端架构说明。

## 采集优先级

1. 页面 HTML / meta
   - `title`
   - `description`
   - `canonical`
   - `og:*`
   - `twitter:*`
   - `structured data`
   - `hreflang`
   - generator / framework 信号（如 Astro / Next.js）
2. 首屏可见交互
   - 导航
   - 搜索框
   - 播放/分页/过滤/排序/语言切换等控件
3. 可见信息结构
   - 分类组
   - 路由/条目数量
   - 文案层级
   - 是否是单页交互壳 / 内容站 / 文档站 / 目录站
4. 配套公开页面
   - `/es/` 等多语言入口
   - `robots.txt`
   - sitemap
   - 公开 manifest（若存在）

## 写卡原则

- 先写**用户看得见的产品结构**，再写技术信号。
- 可以写“首页公开 DOM 可见 40 条路由 / 有搜索 / 有播放控件 / 有 EN/ES 切换”。
- 可以写“页面 meta 暴露 Astro / structured data / WebApplication”。
- **不要**从前端页面反推出不存在的后端模块、数据库、私有服务或仓库结构。
- 如果某一层只是推断，必须标成“从可见路由集合推断”或“公开信号显示”。
- 如果 manifest / API / repo 不可见，就不要编造其能力。

## 推荐叙事

对网站卡，优先回答：
1. 这是什么产品 / 站点
2. 用户在首屏能做什么
3. 信息是如何被组织的
4. 交互节奏如何帮助理解内容
5. 可访问性 / SEO / 多语言这些“产品化信号”说明了什么

## 常见误判

### 误判 1：把网站卡写成仓库卡

症状：开始谈 repo 目录、脚本、CI、源码模块，但用户给的只有网站 URL。

修正：收回到 DOM / meta / 可见路由 / 可见控件 / 公开语言结构。

### 误判 2：把前端信号写成后端事实

症状：看到播放器控件就写“状态机后端”“数据服务层”“任务调度系统”。

修正：只写“页面表现出可播放/步进/搜索/切换的交互面”，除非有公开源码或官方文档支撑。

### 误判 3：把不存在的资源写成功能

症状：`site.webmanifest` 404，仍然宣称完整 PWA 能力。

修正：报告实际可见结果；404 就写“当前公开 manifest 不可取到”，不要继续放大。
