# 技术分享类信息卡的富内容写法（PPT Master 例）

这份参考总结了一个“技术分享 + GitHub 仓库 + 第三方资料”组合卡的稳定写法。

## 适用场景

- 用户提供 GitHub 仓库，要求“使用技术分享的风格”
- 内容是工具、工作流、自动化、办公效率、AI 编排、文档转换等
- 用户希望“内容丰富”，可以引用第三方平台做辅助补充

## 推荐主题选择

- **蓝色技术手册**：适合 PPT、Office、文档工作流、教程、工程化工具说明
- **main-style**：适合通用开源工具总览、偏瑞士密度的 repo 图鉴
- **darkblue**：适合 agent 控制台、并行工作台、桌面编排、运行面板

当内容是“文档 → PPT / 办公自动化 / 演示文稿工作流”时，优先选蓝色技术手册，而不是默认红黑瑞士风。

## 结构模板

1. 一句话结论：先给判断，不铺垫历史
2. 为什么值得看：用 2-4 条讲清价值
3. 能力清单：输入 / 输出 / 工作流 / 预览 / 导出
4. 工作流拆解：用步骤或流程图说清楚怎么跑
5. 适合谁 / 不适合谁：帮助读者快速自我判断
6. 第三方信号：社区文章、教程、版本更新，作为补充证据
7. 示例画廊 / 截图：如果仓库自带示例图，优先本地化嵌入
8. 来源：GitHub README + 文档 + 社区文章链接

## 内容写法

- **结论置顶**，不要先写项目背景
- **过程最少化**，但内容要丰富，重点放在能力、工作流和适用场景
- **全部正文中文优先**，英文只保留必要的专名、命令名和链接
- 第三方内容只做“补强”，不要喧宾夺主
- 如果仓库有示例图，优先下载本地化嵌入，而不是只贴外链
- 如果有社区教程或 release，补充到“第三方信号”一节

## 检查点

- 首屏是否已经给出一句话判断
- 是否说明了“它到底解决什么问题”
- 是否把工作流拆开讲，而不是只讲卖点
- 是否有第三方证据，而不是只靠 README
- 是否本地化了示例图并在卡片内展示
- 是否保留中文正文优先
